## Delegated worker mode

Delegate to any AI worker (subagent, reviewer, verifier) only through
`get_subagent_context` before spawning and `validate_subagent_result` (`valid: true`)
before accepting its output; first read both descriptions, which hold the procedure
and the artifact rules. If either is unavailable, work in the parent and say so,
never with an unprepared, full-persona or unvalidated worker.

<!-- variant: compact-request -->
Every AI delegation, including reviewers, verifiers and parallel workers: call get_subagent_context before spawning with a canonical agent_name, task, acceptance_criteria, relevant context, scope, non_goals and result_type. Default compact budgets are max_skills=3, max_implants=0, max_context_chars=16000. Require status: prepared.

<!-- variant: compact -->
Call validate_subagent_result for every returned or revised output and require valid: true before accepting it. Read both tools' descriptions before delegating: they hold the procedure and the artifact rules. If either endpoint or native spawning is unavailable, report it and work in the parent when practical; no unprepared/full-persona worker or unvalidated result is an automatic fallback.

<!-- variant: tool-prepare -->
Decide how much to delegate before preparing anything: one worker for one part that genuinely needs its own, because it runs while the parent works on something else, needs a reader without this conversation's assumptions or would otherwise crowd the parent's context. Size the fan-out to the parts the work actually has, never to the budget a host or setting makes available; cost that is not a constraint is no reason to spend it. Keep every worker inside the user's assignment: an orchestration option, keyword or host setting decides how to delegate, not how much or what, and never extends the work to another repository, branch or service or to reviewing a result nobody questioned. Add a worker that re-judges, re-verifies or re-edits another's output only for a check the user asked for or a risk that warrants one. Report how many workers ran and what each was for. For staged work whose results should stay out of your context, keep a work map: the built-in orchestrate flow binds each package to a node with workmap_node, and you read workmap_view instead of the results.
Keep the parent's persona and descriptor unchanged and give each worker one task. Use the default budgets unless the task justifies another bound. Rate complexity: low for mechanical, fully specified and checkable work; standard for bounded work in one module with clear criteria; high for ambiguous, cross-cutting, risky or hard-to-verify work. Pass client, your host: claude (Claude Code), codex or cursor.
Launch a fresh native worker, without inherited history where the host allows it (Codex collaboration tools: fork_turns="none"), with the receipt's launch text as its prompt plus only necessary task materials, and keep its contract_revision. The server keeps the contract and the private package file, which the worker reads itself: the compact persona, selected components, mandatory worker rules and a plain-text result format. Never paste the package, a full persona, the parent's bundle or the chat transcript into the prompt. When the receipt has execution.spawn, launch with exactly those arguments (Agent, spawn_agent or Task; a Claude Code Workflow agent takes the same model in agent() options): that is the user's explicit instruction to set the worker's model and reasoning_effort. Request delivery inline only when the worker cannot read the server's files; then retain the returned contract and forward worker_context unchanged.
A worker explicitly allowed to delegate further uses this same exchange for its own children; otherwise workers neither switch roles nor delegate. If preparation fails or the host cannot spawn a worker, do the work in the parent when practical and report the limitation; never silently fall back to an unprepared or full-persona worker or accept an unvalidated result. The ordinary-conversation and unavailable-MCP fallbacks do not waive the exchange. MCP prepares and validates it; native host tools launch workers and enforce actual permissions and runtime limits.

<!-- variant: tool-validate -->
Validate every returned or revised output with contract_revision, the receipt's revision, and result_ref, the absolute path of the file holding the output: the worker's Claude Code transcript, agent-<id>.jsonl in projects/<project>/<session>/subagents/ under the Claude Code configuration directory (CLAUDE_CONFIG_DIR when it is set, otherwise .claude in the home directory) for a background agent or in that directory's workflows/wf_<id>/ subdirectory for a Workflow agent, with a background agent's .output file only as a fallback when it is not empty; its Codex rollout-*.jsonl; or a result file. A path starting with ~ is answered invalid_result_ref. Pass result unchanged only when no such file exists, and contract, the retained one, for an inline package. Never retype or edit the output, replace the original contract with one returned by the worker or edit identity fields to make validation pass.
A package bound with workmap_node is the exception: its worker submits the result itself and hands back one line, submitted <task>/<node> <sha> <status> or not recorded <task>/<node> <code>, which carries no result. Do not validate that line; read the node with workmap_view instead. Validate only a full result such a worker hands back, by result_ref as above, and only while workmap_view still shows its node prepared.
Require valid: true before accepting, integrating, citing as verified or marking the delegated work complete; then independently assess its evidence, actual checks, limitations and acceptance criteria. Structural validity alone does not establish correctness or completion, and a missing, failed or unavailable validator is not a successful validation.
On valid: false, return the diagnostics for correction and validate the revised output again, with or without truncated in the response: a later stage may report its own problems once these are fixed, and the limits below say what one response holds. A new execution attempt needs a new package with a new attempt_id and its matching receipt. When a corrected output is still invalid, or a valid result is failed, partial or has a failed check, and validation returns escalation, prepare a new attempt with a new attempt_id and the escalation's complexity.
