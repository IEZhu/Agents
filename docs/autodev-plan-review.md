# Autodev plan: review findings and decisions

Three review rounds of [autodev-plan.md](autodev-plan.md) on 2026-10-12. Every reviewer was prepared with `get_subagent_context` (protocol `agents-core/subagent/1`, result type `review`) and run as a fresh Workflow worker with its `worker_context` unchanged; every result passed `validate_subagent_result` with `valid: true`. Validation is structural; the decisions record the parent's own assessment. Locations refer to the version each round reviewed; the last column points to the version that applied the decision (round 3: version 5), which also reflects the owner's answer 'no' to question 6 (no dedicated macOS user or GitHub account).

The reviewed versions were Russian drafts that are not in the repository. Quotations from them, and the wording the reviewers proposed for them, are given here in English translation; line numbers still refer to those drafts.

Decisions: **Accepted** (applied), **Partly accepted** (applied with a stated change), **Superseded** (the design element was removed or replaced), **Moot** (removed by the owner's decision to schedule locally, without cloud runs).

- Round 1 (7 reviewers, version 1): Accepted 78, Moot 1, Partly accepted 9, Superseded 7 (95 findings).
- Round 2 (4 reviewers, version 2): Accepted 52, Partly accepted 4 (56 findings).
- Round 3 (1 security reviewer, version 4): Accepted 14, Partly accepted 1 (15 findings).

## Security (security_expert)

**Summary:** The design copies the issue agent's written defenses: the owner's login and numeric ID, the rule that external text is data, reading instructions from origin/main, and no-merge. It does not copy the mechanisms that make those defenses hold, and it treats the owner identity as a trust boundary even though every agent writes under that identity. Four checks this turn confirm this. First, main on IEZhu/Agents has no branch protection and no rulesets. Second, labels added by the cloud issue agent show the same actor (WonderMr, ID 5370211) as the owner's manual labels; only performed_via_github_app differs. Third, the issue-agent bridge does not check that field. Fourth, run_flow serves a cached installation snapshot, resolves a bare flow ID as repo: before user: before builtin:, and the session can call save_flow and set_flow_persona. As a result, the controls in pre-mortem rows 1, 3 and 11 do not hold as written. Section 11 has no row for: - the shared owner identity, which hides who actually acted; - an agent starting the issue agent through /agent comments; - forged state comments; - side effects of a tick that happen before any merge; - the blast radius of the local runner. The routine cannot edit its own saved prompt, because RemoteTrigger is not in its tool list (section 10.1, not verified in a live session).
