Сначала поправлю свой прошлый ответ: я написал «в том же запросе», но это неверно. `selectinload` делает **два** запроса: сначала заказы, потом все items одним `SELECT ... WHERE order_id IN (...)`. Одним запросом через JOIN работает как раз `joinedload`.

**Почему в вашем случае лучше `selectinload`**

- **Связь one-to-many.** `joinedload` на коллекции делает `LEFT OUTER JOIN`, и данные каждого заказа повторяются в каждой строке его items. При ~300 заказах по несколько позиций это сотни или тысячи строк с одинаковыми колонками `orders`. Всё это приходится передать по сети и разобрать в ORM. `selectinload` возвращает каждый заказ один раз и каждый item один раз.
- **Не нужен `.unique()`.** В SQLAlchemy 2.0 при `joinedload` на коллекцию нужно вызывать `result.unique().scalars()`, иначе будет ошибка. С `selectinload` этого делать не нужно.
- **Пагинация.** Если позже добавите `LIMIT`/`OFFSET` к заказам, с `joinedload` лимит применится к строкам JOIN, а не к заказам. SQLAlchemy обходит это через подзапрос, и SQL становится сложнее. С `selectinload` такой проблемы нет.
- **Когда `joinedload` лучше:** для many-to-one или one-to-one, например `OrderItem.product` или `Order.user`. Там строки не размножаются, и получается один round-trip вместо двух.

Документация SQLAlchemy тоже рекомендует `selectinload` как стратегию по умолчанию для коллекций. Сравнение по времени на ваших данных я не проводил. 180 мс против 2.4 с уже подтверждают, что выбор правильный.

**Ветка**

```
fix/orders-n-plus-one-selectinload
```

**Сообщение коммита**

```
fix(orders): eager-load order items with selectinload to remove N+1

get_user_orders() lazily loaded items per order, issuing one SELECT
per order (~300 queries per request for a typical user). Load
Order.items via selectinload so items are fetched in a single
SELECT ... WHERE order_id IN (...) query.

Endpoint latency drops from ~2.4s to ~180ms.

selectinload is preferred over joinedload here: items is a
one-to-many collection, and a JOIN would duplicate order columns
per item row and require .unique() on the result.
```

Если подставляете номер тикета в ветку или коммит, добавьте его по конвенции вашего репозитория. Ещё советую до пуша добавить тест, который проверяет количество запросов (например, через event listener `before_cursor_execute`). Тогда N+1 не вернётся незаметно.
