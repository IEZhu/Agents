**Most likely cause: gunicorn's worker timeout, not nginx.** The default `--timeout` is 30 seconds (from memory; check `gunicorn --help` or the settings docs for your version). Your export runs for about 45 seconds. At the 30-second mark the gunicorn master decides the sync worker is hung and kills it in the middle of the request. The socket then closes before any response headers have been sent, and nginx logs exactly what you're seeing: `upstream prematurely closed connection while reading response header`. It returns 502 to the client.

The wording of the error also tells you nginx didn't give up first. If nginx had run out of time (the default `proxy_read_timeout` is 60s), you would get **504** and `upstream timed out (110: Connection timed out)`. "Prematurely closed" means the upstream side closed the connection.

## Confirm it (takes 1 minute)

Look at the gunicorn log around `14:02:31`:

```
[CRITICAL] WORKER TIMEOUT (pid:NNNN)
... Worker (pid:NNNN) was sent SIGKILL! / exited with code ...
[INFO] Booting worker with pid: MMMM
```

If the gap between the request arriving and the error is about 30 seconds, that settles it.

**If there's no WORKER TIMEOUT line**, the next suspect is the OOM killer. A full-year export can be memory-heavy. Check with:

```bash
dmesg -T | grep -iE 'killed process|out of memory'
journalctl -k --since "2026-09-24 14:00" --until "2026-09-24 14:05"
```

## Fix

**Short-term (stops the 502s today):**

```bash
gunicorn app.wsgi --workers 4 --timeout 120
```

and in nginx, for that location only:

```nginx
location /reports/export/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_read_timeout 120s;   # must be >= the gunicorn timeout, with headroom over 45s
}
```

Downsides of this approach:
- `--timeout` applies to **all** workers and all endpoints. A genuinely hung request elsewhere will now hold a worker for 2 minutes before it gets recycled.
- **Capacity:** you have 4 sync workers and each export holds one for about 45 seconds. Four users exporting at once means **the whole site stops responding** for those 45 seconds, including requests that have nothing to do with reports. The 502s will then just become queueing and 504s.

**Proper fix: take the report generation out of the request cycle.**
- Move it to a background task (Celery/RQ/Django-Q). The `/reports/export/` endpoint returns `202` plus a job id. The client polls a status endpoint and then downloads the finished file from storage (S3 or local media with `X-Accel-Redirect`).
- This also lets you cache the result: last year's report doesn't change, so you can generate it once.

Streaming the response (`StreamingHttpResponse`) won't help with sync workers. As far as I know, a sync worker doesn't send its heartbeat to the master while it's handling a request, so it still gets killed at `--timeout`. Switching to `gthread` workers changes this behaviour, but I'm not certain of the details, so check the gunicorn docs for your version before relying on it. Background tasks are the more reliable option.

## Rollback

Both changes are configuration only. To undo them, remove `--timeout` and the `location` block, then reload nginx (`nginx -t && nginx -s reload`) and restart gunicorn (or `kill -HUP <master>` for a graceful reload). The risk is small: the only effect is that long requests are allowed to run longer.
