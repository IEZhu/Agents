**Most likely cause: gunicorn's worker timeout, not nginx.** Gunicorn's default `--timeout` is 30s. A full-year export takes about 45s, so the gunicorn master decides the sync worker is hung, kills it partway through the request, and the socket closes before any response headers are sent. That is exactly what `upstream prematurely closed connection while reading response header` means.

Why I think it's gunicorn and not nginx:
- An nginx-side timeout looks different. `proxy_read_timeout` defaults to 60s, and hitting it logs `upstream timed out (110: Connection timed out)` and returns a **504**, not a 502.
- "Prematurely closed" means the upstream process closed the connection. A killed worker does exactly that.
- It happens only some of the time because smaller exports finish in under 30s. Only the big ones, like `year=2025`, get killed.

(The defaults above are from memory, not verified here. Check them against the gunicorn and nginx docs for your versions.)

### Confirm it

Check the gunicorn log around `2026/09/24 14:02:31`. You should see something like:

```
[CRITICAL] WORKER TIMEOUT (pid:NNNN)
```

Depending on the version, you may also see the worker being aborted or killed and a new one booting. If that line is there, the diagnosis is confirmed. If it isn't, check `dmesg` / `journalctl -k` for the OOM killer. A large export held in memory can get the worker killed the same way.

To reproduce, bypass nginx:

```bash
time curl -s -o /dev/null -w '%{http_code}\n' 'http://127.0.0.1:8000/reports/export/?year=2025'
```

If it's the timeout, the connection drops at about 30s.

### Fix

**Short-term (unblocks users):** raise the gunicorn timeout above the worst-case export time, and keep nginx's timeout above gunicorn's for this route:

```bash
gunicorn myproject.wsgi --workers 4 --timeout 120
```

```nginx
location /reports/export/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_read_timeout 150s;   # > gunicorn --timeout, so gunicorn fails first and logs it
}
```

Blast radius of this change: a genuinely stuck worker now blocks for up to 120s instead of 30s.

**The real problem is capacity.** You have 4 sync workers and each export holds one for about 45s. Four concurrent exports use every worker, and all other traffic queues behind them, which leads to more timeouts and 502s/504s elsewhere. Raising the timeout hides this; it doesn't solve it.

**Proper fix:** move the export out of the request cycle.
- The request enqueues a job (Celery, RQ, or django-q) and returns `202` with a job ID.
- The worker writes the file to storage (S3 or local disk).
- The client polls a status endpoint, or gets a notification, and then downloads the file. Ideally nginx serves it via `X-Accel-Redirect`.

**Other options, roughly in order of effort:**
- Profile the export first. 45s often comes from N+1 queries or missing indexes, and `select_related`/`iterator()` or aggregation in SQL can shrink it a lot.
- Cache or precompute past years. 2025 is closed, so its report won't change.
- Switch to `--worker-class gthread --threads N`. As I understand it, the timeout there tracks the worker process's liveness rather than individual request duration, so long requests don't get killed the same way. They still tie up threads, though. Treat this as a mitigation, and check the docs for your gunicorn version.

### Verify after the change
- Rerun the `curl` above: you should get `200` in about 45s.
- There should be no `WORKER TIMEOUT` in the gunicorn log.
- Load-test with 4 or more concurrent exports while hitting a normal page, to see whether other traffic starves.

### Rollback
Revert the `--timeout` flag and the nginx `location` block, then run `nginx -t && nginx -s reload` and restart gunicorn with a graceful `HUP`. Both changes are config-only and take effect immediately.
