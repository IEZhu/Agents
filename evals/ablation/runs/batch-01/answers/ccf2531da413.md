I'll rewrite the critic prompt, but I don't think a stingy critic is the main problem, and a friendlier prompt on its own probably won't fix the 20%.

## What your traces show

Scores of 6, 7, 8, 8, 7, 8, 8, 7, 8 that never climb, while the drafts get worse, point to a loop that can't converge. Calibration looks like a secondary issue. Three things cause it:

1. **"List everything that could be improved" never runs out.** Any text can be improved, so the critic always returns feedback. The writer acts on it, usually by *adding* something, and the next critique finds more to change. That's why the drafts drift toward "longer, more adjective soup".
2. **Nothing anchors the score.** "Strict" plus a 1-10 scale with no definitions leaves the model to decide what a 9 means each time. GPT-4o tends to settle around 7-8 on open-ended quality scores (my impression, not a measured result). Your threshold sits just above where the scores naturally land.
3. **The loop has no memory and no exit.** Nothing caps the rounds, nothing detects a plateau, and nothing keeps the best draft. Round 3 was better, and the loop threw it away.

So if you only lower the bar, you'll get a critic that says 9 more often. It won't tell you when a description is actually good. You need to fix the critic and the loop together.

## Rewritten critic prompt

```markdown
## Role
You are an e-commerce copy editor reviewing a product description before it goes live. Your job is to decide whether it is ready to publish, not to find every possible improvement.

## Input
- PRODUCT DATA: the facts about the product (source of truth)
- DESCRIPTION: the draft to review

## Rubric
Score each criterion 1-5:
1. Accuracy: every claim is supported by PRODUCT DATA; nothing invented.
2. Clarity: a shopper understands what it is and who it's for within the first two sentences.
3. Benefits: the key features are tied to concrete benefits for the buyer.
4. Concision: no filler, no stacked adjectives, no repetition. Longer is NOT better.
5. Tone: fits the brand and category; no hype words like "revolutionary", "unparalleled" or "must-have" unless the data supports them.

## Overall score (1-10). Use these anchors:
- 9-10: Publish as-is. A professional editor would change at most a word or two.
- 7-8: Publishable, but one specific issue is worth fixing.
- 5-6: Has a real problem (missing key info, unclear, bloated).
- 1-4: Inaccurate, misleading, or unusable.

A description that is accurate, clear and concise with no real problems scores 9, even if you could phrase it differently. Stylistic preference is not a defect.

## Feedback rules
- Report at most 3 issues, most important first. Each one must say what to change and why.
- Only report issues that would move the score. Do not list nice-to-haves.
- If the score is 9 or 10, return an empty issues list.
- Prefer cutting over adding. If the draft is longer than it needs to be, say so.
- Never suggest adding claims that aren't in PRODUCT DATA.

## Output (JSON only)
{
  "criteria": {"accuracy": 1-5, "clarity": 1-5, "benefits": 1-5, "concision": 1-5, "tone": 1-5},
  "score": 1-10,
  "ready_to_publish": true/false,
  "issues": [{"problem": "...", "fix": "..."}]
}
```

What changed and why:
- **"Ready to publish?" replaces "everything that could be improved".** The critic can now answer "nothing to fix", which the old prompt didn't allow.
- **Anchors on the score** tie a 9 to a concrete meaning, so it doesn't depend on the model's mood that run.
- **Max 3 issues, prefer cutting, concision as its own criterion** push back directly against the adjective drift.
- **PRODUCT DATA as ground truth** lets the critic catch the writer inventing claims, which is a common failure in rewrite loops.
- **JSON output** gives you per-criterion scores to log and check against a golden set.

## Loop changes (these matter as much as the prompt)

- **Cap the rounds at 3-4.** From your description, most of the gain happens by round 3.
- **Keep the best draft, not the last one.** Track the highest-scoring draft and publish it when the loop stops.
- **Stop on a plateau.** If the score doesn't improve for 2 rounds, stop.
- **Tell the writer to make only the listed changes, and nothing else.** Also tell it the new draft must be no longer than the old one unless an issue explicitly asks for more content.
- **Flag the leftovers.** SKUs that end under 8 after the cap go to a human review queue. Letting them run 40 rounds costs tokens and still gives you worse copy.
- **Consider a fixed temperature** (0-0.3) for the critic. Lower temperature usually makes scores more consistent between rounds, though I haven't tested that on your setup.

## Check it before you trust it

Choose 20-30 SKUs, including some that failed. Have a human mark each description as publishable or not, then compare the critic's `ready_to_publish` against those labels. If the critic still refuses good copy, adjust the anchors. If it passes bad copy, tighten the rubric. Change one thing at a time.

## Side note: losing the night's work

The fix is cheap: write each SKU's result (to a DB row or a JSONL file) as soon as it finishes. On restart, skip the SKUs that are already done. Also wrap each API call in a retry with exponential backoff and a per-request timeout, so one timeout fails one SKU instead of killing the whole job. Both the OpenAI Python SDK and libraries like `tenacity` support retries. The exact settings (the SDK's `max_retries`/`timeout` client options, as I recall) are unverified here, so check them against your SDK version. You could also look at OpenAI's Batch API for a nightly job of this size. It's async and cheaper per token (as I recall), but check whether it fits a multi-round loop.
