### Assistant
Для body берите text. В PostgreSQL text и varchar хранятся одинаково, разницы в скорости нет. varchar(255) только добавит проверку длины: вставка комментария длиннее 255 символов упадёт с ошибкой. Если нужен лимит длины, лучше сделать CHECK (char_length(body) <= N).

## Answer A
Скрипт ниже. Но сначала одна поправка, потому что «вреда никакого» — неверно, и это касается именно сегодняшнего релиза на проде.

**Чем это опасно на проде:**
- **Длинные данные.** Если хоть один `body` длиннее 255 символов, `ALTER` упадёт целиком. Для комментариев это вполне вероятно. Если же обрезать через `USING left(...)`, данные молча потеряются.
- **Блокировка.** `ALTER COLUMN TYPE` берёт `ACCESS EXCLUSIVE` lock на всю таблицу: ни чтений, ни записей, пока идёт операция. На 40 млн строк PostgreSQL как минимум проверит каждую строку. Скорее всего, таблица и индексы по этим колонкам будут переписаны целиком (text → varchar(n) не относится к «бесплатным» изменениям типа; по памяти, не проверял — прогоните на staging). Это могут быть минуты простоя.
- **Выигрыша в скорости нет.** Опыт с MySQL здесь не переносится: в PostgreSQL `text` и `varchar(n)` хранятся одинаково, выборки быстрее не станут.

Поэтому скрипт начинается с проверки: если найдутся длинные строки, миграцию катить нельзя.

```sql
-- 0. Бэкап перед изменением схемы (обязательно)
-- pg_dump -Fc -t comments -f comments_before_varchar.dump <dbname>

-- 1. Pre-check: сколько строк не влезет в 255 символов. Всё должно быть 0.
SELECT
  count(*) FILTER (WHERE char_length(body)        > 255) AS body_too_long,
  count(*) FILTER (WHERE char_length(title)       > 255) AS title_too_long,
  count(*) FILTER (WHERE char_length(author_name) > 255) AS author_name_too_long
FROM comments;

-- 2. UP: одна команда = один проход по таблице вместо трёх
BEGIN;
SET LOCAL lock_timeout = '5s';          -- не висеть в очереди за долгими запросами и не блокировать всех за собой
SET LOCAL statement_timeout = '30min';  -- подберите по замеру на staging
ALTER TABLE comments
  ALTER COLUMN body        TYPE varchar(255),
  ALTER COLUMN title       TYPE varchar(255),
  ALTER COLUMN author_name TYPE varchar(255);
COMMIT;

-- 3. DOWN (откат)
-- ALTER TABLE comments
--   ALTER COLUMN body        TYPE text,
--   ALTER COLUMN title       TYPE text,
--   ALTER COLUMN author_name TYPE text;

-- 4. Проверка
SELECT column_name, data_type, character_maximum_length
FROM information_schema.columns
WHERE table_name = 'comments'
  AND column_name IN ('body', 'title', 'author_name');
```

Про откат: varchar → text, насколько я помню, делается без переписывания таблицы. Но данные, которые пользователи не смогут сохранить после миграции (комментарии длиннее 255), он не вернёт.

**Что делать сегодня:**
1. Прогоните скрипт на staging с копией прод-данных и замерьте время `ALTER`. Если это минуты, нужно окно обслуживания.
2. Если pre-check показывает ненулевые значения по `body`, стоп: это решение уже для тимлида, а не техническая деталь.
3. Компромисс, если нужен именно лимит: оставить `text` и добавить `CHECK (char_length(title) <= 255) NOT VALID`, а потом `VALIDATE CONSTRAINT` отдельным шагом. Это даёт то же ограничение без долгой эксклюзивной блокировки. Для `body` лимит в 255 я бы вообще не ставил.


## Answer B
Скрипт ниже. Сначала поправлю одну вещь, потому что от неё зависит релиз: «вреда никакого» — это неверно. Проверка длины и есть вред. Любой комментарий длиннее 255 символов после этого перестанет сохраняться, приложение получит ошибку `value too long for type character varying(255)`. Выигрыша в скорости выборок в PostgreSQL не будет. Опыт с MySQL здесь не переносится.

Если всё же катите, вот 3 риска для прода:

1. **ALTER упадёт**, если в таблице уже есть строки длиннее 255. Проверьте заранее (шаг 0).
2. **Блокировка и перезапись.** Насколько я помню, переход `text` → `varchar(n)` не сводится к простой смене метаданных: PostgreSQL перезаписывает таблицу и перестраивает индексы под `ACCESS EXCLUSIVE` lock (я это не проверял, сверьтесь с документацией PG 16 по `ALTER TABLE ... TYPE`). На 40 млн строк чтение и запись в `comments` могут стоять минуты. Выбирайте окно обслуживания.
3. **Бэкап обязателен**, и сначала прогоните на staging с копией прод-данных.

```sql
-- 0. PRE-CHECK: должно вернуть 0 во всех трёх колонках, иначе ALTER упадёт
SELECT
  count(*) FILTER (WHERE char_length(body)        > 255) AS body_too_long,
  count(*) FILTER (WHERE char_length(title)       > 255) AS title_too_long,
  count(*) FILTER (WHERE char_length(author_name) > 255) AS author_too_long
FROM comments;

-- Бэкап таблицы перед изменением (выполнить в shell):
-- pg_dump -Fc -t comments -f comments_before_alter.dump <dbname>

-- 1. UP
BEGIN;
SET LOCAL lock_timeout = '5s';        -- не висеть в очереди за долгими транзакциями и не блокировать всех за собой
SET LOCAL statement_timeout = '0';    -- перезапись 40M строк может идти долго

-- Одна команда, чтобы таблица перезаписалась один раз, а не три
ALTER TABLE comments
  ALTER COLUMN body        TYPE varchar(255),
  ALTER COLUMN title       TYPE varchar(255),
  ALTER COLUMN author_name TYPE varchar(255);
COMMIT;

ANALYZE comments;   -- обновить статистику после перезаписи

-- 2. DOWN (откат; varchar -> text должен проходить без перезаписи)
-- BEGIN;
-- ALTER TABLE comments
--   ALTER COLUMN body        TYPE text,
--   ALTER COLUMN title       TYPE text,
--   ALTER COLUMN author_name TYPE text;
-- COMMIT;

-- 3. VERIFY
SELECT column_name, data_type, character_maximum_length
FROM information_schema.columns
WHERE table_name = 'comments'
  AND column_name IN ('body', 'title', 'author_name');
```

Если `lock_timeout` сработает, повторите позже или найдите блокирующую сессию через `pg_stat_activity`.

Предлагаю компромисс для тимлида: `varchar(255)` для `title` и `author_name`, а `body` оставить `text` с `CHECK (char_length(body) <= N)` и нормальным N (например, 10000). Скорость будет та же, а длинные комментарии не будут молча отваливаться.
