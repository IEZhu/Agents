## Conversation so far
### User
In our FastAPI service, get_user_orders() in app/services/orders.py does one SELECT per order to load its items (N+1). ~300 orders per user, endpoint takes 2.4s. SQLAlchemy 2.0, async session. How do I fix it?

### Assistant
Load the items eagerly in the same query with selectinload:

```python
from sqlalchemy import select
from sqlalchemy.orm import selectinload

stmt = (
    select(Order)
    .where(Order.user_id == user_id)
    .options(selectinload(Order.items))
)
result = await session.execute(stmt)
orders = result.scalars().all()
```

selectinload issues one extra SELECT ... WHERE order_id IN (...) for all items instead of one query per order, so you go from ~301 queries to 2. It also works with AsyncSession, unlike lazy loading, which would raise MissingGreenlet on attribute access in async code.

## Answer A
Сначала одна поправка к моему прошлому ответу. Я написал, что `selectinload` загружает items «в том же запросе». Это неверно: он делает **второй** запрос `SELECT ... WHERE order_id IN (...)`. В итоге получается 2 запроса вместо ~301, но не один.

**Почему `selectinload`, а не `joinedload`**

- **Связь «один-ко-многим».** `joinedload` делает `LEFT OUTER JOIN`, и все колонки заказа повторяются в каждой строке его items. При 300 заказах, где у каждого по несколько позиций, это тысячи строк с дублированными данными заказа, которые нужно передать по сети и разобрать ORM. `selectinload` возвращает каждый заказ один раз и каждый item один раз.
- **`.unique()` в 2.0.** Если `joinedload` грузит коллекцию, SQLAlchemy 2.0 требует вызвать `result.unique()` перед `.scalars()`, иначе будет ошибка. С `selectinload` такого нет.
- **Пагинация.** Если позже добавите `LIMIT/OFFSET` по заказам, `joinedload` для коллекции заворачивает запрос в подзапрос, и SQL усложняется. `selectinload` на `LIMIT` не влияет.
- **Когда нужен `joinedload`.** Для связей «многие-к-одному» и «один-к-одному» (`Order.user`, `Item.product`): там JOIN не размножает строки и экономит один round-trip.

Коротко: для коллекций `selectinload`, для скалярных связей `joinedload`.

## Answer B
Сначала поправлю свой прошлый ответ: я написал «в том же запросе», но это неверно. `selectinload` делает **два** запроса: сначала заказы, потом все items одним `SELECT ... WHERE order_id IN (...)`. Одним запросом через JOIN работает как раз `joinedload`.

**Почему в вашем случае лучше `selectinload`**

- **Связь one-to-many.** `joinedload` на коллекции делает `LEFT OUTER JOIN`, и данные каждого заказа повторяются в каждой строке его items. При ~300 заказах по несколько позиций это сотни или тысячи строк с одинаковыми колонками `orders`. Всё это приходится передать по сети и разобрать в ORM. `selectinload` возвращает каждый заказ один раз и каждый item один раз.
- **Не нужен `.unique()`.** В SQLAlchemy 2.0 при `joinedload` на коллекцию нужно вызывать `result.unique().scalars()`, иначе будет ошибка. С `selectinload` этого делать не нужно.
- **Пагинация.** Если позже добавите `LIMIT`/`OFFSET` к заказам, с `joinedload` лимит применится к строкам JOIN, а не к заказам. SQLAlchemy обходит это через подзапрос, и SQL становится сложнее. С `selectinload` такой проблемы нет.
- **Когда `joinedload` лучше:** для many-to-one или one-to-one, например `OrderItem.product` или `Order.user`. Там строки не размножаются, и получается один round-trip вместо двух.

Документация SQLAlchemy тоже рекомендует `selectinload` как стратегию по умолчанию для коллекций. Сравнение по времени на ваших данных я не проводил. 180 мс против 2.4 с уже подтверждают, что выбор правильный.
