## Answer A
**Коротко:** 38 → ~12 мин не получится выжать одним кэшем. Нужны три вещи: (1) на PR запускать только затронутое, а полный прогон перенести в **merge queue**, тогда покрытие перед main не теряется; (2) распараллелить критический путь и шардировать его; (3) убрать повторную работу (Go build/test cache, BuildKit cache, одна компиляция вместо 12). ## Шаг 0 — Замерить (1 день)

Без этого не поймёте, какой шаг что дал.

- Время каждого job и **время ожидания раннера в очереди**. С 8 раннерами и шардированием очередь легко станет новым узким местом.
- Какие Go-пакеты дают основную часть из 17 минут: `go test -json ./... | ` → агрегировать `Elapsed` по пакетам. Обычно 2–3 пакета с интеграционными тестами (testcontainers, БД) съедают половину.
- Статистика флейков по конкретным тестам Playwright: JSON reporter + сбор в артефакт.
- Проверить, идут ли сейчас lint / test / build **последовательно**. Если да, это самый дешёвый выигрыш.

## Шаг 1 — Быстрые безрисковые победы (ожидаемо 38 → ~20–22 мин)

**1.1 Параллельные jobs + отмена устаревших прогонов**

```yaml
concurrency:
  group: ci-${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}  # не отменяем merge queue / main
```

lint, go-test и docker-build должны быть независимыми jobs. От build зависит только e2e (`needs: build`).

**1.2 Go cache на self-hosted раннерах.** Раннеры живые, поэтому держите `GOCACHE` и `GOMODCACHE` на локальном диске раннера по фиксированному пути, а не в `actions/cache`: upload/download 1–2 ГБ сами по себе съедают минуты.

```yaml
env:
  GOCACHE: /opt/ci-cache/go-build
  GOMODCACHE: /opt/ci-cache/go-mod
```

Тестовый кэш `go test` сработает только при следующих условиях (поведение по памяти, проверьте на своей версии Go):
- нет `-count=1`. Если он стоит «на всякий случай», уберите его для PR;
- тесты не зависят от меняющихся env и файлов вне модуля: Go отслеживает прочитанные env/файлы, и любое изменение инвалидирует кэш;
- с `-coverprofile` кэш, насколько я помню, работает в современных версиях Go (не проверено здесь).

Если параллельных job на раннере несколько, разнесите кэш по слотам раннера или смиритесь с конкуренцией за lock. Go cache рассчитан на конкурентный доступ, но диск станет узким местом.

**1.3 Docker: компилировать один раз, образы делать тонкими.** 12 минут на 12 образов почти наверняка значат, что каждый Dockerfile заново качает модули и компилирует общий код. Варианты по эффективности:

1. **Лучший вариант:** один job собирает все бинарники `go build -o out/ ./cmd/...` с тёплым GOCACHE (обычно это десятки секунд, а не минуты), а Dockerfile каждого сервиса только делает `COPY out/<svc> /app` поверх distroless/alpine (pin по digest). Сборка образа занимает секунды.
2. Если Dockerfile нужны самодостаточные: BuildKit cache mounts

   ```dockerfile
   RUN --mount=type=cache,target=/go/pkg/mod \
       --mount=type=cache,target=/root/.cache/go-build \
       go build -o /out/svc ./cmd/svc
   ```

   плюс `docker buildx bake` для параллельной сборки всех таргетов одним вызовом и persistent builder на раннере (кэш BuildKit живёт локально). Кэш в registry (`type=registry`) нужен, только если раннеры не делят кэш, а 8 раннеров его не делят. Так что либо registry cache, либо шардирование с привязкой к раннеру.
3. На PR не пушить образы, которые не нужны e2e.

**1.4 Playwright: шардирование + retry вместо «re-run all».**

```ts
// playwright.config.ts
retries: process.env.CI ? 2 : 0,
use: { trace: 'on-first-retry' },
```

```yaml
strategy:
  matrix:
    shard: [1, 2, 3]
steps:
  - run: npx playwright test --shard=${{ matrix.shard }}/3
```

Retry на уровне теста стоит секунды, а «re-run all» стоит 38 минут. Это меняет экономику флейков сильнее, чем что-либо ещё. Но retry **маскирует** флейки, поэтому обязательно делайте шаг 4.

## Шаг 2 — Merge queue с полным прогоном (предпосылка для шага 3)

Именно это даёт «без потери покрытия перед мёржем»: полный пайплайн (все тесты, все образы, весь e2e) гоняется на `merge_group`, то есть на коммите «PR + актуальный main». Это даже строже, чем текущая схема, где PR тестируется против устаревшего main.

```yaml
on:
  pull_request:
  merge_group:
  push:
    branches: [main]
```

В branch protection сделайте required checks, которые существуют и в PR-, и в merge_group-прогоне с одинаковыми именами. Иначе очередь зависнет. Доступность merge queue для приватных репозиториев зависит от плана GitHub (по памяти: organization-репозитории на Team/Enterprise; не проверено, сверьтесь с документацией).

**Стоимость:** каждый мёрж запускает полный прогон. При высокой частоте мёржей настройте в очереди группировку (merge several PRs per group), иначе 8 раннеров не хватит.

## Шаг 3 — Affected-only на PR (ожидаемо ~20 → ~10–12 мин медиана)

Главный рычаг: типичный PR трогает 1–2 сервиса из 12.

**Go:** граф зависимостей через `go list`, а не «папка изменилась → тестируем папку». Иначе изменение в `pkg/common` пропустит зависящие сервисы.

```bash
#!/usr/bin/env bash
# affected.sh — печатает сервисы, чьи транзитивные зависимости затронуты диффом
set -euo pipefail
BASE="${1:-origin/main}"
MODULE=$(go list -m)
changed_pkgs=$(git diff --name-only "$BASE"...HEAD -- '*.go' go.mod go.sum \
  | xargs -r -n1 dirname | sort -u | sed "s|^|$MODULE/|")

# go.mod/go.sum изменились → считаем затронутым всё
if git diff --name-only "$BASE"...HEAD | grep -qE '^go\.(mod|sum)$'; then
  ls cmd; exit 0
fi

for svc in $(ls cmd); do
  deps=$(go list -deps "./cmd/$svc/..." | grep "^$MODULE" || true)
  for p in $changed_pkgs; do
    if grep -qx "$p" <<<"$deps"; then echo "$svc"; break; fi
  done
done
```

Это набросок. Проверьте на своей структуре: как лежат `cmd/`, один ли `go.mod`, есть ли `internal/` вне сервисов. Для тестов нужен обратный граф: какие *тестовые* пакеты импортируют изменённые. Тот же подход, только через `go list -deps -test`. Готовые альтернативы: Bazel/Pants (дорого внедрять) или path-based фильтры `dorny/paths-filter` (дёшево, но грубо). Промахи affected-детекции в итоге ловит merge queue из шага 2, и поэтому шаг 2 идёт первым.

**Выход в матрицу:**

```yaml
jobs:
  detect:
    outputs:
      services: ${{ steps.a.outputs.services }}
    steps:
      - uses: actions/checkout@v4   # закрепить по SHA
        with: { fetch-depth: 0 }
      - id: a
        run: echo "services=$(./affected.sh origin/${{ github.base_ref }} | jq -Rsc 'split("\n")|map(select(.!=""))')" >> "$GITHUB_OUTPUT"
  test:
    needs: detect
    if: needs.detect.outputs.services != '[]'
    strategy:
      matrix:
        service: ${{ fromJson(needs.detect.outputs.services) }}
```

**Frontend/e2e на PR:** запускать, если затронут фронт или сервисы, которые он вызывает. Можно дробнее: помечать Playwright-спеки тегами по сервисам (`@billing`) и гонять `--grep`. Полный e2e всё равно пройдёт в merge queue.

**Шардирование тяжёлых Go-пакетов:** если после шага 0 видно, что 2–3 пакета дают основную часть времени, выносите их в отдельные jobs матрицы. Другой вариант: split по `go test -list` + `-run` regex.

## Шаг 4 — Флейки (параллельно с 2–3, постоянный процесс)

- **Карантин:** тест, который упал и прошёл на retry, автоматически попадает в отчёт. Тест с частотой флейков выше порога помечается `test.fixme` / тегом `@quarantine` и исключается из required-прогона, а на него заводится issue с владельцем. Карантинные тесты гоняются в отдельном non-blocking job, чтобы видеть, починили ли их.
- **Типовые причины в Playwright:** `waitForTimeout` вместо web-first assertions (`expect(locator).toBeVisible()`), общие тестовые данные между шардами и воркерами, отсутствие изоляции окружения (один стенд на параллельные прогоны), анимации.
- **Метрика:** «прогонов, упавших хотя бы с одним retry». Цель — довести с ~17% до < 2%.

## Шаг 5 — Ёмкость раннеров

После шардирования один PR занимает не 1 раннер, а 5–8 одновременно. При 8 раннерах и нескольких активных PR медиана будет упираться в очередь, а не в выполнение. Варианты:

- Больше слотов на хост (несколько runner-процессов на мощной машине с общим Go/BuildKit кэшем). Это дешевле всего и сохраняет локальный кэш.
- Autoscaling через Actions Runner Controller (ARC) на K8s. Минус: эфемерные раннеры теряют локальный кэш, поэтому понадобятся PVC-кэш или registry cache. Внедрять стоит, только если метрика очереди из шага 0 показывает, что проблема именно в ней.
- Cost: больше хостов значит больше денег. Считайте по данным очереди, а не заранее.

## Blast radius и откат

- **Шаг 1:** затрагивает только скорость. Откат — revert workflow-файла. Главный риск — «грязный» кэш на раннере. Держите ручной `workflow_dispatch` для очистки `/opt/ci-cache`.
- **Шаги 2–3:** риск — affected-детекция пропустит зависимость. Страховка — полный прогон в merge queue, так что main не пострадает, пострадает только скорость очереди. Откат: убрать фильтр, и PR снова гоняет всё. Держите старый полный workflow включаемым флагом (`vars.CI_FULL_ON_PR == 'true'`) на время перехода.
- **Merge queue:** если required checks названы не так, мёржи встанут. Включайте в нерабочее время и сначала на одном репо или ветке.
- Все actions в YAML закрепляйте по commit SHA, а не по тегу `@v4`. Выше теги оставлены для читаемости.


## Answer B
**Коротко:** 17 + 12 + 7 + ~2 = 38 мин. Значит, этапы идут **последовательно**, и всё гоняется целиком. Порядок работ:

1. распараллелить;
2. сделать тёплые кэши на self-hosted;
3. на PR гонять только затронутое (affected), а полный прогон перенести в **merge queue**;
4. шардировать и лечить флейки e2e;
5. добавить раннеров.

Покрытие перед мёржем в main не теряется: полный прогон остаётся обязательным, он просто переезжает из PR в merge queue.

Реалистичная цель: медиана PR 9–12 мин, полный прогон в merge queue 15–18 мин. Это оценка, а не замер. Её надо проверить на своих метриках после шагов 1–2.

## Шаг 0. Замер (полдня)

Прежде чем что-то менять, соберите по последним ~200 прогонам:
- время каждого job и step;
- время в очереди на раннер. С 8 раннерами оно может съесть весь выигрыш от параллелизма;
- долю re-run и какие именно e2e-тесты падают;
- долю PR, которые трогают 1–2 сервиса. В монорепо таких обычно большинство, и на этом держится шаг 3.

Без этого не будет понятно, что дал каждый следующий шаг.

## Шаг 1. DAG вместо цепочки: 38 → ~20 мин

Линтеры, `go test` и сборка образов не зависят друг от друга. От сборки зависит только e2e.

```
changes ─┬─ lint (go + next)
         ├─ go-test (matrix: шарды)
         └─ build (matrix: сервисы) ── e2e (matrix: шарды)
```

Критический путь станет build 12 + e2e 7 ≈ 19 мин, `go test` уйдёт в параллель. Сразу же добавьте `concurrency: cancel-in-progress`, чтобы новый push в PR убивал старый прогон и освобождал раннеры.

**Blast radius:** только CI. Откат: revert PR с workflow.

## Шаг 2. Тёплые кэши (главный выигрыш на self-hosted)

Self-hosted раннеры не надо кэшировать через `actions/cache`. Он гоняет архивы через GitHub и на больших Go-кэшах медленный. Держите кэш **на диске раннера**:

- **Go:** `GOCACHE` и `GOMODCACHE` на постоянном томе раннера, например `/var/cache/go-build` и `/var/cache/gomod`. Тогда `go test` возьмёт закэшированные результаты для пакетов, у которых не менялись входы. Оговорки:
  - флаг `-count=1` отключает кэш тестов;
  - насколько кэшируются прогоны с `-coverprofile`, зависит от версии Go. Я не уверен, проверьте на своей версии, запустив дважды подряд;
  - если раннеры ephemeral и диск чистится, нужен shared volume или хотя бы `actions/cache` для `GOMODCACHE`.
- **Docker, 12 мин:** почти наверняка каждый из 12 Dockerfile компилирует зависимости с нуля. Два варианта:
  - **(лучше)** собрать все бинарники **одним** `go build ./cmd/...` на хосте с тёплым `GOCACHE`. Общие зависимости скомпилируются один раз. Затем `COPY` бинарника в тонкий образ (distroless/alpine, с запиненным digest). Сборка образа сводится к секундам;
  - или оставить сборку внутри Docker, но добавить `RUN --mount=type=cache,target=/root/.cache/go-build` и `--mount=type=cache,target=/go/pkg/mod`, плюс BuildKit с кэшем на раннере или `cache-from/cache-to: type=registry`.
- **Next.js:** кэш `.next/cache` и store пакетного менеджера на диске раннера.
- **Линтеры:** кэш `golangci-lint` (`~/.cache/golangci-lint`), в PR режим `--new-from-rev` / only-new-issues. Точный флаг сверьте с вашей версией golangci-lint. Плюс `tsc --incremental` и ESLint `--cache`.

## Шаг 3. Affected на PR + полный прогон в merge queue (до 12 мин)

Это ключевой шаг под вашу цель.

- **На `pull_request`:** job `changes` считает затронутые пакеты и сервисы:
  - `git diff` против merge-base;
  - изменённые Go-пакеты;
  - reverse deps через `go list -deps -test -json ./...`, чтобы изменение в `pkg/shared` задело всех, кто от него зависит;
  - маппинг пакетов на `cmd/<service>`.

  Изменения в `go.mod`/`go.sum`, в CI-конфиге или в общих Dockerfile считаются «затронуто всё».
- **Тесты:** гоняются только affected-пакеты. Собираются только affected-образы. Для остальных сервисов e2e берёт образ из registry с тегом последнего зелёного `main`.
- **На `merge_group`:** GitHub merge queue запускает тот же workflow, и тогда `changes` отдаёт «всё»: полный `go test ./...`, все образы, весь e2e. В main попадает только то, что прошло полный прогон на актуальном main, то есть покрытие перед мёржем даже **выше**, чем сейчас. Сейчас PR тестируется против устаревшей базы.
- **Детали, которые нужно проверить** (по памяти, не сверял с документацией):
  - workflow должен слушать событие `merge_group`, иначе очередь зависнет;
  - required checks должны иметь одинаковые имена в обоих режимах.

  Отдельно для matrix: пустой список сервисов в `fromJSON` ломает job. Нужно условие `if: needs.changes.outputs.services != '[]'`.
- **Страховка:** nightly-прогон полного пайплайна на `main` с `-count=1`, чтобы кэш тестов не скрывал зависимость от окружения.

Скелет:

```yaml
name: ci
on:
  pull_request:
  merge_group:          # полный прогон перед попаданием в main

concurrency:
  group: ci-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true

jobs:
  changes:
    runs-on: [self-hosted, linux]
    outputs:
      services: ${{ steps.affected.outputs.services }}   # JSON-массив
      go_shards: ${{ steps.affected.outputs.go_shards }}
    steps:
      - uses: actions/checkout@v4   # запинить на SHA
        with: { fetch-depth: 0 }
      # merge_group -> всё; pull_request -> diff против merge-base + reverse deps
      - id: affected
        run: ./ci/affected.sh "${{ github.event_name }}" >> "$GITHUB_OUTPUT"

  go-test:
    needs: changes
    runs-on: [self-hosted, linux]
    strategy:
      matrix: { shard: [1, 2, 3, 4] }
    env:
      GOCACHE: /var/cache/go-build      # постоянный том раннера
      GOMODCACHE: /var/cache/gomod
    steps:
      - uses: actions/checkout@v4
      # шардирование по историческому времени пакетов, не по алфавиту
      - run: ./ci/go-test-shard.sh ${{ matrix.shard }} 4

  build:
    needs: changes
    if: needs.changes.outputs.services != '[]'
    runs-on: [self-hosted, linux]
    strategy:
      matrix: { service: "${{ fromJSON(needs.changes.outputs.services) }}" }
    steps:
      - uses: actions/checkout@v4
      - run: ./ci/build-image.sh ${{ matrix.service }} ${{ github.sha }}

  e2e:
    needs: build
    if: ${{ !failure() && !cancelled() }}   # запускать и когда build пропущен
    runs-on: [self-hosted, linux]
    strategy:
      matrix: { shard: [1, 2, 3] }
    steps:
      - uses: actions/checkout@v4
      - run: npx playwright test --shard=${{ matrix.shard }}/3
```

## Шаг 4. e2e: шарды + флейки

- **Шардирование:** `--shard=N/3` превращает 7 мин примерно в 2,5–3. Плюс оверхед на подъём окружения в каждом шарде, поэтому поднимайте окружение из готовых образов, а не собирайте заново.
- **Флейки 1/6** сейчас стоят до 38 мин на каждый re-run all. Что делать:
  1. В CI `retries: 2` и `trace: 'on-first-retry'` в `playwright.config`. Упавший тест перезапускается точечно за секунды, а не весь пайплайн. Отчёт Playwright помечает такие тесты как flaky. Это видимость, а не лечение.
  2. Раз в неделю выгружать список flaky и чинить топ-5. Обычно причины такие: `waitForTimeout` вместо web-first assertions, общие тестовые данные между воркерами, гонки на старте сервисов (нет healthcheck/readiness перед тестами).
  3. Карантин: тег `@quarantine`, такие тесты гоняются отдельным non-required job, чтобы не блокировать мёрж. У каждого есть владелец и срок.
  4. Людям: «Re-run failed jobs», а не «Re-run all jobs». После шага 1 это перезапуск одного шарда.

Флейки почти не двигают медиану, но сильно бьют по p75/p90 и по тому, как люди ощущают CI. Поэтому шаг обязательный, хоть и стоит четвёртым.

## Шаг 5. Мощности раннеров

Сейчас PR занимает 1 раннер на 38 мин. После шагов 1–4 это ~8–10 параллельных job, но каждый короткий. На 8 раннерах при нескольких одновременных PR очередь может съесть весь выигрыш. Поэтому смотрите queue time из шага 0.

- **Варианты:**
  - автоскейлинг (actions-runner-controller на k8s) с отдельными пулами: лёгкие для lint/changes, тяжёлые для go-test/build;
  - или больше job на хост через несколько runner-процессов, если хватает CPU и RAM.
- **Стоимость:** автоскейлинг в облаке добавляет расходы на ноды. Возможно, частично это окупится за счёт `cancel-in-progress` и affected-режима, но это надо проверить. Кэши на постоянных томах конфликтуют с полностью ephemeral-подами, так что нужен PVC или hostPath на ноду.

## Чем проверить результат

- Медиана и p90 длительности workflow и queue time до и после каждого шага (GitHub API `actions/runs` или экспорт в Grafana).
- Доля re-run в неделю.
- Контроль корректности affected: раз в неделю сравнить, ловил ли merge queue падения, которые PR-прогон пропустил. Если такое бывает часто, значит, граф зависимостей в `affected.sh` неполный.

## Откат

Каждый шаг — отдельный PR в `.github/workflows`, откатывается revert'ом. Merge queue выключается в branch protection. Если affected-логика окажется ненадёжной, временно заставьте `changes` всегда отдавать «всё». Параллелизм и кэши останутся, и это всё равно примерно 18–20 мин вместо 38.
