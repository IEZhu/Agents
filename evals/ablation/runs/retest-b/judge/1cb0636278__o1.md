## Latest user message
Dependency hell on our Python service, need a sanity check before I spend another day on it. We use three internal libs plus our shared protobuf runtime (acme-proto), and only one acme-proto major can be installed. Compatibility from the internal docs:

acme-auth 3.0 -> acme-proto 3.x
acme-auth 3.1 -> acme-proto 3.x or 4.x
acme-auth 3.2 -> acme-proto 4.x or 5.x

acme-billing 5.0 -> acme-proto 3.x, acme-events 1.x
acme-billing 5.1 -> acme-proto 3.x or 4.x, acme-events 2.x
acme-billing 6.0 -> acme-proto 4.x or 5.x, acme-events >=2.1

acme-events 1.4 -> acme-proto 3.x
acme-events 2.0 -> acme-proto 3.x or 4.x
acme-events 2.1 -> acme-proto 5.x

Hard requirements: we must be on acme-auth 3.2 (security fix), we need acme-billing >= 5.1 for the refunds API, and acme-proto 5.x is off the table for now because it needs a Python version our base image doesn't have. My plan was to just bump everything to latest (auth 3.2, billing 6.0, events 2.1) and pin proto accordingly, but pip keeps failing. Which exact combo should I pin, or is there none?

2. Explains that billing 6.0 is the dead end because it needs events >= 2.1, which requires proto 5.x

## Answer A
**Short answer:** exactly one combination works with the versions you listed:

**acme-auth 3.2 + acme-billing 5.1 + acme-events 2.0 + acme-proto 4.x**

"Bump everything to latest" can't be resolved. It isn't a pip quirk; your constraints conflict.

### Why latest fails

- acme-billing 6.0 requires acme-events >= 2.1.
- acme-events 2.1 supports **only** acme-proto 5.x.
- You've ruled out proto 5.x, so billing 6.0 is out with it. The cause is a transitive dependency: billing 6.0 itself would accept proto 4.

### How the solution follows

1. **Proto major:** auth 3.2 needs proto 4.x or 5.x. With 5.x excluded, you're on **proto 4.x**.
2. **Events on proto 4:** 1.4 only supports 3.x and 2.1 only supports 5.x, so **events 2.0** is the only option.
3. **Billing >= 5.1 on proto 4 with events 2.0:**
   - 6.0 needs events >= 2.1, so it's out.
   - 5.1 supports proto 3.x or 4.x and events 2.x, so it works.

Every package's constraints are satisfied, and nothing else fits.

### What to pin

```text
acme-auth==3.2.*
acme-billing==5.1.*
acme-events==2.0.*
acme-proto>=4,<5
```

Use `==X.Y.*` or exact patch versions, depending on how you normally pin. Keep `acme-proto` open inside 4.x so pip can choose a patch that all three libraries accept.

### Caveats worth checking before you commit to this

- **The listed versions only.** This assumes your table covers every release. If an acme-events 2.2+ exists that supports proto 4.x, billing 6.0 might become possible. Run `pip index versions acme-events` against your internal index to check.
- **Docs vs. real metadata.** Internal compatibility docs often drift from the actual `Requires-Dist` constraints in the wheels. If pip still fails on the combo above, run `pip install --dry-run --report - ...` (or `pipdeptree` in a clean venv) and compare the real constraints with the docs. A narrower range such as `acme-proto>=4.2,<5` in one of the libs would explain the failure.
- **Refunds API in 5.1.** You said you need billing >= 5.1 for refunds, so 5.1 should cover it. Confirm that the refunds features you use aren't 6.0-only additions.
- **Your upgrade path out:** getting proto 5.x into your base image (the Python version bump) unlocks auth 3.2 + billing 6.0 + events 2.1 + proto 5.x. That combination also satisfies every constraint and is where you'd want to end up.

**Confidence: HIGH.** I checked every allowed proto major against the table you gave. The main risk is that the docs don't match the published package metadata.


## Answer B
There's exactly one combination that works with the versions you listed, and "bump everything to latest" isn't it:

```
acme-auth==3.2.*
acme-billing==5.1.*
acme-events==2.0.*
acme-proto>=4,<5
```

### Why this is the only one

1. **acme-proto is fixed to 4.x.** acme-auth 3.2 accepts only proto 4.x or 5.x, and 5.x is ruled out by your base image.
2. **acme-events 2.1 is ruled out.** It requires proto 5.x.
3. **So acme-billing 6.0 is ruled out too.** It requires acme-events >=2.1, and the only such version in your docs is 2.1, which needs proto 5.
4. **That leaves acme-billing 5.1.** It meets your >=5.1 requirement for the refunds API, accepts proto 4.x, and needs acme-events 2.x.
5. **acme-events 2.0 fills that slot.** It's the only 2.x release that accepts proto 4.x.

A quick check of each pair against proto 4.x:

| Package | Pinned | Requires | OK with proto 4.x? |
|---|---|---|---|
| acme-auth | 3.2 | proto 4.x / 5.x | yes |
| acme-billing | 5.1 | proto 3.x / 4.x, events 2.x | yes (events 2.0) |
| acme-events | 2.0 | proto 3.x / 4.x | yes |

### Why your plan fails

auth 3.2 + billing 6.0 + events 2.1 is unsatisfiable. events 2.1 pulls proto to 5.x, and you can't have 5.x. pip is correct to reject it. Any pin with events 2.1 or billing 6.0 will fail the same way until proto 5 is an option.

### Caveats worth checking before you pin

- **This only covers the versions in your table.** If there's an unlisted acme-events 2.2+ that supports proto 4.x, billing 6.0 would become possible. Check your internal index (`pip index versions acme-events` against it) before you give up on 6.0 for good.
- **Look at the patch-level metadata, not just the docs.** Internal compatibility docs often drift from the actual `Requires-Dist` in the wheels. If pip still fails on the combo above, run `pip install --dry-run --report - ...` or `pip show` on each installed wheel. That shows which declared constraint disagrees with the docs.
- **Check the path back to billing 6.0.** Once your base image supports proto 5, auth 3.2 + billing 6.0 + events 2.1 + proto 5.x becomes valid. That's probably the upgrade to plan for, so the billing 5.1 / events 2.0 pin is a stopgap and not where you want to stay.

If the docs match what the packages actually declare, the pin above will resolve and you don't need to spend another day on it.
