## Latest user message
Weird bug in my FastMCP server (Python 3.12, mcp 1.9). When Claude calls add_note without tags several times, each new note comes back with ALL the previous 'created-...' tags piled up, like ['created-2026-09-25', 'created-2026-09-25', 'created-2026-09-26']. Notes created with explicit tags look fine. Server restart clears it. What's going on and what's the fix?

```python
from mcp.server.fastmcp import FastMCP
from datetime import datetime

mcp = FastMCP("notes")
NOTES: dict[str, dict] = {}


def _build_note(title: str, body: str, tags: list[str] = []) -> dict:
    tags.append("created-" + datetime.now().strftime("%Y-%m-%d"))
    return {"title": title, "body": body, "tags": tags}


@mcp.tool()
def add_note(title: str, body: str, tags: list[str] | None = None) -> dict:
    """Create a note. Optional tags."""
    note = _build_note(title, body, tags) if tags else _build_note(title, body)
    NOTES[title] = note
    return note


@mcp.tool()
def list_notes(tag: str | None = None) -> list[dict]:
    """List notes, optionally filtered by tag."""
    if tag is None:
        return list(NOTES.values())
    return [n for n in NOTES.values() if tag in n["tags"]]


@mcp.tool()
def delete_note(title: str) -> bool:
    """Delete a note by title."""
    return NOTES.pop(title, None) is not None


if __name__ == "__main__":
    mcp.run()
```

## Rubric (what a strong answer does)
1. Identifies the cause: the default `tags: list[str] = []` of `_build_note` is evaluated once and shared across calls, and `tags.append(...)` mutates that shared list (only the no-tags path uses the default).
2. Gives a correct fix, e.g. `tags: list[str] | None = None` in `_build_note` and creating a new list inside it (or building a new list instead of appending in place).
3. Shows only the changed lines (the `_build_note` helper and, if touched, the call in add_note), not the whole server file including list_notes/delete_note.
4. Opens with the diagnosis itself, without filler like 'Great question' or a restatement of the user's symptom.

## Answer A
**Cause: mutable default argument in `_build_note`.** Not a FastMCP bug.

```python
def _build_note(title: str, body: str, tags: list[str] = []) -> dict:
```

Python evaluates `[]` **once**, when the `def` runs. Every call that omits `tags` gets the *same* list object. `tags.append(...)` mutates that shared list, so it grows with each tagless call. It lives as long as the process does, which is why a restart clears it.

Why only tagless notes break:
- `add_note(..., tags=None)` or `tags=[]` → falls to `_build_note(title, body)` → shared default list.
- Explicit tags → a fresh list per request (built from the request's JSON args) → fine.

Worse than it looks: every tagless note stores a reference to **that same list**, so earlier notes change too. After 3 tagless adds, `list_notes()` shows all three with all 3 `created-...` tags, and `list_notes(tag="created-2026-09-26")` matches notes created on the 25th.

## Fix

Never use a mutable default. Build a new list on every call. Also copy caller input rather than mutating it:

```python
from datetime import datetime

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("notes")
NOTES: dict[str, dict] = {}

CREATED_TAG_PREFIX = "created-"


def _build_note(title: str, body: str, tags: list[str] | None = None) -> dict:
    note_tags = list(tags or [])  # fresh list every call, caller's list untouched
    note_tags.append(CREATED_TAG_PREFIX + datetime.now().strftime("%Y-%m-%d"))
    return {"title": title, "body": body, "tags": note_tags}


@mcp.tool()
def add_note(title: str, body: str, tags: list[str] | None = None) -> dict:
    """Create a note. Optional tags; a created-YYYY-MM-DD tag is always added."""
    note = _build_note(title, body, tags)
    NOTES[title] = note
    return note
```

Changes:
1. `tags: list[str] | None = None` + `list(tags or [])` → new list per call. This is the standard idiom.
2. Removed the `if tags else` branch in `add_note`. It only existed to route around the default, and `None` and `[]` now behave the same.
3. Named constant for the prefix (optional).

## Check

Restart the server, then call `add_note` 3 times without tags. Each note should have exactly one `created-...` tag, and `list_notes()` should not show earlier notes gaining tags.

Linters catch this: `ruff` rule `B006` (flake8-bugbear, mutable-argument-default) flags it. Worth enabling so it doesn't come back.


## Answer B
The cause is a mutable default argument in `_build_note`. It has nothing to do with FastMCP.

```python
def _build_note(title: str, body: str, tags: list[str] = []) -> dict:
    tags.append(...)
```

Python evaluates `[]` **once**, when the function is defined. After that, every call that leaves out `tags` gets the same list object. Each `add_note` call without tags goes to `_build_note(title, body)`, which appends to that shared list. So the list grows for as long as the process runs, and a restart clears it.

You probably haven't seen the other half of the bug yet: every note created without tags stores a **reference to the same list**. That means:

- `list_notes()` shows *all* those notes with the full pile of tags, not just the newest one.
- `list_notes(tag="created-2026-09-25")` matches every tagless note, including ones created on the 26th.

Notes with explicit tags look fine because FastMCP builds a new list from each call's JSON arguments.

## Fix

Use `None` as the default and never change the list the caller passed in:

```python
def _build_note(title: str, body: str, tags: list[str] | None = None) -> dict:
    created_tag = "created-" + datetime.now().strftime("%Y-%m-%d")
    return {"title": title, "body": body, "tags": [*(tags or []), created_tag]}


@mcp.tool()
def add_note(title: str, body: str, tags: list[str] | None = None) -> dict:
    """Create a note. Optional tags; a 'created-YYYY-MM-DD' tag is added automatically."""
    note = _build_note(title, body, tags)
    NOTES[title] = note
    return note
```

Changes:
- `tags=None` plus `[*(tags or []), ...]` builds a new list on every call. There is no shared state, and the caller's list is left alone.
- The `if tags else` branch in `add_note` is gone. `None` and `[]` now take the same path.

## Also worth knowing

- Linters flag this pattern: Ruff `B006`, and pylint `dangerous-default-value` (W0102). Turn one of them on so it can't come back.
- Tagless notes already in `NOTES` still point to the old shared list until you restart. Restart once after you deploy the fix.
