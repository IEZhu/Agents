**Коротко:** 17 + 12 + 7 + ~2 = 38 мин. Значит, этапы идут **последовательно**, и всё гоняется целиком. Порядок работ:

1. распараллелить;
2. сделать тёплые кэши на self-hosted;
3. на PR гонять только затронутое (affected), а полный прогон перенести в **merge queue**;
4. шардировать и лечить флейки e2e;
5. добавить раннеров.

Покрытие перед мёржем в main не теряется: полный прогон остаётся обязательным, он просто переезжает из PR в merge queue.

Реалистичная цель: медиана PR 9–12 мин, полный прогон в merge queue 15–18 мин. Это оценка, а не замер. Её надо проверить на своих метриках после шагов 1–2.

---

## Шаг 0. Замер (полдня)

Прежде чем что-то менять, соберите по последним ~200 прогонам:
- время каждого job и step;
- время в очереди на раннер. С 8 раннерами оно может съесть весь выигрыш от параллелизма;
- долю re-run и какие именно e2e-тесты падают;
- долю PR, которые трогают 1–2 сервиса. В монорепо таких обычно большинство, и на этом держится шаг 3.

Без этого не будет понятно, что дал каждый следующий шаг.

## Шаг 1. DAG вместо цепочки: 38 → ~20 мин

Линтеры, `go test` и сборка образов не зависят друг от друга. От сборки зависит только e2e.

```
changes ─┬─ lint (go + next)
         ├─ go-test (matrix: шарды)
         └─ build (matrix: сервисы) ── e2e (matrix: шарды)
```

Критический путь станет build 12 + e2e 7 ≈ 19 мин, `go test` уйдёт в параллель. Сразу же добавьте `concurrency: cancel-in-progress`, чтобы новый push в PR убивал старый прогон и освобождал раннеры.

**Blast radius:** только CI. Откат: revert PR с workflow.

## Шаг 2. Тёплые кэши (главный выигрыш на self-hosted)

Self-hosted раннеры не надо кэшировать через `actions/cache`. Он гоняет архивы через GitHub и на больших Go-кэшах медленный. Держите кэш **на диске раннера**:

- **Go:** `GOCACHE` и `GOMODCACHE` на постоянном томе раннера, например `/var/cache/go-build` и `/var/cache/gomod`. Тогда `go test` возьмёт закэшированные результаты для пакетов, у которых не менялись входы. Оговорки:
  - флаг `-count=1` отключает кэш тестов;
  - насколько кэшируются прогоны с `-coverprofile`, зависит от версии Go. Я не уверен, проверьте на своей версии, запустив дважды подряд;
  - если раннеры ephemeral и диск чистится, нужен shared volume или хотя бы `actions/cache` для `GOMODCACHE`.
- **Docker, 12 мин:** почти наверняка каждый из 12 Dockerfile компилирует зависимости с нуля. Два варианта:
  - **(лучше)** собрать все бинарники **одним** `go build ./cmd/...` на хосте с тёплым `GOCACHE`. Общие зависимости скомпилируются один раз. Затем `COPY` бинарника в тонкий образ (distroless/alpine, с запиненным digest). Сборка образа сводится к секундам;
  - или оставить сборку внутри Docker, но добавить `RUN --mount=type=cache,target=/root/.cache/go-build` и `--mount=type=cache,target=/go/pkg/mod`, плюс BuildKit с кэшем на раннере или `cache-from/cache-to: type=registry`.
- **Next.js:** кэш `.next/cache` и store пакетного менеджера на диске раннера.
- **Линтеры:** кэш `golangci-lint` (`~/.cache/golangci-lint`), в PR режим `--new-from-rev` / only-new-issues. Точный флаг сверьте с вашей версией golangci-lint. Плюс `tsc --incremental` и ESLint `--cache`.

## Шаг 3. Affected на PR + полный прогон в merge queue (до 12 мин)

Это ключевой шаг под вашу цель.

- **На `pull_request`:** job `changes` считает затронутые пакеты и сервисы:
  - `git diff` против merge-base;
  - изменённые Go-пакеты;
  - reverse deps через `go list -deps -test -json ./...`, чтобы изменение в `pkg/shared` задело всех, кто от него зависит;
  - маппинг пакетов на `cmd/<service>`.

  Изменения в `go.mod`/`go.sum`, в CI-конфиге или в общих Dockerfile считаются «затронуто всё».
- **Тесты:** гоняются только affected-пакеты. Собираются только affected-образы. Для остальных сервисов e2e берёт образ из registry с тегом последнего зелёного `main`.
- **На `merge_group`:** GitHub merge queue запускает тот же workflow, и тогда `changes` отдаёт «всё»: полный `go test ./...`, все образы, весь e2e. В main попадает только то, что прошло полный прогон на актуальном main, то есть покрытие перед мёржем даже **выше**, чем сейчас. Сейчас PR тестируется против устаревшей базы.
- **Детали, которые нужно проверить** (по памяти, не сверял с документацией):
  - workflow должен слушать событие `merge_group`, иначе очередь зависнет;
  - required checks должны иметь одинаковые имена в обоих режимах.

  Отдельно для matrix: пустой список сервисов в `fromJSON` ломает job. Нужно условие `if: needs.changes.outputs.services != '[]'`.
- **Страховка:** nightly-прогон полного пайплайна на `main` с `-count=1`, чтобы кэш тестов не скрывал зависимость от окружения.

Скелет:

```yaml
name: ci
on:
  pull_request:
  merge_group:          # полный прогон перед попаданием в main

concurrency:
  group: ci-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: true

jobs:
  changes:
    runs-on: [self-hosted, linux]
    outputs:
      services: ${{ steps.affected.outputs.services }}   # JSON-массив
      go_shards: ${{ steps.affected.outputs.go_shards }}
    steps:
      - uses: actions/checkout@v4   # запинить на SHA
        with: { fetch-depth: 0 }
      # merge_group -> всё; pull_request -> diff против merge-base + reverse deps
      - id: affected
        run: ./ci/affected.sh "${{ github.event_name }}" >> "$GITHUB_OUTPUT"

  go-test:
    needs: changes
    runs-on: [self-hosted, linux]
    strategy:
      matrix: { shard: [1, 2, 3, 4] }
    env:
      GOCACHE: /var/cache/go-build      # постоянный том раннера
      GOMODCACHE: /var/cache/gomod
    steps:
      - uses: actions/checkout@v4
      # шардирование по историческому времени пакетов, не по алфавиту
      - run: ./ci/go-test-shard.sh ${{ matrix.shard }} 4

  build:
    needs: changes
    if: needs.changes.outputs.services != '[]'
    runs-on: [self-hosted, linux]
    strategy:
      matrix: { service: "${{ fromJSON(needs.changes.outputs.services) }}" }
    steps:
      - uses: actions/checkout@v4
      - run: ./ci/build-image.sh ${{ matrix.service }} ${{ github.sha }}

  e2e:
    needs: build
    if: ${{ !failure() && !cancelled() }}   # запускать и когда build пропущен
    runs-on: [self-hosted, linux]
    strategy:
      matrix: { shard: [1, 2, 3] }
    steps:
      - uses: actions/checkout@v4
      - run: npx playwright test --shard=${{ matrix.shard }}/3
```

## Шаг 4. e2e: шарды + флейки

- **Шардирование:** `--shard=N/3` превращает 7 мин примерно в 2,5–3. Плюс оверхед на подъём окружения в каждом шарде, поэтому поднимайте окружение из готовых образов, а не собирайте заново.
- **Флейки 1/6** сейчас стоят до 38 мин на каждый re-run all. Что делать:
  1. В CI `retries: 2` и `trace: 'on-first-retry'` в `playwright.config`. Упавший тест перезапускается точечно за секунды, а не весь пайплайн. Отчёт Playwright помечает такие тесты как flaky. Это видимость, а не лечение.
  2. Раз в неделю выгружать список flaky и чинить топ-5. Обычно причины такие: `waitForTimeout` вместо web-first assertions, общие тестовые данные между воркерами, гонки на старте сервисов (нет healthcheck/readiness перед тестами).
  3. Карантин: тег `@quarantine`, такие тесты гоняются отдельным non-required job, чтобы не блокировать мёрж. У каждого есть владелец и срок.
  4. Людям: «Re-run failed jobs», а не «Re-run all jobs». После шага 1 это перезапуск одного шарда.

Флейки почти не двигают медиану, но сильно бьют по p75/p90 и по тому, как люди ощущают CI. Поэтому шаг обязательный, хоть и стоит четвёртым.

## Шаг 5. Мощности раннеров

Сейчас PR занимает 1 раннер на 38 мин. После шагов 1–4 это ~8–10 параллельных job, но каждый короткий. На 8 раннерах при нескольких одновременных PR очередь может съесть весь выигрыш. Поэтому смотрите queue time из шага 0.

- **Варианты:**
  - автоскейлинг (actions-runner-controller на k8s) с отдельными пулами: лёгкие для lint/changes, тяжёлые для go-test/build;
  - или больше job на хост через несколько runner-процессов, если хватает CPU и RAM.
- **Стоимость:** автоскейлинг в облаке добавляет расходы на ноды. Возможно, частично это окупится за счёт `cancel-in-progress` и affected-режима, но это надо проверить. Кэши на постоянных томах конфликтуют с полностью ephemeral-подами, так что нужен PVC или hostPath на ноду.

## Чем проверить результат

- Медиана и p90 длительности workflow и queue time до и после каждого шага (GitHub API `actions/runs` или экспорт в Grafana).
- Доля re-run в неделю.
- Контроль корректности affected: раз в неделю сравнить, ловил ли merge queue падения, которые PR-прогон пропустил. Если такое бывает часто, значит, граф зависимостей в `affected.sh` неполный.

## Откат

Каждый шаг — отдельный PR в `.github/workflows`, откатывается revert'ом. Merge queue выключается в branch protection. Если affected-логика окажется ненадёжной, временно заставьте `changes` всегда отдавать «всё». Параллелизм и кэши останутся, и это всё равно примерно 18–20 мин вместо 38.
