**Short answer:** I'd go with Plan 2's shape: replicate from the monolith's WAL, then do a short write freeze to cut over. I'd drop the Kafka + Debezium part unless you already run it. For one table going from Postgres 15 to Postgres 15, **native logical replication** (publication/subscription) gives you CDC without new infrastructure. That answers the Plan 1 camp's objection and still avoids the drift problem the Plan 2 camp is right about.

## Why I wouldn't do Plan 1 (dual-write)

The Plan 2 people are right. Dual-write drifts for structural reasons, and more care doesn't fix that:

- **No atomicity across two databases.** Write A succeeds and write B fails or times out. Now you either roll back A, which is hard inside a Django request, or you log it and repair it later. At 2k writes/s, "rare" failures still add up to thousands of divergent rows per week.
- **Ordering races.** Two concurrent updates to the same order can commit in one order on DB1 and in the other order on DB2. Each write succeeded, and the final state is still wrong.
- **Backfill vs. live-write race.** The batch script reads row X, a live update then changes X in both DBs, and the backfill writes its stale copy over the new one. You need upsert-if-newer logic with a reliable version column, and most schemas don't have one.
- **"Counts match" doesn't prove anything.** Equal counts tell you nothing about equal contents. You'd need per-range checksums anyway, and that's the tooling you're trying to avoid.
- **Request-path cost.** It adds latency and a new failure mode to every order write while the migration runs.

The usual fix for dual-write is a transactional outbox plus a relay. That's CDC built by hand, so you end up with Plan 2 anyway.

## What I'd do instead: Plan 2 without Kafka

**Phase 0: find the coupling first. This is the actual hard part.**
- Grep the monolith for every ORM path that touches `orders`: `select_related`, joins, FKs pointing *to* orders from other tables, raw SQL, reports, admin.
- Those code paths break when orders moves to another DB, whichever sync method you use. Each one has to go through the new service's API or a local read replica before cutover.

**Phase 1: replicate.**
- Monolith DB: `CREATE PUBLICATION orders_pub FOR TABLE orders;`. It needs `wal_level = logical`, and changing that requires a restart, so plan it.
- New DB: create a schema-compatible `orders` table, then `CREATE SUBSCRIPTION ... PUBLICATION orders_pub`.
- Keep the new service's table **identical** during migration. Do schema redesign *after* cutover, when the service owns the data. Mixing transformation into replication is where Debezium actually earns its place, and you probably don't need it yet.

**Phase 2: verify continuously.**
- Watch replication lag (`pg_stat_replication` / `pg_stat_subscription`) and retained WAL on the source.
- Reconcile with per-ID-range checksums (e.g. hash of the row's text representation, grouped into ranges of 1M IDs) on both sides. Row counts alone aren't enough.
- Optionally shadow-read: the new service answers read traffic in the background and you diff its responses.

**Phase 3: cutover (target under 60s of write freeze).**
1. Feature flag: order writes in the monolith return a retryable error or queue briefly.
2. Wait until the subscription has caught up to the source's current LSN.
3. Final checksum on the hot ID range (recent orders).
4. **Fix sequences.** Logical replication does not replicate sequence values. Set the new DB's sequence to max(id) + a safety gap. Forgetting this step is how cutovers go wrong.
5. Flip the flag: writes go to the new service.
6. Drop the subscription.

**Phase 4: rollback path.** Before step 5, set up reverse replication (new DB publishing back to the old one) so you can flip back for a few days without losing writes. Tear it down once you trust the new service.

## Risks to plan for

- **Initial sync of 900M rows.** `copy_data = true` runs a single long COPY per table. The slot retains WAL on the source for the whole copy, and at 2k writes/s that can be a lot of disk. Measure your WAL generation rate and size the source's free space before starting. If it's too slow, the alternative is to create the slot first, take a consistent snapshot/dump, restore it, then start streaming from the slot. That takes more steps, but you control it.
- **Replication slot hygiene.** An abandoned or stalled slot will fill the monolith's disk and take down the *whole* monolith, not just orders. Alert on retained WAL size.
- **`REPLICA IDENTITY`.** Updates and deletes need a primary key, or `REPLICA IDENTITY FULL`, which is expensive at this size. Confirm `orders` has a PK.
- **DDL is not replicated.** Freeze schema migrations on `orders` for the migration window, or apply them to both sides by hand.
- **Read flip before write flip.** If you move reads to the new service first, replication lag breaks read-your-writes. Either keep reads on the monolith until the write cutover, or route "just wrote" reads to the source.

## When I'd switch to Debezium + Kafka

- You already run Kafka and have ops experience with it.
- You need to transform or reshape data during migration, not after.
- Other consumers (analytics, search, other services) want an orders event stream anyway. Then the infra pays for itself beyond this migration.

If none of those apply, native logical replication gets you the same guarantees with far fewer moving parts.
