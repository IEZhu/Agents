**Short answer:** I'd go with Plan 2's architecture, which is one-way log-based replication followed by a short write freeze and cutover. I would probably skip Debezium and Kafka, though. Postgres 15 has native logical replication that can stream the `orders` tables straight into the new service's database. That takes away most of the "too much infra" objection and keeps the property that matters, which is that the source of truth is never written twice.

The Plan 2 people are right about drift. The Plan 1 people are right that you probably don't need a Kafka platform just to move one domain.

## Why I wouldn't do Plan 1 (dual-write in the request path)

At 2k writes/s the failure modes aren't edge cases. They'll happen every day.

- **No atomicity across two DBs.** Suppose the write to DB A commits and the write to DB B fails, times out, or the pod dies between the two. Now the databases have diverged. You can retry, but a retry can't cover a process crash. Fixing that properly means an outbox table plus a relay, and that is CDC built by hand.
- **Ordering under concurrency.** Two requests updating the same order can commit in order A→B on one DB and B→A on the other. Both writes "succeeded", yet the final states differ.
- **Backfill races live writes.** The batch script reads row X at T1. A live request updates X at T2 and dual-writes it. The script then writes its stale T1 copy over the new one. You need per-row versioning or `WHERE updated_at <` guards everywhere, and every write path has to get them right.
- **"Counts match" proves almost nothing.** Two tables with 900M rows each can have identical counts and still differ in thousands of rows. You'd need content checksums anyway.
- **It touches every write path.** Every ORM `save()`, `bulk_update`, `QuerySet.update()`, raw SQL, admin action, and management command has to dual-write. Missing even one is a silent drift source. Django makes this especially easy to miss, because `QuerySet.update()` and `bulk_*` skip `save()` and signals.

Plan 1 also puts the new database's latency and availability into your monolith's request path for the whole migration.

## What I'd do instead

**Phase 0: move the data as-is, then refactor the schema.** Keep the new service's tables schema-compatible with the monolith's for now. If you need to reshape the model, do it after the cutover inside the new service. Trying to transform and migrate at the same time is what really forces you into Debezium plus custom consumers.

**Phase 1: replicate.**
- On the monolith DB, create a `PUBLICATION` for the orders tables. That's `orders` plus any child tables the domain owns, such as line items and status history.
- On the new DB, create a `SUBSCRIPTION` with the initial copy enabled, so it snapshots and then streams changes.
- Check that every published table has a primary key, or set `REPLICA IDENTITY` explicitly. Updates and deletes won't replicate correctly otherwise.
- PG 15 also added row filters and column lists on publications, in case you only need part of the data. That's from memory, so check the PG 15 docs before you rely on it.

**Phase 2: move reads early.** The new service can serve reads from its replica as soon as lag is consistently low. Two cases need care:
- Any flow that needs to read its own writes. Keep those on the monolith until cutover.
- Monolith code that joins `orders` with other tables in SQL. This is often the real long pole of the whole project, more than the data movement. I'd `grep` for those joins now.

**Phase 3: cutover, within the ~2 minute freeze.**
1. Turn on the write freeze for orders in the monolith. Use a feature flag that returns 503/retry, or queue the writes if you can. Keep writes to other domains running.
2. Wait for replication lag to reach zero. The slot's confirmed LSN on the source should catch up to the current WAL LSN. With healthy lag this takes seconds.
3. Run fast verification: counts plus checksums on recent partitions or ID ranges. The full-table checksums should already have run before the freeze day.
4. **Advance the sequences on the new DB.** Logical replication doesn't replicate sequence values, and this is the classic cutover bug: the first insert after cutover hits a duplicate PK. Set each sequence to `max(id)` plus a safety margin.
5. Switch writes to the new service and lift the freeze.
6. Set up reverse replication (new → old) *before* lifting the freeze, if you can. That's your rollback path. Without it, rolling back means a second data migration under pressure.

Rehearse this at least twice against a production-sized copy and time each step. The 2 minutes is a budget you should measure, not assume.

## Risks with this approach (and Plan 2 in general)

- **Initial copy of 900M rows.** The replication slot holds WAL on the source for the whole copy, which can take hours. Plan for the extra disk, watch `pg_replication_slots`, and alert on retained WAL. If the copy is too slow, an alternative is to create the slot first, restore a snapshot or dump into the new DB, and then start streaming with the initial copy disabled. That route is more fiddly, so test it.
- **Stalled consumer = source disk risk.** An abandoned slot can fill the monolith's disk. Set `max_slot_wal_keep_size` (PG 13+) so a stuck subscriber breaks replication instead of breaking production.
- **DDL isn't replicated.** Freeze schema changes to the orders tables during the migration window, or apply each change on both sides in a deliberate order.
- **When Debezium/Kafka *is* worth it:** when you need to transform data in flight, fan the changes out to other consumers (search, analytics, events), or already run Kafka. If so, Plan 2 as written is fine. You'd also get an event stream the new service may want anyway. Just don't adopt Kafka *only* for this migration.

## Confidence

**MEDIUM.** The architectural call is solid: dual-write drift and backfill races are well-known failure modes, and log-based replication with a short freeze is the standard pattern. Before committing, verify the version-specific details against the PG 15 docs and time the whole cutover in a rehearsal, since I haven't seen your schema or write paths. The details to check are the publication features, sequence handling, and slot settings.
