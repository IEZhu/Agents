**Коротко:** 38 → ~12 мин не получится выжать одним кэшем. Нужны три вещи: (1) на PR запускать только затронутое, а полный прогон перенести в **merge queue**, тогда покрытие перед main не теряется; (2) распараллелить критический путь и шардировать его; (3) убрать повторную работу (Go build/test cache, BuildKit cache, одна компиляция вместо 12). Флейки на медиану почти не влияют, но бьют по p90 и по нервам, поэтому их чиним отдельным треком.

Порядок ниже выбран так: сначала безопасные изменения, которые ничего не могут сломать, потом изменения, которые меняют *что* запускается.

## Шаг 0 — Замерить (1 день)

Без этого не поймёте, какой шаг что дал.

- Время каждого job и **время ожидания раннера в очереди**. С 8 раннерами и шардированием очередь легко станет новым узким местом.
- Какие Go-пакеты дают основную часть из 17 минут: `go test -json ./... | ` → агрегировать `Elapsed` по пакетам. Обычно 2–3 пакета с интеграционными тестами (testcontainers, БД) съедают половину.
- Статистика флейков по конкретным тестам Playwright: JSON reporter + сбор в артефакт.
- Проверить, идут ли сейчас lint / test / build **последовательно**. Если да, это самый дешёвый выигрыш.

## Шаг 1 — Быстрые безрисковые победы (ожидаемо 38 → ~20–22 мин)

**1.1 Параллельные jobs + отмена устаревших прогонов**

```yaml
concurrency:
  group: ci-${{ github.workflow }}-${{ github.event.pull_request.number || github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}  # не отменяем merge queue / main
```

lint, go-test и docker-build должны быть независимыми jobs. От build зависит только e2e (`needs: build`).

**1.2 Go cache на self-hosted раннерах.** Раннеры живые, поэтому держите `GOCACHE` и `GOMODCACHE` на локальном диске раннера по фиксированному пути, а не в `actions/cache`: upload/download 1–2 ГБ сами по себе съедают минуты.

```yaml
env:
  GOCACHE: /opt/ci-cache/go-build
  GOMODCACHE: /opt/ci-cache/go-mod
```

Тестовый кэш `go test` сработает только при следующих условиях (поведение по памяти, проверьте на своей версии Go):
- нет `-count=1`. Если он стоит «на всякий случай», уберите его для PR;
- тесты не зависят от меняющихся env и файлов вне модуля: Go отслеживает прочитанные env/файлы, и любое изменение инвалидирует кэш;
- с `-coverprofile` кэш, насколько я помню, работает в современных версиях Go (не проверено здесь).

Если параллельных job на раннере несколько, разнесите кэш по слотам раннера или смиритесь с конкуренцией за lock. Go cache рассчитан на конкурентный доступ, но диск станет узким местом.

**1.3 Docker: компилировать один раз, образы делать тонкими.** 12 минут на 12 образов почти наверняка значат, что каждый Dockerfile заново качает модули и компилирует общий код. Варианты по эффективности:

1. **Лучший вариант:** один job собирает все бинарники `go build -o out/ ./cmd/...` с тёплым GOCACHE (обычно это десятки секунд, а не минуты), а Dockerfile каждого сервиса только делает `COPY out/<svc> /app` поверх distroless/alpine (pin по digest). Сборка образа занимает секунды.
2. Если Dockerfile нужны самодостаточные: BuildKit cache mounts

   ```dockerfile
   RUN --mount=type=cache,target=/go/pkg/mod \
       --mount=type=cache,target=/root/.cache/go-build \
       go build -o /out/svc ./cmd/svc
   ```

   плюс `docker buildx bake` для параллельной сборки всех таргетов одним вызовом и persistent builder на раннере (кэш BuildKit живёт локально). Кэш в registry (`type=registry`) нужен, только если раннеры не делят кэш, а 8 раннеров его не делят. Так что либо registry cache, либо шардирование с привязкой к раннеру.
3. На PR не пушить образы, которые не нужны e2e.

**1.4 Playwright: шардирование + retry вместо «re-run all».**

```ts
// playwright.config.ts
retries: process.env.CI ? 2 : 0,
use: { trace: 'on-first-retry' },
```

```yaml
strategy:
  matrix:
    shard: [1, 2, 3]
steps:
  - run: npx playwright test --shard=${{ matrix.shard }}/3
```

Retry на уровне теста стоит секунды, а «re-run all» стоит 38 минут. Это меняет экономику флейков сильнее, чем что-либо ещё. Но retry **маскирует** флейки, поэтому обязательно делайте шаг 4.

## Шаг 2 — Merge queue с полным прогоном (предпосылка для шага 3)

Именно это даёт «без потери покрытия перед мёржем»: полный пайплайн (все тесты, все образы, весь e2e) гоняется на `merge_group`, то есть на коммите «PR + актуальный main». Это даже строже, чем текущая схема, где PR тестируется против устаревшего main.

```yaml
on:
  pull_request:
  merge_group:
  push:
    branches: [main]
```

В branch protection сделайте required checks, которые существуют и в PR-, и в merge_group-прогоне с одинаковыми именами. Иначе очередь зависнет. Доступность merge queue для приватных репозиториев зависит от плана GitHub (по памяти: organization-репозитории на Team/Enterprise; не проверено, сверьтесь с документацией).

**Стоимость:** каждый мёрж запускает полный прогон. При высокой частоте мёржей настройте в очереди группировку (merge several PRs per group), иначе 8 раннеров не хватит.

## Шаг 3 — Affected-only на PR (ожидаемо ~20 → ~10–12 мин медиана)

Главный рычаг: типичный PR трогает 1–2 сервиса из 12.

**Go:** граф зависимостей через `go list`, а не «папка изменилась → тестируем папку». Иначе изменение в `pkg/common` пропустит зависящие сервисы.

```bash
#!/usr/bin/env bash
# affected.sh — печатает сервисы, чьи транзитивные зависимости затронуты диффом
set -euo pipefail
BASE="${1:-origin/main}"
MODULE=$(go list -m)
changed_pkgs=$(git diff --name-only "$BASE"...HEAD -- '*.go' go.mod go.sum \
  | xargs -r -n1 dirname | sort -u | sed "s|^|$MODULE/|")

# go.mod/go.sum изменились → считаем затронутым всё
if git diff --name-only "$BASE"...HEAD | grep -qE '^go\.(mod|sum)$'; then
  ls cmd; exit 0
fi

for svc in $(ls cmd); do
  deps=$(go list -deps "./cmd/$svc/..." | grep "^$MODULE" || true)
  for p in $changed_pkgs; do
    if grep -qx "$p" <<<"$deps"; then echo "$svc"; break; fi
  done
done
```

Это набросок. Проверьте на своей структуре: как лежат `cmd/`, один ли `go.mod`, есть ли `internal/` вне сервисов. Для тестов нужен обратный граф: какие *тестовые* пакеты импортируют изменённые. Тот же подход, только через `go list -deps -test`. Готовые альтернативы: Bazel/Pants (дорого внедрять) или path-based фильтры `dorny/paths-filter` (дёшево, но грубо). Промахи affected-детекции в итоге ловит merge queue из шага 2, и поэтому шаг 2 идёт первым.

**Выход в матрицу:**

```yaml
jobs:
  detect:
    outputs:
      services: ${{ steps.a.outputs.services }}
    steps:
      - uses: actions/checkout@v4   # закрепить по SHA
        with: { fetch-depth: 0 }
      - id: a
        run: echo "services=$(./affected.sh origin/${{ github.base_ref }} | jq -Rsc 'split("\n")|map(select(.!=""))')" >> "$GITHUB_OUTPUT"
  test:
    needs: detect
    if: needs.detect.outputs.services != '[]'
    strategy:
      matrix:
        service: ${{ fromJson(needs.detect.outputs.services) }}
```

**Frontend/e2e на PR:** запускать, если затронут фронт или сервисы, которые он вызывает. Можно дробнее: помечать Playwright-спеки тегами по сервисам (`@billing`) и гонять `--grep`. Полный e2e всё равно пройдёт в merge queue.

**Шардирование тяжёлых Go-пакетов:** если после шага 0 видно, что 2–3 пакета дают основную часть времени, выносите их в отдельные jobs матрицы. Другой вариант: split по `go test -list` + `-run` regex.

## Шаг 4 — Флейки (параллельно с 2–3, постоянный процесс)

- **Карантин:** тест, который упал и прошёл на retry, автоматически попадает в отчёт. Тест с частотой флейков выше порога помечается `test.fixme` / тегом `@quarantine` и исключается из required-прогона, а на него заводится issue с владельцем. Карантинные тесты гоняются в отдельном non-blocking job, чтобы видеть, починили ли их.
- **Типовые причины в Playwright:** `waitForTimeout` вместо web-first assertions (`expect(locator).toBeVisible()`), общие тестовые данные между шардами и воркерами, отсутствие изоляции окружения (один стенд на параллельные прогоны), анимации.
- **Метрика:** «прогонов, упавших хотя бы с одним retry». Цель — довести с ~17% до < 2%.

## Шаг 5 — Ёмкость раннеров

После шардирования один PR занимает не 1 раннер, а 5–8 одновременно. При 8 раннерах и нескольких активных PR медиана будет упираться в очередь, а не в выполнение. Варианты:

- Больше слотов на хост (несколько runner-процессов на мощной машине с общим Go/BuildKit кэшем). Это дешевле всего и сохраняет локальный кэш.
- Autoscaling через Actions Runner Controller (ARC) на K8s. Минус: эфемерные раннеры теряют локальный кэш, поэтому понадобятся PVC-кэш или registry cache. Внедрять стоит, только если метрика очереди из шага 0 показывает, что проблема именно в ней.
- Cost: больше хостов значит больше денег. Считайте по данным очереди, а не заранее.

## Ожидаемый бюджет медианного PR (оценка, не замер)

| Этап | Время |
|---|---|
| checkout + detect | ~1 мин |
| lint (параллельно) | ~2–3 мин |
| go test affected, тёплый кэш, шарды | ~3–6 мин |
| build бинарников + тонкие образы | ~2–3 мин |
| e2e, 3 шарда (после build) | ~3 мин |
| **Критический путь** (detect → build → e2e) | **~8–11 мин** |

Числа — моя оценка по типичным монорепо. Реальный результат зависит от того, что покажет шаг 0: если 17 минут go test — это интеграционные тесты с БД, кэш им не поможет, их придётся шардировать.

## Blast radius и откат

- **Шаг 1:** затрагивает только скорость. Откат — revert workflow-файла. Главный риск — «грязный» кэш на раннере. Держите ручной `workflow_dispatch` для очистки `/opt/ci-cache`.
- **Шаги 2–3:** риск — affected-детекция пропустит зависимость. Страховка — полный прогон в merge queue, так что main не пострадает, пострадает только скорость очереди. Откат: убрать фильтр, и PR снова гоняет всё. Держите старый полный workflow включаемым флагом (`vars.CI_FULL_ON_PR == 'true'`) на время перехода.
- **Merge queue:** если required checks названы не так, мёржи встанут. Включайте в нерабочее время и сначала на одном репо или ветке.
- Все actions в YAML закрепляйте по commit SHA, а не по тегу `@v4`. Выше теги оставлены для читаемости.
