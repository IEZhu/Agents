## Latest user message
Working on a simple hitscan pistol for my Roblox FPS. The LocalScript raycasts from the camera on mouse click, and if it hits a Humanoid it does ShootEvent:FireServer(hitHumanoid, 25). Server script just does hitHumanoid:TakeDamage(dmg). Fire rate is supposed to be 4 shots/sec, the LocalScript has a task.wait(0.25) cooldown. Playtesting with friends feels good. Before I add a shotgun and a sniper using the same system, anything I should change in the architecture?

## Rubric (what a strong answer does)
1. Flags that the client-sent damage value and client-side cooldown can be bypassed by exploiters, and moves damage lookup and fire-rate enforcement to the server (per-player last-shot timestamp)
2. Adds server-side validation of the hit: argument type check, target is a live Humanoid, and a range/line-of-sight or distance check from the shooter
3. Proposes a weapon stats table/ModuleScript held on the server so shotgun and sniper reuse the system without trusting client numbers
4. Advice is concrete and fits the stated hitscan design rather than generic Roblox tips

## Answer A
Yes. Change it before you add more guns, because right now the server believes everything the client says. It feels fine with friends because your friends aren't exploiting. Anyone running an executor can do this:

```lua
for _, p in game.Players:GetPlayers() do
    ShootEvent:FireServer(p.Character.Humanoid, 1e9)
end
```

That kills every player at once, from anywhere on the map, through walls, with no cooldown. There are three problems:

1. **The client picks the damage.** The `25` arrives in a RemoteEvent argument, so it can be any number.
2. **The client picks the target.** The server never checks line of sight, distance, or that the shooter is even alive and holding a gun.
3. **Fire rate is only enforced on the client.** An exploiter deletes or skips your `task.wait(0.25)` and fires 1000 times a second.

Adding a shotgun and a sniper to this design copies all three problems into each new weapon. The fix is also the architecture that makes new weapons cheap to add.

## The shape to aim for

- **The client sends intent, not results.** It says "I fired weapon X from here, in this direction." It never sends damage, and it never has the final say on what got hit.
- **Weapon stats live in one shared config.** The server reads damage, fire rate, range and spread from it. The client can read the same module for UI and effects, but its copy is never trusted.
- **The server enforces fire rate, runs the raycast itself, and applies damage.**
- **A new weapon is a new config entry**, not new networking code.

### 1. Shared weapon config (ModuleScript in `ReplicatedStorage.Shared.WeaponConfig`)

```lua
export type WeaponStats = {
    Damage: number,             -- per pellet
    FireInterval: number,       -- seconds between shots
    Range: number,              -- studs
    Pellets: number,
    SpreadDegrees: number,      -- cone half-angle
    HeadshotMultiplier: number,
}

local WeaponConfig: {[string]: WeaponStats} = {
    Pistol  = { Damage = 25, FireInterval = 0.25, Range = 300,  Pellets = 1, SpreadDegrees = 0, HeadshotMultiplier = 1.5 },
    Shotgun = { Damage = 12, FireInterval = 0.9,  Range = 60,   Pellets = 8, SpreadDegrees = 6, HeadshotMultiplier = 1   },
    Sniper  = { Damage = 90, FireInterval = 1.5,  Range = 1500, Pellets = 1, SpreadDegrees = 0, HeadshotMultiplier = 2   },
}

return WeaponConfig
```

The numbers are placeholders to tune in playtests.

### 2. Server handler (Script in `ServerScriptService`)

```lua
local Players = game:GetService("Players")
local ReplicatedStorage = game:GetService("ReplicatedStorage")

local WeaponConfig = require(ReplicatedStorage.Shared.WeaponConfig)
local ShootEvent = ReplicatedStorage:WaitForChild("ShootEvent")

local FIRE_RATE_TOLERANCE = 0.9  -- accept shots slightly early to absorb network jitter
local MAX_ORIGIN_OFFSET = 15     -- studs allowed between claimed origin and shooter's head (camera offset)

local lastShotTime: {[Player]: {[string]: number}} = {}
local rng = Random.new()

local function applySpread(direction: Vector3, spreadDegrees: number): Vector3
    if spreadDegrees <= 0 then
        return direction
    end
    local aim = CFrame.lookAt(Vector3.zero, direction)
    local roll = rng:NextNumber(0, 2 * math.pi)
    local tilt = rng:NextNumber(0, math.rad(spreadDegrees))
    return (aim * CFrame.Angles(0, 0, roll) * CFrame.Angles(tilt, 0, 0)).LookVector
end

local function isOnCooldown(player: Player, weaponName: string, interval: number): boolean
    local times = lastShotTime[player]
    if not times then
        times = {}
        lastShotTime[player] = times
    end
    local now = os.clock()
    local last = times[weaponName]
    if last and now - last < interval * FIRE_RATE_TOLERANCE then
        return true
    end
    times[weaponName] = now
    return false
end

ShootEvent.OnServerEvent:Connect(function(player: Player, weaponName: any, origin: any, aimDirection: any)
    -- Type-check everything: exploiters can send any value, including nil or NaN
    if typeof(weaponName) ~= "string" or typeof(origin) ~= "Vector3" or typeof(aimDirection) ~= "Vector3" then
        return
    end
    local config = WeaponConfig[weaponName]
    if not config then return end

    -- Written as "not (x within range)" so NaN fails the check (every comparison with NaN is false)
    local aimLength = aimDirection.Magnitude
    if not (aimLength > 0.5 and aimLength < 1.5) then return end

    -- Shooter must be alive and actually holding this weapon
    local character = player.Character
    local humanoid = character and character:FindFirstChildOfClass("Humanoid")
    local head = character and character:FindFirstChild("Head")
    if not (humanoid and head and humanoid.Health > 0) then return end
    local tool = character:FindFirstChild(weaponName)
    if not (tool and tool:IsA("Tool")) then return end

    if isOnCooldown(player, weaponName, config.FireInterval) then return end

    if not ((origin - head.Position).Magnitude <= MAX_ORIGIN_OFFSET) then return end

    local params = RaycastParams.new()
    params.FilterType = Enum.RaycastFilterType.Exclude
    params.FilterDescendantsInstances = { character }

    -- Server rolls the spread and adds up damage per target, so 8 pellets = 1 TakeDamage call
    local damageByHumanoid: {[Humanoid]: number} = {}
    for _ = 1, config.Pellets do
        local direction = applySpread(aimDirection.Unit, config.SpreadDegrees)
        local result = workspace:Raycast(origin, direction * config.Range, params)
        if result then
            local model = result.Instance:FindFirstAncestorOfClass("Model")
            local target = model and model:FindFirstChildOfClass("Humanoid")
            if target and target.Health > 0 then
                local damage = config.Damage
                if result.Instance.Name == "Head" then
                    damage *= config.HeadshotMultiplier
                end
                damageByHumanoid[target] = (damageByHumanoid[target] or 0) + damage
            end
        end
    end

    for target, damage in damageByHumanoid do
        target:TakeDamage(damage)
    end
end)

Players.PlayerRemoving:Connect(function(player)
    lastShotTime[player] = nil
end)
```

### 3. Client

Keep the local raycast for instant feedback: tracer, hit marker and sound. Change what you send to:

```lua
ShootEvent:FireServer("Pistol", ray.Origin, ray.Direction.Unit)
```

Here `ray` is the camera ray you already build from the mouse position. The client cooldown stays in place too, because it stops normal players from spamming the remote. The server cooldown is the one that actually counts.

## Trade-offs to know about

- **Server raycasting vs. latency.** The server raycasts against where players are *on the server*, which can differ from what the shooter saw. At friend-level ping this usually isn't noticeable for the pistol and shotgun. The sniper is the most likely to feel "I clearly hit him": long range, small targets, moving players. If playtests show that, the usual next step is to let the client report what it hit. The server then checks that report within a tolerance: line of sight, the target within some studs of its server position, and the range. Full lag compensation, where the server rewinds player positions, is the heavy version. Don't build either until you actually see the problem.
- **Shotgun visuals won't exactly match server pellets**, because each side rolls its own spread. For a close-range weapon this usually goes unnoticed. If it bothers you, send a random seed so both sides roll the same pellets. Even then, the server must decide how many pellets fire and how wide the cone is.
- **`MAX_ORIGIN_OFFSET`** depends on your camera. If you lock first person, tighten it to around 3–5 studs. If players can zoom out in third person, the camera can sit well away from the head. Set this value to at least your max zoom distance, or switch to raycasting from the head or muzzle instead of the camera.
- **API names:** `RaycastParams`, `Enum.RaycastFilterType.Exclude` (the newer name for `Blacklist`), `workspace:Raycast` and `CFrame.lookAt` are written from memory and not checked here. They're standard, but if Studio flags one, check the Creator Docs.

## Order of work

1. Switch the pistol to this system. Test it in Studio with a **Local Server** and 2 players to check that damage, fire rate and kills still work.
2. Try to break it yourself. From the server-side command bar, or a test LocalScript, fire the remote with a huge damage value, the wrong weapon name, or 100 times in a loop. None of these should do anything.
3. Add Shotgun and Sniper as config entries and Tools. Add weapon-specific behavior (the sniper's scope, the shotgun's reload) only when you need it.

This is the core of it. Once the server owns damage and fire rate, every weapon you add after this is mostly a config change.


## Answer B
Yes. Change one thing before you add more guns, because the shotgun and sniper would inherit it: **right now the client decides who gets hit and for how much.** It feels fine with friends because your friends aren't exploiting. For an exploiter, your server script does whatever this line says:

```lua
-- Any exploiter can run this from their executor:
for _, p in ipairs(game.Players:GetPlayers()) do
    ShootEvent:FireServer(p.Character.Humanoid, math.huge)
end
```

That's instant kill-all, from any distance, through walls, at unlimited fire rate. Your `task.wait(0.25)` only limits honest clients. An exploiter never runs your LocalScript's cooldown; they call `FireServer` directly.

## The fix: the client sends intent, the server decides

| Thing | Today | Should be |
|---|---|---|
| Damage | Client sends `25` | Server looks it up in a weapon config |
| Fire rate | Client `task.wait` | Server tracks the last shot time per player (keep the client wait for feel) |
| Who got hit | Client sends a Humanoid | Server raycasts, or at least checks the client's claim |
| Which weapon | Implied | Client sends the weapon name, server checks it's actually equipped |

The client should only say "I fired weapon X from here in this direction." Everything else happens on the server.

### 1. One data-driven config for all weapons

```lua
-- ReplicatedStorage/Shared/WeaponConfig (ModuleScript)
-- The client may read this for UI/cooldowns, but only the server's copy is trusted.
return {
    Pistol  = { Damage = 25, FireInterval = 0.25, Range = 300,  Pellets = 1, SpreadDegrees = 0, HeadshotMultiplier = 1.5 },
    Shotgun = { Damage = 12, FireInterval = 0.9,  Range = 60,   Pellets = 8, SpreadDegrees = 6, HeadshotMultiplier = 1 },
    Sniper  = { Damage = 90, FireInterval = 1.5,  Range = 1000, Pellets = 1, SpreadDegrees = 0, HeadshotMultiplier = 2 },
}
```

With this, adding a shotgun or sniper means adding one table entry. You don't need new remotes or new server scripts.

### 2. Server: validate, then raycast

```lua
-- ServerScriptService/WeaponServer (Script)
local Players = game:GetService("Players")
local ReplicatedStorage = game:GetService("ReplicatedStorage")

local WeaponConfig = require(ReplicatedStorage.Shared.WeaponConfig)
local ShootEvent = ReplicatedStorage.ShootEvent

local MAX_ORIGIN_OFFSET = 15      -- studs between the claimed camera origin and the head (third-person cameras sit behind the character)
local FIRE_RATE_TOLERANCE = 0.9   -- allow slight network jitter

local lastFireTime: {[Player]: number} = {}

local function isValidVector(v): boolean
    return typeof(v) == "Vector3" and v == v and v.Magnitude < math.huge -- rejects NaN / inf
end

local function getHumanoidFromPart(part: BasePart): Humanoid?
    local model = part:FindFirstAncestorOfClass("Model")
    return model and model:FindFirstChildOfClass("Humanoid")
end

local function applySpread(direction: Vector3, spreadDegrees: number): Vector3
    if spreadDegrees <= 0 then return direction end
    local spread = math.rad(spreadDegrees)
    local cf = CFrame.lookAt(Vector3.zero, direction)
        * CFrame.Angles(0, 0, math.random() * 2 * math.pi)   -- random roll
        * CFrame.Angles(math.random() * spread, 0, 0)         -- random tilt within cone
    return cf.LookVector
end

ShootEvent.OnServerEvent:Connect(function(player, weaponName, origin, aimDirection)
    -- 1. Type checks: never assume the payload is shaped the way your LocalScript sends it
    if typeof(weaponName) ~= "string" or not isValidVector(origin) or not isValidVector(aimDirection) then return end
    local config = WeaponConfig[weaponName]
    if not config or aimDirection.Magnitude < 0.5 then return end

    -- 2. Is the player alive and actually holding this weapon?
    local character = player.Character
    local humanoid = character and character:FindFirstChildOfClass("Humanoid")
    local head = character and character:FindFirstChild("Head")
    local tool = character and character:FindFirstChildOfClass("Tool")
    if not (humanoid and head and tool) or humanoid.Health <= 0 or tool.Name ~= weaponName then return end

    -- 3. Server-side fire rate
    local now = os.clock()
    local last = lastFireTime[player]
    if last and now - last < config.FireInterval * FIRE_RATE_TOLERANCE then return end
    lastFireTime[player] = now

    -- 4. Origin must be near the shooter
    if (origin - head.Position).Magnitude > MAX_ORIGIN_OFFSET then return end

    -- 5. Server raycasts; pellets are aggregated per target
    local params = RaycastParams.new()
    params.FilterType = Enum.RaycastFilterType.Exclude
    params.FilterDescendantsInstances = { character }

    local damageByHumanoid: {[Humanoid]: number} = {}
    for _ = 1, config.Pellets do
        local direction = applySpread(aimDirection.Unit, config.SpreadDegrees)
        local result = workspace:Raycast(origin, direction * config.Range, params)
        if result then
            local target = getHumanoidFromPart(result.Instance)
            if target and target ~= humanoid and target.Health > 0 then
                local multiplier = (result.Instance.Name == "Head") and config.HeadshotMultiplier or 1
                damageByHumanoid[target] = (damageByHumanoid[target] or 0) + config.Damage * multiplier
            end
        end
    end

    for target, damage in pairs(damageByHumanoid) do
        -- add team check here if you have teams
        target:TakeDamage(damage)
    end
end)

Players.PlayerRemoving:Connect(function(player)
    lastFireTime[player] = nil -- no memory leak
end)
```

### 3. Client: simpler than before

```lua
-- Inside your tool's LocalScript, on click:
local camera = workspace.CurrentCamera
local mouse = player:GetMouse()
local config = WeaponConfig[tool.Name]

if canFire then
    canFire = false
    local ray = mouse.UnitRay
    ShootEvent:FireServer(tool.Name, ray.Origin, ray.Direction)
    -- play muzzle flash / sound / tracer locally for instant feedback
    task.wait(config.FireInterval)
    canFire = true
end
```

## One tradeoff to be honest about: latency

A pure server raycast checks targets where they are **on the server now**. What your player saw on screen is a bit behind that. At normal ping it's probably fine for a slow-TTK pistol and a shotgun. With a sniper against strafing targets, players may start saying "I clearly hit him!" If that happens, the usual next step is a hybrid:

- The client does the raycast (like now) and sends the hit part and hit position.
- The server doesn't trust it blindly. It checks that the weapon is equipped, the fire rate, that the distance is within `Range`, that the hit position is within a few studs of the target's current position, and that a server raycast from origin to hit position isn't blocked by a wall.
- Damage still comes from the server config, never from the client.

Start with the server-raycast version above. Switch to the hybrid only if hit registration actually feels bad in playtests, since it's more code and more tolerance values to tune.

## Smaller things worth doing now

- **Visuals stay on the client.** Tracers, muzzle flash, hit markers and sounds go in the LocalScript. If other players need to see tracers, have the server `FireAllClients` a lightweight "player X fired" event and let each client draw it.
- **Shotgun spread lives on the server** in the code above. The client can draw its own cosmetic spread; the pellets won't match the server's exactly, which is normal and nobody notices in practice.
- **Put ammo and reload on the server too** if you add them. Otherwise it's the same exploit again ("infinite ammo").
- **Test the exploit path yourself.** In a Studio server test, run `ShootEvent:FireServer("Pistol", Vector3.zero, Vector3.new(0,0,-1))` from the client command bar a few dozen times in a loop. You should see it throttled and rejected for the bad origin, with no damage dealt.

`Workspace:Raycast`, `RaycastParams`, `Mouse.UnitRay` and `Humanoid:TakeDamage` are standard APIs I'm confident about. Still, check `Enum.RaycastFilterType.Exclude` against the Creator docs if Studio flags it. It replaced the older `Blacklist` name.

Get this foundation right and the shotgun and sniper are about 5 minutes of config each. Have fun with the tuning!
