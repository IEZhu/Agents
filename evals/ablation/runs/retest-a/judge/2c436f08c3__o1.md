```python
class CheckoutService:

        charge = self.gw.charge(cart.user_id, total)

        return total

# tests/test_checkout.py
def test_checkout():

    svc._calc_total = MagicMock(return_value=1000)
    svc._apply_discount = MagicMock(return_value=900)
    result = svc.checkout(42)
    svc._calc_total.assert_called_once()
    svc._apply_discount.assert_called_once_with(svc.repo.get_cart.return_value, 1000)
    svc.gw.charge.assert_called_once()
    assert result == 900
```

## Коротко

Вас смущает вот что: тест проверяет, **как** устроен `checkout`, а не **что** он делает. Строки выполняются, поэтому покрытие 100%, но почти ничего не проверяется. Главная бизнес-ошибка, «списали не ту сумму», и пропущенная отметка об оплате проходят тест незамеченными.

## Проверка: что можно сломать, а тест останется зелёным

| Мутация в `checkout` | Тест упадёт? |
|---|---|
| `self.gw.charge(cart.user_id, 1000)`: списываем сумму без скидки | Нет |
| `self.gw.charge(None, total)`: списываем не с того пользователя | Нет |

## Замечания

### [BLOCKER] Сумма списания не проверяется
**Строка**: `svc.gw.charge.assert_called_once()`
**Проблема**: проверяется только факт вызова, аргументы не проверяются. `assert result == 900` проверяет возвращаемое значение, а не то, что ушло в платёжный шлюз.
**Почему важно**: в платёжном коде самое важное — сколько денег списали и с кого. Именно это тест не проверяет.
**Исправление**:
```python
svc.gw.charge.assert_called_once_with(cart.user_id, 900)
```

### [BLOCKER] `mark_paid` не проверяется совсем
**Проблема**: если строку удалить, тест останется зелёным. Итог: деньги списаны, корзина не оплачена, пользователь платит повторно.
**Исправление**:
```python
svc.repo.mark_paid.assert_called_once_with(42, svc.gw.charge.return_value.id)
```

### [MAJOR] Моки приватных методов тестируемого класса
**Строки**: `svc._calc_total = MagicMock(...)`, `svc._apply_discount = MagicMock(...)`
**Проблема**: замокана логика самого тестируемого объекта. Расчёт суммы и скидки, то есть самое вероятное место для багов, не выполняется. К тому же тест привязан к внутренним именам: переименуете `_apply_discount` или объедините два метода, и тест сломается при неизменном поведении. Если же вызов метода удалить, тест тоже упадёт, хотя поведение могло остаться корректным. Тест хрупкий там, где не надо, и слепой там, где надо.
**Правило**: мокать границы (repo, gateway), а не внутренности SUT.

Попутный вопрос: если `_calc_total` и `_apply_discount` определены в этом же файле, то при таких моках их тела не выполняются, и 100% покрытия по файлу получиться не должно. Либо они покрыты другими тестами, либо лежат в другом месте, либо покрытие меряется не по тому файлу. Стоит проверить отчёт (`--cov-report=term-missing`), я этого не видел.

### [MAJOR] `MagicMock()` без `spec`
**Проблема**: мок принимает любой атрибут. Если в `repo` метод переименуют с `get_cart` на `fetch_cart`, код сломается в проде, а тест пройдёт: мок молча вернёт новый `MagicMock`.
**Исправление**: `create_autospec(CartRepository, instance=True)` / `create_autospec(PaymentGateway, instance=True)` или `MagicMock(spec=...)`. Тогда несуществующие методы и неверные сигнатуры будут падать.

### [MAJOR] Нет негативных сценариев
Весь файл — один happy path. Не хватает как минимум:
- `gw.charge` бросает исключение → `mark_paid` **не** вызван, исключение пробрасывается (или как задумано);
- `get_cart` вернул `None` или бросил not found → `charge` не вызывается;
- `mark_paid` упал **после** успешного `charge`. Что тогда? Сейчас деньги списаны, а корзина не отмечена. Это скорее вопрос к самому `checkout` (нет идемпотентности/компенсации), но тест должен зафиксировать ожидаемое поведение. Не знаю, какое поведение задумано, это нужно решить явно.
- граничные суммы: пустая корзина, скидка больше суммы (итог 0 или отрицательный?).

### [MINOR] Порядок вызовов не зафиксирован
`charge` обязан идти до `mark_paid`. Если это важный инвариант, можно проверить через общий родительский мок и `mock_calls`, но лучше выразить его через тест на ошибку: `charge` упал → `mark_paid` не вызван.

### [MINOR] Название и структура
`test_checkout` ничего не говорит о том, что проверяется. Лучше несколько тестов по одному поведению: `test_charges_discounted_total_to_cart_owner`, `test_marks_cart_paid_with_charge_id`, `test_does_not_mark_paid_when_charge_fails`.

### [POSITIVE]
- Зависимости передаются через конструктор, поэтому сервис легко тестировать. Хорошая основа.
- Проверка `_apply_discount` с конкретными аргументами (`get_cart.return_value, 1000`) показывает, что джун понимает `assert_called_once_with`. Нужно применять это к внешним вызовам, а не к внутренним.

```python
from unittest.mock import create_autospec
import pytest

@pytest.fixture
def repo():
    return create_autospec(CartRepository, instance=True)

@pytest.fixture
def gw():

def make_cart(user_id=7):

    # расчёт суммы и скидки должен выполняться по-настоящему
    return Cart(user_id=user_id, items=[Item(price=600), Item(price=400)], discount_pct=10)

def test_charges_discounted_total_to_cart_owner(repo, gw):

    svc = CheckoutService(repo, gw)

    total = svc.checkout(42)

    gw.charge.assert_called_once_with(7, 900)

def test_marks_cart_paid_with_charge_id(repo, gw):
    repo.get_cart.return_value = make_cart()
    gw.charge.return_value.id = "ch_123"

    CheckoutService(repo, gw).checkout(42)

    repo.mark_paid.assert_called_once_with(42, "ch_123")

def test_does_not_mark_paid_when_charge_fails(repo, gw):

    repo.mark_paid.assert_not_called()
```

## Замечания

### [BLOCKER] Замоканы приватные методы самого тестируемого класса
`svc._calc_total` и `svc._apply_discount` подменены. Получается, что бизнес-логику (подсчёт суммы, скидку) этот тест вообще не исполняет.
- **Почему важно**: если в `_apply_discount` скидка считается неправильно, тест останется зелёным. Он зелёный при любой реализации этих методов.
- **Про покрытие**: в показанном фрагменте `_calc_total` и `_apply_discount` не определены. Если отчёт показывает 100% по файлу, то либо эти методы покрыты другими тестами, либо фрагмент обрезан, либо они живут в другом месте. Стоит посмотреть, откуда в отчёте взялись 100%. Этим тестом их тела точно не покрыты.
- **Как исправить**: мокать только внешние границы (`repo`, `payment_gateway`), а класс тестировать целиком: на вход реальная корзина, на выходе сумма.

### [BLOCKER] Не проверяется сумма, которую списали
`svc.gw.charge.assert_called_once()` без аргументов. Это главный эффект метода, и он не проверен.
- **Сценарий**: кто-то по ошибке передаёт в `charge` `total` до скидки (1000 вместо 900). `result == 900` пройдёт, `assert_called_once()` тоже пройдёт, а клиент заплатит лишнее.
- **Как исправить**: `gw.charge.assert_called_once_with(cart.user_id, 900)`.

### [BLOCKER] `mark_paid` не проверяется совсем
Если удалить строку `self.repo.mark_paid(...)`, тест останется зелёным. Деньги списаны, а заказ не помечен как оплаченный. Это наглядный пример того, что строка покрыта, но не проверена.
- **Как исправить**: `repo.mark_paid.assert_called_once_with(42, gw.charge.return_value.id)`.

### [MAJOR] Нет тестов на ошибки
Сейчас проверен только happy path. Не хватает как минимум:
- `gw.charge` бросает исключение, значит `mark_paid` не должен вызываться, а исключение должно выйти наружу;
- `repo.get_cart` не нашёл корзину (что возвращает `None` или какое исключение бросает, зависит от контракта репозитория, уточните);
- граничные суммы: пустая корзина, `total == 0`, скидка больше суммы. Надо решить, списываем ли 0 или отрицательную сумму.

### [MAJOR] `MagicMock()` без `spec`
Мок без спецификации принимает любой атрибут. Если в gateway метод переименуют (`charge` → `create_charge`), тест продолжит проходить. Опечатка вида `assert_caled_once()` в старых версиях Python тоже молча проходила (в новых часть таких опечаток ловится, но не все, это по памяти, не проверял). Лучше `create_autospec(PaymentGateway, instance=True)` или простые fake-классы.

### [MINOR] Не проверено, что корзина запрошена по правильному id
`repo.get_cart.assert_called_once_with(42)` отсутствует. Вызов `get_cart` с чем угодно тест пропустит.

### [MINOR] Один тест на всё
Один `test_checkout` с кучей assert'ов. Когда он упадёт, по названию будет непонятно, что сломалось. Лучше несколько тестов с именами-сценариями: `test_charges_discounted_total`, `test_marks_cart_paid_with_charge_id`, `test_does_not_mark_paid_when_charge_fails`.

### [POSITIVE] Зависимости передаются через конструктор
`CheckoutService(repo, payment_gateway)` устроен так, что границы легко подменить, и правильный тест пишется без `patch`. Хорошая основа.

## Как это могло бы выглядеть

```python
from unittest.mock import create_autospec
import pytest

def make_svc(cart):
    repo = create_autospec(CartRepository, instance=True)
    gw = create_autospec(PaymentGateway, instance=True)
    repo.get_cart.return_value = cart
    return CheckoutService(repo, gw), repo, gw

def test_charges_discounted_total_and_marks_paid():
    cart = make_cart(user_id=7, items=[item(price=1000)], discount_pct=10)
    svc, repo, gw = make_svc(cart)

    result = svc.checkout(42)

    assert result == 900
    repo.get_cart.assert_called_once_with(42)
    gw.charge.assert_called_once_with(7, 900)
    repo.mark_paid.assert_called_once_with(42, gw.charge.return_value.id)

def test_does_not_mark_paid_when_charge_fails():
    svc, repo, gw = make_svc(make_cart(user_id=7, items=[item(price=1000)]))
    gw.charge.side_effect = PaymentError("declined")

    with pytest.raises(PaymentError):
        svc.checkout(42)

    repo.mark_paid.assert_not_called()
```

Имена `CartRepository`, `PaymentGateway`, `PaymentError`, `make_cart`, `item` условные, подставьте реальные из проекта. Расчёт суммы и скидки лучше покрыть отдельными табличными тестами (`pytest.mark.parametrize`) через публичный `checkout` или вынести в чистую функцию.
