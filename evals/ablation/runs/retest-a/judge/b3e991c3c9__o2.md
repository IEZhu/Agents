## Answer A
Мой прошлый совет был ошибочным, уберите `tenacity` с этой ошибки. `column "usr_id" does not exist` — детерминированная ошибка: тот же SQL упадёт одинаково хоть 5, хоть 500 раз. Retry помогает только при временных сбоях (обрыв соединения, таймаут, deadlock). Здесь он просто умножил каждый неудачный вызов на 5.

Настоящая проблема в другом: модель получает ошибку и не может её исправить. Скорее всего, она не знает реальную схему `payments`: колонка, вероятно, называется `user_id`, но это надо проверить. Поэтому модель снова генерирует тот же запрос, пока не упирается в `recursion_limit`.

## Что сделать (по приоритету)

### 1. Retry только для временных ошибок

```python

# Повторяем только сбои соединения/таймауты. Ошибки SQL (синтаксис, нет колонки) не повторяем.
TRANSIENT_DB_ERRORS = (psycopg.OperationalError,)

@retry(
    retry=retry_if_exception_type(TRANSIENT_DB_ERRORS),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, max=10),
    reraise=True,
)
def _execute(sql: str) -> list[tuple]:
    with pool.connection() as conn:
        return conn.execute(sql).fetchall()
```

Иерархия исключений указана по памяти, я её не проверял. В psycopg 3 `UndefinedColumn` (SQLSTATE 42703), насколько я помню, наследуется от `ProgrammingError`, а не от `OperationalError`. Если у вас psycopg2, SQLAlchemy или другой драйвер, классы будут другими. Сверьтесь с документацией драйвера.

### 2. Возвращайте модели ошибку, по которой её можно исправить

Голого текста ошибки мало. Модели нужно понимать, что повтор бессмыслен, и видеть, какие колонки на самом деле есть:

```python
from langchain_core.tools import tool

@tool
def run_sql(query: str) -> str:
    """Выполняет read-only SQL в Postgres. При SQL_ERROR исправь запрос, не повторяй его."""
    try:
        rows = _execute(query)
    except psycopg.ProgrammingError as e:
        return (
            f"SQL_ERROR: {e}\n"
            "Повтор того же запроса даст ту же ошибку. "
            "Вызови describe_table, чтобы узнать реальные колонки."
        )
    return format_rows(rows)


@tool
def describe_table(table: str) -> str:
    """Возвращает колонки и типы таблицы."""
    with pool.connection() as conn:
        rows = conn.execute(
            "SELECT column_name, data_type FROM information_schema.columns "
            "WHERE table_name = %s ORDER BY ordinal_position",
            (table,),  # параметризовано, имя таблицы не подставляется в строку
        ).fetchall()
    if not rows:
        return f"Таблица {table!r} не найдена"
    return "\n".join(f"{name}: {dtype}" for name, dtype in rows)
```

Если таблиц немного, ещё проще и дешевле по токенам сразу положить их схему (`CREATE TABLE ...` или список колонок) в системный промпт. Тогда `usr_id` вообще не появится.

### 3. Жёсткий предохранитель от циклов в графе

Не надейтесь только на `recursion_limit`: это аварийный тормоз, а не логика. Добавьте свой бюджет ошибок и мягкий выход:

```python
from langchain_core.messages import AIMessage, ToolMessage
from langgraph.graph import END, MessagesState

MAX_SQL_ERRORS = 3

def route_after_agent(state: MessagesState) -> str:
    last = state["messages"][-1]
    if not getattr(last, "tool_calls", None):
        return END

        1 for m in state["messages"]

        "Уточните, пожалуйста, названия таблиц/колонок."
```

## Answer B
Мой прошлый совет был ошибкой, и трейс это наглядно показывает. `column "usr_id" does not exist` — **детерминированная** ошибка: тот же SQL на той же схеме упадёт в 100% случаев. Retry помогает только при временных сбоях (обрыв соединения, deadlock, таймаут). Здесь tenacity просто умножил каждый неудачный вызов на 5, а зацикливание осталось, потому что его причина в другом.

## Почему агент зацикливается

Судя по трейсу, LLM на каждом шаге генерирует **один и тот же** запрос. Так бывает, если модель не видит, что именно не так. Обычно этому две причины (в вашем коде я их не проверял):

1. Ошибка не доходит до модели в полезном виде: исключение проглатывается, превращается в общее "tool failed" или после tenacity приходит как `RetryError` без исходного текста.
2. Модель не знает реальной схемы `payments` и гадает имя колонки (`usr_id` вместо, скорее всего, `user_id`).

Проверить можно одной командой: посмотрите, какой `ToolMessage` получает модель после неудачного `run_sql` (LangSmith или `print(state["messages"][-1])` в узле агента). Если там нет текста `column "usr_id" does not exist` и списка колонок, дело в пункте 1.

## Что делать

### 1. Retry только для временных ошибок

Уберите безусловный `@retry` и оставьте повтор только для ошибок соединения и конкурентного доступа. Пример для psycopg 3 (имена классов исключений привожу по памяти, сверьте с документацией вашего драйвера):

```python
from psycopg import errors as pg_errors
from tenacity import retry, retry_if_exception_type, stop_after_attempt, wait_exponential

TRANSIENT_DB_ERRORS = (
    pg_errors.OperationalError,        # connection lost, server restart
    pg_errors.SerializationFailure,    # SQLSTATE 40001
    pg_errors.DeadlockDetected,        # SQLSTATE 40P01
)

@retry(
    retry=retry_if_exception_type(TRANSIENT_DB_ERRORS),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=0.5, max=5),
    reraise=True,  # чтобы наружу вышло исходное исключение, а не RetryError
)
def _execute(sql: str) -> list[tuple]:
    ...
```

`UndefinedColumn`, `UndefinedTable`, `SyntaxError` (SQLSTATE 42xxx) не повторяются, а сразу возвращаются модели.

### 2. Возвращать модели ошибку, по которой можно исправить запрос

Инструмент не должен бросать исключение при ошибке в SQL. Пусть он вернёт текст ошибки и подсказку со схемой:

```python
MAX_ROWS = 200

@tool
def run_sql(query: str) -> str:
    """Run a read-only SQL query against the analytics DB."""
    try:
        rows = _execute(query)
    except (pg_errors.UndefinedColumn, pg_errors.UndefinedTable) as exc:
        return (
            f"SQL ERROR: {exc}\n"
            f"Available schema:\n{describe_tables_for(query)}\n"
            "Fix the query using ONLY these column names. Do not repeat the same query."
        )
    except pg_errors.Error as exc:
        return f"SQL ERROR ({exc.sqlstate}): {exc}. Do not repeat the same query."
    return format_rows(rows[:MAX_ROWS])
```

`describe_tables_for` — ваша функция, которая достаёт колонки из `information_schema.columns` для таблиц в запросе. Можно проще: сразу положить схему нужных таблиц в system prompt или дать агенту отдельный инструмент `describe_table`. В большинстве случаев этого уже хватает, чтобы модель на следующем шаге написала `user_id`.

Если вы используете `ToolNode` из `langgraph.prebuilt`, у него есть параметр `handle_tool_errors`, который превращает исключения в `ToolMessage` (по памяти, сверьте с документацией вашей версии). Но генерический текст ошибки хуже явной подсказки со схемой.

### 3. Предохранитель от повторяющихся вызовов

Даже при хорошем тексте ошибки модель иногда застревает. Добавьте детерминированную защиту в state:

```python
from collections import Counter

MAX_IDENTICAL_CALLS = 2

def guard_repeated_calls(state) -> dict:
    last_calls = state["messages"][-1].tool_calls
    seen: Counter = state.get("tool_call_counts", Counter())
    for call in last_calls:
        key = (call["name"], normalize_sql(call["args"].get("query", "")))
        seen[key] += 1
        if seen[key] > MAX_IDENTICAL_CALLS:
            return {"stop_reason": f"repeated identical call: {call['name']}"}
    return {"tool_call_counts": seen}
```

Поставьте его условным ребром между агентом и узлом инструментов: при `stop_reason` идите в финальный узел, который честно отвечает пользователю "не смог построить запрос: …", а не в ещё один круг.

### 4. `recursion_limit` — это аварийный тормоз, а не логика

Лимит 25 сработал правильно: без него токены жглись бы дальше. Оставьте его (`graph.invoke(inputs, config={"recursion_limit": 25})`), но ловите `GraphRecursionError` (`from langgraph.errors import GraphRecursionError`, по памяти) и отдавайте пользователю понятный ответ. Штатно агент должен останавливаться раньше, на guard'е из пункта 3.

## Порядок действий

1. Проверьте, что именно видит модель в `ToolMessage` после ошибки. Это главная диагностическая точка.
2. Сузьте tenacity до временных ошибок, `reraise=True`.
3. Возвращайте ошибку со схемой, а не исключение.
4. Добавьте guard на повторяющиеся вызовы.
