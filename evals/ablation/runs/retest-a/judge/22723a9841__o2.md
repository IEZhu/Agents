## Latest user message
Postmortem help. Our AP agent (Claude Sonnet, tool use) paid a vendor invoice twice. Trace:

1. get_invoice("INV-20931") -> {status: "approved", amount: 12400.00, currency: "EUR"}
2. pay_invoice("INV-20931", 12400.00) -> ToolError: upstream timeout after 30s
3. [model thought] "The payment failed due to a timeout. I'll retry."
4. pay_invoice("INV-20931", 12400.00) -> {ok: true, payment_id: "pay_5512"}

Bank shows two debits: pay_5498 and pay_5512. My teammate wants to just add "never retry pay_invoice" to the prompt. Is that the right fix? What would you change?

## Rubric (what a strong answer does)
1. Points out the model wrongly treated a timeout as a confirmed failure; the payment outcome was unknown
2. Recommends that after a timeout the agent re-check state via a lookup (e.g. get_invoice or a payment-status query) before deciding to pay again, rather than a blanket 'never retry'
3. Recommends a system-level safeguard such as an idempotency key on pay_invoice or a server-side check that rejects paying an already-paid invoice
4. Directly answers whether the teammate's fix is adequate and explains its downside (e.g. genuine failures are then never completed or need a human)

## Answer A
**Short answer: no.** "Never retry pay_invoice" deals with the symptom, and it does so in a component that only follows instructions most of the time. The real bug is that a tool that moves money is not idempotent, and it reported a result it didn't know ("unknown") as a failure. Fix it in the tool and payment layer so that a double payment can't happen whatever the model decides.

## What actually went wrong

1. **A timeout is not a failure.** "upstream timeout after 30s" means *we don't know whether the payment went through*. In this case it did: pay_5498 was created. The tool turned "unknown" into a `ToolError`, and the model reasonably read that as "failed."
2. **The model's reasoning followed from what the tool told it.** "The payment failed due to a timeout. I'll retry" is the sensible move if you believe the error message. The model reasoned correctly from wrong information.
3. **Nothing below the model stopped a second payment.** No idempotency key, no check on invoice state, no dedupe. The second call was treated as a brand-new payment.
4. **The agent didn't check the state before acting again.** It never called `get_invoice` again or looked up existing payments before retrying.

## Why the prompt-only fix is weak

- **It's probabilistic.** A prompt rule lowers the odds of a retry. It doesn't guarantee there won't be one. For an action that moves money, "usually" isn't good enough. Prompt rules also tend to lose force as the context gets long or the instructions start competing.
- **It creates the opposite failure.** On a timeout where the payment really did *not* go through, the invoice now stays unpaid with no signal to anyone. You swap duplicate payments for missed ones: late fees and annoyed vendors.
- **It doesn't cover other paths.** Other ways to double-pay remain: a second agent run for the same invoice, a queue redelivery, a user asking again, or a different tool name later on. Not one of them involves the model "retrying."
- **It leaves the error message misleading.** The next tool with an ambiguous timeout will fail in the same way.

## What I'd change, in priority order

### 1. Idempotency at the payment boundary (the actual fix)
- Derive a deterministic idempotency key from the business action, e.g. `pay:{invoice_id}:{approval_version}`. Don't use a random UUID per call, because the key has to be the same when the call is retried.
- The tool wrapper sends that key to the payment provider, if it supports idempotency keys. Many payment APIs do (Stripe's `Idempotency-Key` header is the best-known example), but check your bank or PSP's docs to confirm theirs does.
- If the provider doesn't support it, enforce the key yourself: write a `payment_attempt` row with a unique constraint on `(invoice_id, approval_version)` *before* calling upstream. A second insert fails, and the tool returns the existing attempt instead of paying again.

With this in place, the retry in step 4 would have been harmless: it would have returned pay_5498.

### 2. Make the invoice status an explicit state machine
```
approved -> payment_pending -> paid
                 |-> payment_unknown -> (reconcile) -> paid | approved
                 |-> payment_failed  -> approved (retry allowed)
```
- `pay_invoice` is only allowed from `approved`. It moves the invoice to `payment_pending` atomically before calling upstream.
- From `payment_pending` or `payment_unknown`, `pay_invoice` refuses and returns the current state. The model can't bypass this, whatever the prompt says.

### 3. Return typed tool results that show uncertainty
Replace the plain `ToolError` with:
```json
{"status": "outcome_unknown",
 "invoice_id": "INV-20931",
 "attempt_id": "att_...",
 "retry_safe": false,
 "next_step": "call get_payment_status(attempt_id) before any further action"}
```
Separate definite failures (`declined`, `validation_error`, with `retry_safe: true`) from ambiguous ones (timeout, connection reset, 5xx after the request was sent). The model will read "outcome_unknown, retry_safe: false" correctly. It can't be expected to guess that "timeout" means "maybe succeeded."

### 4. Add a reconciliation tool and step
- Add `get_payment_status(attempt_id)` or `list_payments(invoice_id)`, which asks the provider or bank for the true state.
- On `outcome_unknown`, the wrapper polls this for a bounded time *itself*, before returning anything to the model. The model only sees the reconciled result, or `still_unknown` after the timeout.
- `still_unknown` goes to a human queue. It is not something the model resolves on its own.

### 5. Then update the prompt, as defense in depth
A better rule than "never retry":
> Payment tools can return `outcome_unknown`. Never call `pay_invoice` again after `outcome_unknown`. Call `get_payment_status` and act on its result. If it is still unknown, escalate to a human with the attempt_id.

That handles both failure modes. Unlike "never retry," it doesn't block legitimate retries after a definite failure.

### 6. Human-in-the-loop threshold
Per the default-to-HITL principle: for payments above some amount, or any payment reached through a retry or reconciliation path, the agent prepares the payment and a human approves it. €12.4k is well within the range where one click of confirmation costs very little compared with the error it prevents. Where to set the threshold is a business call. I don't have a number to give you.

## Immediate remediation
- Reverse or recall one of pay_5498 / pay_5512, or ask the vendor for a credit note or refund.
- **Look for other occurrences.** Query the payments ledger for any invoice with more than one successful payment, and for any tool call that timed out and was followed by another `pay_invoice` on the same invoice. A pattern like this is unlikely to have happened only once.
- Find out whether other side-effecting tools (vendor creation, bank detail updates, emails) share the same "timeout = error" wrapper.

## Postmortem framing and tests
- **Root cause:** a non-idempotent tool that moves money, combined with ambiguous-failure semantics that report "unknown" as "failed." **Contributing factor:** the agent had no step to reconcile state before acting again. The model's retry was the *trigger*, not the root cause.
- **Regression tests (fault injection):**
  - The upstream call succeeds but the response times out. Expect exactly one payment and an `outcome_unknown` result. Then reconcile to `paid`.
  - The upstream fails before the request is sent. Expect `retry_safe: true`, and the retry succeeds once.
  - Two concurrent agent runs on the same invoice. Expect one payment, with the other run getting the existing attempt back.
  - A queue redelivers the same task. Expect one payment.
  - The model is told explicitly to "pay it again." Expect the tool to refuse because of the state machine.
- **Metric to monitor:** duplicate payments per invoice. The target is 0, with an alert on the first one. Also track the `outcome_unknown` rate per provider, since it tells you how often you depend on reconciliation.

Two assumptions to confirm before you commit to this design:
- **That pay_5498 is the first call.** Check that pay_5498's provider-side timestamp or request log lines up with step 2's timeout window. If it doesn't, something other than this retry may be producing duplicates.
- **That your provider supports idempotency keys.** Check its API docs for an idempotency header or parameter. If it doesn't, you'll need the local unique-constraint table from fix #1.


## Answer B
**Short answer: no.** "Never retry pay_invoice" addresses the symptom, and it only does so probabilistically. The root cause is in the tool layer: a non-idempotent money-moving tool reported an *ambiguous* outcome (timeout) as a *failure*. The model then did what most engineers would do with a "ToolError": it retried. Fix the contract first, then the prompt.

## What actually happened

- The first `pay_invoice` call did reach the payment provider and created `pay_5498`. Only the **response** timed out, after 30s. A timeout tells you "I don't know if it happened", not "it failed".
- The tool turned that unknown into `ToolError`, which the model read as a failure. Step 3's reasoning is the predictable result of how the error was surfaced.
- Nothing downstream stopped a second payment on an invoice that already had one in flight. There was no idempotency key, no state check, and no lock.

So there are three missing safeguards, and the prompt is not the right place for any of them.

## Why "never retry" is the wrong fix

1. **Prompt rules are soft.** Under a different error message, a long context, or a paraphrased tool name, the model may retry anyway. For a double payment you want a guarantee that holds 100% of the time, and a prompt instruction can't give you that.
2. **It breaks the opposite case.** If the call really did fail before it reached the bank (connection refused, 4xx validation error), "never retry" leaves an approved invoice unpaid, and a vendor ends up chasing you. You trade duplicate payments for missed payments, and the agent can't tell the two cases apart either.
3. **It doesn't cover other paths to a duplicate.** A human re-running the workflow, a queue redelivering the job, or two agent instances picking up the same invoice can all still pay twice.

## What I'd change, in priority order

### 1. Make `pay_invoice` idempotent (the actual fix)
- Derive a deterministic idempotency key from the business operation, e.g. `pay:INV-20931:v1` (or invoice ID + approval ID). Don't use a random UUID per call. That way a retry reuses the same key.
- Send it to the payment provider if it supports idempotency keys. Many payment APIs do; check your provider's docs for the exact header or field name, since I can't confirm it for your bank. If it doesn't, enforce idempotency in your own service: before submitting, write a `payment_attempt` row with a unique constraint on `invoice_id`.
- With this in place, a retry returns the original `pay_5498` instead of creating `pay_5512`. Retrying becomes safe, and you *want* the agent to be able to retry.

### 2. Guard on invoice state inside the tool, not in the model
Make the invoice an explicit state machine and enforce it server-side:

```
approved --pay_invoice--> payment_pending --provider confirms--> paid
                                   \--provider rejects--> payment_failed --(retry allowed)--> payment_pending
```

`pay_invoice` should refuse (return a structured "already in progress / already paid" result, not an error) unless the invoice is `approved` or `payment_failed`. Do the state transition atomically, with a conditional update or a row lock, so concurrent callers can't both pass the check.

### 3. Return honest, structured outcomes instead of bare errors
Replace `ToolError: upstream timeout` with something the model can reason about:

```json
{
  "status": "unknown",
  "reason": "upstream_timeout",
  "invoice_id": "INV-20931",
  "idempotency_key": "pay:INV-20931:v1",
  "safe_to_retry": true,
  "next_step": "call get_payment_status(invoice_id) before any further action"
}
```

Use three distinct outcomes: `succeeded`, `failed` (definitely not submitted, safe to retry), and `unknown` (reconcile first). Most of the model's decision quality comes from this shape.

### 4. Add a reconciliation tool
Add `get_payment_status(invoice_id)` (or `list_payments(invoice_id)`), which queries the provider or your ledger. On `unknown`, the agent checks, finds `pay_5498`, and stops. This is the "read current state before a side-effecting action" step, and the tool contract makes it cheap to do.

### 5. Then update the prompt, as the last layer
Replace "never retry" with a rule that matches the new contract:

> Before calling `pay_invoice`, confirm with `get_invoice` that status is `approved` or `payment_failed`. If `pay_invoice` returns `status: "unknown"`, do not call it again. Call `get_payment_status` first and act on what it returns. If the status is still unknown after reconciliation, stop and escalate to a human with the invoice ID and idempotency key.

This rule is defense in depth. The guarantee comes from layers 1 and 2.

### 6. Human override point for money
Consider requiring human approval for any payment action after an `unknown` outcome, and possibly above an amount threshold. The threshold is a policy choice, and 12.4k EUR may or may not be over yours. This is the one place where Co-Pilot-level control is worth the friction.

## Regression tests to add
Use fault injection against a mock provider:
- **Timeout after commit:** the provider records the payment, then the response times out. Expect exactly one payment and the agent reconciling rather than re-paying. This is your exact incident; it should be the first test.
- **Timeout before commit:** the provider never receives the call. Expect the agent to retry with the same key, ending in exactly one payment.
- **Definite failure (4xx):** expect no payment and an escalation or `payment_failed` state.
- **Concurrent double invocation:** two agents or jobs hit the same invoice. Expect exactly one payment.
- **Invoice already `paid`:** expect `pay_invoice` to refuse without calling the provider.

Track the duplicate-payment rate per invoice as a hard metric with a zero target and alerting. Also check the time from `unknown` to reconciliation.

## Immediate remediation
- Reverse or recall one of the two debits (`pay_5512` is the natural candidate) through your bank or provider, or ask the vendor for a refund or a credit note. Recall windows depend on the payment rail, so move quickly.
- Search your payment logs for any other invoice with more than one payment ID. If the tool has run for a while, this is unlikely to be the only time it happened.
- Check the timeout mismatch. Your client gave up at 30s while the provider evidently kept processing. Make the client timeout at least as long as the provider's own processing timeout, or treat anything past it as `unknown` (see point 3).

**Bottom line:** tell your teammate the prompt change is fine as an extra layer, but it isn't the fix. The fix is an idempotency key plus a server-side state guard plus a tool result that says "unknown" when the outcome is unknown. With those in place, retrying becomes safe, and that's the property you want.
