## Latest user message
Customer support flagged that some split payments are off by a cent. This is our function (Python 3.11):

```python
def split_amount(total_cents: int, n: int) -> list[int]:
    share = round(total_cents / n)
    return [share] * n
```

e.g. split_amount(1000, 3) gives [333, 333, 333] = 999. Can you give me a fixed version? We want the leftover cents to go to the first people in the list. Tests for this module currently only check split_amount(900, 3) == [300, 300, 300].

## Rubric (what a strong answer does)
1. Provides a correct fix, e.g. using divmod so the first `remainder` people get one extra cent (split_amount(1000, 3) == [334, 333, 333])
2. Adds a regression test reproducing the reported case (1000 split 3 ways) that fails on the old code and passes on the new

4. Mentions or handles invalid input such as n <= 0 (raise or document) rather than silently ignoring it

## Answer A
The fix is to divide with integers, not floats, and hand the remainder out one cent at a time: `divmod(total_cents, n)` gives the base share and the number of leftover cents, and the first `remainder` people get one extra cent each.

### Why the current version is wrong

`round(total_cents / n)` gives every person the same share, so the total can only be correct when `n` divides `total_cents` exactly. It can go wrong in either direction:

- **Under-collects:** `split_amount(1000, 3)` gives `[333, 333, 333]`, which sums to 999. One cent is lost.
- **Over-collects:** `split_amount(1001, 3)` gives `1001 / 3 = 333.67`, rounded to 334, so the list is `[334, 334, 334]` = 1002. The customer is charged a cent too much, which is arguably worse.

Your only test, `(900, 3)`, divides evenly, so it can't catch either case.

### Fixed version

```python
def split_amount(total_cents: int, n: int) -> list[int]:
    """Split total_cents into n integer shares that sum exactly to total_cents.

    Leftover cents go one each to the first people in the list, so shares
    differ by at most one cent.
    """
    if n < 1:
        raise ValueError(f"n must be a positive integer, got {n}")
    if total_cents < 0:
        raise ValueError(f"total_cents must be non-negative, got {total_cents}")

    base, remainder = divmod(total_cents, n)
    return [base + 1] * remainder + [base] * (n - remainder)
```

Notes:

- **Integers only.** No float division, so large amounts can't lose precision and there's no rounding step to get wrong.
- **Invariant:** `sum(result) == total_cents` and `max(result) - min(result) <= 1` for every valid input.
- **Negative totals are rejected** on purpose. With `divmod`, a negative total would still sum correctly, but the "extra" cents would end up on the *last* people (`divmod(-1000, 3) == (-334, 2)` gives `[-333, -333, -334]`). If you split refunds with this function, tell me which convention you want and I'll handle the sign explicitly instead of rejecting it.
- **Behavior change:** callers that pass `n <= 0` now get a `ValueError`. Before, `n = 0` raised `ZeroDivisionError` and a negative `n` returned `[]` without complaint.
- Complexity is O(n) time and space, the same as before.

## Answer B
### Analysis

**Root cause:** `round(total_cents / n)` computes one share and hands it to everyone, so any remainder (`total_cents % n`) is either lost or over-allocated. The bug goes both ways, not only under-charging:

- `split_amount(1000, 3)` → `round(333.33)` = 333 → sum **999** (1 cent lost)
- `split_amount(1000, 6)` → `round(166.67)` = 167 → sum **1002** (2 cents over-charged)

The existing test (`900, 3`) divides evenly, which is why it never caught this. Using float division on money also adds risk you don't need: stay in integers.

**Fix:** use `divmod` to get the base share and the remainder, then give one extra cent to each of the first `remainder` people.

### Implementation

```python
def split_amount(total_cents: int, n: int) -> list[int]:
    """Split total_cents into n integer shares that sum exactly to total_cents.

    Leftover cents go one each to the first people in the list, so shares
    differ by at most 1 cent and are in non-increasing order.
    """
    if n < 1:
        raise ValueError(f"n must be a positive integer, got {n}")
    if total_cents < 0:
        raise ValueError(f"total_cents must be non-negative, got {total_cents}")

    base_share, leftover_cents = divmod(total_cents, n)
    return [base_share + 1] * leftover_cents + [base_share] * (n - leftover_cents)
```

Notes:
- **Integer-only arithmetic**, so there's no float rounding at all. This is O(n) time and space, which is the minimum since you have to return n items.
- **Negative totals:** I rejected them explicitly. `divmod` floors toward negative infinity, so `divmod(-1000, 3)` gives `(-334, 2)`, and the result `[-333, -333, -334]` still sums correctly but gives the "extra" to the *last* person. If you split refunds with this function, tell me and I'll handle the sign on purpose (split `abs(total)` and negate it) rather than rely on floor semantics.
- **`n < 1`** used to raise `ZeroDivisionError` for 0 and return `[]` for negative values. It now fails fast with a clear message. This is a small behavior change for any caller that relied on the old exception type.
