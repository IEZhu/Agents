## Latest user message
Our VP of Eng just mandated 90% coverage on our main Rails 7 monolith (~180k LOC, currently at 31%) by end of Q1. The QA lead's plan: hire two contractors to write Cypress tests for every screen in the app, since "that exercises the most code per test and it's what users actually see". We already have ~120 Cypress specs that take 47 minutes in CI and fail randomly maybe 1 in 8 runs. I'm the tech lead and I need to either back this plan or push back with something better in Thursday's meeting. What should I propose?

## Rubric (what a strong answer does)
1. Pushes back on expanding Cypress to every screen: explains cost in CI time, flakiness and maintenance, and recommends keeping E2E to a small set of critical user journeys (e.g. signup/login, checkout or the core workflow)
2. Proposes shifting most new tests down to model/service-level unit tests and request/integration tests at boundaries (DB, external APIs), consistent with a pyramid shape
3. Argues that a line-coverage target alone does not measure test quality and suggests risk- or criticality-based targets (e.g. prioritising high-change or high-incident code, or checking whether tests catch faults) instead of or alongside the 90% number
4. Addresses the existing flaky 1-in-8 suite as a problem to fix (root cause, quarantine) rather than grow, and gives an actionable plan the tech lead can present

## Answer A
## Bottom line

Push back on this plan. Adding Cypress specs will slow CI and make it more flaky, and it probably won't raise your coverage number much. Don't just say no on Thursday, though. Offer a plan that still makes real progress on coverage by Q1: unit and request specs written against a risk map, a gate on changed code, stabilizing the Cypress suite you already have, and a revised overall target that you can defend with numbers.

## Why the Cypress plan fails (with numbers)

**1. It may not move the metric at all.** Your coverage number almost certainly comes from SimpleCov, which measures the Ruby process running the tests. Cypress drives a browser against a separately booted Rails server. That server's lines only count if you start SimpleCov inside it and merge its results with the RSpec/Minitest results. It can be done, but it isn't the default, and it's easy to get wrong. Before Thursday, check how your coverage is actually collected. If E2E runs aren't instrumented, the contractors' work counts for nothing.

**2. Flakiness grows with suite size.** If 1 in 8 runs fails with 120 specs, the per-spec flake rate is about 0.11%, since (1 − p)^120 ≈ 0.875 gives p ≈ 0.0011. At the same rate:

| Total Cypress specs | P(a run is green) | Serial runtime (at ~23 s/spec) |
|---|---|---|
| 120 (today) | ~88% | 47 min |
| 400 | ~64% | ~2.6 h |
| 620 | ~50% | ~4 h |

With "every screen" covered, about half of all CI runs go red for reasons unrelated to the change being tested. At that point the team stops trusting red builds, and the whole suite stops protecting you.

**3. The gap is too big for this approach.** 90% of 180k LOC means about 106k more covered lines (from ~56k to ~162k). E2E tests mostly run the happy path of controllers and views. They rarely reach error branches, edge cases in service objects, background jobs, mailers or rake tasks, and those are where the uncovered lines usually are. Most E2E suites plateau well below 90% however many screens they visit (that's a judgment from experience, not a measured figure).

**4. Coverage from E2E is executed, not asserted.** A screen test that loads a page runs hundreds of lines and checks two of them. You would hit the number without getting the thing the VP presumably wants, which is confidence that changes don't break production.

**5. Contractors without domain knowledge write tests that check very little.** This problem exists at every layer of the test pyramid, but at the E2E layer it's also the slowest and most expensive kind.

## What to propose instead

### Track 1: Put the coverage work at the right layer (the contractors go here)
- **Request specs** (or integration tests) for controllers. One test covers routing, controller, model and serialization, and it runs in milliseconds, not ~23 seconds. This gets you the most covered lines per hour of effort.
- **Model and service specs** for domain logic, prioritized by a risk map:
  - churn (git log frequency) × complexity × incident history
  - billing, auth, permissions and data-mutation paths first
- **Characterization tests** for legacy code nobody understands. They pin down current behavior before anyone refactors it.
- Turn on **branch coverage** in SimpleCov (`enable_coverage :branch`, recalled, not verified; confirm for your SimpleCov version). Line coverage alone overstates how well you're tested.

### Track 2: Stop the bleeding with a gate on changed code
- Require about 90% coverage on changed and new lines in each PR. Codecov/Coveralls patch coverage or the `undercover` gem can enforce this (tool names recalled; pick whichever fits your CI).
- This is the cheapest way to raise overall coverage over time, and it fits the VP's intent. Every PR is covered from now on.
- Add a **ratchet**: CI fails if overall coverage drops below the last recorded value.

### Track 3: Shrink the denominator honestly
- In a 180k-LOC monolith, a good share of code is probably dead. Production coverage tooling such as **Coverband** (recalled; verify fit) shows which code never runs in production.
- Delete dead code. Don't exclude it in the SimpleCov config. Deleting code is legitimate; adding exclusions for live code is gaming the metric, and someone will eventually notice.

### Track 4: Fix Cypress before growing it
- **Quarantine** the flaky specs, and track and fix them: usually fixed sleeps, shared test data, no network stubbing, or animation timing.
- **Reduce** to about 20–40 critical user journeys (signup, checkout, core workflow). Push the rest down to request or system specs.
- **Parallelize** the suite across CI nodes. Target under 15 minutes wall-clock and under 1% flake rate per run.
- New Cypress specs only for journeys that no lower layer can test.

## Target to put on the table

Here's a rough estimate, with generous rounding. Assume a request or model spec adds ~30–100 covered lines, so ~106k lines takes about 1,500–3,000 meaningful tests. Two contractors at about 10 good tests per day each, over roughly 60 working days, produce about 1,200. **So 90% overall by end of Q1 is probably not reachable honestly**, even with the better approach. If your Q1 is a fiscal quarter that ends sooner, it's even less likely.

A proposal you can defend:

| Metric | By end of Q1 | Why |
|---|---|---|
| Changed-code coverage | ≥ 90%, enforced in CI from week 1 | Fits the mandate's intent, starting now |
| Critical domains (billing, auth, etc.) | ≥ 85–90% line + branch | Coverage where incidents cost the most |
| Overall line coverage | ~55–65%, ratcheted | Realistic, keeps rising after Q1 |
| Cypress | ≤ 15 min, < 1% flaky runs | Restores trust in CI |
| Dead code removed | measured in LOC | Honestly lowers the denominator |

Your team's velocity and your codebase could shift these numbers either way. Present them as an estimate to revisit after 3–4 weeks of real throughput data.

## How to run the meeting

1. **Open by agreeing with the goal:** "We need much more test coverage, and I support the mandate's intent."
2. **Show the flake table.** It's the strongest argument you have, because it's your own data taken to its conclusion.
3. **Ask the VP one question:** "What outcome is 90% standing in for? Fewer incidents, faster releases, safer refactoring?" If the answer is outcomes, your plan serves them better. If the literal number really matters (an audit or a customer contract), you still get there faster through Tracks 1–3 than through Cypress.
4. **Give the QA lead a real role.** They own the Cypress stabilization and the critical-journey list. That's a better use of their expertise, and it turns a disagreement into a joint plan.
5. **Commit to a checkpoint:** report coverage, test throughput and CI health at week 4, then re-forecast.

One risk to mention before anyone else does: if leadership only rewards the number, people will write tests that assert nothing. Spot-check contractor PRs, or run a mutation-testing tool like `mutant` (recalled) on one critical module, to show the new tests actually catch bugs.


## Answer B
## Bottom line

Don't back the Cypress plan. With your own numbers, it probably makes CI slower and less reliable, it may add little or nothing to the coverage figure the VP is tracking, and it spends the contractor budget on the most expensive kind of test. In the meeting, question how the target is shaped rather than the goal behind it, and bring a counter-plan that raises coverage faster and more cheaply.

## Why the Cypress-for-every-screen plan fails (bring these numbers)

**1. Flakiness grows with suite size.** At 120 specs, 1 failed run in 8 means each spec flakes about 0.11% of the time (1 − (1−p)^120 = 0.125 gives p ≈ 0.0011). Keep that per-spec rate and scale the suite up:

| Cypress specs | P(a CI run fails randomly) |
|---|---|
| 120 (today) | ~12% |
| 400 | ~36% |
| 600 | ~48% |
| 1,000 | ~67% |

A 180k-LOC Rails app probably has several hundred screens. Past about 500 specs, **roughly every other run goes red for no reason**. Engineers will learn to hit "retry" and stop trusting the suite, and at that point it is worth nothing as a safety net.

**2. CI time.** 47 min / 120 specs ≈ 23.5 s per spec. Adding 500 specs adds about 200 minutes of serial runtime, which puts the suite near 4 hours. Parallelizing fixes the wall-clock time and costs you in runners and in more flakiness from shared state.

**3. The coverage may not count at all.** Your 31% almost certainly comes from SimpleCov instrumenting the Ruby process that runs RSpec/Minitest. Cypress drives a browser against a separately booted Rails server, so its Ruby coverage is only recorded if someone sets up SimpleCov in that server process and merges the results (tools like `cypress-on-rails` help with this; recalled, not verified, so check what your pipeline does today). **Before Thursday, find out which suites feed the 31%.** If Cypress isn't in it, the QA plan adds 0 points, and that alone ends the discussion.

**4. Coverage from E2E tests is shallow.** One E2E test executes many lines but asserts on almost none of them. It walks the happy path, so error branches, validations, permission checks and edge cases stay uncovered, and those are where the bugs are. Returns also shrink quickly: after the first 50 screens, each new spec mostly re-runs the same layout, auth, and base controller code. Getting from 70% to 90% with E2E tests is close to impossible.

## What to propose instead

### Phase 0: Measure and stabilize (first 2–3 weeks)
- **Confirm how coverage is measured.** Turn on SimpleCov branch coverage and produce a per-directory report so you know where the uncovered lines are.
- **Look for dead code.** Run Coverband (or similar production line-usage tracking) for a few weeks. Legacy monoliths often carry a lot of unreachable code. Deleting it raises coverage honestly and lowers maintenance cost. This is probably your cheapest source of coverage points, though how much you gain depends on the codebase.
- **Fix the Cypress suite you already have.** Quarantine flaky specs into a non-blocking job, fix the top offenders (usually timing waits, shared DB state, test order), and split across parallel runners. Target: under 15 min and under 2% flake rate.

### Phase 1: Put contractor effort where coverage is cheap and valuable
Keep the two contractors and change what they write:
- **Request specs** (controller → model → view, no browser). These cover much of what a Cypress test covers and usually run 10–100× faster, with no browser flakiness. This is the best replacement for the screen-by-screen idea.
- **Model / service / job unit specs** for business logic, including error and edge branches.
- **Characterization tests** for scary legacy code: pin down current behavior before anyone refactors it.
- **Prioritize by risk, not by screen list:** rank files by git churn × complexity × business criticality (payments, auth, data export, and similar). Cover the top 20% of that list first.

### Phase 2: Keep the number from sliding back
- **Diff coverage gate in CI:** new and changed lines must be ≥90% covered (`undercover` or `diff-cover`). This reaches the VP's 90% on everything written from now on, which is the code most likely to break.
- **Coverage ratchet:** CI fails if overall coverage drops below the last recorded value.
- **Cypress for critical journeys only.** That means about 15–30 flows: signup, login, checkout, core workflow. Everything else goes through request specs.

### Target test mix

| Layer | Role | Rough share of new tests |
|---|---|---|
| Unit (models, services, jobs) | Logic, branches, edge cases | ~60% |
| Request / integration | Endpoints, auth, rendering | ~35% |
| Cypress E2E | Critical user journeys | ~5% |

## How to handle the 90% mandate itself

Don't fight the VP head-on. Ask what problem the number is supposed to solve. It is almost always "too many production regressions" or "we're afraid to change the monolith." Then offer a scorecard that tracks that problem better than one global percentage:

1. Overall coverage trending up every sprint, with an honest end-of-Q1 projection. For a legacy monolith my guess is 60–70% is reachable with the plan above; 90% by Q1 from 31% is probably not achievable without low-quality tests. Say that plainly rather than over-promising.
2. ≥90% diff coverage on all new code, enforced by CI from week 3.
3. ≥90% coverage on the top-risk modules you identified.
4. CI under 15 min and flake rate under 2%.
5. Escaped defects per release, since that's the outcome the VP actually cares about.

If the VP insists on a literal 90% global number, the answer is still request and unit specs. They reach the number faster and more cheaply than Cypress. The disagreement is only about how much weak testing you're willing to accept to hit it.

## Pre-mortem on your own plan (have answers ready)

- **"Contractors write tests with no real assertions just to hit lines."** Mitigate by requiring a reviewer from the owning team on every test PR, and run occasional mutation testing (e.g. `mutant`) on the high-risk modules to check that the tests actually catch changes.
- **"Contractors don't know the domain, so they're slow on unit tests."** That is true. Pair them with an engineer for the first two weeks, and start them on request specs, which need less internal knowledge than unit specs.
- **"The QA lead feels overruled."** Give QA ownership of the critical-journey Cypress suite and the flake-rate SLO. Their instinct about testing what users see is right; it just belongs in a small number of tests, not all of them.
- **"Coverage stalls at ~55%."** This usually means untestable code: fat controllers and hard-wired dependencies. Budget some refactoring time from Phase 1 onward rather than finding this out in March.
