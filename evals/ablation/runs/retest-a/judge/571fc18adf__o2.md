## Latest user message
Странная штука. Тесты на репозиторий пользователей (pytest + SQLAlchemy 2.0 + PostgreSQL 15 в docker) по одному проходят все, `pytest tests/test_users_repo.py` целиком тоже зелёный. Но как только включили pytest-randomly, стабильно валятся 3-4 теста: то `UniqueViolation: duplicate key value violates unique constraint "users_email_key"`, то `assert len(repo.list_active()) == 2` получает 3. Фикстура сессии у нас такая:

```python
@pytest.fixture(scope="module")
def session():
    engine = create_engine(DB_URL)
    Base.metadata.create_all(engine)
    with Session(engine) as s:
        yield s
    Base.metadata.drop_all(engine)
```

А тест test_create_user создаёт alice@example.com, и test_list_active на него рассчитывает. Может, просто выключить pytest-randomly для этого файла?

## Rubric (what a strong answer does)
1. Объясняет, что причина — общее состояние: сессия/данные на уровне модуля и зависимость test_list_active от данных, созданных test_create_user; pytest-randomly лишь выявил это
2. Не рекомендует отключать рандомизацию или фиксировать порядок тестов как решение
3. Предлагает изоляцию на каждый тест, например function-scoped сессию внутри транзакции с откатом после теста (engine/таблицы можно оставить на уровне session/module), и чтобы каждый тест сам создавал нужные ему данные
4. Приводит корректный пример фикстуры для SQLAlchemy 2.0 с откатом транзакции

## Answer A
Выключать pytest-randomly не стоит. Он не создаёт баг, а показывает уже существующий: тесты зависят от порядка запуска, потому что делят общее состояние БД. Если выключить плагин, проблема просто спрячется до первого нового теста, `-k`-фильтра или `pytest-xdist`.

## Почему валится

- `scope="module"` означает одну сессию и одну БД на весь файл. Всё, что тест закоммитил, остаётся в таблицах для следующих тестов.
- В порядке «как в файле» `test_create_user` случайно идёт раньше `test_list_active`, и накопленное состояние совпадает с ожиданиями. Поэтому весь файл зелёный.
- При случайном порядке:
  - `UniqueViolation users_email_key` появляется, когда `alice@example.com` вставляется второй раз (другим тестом или повторно) в ту же неочищенную таблицу;
  - `len(...) == 3` получается, когда до `test_list_active` уже отработал тест, добавивший ещё одного активного пользователя.
- Есть и побочный эффект: если один тест упадёт посреди транзакции, общая сессия останется в состоянии failed. Тогда следующие тесты в модуле получат `PendingRollbackError`, и отказы начнут каскадом расползаться по файлу.

`test_list_active`, который рассчитывает на данные из `test_create_user`, сам по себе является ошибкой дизайна. Каждый тест должен сам готовить свои данные.

## Решение: изоляция через транзакцию с rollback на каждый тест

Схема создаётся один раз, а каждый тест работает внутри внешней транзакции, которая в конце откатывается. `session.commit()` внутри кода репозитория при этом коммитит только SAVEPOINT, а не реальную транзакцию.

```python
# conftest.py
import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import Session

@pytest.fixture(scope="session")
def engine():
    engine = create_engine(DB_URL)
    Base.metadata.drop_all(engine)    # чистый старт, если прошлый прогон упал
    Base.metadata.create_all(engine)
    yield engine
    Base.metadata.drop_all(engine)
    engine.dispose()

@pytest.fixture
def session(engine):
    # Внешняя транзакция на соединении. Всё, что сделает тест, будет откатено
    with engine.connect() as conn:
        trans = conn.begin()
        # commit() внутри теста/репозитория работает с SAVEPOINT, а не с внешней транзакцией
        s = Session(bind=conn, join_transaction_mode="create_savepoint")
        try:
            yield s
        finally:
            s.close()
            trans.rollback()
```

`join_transaction_mode="create_savepoint"` появился в SQLAlchemy 2.0 (это по памяти, я не проверял; сверьтесь с разделом документации «Joining a Session into an External Transaction» для вашей минорной версии). В 1.4 для того же использовали рецепт с событием `after_transaction_end` и `begin_nested()`.

Данные теперь готовятся явно, через фикстуры:

```python
@pytest.fixture
def alice(session):
    user = User(email="alice@example.com", is_active=True)
    session.add(user)
    session.flush()          # получаем id, но не выходим за пределы транзакции теста
    return user

def test_list_active(session):
    repo = UsersRepo(session)
    session.add_all([
        User(email="a@example.com", is_active=True),
        User(email="b@example.com", is_active=True),
        User(email="c@example.com", is_active=False),
    ])
    session.flush()
    assert len(repo.list_active()) == 2
```

## Подводные камни

- **Репозиторий должен получать сессию снаружи.** Если он сам вызывает `create_engine`/`Session()` или берёт глобальный `sessionmaker`, то работает на другом соединении, и rollback его записи не откатит. Проверить это просто: `grep -n "create_engine\|sessionmaker\|Session(" src/…/users_repo.py`.
- **Sequences не откатываются.** После rollback id продолжают расти, поэтому не проверяйте в тестах конкретные `id == 1`.
- **Если код коммитит через отдельные соединения** (фоновые задачи, второй engine), транзакционная изоляция не поможет. Тогда нужен `TRUNCATE users RESTART IDENTITY CASCADE` в teardown функции-фикстуры. Это медленнее, но надёжно.
- **С `pytest-xdist`** воркерам понадобится отдельная БД или схема на каждого (например, по `worker_id`), иначе они будут конфликтовать на одной таблице.

## Как проверить

1. Воспроизведите падение с фиксированным seed. pytest-randomly печатает его в шапке прогона: `pytest tests/test_users_repo.py -p randomly --randomly-seed=<seed>` (флаг по памяти, сверьтесь с `pytest --help`).
2. После правки прогоните файл несколько раз с разными seed, например `for i in 1 2 3 4 5; do pytest tests/test_users_repo.py -q || break; done`. Каждый прогон должен быть зелёным.
3. Можно прогнать `pytest tests/test_users_repo.py -p no:randomly`, а затем с `--randomly-seed=last`. Результат должен совпадать.

Если нужно срочно разблокировать CI, `-p no:randomly` на этот файл можно поставить как временную меру с TODO. Но настоящее исправление — фикстура на уровне функции с rollback, описанная выше.


## Answer B
Не стоит отключать. pytest-randomly тут не виноват: он показал, что тесты зависят друг от друга. Сейчас в фикстуре одна сессия и одна БД на весь модуль, поэтому всё, что тест закоммитил (или просто сделал flush), видят все следующие тесты. Если выключить рандом, баг никуда не денется. Он всплывёт, как только кто-то добавит тест, переименует существующий или запустит один тест через `-k`.

## Откуда берутся оба симптома

- **`UniqueViolation users_email_key`**: `alice@example.com` создают `test_create_user` и ещё какой-то тест (или фикстура). В исходном порядке они, видимо, так расположены, что конфликта нет. В случайном порядке второй INSERT натыкается на строку, которую оставил первый.
- **`len(list_active()) == 3` вместо 2**: `test_list_active` ожидает определённое состояние таблицы, но в неё уже что-то дописали тесты, отработавшие раньше.
- **Каскад на 3-4 теста**: после ошибки на flush или commit сессия переходит в failed-состояние. Все следующие тесты модуля получают ту же сессию, поэтому, скорее всего, падают с `PendingRollbackError` или повторяют ошибку. Отсюда и «стабильно несколько».
- То, что `test_list_active` «рассчитывает» на `test_create_user`, само по себе баг. Каждый тест должен сам готовить свои данные.

## Решение: каждый тест в своей транзакции с откатом

Engine и схему создаём один раз на весь прогон. Каждый тест работает внутри внешней транзакции, которую в конце откатываем. Даже если репозиторий внутри вызывает `commit()`, в SQLAlchemy 2.0 его можно превратить в SAVEPOINT:

```python
# conftest.py
import pytest
from sqlalchemy import create_engine
from sqlalchemy.orm import Session

@pytest.fixture(scope="session")
def engine():
    engine = create_engine(DB_URL)
    Base.metadata.drop_all(engine)      # на случай мусора от прошлого упавшего прогона
    Base.metadata.create_all(engine)
    yield engine
    Base.metadata.drop_all(engine)
    engine.dispose()

@pytest.fixture()
def session(engine):
    # Внешняя транзакция на весь тест, в конце откатывается
    connection = engine.connect()
    trans = connection.begin()
    # commit() внутри кода превращается в RELEASE SAVEPOINT,
    # поэтому наружу ничего не попадает
    s = Session(bind=connection, join_transaction_mode="create_savepoint")
    try:
        yield s
    finally:
        s.close()
        trans.rollback()
        connection.close()
```

Про `join_transaction_mode="create_savepoint"`: это параметр `Session` из SQLAlchemy 2.0 (раздел документации «Joining a Session into an External Transaction», например для тест-сьютов). Пишу по памяти, при внедрении сверьте с документацией своей версии 2.0.x.

Тесты делаем самодостаточными:

```python
def test_list_active(session):
    repo = UsersRepo(session)
    repo.create(email="alice@example.com", active=True)
    repo.create(email="bob@example.com", active=True)
    repo.create(email="carol@example.com", active=False)

    assert len(repo.list_active()) == 2
```

Если одни и те же пользователи нужны многим тестам, вынесите их в function-scoped фикстуру (`alice`, `users_seed`), а не полагайтесь на соседний тест.

## Трейд-оффы

- Откат транзакции работает быстрее, чем `TRUNCATE` или пересоздание схемы для каждого теста, и изоляция получается полной.
- Внутри одной транзакции не проверить то, что зависит от реального коммита: несколько соединений, `SERIALIZABLE`, advisory locks, `LISTEN/NOTIFY`, `DEFERRABLE INITIALLY DEFERRED` constraints. Для таких тестов нужна отдельная фикстура с `TRUNCATE ... RESTART IDENTITY CASCADE` в teardown.
- Если репозиторий сам создаёт себе сессию или engine, а не получает их снаружи, откат их не накроет. Тогда сессию нужно внедрять через конструктор или DI.
- Если распараллелите тесты через pytest-xdist, каждому воркеру понадобится своя БД или схема.

## Как проверить

1. Воспроизведите текущее падение с конкретным seed. pytest-randomly печатает его в заголовке прогона:
   ```
   pytest tests/test_users_repo.py -p randomly --randomly-seed=<seed из заголовка>
   ```
   (флаг `--randomly-seed` и `-p no:randomly` для отключения я пишу по памяти, проверьте в `pytest --help`)
2. Поменяйте фикстуры. Тот же seed должен дать зелёный прогон.
3. Прогоните несколько разных seed подряд, например `for i in $(seq 1 20); do pytest tests/test_users_repo.py -q -p randomly --randomly-seed=$RANDOM || break; done`.
4. Проверьте, что после прогона таблица пустая и в БД не осталось мусора: `SELECT count(*) FROM users;` (схему при этом удаляет только engine-фикстура).

Итог: pytest-randomly оставьте включённым. Он нашёл настоящую утечку состояния между тестами, и после перехода на транзакцию с откатом для каждого теста он будет защищать от таких багов в будущем.
