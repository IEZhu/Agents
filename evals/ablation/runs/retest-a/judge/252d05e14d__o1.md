## Latest user message
У нас в игре есть обмен предметами между игроками, около 40 CCU. Сохраняю так: в PlayerRemoving делаю store:SetAsync(player.UserId, data), загружаю через store:GetAsync(player.UserId) в PlayerAdded. Иногда игроки жалуются, что после обмена предмет остался у обоих, а пару раз у человека вообще обнулился инвентарь после захода (в Output видел ошибку 502 от DataStore). Что тут не так и как переписать сохранение/загрузку?

## Rubric (what a strong answer does)
1. Оборачивает GetAsync и сохранение в pcall и объясняет, что при неудачной загрузке нельзя давать игроку пустой инвентарь и потом сохранять его поверх настоящих данных (нужен флаг/повторные попытки/кик)
2. Рекомендует UpdateAsync вместо SetAsync для сохранения экономики/инвентаря
3. Предлагает периодическое автосохранение и сохранение при закрытии сервера (game:BindToClose), а не только в PlayerRemoving
4. Объясняет механизм дюпа при обмене (например, сохранение одного игрока прошло, другого нет, или обмен не сохраняется атомарно) и даёт осмысленное направление решения

## Answer A
Здесь сразу несколько проблем, и обе жалобы (дюп и вайп) — классические последствия схемы «`GetAsync` при входе / `SetAsync` при выходе».

## Что не так

### 1. Обнуление инвентаря: провал загрузки считается «новым игроком»

Скорее всего, у вас сейчас что-то такое:

```lua
local ok, data = pcall(store.GetAsync, store, player.UserId)
data = data or DEFAULT_DATA -- при 502 сюда попадает пустой инвентарь
```

Дальше всё происходит так:
1. `GetAsync` падает с 502 (это временная ошибка на стороне сервиса DataStore; сам запрос у вас правильный).
2. Код не различает «данных нет» и «данные не загрузились» и выдаёт дефолт.
3. Игрок играет с пустым инвентарём.
4. В `PlayerRemoving` `SetAsync` **перезаписывает** настоящие данные пустыми. Предметы пропадают насовсем.

Правило простое: **если загрузка не удалась, этот профиль нельзя сохранять никогда.** Лучше кикнуть игрока с просьбой перезайти, чем стереть ему сохранение.

### 2. Дюп при обмене: нет session locking

Самый частый сценарий дюпа:
1. A отдаёт предмет B. Сейчас это изменение есть только в памяти сервера 1.
2. A сразу выходит и заходит на сервер 2 (например, к другу).
3. Сервер 2 делает `GetAsync` **раньше**, чем сервер 1 успел выполнить `SetAsync` в `PlayerRemoving`, и загружает старую версию, где предмет ещё у A.
4. Сервер 1 сохраняет A уже без предмета, но позже сервер 2 перезапишет это своей старой копией с предметом.
5. Итог: предмет у B **и** у A.

`SetAsync` слепо перезаписывает ключ, поэтому «последний записавший побеждает», даже если он писал устаревшие данные.

### 3. Сохранение только в `PlayerRemoving`

- **Нет `BindToClose`.** При shutdown сервера (обновление игры, краш) сохранения в `PlayerRemoving` могут не успеть выполниться. Если после обмена сохранилась одна сторона, а другая нет, получается дюп или потеря предмета.
- **Нет автосейва.** Всё, что произошло с момента входа, живёт только в памяти.
- **Нет ретраев.** Одна 502 при сохранении означает потерянный прогресс.

## Как исправить

1. **Загрузка:** ретраи с backoff. Если данные не загрузились, делаем кик и **не** помечаем профиль как загруженный.
2. **Session lock:** в записи хранится `JobId` сервера, который сейчас владеет данными. Второй сервер ждёт, пока лок снимут, и не читает устаревшую версию.
3. **`UpdateAsync` вместо `SetAsync`:** сохраняем только если этот сервер всё ещё владеет локом.
4. **Обмен:** всё валидирует сервер, у предметов уникальные ID, обе стороны сохраняются **сразу** после обмена.
5. **Автосейв + `BindToClose`.**

Честно о пределах: DataStore не даёт атомарной транзакции между двумя ключами. Поэтому между сохранением A и сохранением B остаётся маленькое окно (краш сервера ровно между двумя записями). Session lock и немедленное сохранение сужают его до практически нулевого при 40 CCU, но не убирают теоретически. Уникальные ID предметов нужны в том числе для того, чтобы такие случаи можно было найти и откатить.

local Players = game:GetService("Players")
local DataStoreService = game:GetService("DataStoreService")

-- Keep your CURRENT store name: a new name = a new empty store for everyone.
local STORE_NAME = "PlayerData"
local SCHEMA_VERSION = 2

local MAX_RETRIES = 5
local RETRY_BASE_DELAY = 1          -- seconds, doubles every attempt
local LOCK_STALE_SECONDS = 30 * 60  -- lock with no refresh for this long = dead server
local LOCK_WAIT_ATTEMPTS = 6
local LOCK_WAIT_SECONDS = 5
local AUTOSAVE_INTERVAL = 120

local store = DataStoreService:GetDataStore(STORE_NAME)

type Item = { Id: string }
export type PlayerData = {
	Coins: number,
	Items: { [string]: Item }, -- key = unique item uid (HttpService:GenerateGUID)
}
type Record = {
	Schema: number,
	Data: PlayerData,
	Lock: { JobId: string, Time: number }?,
}

local DataManager = {}
local profiles: { [Player]: PlayerData } = {} -- only SUCCESSFULLY loaded players

local function defaultData(): PlayerData
	return { Coins = 0, Items = {} }
end

-- Old format was the raw data table written by SetAsync; wrap it once.
local function toRecord(stored: any): Record?
	if stored == nil then
		return nil
	end
	if stored.Schema == nil then
		-- Convert your old inventory format here (e.g. assign uids to items).
		return { Schema = SCHEMA_VERSION, Data = stored, Lock = nil }
	end
	return stored
end

local function withRetries(label: string, fn: () -> ()): boolean
	for attempt = 1, MAX_RETRIES do
		local ok, err = pcall(fn)
		if ok then
			return true
		end
		warn(("[DataManager] %s failed (%d/%d): %s"):format(label, attempt, MAX_RETRIES, tostring(err)))
		if attempt < MAX_RETRIES then
			task.wait(RETRY_BASE_DELAY * 2 ^ (attempt - 1))
		end
	end
	return false
end

-- Writes data only if THIS server still owns the lock. Never overwrites blindly.
local function commit(userId: number, data: PlayerData, releaseLock: boolean): boolean
	local lockLost = false
	local ok = withRetries("save " .. userId, function()
		store:UpdateAsync(userId, function(stored)
			lockLost = false -- transform may run several times
			local record = toRecord(stored)
			if not record or not record.Lock or record.Lock.JobId ~= game.JobId then
				lockLost = true
				return nil -- nil = cancel the write
			end
			record.Data = data
			record.Lock = if releaseLock then nil else { JobId = game.JobId, Time = os.time() }
			return record
		end)
	end)
	if lockLost then
		warn("[DataManager] lock lost for", userId, "- save skipped to avoid overwriting newer data")
	end
	return ok and not lockLost
end

-- Returns data if lock acquired, nil if another server still holds it.
local function tryAcquire(userId: number): (boolean, PlayerData?)
	local acquired: PlayerData? = nil
	local ok = withRetries("load " .. userId, function()
		store:UpdateAsync(userId, function(stored)
			acquired = nil
			local record = toRecord(stored)
				or { Schema = SCHEMA_VERSION, Data = defaultData(), Lock = nil }
			local lock = record.Lock
			if lock and lock.JobId ~= game.JobId and os.time() - lock.Time < LOCK_STALE_SECONDS then
				return nil -- another server is still saving/holding this player
			end
			record.Lock = { JobId = game.JobId, Time = os.time() }
			acquired = record.Data
			return record
		end)
	end)
	return ok, acquired
end

function DataManager.load(player: Player): boolean
	for _ = 1, LOCK_WAIT_ATTEMPTS do
		local ok, data = tryAcquire(player.UserId)
		if not ok then
			return false -- DataStore down: do NOT hand out default data
		end
		if data then
			if player.Parent ~= Players then
				commit(player.UserId, data, true) -- left while loading: just release
				return false
			end
			profiles[player] = data
			return true
		end
		task.wait(LOCK_WAIT_SECONDS) -- old server usually finishes its save in a few seconds
	end
	return false
end

function DataManager.get(player: Player): PlayerData?
	return profiles[player]
end

function DataManager.release(player: Player)
	local data = profiles[player]
	if not data then
		return -- never loaded => never saved. This is what prevents wipes.
	end
	profiles[player] = nil
	commit(player.UserId, data, true)
end

function DataManager.releaseAll()
	local pending = 0
	for player in profiles do
		pending += 1
		task.spawn(function()
			DataManager.release(player)
			pending -= 1
		end)
	end
	while pending > 0 do
		task.wait()
	end
end

function DataManager.startAutosave()
	task.spawn(function()
		while true do
			task.wait(AUTOSAVE_INTERVAL)
			for player, data in profiles do
				task.spawn(commit, player.UserId, data, false) -- also refreshes lock time
			end
		end
	end)
end

-- Validates BOTH sides before mutating anything, then persists both immediately.
local function collectOwned(data: PlayerData, uids: { string }): boolean
	local seen = {}
	for _, uid in uids do
		if typeof(uid) ~= "string" or seen[uid] or not data.Items[uid] then
			return false
		end
		seen[uid] = true
	end
	return true
end

function DataManager.executeTrade(a: Player, aUids: { string }, b: Player, bUids: { string }): boolean
	local aData, bData = profiles[a], profiles[b]
	if a == b or not aData or not bData then
		return false
	end
	if not collectOwned(aData, aUids) or not collectOwned(bData, bUids) then
		return false
	end

	for _, uid in aUids do
		bData.Items[uid] = aData.Items[uid]
		aData.Items[uid] = nil
	end
	for _, uid in bUids do
		aData.Items[uid] = bData.Items[uid]
		bData.Items[uid] = nil
	end

	task.spawn(commit, a.UserId, aData, false)
	task.spawn(commit, b.UserId, bData, false)
	return true
end

return DataManager

## Важные детали

- **Ключ не меняйте.** `UpdateAsync(player.UserId, ...)` использует тот же ключ и то же хранилище, что и раньше. `toRecord` один раз обернёт старые данные в новый формат. Если старые предметы лежат как `{ Sword = 2 }`, в месте миграции раздайте им uid.
- **Функция внутри `UpdateAsync` не должна yield-ить** и может вызываться несколько раз. Поэтому флаги сбрасываются в начале функции. Возврат `nil` отменяет запись: это документированное поведение, на нём держится весь лок.
- **Сама торговля:** клиент присылает только *намерение* (uid предметов и подтверждение). Всё остальное делает сервер: проверяет, что оба игрока загружены и находятся рядом/в сессии обмена, что предметы действительно их, и защищается от спама RemoteEvent (rate limit, флаг «обмен в процессе» на игрока). Два одновременных обмена одного и того же предмета отсекутся проверкой `data.Items[uid]`, потому что `executeTrade` не yield-ит между проверкой и изменением.
- **`BindToClose`** даёт ограниченное время на завершение (насколько я помню, около 30 секунд — лучше проверить в документации). При 40 CCU этого с запасом хватает, но большие задержки ретраев там не помогут.
- **Лок в Studio:** `game.JobId` в Studio, насколько я знаю, пустая строка, так что два окна Studio будут считать лок своим. Для тестирования это не мешает, просто учитывайте это.

## Альтернатива, которую я бы рассмотрел всерьёз

Session locking — это ровно то, что делает **ProfileStore** (преемник ProfileService от loleris). Насколько я помню, там же есть автосейв, обработка shutdown и защита от перезаписи. Писать свой лок можно (код выше рабочий по принципу), но у готовой библиотеки намного больше обкатанных краевых случаев. Для игры с торговлей, где дюп обесценивает экономику, я бы, скорее всего, взял её. Актуальный API проверьте в репозитории/на DevForum: названия методов по памяти приводить не буду.

## Как проверить

1. **Вайп:** временно сделайте `tryAcquire` всегда возвращающим `false, nil`. Игрока должно кикнуть, а данные в хранилище остаться нетронутыми (смотрите через DataStore Editor или `GetAsync` из командной строки).
2. **Лок:** в Local Server с двумя серверами (или вручную записав в ключ чужой `Lock` со свежим `Time`) проверьте, что загрузка ждёт и не выдаёт данные.
3. **Обмен:** выполните обмен и сразу принудительно закройте сервер. После перезахода у каждой стороны должно быть корректное состояние.
4. **Аудит:** раз в какое-то время прогоните по сохранениям поиск одинаковых uid у разных игроков. Если найдутся, значит где-то ещё остаётся дыра.

И не забудьте включить «Enable Studio Access to API Services», иначе в Studio DataStore работать не будет.


## Answer B
В этой схеме две отдельные проблемы, и обе типичны для связки «`SetAsync` в `PlayerRemoving` + `GetAsync` в `PlayerAdded`». Сначала о том, откуда берутся симптомы, потом код на замену.

## Что происходит

### 1. Обнулённый инвентарь после ошибки 502

Скорее всего, загрузка устроена так:

```lua
local data = store:GetAsync(player.UserId)  -- 502 → ошибка (или pcall вернул false)
-- data == nil → игрок считается «новым», ему выдаются пустые данные
...
store:SetAsync(player.UserId, data)          -- при выходе пустой инвентарь записывается поверх настоящего
```

Код не отличает **«данных нет, это новый игрок»** от **«данные не загрузились»**. Во втором случае пустой шаблон при выходе перезаписывает настоящий сохранённый инвентарь. Правило такое: **если загрузка не удалась, сохранять ничего нельзя.** Нужно повторить запрос, а если он так и не прошёл, кикнуть игрока с понятным сообщением.

### 2. Предмет остался у обоих (дюп)

Классический сценарий:

1. A отдаёт предмет B. На сервере у A предмета уже нет, у B он появился.
2. A выходит и сразу заходит на **другой** сервер (или заходит повторно на тот же).
3. `SetAsync` на старом сервере ещё не завершился, упал с ошибкой или был потерян при краше сервера.
4. Новый сервер через `GetAsync` читает **старую** запись, где предмет ещё у A.
5. B сохраняется нормально. В итоге предмет есть у обоих.

Кроме того:
- **Автосейва нет.** Если сервер падает, теряется всё с момента входа. Причём у одного участника обмена сохранение может пройти, а у другого нет.
- Скорее всего, нет **`BindToClose`**: при выключении сервера `PlayerRemoving`-сейвы могут не успеть завершиться.
- `SetAsync` пишет вслепую и никак не проверяет, не владеет ли этими данными сейчас другой сервер.

Если это эксплуатируют намеренно (выход в момент обмена, краш или лаг сервера), дюп будет повторяться. Лечится это **session locking**: запись данных игрока в каждый момент времени «принадлежит» одному серверу.

## Как переписать

Самый надёжный путь: взять **ProfileStore** (преемник ProfileService от loleris). В нём уже есть session locking, автосейв, `BindToClose` и защита от повторных сессий. Если хотите разобраться в механике или обойтись без библиотеки, ниже минимальная реализация тех же идей.

Основные принципы:
- **`UpdateAsync` вместо `Get/SetAsync`**, чтобы проверять блокировку атомарно.
- **Lock** в записи: `JobId` сервера и время. Чужой сервер эту запись не перезаписывает.
- **Повторы с backoff** при ошибках вроде 502.
- **Сбой загрузки → кик, запись запрещена.**
- **Автосейв** плюс **`BindToClose`**.
- Существующие данные в старом формате мигрируют автоматически.

```lua
--!strict
-- ServerScriptService/Core/DataManager (ModuleScript)
local DataStoreService = game:GetService("DataStoreService")
local Players = game:GetService("Players")
local RunService = game:GetService("RunService")

-- В Studio game.JobId пустой, поэтому пишем в отдельный store, чтобы тесты не трогали боевые данные
local STORE_NAME = if RunService:IsStudio() then "PlayerData_Studio" else "PlayerData"
local MAX_RETRIES = 5
local AUTOSAVE_INTERVAL = 60        -- заодно продлевает lock
local LOCK_TIMEOUT = 5 * 60         -- lock старше этого считается брошенным (сервер упал)
local LOCK_WAIT = 5
local MAX_LOCK_WAITS = 6            -- ~30 секунд ждём, пока другой сервер отпустит данные

local store = DataStoreService:GetDataStore(STORE_NAME)

export type Profile = { Key: string, Data: any }

local DataManager = {}
local profiles: { [Player]: Profile } = {}
local activeSaves = 0

local function defaultData()
	return { Inventory = {}, Coins = 0 }
end

-- Отличаем «ошибку сервиса» от «пустых данных»: pcall + повторы
local function withRetries(label: string, fn: () -> any): (boolean, any)
	for attempt = 1, MAX_RETRIES do
		local ok, result = pcall(fn)
		if ok then
			return true, result
		end
		warn(("[DataManager] %s failed (%d/%d): %s"):format(label, attempt, MAX_RETRIES, tostring(result)))
		if attempt < MAX_RETRIES then
			task.wait(2 ^ attempt) -- 2, 4, 8, 16 с
		end
	end
	return false, nil
end

local function isLockedByOther(record): boolean
	local lock = record and record.Lock
	return lock ~= nil
		and lock.JobId ~= game.JobId
		and os.time() - lock.Time < LOCK_TIMEOUT
end

local function tryAcquire(key: string): (boolean, any, boolean)
	local lockedByOther = false
	local ok, record = withRetries("Load " .. key, function()
		lockedByOther = false
		return store:UpdateAsync(key, function(old)
			if old ~= nil and old.Data == nil then
				old = { Data = old } -- миграция старого формата (запись была «голыми» данными)
			end
			old = old or { Data = defaultData() } -- nil без ошибки = действительно новый игрок
			if isLockedByOther(old) then
				lockedByOther = true
				return nil -- отменяем запись, чужой lock не трогаем
			end
			old.Lock = { JobId = game.JobId, Time = os.time() }
			return old
		end)
	end)
	return ok, record, lockedByOther
end

local function writeProfile(profile: Profile, release: boolean): boolean
	activeSaves += 1
	local ok = withRetries("Save " .. profile.Key, function()
		store:UpdateAsync(profile.Key, function(old)
			if old and old.Lock and old.Lock.JobId ~= game.JobId then
				-- Сессией уже владеет другой сервер: наши данные устарели, не перетираем их
				return nil
			end
			return {
				Data = profile.Data,
				Lock = if release then nil else { JobId = game.JobId, Time = os.time() },
			}
		end)
	end)
	activeSaves -= 1
	return ok
end

function DataManager.Load(player: Player)
	local key = tostring(player.UserId)
	for _ = 1, MAX_LOCK_WAITS do
		local ok, record, lockedByOther = tryAcquire(key)
		if not ok then
			-- Именно здесь раньше обнулялся инвентарь. Теперь игрок уходит, а данные остаются нетронутыми
			player:Kick("Не удалось загрузить данные (сбой Roblox). Прогресс в безопасности, перезайдите чуть позже.")
			return
		end
		if not lockedByOther then
			local profile: Profile = { Key = key, Data = record.Data }
			if player.Parent == nil then
				writeProfile(profile, true) -- игрок ушёл, пока грузились данные: просто отпускаем lock
				return
			end
			profiles[player] = profile
			return
		end
		task.wait(LOCK_WAIT) -- старый сервер ещё сохраняет данные этого игрока, ждём
	end
	player:Kick("Ваши данные ещё сохраняются на другом сервере. Перезайдите через минуту.")
end

function DataManager.Get(player: Player): Profile?
	return profiles[player] -- nil = НЕ загружен, с таким игроком ничего не делаем (в т.ч. обмен)
end

function DataManager.SaveNow(player: Player)
	local profile = profiles[player]
	if profile then
		task.spawn(writeProfile, profile, false)
	end
end

local function onPlayerRemoving(player: Player)
	local profile = profiles[player]
	if not profile then
		return -- данные не загрузились → ничего не пишем
	end
	profiles[player] = nil
	writeProfile(profile, true)
end

function DataManager.Start()
	Players.PlayerAdded:Connect(DataManager.Load)
	for _, player in Players:GetPlayers() do
		task.spawn(DataManager.Load, player)
	end
	Players.PlayerRemoving:Connect(onPlayerRemoving)

	task.spawn(function()
		while true do
			task.wait(AUTOSAVE_INTERVAL)
			for _, profile in profiles do
				task.spawn(writeProfile, profile, false)
			end
		end
	end)

	game:BindToClose(function()
		for player in profiles do
			task.spawn(onPlayerRemoving, player)
		end
		while activeSaves > 0 do
			task.wait() -- ждём и сейвы из PlayerRemoving, и из цикла выше
		end
	end)
end

return DataManager
```

## Сам обмен

Session locking закрывает дюп через перезаход. Кроме него, сам обмен должен проходить на сервере атомарно:

```lua
-- Вызывается сервером, когда ОБА игрока подтвердили обмен (подтверждения пришли через RemoteEvent и проверены)
local function executeTrade(a: Player, b: Player, itemFromA: string, itemFromB: string): boolean
	local pa, pb = DataManager.Get(a), DataManager.Get(b)
	if not (pa and pb) or a == b then
		return false
	end
	local invA, invB = pa.Data.Inventory, pb.Data.Inventory

	-- Проверка и перенос идут без yield между ними: никакого task.wait / DataStore-вызовов внутри
	if (invA[itemFromA] or 0) < 1 or (invB[itemFromB] or 0) < 1 then
		return false
	end
	local function move(from, to, id)
		from[id] -= 1
		if from[id] == 0 then from[id] = nil end
		to[id] = (to[id] or 0) + 1
	end
	move(invA, invB, itemFromA)
	move(invB, invA, itemFromB)

	-- Сохраняем обоих сразу, не дожидаясь автосейва: окно для потери сокращается до секунд
	DataManager.SaveNow(a)
	DataManager.SaveNow(b)
	return true
end
```

И ещё несколько вещей:
- Клиент присылает только **намерение** («предлагаю такой-то предмет», «подтверждаю»). Наличие предметов сервер проверяет **в момент исполнения**, а не в момент предложения.
- Пока идёт обмен, помечайте обоих игроков флагом `Trading` и запрещайте продавать, выбрасывать или крафтить предложенные предметы. Иначе можно предложить предмет, продать его и получить за него что-то в обмене.
- Защищайтесь от повторного «Accept» (debounce и проверка состояния сессии обмена). При изменении предложения подтверждение должно сбрасываться.
- Если одного из участников нет в `profiles` (не загрузился или уже вышел), обмен отменяется.

**Честное ограничение:** два игрока хранятся под двумя разными ключами, а DataStore не умеет транзакции между ключами. Если сервер упадёт ровно между двумя записями, небольшое окно рассинхрона останется. Для ~40 CCU `SaveNow` сразу после обмена и session locking на практике сводят проблему почти к нулю. Если нужна полная гарантия, пишут журнал обменов: `TradeId` сохраняется в записи обоих игроков, а при загрузке незавершённые обмены сверяются. Это заметно сложнее, я бы делал его, только если дюпы продолжатся.

## Проверка

1. **Сбой загрузки:** в Studio временно добавьте `error("502 test")` внутрь `fn` в `withRetries` для Load. Игрок должен получить кик, а запись в store должна остаться нетронутой.
2. **Перезаход:** Local Server на 2 игрока. Сделайте обмен, выйдите одним игроком и сразу зайдите снова. Предмет должен остаться только у получателя.
3. **Shutdown:** остановите сервер сразу после обмена и проверьте, что `BindToClose` дождался сейвов.
4. В Game Settings включите «Enable Studio Access to API Services». Для тестов используется отдельный store `PlayerData_Studio`.

## Что стоит перепроверить в документации

Это я пишу по памяти, в этом ответе не сверял:
- **Отмена записи при возврате `nil` из колбэка `UpdateAsync`.** На этом держится вся логика блокировки, поэтому проверьте в первую очередь.
- **`BindToClose` даёт около 30 секунд.** Backoff из примера в худшем случае туда не укладывается. Если это критично, уменьшите `MAX_RETRIES` при shutdown.
- **Лимиты DataStore:** бюджет запросов около `60 + 10 × игроков` в минуту на сервер и примерно 6 секунд между записями в один ключ. Автосейв раз в 60 секунд укладывается с большим запасом.
- **Кэш `GetAsync` около 4 секунд.** Это ещё одна причина не использовать его для чтения «свежих» данных после перезахода.

Если переходите на ProfileStore, переносите логику обмена и правило «не загружен → не трогаем», а блокировку, автосейв и `BindToClose` библиотека берёт на себя.
