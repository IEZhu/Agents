Здесь сразу несколько проблем, и обе жалобы (дюп и вайп) — классические последствия схемы «`GetAsync` при входе / `SetAsync` при выходе».

## Что не так

### 1. Обнуление инвентаря: провал загрузки считается «новым игроком»

Скорее всего, у вас сейчас что-то такое:

```lua
local ok, data = pcall(store.GetAsync, store, player.UserId)
data = data or DEFAULT_DATA -- при 502 сюда попадает пустой инвентарь
```

Дальше всё происходит так:
1. `GetAsync` падает с 502 (это временная ошибка на стороне сервиса DataStore; сам запрос у вас правильный).
2. Код не различает «данных нет» и «данные не загрузились» и выдаёт дефолт.
3. Игрок играет с пустым инвентарём.
4. В `PlayerRemoving` `SetAsync` **перезаписывает** настоящие данные пустыми. Предметы пропадают насовсем.

Правило простое: **если загрузка не удалась, этот профиль нельзя сохранять никогда.** Лучше кикнуть игрока с просьбой перезайти, чем стереть ему сохранение.

### 2. Дюп при обмене: нет session locking

Самый частый сценарий дюпа:
1. A отдаёт предмет B. Сейчас это изменение есть только в памяти сервера 1.
2. A сразу выходит и заходит на сервер 2 (например, к другу).
3. Сервер 2 делает `GetAsync` **раньше**, чем сервер 1 успел выполнить `SetAsync` в `PlayerRemoving`, и загружает старую версию, где предмет ещё у A.
4. Сервер 1 сохраняет A уже без предмета, но позже сервер 2 перезапишет это своей старой копией с предметом.
5. Итог: предмет у B **и** у A.

`SetAsync` слепо перезаписывает ключ, поэтому «последний записавший побеждает», даже если он писал устаревшие данные.

### 3. Сохранение только в `PlayerRemoving`

- **Нет `BindToClose`.** При shutdown сервера (обновление игры, краш) сохранения в `PlayerRemoving` могут не успеть выполниться. Если после обмена сохранилась одна сторона, а другая нет, получается дюп или потеря предмета.
- **Нет автосейва.** Всё, что произошло с момента входа, живёт только в памяти.
- **Нет ретраев.** Одна 502 при сохранении означает потерянный прогресс.

## Как исправить

1. **Загрузка:** ретраи с backoff. Если данные не загрузились, делаем кик и **не** помечаем профиль как загруженный.
2. **Session lock:** в записи хранится `JobId` сервера, который сейчас владеет данными. Второй сервер ждёт, пока лок снимут, и не читает устаревшую версию.
3. **`UpdateAsync` вместо `SetAsync`:** сохраняем только если этот сервер всё ещё владеет локом.
4. **Обмен:** всё валидирует сервер, у предметов уникальные ID, обе стороны сохраняются **сразу** после обмена.
5. **Автосейв + `BindToClose`.**

Честно о пределах: DataStore не даёт атомарной транзакции между двумя ключами. Поэтому между сохранением A и сохранением B остаётся маленькое окно (краш сервера ровно между двумя записями). Session lock и немедленное сохранение сужают его до практически нулевого при 40 CCU, но не убирают теоретически. Уникальные ID предметов нужны в том числе для того, чтобы такие случаи можно было найти и откатить.

## Код

`ServerScriptService/Core/DataManager` (ModuleScript):

```lua
local Players = game:GetService("Players")
local DataStoreService = game:GetService("DataStoreService")

-- Keep your CURRENT store name: a new name = a new empty store for everyone.
local STORE_NAME = "PlayerData"
local SCHEMA_VERSION = 2

local MAX_RETRIES = 5
local RETRY_BASE_DELAY = 1          -- seconds, doubles every attempt
local LOCK_STALE_SECONDS = 30 * 60  -- lock with no refresh for this long = dead server
local LOCK_WAIT_ATTEMPTS = 6
local LOCK_WAIT_SECONDS = 5
local AUTOSAVE_INTERVAL = 120

local store = DataStoreService:GetDataStore(STORE_NAME)

type Item = { Id: string }
export type PlayerData = {
	Coins: number,
	Items: { [string]: Item }, -- key = unique item uid (HttpService:GenerateGUID)
}
type Record = {
	Schema: number,
	Data: PlayerData,
	Lock: { JobId: string, Time: number }?,
}

local DataManager = {}
local profiles: { [Player]: PlayerData } = {} -- only SUCCESSFULLY loaded players

local function defaultData(): PlayerData
	return { Coins = 0, Items = {} }
end

-- Old format was the raw data table written by SetAsync; wrap it once.
local function toRecord(stored: any): Record?
	if stored == nil then
		return nil
	end
	if stored.Schema == nil then
		-- Convert your old inventory format here (e.g. assign uids to items).
		return { Schema = SCHEMA_VERSION, Data = stored, Lock = nil }
	end
	return stored
end

local function withRetries(label: string, fn: () -> ()): boolean
	for attempt = 1, MAX_RETRIES do
		local ok, err = pcall(fn)
		if ok then
			return true
		end
		warn(("[DataManager] %s failed (%d/%d): %s"):format(label, attempt, MAX_RETRIES, tostring(err)))
		if attempt < MAX_RETRIES then
			task.wait(RETRY_BASE_DELAY * 2 ^ (attempt - 1))
		end
	end
	return false
end

-- Writes data only if THIS server still owns the lock. Never overwrites blindly.
local function commit(userId: number, data: PlayerData, releaseLock: boolean): boolean
	local lockLost = false
	local ok = withRetries("save " .. userId, function()
		store:UpdateAsync(userId, function(stored)
			lockLost = false -- transform may run several times
			local record = toRecord(stored)
			if not record or not record.Lock or record.Lock.JobId ~= game.JobId then
				lockLost = true
				return nil -- nil = cancel the write
			end
			record.Data = data
			record.Lock = if releaseLock then nil else { JobId = game.JobId, Time = os.time() }
			return record
		end)
	end)
	if lockLost then
		warn("[DataManager] lock lost for", userId, "- save skipped to avoid overwriting newer data")
	end
	return ok and not lockLost
end

-- Returns data if lock acquired, nil if another server still holds it.
local function tryAcquire(userId: number): (boolean, PlayerData?)
	local acquired: PlayerData? = nil
	local ok = withRetries("load " .. userId, function()
		store:UpdateAsync(userId, function(stored)
			acquired = nil
			local record = toRecord(stored)
				or { Schema = SCHEMA_VERSION, Data = defaultData(), Lock = nil }
			local lock = record.Lock
			if lock and lock.JobId ~= game.JobId and os.time() - lock.Time < LOCK_STALE_SECONDS then
				return nil -- another server is still saving/holding this player
			end
			record.Lock = { JobId = game.JobId, Time = os.time() }
			acquired = record.Data
			return record
		end)
	end)
	return ok, acquired
end

function DataManager.load(player: Player): boolean
	for _ = 1, LOCK_WAIT_ATTEMPTS do
		local ok, data = tryAcquire(player.UserId)
		if not ok then
			return false -- DataStore down: do NOT hand out default data
		end
		if data then
			if player.Parent ~= Players then
				commit(player.UserId, data, true) -- left while loading: just release
				return false
			end
			profiles[player] = data
			return true
		end
		task.wait(LOCK_WAIT_SECONDS) -- old server usually finishes its save in a few seconds
	end
	return false
end

function DataManager.get(player: Player): PlayerData?
	return profiles[player]
end

function DataManager.release(player: Player)
	local data = profiles[player]
	if not data then
		return -- never loaded => never saved. This is what prevents wipes.
	end
	profiles[player] = nil
	commit(player.UserId, data, true)
end

function DataManager.releaseAll()
	local pending = 0
	for player in profiles do
		pending += 1
		task.spawn(function()
			DataManager.release(player)
			pending -= 1
		end)
	end
	while pending > 0 do
		task.wait()
	end
end

function DataManager.startAutosave()
	task.spawn(function()
		while true do
			task.wait(AUTOSAVE_INTERVAL)
			for player, data in profiles do
				task.spawn(commit, player.UserId, data, false) -- also refreshes lock time
			end
		end
	end)
end

-- Validates BOTH sides before mutating anything, then persists both immediately.
local function collectOwned(data: PlayerData, uids: { string }): boolean
	local seen = {}
	for _, uid in uids do
		if typeof(uid) ~= "string" or seen[uid] or not data.Items[uid] then
			return false
		end
		seen[uid] = true
	end
	return true
end

function DataManager.executeTrade(a: Player, aUids: { string }, b: Player, bUids: { string }): boolean
	local aData, bData = profiles[a], profiles[b]
	if a == b or not aData or not bData then
		return false
	end
	if not collectOwned(aData, aUids) or not collectOwned(bData, bUids) then
		return false
	end

	for _, uid in aUids do
		bData.Items[uid] = aData.Items[uid]
		aData.Items[uid] = nil
	end
	for _, uid in bUids do
		aData.Items[uid] = bData.Items[uid]
		bData.Items[uid] = nil
	end

	task.spawn(commit, a.UserId, aData, false)
	task.spawn(commit, b.UserId, bData, false)
	return true
end

return DataManager
```

Серверный скрипт (`ServerScriptService/Core/DataBootstrap`):

```lua
local Players = game:GetService("Players")
local DataManager = require(script.Parent.DataManager)

local function onPlayerAdded(player: Player)
	if not DataManager.load(player) then
		player:Kick("Не удалось загрузить сохранение. Перезайди через минуту — твои предметы в безопасности.")
	end
end

Players.PlayerAdded:Connect(onPlayerAdded)
for _, player in Players:GetPlayers() do -- players who joined before this script ran
	task.spawn(onPlayerAdded, player)
end

Players.PlayerRemoving:Connect(DataManager.release)
game:BindToClose(DataManager.releaseAll)
DataManager.startAutosave()
```

## Важные детали

- **Ключ не меняйте.** `UpdateAsync(player.UserId, ...)` использует тот же ключ и то же хранилище, что и раньше. `toRecord` один раз обернёт старые данные в новый формат. Если старые предметы лежат как `{ Sword = 2 }`, в месте миграции раздайте им uid.
- **Функция внутри `UpdateAsync` не должна yield-ить** и может вызываться несколько раз. Поэтому флаги сбрасываются в начале функции. Возврат `nil` отменяет запись: это документированное поведение, на нём держится весь лок.
- **Сама торговля:** клиент присылает только *намерение* (uid предметов и подтверждение). Всё остальное делает сервер: проверяет, что оба игрока загружены и находятся рядом/в сессии обмена, что предметы действительно их, и защищается от спама RemoteEvent (rate limit, флаг «обмен в процессе» на игрока). Два одновременных обмена одного и того же предмета отсекутся проверкой `data.Items[uid]`, потому что `executeTrade` не yield-ит между проверкой и изменением.
- **`BindToClose`** даёт ограниченное время на завершение (насколько я помню, около 30 секунд — лучше проверить в документации). При 40 CCU этого с запасом хватает, но большие задержки ретраев там не помогут.
- **Лок в Studio:** `game.JobId` в Studio, насколько я знаю, пустая строка, так что два окна Studio будут считать лок своим. Для тестирования это не мешает, просто учитывайте это.

## Альтернатива, которую я бы рассмотрел всерьёз

Session locking — это ровно то, что делает **ProfileStore** (преемник ProfileService от loleris). Насколько я помню, там же есть автосейв, обработка shutdown и защита от перезаписи. Писать свой лок можно (код выше рабочий по принципу), но у готовой библиотеки намного больше обкатанных краевых случаев. Для игры с торговлей, где дюп обесценивает экономику, я бы, скорее всего, взял её. Актуальный API проверьте в репозитории/на DevForum: названия методов по памяти приводить не буду.

## Как проверить

1. **Вайп:** временно сделайте `tryAcquire` всегда возвращающим `false, nil`. Игрока должно кикнуть, а данные в хранилище остаться нетронутыми (смотрите через DataStore Editor или `GetAsync` из командной строки).
2. **Лок:** в Local Server с двумя серверами (или вручную записав в ключ чужой `Lock` со свежим `Time`) проверьте, что загрузка ждёт и не выдаёт данные.
3. **Обмен:** выполните обмен и сразу принудительно закройте сервер. После перезахода у каждой стороны должно быть корректное состояние.
4. **Аудит:** раз в какое-то время прогоните по сохранениям поиск одинаковых uid у разных игроков. Если найдутся, значит где-то ещё остаётся дыра.

И не забудьте включить «Enable Studio Access to API Services», иначе в Studio DataStore работать не будет.
