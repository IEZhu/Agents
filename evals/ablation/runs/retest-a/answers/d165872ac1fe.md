**Коротко:** дело не в том, что модель «ошиблась», а в архитектуре. Цикл исполняет всё, что модель выдала, и ничего не проверяет. Parallel tool calls позволяют модели в одном ответе выдать *зависимые* вызовы: `cancel` должен был использовать результат `get`, но модель этого результата ещё не видела, поэтому `sub_77` она взяла из головы или из старого контекста. Защищаться нужно не промптом, а кодом: разрешения на запись, проверки на сервере и подтверждение перед необратимым действием.

## Что не так

1. **Чтение и запись исполняются одинаково.** `get_subscription` безопасен, а `cancel_subscription` меняет деньги и состояние. В цикле у них одна и та же политика «выполнить сразу».
2. **Зависимые вызовы попадают в один батч.** Модель выдаёт вызовы параллельно, но проверить, что второй зависит от первого, она не может. `sub_77` не взят из ответа `get_subscription`, потому что этого ответа ещё не было.
3. **Идентификатор выбирает модель.** `cancel_subscription(subscription_id=...)` верит тому, что сгенерировала LLM. Сервер не проверяет, что подписка принадлежит этому юзеру и что она активна.
4. **Бэкенд, судя по всему, спокойно принял отмену уже отменённой подписки.** Это отдельный баг. Скорее всего, модель получила «успех» и сказала юзеру, что подписка отменена, хотя `sub_91` осталась активной. Для биллинга это как раз «сломалось»: юзеру дальше списываются деньги. Проверьте в логах, что модель ответила юзеру после этих вызовов.
5. **Нет подтверждения перед необратимым действием.** Отмену подписки должен подтвердить человек или хотя бы детерминированная проверка.
6. **Цикл хрупкий.** `while True` без лимита итераций. Если инструмент бросит исключение или `json.loads` упадёт на кривых аргументах, цикл вылетит. А если просто пропустить вызов, в истории не будет tool-сообщения для этого `tool_call_id`, и следующий запрос к API, насколько я помню, завершится ошибкой.

## Как поправить (от самого важного)

### 1. Проверки на сервере: главный фикс
Сузьте инструмент так, чтобы ошибиться было нельзя:

- `user_id` берётся из сессии, а не из аргументов модели;
- `cancel_subscription` проверяет, что подписка принадлежит этому юзеру и что `status == active`. Иначе возвращает понятную ошибку: `{"error": "subscription_not_active", "active_subscriptions": ["sub_91"]}`. Модель прочитает её и исправится на следующем шаге;
- ещё лучше вообще убрать выбор ID: `cancel_active_subscription()` для типичного случая, когда у юзера одна активная подписка.

Это защищает от любых галлюцинаций, а не только от тех, что возникли из-за параллельности.

### 2. Запись только отдельным шагом
Вариант попроще: отключить параллельность целиком, `parallel_tool_calls=False` в `chat.completions.create` (параметр указываю по памяти, сверьтесь с докой OpenAI). Минус: чтения тоже станут последовательными и медленнее.

Вариант получше: оставить параллельные чтения, но если в батче есть мутирующий вызов вместе с другими, мутацию не выполнять, а вернуть модели ошибку «вызови повторно отдельно, после того как получишь результаты чтения».

### 3. Подтверждение для необратимых действий (human-in-the-loop)
`cancel` не выполняется сразу. Сначала готовится действие: «Отменить sub_91 (тариф X, активна до ...)?». Выполняется оно только после явного «да» от юзера, и подтверждается ровно тот ID, который показали.

### 4. Идемпотентность и аудит
Для каждого мутирующего вызова нужен idempotency key (например, из `tool_call_id`) и запись в журнал: кто вызвал, с какими аргументами, что вернул бэкенд.

## Эскиз цикла

```python
MUTATING = {"cancel_subscription", "refund", "change_plan"}
MAX_ITERS = 10

def run_tool(tc, session):
    try:
        args = json.loads(tc.function.arguments)
        impl = TOOL_IMPL[tc.function.name]
    except (json.JSONDecodeError, KeyError) as e:
        return {"error": f"bad_call: {e}"}
    try:
        # user_id берём из сессии, а не от модели
        return impl(session=session, **args)
    except ToolError as e:  # доменные ошибки: not_owner, not_active, ...
        return {"error": str(e)}

for _ in range(MAX_ITERS):
    resp = client.chat.completions.create(model="gpt-4.1", messages=msgs, tools=TOOLS)
    msg = resp.choices[0].message
    msgs.append(msg)
    if not msg.tool_calls:
        break

    calls = msg.tool_calls
    has_write = any(tc.function.name in MUTATING for tc in calls)

    for tc in calls:
        name = tc.function.name
        if name in MUTATING and len(calls) > 1:
            result = {"error": "write_must_be_alone",
                      "hint": "Call this again on its own, after reading the results of the other calls."}
        elif name in MUTATING:
            result = request_confirmation(tc, session)  # в ответ идёт pending_confirmation, а не выполнение
        else:
            result = run_tool(tc, session)
        # на каждый tool_call_id обязательно отвечаем, даже ошибкой
        msgs.append({"role": "tool", "tool_call_id": tc.id, "content": json.dumps(result)})
else:
    escalate_to_human(msgs)  # лимит итераций исчерпан
```

## Что проверить у себя

- Откуда взялся `sub_77`: из прошлой истории диалога, из few-shot примера в системном промпте или выдуман. Если из примера, уберите реальные на вид ID из промпта.
- Что возвращает бэкенд на отмену уже отменённой подписки (`status` / HTTP-код). Если 200 и «ок», это баг бэкенда, его стоит чинить независимо от агента.
- Что модель написала юзеру после этого эпизода. Если «отменено», значит у юзера до сих пор активна `sub_91`, и это надо разрулить вручную.

## Как не допустить повторения
Соберите небольшой набор тестов: у юзера несколько подписок; активная одна, а в истории упоминается старая; юзер с чужим ID в запросе; модель выдаёт get и cancel одним батчем. Для каждого проверяйте, что мутация без валидного, подтверждённого и принадлежащего юзеру ID не проходит. Для биллинга здесь целевое значение ноль, а не «почти всегда».
