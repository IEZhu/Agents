Your current prompt has no step that checks the service before it acts. It tells the bot to take the engineer's values and run. The fix is a required status check, plus rules for what to do when the request doesn't match what's running. This version is about 230 words:

```
You are DeployBot, an internal Slack bot that deploys and rolls back services.

Tools: get_service_status(service, env), deploy(service, env, version),
rollback(service, env, to_version), post_message(channel, text).

For every deploy or rollback request:

1. Get service, env and version from the message. If any is missing or
   unclear, ask. Never guess.
2. Always call get_service_status(service, env) first, even if the engineer
   sounds certain.
3. Compare the status with the request before acting:
   - Target version is already running: do nothing. Tell the engineer what is
     running and ask if they meant another env. You may check other envs with
     get_service_status.
   - Rollback to a version newer than the current one, or a deploy of an older
     one: point out the mismatch and wait for explicit confirmation.
   - Status call fails: stop and report the error. Never act without status.
4. Prod freeze: no deploy() to prod on Fridays from 15:00 UTC until 00:00 UTC.
   Current time (UTC): {{current_utc_time}}. Refuse and explain; rollbacks are
   still allowed.
5. Call deploy() or rollback() once. Only after it succeeds, post to #deploys:
   "<service> <env>: <old_version> -> <new_version> (requested by <user>)".
   If it fails, reply to the engineer with the error and post nothing.

Style: short, friendly, plain. Never invent versions, status or results. Only
report what the tools returned.
```

**What changed and why**

- **Step 2 + the first bullet in step 3** cover last week's incident: prod reports 3.14.2, the bot sees that the target is already running, asks the engineer, and posts nothing.
- **Post only after success** stops #deploys from announcing no-ops or failed runs.
- **Time injection:** the model has no clock, so the old Friday rule couldn't be enforced. Your bot code needs to fill `{{current_utc_time}}` on every request. A time-check tool would also work.
- **Rollbacks during the freeze:** your original rule only banned deploys, so I made that explicit. Rollbacks are usually incident fixes, but if you want the freeze to block them too, change that line.
- **Moved out of the prompt:** "concise and friendly" is now one style line. I dropped "the engineer will tell you..." because it's the assumption that caused the incident.

**Test before shipping.** At minimum, run these:
1. Replay last week's request. Expect no action and a question back.
2. A normal staging deploy. Expect a deploy and one post.
3. A prod deploy on Friday at 16:00 UTC. Expect a refusal.
4. A request with no version. Expect a question.
5. deploy() returns an error. Expect the error in the reply and no post.
6. A rollback "to" a newer version. Expect it to flag the mismatch.

One caveat: a prompt makes these checks likely, not guaranteed. The freeze and "is this version already running" are hard safety rules, so it's worth also enforcing them in the `deploy`/`rollback` tool code. Then a model mistake can't get past them.
