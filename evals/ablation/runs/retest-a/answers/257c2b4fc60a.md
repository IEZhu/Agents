**Short answer: no.** "Never retry pay_invoice" addresses the symptom, and it only does so probabilistically. The root cause is in the tool layer: a non-idempotent money-moving tool reported an *ambiguous* outcome (timeout) as a *failure*. The model then did what most engineers would do with a "ToolError": it retried. Fix the contract first, then the prompt.

## What actually happened

- The first `pay_invoice` call did reach the payment provider and created `pay_5498`. Only the **response** timed out, after 30s. A timeout tells you "I don't know if it happened", not "it failed".
- The tool turned that unknown into `ToolError`, which the model read as a failure. Step 3's reasoning is the predictable result of how the error was surfaced.
- Nothing downstream stopped a second payment on an invoice that already had one in flight. There was no idempotency key, no state check, and no lock.

So there are three missing safeguards, and the prompt is not the right place for any of them.

## Why "never retry" is the wrong fix

1. **Prompt rules are soft.** Under a different error message, a long context, or a paraphrased tool name, the model may retry anyway. For a double payment you want a guarantee that holds 100% of the time, and a prompt instruction can't give you that.
2. **It breaks the opposite case.** If the call really did fail before it reached the bank (connection refused, 4xx validation error), "never retry" leaves an approved invoice unpaid, and a vendor ends up chasing you. You trade duplicate payments for missed payments, and the agent can't tell the two cases apart either.
3. **It doesn't cover other paths to a duplicate.** A human re-running the workflow, a queue redelivering the job, or two agent instances picking up the same invoice can all still pay twice.

## What I'd change, in priority order

### 1. Make `pay_invoice` idempotent (the actual fix)
- Derive a deterministic idempotency key from the business operation, e.g. `pay:INV-20931:v1` (or invoice ID + approval ID). Don't use a random UUID per call. That way a retry reuses the same key.
- Send it to the payment provider if it supports idempotency keys. Many payment APIs do; check your provider's docs for the exact header or field name, since I can't confirm it for your bank. If it doesn't, enforce idempotency in your own service: before submitting, write a `payment_attempt` row with a unique constraint on `invoice_id`.
- With this in place, a retry returns the original `pay_5498` instead of creating `pay_5512`. Retrying becomes safe, and you *want* the agent to be able to retry.

### 2. Guard on invoice state inside the tool, not in the model
Make the invoice an explicit state machine and enforce it server-side:

```
approved --pay_invoice--> payment_pending --provider confirms--> paid
                                   \--provider rejects--> payment_failed --(retry allowed)--> payment_pending
```

`pay_invoice` should refuse (return a structured "already in progress / already paid" result, not an error) unless the invoice is `approved` or `payment_failed`. Do the state transition atomically, with a conditional update or a row lock, so concurrent callers can't both pass the check.

### 3. Return honest, structured outcomes instead of bare errors
Replace `ToolError: upstream timeout` with something the model can reason about:

```json
{
  "status": "unknown",
  "reason": "upstream_timeout",
  "invoice_id": "INV-20931",
  "idempotency_key": "pay:INV-20931:v1",
  "safe_to_retry": true,
  "next_step": "call get_payment_status(invoice_id) before any further action"
}
```

Use three distinct outcomes: `succeeded`, `failed` (definitely not submitted, safe to retry), and `unknown` (reconcile first). Most of the model's decision quality comes from this shape.

### 4. Add a reconciliation tool
Add `get_payment_status(invoice_id)` (or `list_payments(invoice_id)`), which queries the provider or your ledger. On `unknown`, the agent checks, finds `pay_5498`, and stops. This is the "read current state before a side-effecting action" step, and the tool contract makes it cheap to do.

### 5. Then update the prompt, as the last layer
Replace "never retry" with a rule that matches the new contract:

> Before calling `pay_invoice`, confirm with `get_invoice` that status is `approved` or `payment_failed`. If `pay_invoice` returns `status: "unknown"`, do not call it again. Call `get_payment_status` first and act on what it returns. If the status is still unknown after reconciliation, stop and escalate to a human with the invoice ID and idempotency key.

This rule is defense in depth. The guarantee comes from layers 1 and 2.

### 6. Human override point for money
Consider requiring human approval for any payment action after an `unknown` outcome, and possibly above an amount threshold. The threshold is a policy choice, and 12.4k EUR may or may not be over yours. This is the one place where Co-Pilot-level control is worth the friction.

## Regression tests to add
Use fault injection against a mock provider:
- **Timeout after commit:** the provider records the payment, then the response times out. Expect exactly one payment and the agent reconciling rather than re-paying. This is your exact incident; it should be the first test.
- **Timeout before commit:** the provider never receives the call. Expect the agent to retry with the same key, ending in exactly one payment.
- **Definite failure (4xx):** expect no payment and an escalation or `payment_failed` state.
- **Concurrent double invocation:** two agents or jobs hit the same invoice. Expect exactly one payment.
- **Invoice already `paid`:** expect `pay_invoice` to refuse without calling the provider.

Track the duplicate-payment rate per invoice as a hard metric with a zero target and alerting. Also check the time from `unknown` to reconciliation.

## Immediate remediation
- Reverse or recall one of the two debits (`pay_5512` is the natural candidate) through your bank or provider, or ask the vendor for a refund or a credit note. Recall windows depend on the payment rail, so move quickly.
- Search your payment logs for any other invoice with more than one payment ID. If the tool has run for a while, this is unlikely to be the only time it happened.
- Check the timeout mismatch. Your client gave up at 30s while the provider evidently kept processing. Make the client timeout at least as long as the provider's own processing timeout, or treat anything past it as `unknown` (see point 3).

**Bottom line:** tell your teammate the prompt change is fine as an extra layer, but it isn't the fix. The fix is an idempotency key plus a server-side state guard plus a tool result that says "unknown" when the outcome is unknown. With those in place, retrying becomes safe, and that's the property you want.
