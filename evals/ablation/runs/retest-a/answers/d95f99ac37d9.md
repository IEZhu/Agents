**Коротко:** цикл выполняет любой пакет tool calls вслепую. Модель запросила чтение и запись в одном ответе, поэтому `subscription_id` для `cancel_subscription` она сгенерировала **до** того, как увидела результат `get_subscription`. Сама по себе модель тут ни при чём: ошибка в том, что инвариант «сначала прочитай состояние, потом меняй» нигде не принуждается. Ни цикл, ни инструмент его не проверяют. Исправлять надо на трёх уровнях: в цикле, в контракте инструмента и в разграничении прав.

## Что именно сломалось

1. **Мутация идёт в одном батче с чтением.** При parallel tool calls все аргументы генерируются за один проход. `sub_77` не может быть основан на ответе `get_subscription`, потому что этого ответа ещё не было. Скорее всего, id взят из старого контекста (истории диалога, прошлой сессии, примера в промпте) или просто выдуман. Точно покажут логи: поищите `sub_77` в `msgs` до этого шага.
2. **Инструмент не проверяет предусловия.** `cancel_subscription` поверил аргументу модели и не проверил, что подписка принадлежит этому пользователю и что она активна. Вся защита держалась на том, что модель «правильно подумает».
3. **Вам повезло сильнее, чем кажется.** Всё обошлось только потому, что `sub_77` уже была отменена. Будь это **активная подписка другого клиента**, вы бы отменили её, и цикл бы это позволил: модель может подставить любой `user_id` или `subscription_id`, и ничто не привязывает вызов к текущему пользователю.
4. **Прочие дефекты цикла**, которые выстрелят следующими:
   - `while True` без лимита шагов;
   - исключение в инструменте (или `KeyError` на неизвестном имени, или битый JSON в `arguments`) роняет весь цикл вместо того, чтобы вернуть модели ошибку как observation;
   - нет идемпотентности у мутаций: при ретрае возможен двойной cancel или refund.

## Как исправить

### 1. Инструмент сам проверяет свои предусловия (главное)

Это единственный слой, который работает независимо от поведения модели. Промпт вида «сначала вызови get_subscription» полезен, но это пожелание, а не гарантия.

```python
class BillingError(Exception):
    pass

def cancel_subscription(subscription_id: str, *, user_id: int, idempotency_key: str):
    sub = billing.get_subscription_by_id(subscription_id)
    if sub is None or sub.user_id != user_id:
        # Одинаковый ответ для обоих случаев: не раскрываем чужие подписки
        raise BillingError(f"subscription {subscription_id} not found for this user")
    if sub.status != "active":
        raise BillingError(
            f"subscription {subscription_id} is '{sub.status}', not active; "
            "call get_subscription to find the active one"
        )
    return billing.cancel(subscription_id, idempotency_key=idempotency_key)
```

Сообщение об ошибке пишите для модели: что не так и что делать дальше. Тогда на следующем шаге она сама вызовет `get_subscription` и найдёт `sub_91`.

### 2. `user_id` берётся из сессии, а не от модели

Уберите `user_id` из JSON-схем инструментов. Цикл подставляет его из аутентифицированной сессии. Тогда модель физически не может действовать от имени другого клиента.

### 3. Цикл: мутации только поодиночке и после чтения

```python
MAX_STEPS = 10
MUTATING = {"cancel_subscription", "refund_invoice", "change_plan"}

def run_agent(msgs, session_user_id):
    for _ in range(MAX_STEPS):
        resp = client.chat.completions.create(
            model="gpt-4.1",
            messages=msgs,
            tools=TOOLS,
            parallel_tool_calls=False,  # см. примечание ниже
        )
        msg = resp.choices[0].message
        msgs.append(msg)
        if not msg.tool_calls:
            return msg.content

        batch = msg.tool_calls
        batch_has_write = len(batch) > 1 and any(tc.function.name in MUTATING for tc in batch)

        for tc in batch:
            # Ответ нужен на КАЖДЫЙ tool_call_id, иначе следующий запрос упадёт
            if batch_has_write and tc.function.name in MUTATING:
                result = {"error": "Not executed: state-changing calls must be issued alone, "
                                   "after reading current state. Re-issue it separately."}
            else:
                result = execute_tool(tc, session_user_id)
            msgs.append({"role": "tool", "tool_call_id": tc.id, "content": json.dumps(result)})

    raise RuntimeError(f"agent did not finish in {MAX_STEPS} steps")


def execute_tool(tc, session_user_id):
    impl = TOOL_IMPL.get(tc.function.name)
    if impl is None:
        return {"error": f"unknown tool '{tc.function.name}'"}
    try:
        args = json.loads(tc.function.arguments)
    except json.JSONDecodeError as e:
        return {"error": f"arguments are not valid JSON: {e}"}
    args["user_id"] = session_user_id
    if tc.function.name in MUTATING:
        args["idempotency_key"] = tc.id  # повтор того же вызова не выполнится дважды
    try:
        return impl(**args)
    except (BillingError, TypeError) as e:  # TypeError: неверные/лишние аргументы
        return {"error": str(e)}
```

Примечание: параметр `parallel_tool_calls` в Chat Completions я привожу по памяти, не проверял. Сверьтесь с документацией OpenAI. Даже если он работает как ожидается, оставьте проверку батча в цикле: это защита на уровне кода, а не на уровне настройки модели.

Почему не выключать параллельность совсем: параллельные **чтения** полезны, так как экономят раунды и латентность. Опасны только мутации в батче. Поэтому правило именно такое: чтения в батче выполняются, мутация в батче отклоняется с понятной ошибкой.

### 4. Для необратимых действий: подтверждение

Отмена подписки и возвраты денег необратимы или дороги в откате. Здесь стоит сделать двухфазную схему:

- `prepare_cancel(subscription_id)` проверяет состояние и возвращает сводку («Отменить sub_91, план Pro, списание 12 окт.?») и `confirmation_token`;
- `confirm_cancel(token)` выполняется только после явного «да» от пользователя (или оператора) и только с валидным, не истёкшим токеном.

Токен, привязанный к конкретной подписке и её состоянию на момент prepare, заодно закрывает гонку: если подписка изменилась между шагами, подтверждение не пройдёт.

## Итоговая схема ответственности

| Слой | Что гарантирует |
|---|---|
| Промпт: «перед изменением всегда читай текущее состояние» | Снижает частоту ошибок, но ничего не гарантирует |
| Цикл: мутации только поодиночке, лимит шагов, ошибки как observation | Модель всегда видит результат чтения до записи |
| Инструмент: проверка владельца и статуса, идемпотентность | Неверный вызов не может причинить вред, даже если модель ошиблась |
| Сессия: `user_id` вне контроля модели | Нельзя затронуть чужого клиента |
| Подтверждение для необратимых действий | Человек в контуре там, где цена ошибки высока |

Что проверить после правки:
- модель в одном ответе выдаёт `get` + `cancel`: cancel отклонён, на следующем шаге выполняется с правильным id;
- cancel уже отменённой подписки: понятная ошибка;
- cancel подписки чужого пользователя: «not found»;
- битый JSON в аргументах;
- повтор того же `tool_call_id`: второй раз не выполняется;
- модель зацикливается: срабатывает `MAX_STEPS`.

Отдельно залогируйте частоту отклонённых мутаций из батчей. Если она заметная, добавьте в системный промпт пару few-shot примеров последовательности «прочитать, потом изменить». Это уменьшит число лишних раундов.
