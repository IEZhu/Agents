## Latest user message
Our Node 20.11 image service (Express, runs in k8s with a 2Gi memory limit) keeps getting OOMKilled every ~6 hours. RSS climbs steadily from ~300MB to ~1.9GB, but process.memoryUsage().heapUsed in our Grafana stays flat around 170-190MB the whole time. This started the week we (a) upgraded from Node 18 to 20 and (b) shipped a new /thumb endpoint that uses sharp 0.33 to resize uploaded JPEGs. We also added an in-memory cache with lru-cache v10, `max: 5000`, that stores the resized thumbnails as Buffers keyed by URL. Base image is node:20-bookworm-slim. I have about half a day before I hand this over to on-call. Where should I spend that time, in what order?

## Answer A
**Short answer:** The memory is growing off the V8 heap, and your heap metric can't see it. That leaves two main suspects: (1) the lru-cache, which limits the number of entries but not their total size, and (2) sharp/libvips native memory combined with glibc malloc fragmentation. Spend the first hour finding out which one it is. The Node 18 → 20 upgrade is the least likely cause, so check it last.

`heapUsed` staying flat while RSS climbs tells you a lot. A Buffer's backing store is allocated outside the JS heap, so neither 5,000 cached thumbnails nor libvips pixel buffers would ever show up in `heapUsed`. That means your dashboard currently can't tell you anything about either suspect.

## Plan for the half day

### 1. Instrument so you can tell the suspects apart (~45 min)

Export these next to `rss` and `heapUsed`:

- `process.memoryUsage().external` and `.arrayBuffers`: Buffer memory, which includes your cache.
- `cache.size` and the total byte size of the cached values.
- In-flight `/thumb` requests (a gauge).

Also do a quick calculation: **average thumbnail size × 5000**. If the thumbnails average around 300 KB, a full cache is about 1.5 GB, which by itself accounts for most of the growth you're seeing. If they're around 30 KB, the cache tops out near 150 MB and is not your main problem.

How to read the result:

| What you see | Likely cause |
|---|---|
| `arrayBuffers` rises in step with RSS, and cache bytes rise with it | The cache (step 2) |
| `arrayBuffers` stays flat or bounded, but `rss − (heapTotal + external)` keeps growing | Native memory or allocator fragmentation (step 3) |
| Both grow | Both. Fix the cache first because it's cheap |

### 2. Limit the cache by bytes, not entries (~30 min; do it whatever step 1 shows)

`max: 5000` puts no limit on memory. Switch to a byte budget:

```js
import { LRUCache } from 'lru-cache';

const THUMB_CACHE_BYTES = 256 * 1024 * 1024;   // pick a budget that fits the 2Gi pod
const THUMB_MAX_ENTRY_BYTES = 2 * 1024 * 1024;

const thumbCache = new LRUCache({
  maxSize: THUMB_CACHE_BYTES,
  maxEntrySize: THUMB_MAX_ENTRY_BYTES,
  sizeCalculation: (buf) => buf.length,
});
```

I'm working from memory on `maxSize`, `maxEntrySize` and `sizeCalculation` in v10, so check them against the lru-cache README for your installed version. If you use `maxSize`, `sizeCalculation` is required, or you must pass `size` on every `set()`.

Two more things to check:

- Make sure you cache what `sharp().toBuffer()` returns, and not a `subarray()` or slice of some larger buffer. A slice keeps its whole parent buffer alive.
- Put the cache behind an env flag (`THUMB_CACHE_ENABLED=false`). That gives on-call a way to turn it off.

It's also worth asking whether this cache should be in the process at all. With several pods, each one keeps its own copy. `Cache-Control` headers plus a CDN or nginx cache in front would probably work better. That's a question for later, not for today.

### 3. Rule out sharp/libvips and the allocator (~1.5 h)

On glibc-based images such as `bookworm-slim`, libvips' many threads and short-lived allocations are known to fragment glibc malloc. RSS then keeps rising even though nothing is leaking. sharp's own docs recommend jemalloc on glibc Linux for this reason. Try these **one at a time**:

1. **jemalloc** (usually the fix that makes the biggest difference):
   ```dockerfile
   RUN apt-get update && apt-get install -y --no-install-recommends libjemalloc2 \
       && rm -rf /var/lib/apt/lists/*
   ENV LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2
   ```
   The path depends on the architecture (on arm64 it's `aarch64-linux-gnu`). Confirm it with `dpkg -L libjemalloc2`.
2. **Or `MALLOC_ARENA_MAX=2`**: less effective than jemalloc, but it's only an env var.
3. **Tune sharp**: `sharp.concurrency(1)` if the pod has few CPUs, and `sharp.cache(false)` or a small `sharp.cache({ memory: … })`. I believe libvips' operation cache defaults to about 50 MB, but that's from memory, so check the sharp docs.
4. **Reduce what gets decoded**: set `limitInputPixels`, enforce an upload size limit, and use `sharp(input).resize(...)` directly. JPEG shrink-on-load only helps if the resize is part of the same pipeline.

### 4. Reproduce locally and compare fixes (~1.5 h, alongside step 3)

Run the image with `docker run --memory=2g`. Send `/thumb` requests with **unique URLs** so the cache keeps filling, for example with `autocannon` or `k6`. Plot RSS against `arrayBuffers` for 20–30 minutes, once per variant: baseline, byte-limited cache, cache disabled, jemalloc. The steady climb should make the difference visible well before 6 hours.

### 5. Read through the `/thumb` code (~30 min)

Look for:

- **Unlimited concurrency.** If nothing caps in-flight sharp jobs, a burst means N full-size decoded images in memory at once. Add a semaphore such as `p-limit` sized to the CPU count.
- **Uploads held in memory**, for example `multer.memoryStorage()` with no `limits.fileSize`.
- **Streams not destroyed** when a request is aborted or errors. Use `stream.pipeline`, not `.pipe()`.

### 6. Node 18 → 20 (only if nothing above explains it)

Your symptoms point to off-heap memory, and the upgrade mostly affects the V8 heap, so this is probably not the cause. If you still have unexplained growth after steps 2–3, run the same build on `node:18-bookworm-slim` in the local repro. Don't roll back production for this.

### 7. Handover (last 30 min)

- Ship the cache byte limit and jemalloc (or at least the flag to disable the cache) before you hand over.
- Leave on-call the Grafana panel (`rss`, `heapUsed`, `external`, `arrayBuffers`, cache bytes), the env flags, and your notes on which suspect you confirmed.
- Set up an alert at about 80% of the memory limit so a restart happens in a controlled way instead of an OOMKill. That doesn't fix anything, but it protects users while the root cause is confirmed. Don't bother with `--max-old-space-size`: the heap isn't what's growing.

## Answer B
**Short answer:** skip heap snapshots and the Node 18→20 upgrade for now. A flat `heapUsed` with RSS climbing means the memory is **outside the V8 JS heap**. That leaves two suspects, both from the new `/thumb` work: (1) the Buffers in your LRU cache, which is capped by entry count and not by bytes, and (2) native memory from sharp/libvips, made worse by glibc malloc fragmentation. Spend the half day separating those two, put a mitigation in place, and hand over with the right metrics on the dashboard.

## Why heapUsed is misleading here

Buffer contents live off the V8 heap. They show up in `process.memoryUsage().external` / `.arrayBuffers`, not in `heapUsed`. libvips allocations (decode buffers, its operation cache, thread pools) don't appear in any `memoryUsage()` field except `rss`. So your Grafana panel can't see either suspect.

## Suggested order (~4 hours)

### 1. Instrument first (30 min)
Add these to the metrics you already export:

```js
setInterval(() => {
  const m = process.memoryUsage();
  metrics.gauge('mem_rss', m.rss);
  metrics.gauge('mem_heap_used', m.heapUsed);
  metrics.gauge('mem_external', m.external);
  metrics.gauge('mem_array_buffers', m.arrayBuffers);
  metrics.gauge('thumb_cache_entries', thumbCache.size);
  metrics.gauge('thumb_cache_bytes', thumbCache.calculatedSize ?? 0); // once sizeCalculation exists (step 2)
}, 15_000).unref();
```

After deploy, the curves answer the main question within an hour or two of traffic:
- **`arrayBuffers` climbs along with RSS** → it's the cache (or some other Buffer retention). Go to step 2.
- **`arrayBuffers` stays flat and RSS keeps climbing** → it's native memory (sharp/libvips/malloc). Go to step 3.

While you wait, set up the local repro in step 4 so it's ready.

### 2. Cap the cache by bytes (30 min). Do this whatever the metrics show.
`max: 5000` limits entry count, not memory. Rough math: 5000 thumbnails × 100–300 KB each is roughly **0.5–1.5 GB** of Buffers. That alone fits "300 MB → 1.9 GB over a few hours". Two things make it worse:
- If the key is the raw URL, query-string variants (`?w=200` vs `?w=201`, cache-busters, signed URLs) create many near-duplicate entries, so the cache fills faster than you'd expect.
- If any cached value is a *slice* of a larger Buffer (for example the original upload from multer `memoryStorage`), the whole parent buffer stays in memory. Values straight from sharp's `toBuffer()` should be standalone, but check that nothing else ends up in the cache.

lru-cache v10 supports byte-based limits:

```js
import { LRUCache } from 'lru-cache';

const THUMB_CACHE_MAX_BYTES = 256 * 1024 * 1024; // budget explicitly against the 2Gi limit

const thumbCache = new LRUCache({
  maxSize: THUMB_CACHE_MAX_BYTES,
  sizeCalculation: (buf) => buf.byteLength,
  maxEntrySize: 2 * 1024 * 1024, // don't let one oversized result evict everything
  ttl: 60 * 60 * 1000,           // optional, keeps the cache from pinning cold entries forever
});
```

Also normalize the cache key: strip parameters that don't affect the output and use a canonical `(sourceId, width, height, format)` tuple. `maxSize`/`sizeCalculation`/`maxEntrySize` are the documented v10 options as I remember them. Check them against the README of the version in your lockfile.

If RSS now **plateaus** around baseline + cache budget, you've found the problem.

### 3. Native memory: sharp + glibc (1 hour)
`node:20-bookworm-slim` is glibc-based. glibc malloc handles libvips' pattern of many large, short-lived allocations across threads badly: freed memory gets fragmented across per-thread arenas and doesn't go back to the OS, so RSS keeps rising while nothing is actually leaking. sharp's docs cover this and recommend jemalloc on glibc Linux (recalled, not verified here; see the "memory allocator" section of the sharp install docs). Things to try, cheapest first:

```dockerfile
# Option A: jemalloc (usually the most effective)
RUN apt-get update && apt-get install -y --no-install-recommends libjemalloc2 \
    && rm -rf /var/lib/apt/lists/*
ENV LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2
# path is arch-specific: aarch64-linux-gnu on ARM nodes. Verify with `dpkg -L libjemalloc2`

# Option B: no new package, limit glibc arenas
ENV MALLOC_ARENA_MAX=2
```

In code, bound what libvips holds and how much it does in parallel:

```js
import sharp from 'sharp';
sharp.cache(false);      // or a small bound, e.g. sharp.cache({ memory: 50 })
sharp.concurrency(1);    // per-image libvips threads; request-level parallelism still applies
```

Also cap request-level concurrency on `/thumb` (a simple semaphore or `p-limit`, e.g. 4 in flight). 20 concurrent decodes of 24 MP JPEGs cost roughly 20 × ~70 MB of pixel buffers at peak, which adds to the fragmentation. Use `sharp(input, { limitInputPixels: ... })` so one huge upload can't blow the budget.

While you're in that code, check for error paths that leave pipelines half-consumed: sharp streams piped into `res` without `pipeline()` error handling, or `.toBuffer()` promises whose rejection is swallowed.

### 4. Reproduce locally and A/B the fixes (1.5 hours)
This is where you get proof instead of guesses:

```bash
docker run --rm -m 2g -p 3000:3000 your-image
# second terminal: realistic JPEGs, realistic key spread
npx autocannon -c 20 -d 1200 'http://localhost:3000/thumb?...'
docker stats   # watch the MEM USAGE slope
```

Run about 20 minutes per variant and compare the RSS slopes:
1. baseline
2. cache disabled (tells you how much is the cache vs everything else)
3. baseline + jemalloc
4. byte-capped cache + jemalloc + `sharp.cache(false)`

Change one variable per run. If variant 2 is flat, it's the cache. If variant 2 still climbs and variant 3 flattens it, it's allocator fragmentation.

### 5. Node 18 → 20: last, and only if 2–4 don't explain it
With `heapUsed` flat, a V8 change is unlikely to be the cause. The only cheap check is to rerun the step-4 baseline on a `node:18-bookworm-slim` image. If the slope matches, rule it out. I wouldn't spend more than 20 minutes here.

### 6. Hand over (30 min)
- Ship the byte-capped cache and jemalloc (or `MALLOC_ARENA_MAX=2`) if the repro supports them.
- Leave the new panels in place: `rss`, `external`, `arrayBuffers`, cache bytes. On-call can then tell "cache full" apart from "native growth" at a glance.
- Alert at about 80% of the container limit (container working set, not `heapUsed`) so on-call hears about a restart before the OOMKill does it.
- Write down what's still open: which A/B variant fixed it, and what to do if RSS still climbs (a rolling restart is an acceptable stopgap, not a fix).
