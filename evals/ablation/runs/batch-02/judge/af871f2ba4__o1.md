## Блокеры (чинить сегодня)

### 1. SQL injection в `/api/orders`
- **Severity:** Critical
- **Vector:** `user_id` и `status` подставляются в SQL через f-string. `status=x' OR '1'='1` отдаёт все заказы. `user_id=1 UNION SELECT ...` читает любые таблицы, включая пользователей и хэши. `user_id` вставлен без кавычек, так что инъекция работает даже без экранирования. В Postgres риск выше, чем в тестах на SQLite: `sqlite3` не выполняет несколько statements в одном `execute`, а драйверы Postgres в ряде режимов выполняют, и тогда возможны stacked queries (`; UPDATE ...`). Поведение зависит от драйвера и режима, это я помню, а не проверял. Тесты на SQLite могут не показать худший случай.
- **Mitigation:** параметризация плюс валидация типов.
  ```python
  ALLOWED_STATUSES = {"new", "paid", "shipped", "cancelled"}

  status = request.args.get("status", "new")
  if status not in ALLOWED_STATUSES:
      abort(400)
  rows = db.execute(
      text("SELECT id, status, total, created_at FROM orders "
           "WHERE user_id = :uid AND status = :status"),
      {"uid": current_user_id, "status": status},
  ).fetchall()
  ```
  Синтаксис плейсхолдеров зависит от того, что такое `db`. Если это SQLAlchemy, то `text()` и `:name`. У голого `sqlite3` это `?`, у psycopg `%s`. Раз один и тот же `db.execute` работает на обеих БД, скорее всего это SQLAlchemy, но проверьте.
- `[CONF: HIGH]`: классический CWE-89, видно прямо в коде.

### 2. IDOR: `user_id` берётся из query string
- **Severity:** Critical, если middleware не висит на роуте. High, если висит.
- **Vector:** даже с рабочей авторизацией любой залогиненный пользователь меняет `?user_id=` и читает чужие заказы. Если middleware на `/api/orders` не вешается, эндпоинт отдаёт заказы всех пользователей анонимно. Параметризация из п.1 это **не** закрывает.
- **Mitigation:** брать идентификатор из аутентифицированного контекста, а не от клиента:
  ```python
  current_user_id = g.user.id   # или что выставляет ваш middleware
  if current_user_id is None:
      abort(401)
  ```
  Сегодня же проверьте руками, что анонимный `curl https://.../api/orders?user_id=1` получает 401/403, а не 200. Это надёжнее, чем читать код middleware.
- `[CONF: HIGH]` на IDOR: следует из кода. `[CONF: LOW]` на то, покрыт ли роут авторизацией: middleware я не видел.

### 3. `SECRET_KEY` с дефолтом `"dev"`
- **Severity:** High (условно)
- **Vector:** если в проде переменная не выставлена, тихо используется `"dev"`. Flask подписывает session cookie этим ключом, значит любой может подделать сессию, например `user_id`/`is_admin` в `session`. Насколько это критично, зависит от того, хранит ли ваш auth что-то в Flask session.
- **Mitigation:** fail fast, без дефолта:
  ```python
  app.config["SECRET_KEY"] = os.environ["SECRET_KEY"]  # KeyError на старте, если не задан
  ```
  Если ключ уже задан в проде, изменение ничего не ломает. Если не задан, вы узнаете об этом на деплое, а не от атакующего.
- `[CONF: MEDIUM]`: уязвимость реальна только если env не задан в проде. Проверьте окружение.

## Rate limit на `/login`: сегодня только при ответе девопсов

- **Severity:** High
- **Vector:** `X-Forwarded-For` приходит от клиента. Атакующий ставит новое значение в каждом запросе и получает новый bucket, лимит 5/min не работает, брутфорс паролей открыт. Если nginx делает `proxy_add_x_forwarded_for`, он дописывает реальный IP к клиентскому значению. Строка всё равно уникальна на каждый запрос, так что обход сохраняется.
- **Почему нельзя просто заменить на `request.remote_addr`:** за nginx `remote_addr` равен IP nginx. Все пользователи попадут в один bucket, и 5 логинов в минуту на весь сервис превратятся в самодельный DoS в день релиза.
- **Mitigation (после ответа девопсов):**
  ```python
  from werkzeug.middleware.proxy_fix import ProxyFix
  app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1)  # x_for = число доверенных прокси перед приложением
  # и key_func=get_remote_address из flask_limiter.util
  ```
  В nginx нужно `proxy_set_header X-Forwarded-For $remote_addr;` (перезапись, не дописывание) или корректный `real_ip`. Значение `x_for` должно совпадать с реальным числом прокси. Если за nginx стоит ещё LB/CDN, будет 2.
- **Решение:** если девопсы до вечера подтверждают топологию, чиним сегодня. Если нет, в бэклог с P1 и дедлайном. Слепой фикс опаснее текущего бага.
- `[CONF: HIGH]` на спуфинг: заголовок полностью контролируется клиентом. `[CONF: MEDIUM]` на детали фикса: они зависят от невиденного nginx-конфига.

## 1. SQL injection. `[CONF: HIGH]`

- **Severity:** Critical
- **Vector:** в f-string попадают оба параметра. Через `user_id` инъекция идёт даже без кавычек: `?user_id=1 OR 1=1` отдаёт все заказы. Через `status` работает `' UNION SELECT ... --`, так можно вытащить любую таблицу, до которой есть права у DB-юзера (users, хэши паролей). В Postgres инъекция дополнительно открывает функции самой СУБД. Раз код один и тот же, тесты на SQLite ничего не доказывают.
- **Mitigation:** параметризованный запрос. **Синтаксис плейсхолдера зависит от того, что такое `db`**, и это ловушка именно вашего сетапа:
  - сырой `sqlite3` понимает `?`, а `psycopg2`/`psycopg` понимают `%s`. Фикс с `?` пройдёт тесты на SQLite и упадёт в проде на Postgres, или наоборот;
  - если `db` это SQLAlchemy (`db.session` / `engine.connect()`), используйте `text()` с `:name`, он одинаково работает на обоих бэкендах.

```python
from sqlalchemy import text

ALLOWED_STATUSES = {"new", "paid", "shipped", "cancelled"}  # подставьте реальные

@app.route("/api/orders")
def orders():
    user_id = current_user_id()          # см. п.2 — НЕ из request.args
    status = request.args.get("status", "new")
    if status not in ALLOWED_STATUSES:
        abort(400)
    rows = db.execute(
        text("SELECT id, status, total, created_at FROM orders "
             "WHERE user_id = :uid AND status = :status LIMIT 100"),
        {"uid": user_id, "status": status},
    ).mappings().all()
    return jsonify([dict(r) for r in rows])
```

`text()` / `.mappings()` относятся к SQLAlchemy (API 1.4/2.0, по памяти, сверьте с вашей версией). Если `db` окажется обёрткой над сырым драйвером, оставьте ту же логику и поменяйте стиль плейсхолдеров. **Обязательно прогоните фикс на Postgres (staging/контейнер), а не только на SQLite.**

## 2. IDOR / Broken Access Control. `[CONF: HIGH]` по коду, `[CONF: MEDIUM]` по реальному эффекту

- **Severity:** Critical, если middleware на `/api/orders` не висит: тогда любой анонимный пользователь перебирает `user_id=1..N` и выгружает все заказы. High, если middleware висит: аутентифицированный пользователь всё равно читает чужие заказы, потому что `user_id` приходит от клиента, а не из сессии или токена.
- **Vector:** `GET /api/orders?user_id=<чужой id>`.
- **Mitigation:** брать идентичность только из контекста аутентификации (`g.user`, `flask_login.current_user`, claims из JWT, смотря что ставит ваш middleware), параметр `user_id` игнорировать. Если middleware не гарантирован, добавьте явный декоратор на роут: defense in depth, fail closed.

```python
def current_user_id() -> int:
    uid = getattr(g, "user_id", None)    # то, что кладёт ваш middleware
    if uid is None:
        abort(401)
    return uid
```

Если админам действительно нужно смотреть чужие заказы, сделайте для этого отдельный роут с проверкой роли, а не этот.

**Сегодня проверить:** где и как регистрируется middleware (`before_request`, WSGI-обёртка, allowlist/denylist путей). Самый надёжный тест: `curl` без токена на `/api/orders?user_id=1` в staging.

## 3. `SECRET_KEY = os.getenv("SECRET_KEY", "dev")`. `[CONF: HIGH]`

- **Severity:** High, если переменная в проде не задана. Если задана, риска нет, но fallback всё равно мина на будущее.
- **Vector:** Flask подписывает session cookie этим ключом. Если ключ `"dev"`, атакующий подделывает cookie с любым `user_id`/ролью. Если auth-middleware опирается на Flask session, это полный обход авторизации. Подписанные токены (reset password, CSRF) тоже становятся подделываемыми.
- **Mitigation:** fail fast при старте:

```python
app.config["SECRET_KEY"] = os.environ["SECRET_KEY"]  # KeyError при старте — это фича
```

Для тестов задайте ключ в конфиге или фикстуре. Перед релизом убедитесь, что переменная есть в прод-окружении, иначе приложение не поднимется. Узнать это лучше сегодня, чем завтра на деплое.

## 4. Rate limit по `X-Forwarded-For`. `[CONF: HIGH]` по коду, `[CONF: MEDIUM]` по эксплуатабельности (зависит от nginx)

- **Severity:** Medium–High. На `/login` это, вероятно, единственная защита от brute force.
- **Vector:** заголовок контролирует клиент. Ключом служит **вся строка** заголовка, поэтому:
  1. атакующий шлёт каждый запрос с новым `X-Forwarded-For: <random>`, получает новый bucket и перебирает пароли без лимита;
  2. если nginx настроен как `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` (распространённый вариант), он **дописывает** реальный IP к клиентскому значению, и строка всё равно уникальна для каждого запроса. Обход работает. Защищает только вариант, где nginx перезаписывает заголовок через `$remote_addr`, а этого вы не знаете;
  3. если приложение доступно напрямую в обход nginx (открытый порт gunicorn, внутренняя сеть), заголовок полностью ваш;
  4. можно подставить IP жертвы и выжечь её лимит (мелкий DoS).
- **Mitigation:** доверять только тому hop'у, который добавил ваш nginx:

```python
from werkzeug.middleware.proxy_fix import ProxyFix
from flask_limiter.util import get_remote_address

app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1)   # 1 = ровно один доверенный прокси
...
@limiter.limit("5/minute", key_func=get_remote_address)
```

`x_for=1` подходит только если между клиентом и Flask ровно один прокси. Если перед nginx есть ещё LB или CDN, значение другое, и неверное число либо оставит обход, либо сведёт всех клиентов к IP балансировщика (все делят один лимит, и логин ляжет для всех). **Это вопрос к девопсам сегодня.** Если ответа нет, лучше отложить этот фикс на день после релиза, чем выкатить `ProxyFix` вслепую.

Бэклог к этому пункту: добавить лимит **по username/аккаунту** в дополнение к IP. Лимит только по IP не защищает от распределённого перебора.

## 5. `SELECT *` + `dict(r)`. `[CONF: MEDIUM]`

- **Severity:** Medium.
- **Vector:** клиенту уходят все колонки, включая внутренние (`internal_note`, платёжные токены, адреса), и те, что добавят в таблицу потом.
- **Mitigation:** явный список колонок, он уже есть в примере выше. Если в `orders` сейчас есть чувствительные поля, фикс переезжает в сегодняшний список. Заодно проверьте, что `dict(r)` работает с row-объектом прод-драйвера: для `sqlite3.Row` и для курсора psycopg поведение разное.

## 6. Валидация и пагинация. `[CONF: MEDIUM]`

- `user_id=None` превращается в `WHERE user_id = None`, это SQL error и 500. Если в проде `DEBUG=True`, отдаётся стектрейс. Проверьте, что debug выключен.
- Нет `LIMIT`/пагинации: один запрос выгружает всю историю, это нагрузка и DoS. В бэклог, но `LIMIT` в фиксе п.1 стоит поставить сразу.

## Red team по предлагаемым фиксам

1. **Параметризация:** может остаться второй роут с тем же f-string паттерном. Прогрепайте `execute(f"` и `.format(` по всему бэкенду, а не только по этому файлу.
2. **Параметризация:** фикс сделан под SQLite-плейсхолдеры и сломает прод. Защита: прогон на Postgres до мержа.
3. **IDOR:** middleware может класть `g.user` не на всех путях (например, прописан prefix `/api/v1`, а роут висит на `/api/orders`). Тогда `current_user_id()` отдаст 401 легитимным пользователям. Это безопасный отказ, но usability-регрессия; проверьте в staging.
4. **ProxyFix:** неверный `x_for` откроет обход заново или склеит всех в один IP (п.4).

Побочные эффекты по производительности пренебрежимы. Единственный usability-риск: `SECRET_KEY` без fallback, приложение не поднимется, если переменная не задана.
