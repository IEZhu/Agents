## Блокеры (чинить сегодня)

### 1. SQL injection в `/api/orders`
- **Severity:** Critical
- **Vector:** `user_id` и `status` подставляются в SQL через f-string. `status=x' OR '1'='1` отдаёт все заказы. `user_id=1 UNION SELECT ...` читает любые таблицы, включая пользователей и хэши. `user_id` вставлен без кавычек, так что инъекция работает даже без экранирования. В Postgres риск выше, чем в тестах на SQLite: `sqlite3` не выполняет несколько statements в одном `execute`, а драйверы Postgres в ряде режимов выполняют, и тогда возможны stacked queries (`; UPDATE ...`). Поведение зависит от драйвера и режима, это я помню, а не проверял. Тесты на SQLite могут не показать худший случай.
- **Mitigation:** параметризация плюс валидация типов.
  ```python
  ALLOWED_STATUSES = {"new", "paid", "shipped", "cancelled"}

  status = request.args.get("status", "new")
  if status not in ALLOWED_STATUSES:
      abort(400)
  rows = db.execute(
      text("SELECT id, status, total, created_at FROM orders "
           "WHERE user_id = :uid AND status = :status"),
      {"uid": current_user_id, "status": status},
  ).fetchall()
  ```
  Синтаксис плейсхолдеров зависит от того, что такое `db`. Если это SQLAlchemy, то `text()` и `:name`. У голого `sqlite3` это `?`, у psycopg `%s`. Раз один и тот же `db.execute` работает на обеих БД, скорее всего это SQLAlchemy, но проверьте.
- `[CONF: HIGH]`: классический CWE-89, видно прямо в коде.

### 2. IDOR: `user_id` берётся из query string
- **Severity:** Critical, если middleware не висит на роуте. High, если висит.
- **Vector:** даже с рабочей авторизацией любой залогиненный пользователь меняет `?user_id=` и читает чужие заказы. Если middleware на `/api/orders` не вешается, эндпоинт отдаёт заказы всех пользователей анонимно. Параметризация из п.1 это **не** закрывает.
- **Mitigation:** брать идентификатор из аутентифицированного контекста, а не от клиента:
  ```python
  current_user_id = g.user.id   # или что выставляет ваш middleware
  if current_user_id is None:
      abort(401)
  ```
  Сегодня же проверьте руками, что анонимный `curl https://.../api/orders?user_id=1` получает 401/403, а не 200. Это надёжнее, чем читать код middleware.
- `[CONF: HIGH]` на IDOR: следует из кода. `[CONF: LOW]` на то, покрыт ли роут авторизацией: middleware я не видел.

### 3. `SECRET_KEY` с дефолтом `"dev"`
- **Severity:** High (условно)
- **Vector:** если в проде переменная не выставлена, тихо используется `"dev"`. Flask подписывает session cookie этим ключом, значит любой может подделать сессию, например `user_id`/`is_admin` в `session`. Насколько это критично, зависит от того, хранит ли ваш auth что-то в Flask session.
- **Mitigation:** fail fast, без дефолта:
  ```python
  app.config["SECRET_KEY"] = os.environ["SECRET_KEY"]  # KeyError на старте, если не задан
  ```
  Если ключ уже задан в проде, изменение ничего не ломает. Если не задан, вы узнаете об этом на деплое, а не от атакующего.
- `[CONF: MEDIUM]`: уязвимость реальна только если env не задан в проде. Проверьте окружение.

## Rate limit на `/login`: сегодня только при ответе девопсов

- **Severity:** High
- **Vector:** `X-Forwarded-For` приходит от клиента. Атакующий ставит новое значение в каждом запросе и получает новый bucket, лимит 5/min не работает, брутфорс паролей открыт. Если nginx делает `proxy_add_x_forwarded_for`, он дописывает реальный IP к клиентскому значению. Строка всё равно уникальна на каждый запрос, так что обход сохраняется.
- **Почему нельзя просто заменить на `request.remote_addr`:** за nginx `remote_addr` равен IP nginx. Все пользователи попадут в один bucket, и 5 логинов в минуту на весь сервис превратятся в самодельный DoS в день релиза.
- **Mitigation (после ответа девопсов):**
  ```python
  from werkzeug.middleware.proxy_fix import ProxyFix
  app.wsgi_app = ProxyFix(app.wsgi_app, x_for=1)  # x_for = число доверенных прокси перед приложением
  # и key_func=get_remote_address из flask_limiter.util
  ```
  В nginx нужно `proxy_set_header X-Forwarded-For $remote_addr;` (перезапись, не дописывание) или корректный `real_ip`. Значение `x_for` должно совпадать с реальным числом прокси. Если за nginx стоит ещё LB/CDN, будет 2.
- **Решение:** если девопсы до вечера подтверждают топологию, чиним сегодня. Если нет, в бэклог с P1 и дедлайном. Слепой фикс опаснее текущего бага.
- `[CONF: HIGH]` на спуфинг: заголовок полностью контролируется клиентом. `[CONF: MEDIUM]` на детали фикса: они зависят от невиденного nginx-конфига.

## Red team по предложенным фиксам

1. **Параметризация без п.2.** Инъекция закрыта, но данные всё равно утекают через подмену `user_id`. Нужны оба фикса вместе.
2. **ProxyFix с неверным `x_for`.** Если прокси больше, чем указано, ключом станет IP промежуточного прокси (общий bucket). Если меньше, клиент снова спуфит заголовок.
3. **`g.user.id` при непокрытом middleware.** Если middleware не отработал, `g.user` не существует, получится 500 вместо 401, либо, хуже, где-то останется fallback на query param. Нужна явная проверка и тест «аноним получает 401».

Побочные эффекты: whitelist статусов сломает клиентов, которые шлют неизвестные статусы (400 вместо пустого списка). Сверьтесь с фронтом.
