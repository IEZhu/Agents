**Short answer:** skip heap snapshots and the Node 18→20 upgrade for now. A flat `heapUsed` with RSS climbing means the memory is **outside the V8 JS heap**. That leaves two suspects, both from the new `/thumb` work: (1) the Buffers in your LRU cache, which is capped by entry count and not by bytes, and (2) native memory from sharp/libvips, made worse by glibc malloc fragmentation. Spend the half day separating those two, put a mitigation in place, and hand over with the right metrics on the dashboard.

## Why heapUsed is misleading here

Buffer contents live off the V8 heap. They show up in `process.memoryUsage().external` / `.arrayBuffers`, not in `heapUsed`. libvips allocations (decode buffers, its operation cache, thread pools) don't appear in any `memoryUsage()` field except `rss`. So your Grafana panel can't see either suspect.

## Suggested order (~4 hours)

### 1. Instrument first (30 min)
Add these to the metrics you already export:

```js
setInterval(() => {
  const m = process.memoryUsage();
  metrics.gauge('mem_rss', m.rss);
  metrics.gauge('mem_heap_used', m.heapUsed);
  metrics.gauge('mem_external', m.external);
  metrics.gauge('mem_array_buffers', m.arrayBuffers);
  metrics.gauge('thumb_cache_entries', thumbCache.size);
  metrics.gauge('thumb_cache_bytes', thumbCache.calculatedSize ?? 0); // once sizeCalculation exists (step 2)
}, 15_000).unref();
```

After deploy, the curves answer the main question within an hour or two of traffic:
- **`arrayBuffers` climbs along with RSS** → it's the cache (or some other Buffer retention). Go to step 2.
- **`arrayBuffers` stays flat and RSS keeps climbing** → it's native memory (sharp/libvips/malloc). Go to step 3.

While you wait, set up the local repro in step 4 so it's ready.

### 2. Cap the cache by bytes (30 min). Do this whatever the metrics show.
`max: 5000` limits entry count, not memory. Rough math: 5000 thumbnails × 100–300 KB each is roughly **0.5–1.5 GB** of Buffers. That alone fits "300 MB → 1.9 GB over a few hours". Two things make it worse:
- If the key is the raw URL, query-string variants (`?w=200` vs `?w=201`, cache-busters, signed URLs) create many near-duplicate entries, so the cache fills faster than you'd expect.
- If any cached value is a *slice* of a larger Buffer (for example the original upload from multer `memoryStorage`), the whole parent buffer stays in memory. Values straight from sharp's `toBuffer()` should be standalone, but check that nothing else ends up in the cache.

lru-cache v10 supports byte-based limits:

```js
import { LRUCache } from 'lru-cache';

const THUMB_CACHE_MAX_BYTES = 256 * 1024 * 1024; // budget explicitly against the 2Gi limit

const thumbCache = new LRUCache({
  maxSize: THUMB_CACHE_MAX_BYTES,
  sizeCalculation: (buf) => buf.byteLength,
  maxEntrySize: 2 * 1024 * 1024, // don't let one oversized result evict everything
  ttl: 60 * 60 * 1000,           // optional, keeps the cache from pinning cold entries forever
});
```

Also normalize the cache key: strip parameters that don't affect the output and use a canonical `(sourceId, width, height, format)` tuple. `maxSize`/`sizeCalculation`/`maxEntrySize` are the documented v10 options as I remember them. Check them against the README of the version in your lockfile.

If RSS now **plateaus** around baseline + cache budget, you've found the problem.

### 3. Native memory: sharp + glibc (1 hour)
`node:20-bookworm-slim` is glibc-based. glibc malloc handles libvips' pattern of many large, short-lived allocations across threads badly: freed memory gets fragmented across per-thread arenas and doesn't go back to the OS, so RSS keeps rising while nothing is actually leaking. sharp's docs cover this and recommend jemalloc on glibc Linux (recalled, not verified here; see the "memory allocator" section of the sharp install docs). Things to try, cheapest first:

```dockerfile
# Option A: jemalloc (usually the most effective)
RUN apt-get update && apt-get install -y --no-install-recommends libjemalloc2 \
    && rm -rf /var/lib/apt/lists/*
ENV LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2
# path is arch-specific: aarch64-linux-gnu on ARM nodes. Verify with `dpkg -L libjemalloc2`

# Option B: no new package, limit glibc arenas
ENV MALLOC_ARENA_MAX=2
```

In code, bound what libvips holds and how much it does in parallel:

```js
import sharp from 'sharp';
sharp.cache(false);      // or a small bound, e.g. sharp.cache({ memory: 50 })
sharp.concurrency(1);    // per-image libvips threads; request-level parallelism still applies
```

Also cap request-level concurrency on `/thumb` (a simple semaphore or `p-limit`, e.g. 4 in flight). 20 concurrent decodes of 24 MP JPEGs cost roughly 20 × ~70 MB of pixel buffers at peak, which adds to the fragmentation. Use `sharp(input, { limitInputPixels: ... })` so one huge upload can't blow the budget.

While you're in that code, check for error paths that leave pipelines half-consumed: sharp streams piped into `res` without `pipeline()` error handling, or `.toBuffer()` promises whose rejection is swallowed.

### 4. Reproduce locally and A/B the fixes (1.5 hours)
This is where you get proof instead of guesses:

```bash
docker run --rm -m 2g -p 3000:3000 your-image
# second terminal: realistic JPEGs, realistic key spread
npx autocannon -c 20 -d 1200 'http://localhost:3000/thumb?...'
docker stats   # watch the MEM USAGE slope
```

Run about 20 minutes per variant and compare the RSS slopes:
1. baseline
2. cache disabled (tells you how much is the cache vs everything else)
3. baseline + jemalloc
4. byte-capped cache + jemalloc + `sharp.cache(false)`

Change one variable per run. If variant 2 is flat, it's the cache. If variant 2 still climbs and variant 3 flattens it, it's allocator fragmentation.

### 5. Node 18 → 20: last, and only if 2–4 don't explain it
With `heapUsed` flat, a V8 change is unlikely to be the cause. The only cheap check is to rerun the step-4 baseline on a `node:18-bookworm-slim` image. If the slope matches, rule it out. I wouldn't spend more than 20 minutes here.

### 6. Hand over (30 min)
- Ship the byte-capped cache and jemalloc (or `MALLOC_ARENA_MAX=2`) if the repro supports them.
- Leave the new panels in place: `rss`, `external`, `arrayBuffers`, cache bytes. On-call can then tell "cache full" apart from "native growth" at a glance.
- Alert at about 80% of the container limit (container working set, not `heapUsed`) so on-call hears about a restart before the OOMKill does it.
- Write down what's still open: which A/B variant fixed it, and what to do if RSS still climbs (a rolling restart is an acceptable stopgap, not a fix).

## Summary of priorities
| Order | Hypothesis | Likelihood | Cost to test |
|---|---|---|---|
| 1 | LRU cache unbounded in bytes (`max: 5000` Buffers) | High | Very low |
| 2 | glibc fragmentation from sharp/libvips | High (often together with #1) | Low |
| 3 | sharp pipeline/stream error-path retention | Medium | Medium |
| 4 | Node 20 runtime change | Low (heap is flat) | Low |

Overall confidence: fairly high that the cause is one or both of the first two. I can't tell you which until the `arrayBuffers` metric or the cache-disabled A/B run separates them, and that's why they come first.
