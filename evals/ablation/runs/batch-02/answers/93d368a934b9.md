**Short answer:** The memory is growing off the V8 heap, and your heap metric can't see it. That leaves two main suspects: (1) the lru-cache, which limits the number of entries but not their total size, and (2) sharp/libvips native memory combined with glibc malloc fragmentation. Spend the first hour finding out which one it is. The Node 18 → 20 upgrade is the least likely cause, so check it last.

`heapUsed` staying flat while RSS climbs tells you a lot. A Buffer's backing store is allocated outside the JS heap, so neither 5,000 cached thumbnails nor libvips pixel buffers would ever show up in `heapUsed`. That means your dashboard currently can't tell you anything about either suspect.

## Plan for the half day

### 1. Instrument so you can tell the suspects apart (~45 min)

Export these next to `rss` and `heapUsed`:

- `process.memoryUsage().external` and `.arrayBuffers`: Buffer memory, which includes your cache.
- `cache.size` and the total byte size of the cached values.
- In-flight `/thumb` requests (a gauge).

Also do a quick calculation: **average thumbnail size × 5000**. If the thumbnails average around 300 KB, a full cache is about 1.5 GB, which by itself accounts for most of the growth you're seeing. If they're around 30 KB, the cache tops out near 150 MB and is not your main problem.

How to read the result:

| What you see | Likely cause |
|---|---|
| `arrayBuffers` rises in step with RSS, and cache bytes rise with it | The cache (step 2) |
| `arrayBuffers` stays flat or bounded, but `rss − (heapTotal + external)` keeps growing | Native memory or allocator fragmentation (step 3) |
| Both grow | Both. Fix the cache first because it's cheap |

### 2. Limit the cache by bytes, not entries (~30 min; do it whatever step 1 shows)

`max: 5000` puts no limit on memory. Switch to a byte budget:

```js
import { LRUCache } from 'lru-cache';

const THUMB_CACHE_BYTES = 256 * 1024 * 1024;   // pick a budget that fits the 2Gi pod
const THUMB_MAX_ENTRY_BYTES = 2 * 1024 * 1024;

const thumbCache = new LRUCache({
  maxSize: THUMB_CACHE_BYTES,
  maxEntrySize: THUMB_MAX_ENTRY_BYTES,
  sizeCalculation: (buf) => buf.length,
});
```

I'm working from memory on `maxSize`, `maxEntrySize` and `sizeCalculation` in v10, so check them against the lru-cache README for your installed version. If you use `maxSize`, `sizeCalculation` is required, or you must pass `size` on every `set()`.

Two more things to check:

- Make sure you cache what `sharp().toBuffer()` returns, and not a `subarray()` or slice of some larger buffer. A slice keeps its whole parent buffer alive.
- Put the cache behind an env flag (`THUMB_CACHE_ENABLED=false`). That gives on-call a way to turn it off.

It's also worth asking whether this cache should be in the process at all. With several pods, each one keeps its own copy. `Cache-Control` headers plus a CDN or nginx cache in front would probably work better. That's a question for later, not for today.

### 3. Rule out sharp/libvips and the allocator (~1.5 h)

On glibc-based images such as `bookworm-slim`, libvips' many threads and short-lived allocations are known to fragment glibc malloc. RSS then keeps rising even though nothing is leaking. sharp's own docs recommend jemalloc on glibc Linux for this reason. Try these **one at a time**:

1. **jemalloc** (usually the fix that makes the biggest difference):
   ```dockerfile
   RUN apt-get update && apt-get install -y --no-install-recommends libjemalloc2 \
       && rm -rf /var/lib/apt/lists/*
   ENV LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2
   ```
   The path depends on the architecture (on arm64 it's `aarch64-linux-gnu`). Confirm it with `dpkg -L libjemalloc2`.
2. **Or `MALLOC_ARENA_MAX=2`**: less effective than jemalloc, but it's only an env var.
3. **Tune sharp**: `sharp.concurrency(1)` if the pod has few CPUs, and `sharp.cache(false)` or a small `sharp.cache({ memory: … })`. I believe libvips' operation cache defaults to about 50 MB, but that's from memory, so check the sharp docs.
4. **Reduce what gets decoded**: set `limitInputPixels`, enforce an upload size limit, and use `sharp(input).resize(...)` directly. JPEG shrink-on-load only helps if the resize is part of the same pipeline.

### 4. Reproduce locally and compare fixes (~1.5 h, alongside step 3)

Run the image with `docker run --memory=2g`. Send `/thumb` requests with **unique URLs** so the cache keeps filling, for example with `autocannon` or `k6`. Plot RSS against `arrayBuffers` for 20–30 minutes, once per variant: baseline, byte-limited cache, cache disabled, jemalloc. The steady climb should make the difference visible well before 6 hours.

### 5. Read through the `/thumb` code (~30 min)

Look for:

- **Unlimited concurrency.** If nothing caps in-flight sharp jobs, a burst means N full-size decoded images in memory at once. Add a semaphore such as `p-limit` sized to the CPU count.
- **Uploads held in memory**, for example `multer.memoryStorage()` with no `limits.fileSize`.
- **Streams not destroyed** when a request is aborted or errors. Use `stream.pipeline`, not `.pipe()`.

### 6. Node 18 → 20 (only if nothing above explains it)

Your symptoms point to off-heap memory, and the upgrade mostly affects the V8 heap, so this is probably not the cause. If you still have unexplained growth after steps 2–3, run the same build on `node:18-bookworm-slim` in the local repro. Don't roll back production for this.

### 7. Handover (last 30 min)

- Ship the cache byte limit and jemalloc (or at least the flag to disable the cache) before you hand over.
- Leave on-call the Grafana panel (`rss`, `heapUsed`, `external`, `arrayBuffers`, cache bytes), the env flags, and your notes on which suspect you confirmed.
- Set up an alert at about 80% of the memory limit so a restart happens in a controlled way instead of an OOMKill. That doesn't fix anything, but it protects users while the root cause is confirmed. Don't bother with `--max-old-space-size`: the heap isn't what's growing.
