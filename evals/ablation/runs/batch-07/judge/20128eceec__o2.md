## 1. Почему агент крутится по 40 итераций

Посмотрите, что получает модель, когда `search_logs` падает по таймауту:

```python
except Exception:
    log.exception("tool failed")   # причина остаётся в ваших логах
    return None                     # модель видит content = "null"
```

`json.dumps(None)` даёт строку `"null"`. Для модели это выглядит так: «вызвала поиск, получила пустоту». Она не может отличить это от «ничего не найдено» или от сбоя сети, и не знает, что причина в слишком большом диапазоне. Повторить тот же запрос в такой ситуации вполне разумно, и она повторяет его, пока не упрётся в контекст или деньги. Всю информацию об ошибке (`TimeoutError`) вы записали в свой лог, а модели ничего не передали.

К этому добавляются ещё две вещи:
- **Нет ограничителей.** `while True` без лимита шагов, бюджета и детекции повторов. Любой сбой в инструменте превращается в бесконечный цикл за ваш счёт.
- **Сам инструмент нельзя вызвать удачно.** Если поиск по суткам логов стабильно не укладывается в таймаут, модель физически не может получить результат. Инструмент должен принудительно ограничивать объём: обязательное окно времени, фильтры, `limit`, режим агрегации.

## 2. Почему тикет получается с выдуманной причиной

Когда `search_logs` и `create_ticket` приходят в одном ответе, аргументы для тикета модель написала **до того**, как увидела хоть один результат поиска. Выдумывать ей там больше нечего. Параллельный tool calling рассчитан на независимые вызовы, а здесь между ними жёсткая зависимость по данным. Инструкцией в промпте («сначала поищи») это снижается, но не гарантируется. Гарантию даёт только код: действие с побочным эффектом не должно выполняться, пока нет доказательств, полученных на **предыдущем** шаге.

## Как переписать

Идея такая: агент — это небольшой конечный автомат с двумя фазами (расследование и действие), и переход между ними проверяет код, а не модель.

```python
import json
from collections import Counter

MAX_STEPS = 15
MAX_COST_USD = 0.50
MAX_SAME_CALL = 2
SIDE_EFFECT_TOOLS = {"create_ticket"}


class ToolError(Exception):
    """Ошибка, которую стоит показать модели: что случилось и что делать дальше."""
    def __init__(self, code, message, hint=None):
        super().__init__(message)
        self.code, self.message, self.hint = code, message, hint


def err(code, message, hint=None):
    return {"ok": False, "error": code, "message": message, "hint": hint}


def run_tool(name, raw_args):
    try:
        args = json.loads(raw_args or "{}")
    except json.JSONDecodeError as e:
        return err("invalid_json", f"Arguments are not valid JSON: {e}")

    fn = TOOLS_IMPL.get(name)
    if fn is None:
        return err("unknown_tool", f"No tool named {name!r}.")

    try:
        return {"ok": True, "result": fn(**args)}
    except ToolError as e:
        return err(e.code, e.message, e.hint)
    except TypeError as e:  # неверные/лишние аргументы
        return err("bad_arguments", str(e))
    except Exception as e:
        log.exception("tool %s failed", name)
        return err(type(e).__name__, str(e)[:500])


def canonical(raw_args):
    try:
        return json.dumps(json.loads(raw_args or "{}"), sort_keys=True)
    except json.JSONDecodeError:
        return raw_args


def agent(task):
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": task}]
    call_counts = Counter()
    evidence = []          # успешные непустые результаты search_logs
    cost = 0.0

    for step in range(MAX_STEPS):
        # Фаза определяется кодом: до появления доказательств create_ticket модели просто не показывается.
        tools = TOOLS_ALL if evidence else TOOLS_INVESTIGATE
        resp = llm(messages, tools=tools, parallel_tool_calls=False)
        cost += resp.cost
        messages.append(resp.message)

        if not resp.tool_calls:
            return resp.content

        # Снимок до выполнения батча: доказательства из ЭТОГО же ответа не считаются.
        had_evidence = bool(evidence)

        for tc in resp.tool_calls:
            key = (tc.name, canonical(tc.arguments))
            call_counts[key] += 1

            if call_counts[key] > MAX_SAME_CALL:
                out = err("duplicate_call",
                          f"Identical {tc.name} call made {call_counts[key]} times.",
                          "Change the arguments (narrower time window, extra filters) or stop and report what you know.")
            elif tc.name in SIDE_EFFECT_TOOLS and not had_evidence:
                out = err("precondition_failed",
                          f"{tc.name} requires evidence from a successful search_logs call in a PREVIOUS step.",
                          "Search the logs first, read the results, then create the ticket.")
            else:
                out = run_tool(tc.name, tc.arguments)
                if tc.name == "search_logs" and out["ok"] and out["result"].get("hits"):
                    evidence.append(out["result"])

            # Ответ на КАЖДЫЙ tool_call_id обязателен, даже если вызов отклонён.
            messages.append({"role": "tool", "tool_call_id": tc.id,
                             "content": json.dumps(out, ensure_ascii=False, default=str)})

        if cost > MAX_COST_USD:
            break

    # Бюджет исчерпан: последний вызов без инструментов, чтобы модель подвела итог.
    messages.append({"role": "user", "content":
                     "Budget exhausted. Do not call tools. Summarize what you found, "
                     "what is confirmed vs. unconfirmed, and what a human should check next."})
    return llm(messages, tools=None).content
```

Что здесь важно:

- **Ошибки возвращаются модели как данные**: код ошибки, сообщение и подсказка, что делать дальше. Подсказка — самая полезная часть: она превращает «повторить вслепую» в «сузить окно».
- **`had_evidence` снимается до выполнения батча.** Без этого, если модель всё же пришлёт оба вызова разом, `search_logs` выполнится первым, `evidence` заполнится, и `create_ticket` проскочит в том же шаге.
- **Двойная защита для `create_ticket`**: его нет в списке инструментов на фазе расследования, а если модель всё равно его вызовет (например, по памяти из истории), вызов отклонит проверка предусловия.
- **`parallel_tool_calls=False`** — так параметр называется в OpenAI API, у Anthropic есть аналог `tool_choice={"type": "auto", "disable_parallel_tool_use": True}` (оба имени по памяти, не проверял — сверьте с документацией вашего провайдера и версии SDK). Даже без этого флага guard выше закрывает проблему. Флаг лишь экономит лишние шаги.
- **Стоимость.** `resp.cost` — заглушка: посчитайте её из `usage` (input/output tokens × цена вашей модели).

## Починить сам `search_logs`

Без этого пункта остальное лечит симптомы: модель будет вежливо останавливаться, но причину так и не найдёт.

```python
def search_logs(query, since, until, status=None, service=None, limit=50, mode="lines"):
    if parse(until) - parse(since) > timedelta(hours=2):
        raise ToolError("range_too_large",
                        "Time window exceeds 2h.",
                        "Split into ≤2h windows, or use mode='aggregate' for an overview.")
    try:
        ...  # запрос с серверным таймаутом
    except TimeoutError:
        raise ToolError("timeout",
                        f"Search {since}..{until} timed out.",
                        "Do NOT repeat this query. Halve the window or add status/service filters.")
```

- **`since`/`until` сделайте обязательными** в JSON-схеме, а в описании инструмента напишите, какое окно разумно.
- **Добавьте `mode="aggregate"`**, который возвращает, например, число 500-ок по сервису/эндпоинту/часу. Для задачи «найди причину» это правильный первый шаг: дешёвый обзор, потом детализация по горячей точке.
- **`limit` применяйте внутри инструмента** и возвращайте `truncated: true`, `total: N`. Не обрезайте JSON-строку в цикле: получится невалидный JSON.
- **Каждая строка лога должна иметь `id`** — он понадобится для проверки ниже.

## Заземление тикета

Чтобы тикет не содержал выдуманную причину, одного «сначала поищи» мало. Сделайте в `create_ticket` обязательное поле `evidence_ids: list[str]` и в реализации проверяйте, что каждый id действительно встречался в результатах `search_logs` этого запуска (держите `set` увиденных id). Если нет — `ToolError("ungrounded", "...", "Cite log line ids returned by search_logs")`. Это дешёвая детерминированная проверка на галлюцинации, и работает она лучше любого промпта.

Если ошибка в тикете стоит дорого (тикет будит дежурного), добавьте подтверждение человеком: агент формирует черновик, а вы показываете его и создаёте тикет по «ок». Для первой версии я бы так и сделал, а автономное создание включил бы, когда накопится статистика, что черновики корректны.

## Проблема 1: 40+ одинаковых вызовов `search_logs`

Посмотрите, что на самом деле видит модель, когда `search_logs` падает по таймауту:

```python
except Exception:
    log.exception("tool failed")   # traceback уходит в ВАШ лог
    return None                    # а модели достаётся json.dumps(None) == "null"
```

В `content` приходит строка `"null"`. Для модели это выглядит как пустой результат без объяснений. Она не знает, что был таймаут, и не знает, что запрос надо сузить. Поэтому она логично повторяет тот же вызов, и так до бесконечности, потому что у цикла `while True` нет ни лимита итераций, ни лимита бюджета. Модель ведёт себя разумно, просто ей не хватает информации.

Итого три дефекта:
1. **Ошибка проглатывается.** Модель должна получить тип ошибки и подсказку, что делать дальше.
2. **Нет предохранителей:** лимита шагов и стоимости, детекта повторов.
3. **Сам инструмент не рассчитан на такой объём.** Поиск по логам за целые сутки без обязательного окна и `limit` будет таймаутить регулярно, как ни проси модель.

## Проблема 2: `search_logs` и `create_ticket` в одном ответе

Это parallel tool calling. Модель выдаёт оба вызова в одном ходе, поэтому на момент генерации аргументов `create_ticket` результатов поиска у неё ещё нет, и причину она придумывает. Ваш цикл послушно выполняет оба вызова.

Тут нужно два слоя защиты:
- **На уровне API** запретите параллельные вызовы. В OpenAI-совместимых API это `parallel_tool_calls=False`, в Anthropic `tool_choice={"type": "auto", "disable_parallel_tool_use": True}`. Названия параметров привожу по памяти, сверьте с документацией вашего провайдера.
- **На уровне кода** закрепите зависимость жёстко, промпта тут мало. `create_ticket` с побочным эффектом нельзя выполнять, пока в истории нет успешного результата поиска. Если модель всё же вызвала его раньше, верните ей ошибку. Лучше вообще не давать агенту создавать тикет напрямую: пусть он возвращает черновик, а создание подтверждает человек или отдельная валидация. Ошибка здесь обходится дорого (выдуманная причина в трекере), поэтому такой шаг должен проходить через человека.

## Как переписать

```python
import json, time, hashlib, logging

log = logging.getLogger("agent")

MAX_STEPS = 12
MAX_COST_USD = 0.50
MAX_SAME_CALL = 2          # сколько раз разрешаем идентичный вызов
MAX_TOOL_OUTPUT_CHARS = 8_000

SIDE_EFFECT_TOOLS = {"create_ticket"}
REQUIRES_EVIDENCE = {"create_ticket": "search_logs"}   # tool -> от чего зависит


class ToolError(Exception):
    """Ошибка, которую нужно показать модели с подсказкой."""
    def __init__(self, kind, message, hint=None):
        super().__init__(message)
        self.kind, self.message, self.hint = kind, message, hint


def tool_result(ok, **payload):
    return json.dumps({"ok": ok, **payload}, ensure_ascii=False, default=str)


def truncate(s, n=MAX_TOOL_OUTPUT_CHARS):
    return s if len(s) <= n else s[:n] + f"\n...[truncated {len(s) - n} chars]"


def call_key(name, args):
    return hashlib.sha256(f"{name}:{json.dumps(args, sort_keys=True)}".encode()).hexdigest()


def run_tool(tc, state):
    # 1. Аргументы: невалидный JSON тоже ошибка для модели, а не падение цикла
    try:
        args = json.loads(tc.arguments or "{}")
    except json.JSONDecodeError as e:
        return tool_result(False, error="bad_arguments", message=str(e),
                           hint="Верни аргументы валидным JSON по схеме инструмента.")

    if tc.name not in TOOLS_IMPL:
        return tool_result(False, error="unknown_tool", message=tc.name)

    # 2. Детект повторов
    key = call_key(tc.name, args)
    state["calls"][key] = state["calls"].get(key, 0) + 1
    if state["calls"][key] > MAX_SAME_CALL:
        return tool_result(False, error="repeated_call",
                           message="Этот вызов с этими аргументами уже выполнялся и не помог.",
                           hint="Измени аргументы (сузь окно времени, добавь фильтр) "
                                "или заверши задачу и честно опиши, что найти не удалось.")

    # 3. Зависимости: без доказательств тикет не создаём
    dep = REQUIRES_EVIDENCE.get(tc.name)
    if dep and not state["successful"].get(dep):
        return tool_result(False, error="precondition_failed",
                           message=f"{tc.name} требует успешного результата {dep}.",
                           hint=f"Сначала вызови {dep} и дождись результата.")

    # 4. Выполнение с типизированными ошибками
    try:
        out = TOOLS_IMPL[tc.name](**args)
    except TimeoutError:
        log.warning("tool timeout: %s %s", tc.name, args)
        return tool_result(False, error="timeout",
                           message=f"{tc.name} не уложился в таймаут.",
                           hint="Сузь запрос: окно не больше 1 часа, фильтр по status=500 "
                                "и сервису, limit<=100. Не повторяй тот же запрос.")
    except ToolError as e:
        return tool_result(False, error=e.kind, message=e.message, hint=e.hint)
    except TypeError as e:          # чаще всего неверные/лишние аргументы
        return tool_result(False, error="bad_arguments", message=str(e))
    except Exception as e:
        log.exception("tool failed: %s", tc.name)
        return tool_result(False, error="internal_error",
                           message=f"{type(e).__name__}: {e}",
                           hint="Инструмент недоступен. Не повторяй вызов больше одного раза.")

    state["successful"][tc.name] = True
    return truncate(tool_result(True, result=out))


def run_agent(messages):
    state = {"calls": {}, "successful": {}, "cost": 0.0}

    for step in range(MAX_STEPS):
        resp = llm(messages, tools=TOOLS, parallel_tool_calls=False)  # см. оговорку про имя параметра
        state["cost"] += resp.cost_usd          # считайте из usage * цена вашей модели
        messages.append(resp.message)

        if not resp.tool_calls:
            return resp.content

        # Страховка, если провайдер всё равно вернул несколько вызовов:
        # side-effect инструмент в одной пачке с другими не выполняем.
        batch_has_side_effect = any(tc.name in SIDE_EFFECT_TOOLS for tc in resp.tool_calls)
        mixed_batch = batch_has_side_effect and len(resp.tool_calls) > 1

        for tc in resp.tool_calls:
            if mixed_batch and tc.name in SIDE_EFFECT_TOOLS:
                content = tool_result(False, error="rejected",
                                      message="Инструмент с побочным эффектом нельзя вызывать "
                                              "вместе с другими. Дождись результатов поиска.")
            else:
                content = run_tool(tc, state)
            # На каждый tool_call обязательно должен быть ответ, иначе API вернёт ошибку
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": content})

        if state["cost"] > MAX_COST_USD:
            return f"[stopped] бюджет ${MAX_COST_USD} исчерпан на шаге {step + 1}"

    return f"[stopped] достигнут лимит {MAX_STEPS} шагов"
```

## Что поменять в самих инструментах

Это даст больше, чем любой промпт:

- **`search_logs`:** сделайте `start`/`end` обязательными и ограничьте окно (например, ≤1 ч), добавьте `status`, `service`, `limit` и курсор пагинации. Ещё лучше добавить агрегирующий инструмент вроде `count_errors(start, end, group_by="service|endpoint|exception")`. Тогда модель сначала увидит картину «где и когда 500-ки», а в сырые логи пойдёт уже прицельно. На сутках логов это, скорее всего, уберёт большую часть таймаутов.
- **Возвращайте сводку, а не сырые логи.** Топ исключений с количеством и 3–5 примерами стектрейсов. Иначе контекст раздувается, и каждая итерация дорожает.
- **`create_ticket`:** требуйте поле `evidence`, то есть ID лог-записей или цитаты. Проверяйте в коде, что эти ID действительно встречались в результатах поиска в этой сессии. Если нет, возвращайте `precondition_failed`. Это прямая защита от выдуманной причины.

## Промпт

Промпт вторичен, но пара строк помогает:

```
Порядок работы: 1) найди, где и когда были 500-ки; 2) найди причину в логах;
3) только после этого создай тикет, указав в evidence ID конкретных записей.
Если инструмент вернул ok=false — прочитай hint и измени запрос, не повторяй его.
Если причину найти не удалось — не создавай тикет, опиши, что проверено.
```

## Как проверить, что стало лучше

Соберите 10–20 прогонов на реальных днях логов, включая день, где `search_logs` гарантированно таймаутит. Сравните до и после по четырём метрикам: число шагов, стоимость прогона, доля тикетов, у которых `evidence` ссылается на реально найденные записи, доля честных отказов «не нашёл». Конкретных цифр улучшения обещать не буду. Но с лимитами в коде сценарий «40 итераций и $3» исключён конструктивно, и от поведения модели это не зависит.
