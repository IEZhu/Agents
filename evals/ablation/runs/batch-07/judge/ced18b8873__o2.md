## Latest user message
I own the system prompt for our customer support bot (GPT-4o class model, tools: get_order(order_id), get_customer(email), issue_refund(order_id, amount), escalate_to_human(reason)). Current instructions section is basically: "You are a helpful support agent. Use the tools to resolve customer issues quickly. Be concise."

Three failure modes from last week's transcript review:
- It tells customers "Your refund of $49.99 has been processed" in the same message where it calls issue_refund, before the result comes back. Twice the refund actually failed (order already refunded / amount exceeds order total) and the customer was never told.
- When the customer gives only an email, it sometimes calls get_order with a made-up order id instead of looking the customer up first.
- When get_order returns 404, it apologizes and ends the conversation.

Can you rewrite the instructions section to fix these? Keep it under ~250 words, it goes into the prompt as-is.

## Rubric (what a strong answer does)
1. The rewritten prompt forbids stating that a refund (or any action) succeeded until the tool result has been received, and requires telling the customer the actual outcome, including failure reasons.
2. It requires checking the order with get_order (e.g. existing refund status and order total) before calling issue_refund, and resolving a missing order id via get_customer by email rather than inventing one.
3. It gives a recovery path for tool errors, e.g. after a get_order 404 confirm the id with the customer, look up by email, or escalate_to_human, instead of ending the conversation.
4. The deliverable is a usable prompt section of roughly 250 words or fewer that uses only the four stated tools and keeps a concise support tone.

## Answer A
Here's a replacement you can paste in as-is. It's about 240 words.

```
You are a customer support agent. Resolve issues accurately using your tools. Be concise, but never at the cost of accuracy.

1. Never claim an outcome before you see the tool result.
   - When you call a tool, do not tell the customer what it did in that same turn. Wait for the result.
   - Before issue_refund, call get_order to check the order total and whether it has already been refunded.
   - Refund succeeded: confirm the amount and the order ID.
   - Refund failed: tell the customer plainly that it did not go through and why. Then fix the cause (for example, use a valid amount) or call escalate_to_human.

2. Only use order IDs that the customer gave you or that a tool returned. Never guess or invent one.
   - Email only: call get_customer(email) first and take order IDs from that result. If more than one order could match, ask which one.
   - No email and no order ID: ask the customer for one.

3. If get_order finds nothing, keep the conversation going.
   - Read back the ID you used and ask the customer to check it, or ask for the email on the order and look it up with get_customer.
   - Still not found: call escalate_to_human.

4. Call escalate_to_human when a tool fails for an unclear reason, when the request is beyond what your tools can do, or when the customer asks for a person. Tell the customer you've escalated and what happens next.

Never end a conversation while the issue is unresolved and hasn't been escalated.
```

**How each change maps to your failures:**
- **Premature refund confirmation:** rule 1 separates the tool call from the claim about its outcome, and it spells out what to say when a refund fails. The pre-check with get_order should stop both failures you saw (already refunded, amount above the order total) before they happen.
- **Made-up order IDs:** rule 2 limits which IDs the model may use and gives it a fixed lookup order.
- **Ending on a 404:** rule 3 gives it a recovery path, and the last line forbids ending the conversation with the issue still open.

**Caveats:**
- Rule 2 assumes get_customer returns the customer's orders or order IDs. If it doesn't, the model has no way to get from an email to an order, so you'd need a list-orders tool or should have it ask for the order ID instead.
- A prompt only makes failure 1 less likely. It can't rule it out. If a refund confirmation must never go out before the refund really happens, enforce it in your orchestration code. For example, drop or hold any customer-facing text in an assistant turn that also calls issue_refund, and only release a success message after the tool returns success.
- Test it before shipping. Replay last week's failing transcripts, and add cases for: email only, several orders, a refund amount above the order total, an order that was already refunded, and a 404 followed by a second 404. Check two things for each: whether any success message appears before a success result, and whether the model ever uses an order ID that didn't come from the customer or a tool.


## Answer B
Here's a replacement for the instructions section (~240 words):

```
You are a customer support agent. Resolve customer issues accurately using your tools. Be concise, but accuracy comes before speed.

## Tool rules

1. Never invent or guess IDs. Only pass an order_id that the customer gave you or that a tool returned.
   - Customer gave only an email: call get_customer(email) first, then use the order IDs it returns. If several orders match, ask which one.
   - Customer gave neither: ask for their order number or email.

2. Report an outcome only after you have the tool result. In a message where you call a tool, you may say "Let me check that", but never state or imply the result.
   After issue_refund returns:
   - Success: confirm the amount and the order.
   - Failure: tell the customer plainly that the refund did NOT go through and why (e.g., already refunded, amount exceeds order total). Don't retry with a different amount unless the customer agrees. If you can't fix it, use escalate_to_human.

3. A "not found" or error result does not end the conversation. If get_order returns 404:
   - Tell the customer you couldn't find that order and ask them to double-check the number.
   - Offer to look it up by email with get_customer.
   - If the second attempt also fails, call escalate_to_human with a short summary.

4. Call escalate_to_human when a tool fails twice for the same request, the customer asks for a person, or the request is outside what your tools can do. Tell the customer you've escalated.

Never end a conversation while the customer's issue is unresolved and not escalated.
```

**Why it's built this way**

- Each rule maps to one failure mode (1 = invented IDs, 2 = premature refund confirmation, 3 = 404 dead end). That lets you check each fix separately in transcripts.
- "Be concise" probably helped cause failure #1, because the model saves a turn by announcing the result along with the call. The prompt now says outright that accuracy comes first.
- Rule 2 gives the model something it's allowed to say ("Let me check that"). That tends to work better than a bare prohibition.

**Don't rely on the prompt alone for #1 and #2.** A prompt lowers the rate. It won't get it to zero. Two cheap guards in code:
- Validate order_id format and ownership server-side before get_order or issue_refund runs, so a made-up ID fails loudly.
- Make issue_refund return an explicit `{status: "failed", reason: ...}`. Consider blocking text output in the same turn as a refund call. If you use the OpenAI API, `parallel_tool_calls=false` may also help (recalled, not verified; check your SDK docs).

**Minimum regression set before shipping** (replay each several times):

| Case | Expected |
|---|---|
| Refund succeeds | Confirms only after the result |
| Refund fails: already refunded | Says it failed and why, no false confirmation |
| Refund fails: amount > total | Explains, offers the correct amount or escalates |
| Email only | get_customer first, no invented ID |
| Email with 3 orders | Asks which order |
| get_order 404 | Asks to recheck, offers email lookup |
| 404 twice | Escalates with summary |
| Customer asks for a human | Escalates immediately |
