**Short answer:** return one small, **flat** JSON object with three fields: `reasoning` first, then `priority` and `team` as enums. Enforce it with a schema, not with regex. Don't go with the deeply nested structure your teammate suggested.

## Why your current setup breaks

- **Free text plus regex.** The model decides the formatting (`**Priority:**`, "priority is high"), and your regex has to guess every variant.
- **The answer lives in the same text as the reasoning.** When the reasoning says "could be P1, but it's really P2", the regex can't tell a considered option from the final decision. Moving the answer into its own field fixes this.

## Why not `ticket -> analysis -> reasoning -> steps -> text`

- Five levels of nesting only to reach a string. Deep nesting gives the model more ways to drift from the structure, and it makes your parsing code more fragile (`data["ticket"]["analysis"]["reasoning"]["steps"][0]["text"]`).
- Support leads want one readable paragraph, not an array of step objects.
- "Organized" belongs in the prompt (clear criteria), not in the output tree. A good rule of thumb is no more than 2–3 levels. Here you need 1.

## Recommended schema

```json
{
  "type": "object",
  "properties": {
    "reasoning": {
      "type": "string",
      "description": "2-4 sentences for support leads: what the issue is, impact/urgency, why this team."
    },
    "priority": { "type": "string", "enum": ["P1", "P2", "P3", "P4"] },
    "team":     { "type": "string", "enum": ["billing", "auth", "infra", "other"] }
  },
  "required": ["reasoning", "priority", "team"],
  "additionalProperties": false
}
```

Put `reasoning` **first**. The model generates fields in order, so it reasons before it commits to a label, and you keep the benefit of "explain, then decide".

## How to enforce it (strongest first)

1. **Native structured output / tool calling.** Most major APIs can constrain output to a JSON schema. You can use a strict JSON-schema response format, or define a single tool such as `triage_ticket` with the schema above and force the model to call it. The exact parameter names differ by provider and SDK version (recalled, not verified here, so check your provider's docs). With this approach, invalid enums and malformed JSON mostly stop happening.
2. **If you can't do that: prompt for JSON plus validation plus retry.** Parse with a validator (for example a Pydantic model with `Literal["P1","P2","P3","P4"]`). On failure, retry once and include the validation error in the retry prompt. If it still fails, fall back to `team="other"` with the ticket flagged for human review instead of guessing.
3. **Never regex the answer out of prose again.** If JSON is somehow off the table, use XML tags (`<reasoning>…</reasoning><priority>P2</priority><team>auth</team>`) and read only the tag contents.

## Prompt template

```text
You triage helpdesk tickets. Read the ticket and return ONLY a JSON object matching the schema.

Priority definitions:
- P1: service down or data/security exposure affecting many users; no workaround.
- P2: major feature broken for a user or account; no reasonable workaround.
- P3: degraded function or a workaround exists.
- P4: question, cosmetic issue, or feature request.

Team definitions:
- billing: charges, invoices, refunds, plans, payment methods.
- auth: login, password, 2FA/SSO, account lockout, permissions.
- infra: outages, latency, errors/timeouts, integrations failing.
- other: anything not clearly in the above.

Rules:
- "reasoning": 2-4 plain sentences for a support lead. You may discuss alternatives here.
- "priority" and "team" hold your single final decision, using only the allowed values.
- If the ticket spans teams, pick the team that must act first.

Example:
Ticket: "Charged twice for March and now I can't log in to download the invoice."
{"reasoning": "Duplicate charge is the customer's main problem and needs a refund; the login issue blocks invoice access but billing can send the invoice directly. Money-impacting, single customer, workaround exists for the invoice.", "priority": "P2", "team": "billing"}

Ticket:
<ticket>
{ticket_text}
</ticket>
```

Notes on the template:
- **Write your own P1–P4 and team definitions.** The ones above are placeholders. Unclear criteria cause inconsistent labels even when parsing works perfectly.
- Give 2–3 examples, including at least one ambiguous or multi-team ticket like the one above. Those cases are where the labels drift.
- Wrap the ticket in `<ticket>` tags so any instructions inside the ticket text are treated as data.

## Minimal parsing code

```python
from typing import Literal
from pydantic import BaseModel, ValidationError

class Triage(BaseModel):
    reasoning: str
    priority: Literal["P1", "P2", "P3", "P4"]
    team: Literal["billing", "auth", "infra", "other"]

def parse(raw: str) -> Triage | None:
    try:
        return Triage.model_validate_json(raw)   # Pydantic v2 API
    except ValidationError:
        return None  # retry with error message, then route to human review
```

If you use native structured output (option 1), most of the retry path won't run in practice. Keep the validator anyway as a cheap safety net.
