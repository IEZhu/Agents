# Runbook: «Disk usage > 90%» на диске PostgreSQL (db-server [ЗАПОЛНИТЬ имя хоста])

**Кратко.** Почти всегда место съедает WAL, который держит сломавшийся Debezium. Порядок действий: проверить → перезапустить Debezium → если не помогло или места мало, звонить Андрею. Сами файлы ничего не удаляете.

**Андрей (DBA): +7 900 000-00-00.** Звонить можно в любое время, будить можно.

---

## 0. Что делать НЕЛЬЗЯ (прочитайте до начала)

| ❌ Нельзя | Почему |
|---|---|
| Удалять что-либо в `/var/lib/postgresql/15/main/` и особенно в `pg_wal/` | База перестанет запускаться, данные можно потерять безвозвратно |
| Запускать `pg_resetwal` | Разрушает базу |
| Перезапускать или останавливать PostgreSQL (`systemctl restart/stop postgresql`), чтобы «освободить место» | Место не освободится, а база может не подняться |
| Трогать другие слоты репликации, кроме `debezium_slot` | Они могут быть нужны репликам |
| Выполнять SQL-команды, которых нет в этой инструкции | — |

Если что-то идёт не так, как описано, **остановитесь и звоните Андрею**.

---

## 1. Зайти на сервер и посмотреть диск

```bash
ssh [ЗАПОЛНИТЬ пользователь]@[ЗАПОЛНИТЬ хост]
df -h /var/lib/postgresql/15/main
```

Смотрите на колонку `Use%` и запишите значение и время.

- **100% или близко к нему (≥ 98%)** → сразу **шаг 7 (звонок Андрею)**, остальное потом.
- Иначе переходите к шагу 2.

## 2. Проверить, что PostgreSQL жив

```bash
pg_lsclusters
```

Ожидаемый вывод: строка `15  main ... online ...`.

- `online` → шаг 3.
- `down` или ошибка → **ничего не делайте, звоните Андрею (шаг 7)**.

## 3. Убедиться, что причина та же (WAL + Debezium)

Сколько занимает WAL:

```bash
sudo du -sh /var/lib/postgresql/15/main/pg_wal
```

Состояние слотов репликации (одна команда, копируйте целиком):

```bash
sudo -u postgres psql -x -c "SELECT slot_name, active, wal_status, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_held FROM pg_replication_slots;"
```

Как читать результат:

| Что видите | Что это значит | Что дальше |
|---|---|---|
| `pg_wal` большой (десятки–сотни ГБ), у `debezium_slot` `active = f`, `wal_held` большой | Та самая известная проблема | Шаг 4 |
| `pg_wal` маленький (единицы ГБ) | Место съело что-то другое | **Звонок Андрею (шаг 7)** |
| `debezium_slot` `active = t`, но `wal_held` огромный и растёт | Debezium подключён, но не успевает | **Звонок Андрею (шаг 7)** |
| Слота `debezium_slot` нет или команда выдала ошибку | Непонятная ситуация | **Звонок Андрею (шаг 7)** |

## 4. Оценить скорость заполнения

Подождите 10 минут и снова выполните:

```bash
df -h /var/lib/postgresql/15/main
```

Посчитайте, на сколько процентов вырос `Use%` за 10 минут. Диск 500 ГБ, так что 1% ≈ 5 ГБ.

- Если при такой скорости диск заполнится **меньше чем за 2 часа**, звоните Андрею прямо сейчас (шаг 7), а шаг 5 делайте параллельно.
- Если времени больше, переходите к шагу 5.

## 5. Перезапустить Debezium

**[ЗАПОЛНИТЬ: точный способ перезапуска для вашей установки.]** Например, если Debezium работает в Kafka Connect:

```bash
# проверить состояние коннектора
curl -s http://[ЗАПОЛНИТЬ connect-host]:8083/connectors/[ЗАПОЛНИТЬ имя коннектора]/status

# перезапустить коннектор вместе с задачами
curl -s -X POST "http://[ЗАПОЛНИТЬ connect-host]:8083/connectors/[ЗАПОЛНИТЬ имя коннектора]/restart?includeTasks=true"
```

Если он работает как systemd-сервис или контейнер, укажите здесь `sudo systemctl restart ...` / `docker restart ...`.

Через 2–3 минуты повторите запрос слотов из шага 3:

- у `debezium_slot` стало `active = t` → шаг 6;
- осталось `active = f` → повторите перезапуск **один раз**. Не помогло → **звонок Андрею (шаг 7)**.

## 6. Проверить, что стало лучше

После того как Debezium подключился, он начнёт вычитывать накопленное, и `wal_held` будет уменьшаться. Место на диске освобождается **не сразу**, а через несколько минут (на контрольной точке PostgreSQL). Это нормально.

Каждые 10 минут в течение получаса выполняйте:

```bash
df -h /var/lib/postgresql/15/main
sudo -u postgres psql -x -c "SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_held FROM pg_replication_slots WHERE slot_name = 'debezium_slot';"
```

- `wal_held` уменьшается, `Use%` падает или хотя бы не растёт → инцидент локализован. Андрею можно не звонить: напишите ему отчёт утром (см. шаг 8).
- `wal_held` не уменьшается, а `Use%` продолжает расти → **звонок Андрею (шаг 7)**.

## 7. Звонок Андрею

**+7 900 000-00-00.** Если не отвечает, повторяйте каждые 5 минут. Резервный контакт: **[ЗАПОЛНИТЬ]**.

Сразу сообщите:
1. `Use%` сейчас и насколько он вырос за последние 10 минут;
2. вывод `pg_lsclusters`;
3. вывод запроса по слотам из шага 3;
4. что уже сделали (перезапускали ли Debezium и что получилось).

Дальше действуйте **только по указаниям Андрея**.

### 7а. Аварийная мера: только если Андрей недоступен

> **[ЗАПОЛНИТЬ / утвердить Андрею]**: разрешено ли дежурному это делать и при каком пороге. Ниже предлагаемый вариант.

**Условия (должны выполняться ВСЕ):**
- до Андрея и резервного контакта не удалось дозвониться за 20 минут;
- `Use%` **≥ 97%** и продолжает расти;
- по шагу 3 причина подтверждена: `debezium_slot`, `active = f`.

**Что произойдёт.** Место освободится, база продолжит работать. Но Debezium потеряет свою позицию, и утром Андрею придётся пересинхронизировать его с Kafka (заново делать snapshot). Это неприятно, но исправимо. Заполненный на 100% диск остановит всю базу, и это намного хуже.

```bash
sudo -u postgres psql -c "SELECT pg_drop_replication_slot('debezium_slot');"
sudo -u postgres psql -c "CHECKPOINT;"
```

Первая команда удаляет **только** слот `debezium_slot`, имя вводите ровно так. Вторая заставляет PostgreSQL сразу убрать ненужный WAL, это безопасно.

Если первая команда ответила ошибкой `is active for PID`, значит Debezium успел переподключиться. Ничего больше не делайте и возвращайтесь к шагу 6.

Проверка через 5 минут:

```bash
df -h /var/lib/postgresql/15/main
```

`Use%` должен заметно упасть. Продолжайте звонить Андрею: он должен узнать об этом как можно раньше.

Утром напишите Андрею в [ЗАПОЛНИТЬ канал/чат]:

## Заметки для вас, Андрей (не для дежурных)

- **Ограничитель на уровне PostgreSQL.** Параметр `max_slot_wal_keep_size` (есть с PG13) ограничивает объём WAL, который слот может удерживать. Если выставить его, скажем, на 250–300 ГБ, при следующем падении Debezium PostgreSQL сам пометит слот как `lost`, и диск не заполнится. По сути это автоматический шаг 7а: CDC всё равно придётся пересинхронизировать, зато ночью никого не будят. Параметр меняется без рестарта (`ALTER SYSTEM` + `pg_reload_conf()`), но перед применением проверьте поведение по документации 15-й версии: я описываю его по памяти.
- **Более ранний алерт.** Сейчас Zabbix срабатывает на заполнение диска, то есть на симптом. Если добавить триггер «`debezium_slot` неактивен > 15 мин» или «удерживаемый WAL > N ГБ» по запросу из шага 3, проблему будет видно за часы до 90%.
- **Корневая причина.** Три падения Debezium за два месяца — это отдельная проблема. Стоит разобрать логи Kafka Connect за эти три раза и понять, почему коннектор не переподключается сам.
- **Проверка инструкции.** Попросите одного из дежурных днём пройти шаги 1–3 и 5 на живом сервере под вашим присмотром. Так выяснится, хватает ли ему прав на `sudo -u postgres` и доступа к Kafka Connect.
