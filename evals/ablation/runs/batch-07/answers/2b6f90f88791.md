**Short answer:** return a flat JSON object with three fields, in this order: `reasoning`, then `priority`, then `team`. Make `priority` and `team` enums and validate them in code. If your API supports schema-enforced output (structured outputs, JSON mode with a schema, or a forced tool call), use it. That removes the parsing problem entirely. Don't use your teammate's deep nesting.

## Why your regex breaks

The decision is buried in free text that uses the same words ("priority", "P2") as the reasoning. No regex can reliably tell "the answer" apart from "a priority mentioned while thinking". The fix is structural: put the answer in its own field, so the reasoning can mention P1 and P3 all it likes.

## Why not `ticket -> analysis -> reasoning -> steps -> text`

- Nesting adds no reliability. It just adds more keys and brackets the model can get wrong, and more path-walking code on your side.
- "Organized" belongs in the content of the reasoning, not in the depth of the JSON.
- The support leads want readable text. Rebuilding prose from `steps[].text` fragments is extra work that buys you nothing.

If leads really want bullet points, allow one level at most: `"reasoning": ["point 1", "point 2"]`. Otherwise use a single string.

## Field order matters

Put `reasoning` **first**. The model generates tokens in order, so writing the reasoning before `priority` and `team` lets the decision follow from the analysis. If the decision comes first, the reasoning turns into a justification written after the fact.

## Schema

```json
{
  "type": "object",
  "properties": {
    "reasoning": {
      "type": "string",
      "description": "2-4 sentences for support leads: what the issue is, impact/urgency signals, why this team."
    },
    "priority": { "type": "string", "enum": ["P1", "P2", "P3", "P4"] },
    "team":     { "type": "string", "enum": ["billing", "auth", "infra", "other"] }
  },
  "required": ["reasoning", "priority", "team"],
  "additionalProperties": false
}
```

## Prompt

```text
You triage helpdesk tickets. Read the ticket and return ONLY a JSON object
matching this shape, with no prose or code fences around it:

{"reasoning": "<string>", "priority": "P1|P2|P3|P4", "team": "billing|auth|infra|other"}

Fields:
- reasoning: 2-4 plain sentences for support leads. State the core issue,
  the urgency/impact signals you saw, and why the chosen team owns it.
- priority: exactly one of P1, P2, P3, P4.
  - P1: outage or security issue affecting many users / data loss / payments down
  - P2: a single customer blocked with no workaround, or a degraded core feature
  - P3: impaired but a workaround exists
  - P4: question, cosmetic issue, feature request
- team: exactly one of billing, auth, infra, other.
  - billing: charges, invoices, refunds, plans
  - auth: login, SSO, passwords, MFA, permissions
  - infra: downtime, latency, errors, integrations failing
  - other: anything else

If signals conflict, pick the higher priority and say why in reasoning.

<ticket>
{ticket_text}
</ticket>
```

Adjust the P1-P4 definitions to your SLA. Explicit criteria also make priorities consistent between tickets, not just parseable.

## Parsing and validation

```python
import json
from typing import Literal
from pydantic import BaseModel, ValidationError

class Triage(BaseModel):
    reasoning: str
    priority: Literal["P1", "P2", "P3", "P4"]
    team: Literal["billing", "auth", "infra", "other"]

def parse_triage(raw: str) -> Triage:
    raw = raw.strip()
    # tolerate accidental ```json fences if not using enforced output
    if raw.startswith("```"):
        raw = raw.split("\n", 1)[1].rsplit("```", 1)[0]
    return Triage.model_validate(json.loads(raw))
```

On `ValidationError` or `JSONDecodeError`: retry once and include the error message in the retry prompt. If the retry also fails, fall back to `priority="P2", team="other"` and flag the ticket for human review. Never guess silently.

## Options by reliability

| Approach | Parse reliability | Notes |
|---|---|---|
| Schema-enforced output (structured outputs / forced tool call) | Highest: output is constrained to the schema | Check your provider's docs for the exact parameter name. I haven't verified it for your stack. |
| Prompted JSON + Pydantic validation + retry | High | Works on any model. Keep the code-fence stripping. |
| XML tags (`<reasoning>…</reasoning><priority>P2</priority><team>auth</team>`) | High | Good fallback if the model struggles to escape quotes and newlines in long reasoning inside JSON. Extract the tag contents, then validate against the same enums. |
| Free text + regex (current) | Low | Drop it. |

## Before switching, check

- Does your model/API support schema-enforced output? Check your provider's docs for "structured outputs" or "tool use / function calling". If it doesn't, use the prompted-JSON row. The design stays the same.
- Does any downstream consumer expect the old `Priority: P2` text? Grep for the regex before you remove it.
