# Runbook: алерт «disk usage > 90%» на диске PostgreSQL (prod-db)

**Для кого:** дежурный техподдержки. Знать PostgreSQL не нужно.
**Сколько времени:** 10–20 минут.
**Главное правило:** если что-то идёт не так, как написано, **остановись и звони Андрею**. Звонить можно в любое время.

**Андрей (DBA): +7 900 000-00-00**

## ЗАПРЕЩЕНО (даже если очень хочется освободить место)

- ❌ Удалять, перемещать или сжимать **любые** файлы в `/var/lib/postgresql/`, особенно в `pg_wal`. Это гарантированно убьёт базу, восстанавливать придётся из бэкапа.
- ❌ Запускать `pg_resetwal`, `pg_archivecleanup` и любые команды, которых нет в этой инструкции.
- ❌ Перезапускать или останавливать PostgreSQL (`systemctl restart/stop postgresql`), убивать процессы `postgres`.
- ❌ Трогать разделы, LVM и fstab.

Место освобождается **только** через шаги ниже.

---

## Шаг 0. Зайти на сервер

```bash
ssh <пользователь>@<prod-db-хост>
```

## Шаг 1. Насколько всё плохо

```bash
df -h /var/lib/postgresql/15/main
```

Смотри колонку `Use%`:

| Use% | Что делать |
|---|---|
| 90–94% | Спокойно идём по шагам 2–5 |
| 95–97% | Идём по шагам 2–5, **параллельно звоним Андрею** |
| 98% и выше | **Сразу звони Андрею**, потом шаги 2–5 |

Запиши время и процент, это пригодится.

## Шаг 2. Жива ли база

```bash
systemctl status postgresql@15-main --no-pager
```

- Видишь `active (running)` зелёным → переходи к шагу 3.
- Видишь `failed` или `inactive` → **база упала. Ничего больше не делай, звони Андрею.** Не пытайся её запустить.

## Шаг 3. Подтвердить, что причина та же (Debezium)

Скопируй команду целиком:

```bash
sudo -u postgres psql -c "SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS zaderzhano FROM pg_replication_slots;"
```

Эта команда только **читает**, ничего не меняет. `sudo -u postgres` нужен, потому что зайти в базу может только системный пользователь `postgres`.

Пример вывода:

```
   slot_name   | active | zaderzhano
---------------+--------+------------
 debezium_slot | f      | 412 GB
```

Как читать:

- `active` = `f` (false) у `debezium_slot` и в `zaderzhano` десятки или сотни GB → **это наш типичный случай**. Переходи к шагу 4.
- `active` = `t` и `zaderzhano` маленькое (MB или пара GB) → причина **другая**. Звони Андрею.
- Команда выдала ошибку → скопируй текст ошибки и звони Андрею.

## Шаг 4. Перезапустить коннектор Debezium

Проверь статус коннектора:

```bash
curl -s http://<connect-хост>:8083/connectors/<имя-коннектора>/status
```

Если в ответе видно `"state":"FAILED"` (у коннектора или у задачи, `tasks`), перезапусти его:

```bash
curl -s -X POST "http://<connect-хост>:8083/connectors/<имя-коннектора>/restart?includeTasks=true&onlyFailed=true"
```

Команда перезапускает только упавшие части Debezium. Базу она не трогает и данных не теряет.

Подожди 2–3 минуты и повтори команду из **шага 3**.

- `active` стало `t` → отлично, переходи к шагу 5.
- Всё ещё `f` → повтори рестарт **один** раз. Не помогло → звони Андрею.
- `curl` не отвечает (`Connection refused`, таймаут) → звони Андрею.

## Шаг 5. Убедиться, что место освобождается

Debezium догоняет не сразу: после запуска ему нужно вычитать накопленное. Диск освобождается постепенно, иногда только через 10–30 минут.

Чтобы ускорить очистку, можно выполнить безопасную команду:

```bash
sudo -u postgres psql -c "CHECKPOINT;"
```

Она говорит базе «сохрани всё и убери ненужные старые файлы». Безопасна, но может на минуту дать повышенную нагрузку на диск.

Каждые 5 минут проверяй:

```bash
df -h /var/lib/postgresql/15/main
sudo -u postgres psql -c "SELECT slot_name, active, pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS zaderzhano FROM pg_replication_slots;"
```

**Всё хорошо, если:** `active` = `t`, `zaderzhano` уменьшается, `Use%` падает. Когда `Use%` опустится ниже 85%, инцидент закрыт (см. «После инцидента»).

**Звони Андрею, если:** через 30 минут `Use%` не падает или продолжает расти.

## Шаг 6. Крайняя мера: только если диск почти полон, а Андрей недоступен

> ⚠️ `<АНДРЕЙ: оставь этот шаг, только если ты заранее разрешаешь его дежурным. Иначе удали его целиком.>`

Условия, **все одновременно**:

1. `Use%` **98% или выше** и продолжает расти.
2. Андрей не ответил на **3 звонка** за 15 минут, `<резервный контакт>` тоже.
3. Шаг 4 не помог (`active` так и осталось `f`).

Только тогда:

```bash
sudo -u postgres psql -c "SELECT pg_drop_replication_slot('debezium_slot');"
sudo -u postgres psql -c "CHECKPOINT;"
```

**Последствия:** база спасена от остановки, но Debezium **потеряет позицию**, и утром Андрею придётся заново настраивать выгрузку в Kafka. Поэтому это последний шаг, а не первый. Если база остановится из-за полного диска, встанет весь прод, а это хуже.

Обязательно напиши в `<канал инцидентов>`: «удалил debezium_slot в ЧЧ:ММ, диск был N%».

## После инцидента

Напиши в `<канал / тикет>`:

- время алерта и `Use%` в начале;
- вывод команды из шага 3 (до и после);
- что делал (рестарт коннектора / CHECKPOINT / удаление слота);

## Для Андрея: что заполнить и как убрать причину

**Заполнить в runbook'е:** хост и порт Kafka Connect, имя коннектора, резервный контакт, канал инцидентов, решение по шагу 6. Хорошо бы прогнать инструкцию днём с кем-то из дежурных: проверить, что их `sudo` пускает в `sudo -u postgres`, а `curl` до Connect доходит с prod-db (если нет, дай команду с другого хоста).

Что я сделал допущениями, проверь (команды за 5 секунд):

- `pg_wal` лежит на том же диске, а не вынесен симлинком: `sudo ls -ld /var/lib/postgresql/15/main/pg_wal`.
- Юнит называется `postgresql@15-main` (стандартно для Ubuntu/PGDG): `systemctl list-units 'postgresql*'`.
- Параметр `onlyFailed` у рестарта в REST API Kafka Connect есть начиная с Kafka 3.0, насколько помню (не проверял, сверь с вашей версией). На старой версии оставь просто `POST .../restart`.

**Корневое решение.** Три одинаковых инцидента за два месяца значат, что runbook тут лечит симптом:

1. **`max_slot_wal_keep_size`** (есть с PG 13). Ограничивает, сколько WAL может удерживать слот. Например, `max_slot_wal_keep_size = '300GB'` в `postgresql.conf` + `SELECT pg_reload_conf();` (рестарт не нужен, насколько помню). При превышении слот инвалидируется (`wal_status = 'lost'`), и Debezium придётся пересоздавать. Фактически это тот же шаг 6, только автоматический и **до** того, как диск кончится, без участия человека в 3 ночи. Значение подбери по скорости генерации WAL и по тому, сколько часов простоя Debezium ты готов терпеть.
2. **Алерт на сам слот, а не на диск.** Zabbix-item на `SELECT active, pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn) FROM pg_replication_slots WHERE slot_name='debezium_slot'` и триггер «`active = f` дольше 15 минут» или «задержано > 50 GB». Тогда узнаешь о проблеме за часы до 90%, возможно ещё днём.
3. **Почему Debezium отваливается.** Три раза за два месяца это закономерность. Стоит посмотреть логи Connect в моменты падений. Типичные подозреваемые: таймауты или сетевые разрывы, ребаланс воркеров, `heartbeat.interval.ms` не настроен (без него на малоактивных таблицах слот и так копит WAL). Это гипотезы, не диагноз.
4. **Авторестарт упавших задач.** Простой cron или скрипт, который проверяет `/status` и делает `restart` при `FAILED`. Он закроет шаг 4 без человека.
