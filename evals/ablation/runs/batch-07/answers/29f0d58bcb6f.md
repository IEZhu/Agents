Короткий ответ: обе проблемы в основном в цикле, а не в модели. Первая целиком ваша. Во второй модель действительно поступает неправильно, но цикл это никак не ограничивает.

## 1. Почему агент крутится по 40 итераций

Посмотрите, что получает модель, когда `search_logs` падает по таймауту:

```python
except Exception:
    log.exception("tool failed")   # причина остаётся в ваших логах
    return None                     # модель видит content = "null"
```

`json.dumps(None)` даёт строку `"null"`. Для модели это выглядит так: «вызвала поиск, получила пустоту». Она не может отличить это от «ничего не найдено» или от сбоя сети, и не знает, что причина в слишком большом диапазоне. Повторить тот же запрос в такой ситуации вполне разумно, и она повторяет его, пока не упрётся в контекст или деньги. Всю информацию об ошибке (`TimeoutError`) вы записали в свой лог, а модели ничего не передали.

К этому добавляются ещё две вещи:
- **Нет ограничителей.** `while True` без лимита шагов, бюджета и детекции повторов. Любой сбой в инструменте превращается в бесконечный цикл за ваш счёт.
- **Сам инструмент нельзя вызвать удачно.** Если поиск по суткам логов стабильно не укладывается в таймаут, модель физически не может получить результат. Инструмент должен принудительно ограничивать объём: обязательное окно времени, фильтры, `limit`, режим агрегации.

## 2. Почему тикет получается с выдуманной причиной

Когда `search_logs` и `create_ticket` приходят в одном ответе, аргументы для тикета модель написала **до того**, как увидела хоть один результат поиска. Выдумывать ей там больше нечего. Параллельный tool calling рассчитан на независимые вызовы, а здесь между ними жёсткая зависимость по данным. Инструкцией в промпте («сначала поищи») это снижается, но не гарантируется. Гарантию даёт только код: действие с побочным эффектом не должно выполняться, пока нет доказательств, полученных на **предыдущем** шаге.

## Как переписать

Идея такая: агент — это небольшой конечный автомат с двумя фазами (расследование и действие), и переход между ними проверяет код, а не модель.

```python
import json
from collections import Counter

MAX_STEPS = 15
MAX_COST_USD = 0.50
MAX_SAME_CALL = 2
SIDE_EFFECT_TOOLS = {"create_ticket"}


class ToolError(Exception):
    """Ошибка, которую стоит показать модели: что случилось и что делать дальше."""
    def __init__(self, code, message, hint=None):
        super().__init__(message)
        self.code, self.message, self.hint = code, message, hint


def err(code, message, hint=None):
    return {"ok": False, "error": code, "message": message, "hint": hint}


def run_tool(name, raw_args):
    try:
        args = json.loads(raw_args or "{}")
    except json.JSONDecodeError as e:
        return err("invalid_json", f"Arguments are not valid JSON: {e}")

    fn = TOOLS_IMPL.get(name)
    if fn is None:
        return err("unknown_tool", f"No tool named {name!r}.")

    try:
        return {"ok": True, "result": fn(**args)}
    except ToolError as e:
        return err(e.code, e.message, e.hint)
    except TypeError as e:  # неверные/лишние аргументы
        return err("bad_arguments", str(e))
    except Exception as e:
        log.exception("tool %s failed", name)
        return err(type(e).__name__, str(e)[:500])


def canonical(raw_args):
    try:
        return json.dumps(json.loads(raw_args or "{}"), sort_keys=True)
    except json.JSONDecodeError:
        return raw_args


def agent(task):
    messages = [{"role": "system", "content": SYSTEM_PROMPT},
                {"role": "user", "content": task}]
    call_counts = Counter()
    evidence = []          # успешные непустые результаты search_logs
    cost = 0.0

    for step in range(MAX_STEPS):
        # Фаза определяется кодом: до появления доказательств create_ticket модели просто не показывается.
        tools = TOOLS_ALL if evidence else TOOLS_INVESTIGATE
        resp = llm(messages, tools=tools, parallel_tool_calls=False)
        cost += resp.cost
        messages.append(resp.message)

        if not resp.tool_calls:
            return resp.content

        # Снимок до выполнения батча: доказательства из ЭТОГО же ответа не считаются.
        had_evidence = bool(evidence)

        for tc in resp.tool_calls:
            key = (tc.name, canonical(tc.arguments))
            call_counts[key] += 1

            if call_counts[key] > MAX_SAME_CALL:
                out = err("duplicate_call",
                          f"Identical {tc.name} call made {call_counts[key]} times.",
                          "Change the arguments (narrower time window, extra filters) or stop and report what you know.")
            elif tc.name in SIDE_EFFECT_TOOLS and not had_evidence:
                out = err("precondition_failed",
                          f"{tc.name} requires evidence from a successful search_logs call in a PREVIOUS step.",
                          "Search the logs first, read the results, then create the ticket.")
            else:
                out = run_tool(tc.name, tc.arguments)
                if tc.name == "search_logs" and out["ok"] and out["result"].get("hits"):
                    evidence.append(out["result"])

            # Ответ на КАЖДЫЙ tool_call_id обязателен, даже если вызов отклонён.
            messages.append({"role": "tool", "tool_call_id": tc.id,
                             "content": json.dumps(out, ensure_ascii=False, default=str)})

        if cost > MAX_COST_USD:
            break

    # Бюджет исчерпан: последний вызов без инструментов, чтобы модель подвела итог.
    messages.append({"role": "user", "content":
                     "Budget exhausted. Do not call tools. Summarize what you found, "
                     "what is confirmed vs. unconfirmed, and what a human should check next."})
    return llm(messages, tools=None).content
```

Что здесь важно:

- **Ошибки возвращаются модели как данные**: код ошибки, сообщение и подсказка, что делать дальше. Подсказка — самая полезная часть: она превращает «повторить вслепую» в «сузить окно».
- **`had_evidence` снимается до выполнения батча.** Без этого, если модель всё же пришлёт оба вызова разом, `search_logs` выполнится первым, `evidence` заполнится, и `create_ticket` проскочит в том же шаге.
- **Двойная защита для `create_ticket`**: его нет в списке инструментов на фазе расследования, а если модель всё равно его вызовет (например, по памяти из истории), вызов отклонит проверка предусловия.
- **`parallel_tool_calls=False`** — так параметр называется в OpenAI API, у Anthropic есть аналог `tool_choice={"type": "auto", "disable_parallel_tool_use": True}` (оба имени по памяти, не проверял — сверьте с документацией вашего провайдера и версии SDK). Даже без этого флага guard выше закрывает проблему. Флаг лишь экономит лишние шаги.
- **Стоимость.** `resp.cost` — заглушка: посчитайте её из `usage` (input/output tokens × цена вашей модели).

## Починить сам `search_logs`

Без этого пункта остальное лечит симптомы: модель будет вежливо останавливаться, но причину так и не найдёт.

```python
def search_logs(query, since, until, status=None, service=None, limit=50, mode="lines"):
    if parse(until) - parse(since) > timedelta(hours=2):
        raise ToolError("range_too_large",
                        "Time window exceeds 2h.",
                        "Split into ≤2h windows, or use mode='aggregate' for an overview.")
    try:
        ...  # запрос с серверным таймаутом
    except TimeoutError:
        raise ToolError("timeout",
                        f"Search {since}..{until} timed out.",
                        "Do NOT repeat this query. Halve the window or add status/service filters.")
```

- **`since`/`until` сделайте обязательными** в JSON-схеме, а в описании инструмента напишите, какое окно разумно.
- **Добавьте `mode="aggregate"`**, который возвращает, например, число 500-ок по сервису/эндпоинту/часу. Для задачи «найди причину» это правильный первый шаг: дешёвый обзор, потом детализация по горячей точке.
- **`limit` применяйте внутри инструмента** и возвращайте `truncated: true`, `total: N`. Не обрезайте JSON-строку в цикле: получится невалидный JSON.
- **Каждая строка лога должна иметь `id`** — он понадобится для проверки ниже.

## Заземление тикета

Чтобы тикет не содержал выдуманную причину, одного «сначала поищи» мало. Сделайте в `create_ticket` обязательное поле `evidence_ids: list[str]` и в реализации проверяйте, что каждый id действительно встречался в результатах `search_logs` этого запуска (держите `set` увиденных id). Если нет — `ToolError("ungrounded", "...", "Cite log line ids returned by search_logs")`. Это дешёвая детерминированная проверка на галлюцинации, и работает она лучше любого промпта.

Если ошибка в тикете стоит дорого (тикет будит дежурного), добавьте подтверждение человеком: агент формирует черновик, а вы показываете его и создаёте тикет по «ок». Для первой версии я бы так и сделал, а автономное создание включил бы, когда накопится статистика, что черновики корректны.

## Системный промпт (фрагмент)

```text
You investigate HTTP 500 errors and file a ticket.

Procedure:
1. Get an overview first: search_logs with mode="aggregate" over ≤2h windows covering the requested day.
2. Drill into the top offender with mode="lines" and narrow filters.
3. State the root cause ONLY if specific log lines support it. Otherwise say "cause not established".
4. Only after step 3, call create_ticket, citing evidence_ids from lines you actually received.

When a tool returns ok=false, read "hint" and change your approach. Never repeat an identical call.
```

## Как проверить, что стало лучше

Соберите 10–20 прогонов на реальных днях (включая «тяжёлый» день, где раньше были таймауты, и день, где причина неочевидна) и смотрите:
- число шагов и стоимость за прогон (распределение, а не среднее);
- долю прогонов, упёршихся в `MAX_STEPS`/бюджет;
- долю тикетов, где причина подтверждается `evidence_ids` при ручной проверке;
- срабатывания `duplicate_call` и `precondition_failed`. Если они частые, дело в промпте или описании инструментов.

Для всего этого LangChain не нужен: логика укладывается примерно в сотню строк, и вам видно каждое решение. Главное, что сейчас не хватает, — это протокол ошибок и проверки предусловий, а не фреймворк.
