### Corrected storage math

| | Value |
|---|---|
| Per second | 2,000 × 200 B = 400 KB/s |
| Per day | 400 KB/s × 86,400 s = **34.56 GB/day** (~32.2 GiB) |
| 90 days, raw heap | 34.56 × 90 ≈ **3.11 TB** (~2.83 TiB) |
| +40% for indexes/bloat | ≈ **4.35 TB** (~3.96 TiB) |

Before you size the volume, check these:
- **Is 40% enough?** Maybe not. With rows this small, each index entry is large relative to the row. A B-tree on `(event_time)` plus one or two more on `user_id`/`session_id` could add 30–60% on its own. Bloat, WAL (`max_wal_size` plus any `wal_keep_size` or replication-slot retention) and temp files come on top of that. I'd plan for 50–70% overhead until you measure it.
- **What does "200 bytes on disk" include?** If it's just the payload, add about 28 bytes per row for the tuple header and line pointer, plus page fill overhead. That's another ~15%. Measure it on a test load: `SELECT pg_total_relation_size('events') / count(*) FROM events;`
- **Leave free space.** Don't plan to run the volume above ~80% full.

A realistic size is **5–6 TB**, or start smaller and grow it. gp3 volumes can be resized online, up to a 16 TiB maximum (recalled, not verified; check current AWS limits). The throughput is not a concern: 400 KB/s plus WAL is far below gp3's baseline of 3,000 IOPS and 125 MB/s (also recalled).

### Monthly or daily partitions: go daily

| | Monthly | Daily |
|---|---|---|
| Partitions kept | ~3–4 | 90–91 |
| Rows per partition | ~5.2 B | 172.8 M |
| Size per partition (heap) | ~1 TB | ~35 GB |
| Retention granularity | You drop a whole month at once, so you store up to ~120 days of data to keep 90 | Exactly 90 days |
| VACUUM / index build per partition | Very long | Manageable |

Daily partitioning fits better here:
- **Retention is cheap.** Removing old data is `DETACH PARTITION ... CONCURRENTLY` followed by `DROP TABLE`. No `DELETE`, so no bloat.
- **Maintenance stays manageable.** Autovacuum, including the anti-wraparound freeze, runs on ~35 GB pieces instead of ~1 TB ones.
- **~90 partitions is fine** for the planner in PG 16, as long as your queries filter on the partition key so pruning works.

Sketch:

```sql
-- Parent table, range-partitioned by event time
CREATE TABLE events (
    event_time  timestamptz NOT NULL,
    user_id     bigint,
    session_id  uuid,
    event_type  text,
    payload     jsonb
) PARTITION BY RANGE (event_time);

-- One partition per day (automate this with pg_partman or a cron job)
CREATE TABLE events_2026_09_25 PARTITION OF events
    FOR VALUES FROM ('2026-09-25') TO ('2026-09-26');

-- A BRIN index on append-only time data is tiny compared to a B-tree
CREATE INDEX ON events USING brin (event_time);

-- Retention: remove the oldest day without blocking reads/writes on the parent
ALTER TABLE events DETACH PARTITION events_2026_06_26 CONCURRENTLY;
DROP TABLE events_2026_06_26;  -- take a backup/archive first if you need the data
```

Trade-offs:
- **BRIN vs B-tree:** BRIN saves a lot of space and write overhead, but it only helps range scans on data inserted roughly in time order. Point lookups by `user_id` still need a B-tree, and each B-tree adds space and write cost.
- **Pre-create partitions:** keep a few days ahead (pg_partman's `premake`). Otherwise, if no partition covers an event's timestamp, the insert fails. A `DEFAULT` partition catches those rows, but it makes later partition creation slower.
- **Connection pooling:** at 2,000 events/s, batch inserts (multi-row `INSERT` or `COPY`) and run them through a pooler such as pgBouncer. Don't do single-row inserts over many connections.

Next step: load a day's worth of synthetic data into staging and measure `pg_total_relation_size` per partition, including your real indexes. Size the volume from that number, not from the 40% guess.

### Is 40% overhead realistic?

It's probably in the right range, but it depends on things I can't see yet:

- **Does "200 bytes on disk" include per-row overhead?** Postgres adds a 23-byte tuple header (padded to 24) and a 4-byte line pointer to every row, and page fill is never perfect. If 200 B is only the payload, the heap is really about 230 B/row, or ~3.6 TB before indexes.
- **Each B-tree index costs a lot at this row count.** A single `bigint` or `timestamptz` B-tree takes roughly 20–30 B per row once you count tuple overhead and fill factor. That's about 300–450 GB per index across 15.5B rows (this is an estimate, so measure it on real data). Two B-trees plus some bloat takes up most of the 40%. A third index goes past it.
- **Use BRIN on the event timestamp instead of a B-tree** where range scans are the main pattern. On append-only, time-ordered data it's usually a few MB, not hundreds of GB. The trade-off is that BRIN is poor for point lookups.
- **Budget beyond the table:** WAL (`max_wal_size`, plus any retention for replication slots or archiving), temp files from big sorts, and free headroom. Don't run a volume above about 80% full.

**Practical provisioning:** start at roughly **5–6 TB of gp3**, or start smaller and grow online. EBS Elastic Volumes let you resize without downtime, though as I recall you can only modify a volume about once every 6 hours (check the AWS docs). Throughput is not a concern: 400 KB/s of heap plus WAL is far below gp3's baseline, which I recall as 3,000 IOPS and 125 MB/s.

### Monthly vs daily partitioning

**Go daily.** At this volume, monthly is too coarse:

| | Monthly | Daily |
|---|---|---|
| Rows per partition | ~5.2B | ~173M |
| Size per partition (heap) | ~1.04 TB | ~35 GB |
| Partitions live | 3–4 | ~90 (plus a few pre-created) |
| Retention precision | Poor. To guarantee 90 days you hold up to ~120, which is **~33% extra storage (~1 TB)** | Exact. Drop one day each day |
| Index build, `VACUUM`, `pg_repack` per partition | Hours, on TB-sized objects | Minutes, on ~35 GB |

Why daily wins:

1. **Retention by `DROP` or `DETACH PARTITION`, never `DELETE`.** Deleting 173M rows a day would create heavy bloat and vacuum load. Dropping a partition is a metadata operation that returns disk space immediately. This is also why a 40% bloat allowance is realistic at all: with partition drops, the table itself barely bloats.
2. **Smaller units for maintenance.** Autovacuum still has to freeze insert-only tables. PG 13+ triggers vacuum on inserts via `autovacuum_vacuum_insert_threshold`. It's much gentler on 35 GB partitions than on 1 TB ones.
3. **About 95 partitions is fine for the PG 16 planner**, as long as queries filter on the partition key so pruning applies. Queries without a time predicate will scan every partition. That's the main trade-off, so check your query patterns.

Trade-offs of daily: you have more objects to manage, and you need automation to create partitions ahead of time and drop old ones. `pg_partman` with its background worker or a cron job is the usual tool. Always pre-create several days ahead. If an insert arrives with no matching partition, it fails, unless you add a `DEFAULT` partition. A `DEFAULT` partition has its own drawbacks: attaching a new partition then has to scan it.

### Minimal daily-partition DDL (PG 16)

```sql
-- Parent table, range-partitioned on event time
CREATE TABLE clickstream_events (
    event_id    bigint GENERATED ALWAYS AS IDENTITY,
    occurred_at timestamptz NOT NULL,
    user_id     bigint,
    event_type  text NOT NULL,
    payload     jsonb,
    PRIMARY KEY (event_id, occurred_at)   -- PK on a partitioned table must include the partition key
) PARTITION BY RANGE (occurred_at);

-- BRIN for time-range scans: tiny, cheap to maintain on append-only data
CREATE INDEX ON clickstream_events USING brin (occurred_at);

-- One daily partition (automate this with pg_partman or a scheduled job)
CREATE TABLE clickstream_events_20261001
    PARTITION OF clickstream_events
    FOR VALUES FROM ('2026-10-01') TO ('2026-10-02');

-- Retention: detach without blocking readers, then drop
ALTER TABLE clickstream_events
    DETACH PARTITION clickstream_events_20260702 CONCURRENTLY;
DROP TABLE clickstream_events_20260702;
```

Think twice about that PK. At 15.5B rows it's one of the ~300–450 GB B-trees above. If nothing does lookups or deduplication by `event_id`, dropping it is the biggest single storage saving available.

### Check before you commit to a volume size

Load a representative day, or even one hour, into a staging partition, then measure the actual bytes per row:

```sql
SELECT
    pg_size_pretty(pg_table_size('clickstream_events_20261001'))   AS heap,
    pg_size_pretty(pg_indexes_size('clickstream_events_20261001')) AS indexes,
    pg_table_size('clickstream_events_20261001')::numeric
        / NULLIF((SELECT count(*) FROM clickstream_events_20261001), 0) AS heap_bytes_per_row;
```

Multiply the measured per-day size by 90 and add WAL and headroom. That figure should replace the estimates above.
