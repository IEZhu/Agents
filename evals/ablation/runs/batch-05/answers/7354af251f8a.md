### Corrected storage math

| | Value |
|---|---|
| Per second | 2,000 × 200 B = 400 KB/s |
| Per day | 400 KB/s × 86,400 s = **34.56 GB/day** (~32.2 GiB) |
| 90 days, raw heap | 34.56 × 90 ≈ **3.11 TB** (~2.83 TiB) |
| +40% for indexes/bloat | ≈ **4.35 TB** (~3.96 TiB) |

Before you size the volume, check these:
- **Is 40% enough?** Maybe not. With rows this small, each index entry is large relative to the row. A B-tree on `(event_time)` plus one or two more on `user_id`/`session_id` could add 30–60% on its own. Bloat, WAL (`max_wal_size` plus any `wal_keep_size` or replication-slot retention) and temp files come on top of that. I'd plan for 50–70% overhead until you measure it.
- **What does "200 bytes on disk" include?** If it's just the payload, add about 28 bytes per row for the tuple header and line pointer, plus page fill overhead. That's another ~15%. Measure it on a test load: `SELECT pg_total_relation_size('events') / count(*) FROM events;`
- **Leave free space.** Don't plan to run the volume above ~80% full.

A realistic size is **5–6 TB**, or start smaller and grow it. gp3 volumes can be resized online, up to a 16 TiB maximum (recalled, not verified; check current AWS limits). The throughput is not a concern: 400 KB/s plus WAL is far below gp3's baseline of 3,000 IOPS and 125 MB/s (also recalled).

### Row count

- Per day: 2,000 × 86,400 = **172.8 M rows**
- Steady state at 90 days: **~15.55 billion rows**

### Monthly or daily partitions: go daily

| | Monthly | Daily |
|---|---|---|
| Partitions kept | ~3–4 | 90–91 |
| Rows per partition | ~5.2 B | 172.8 M |
| Size per partition (heap) | ~1 TB | ~35 GB |
| Retention granularity | You drop a whole month at once, so you store up to ~120 days of data to keep 90 | Exactly 90 days |
| VACUUM / index build per partition | Very long | Manageable |

Daily partitioning fits better here:
- **Retention is cheap.** Removing old data is `DETACH PARTITION ... CONCURRENTLY` followed by `DROP TABLE`. No `DELETE`, so no bloat.
- **Maintenance stays manageable.** Autovacuum, including the anti-wraparound freeze, runs on ~35 GB pieces instead of ~1 TB ones.
- **~90 partitions is fine** for the planner in PG 16, as long as your queries filter on the partition key so pruning works.

Sketch:

```sql
-- Parent table, range-partitioned by event time
CREATE TABLE events (
    event_time  timestamptz NOT NULL,
    user_id     bigint,
    session_id  uuid,
    event_type  text,
    payload     jsonb
) PARTITION BY RANGE (event_time);

-- One partition per day (automate this with pg_partman or a cron job)
CREATE TABLE events_2026_09_25 PARTITION OF events
    FOR VALUES FROM ('2026-09-25') TO ('2026-09-26');

-- A BRIN index on append-only time data is tiny compared to a B-tree
CREATE INDEX ON events USING brin (event_time);

-- Retention: remove the oldest day without blocking reads/writes on the parent
ALTER TABLE events DETACH PARTITION events_2026_06_26 CONCURRENTLY;
DROP TABLE events_2026_06_26;  -- take a backup/archive first if you need the data
```

Trade-offs:
- **BRIN vs B-tree:** BRIN saves a lot of space and write overhead, but it only helps range scans on data inserted roughly in time order. Point lookups by `user_id` still need a B-tree, and each B-tree adds space and write cost.
- **Pre-create partitions:** keep a few days ahead (pg_partman's `premake`). Otherwise, if no partition covers an event's timestamp, the insert fails. A `DEFAULT` partition catches those rows, but it makes later partition creation slower.
- **Connection pooling:** at 2,000 events/s, batch inserts (multi-row `INSERT` or `COPY`) and run them through a pooler such as pgBouncer. Don't do single-row inserts over many connections.
