**Short answer: no.** Don't rerun it as one statement with `statement_timeout = 0`. Run the backfill in small batches that each commit on their own. And don't let step 4 start automatically "right after": put a duplicate check in front of it first. My step 3 as I wrote it (one `UPDATE` over 18M rows) was the wrong advice for a table this size. That's my mistake.

## Why rerunning the single UPDATE is a bad idea

- **You kept nothing from last night.** The statement was cancelled, so the whole transaction rolled back. You're at 0%, not 60%. A rerun has to do the full 18M rows again, and at your observed rate that's probably 60–70 minutes in one transaction.
- **It holds row locks until it commits.** Every row it touches stays locked until the end. Your step 2 code now writes `normalized_email` on every user update, so any app update to a row the backfill has already touched will wait. That can mean logins and profile saves hanging for up to an hour. Check whether you saw lock waits or app timeouts last night.
- **Every row gets rewritten, and cleanup has to wait.** Each updated row leaves an old copy behind. A transaction open for an hour stops vacuum from cleaning those copies up, on this table and across the whole cluster. It also produces a large burst of WAL, which means replica lag.
- **Last night already left bloat.** The aborted run probably left around 10M dead row versions in `users`. Check this before you start again:
  ```sql
  SELECT n_live_tup, n_dead_tup, last_autovacuum, last_vacuum
  FROM pg_stat_user_tables WHERE relname = 'users';
  ```
  If autovacuum hasn't run since, do `VACUUM (VERBOSE) users;` first. Plain `VACUUM` doesn't block reads or writes.

A side note on the "~60%" figure: as far as I recall, Postgres 15 has no `pg_stat_progress_*` view for `UPDATE`. Those views cover things like VACUUM, CREATE INDEX, ANALYZE and COPY. So that number was probably a rough estimate. It doesn't change the plan, but don't rely on it.

## Revised step 3: batched backfill

Each batch is short, commits on its own, and holds locks for milliseconds. Because of that it can safely run during normal hours at a modest rate, so it doesn't need to wait for tonight. Here's a Rails version:

```ruby
# lib/tasks/backfill_normalized_email.rake
task backfill_normalized_email: :environment do
  User.where(normalized_email: nil).in_batches(of: 5_000) do |batch|
    batch.update_all("normalized_email = lower(btrim(email))")
    sleep 0.05 # throttle; tune against replica lag
  end
end
```

Or in plain SQL, looping over primary-key ranges from a script (one statement per batch, autocommit on):

```sql
UPDATE users
SET normalized_email = lower(btrim(email))
WHERE id >= :lo AND id < :lo + 5000
  AND normalized_email IS NULL;
```

Operational notes:
- Keep a normal `statement_timeout`, for example `SET statement_timeout = '30s'` for that session. A batch that runs long is a warning sign, not something to get around.
- Watch replica lag while it runs. If lag grows, increase the sleep.
- You can stop and restart it at any time. The `IS NULL` filter makes it idempotent.
- Rough runtime: last night's pace suggests about an hour of actual work, plus whatever time the throttle adds. I'm extrapolating from your numbers here, not quoting a benchmark.

## Before step 4: two issues that will otherwise break it

**1. Existing duplicates will make the unique index fail.** With 18M users, I'd expect some addresses that only differ by case, like `Foo@x.com` and `foo@x.com`. You can check today, before the backfill finishes:

```sql
SELECT lower(btrim(email)) AS ne, count(*)
FROM users
GROUP BY 1 HAVING count(*) > 1
ORDER BY 2 DESC
LIMIT 50;
```

If this returns rows, someone has to decide how to handle each group (merge, rename, or deactivate) before step 4. That's a product decision, not something to fix in a migration. If `CREATE UNIQUE INDEX CONCURRENTLY` hits a duplicate, it fails and leaves an **INVALID** index behind. That index still adds cost to every write until you `DROP INDEX CONCURRENTLY` it.

**2. Ruby and SQL don't normalize emails the same way.** Ruby's `strip` removes all leading and trailing whitespace (tabs, newlines, etc.). Postgres `trim()`/`btrim()` removes only spaces by default. `downcase` and `lower()` can also differ on non-ASCII characters. That means rows written by the app and rows written by the backfill could be normalized differently, which is exactly what a uniqueness constraint needs to avoid. Choose one definition and use it in both places, for example `lower(btrim(email, E' \t\r\n'))` in SQL with the Ruby side matched to it. Then measure how many rows are affected:

```sql
SELECT count(*) FROM users WHERE email <> btrim(email, E' \t\r\n');
SELECT count(*) FROM users WHERE email ~ '[^\x01-\x7F]';
```

If both return 0, the difference is only theoretical for your data, and you can keep what you have.
