## Latest user message
Our in-house config loader (Node service, v2.3) has these rules: a file may have an `extends` array; the listed files are each fully resolved first (including their own extends) and then applied left-to-right; after that the file's own keys are applied on top. Objects deep-merge, arrays replace wholesale, and a value of `null` deletes the key.

base.json
```json
{"server": {"port": 8080, "host": "0.0.0.0", "tls": {"enabled": false}}, "features": ["auth"], "logLevel": "info"}
```
secure.json
```json
{"extends": ["base.json"], "server": {"tls": {"enabled": true, "cert": "/etc/ssl/app.pem"}}, "logLevel": "warn"}
```
dev.json
```json
{"extends": ["base.json"], "server": {"port": 3000}, "features": ["auth", "debug-panel"], "logLevel": "debug"}
```
app.json
```json
{"extends": ["secure.json", "dev.json"], "server": {"host": "127.0.0.1", "tls": {"cert": null}}, "features": ["auth", "billing"]}
```

We boot staging with app.json and the health check says TLS is off and the debug panel route is 404. I thought secure.json would make TLS win. What exactly does app.json resolve to, and why?

## Rubric (what a strong answer does)
1. States the final resolved config: server.port 3000, server.host "127.0.0.1", server.tls = {"enabled": false} with no cert key, features ["auth", "billing"], logLevel "debug".
2. Explains that TLS is off because resolved dev.json includes tls.enabled=false inherited from base.json, and dev.json is applied after secure.json, so it overrides secure's enabled=true.
3. Explains that the debug panel is missing because app.json's own features array replaces the inherited ["auth", "debug-panel"] wholesale.
4. Shows the intermediate resolved forms of secure.json and dev.json (or an equivalent step-by-step merge) and suggests a concrete fix, such as reordering extends or setting tls.enabled explicitly in app.json.

## Answer A
**Short answer:** `secure.json` does set TLS on, but `dev.json` is applied after it, and `dev.json` carries its own fully resolved copy of `base.json`, including `tls.enabled: false`. That copy overwrites secure's `true`. The debug panel is missing because `app.json`'s own `features` array replaces the whole array.

Under the rules you described, `app.json` resolves to:

```json
{
  "server": {
    "port": 3000,
    "host": "127.0.0.1",
    "tls": { "enabled": false }
  },
  "features": ["auth", "billing"],
  "logLevel": "debug"
}
```

(I'm assuming the `extends` key itself is removed from the output.)

## Step by step

**1. Resolve `secure.json`** (base, then secure's own keys):
```json
{"server": {"port": 8080, "host": "0.0.0.0", "tls": {"enabled": true, "cert": "/etc/ssl/app.pem"}},
 "features": ["auth"], "logLevel": "warn"}
```

**2. Resolve `dev.json`** (base, then dev's own keys):
```json
{"server": {"port": 3000, "host": "0.0.0.0", "tls": {"enabled": false}},
 "features": ["auth", "debug-panel"], "logLevel": "debug"}
```
`tls.enabled: false` is present here because dev inherits it from base. Dev never mentions TLS, but its resolved result still contains base's value.

**3. Apply `extends` left to right: resolved secure first, then resolved dev on top:**
- `server.port`: 8080, then **3000** (from dev)
- `server.host`: `0.0.0.0` (same in both)
- `server.tls.enabled`: `true`, then **`false`** (base's value, carried in through dev)
- `server.tls.cert`: `/etc/ssl/app.pem` survives the deep merge, because dev's tls object has no `cert` key
- `features`: `["auth"]`, then **`["auth", "debug-panel"]`** (array replaced)
- `logLevel`: `warn`, then **`debug`**

**4. Apply `app.json`'s own keys:**
- `server.host`: **`127.0.0.1`**
- `server.tls.cert: null` **deletes** the cert
- `features: ["auth", "billing"]` **replaces** the array, so `debug-panel` is gone

## The two root causes

1. **Diamond inheritance re-applies base.** Both parents extend `base.json`. Each parent is fully resolved before merging, so the later parent (`dev`) brings back every base default it didn't override itself. Here that's `tls.enabled: false`. With this loader, the last parent in `extends` wins for every key it contains, including keys it only inherited.
2. **Arrays replace, they don't merge.** `app.json` writes `features` in full, so nothing inherited survives. If `debug-panel` should be enabled, it has to appear in `app.json`'s own list.

There's also a hidden third problem: `app.json` deletes `tls.cert`. Even if TLS came out enabled, it would have no certificate. Unless the service has a cert fallback, TLS would probably fail at startup.

The config also runs staging with `logLevel: "debug"` and dev's port 3000. That may not be what you intended either.

## Fixes

**Recommended: state what staging needs directly in `app.json`**, so it doesn't depend on `extends` order:
```json
{
  "extends": ["secure.json", "dev.json"],
  "server": { "host": "127.0.0.1", "tls": { "enabled": true } },
  "features": ["auth", "debug-panel", "billing"],
  "logLevel": "warn"
}
```
I dropped `"cert": null`, so secure's cert is kept. Only include `debug-panel` if you really want it in staging. The 404 may be the safer outcome.

**Not recommended: reordering to `["dev.json", "secure.json"]`.** This makes TLS and `logLevel: warn` win, but secure's resolved copy of base then resets `port` to 8080 and `features` to `["auth"]`. It moves the diamond problem somewhere else instead of removing it.

**Longer term:** consider not letting sibling parents both extend `base.json`. Either make `dev.json` a thin overlay with no `extends`, or chain them (`app → dev → secure → base`), so each default is applied only once.

I haven't seen the loader's source. This is based on the merge rules exactly as you described them. You can check quickly by logging the merged config at boot. It should match the JSON above.


## Answer B
Under the rules you described, secure.json doesn't win. It's applied first, and then dev.json's resolved copy of base.json writes `tls.enabled: false` back over it. The `features` array in app.json then replaces dev's list, which is why the debug panel is gone.

### What app.json resolves to

```json
{
  "server": {
    "port": 3000,
    "host": "127.0.0.1",
    "tls": { "enabled": false }
  },
  "features": ["auth", "billing"],
  "logLevel": "debug"
}
```

(This assumes the loader strips the `extends` key from the output.)

### Step by step

**1. Resolve secure.json** (base, then secure's own keys):
```json
{"server": {"port": 8080, "host": "0.0.0.0", "tls": {"enabled": true, "cert": "/etc/ssl/app.pem"}},
 "features": ["auth"], "logLevel": "warn"}
```

**2. Resolve dev.json** (base, then dev's own keys):
```json
{"server": {"port": 3000, "host": "0.0.0.0", "tls": {"enabled": false}},
 "features": ["auth", "debug-panel"], "logLevel": "debug"}
```
dev.json never mentions TLS, but its resolved form still contains `tls.enabled: false`, inherited from base.json. Resolving a file means including everything it inherits.

**3. Apply them left to right: secure, then dev.**
- `server.port`: 8080 becomes **3000**
- `server.tls.enabled`: true becomes **false**, because dev's inherited copy of base is applied after secure
- `server.tls.cert`: survives, because deep merge only overwrites keys that dev's `tls` object has, and it has only `enabled`
- `features`: `["auth"]` is replaced by `["auth", "debug-panel"]`
- `logLevel`: `"warn"` becomes **`"debug"`**

**4. Apply app.json's own keys:**
- `server.host`: becomes `"127.0.0.1"`
- `server.tls.cert: null`: **deletes** the cert
- `features: ["auth", "billing"]`: **replaces the whole array**, so `"debug-panel"` is dropped

### Why this happens

- **TLS off.** This is a diamond dependency: base.json comes in twice, once through each parent. The later parent (dev) brings in its own full copy of base, including the `tls.enabled: false` default. "Last applied wins" works on whole resolved files, not on the file that set a value on purpose.
- **Debug panel 404.** Arrays replace wholesale, so app.json's `features` overrides the combined list completely. Nothing is appended.

### Other things staging is getting

- **Port 3000 and `logLevel: "debug"`**, both from dev.json. Staging is probably not meant to run with debug logging.
- **No cert.** Even if TLS were on, `cert: null` removes the path, so enabling TLS alone would probably fail at startup, or leave TLS without a cert, depending on how the service handles it.

### Fix: say what you mean in app.json

Swapping the order to `["dev.json", "secure.json"]` is not a clean fix. secure's resolved copy of base would then reset `port` to 8080 and `logLevel` to `"warn"`. That may or may not be what you want, but it swaps one hidden override for another. It's better to make the leaf file explicit:

```json
{
  "extends": ["secure.json", "dev.json"],
  "server": { "host": "127.0.0.1", "tls": { "enabled": true } },
  "features": ["auth", "debug-panel", "billing"],
  "logLevel": "warn"
}
```

Also:
- Drop `cert: null`, or set it to the staging cert path.
- Decide whether staging should inherit from dev.json at all. A dev overlay in a staging chain is where this surprise comes from.
- Longer term, keep base values out of overlays. Either give the loader a "resolve each shared ancestor once" rule, or make overlays like dev.json extend nothing, so they carry only their own changes.
