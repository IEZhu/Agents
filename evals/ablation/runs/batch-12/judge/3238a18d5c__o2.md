## Latest user message
I'm stuck on how to even approach this. We have a tool-using agent that does a 40-step onboarding workflow (create accounts, set permissions, send invites, etc.). Our per-step eval says each step is correct 92% of the time. The eval replays recorded sessions: at each step we feed the agent the recorded state up to that point and check its next tool call. But in real end-to-end runs only about 20% of workflows finish correctly. My manager wants to double down on improving per-step accuracy to 97%+. Is that the right move? How should I figure out what's actually going on?

## Rubric (what a strong answer does)
1. Does the arithmetic: independent 92% steps over 40 steps give about 0.92^40 ≈ 3.6% end-to-end, and notes that the observed 20% does not fit a simple independent-compounding model (errors are correlated, concentrated in some steps, or partly recovered).
2. Identifies that the per-step eval feeds the agent the recorded state rather than its own previous outputs, so it does not measure how the agent behaves after its own mistakes or on real live state, and recommends evaluating on the agent's own trajectories.
3. Proposes localizing failures in real end-to-end runs (e.g. finding the first divergent step per failed run and clustering by step or error type) before investing in uniform per-step accuracy gains.
4. Answers the manager's question directly: a blanket push to 97% per-step accuracy is not justified until the failure analysis is done, and suggests alternatives such as targeted fixes at the few steps where failures cluster, verification or recovery checks, or checkpointing.

## Answer A
**Short answer:** Probably not, at least not yet. Your two numbers don't agree with each other, and that disagreement tells you more than either number does. Work out why before you spend effort on per-step accuracy.

## 1. Check whether the numbers are consistent

If each step were independently correct 92% of the time, a 40-step workflow would succeed:

- 0.92^40 ≈ **3.6%**

But you observe **~20%**. That is better than the simple model predicts. To get 20% from 40 independent steps, each step would need about 0.2^(1/40) ≈ **96%** accuracy.

For comparison, if you hit your manager's target:

- 0.97^40 ≈ **30%**
- 0.99^40 ≈ **67%**

So two things follow:

1. **Your per-step eval is not measuring what drives end-to-end failure.** Errors aren't independent, the grader is miscalibrated, or both. Until you know which, you can't predict how much a per-step gain will help. It could help a lot, a little, or not at all.
2. **Even in the best case, 97% only gets you to about 30%.** Chaining 40 LLM decisions is fragile by nature. Per-step accuracy alone is unlikely to get you to a reliable workflow.

## 2. Likely explanations for the mismatch

| Hypothesis | What it means | How to test it |
|---|---|---|
| **Grader is too strict** | The eval marks valid alternatives as wrong (a different call order, equivalent arguments, an extra harmless lookup). The real 92% might be ~96%. | Hand-review 50–100 steps graded "wrong". Count how many were actually acceptable. |
| **Errors cluster** | A 92% average hides a few steps at 50–70% while most are ~99%. Some workflow types fail repeatedly and others never do. | Break per-step accuracy down by step index and by workflow type. Look at the distribution, not the mean. |
| **Some errors are harmless or recoverable** | Some wrong calls don't matter, or the agent fixes them on the next step. | In end-to-end traces, compare where the agent first diverged with whether the final state was still correct. |
| **Off-policy gap (the big one)** | Replay always feeds the agent the *recorded, correct* history. In real runs the agent sees its *own* history, including earlier slips. Replay never tests recovery or drift. | Replay from the agent's own failed trajectories. Inject small perturbations into recorded states and measure recovery. |
| **Environment differences** | Recordings don't capture real API errors, timeouts, rate limits, partial failures, non-idempotent retries (such as a duplicate invite) or eventual consistency (such as a permission set before the account has propagated). | Classify end-to-end failures as "agent picked the wrong call" or "the right call failed or behaved differently in production". |

## 3. How to find out what's going on

1. **Do error analysis on real failed runs first.** Pull 50–100 failed end-to-end traces. For each, record:
   - the first step where it went wrong
   - the error type: wrong tool, wrong arguments, skipped step, tool or environment failure, or bad recovery
   - whether the failure was caused by an earlier step

   Then build a failure taxonomy and count. This usually shows that 2–4 failure modes cause most of the damage.
2. **Audit the per-step grader.** Hand-label a sample to measure its false-negative and false-positive rates. If it's badly miscalibrated, the 92% means little, and so would a future 97%.
3. **Measure outcomes, not just trajectories.** Add an end-state check: accounts exist, permissions match the spec, invites were sent exactly once. That's the metric the business cares about. Make it the headline number.
4. **Add on-policy and recovery evals.** Test the agent from imperfect states, not just recorded ones. In real runs, "can it notice and fix a mistake?" may matter more than "does it get step N right on a clean history?"
5. **Map errors by step.** If a few steps cause most failures, targeted fixes will beat raising the average.

## 4. Levers that may beat per-step accuracy

- **Move deterministic parts into code.** A 40-step onboarding flow is probably mostly fixed sequence. If so, put the sequence in code and use the agent only where judgment is needed, such as parsing messy input or handling exceptions. That shortens the chain the agent controls, which is the biggest multiplier.
- **Add checkpoints and verification.** After key stages, read back the system state and confirm it before continuing.
- **Make tools idempotent and retry safely.** This removes a whole class of environment failures.
- **Break the workflow into stages with separate success checks.** That limits how far one error can spread.

## What to tell your manager

"Our per-step eval predicts ~4% end-to-end success, but we see 20%. So it isn't measuring what actually causes failures, and optimizing it may not move the real number. Even a perfectly measured 97% only gives ~30%. I'd like 1–2 weeks for error analysis on real failures, plus an end-state success metric. Then we can put effort where the failures actually are. That might be per-step accuracy, but it's just as likely to be recovery, a few hard steps, environment issues, or moving deterministic steps out of the agent."

I can't know which hypothesis dominates without seeing your traces. From experience, off-policy replay evals very often miss recovery and compounding, so I'd put that on your checklist first.


## Answer B
**Short answer: probably not, at least not yet.** Your per-step eval and your end-to-end result don't agree with each other, and that gap tells you more than the 92% does. Work out why they disagree before you pick a metric to push.

## 1. The numbers don't fit a simple model

If the 40 steps failed independently at 92%:

- 0.92^40 ≈ **3.6%** end-to-end success
- 0.97^40 ≈ **30%**
- 0.99^40 ≈ **67%**

You see **20%**, which is far above 3.6%. So the step errors are not independent, and the 92% isn't measuring what you think it is. Some likely explanations:

- **Errors cluster.** A few steps (or a few kinds of session) cause most of the failures, and the rest are close to 100%. An average of 92% hides this. If so, the fix is targeted, and "raise every step to 97%" is the wrong way to frame it.
- **The eval over-counts errors.** It checks the next call against the recorded call. Many "wrong" calls may be valid alternatives, such as a different argument order, an equivalent tool, or a harmless extra read. That makes the 92% pessimistic and noisy.
- **Some errors don't matter or get fixed later.** A bad step doesn't always sink the workflow.

Meanwhile, some real failure modes are **invisible** to your eval:

- **Replaying recorded state only tests the agent on states it has seen.** The agent is always given a clean, correct history. In production it acts on its own history, including its own mistakes. Your eval never measures what happens after a mistake: whether the agent notices, recovers or makes things worse.
- **Failures outside the model's decisions.** Tool errors, timeouts, API rate limits, partial writes, retries that create duplicates, and live state that differs from what was recorded.
- **Problems that grow over a long run.** Late steps with a long history, losing track of which accounts already exist, loops, stopping early or never stopping.

So a better score on this eval is not guaranteed to raise the 20%. You could reach 97% on replayed sessions and still fail live, because the thing that's breaking isn't being measured.

## 2. How to find out what's actually going on

In rough order of value per hour spent:

1. **Look at 30–50 failed real runs by hand.** For each one, find the **first step where it went wrong** and the **step where it became unrecoverable**. Tag the cause: wrong tool call, bad arguments, tool or environment error, lost track of state, no recovery, early stop, loop, eval false-negative. This alone will probably settle the question.
2. **Plot failures by step number.** Is the first-divergence step spread evenly, bunched at certain steps (for example, permissions), or rising toward the end (long history)? Each pattern points to a different fix.
3. **Break down the per-step eval.** Report accuracy per step and per session type instead of one average. Then hand-check a sample of the "incorrect" calls to find out how many were actually acceptable. Fix the grader if it's too strict.
4. **Add a live, end-to-end eval.** Run full workflows against a sandbox or mocked environment and score **the final state**: were the right accounts created, with the right permissions, and were the invites sent? Don't score how closely the calls match a recording. Make this the headline metric.
5. **Measure recovery directly.** Take recorded sessions, inject a realistic error at step k (a failed tool call, a wrong earlier action), and check whether the agent recovers. If it rarely does, recovery is worth more to you than per-step accuracy.

## 3. Likely fixes, depending on what you find

- **Failures cluster at a few steps:** improve those steps (prompting, tool design, examples) and leave the rest alone.
- **Failures cascade after errors:** add checks after important steps (read back the state and confirm the account exists), make tools idempotent so retries are safe, and give the agent clear error messages it can act on.
- **The agent loses track of state:** give it an explicit checklist or state object to work from, so it doesn't have to reconstruct progress from the chat history.
- **Environment problems:** add retries and backoff, and handle partial failures in the code around the tools, not in the model.
- **Steps that are mostly deterministic:** a 40-step onboarding is probably largely a fixed procedure. Consider taking the sequence out of the LLM's hands entirely. Let code run the workflow and use the model only for the steps that need judgment. This often gains more than any accuracy work.

## 4. What to tell your manager

"Per-step accuracy on replayed sessions doesn't predict end-to-end success. Under an independence model 92% should give about 4%, and we see 20%, so the metric is measuring something else. Before we invest in reaching 97%, give me about a week to (a) categorize real failures and (b) build an end-to-end eval scored on the final state. Then we'll target the failure modes that actually break workflows."

This isn't a rejection of the goal. Per-step accuracy may well turn out to matter for a few specific steps. The point is to confirm where the failures are before spending effort on them.
