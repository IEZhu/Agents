## Latest user message
Adding a sync job to root's crontab on Ubuntu 22.04 (stock cron package). Requirements: every 15 minutes, first run of the day at 08:00 and last run at exactly 18:00 (nothing after 18:00), Monday to Friday only, and only during the first 7 days of each month. Script is /opt/sync/run.sh. The schedule part I already have: `*/15 8-18 1-7 * 1-5`. What I need help with is wrapping it so two runs never overlap if one takes longer than 15 minutes, and so stdout+stderr get appended to /var/log/sync.log. Give me the final line(s) to paste.

## Rubric (what a strong answer does)
1. Points out that the hour field 8-18 with */15 also produces runs at 18:15, 18:30 and 18:45, and fixes it (e.g. an 8-17 line plus a separate `0 18` line).
2. Points out that when both day-of-month and day-of-week are restricted, cron runs the job when either one matches (OR), so `1-7 * 1-5` does not mean 'weekdays within days 1-7', and fixes it with a guard (e.g. day-of-week `*` plus `[ "$(date +\%u)" -le 5 ] &&`), escaping any `%` as `\%` inside the crontab line.
3. The final lines, taken together, fire at 08:00 through 18:00 inclusive every 15 minutes on Monday-Friday of days 1-7 only, and at no other times.
4. The final lines prevent overlapping runs (e.g. `flock -n` on a lock file) and append both stdout and stderr to /var/log/sync.log (e.g. `>> /var/log/sync.log 2>&1`).

## Answer A
Your schedule has two bugs, so you need two lines. Here they are, then the reasons.

```cron
# m     h     dom  mon dow  command
*/15    8-17  1-7  *   *    [ "$(date +\%u)" -le 5 ] && /usr/bin/flock -n /run/lock/sync.lock /opt/sync/run.sh >> /var/log/sync.log 2>&1
0       18    1-7  *   *    [ "$(date +\%u)" -le 5 ] && /usr/bin/flock -n /run/lock/sync.lock /opt/sync/run.sh >> /var/log/sync.log 2>&1
```

Add them with `sudo crontab -e`. Root's personal crontab has no user field.

## What was wrong with `*/15 8-18 1-7 * 1-5`

1. **It runs after 18:00.** `*/15` with hour `8-18` fires at 18:15, 18:30 and 18:45 too. The fix is two lines: `*/15 8-17` covers 08:00 to 17:45, and `0 18` adds exactly 18:00.
2. **Day-of-month and day-of-week are OR'd, not AND'd.** When both fields are restricted (neither is `*`), cron runs the job if *either* one matches. Your line would run on days 1-7 of the month (weekends included) **and** on every Monday-Friday of the month. The fix is to keep `1-7` in the day-of-month field, set day-of-week to `*`, and check the weekday in the command. `date +%u` gives 1=Mon through 7=Sun, so `-le 5` means Mon-Fri.

## The wrapper

- **`flock -n`** (from util-linux, at `/usr/bin/flock` on Ubuntu) takes an exclusive lock on the lock file before starting the script. If the previous run still holds the lock, the new one exits at once instead of waiting or running alongside it. Both lines use the **same** lock file, so the 18:00 run can't overlap a slow 17:45 run either.
- The lock is tied to the open file descriptor. If the script crashes, the kernel releases it, so you never get a stale lock. `/run/lock` is tmpfs and gets cleared on reboot, which is fine.
- **`\%`** matters: in a crontab an unescaped `%` becomes a newline. Without the backslash the `date` test breaks.
- **`>> /var/log/sync.log 2>&1`** appends both stdout and stderr. It applies to the whole `flock ... run.sh` command.

## Optional tweaks

- **Log skipped runs.** At the moment a skipped run leaves no trace. `flock -n -E 75 ...` makes flock exit with 75 when the lock is busy, so you can tell a skip apart from a script failure, e.g. `...; [ $? -eq 75 ] && echo "$(date) skipped: previous run active" >> /var/log/sync.log`. That makes the line noticeably longer.
- **Make sure 18:00 always runs.** If the last run must happen even when 17:45 is still going, use `flock -w 600` (wait up to 10 minutes) on the 18:00 line instead of `-n`.
- **Rotate the log.** `/var/log/sync.log` will keep growing, so add a small `/etc/logrotate.d/sync` entry.

## Verify

```bash
sudo crontab -l                                   # lines present
grep CRON /var/log/syslog | grep sync             # cron actually firing them
sudo flock -n /run/lock/sync.lock true; echo $?   # 0 = lock free, 1 = a run is active
```

## Answer B
Your schedule `*/15 8-18 1-7 * 1-5` has two bugs. Fix them before adding the wrapper:

1. **Runs after 18:00.** `*/15` with hour `8-18` fires at 18:15, 18:30 and 18:45 too. You need two lines: `*/15 8-17` plus `0 18`.
2. **The day-of-month and day-of-week fields are ORed, not ANDed.** When both fields are restricted (neither is `*`), cron runs the job if *either* one matches (see `man 5 crontab`). So `1-7 * 1-5` means "days 1–7 of the month, **or** any Monday–Friday". In practice that's every weekday of the month plus any weekend days that fall on the 1st–7th. Cron can't express an AND here. The fix is to keep `1-7` in the schedule, set day-of-week to `*`, and check the weekday in the command.

## Lines to paste (`sudo crontab -e`)

```cron
# Sync: every 15 min 08:00-18:00, Mon-Fri, days 1-7 only.
# The weekday is checked in the command because cron ORs day-of-month with day-of-week.
# flock -n: if the previous run still holds the lock, skip this run instead of overlapping.
*/15 8-17 1-7 * * [ "$(date +\%u)" -le 5 ] && /usr/bin/flock -n /run/lock/sync.lock /opt/sync/run.sh >> /var/log/sync.log 2>&1
0    18   1-7 * * [ "$(date +\%u)" -le 5 ] && /usr/bin/flock -n /run/lock/sync.lock /opt/sync/run.sh >> /var/log/sync.log 2>&1
```

What each part does:
- `\%` is required. An unescaped `%` in a crontab line is turned into a newline and cuts the command off.
- `date +%u` gives 1 for Monday through 7 for Sunday, so `-le 5` means Monday to Friday.
- `flock -n` gives up right away if the lock is held, so a run that takes longer than 15 minutes makes the next slot get skipped rather than run in parallel. Both lines use the same lock file, so the 18:00 run is covered too. The lock is released automatically when `run.sh` exits, including after a crash, so a stale lock file can't block future runs. `/run/lock` is a tmpfs and is cleared on reboot, which is fine.
- `>> /var/log/sync.log 2>&1` appends both stdout and stderr. It applies to the `flock` command, which covers the script's output.

## Caveats
- The `/usr/bin/flock` path is from memory (it's part of `util-linux`, which is installed by default). Check it with `command -v flock`.
- If a long 17:45 run is still going at 18:00, the 18:00 run is skipped. That's the price of "never overlap". If 18:00 must always run, use `flock -w 900` (wait up to 15 minutes) on that line only.
- Skipped runs leave nothing in the log. To log them, add `-E 0` plus a message, or wrap the job in a small script.
- `run.sh` needs to be executable (`chmod +x`), or call it as `/bin/bash /opt/sync/run.sh`.
- Consider adding a `logrotate` rule for `/var/log/sync.log`, because appending grows the file forever.
