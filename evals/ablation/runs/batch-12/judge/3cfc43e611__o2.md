## Latest user message
I need a cron entry on our Ubuntu 22.04 box (plain cron, not systemd timers) that runs /opt/reports/send_payroll.sh on Mondays, but kind of every other week, roughly 9 in the morning. The payroll team is in Berlin but the server clock is UTC. Something like `0 9 * * 1/2`? Just give me the line to paste into crontab -e.

## Rubric (what a strong answer does)
1. Explicitly restates the requirement it is solving (biweekly on Mondays, around 09:00 Berlin time, on a UTC server) before or alongside the crontab line
2. Points out that `0 9 * * 1/2` does not mean every other Monday and that standard cron has no native every-other-week syntax
3. Provides a working approach such as a weekly Monday entry plus a week-parity check inside the command or script, and if `%` is used inside the crontab line it is escaped as `\%`
4. Addresses the timezone mismatch instead of silently scheduling 09:00 UTC, e.g. by scheduling in UTC with the Berlin offset and noting that daylight saving time shifts it by an hour, or by checking Berlin local time inside the command

## Answer A
Don't use `0 9 * * 1/2`. It doesn't mean "every other Monday". A step in the day-of-week field counts days of the week, not weeks. Where it's accepted, `1/2` is read as `1-7/2`, so it fires on **Mon, Wed, Fri and Sun** (7 = Sunday). Some cron builds reject a start/step without a range, so behaviour may vary (from memory, not checked on your box). It would also run at 09:00 **UTC**, which is 10:00 or 11:00 in Berlin.

Plain cron can't do "every other week" or a different time zone on its own, so the line below puts both checks in the command:

```
0 7,8 * * 1 [ "$(TZ=Europe/Berlin date +\%H)" = 09 ] && [ $(( $(date +\%s) / 604800 \% 2 )) -eq 0 ] && /opt/reports/send_payroll.sh >> /var/log/payroll_cron.log 2>&1
```

**What each part does:**
- `0 7,8 * * 1`: runs every Monday at 07:00 and 08:00 UTC. 09:00 in Berlin is 07:00 UTC in summer (CEST) and 08:00 UTC in winter (CET).
- `TZ=Europe/Berlin date +%H` = `09`: only the run that lands at 09:00 Berlin time goes ahead, so DST changes are handled automatically.
- `$(date +%s) / 604800 % 2`: epoch seconds divided by one week, then even or odd. This alternates cleanly every 7 days. I used it instead of `date +%V` (ISO week number) because `%V` goes 53 then 1 across some year ends, which would run two weeks in a row.
- `\%`: crontab turns a bare `%` into a newline, so every `%` has to be escaped.
- I didn't use `CRON_TZ=Europe/Berlin` because, as far as I recall, Ubuntu's Debian-based cron doesn't support it (cronie does). Treat that as unverified.

**Choose which Mondays it runs.** Check which parity next Monday has:
```
echo $(( $(date -d 'next monday' +%s) / 604800 % 2 ))
```
If it prints `0`, the next run is next Monday. If you want the week after instead, change `-eq 0` to `-eq 1`.

**Verification:**
```
# check the conditions without sending anything (run in a normal shell, no escaping)
[ "$(TZ=Europe/Berlin date +%H)" = 09 ] && echo "hour ok"; echo "parity: $(( $(date +%s) / 604800 % 2 ))"
crontab -l                                   # confirm the line was saved
grep CRON /var/log/syslog | tail             # after a Monday: confirm cron fired at 07 and 08 UTC
tail /var/log/payroll_cron.log               # script output
```

A couple of other points:
- The script must be executable (`chmod +x /opt/reports/send_payroll.sh`). cron runs it with a minimal `PATH`, so use absolute paths inside the script or set `PATH=` at the top of the crontab.
- If the log path isn't writable by the crontab's user, change it (for example to `$HOME/payroll_cron.log`) or create the file first.


## Answer B
`0 9 * * 1/2` won't do what you want. In the day-of-week field, `1/2` means "start at 1, step 2", so it runs Mon, Wed and Fri every week. Plain cron has no "every other week" syntax, and it would fire at 09:00 UTC, which is 10:00 or 11:00 in Berlin.

Paste this:

```
0 7,8 * * 1 [ "$(TZ=Europe/Berlin date +\%H)" = 09 ] && [ $(( $(date +\%s) / 604800 \% 2 )) -eq 0 ] && /opt/reports/send_payroll.sh >> /var/log/send_payroll.log 2>&1
```

What each part does:
- `0 7,8 * * 1`: cron tries at 07:00 and 08:00 UTC every Monday. Berlin 09:00 is 07:00 UTC in summer (CEST) and 08:00 UTC in winter (CET).
- `TZ=Europe/Berlin date +\%H` = `09`: only the attempt that lands on 09:00 Berlin time continues, so the script runs once and the time follows DST. I'm not using `CRON_TZ` because, as I recall, Debian/Ubuntu's cron doesn't support it (cronie does). I haven't checked that on 22.04.
- `date +%s / 604800 % 2`: this is the week number counted from the Unix epoch, taken mod 2. It alternates every Monday without exception. ISO week parity (`date +%V`) doesn't: it breaks after 53-week years, and 2026 is one, so weeks 53 and 1 are back to back and both odd.
- `\%`: crontab turns a bare `%` into a newline, so it has to be escaped. Cron removes the backslash before running the command.

**Pick the right week.** Run this in a shell on a Monday you want payroll to go out (no escaping here):

```
echo $(( $(date +%s) / 604800 % 2 ))
```

If it prints `1`, change `-eq 0` to `-eq 1` in the crontab line. By my arithmetic Monday 2026-09-28 gives `0`, but check it before you rely on it.

**Verify:**
- `crontab -l`: confirms the entry was saved.
- `TZ=Europe/Berlin date +%H` at 07:00 and 08:00 UTC: shows which attempt passes the hour check.
- After the first Monday it should have run, look at `/var/log/send_payroll.log` and `grep CRON /var/log/syslog`.

**Risks:**
- The redirect writes to `/var/log/`. If this isn't root's crontab, that user needs write access there, or log somewhere else, e.g. `$HOME/send_payroll.log`.
- Cron runs with a minimal `PATH`. Make sure the script uses absolute paths or sets its own `PATH`, and that it's executable (`chmod +x`).
- If the server is down when the slot comes around, that run is skipped. Cron doesn't catch up on missed runs.
