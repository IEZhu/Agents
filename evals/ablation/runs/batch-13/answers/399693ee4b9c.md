**Short answer:** ConfigMaps aren't the problem here, and moving to a config service won't fix it. Env vars filled from a ConfigMap with `envFrom` are read **once, when the container starts**. Kubernetes never pushes ConfigMap changes into the environment of a pod that's already running. Your 6 pods are still using the environment they started with, so this would look the same 3 hours or 3 weeks later. `@lru_cache` would also keep the old value, but it's the second problem, not the first: even without the cache, `os.environ` in those pods still says the flag is off.

Fix it today with:

```bash
kubectl rollout restart deployment/<your-service>
kubectl rollout status deployment/<your-service>
```

A migration may still make sense, but only if you need **runtime** toggling: flipping a flag without a restart, percentage rollouts, per-user targeting, or a kill switch. If all you need is for config changes to stick, you can do that without a new vendor.

## 1. Make ConfigMap changes stick (do this regardless)

The goal is for any ConfigMap change to trigger a rolling restart automatically. Pick one of these:

- **Kustomize `configMapGenerator`**: it adds a content hash to the ConfigMap name. When the data changes, the name changes, the Deployment spec changes with it, and a rollout happens.
- **Helm checksum annotation** on the pod template:
  ```yaml
  annotations:
    checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
  ```
- **A controller such as Stakater Reloader**: annotate the Deployment and it restarts pods when the ConfigMap they reference changes. (I'm recalling the annotation key, `reloader.stakater.com/auto: "true"`, from memory, so check it against their README.)

Also add a guardrail so the pod's view of the config can be checked instead of guessed. For example, expose the loaded settings (minus secrets) or a config hash on an internal `/debug/config` endpoint or as a startup log line. You'd then have seen within a minute that the pods were never running the new value.

## 2. Separate config from flags

Your setup mixes two different kinds of data:

| | Static config | Feature flags |
|---|---|---|
| Examples | DB URL, timeouts, service endpoints | `ENABLE_NEW_CHECKOUT`, rollout percentages |
| Changes | Rarely, through a deploy | Often, with no deploy |
| Right home | ConfigMap + env + `BaseSettings` + `lru_cache` (fine as is) | Flag service with an SDK that caches in memory and updates in the background |

The key rule: **flags must never go through `get_settings()`.** If you move to LaunchDarkly or Unleash and read the flag into a cached `BaseSettings` object, you'll have the same "doesn't stick" bug with a vendor bill on top.

## 3. Which service for a team of 8

**I'd probably pick Unleash**, with LaunchDarkly as the pick if budget isn't a concern.

- **Unleash:** open source. You can self-host it (one small service plus Postgres) or use their hosted plan. It has a Python SDK, gradual rollouts, per-user targeting and a UI that non-engineers can use. For 8 people it covers nearly everything you'd want. The downside of self-hosting is one more stateful thing to run. The hosted plan removes that.
- **LaunchDarkly:** the most polished option, with streaming updates (changes land in seconds), good auditing and experimentation. The downside is cost, which grows with seats and usage. I don't have current prices, so check their pricing page against your MAU numbers. If budget isn't a constraint, it's the lowest-effort choice.
- **Consul KV + watcher:** I'd avoid this unless you already run Consul for something else. It's a key-value store, not a flag system. You'd have to build targeting, percentage rollouts, audit history, a UI, SDK-side caching and fallback defaults yourself. For 8 people that's a product you'd have to maintain.

(This is a judgment call based on team size and operating overhead, not measured data. If you already have Consul, or need data to stay inside your VPC, that changes the answer.)

## 4. Migration plan

1. **Stop the bleeding (day 0):** set up automatic restarts on ConfigMap changes (section 1) and add the config visibility endpoint.
2. **Add a flag abstraction (a few days):** put one small interface in front of flags so business code never imports the vendor SDK directly:
   ```python
   class Flags(Protocol):
       def is_enabled(self, name: str, ctx: FlagContext | None = None, default: bool = False) -> bool: ...
   ```
   Build `EnvFlags` first (reads your current settings) and route every existing flag read through it. This is a pure refactor with no behavior change.
3. **Add the vendor implementation:** `UnleashFlags` / `LaunchDarklyFlags`. Initialize the client **once per process** in the FastAPI lifespan startup, not per request and not inside `lru_cache`. Close it on shutdown. Every call passes a code-level `default`, so a vendor outage falls back to known-safe behavior.
4. **Migrate one flag at a time**, starting with `ENABLE_NEW_CHECKOUT`, since it's the one that needs runtime control. Create it in the service to match the current env value, then switch the reader. Only after it has been stable for a while, remove the env var from the ConfigMap.
5. **Keep static config where it is.** Only real feature flags move, not DB URLs or timeouts.
6. **Add flag hygiene:** give each flag an owner and an expiry date or cleanup ticket. After a year, stale flags usually cost more than the platform does.

### Gotchas to plan for
- **Multiple workers:** each Gunicorn/Uvicorn worker process has its own SDK client and background poller or stream. That's usually fine, but it multiplies connections (6 replicas × N workers). If you use `--preload`, initialize the client after the fork, not before, or the background thread won't survive the fork.
- **Propagation delay:** polling SDKs (Unleash's default interval is around 15 s as I remember it, so check the SDK docs) mean pods can disagree for a short window. Streaming (LaunchDarkly) narrows that window. For checkout, decide whether a user can see both code paths within one session. If not, target flags by user ID so the evaluation stays consistent.
- **Tests:** give `Flags` an in-memory fake so tests never call the vendor.

**Priorities:** restart the Deployment now and add a config-hash rollout this week. Then decide whether you actually need runtime flags. If you do, go with Unleash, or LaunchDarkly if cost doesn't matter, and put it behind your own interface.
