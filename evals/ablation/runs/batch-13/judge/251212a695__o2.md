# Онбординг бэкенд-разработчика: команда платежей

Документ читается примерно за 10 минут. Разделы независимы: можно читать и править любой отдельно.

**Как править:** меняйте только свой раздел. Если меняется правило, которое упоминается в других разделах (например, доступ в Vault или работа с `ledger_entries`), обновите короткие ссылки на него там же.

## 1. Первый день: запросите доступ в Vault

*Владелец раздела: тимлид команды платежей*

**В первый же день заведите тикет на доступ к секретам стейджинга в Vault.**

Пока доступа нет, вы:
- не поднимете локально заглушку платёжного шлюза;
- не сможете деплоить на стейджинг.

Выдача доступа занимает время, поэтому не откладывайте тикет до момента, когда он понадобится.

---

## 2. Локальное окружение

*Владелец раздела: ответственный за dev-окружение*

**Что нужно:** Docker с Compose и доступ к секретам стейджинга в Vault (см. раздел 1). Без Vault не запустится заглушка платёжного шлюза.

**Состав окружения:** Postgres 15 и Redis 7 поднимаются через docker compose.

**Шаги:**

```bash
# 1. Поднять инфраструктуру
docker compose up -d

# 2. Засидить основные данные
make seed

# 3. Отдельно засидить ledger: make seed его НЕ создаёт
make seed-ledger
```

**Частая ошибка:** данные есть, а проводок нет. Значит, забыли `make seed-ledger`.

---

## 3. Код-ревью

*Владелец раздела: core-команда*

- Каждый PR должен получить **минимум два апрува**.
- **Один из апрувов обязательно от участника core-команды.**
- Миграции, которые затрагивают `ledger_entries`, дополнительно требуют ревью от финконтроля (см. раздел 5).

## 4. Деплой

| Окружение | Как попадает | Когда |
|-----------|--------------|-------|
| Стейджинг | Автоматически после мёржа в `main` | Сразу |
| Прод | Через релизный чат | Только по **вторникам и четвергам** |

- Для деплоя на стейджинг нужен доступ в Vault (см. раздел 1).
- В другие дни выкладка в прод не делается.

## 5. Таблица `ledger_entries`: правила для прода

*Владелец раздела: финконтроль*

**На проде таблицу `ledger_entries` нельзя менять руками.** Никаких ручных `UPDATE`/`DELETE`/`INSERT`, даже для «быстрого фикса» во время инцидента.

Любое изменение делается так:
1. Пишется миграция.
2. Миграция проходит обычное код-ревью (см. раздел 3).
3. Миграцию дополнительно ревьюит финконтроль.

Про локальный ledger: он создаётся отдельной командой `make seed-ledger` (см. раздел 2).
