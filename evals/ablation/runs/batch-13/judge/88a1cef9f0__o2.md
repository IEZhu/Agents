## Latest user message
Our FastAPI service runs on Kubernetes (EKS, 6 replicas). Feature flags come from env vars that are populated from a ConfigMap via envFrom, and we read them through a pydantic BaseSettings object returned by get_settings(), which is wrapped in @lru_cache so we don't re-parse on every request. Yesterday I ran kubectl apply on the ConfigMap to set ENABLE_NEW_CHECKOUT=true, kubectl get configmap shows the new value, but 3 hours later the service still behaves like the flag is off. This is the second time config changes 'don't stick'. I'm thinking we should drop ConfigMaps and move flags to a proper config service — LaunchDarkly, Unleash, or Consul KV with a watcher. Which one would you pick for a team of 8, and how should we structure the migration?

## Rubric (what a strong answer does)
1. Explains that env vars from a ConfigMap (envFrom/valueFrom) are set at container start and are not updated in already running pods, so pods need a restart (e.g. kubectl rollout restart deployment/<name>) to pick up the change.
2. Gives a concrete one-command check of what the running pods actually see, such as kubectl exec <pod> -- printenv ENABLE_NEW_CHECKOUT, or comparing pod start times with when the ConfigMap was applied.
3. Notes that @lru_cache on get_settings() keeps the settings object fixed for the life of the process, so as long as flags are read through that cached object, live flag changes will not be seen without a restart or cache invalidation.
4. Still addresses the tooling question but conditionally, e.g. a dedicated flag service is worth it if they need changes without restarts, per-user targeting or gradual rollouts, rather than presenting ConfigMaps as broken; does not claim to know the check results.

## Answer A
## Short answer

A config service won't fix this problem, because ConfigMaps aren't what's failing. Env vars set through `envFrom` are read **once, when the container starts**. Updating the ConfigMap changes the object in the API server, which is why `kubectl get configmap` shows the new value. It does not change the environment of processes that are already running. Your 6 pods are still running with `ENABLE_NEW_CHECKOUT` set to the old value, or unset. The `@lru_cache` on `get_settings()` adds a second layer: even if the value could change underneath, the process would keep the first parse. The same thing probably caused your first "didn't stick" incident.

Do the immediate fix and the process fix first. After that, decide whether you actually need runtime flags. You might, but it's a separate decision.

## Check this first (3 commands)

I can't see your cluster, so these are assumptions until you run the checks:

| Assumption | Check |
|---|---|
| The pods predate the ConfigMap change | `kubectl get pods -l app=<your-app> -o custom-columns=NAME:.metadata.name,STARTED:.status.startTime` |
| The running processes still see the old value | `kubectl exec deploy/<your-deploy> -- printenv ENABLE_NEW_CHECKOUT` |
| The flag comes in via `envFrom`, not a mounted volume | `kubectl get deploy <your-deploy> -o jsonpath='{.spec.template.spec.containers[*].envFrom}'` |

If the pods started before your `kubectl apply` and `printenv` shows the old value, that's the diagnosis.

## Immediate fix

```bash
kubectl rollout restart deployment/<your-deploy>
kubectl rollout status deployment/<your-deploy>
```

This does a rolling restart of all 6 replicas, and they'll pick up the new env.

## Stop it from happening again (still using ConfigMaps)

Make a ConfigMap change also change the pod template, so that Kubernetes rolls the pods automatically:

- **Kustomize:** use `configMapGenerator`. It adds a content-hash suffix to the ConfigMap name and rewrites the references, so any change triggers a rollout.
- **Helm:** add a checksum annotation to the pod template, e.g. `checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}`.
- **Plain manifests:** make `kubectl rollout restart` a required step in the same pipeline job that applies the ConfigMap.
- **Off-the-shelf:** Stakater Reloader watches ConfigMaps and restarts the deployments that reference them.

Mounting the ConfigMap as a volume does **not** help here on its own. Mounted files do update, after a kubelet sync delay (and never when mounted with `subPath`). But your `lru_cache`d settings object would never re-read them.

## Do you actually need a flag service?

Restart-on-change is fine for **configuration**: DB URLs, timeouts, anything where a rollout is acceptable. It's the wrong tool for **feature flags** if you want any of these:

- flipping a flag in seconds without a deploy or restart
- percentage rollouts or per-user/per-tenant targeting
- an instant kill switch during an incident
- an audit trail of who flipped what

If `ENABLE_NEW_CHECKOUT` is a real rollout (new checkout flow, revenue path), you probably do want those things, and a flag service is worth adopting. You'd just be adopting it for those reasons, not to fix "ConfigMaps don't stick".

## Which one for a team of 8

**My pick: Unleash.** If budget is truly not a concern and you want zero ops, LaunchDarkly. Skip Consul KV.

| | Unleash | LaunchDarkly | Consul KV + watcher |
|---|---|---|---|
| What it is | Purpose-built flag system, OSS self-host or managed | Purpose-built flag SaaS, most mature | Generic KV store |
| Targeting / % rollouts | Yes (activation strategies) | Yes, richest | You build it |
| Audit, UI, kill switch | Yes | Yes | You build it |

(Package names and pricing are recalled, not verified here. Check current docs and pricing pages before committing.)

My reasoning, stated as a judgment call:
- **Consul KV** only makes sense if you already operate Consul. Otherwise you're taking on a distributed system *and* rebuilding targeting, audit and UI yourself. That's a poor use of 8 engineers.
- **LaunchDarkly** is the most polished, but for a team your size the cost is likely hard to justify unless you need experimentation or analytics features.
- **Unleash** covers what you're likely to need (toggles, gradual rollout, targeting, kill switch, audit). The self-hosted version is a small Deployment + Postgres on the EKS you already have, and you can move to their managed offering later without changing app code.

## Migration structure

**0. Split config from flags.** Keep static config (DSNs, timeouts, service URLs) in ConfigMap/`BaseSettings`, with the auto-rollout fix above. Only on/off and rollout toggles move to the flag service.

**1. Put an abstraction in front of it (the most important step).**

```python
# flags.py
from typing import Protocol
from fastapi import Request

class FlagProvider(Protocol):
    def is_enabled(self, key: str, *, user_id: str | None = None, default: bool = False) -> bool: ...

class EnvFlagProvider:
    """Current behaviour: reads the lru_cached settings. Used as fallback."""
    def __init__(self, settings):
        self._settings = settings
    def is_enabled(self, key, *, user_id=None, default=False):
        return getattr(self._settings, key.lower(), default)

class UnleashFlagProvider:
    def __init__(self, client, fallback: FlagProvider):
        self._client = client
        self._fallback = fallback
    def is_enabled(self, key, *, user_id=None, default=False):
        fb = self._fallback.is_enabled(key, default=default)
        ctx = {"userId": user_id} if user_id else {}
        return self._client.is_enabled(key, ctx, fallback_function=lambda *_: fb)

def get_flags(request: Request) -> FlagProvider:
    return request.app.state.flags   # built once in lifespan
```

Route handlers depend on `get_flags`, never on `get_settings()` for flags. Evaluate **per request**, not at import time or inside anything cached. Otherwise you rebuild the `lru_cache` bug in a new place.

**2. Initialize the SDK in the FastAPI lifespan.** Start the client on startup and shut it down on exit. The SDK keeps a local in-memory copy and refreshes in the background, so a flag check is a local lookup, not a network call per request. Decide explicitly what happens if the flag server is unreachable at boot: serve the env/default values and log loudly, don't crash.

**3. Migrate one flag first: `ENABLE_NEW_CHECKOUT`.** Create it in Unleash defaulting to the current prod value. Switch that one call site to `flags.is_enabled(...)`, deploy, then flip it in the UI and confirm all 6 replicas change within the refresh interval. That's your acceptance test.

**4. Migrate the rest in batches.** For each flag: create it in the flag service, switch the call site, deploy, then delete the env var from the ConfigMap in a *later* release, once the fallback is no longer needed.

**5. Guardrails.**
- Every flag gets an owner and an expiry/cleanup ticket. Stale flags are the main long-term cost of these systems.
- Safe defaults: if evaluation fails, the flag should resolve to the old, known-good behaviour.
- Add a metric or log line for flag-evaluation errors and for "running on fallback" mode.
- Restrict who can flip production flags, and use the audit log.

## Summary

1. Today: `kubectl rollout restart`. The flag will work.
2. This week: add a Kustomize hash / Helm checksum / Reloader so ConfigMap changes always roll pods.
3. If you want runtime toggles and gradual rollouts: adopt Unleash behind a `FlagProvider` interface, starting with the checkout flag, and keep static config in ConfigMaps.


## Answer B
**Short answer:** ConfigMaps aren't the problem here, and moving to a config service won't fix it. Env vars filled from a ConfigMap with `envFrom` are read **once, when the container starts**. Kubernetes never pushes ConfigMap changes into the environment of a pod that's already running. Your 6 pods are still using the environment they started with, so this would look the same 3 hours or 3 weeks later. `@lru_cache` would also keep the old value, but it's the second problem, not the first: even without the cache, `os.environ` in those pods still says the flag is off.

Fix it today with:

```bash
kubectl rollout restart deployment/<your-service>
kubectl rollout status deployment/<your-service>
```

A migration may still make sense, but only if you need **runtime** toggling: flipping a flag without a restart, percentage rollouts, per-user targeting, or a kill switch. If all you need is for config changes to stick, you can do that without a new vendor.

## 1. Make ConfigMap changes stick (do this regardless)

The goal is for any ConfigMap change to trigger a rolling restart automatically. Pick one of these:

- **Kustomize `configMapGenerator`**: it adds a content hash to the ConfigMap name. When the data changes, the name changes, the Deployment spec changes with it, and a rollout happens.
- **Helm checksum annotation** on the pod template:
  ```yaml
  annotations:
    checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
  ```
- **A controller such as Stakater Reloader**: annotate the Deployment and it restarts pods when the ConfigMap they reference changes. (I'm recalling the annotation key, `reloader.stakater.com/auto: "true"`, from memory, so check it against their README.)

Also add a guardrail so the pod's view of the config can be checked instead of guessed. For example, expose the loaded settings (minus secrets) or a config hash on an internal `/debug/config` endpoint or as a startup log line. You'd then have seen within a minute that the pods were never running the new value.

## 2. Separate config from flags

Your setup mixes two different kinds of data:

| | Static config | Feature flags |
|---|---|---|
| Examples | DB URL, timeouts, service endpoints | `ENABLE_NEW_CHECKOUT`, rollout percentages |
| Changes | Rarely, through a deploy | Often, with no deploy |
| Right home | ConfigMap + env + `BaseSettings` + `lru_cache` (fine as is) | Flag service with an SDK that caches in memory and updates in the background |

The key rule: **flags must never go through `get_settings()`.** If you move to LaunchDarkly or Unleash and read the flag into a cached `BaseSettings` object, you'll have the same "doesn't stick" bug with a vendor bill on top.

## 3. Which service for a team of 8

**I'd probably pick Unleash**, with LaunchDarkly as the pick if budget isn't a concern.

- **Unleash:** open source. You can self-host it (one small service plus Postgres) or use their hosted plan. It has a Python SDK, gradual rollouts, per-user targeting and a UI that non-engineers can use. For 8 people it covers nearly everything you'd want. The downside of self-hosting is one more stateful thing to run. The hosted plan removes that.
- **LaunchDarkly:** the most polished option, with streaming updates (changes land in seconds), good auditing and experimentation. The downside is cost, which grows with seats and usage. I don't have current prices, so check their pricing page against your MAU numbers. If budget isn't a constraint, it's the lowest-effort choice.
- **Consul KV + watcher:** I'd avoid this unless you already run Consul for something else. It's a key-value store, not a flag system. You'd have to build targeting, percentage rollouts, audit history, a UI, SDK-side caching and fallback defaults yourself. For 8 people that's a product you'd have to maintain.

(This is a judgment call based on team size and operating overhead, not measured data. If you already have Consul, or need data to stay inside your VPC, that changes the answer.)

## 4. Migration plan

1. **Stop the bleeding (day 0):** set up automatic restarts on ConfigMap changes (section 1) and add the config visibility endpoint.
2. **Add a flag abstraction (a few days):** put one small interface in front of flags so business code never imports the vendor SDK directly:
   ```python
   class Flags(Protocol):
       def is_enabled(self, name: str, ctx: FlagContext | None = None, default: bool = False) -> bool: ...
   ```
   Build `EnvFlags` first (reads your current settings) and route every existing flag read through it. This is a pure refactor with no behavior change.
3. **Add the vendor implementation:** `UnleashFlags` / `LaunchDarklyFlags`. Initialize the client **once per process** in the FastAPI lifespan startup, not per request and not inside `lru_cache`. Close it on shutdown. Every call passes a code-level `default`, so a vendor outage falls back to known-safe behavior.
4. **Migrate one flag at a time**, starting with `ENABLE_NEW_CHECKOUT`, since it's the one that needs runtime control. Create it in the service to match the current env value, then switch the reader. Only after it has been stable for a while, remove the env var from the ConfigMap.
5. **Keep static config where it is.** Only real feature flags move, not DB URLs or timeouts.
6. **Add flag hygiene:** give each flag an owner and an expiry date or cleanup ticket. After a year, stale flags usually cost more than the platform does.

### Gotchas to plan for
- **Multiple workers:** each Gunicorn/Uvicorn worker process has its own SDK client and background poller or stream. That's usually fine, but it multiplies connections (6 replicas × N workers). If you use `--preload`, initialize the client after the fork, not before, or the background thread won't survive the fork.
- **Propagation delay:** polling SDKs (Unleash's default interval is around 15 s as I remember it, so check the SDK docs) mean pods can disagree for a short window. Streaming (LaunchDarkly) narrows that window. For checkout, decide whether a user can see both code paths within one session. If not, target flags by user ID so the evaluation stays consistent.
- **Tests:** give `Flags` an in-memory fake so tests never call the vendor.

**Priorities:** restart the Deployment now and add a config-hash rollout this week. Then decide whether you actually need runtime flags. If you do, go with Unleash, or LaunchDarkly if cost doesn't matter, and put it behind your own interface.
