## Latest user message
PostgreSQL 14, таблица orders ~120 млн строк. Запрос вида SELECT ... FROM orders WHERE customer_id = $1 AND created_at >= now() - interval '30 days' ORDER BY created_at DESC LIMIT 50 выполняется ~4 секунды. Что уже сделали: 1) CREATE INDEX CONCURRENTLY idx_orders_cust_created ON orders (customer_id, created_at); в первый раз он упал с 'deadlock detected', запустили ещё раз — написало 'relation "idx_orders_cust_created" already exists', значит индекс есть. 2) Подняли shared_buffers с 128MB до 8GB в postgresql.conf (на сервере 32 GB RAM) и сделали SELECT pg_reload_conf(). Ничего не изменилось, всё те же 4 секунды. Похоже, Postgres упёрся в потолок. Сейчас выбираем между переездом этой таблицы в ClickHouse и партиционированием по месяцам. Что посоветуешь и как лучше мигрировать?

## Rubric (what a strong answer does)
1. Points out that a failed CREATE INDEX CONCURRENTLY can leave an INVALID index, so 'already exists' does not prove the index is usable, and gives a concrete check (e.g. \d orders, or querying pg_index.indisvalid) plus the fix (DROP INDEX CONCURRENTLY and recreate, or REINDEX).
2. Points out that shared_buffers requires a server restart and is not applied by pg_reload_conf(), with a concrete check such as SHOW shared_buffers or pending_restart in pg_settings.
3. Suggests running EXPLAIN (ANALYZE, BUFFERS) on the query to see whether the index is actually used before deciding on an architecture change, and notes that with a valid (customer_id, created_at) index this query shape should normally be fast.
4. Makes the ClickHouse/partitioning recommendation explicitly conditional on these checks (e.g. revisit only if the query is still slow with a valid index in use) rather than recommending a migration outright, and does not claim the check results are known.

## Answer A
Коротко: ни ClickHouse, ни партиционирование сейчас не нужны. Postgres не упёрся в потолок: скорее всего, оба ваших изменения просто не применились. Такой запрос на правильном индексе обычно отрабатывает за миллисекунды даже на 120 млн строк. Сначала почините индекс и настройки, потом измерьте.

## Что пошло не так

### 1. Индекс, скорее всего, INVALID

Сообщение `relation "idx_orders_cust_created" already exists` не значит, что индекс рабочий. Если `CREATE INDEX CONCURRENTLY` падает (в том числе с `deadlock detected`), Postgres не удаляет недостроенный индекс. Он остаётся в каталоге с флагом `indisvalid = false`. Планировщик такой индекс не использует, но при этом он продолжает обновляться при каждом INSERT/UPDATE. В итоге вы платите за индекс на записи и ничего не получаете на чтении.

Проверка:

```sql
-- indisvalid = false означает, что индекс битый и планировщик его игнорирует
SELECT c.relname, i.indisvalid, i.indisready
FROM pg_index i
JOIN pg_class c ON c.oid = i.indexrelid
WHERE c.relname = 'idx_orders_cust_created';
```

В `\d orders` такой индекс тоже будет помечен как `INVALID`.

### 2. shared_buffers не применился

`shared_buffers` меняется только перезапуском сервера. `pg_reload_conf()` его не применяет. Проверка:

```sql
SHOW shared_buffers;  -- скорее всего, всё ещё 128MB

-- pending_restart = true: значение в файле изменено, но ждёт рестарта
SELECT name, setting, unit, pending_restart
FROM pg_settings
WHERE name = 'shared_buffers';
```

8GB на 32GB RAM — нормальное стартовое значение (около 25% RAM — распространённая рекомендация). Но это не главная проблема: без рабочего индекса запрос всё равно будет читать огромную часть таблицы.

## Что делать

### Шаг 1. Пересоздать индекс

```sql
-- Удаляем битый индекс без блокировки записи в orders
DROP INDEX CONCURRENTLY IF EXISTS idx_orders_cust_created;

-- Строим заново. Выполнять вне транзакции (не внутри BEGIN, не в миграции с транзакцией)
CREATE INDEX CONCURRENTLY idx_orders_cust_created
    ON orders (customer_id, created_at);
```

Порядок колонок `(customer_id, created_at)` для вашего запроса правильный. Равенство идёт по первой колонке, диапазон и `ORDER BY created_at DESC` — по второй. B-tree читается в обратном порядке, поэтому отдельный `DESC` в определении индекса не нужен. План должен получиться вида `Index Scan Backward` + `Limit` без отдельного шага сортировки.

Перед повторным запуском разберитесь, откуда взялся deadlock, иначе история может повториться. `CREATE INDEX CONCURRENTLY` ждёт завершения всех транзакций, которые начались раньше него. Deadlock обычно получается, если параллельно шла другая DDL на этой таблице (второй `CREATE INDEX CONCURRENTLY`, `ALTER TABLE`, `VACUUM FULL`) или долгая транзакция, которая сама берёт конфликтующие блокировки. Точную причину покажет лог Postgres за то время, там указаны оба участника deadlock. На время сборки посмотрите в `pg_stat_activity`, нет ли долгих транзакций и сессий в статусе `idle in transaction`.

Сборка на 120 млн строк займёт заметное время (от минут до десятков минут, зависит от диска и `maintenance_work_mem`). В это время индекс создаёт дополнительную нагрузку на I/O. Прогресс можно смотреть так:

```sql
SELECT phase, blocks_done, blocks_total, tuples_done, tuples_total
FROM pg_stat_progress_create_index;
```

Компромисс: индекс немного замедлит INSERT и UPDATE затронутых колонок в orders и займёт место на диске (порядка нескольких GB — это оценка, реальный размер проверьте через `pg_relation_size`). Для OLTP-запроса такого вида это почти всегда оправдано.

### Шаг 2. Применить shared_buffers

Перезапустите Postgres в окно обслуживания (`systemctl restart postgresql` или аналог для вашей установки). Если есть реплики, учтите, что на standby `shared_buffers` задаётся отдельно. Заодно проверьте `effective_cache_size`: для 32GB RAM обычно ставят около 20–24GB. Эта настройка ничего не выделяет, только подсказывает планировщику, сколько данных, вероятно, лежит в кэше.

### Шаг 3. Измерить

```sql
ANALYZE orders;  -- обновить статистику после изменений

EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
FROM orders
WHERE customer_id = 12345
  AND created_at >= now() - interval '30 days'
ORDER BY created_at DESC
LIMIT 50;
```

Ожидаемый результат: `Index Scan Backward using idx_orders_cust_created`, время выполнения — миллисекунды или десятки миллисекунд. Это оценка, а не гарантия: многое зависит от того, сколько строк у одного клиента и насколько они разбросаны по heap. Если после этого запрос всё ещё медленный, пришлите вывод `EXPLAIN (ANALYZE, BUFFERS)`, и я посмотрю предметно. Без плана дальнейшие советы будут гаданием.

## Про ClickHouse и партиционирование

**ClickHouse для этого запроса не подходит.** Он рассчитан на аналитику: сканирование и агрегация больших объёмов по немногим колонкам. Точечная выборка «последние 50 заказов одного клиента» с `SELECT ...` по многим колонкам — типичный OLTP-запрос, и B-tree в Postgres справляется с ним лучше. К тому же ClickHouse не даёт транзакций и удобных UPDATE/DELETE, которые обычно нужны таблице заказов, а вы получите вторую систему с синхронизацией данных. Он имеет смысл как отдельная аналитическая реплика (например, через CDC), если у вас есть тяжёлые отчёты, но не как замена.

**Партиционирование по месяцам тоже почти ничего не даст именно этому запросу.** С рабочим индексом Postgres и так читает только нужные строки. Partition pruning отсечёт старые месяцы, но индексный поиск по `customer_id` уже делает это эффективнее. Партиционирование полезно для другого: быстрое удаление старых данных через `DETACH`/`DROP PARTITION` вместо массового `DELETE`, более лёгкий VACUUM, меньшие индексы. Если такие задачи появятся, к нему стоит вернуться. Но миграция 120 млн строк в партиционированную таблицу в PG 14 — это отдельный проект с копированием данных и переключением, и затевать его ради проблемы, которую решает один валидный индекс, не стоит.

## Итог по порядку действий

1. Проверить `indisvalid` и `SHOW shared_buffers`, чтобы подтвердить диагноз.
2. `DROP INDEX CONCURRENTLY` и повторный `CREATE INDEX CONCURRENTLY`, без параллельной DDL и долгих транзакций.
3. Рестарт Postgres, чтобы применить `shared_buffers`.
4. `ANALYZE` и `EXPLAIN (ANALYZE, BUFFERS)` до и после, с цифрами.
5. Если в production нет пулера соединений (PgBouncer или аналог), добавьте его. На этот запрос он не повлияет, но при нагрузке это обязательная вещь.

Сначала всё это стоит прогнать на staging, если там есть копия таблицы сопоставимого размера. Удаление битого индекса данные не затрагивает, но свежий бэкап перед работами с таблицей такого размера всё равно нужен.


## Answer B
Коротко: я бы пока не переезжал ни в ClickHouse, ни на партиционирование. Postgres здесь не упёрся в потолок: судя по вашему описанию, обе оптимизации на самом деле не применились. Запрос «последние 50 заказов одного клиента за 30 дней» по индексу `(customer_id, created_at)` на 120 млн строк обычно отрабатывает за единицы миллисекунд.

## Почему ничего не изменилось

### 1. Индекс, скорее всего, INVALID

Если `CREATE INDEX CONCURRENTLY` падает (у вас это был `deadlock detected`), Postgres **не удаляет** недостроенный индекс. Запись о нём остаётся в каталоге с флагом `indisvalid = false`. Повторный запуск видит это имя и выдаёт `already exists`, но планировщик такой индекс **не использует**. Так что сообщение «already exists» не значит, что индекс готов. Оно значит только, что имя занято.

Проверка:

```sql
-- Статус индекса: нужно indisvalid = true и indisready = true
SELECT c.relname, i.indisvalid, i.indisready
FROM pg_index i
JOIN pg_class c ON c.oid = i.indexrelid
WHERE c.relname = 'idx_orders_cust_created';
```

В `psql` это же видно через `\d orders`: у такого индекса будет пометка `INVALID`.

Исправление (обе команды без блокировки записи в таблицу):

```sql
-- 1. Удаляем битый индекс без блокировки записи в orders
DROP INDEX CONCURRENTLY idx_orders_cust_created;

-- 2. Строим заново. Выполнять вне транзакции и не параллельно с другим DDL по orders
CREATE INDEX CONCURRENTLY idx_orders_cust_created
    ON orders (customer_id, created_at);

-- 3. Обновляем статистику
ANALYZE orders;
```

Про deadlock. CIC ждёт завершения всех транзакций, которые держат снапшоты или блокировки на таблице. Deadlock обычно получается, когда параллельно шёл другой DDL, `VACUUM FULL`/`CLUSTER`, миграция или долгая транзакция, взявшая конфликтующую блокировку. Перед повторным запуском посмотрите, что ещё работает с таблицей:

```sql
SELECT pid, state, xact_start, wait_event_type, left(query, 100)
FROM pg_stat_activity
WHERE xact_start < now() - interval '5 minutes'
ORDER BY xact_start;
```

Пересоздавать индекс как `(customer_id, created_at DESC)` не нужно: B-tree прекрасно читается в обратном порядке, и `ORDER BY created_at DESC LIMIT 50` отработает через Index Scan Backward.

Компромисс: каждый новый индекс замедляет вставки в `orders`. Для одного B-tree на двух колонках это обычно приемлемо, но если запись идёт интенсивно, проверьте, нет ли уже индекса только по `customer_id`. После создания составного он станет лишним, и его можно удалить.

### 2. shared_buffers не применился

`shared_buffers` задаётся только при старте сервера, и `pg_reload_conf()` его не меняет. Нужен **рестарт** Postgres. Проверить:

```sql
SHOW shared_buffers;   -- скорее всего, всё ещё 128MB

SELECT name, setting, unit, pending_restart
FROM pg_settings
WHERE name = 'shared_buffers';   -- pending_restart = true означает, что ждёт рестарта
```

8 GB на сервере с 32 GB (около 25% RAM) — нормальное стартовое значение. Заодно при рестарте стоит выставить `effective_cache_size` примерно в 20–24GB (этот параметр применяется и через reload). Но важно понимать: даже с 128MB правильный индексный план не выполнялся бы 4 секунды. Главная проблема в индексе, а не в памяти.

## Что сделать после пересоздания индекса

Прогоните запрос с реальным значением `customer_id` и пришлите план, если он всё ещё медленный:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
FROM orders
WHERE customer_id = 12345
  AND created_at >= now() - interval '30 days'
ORDER BY created_at DESC
LIMIT 50;
```

Ожидаемо должно получиться `Index Scan Backward using idx_orders_cust_created` и время порядка миллисекунд. Если индекс валиден, а план всё равно `Seq Scan` или скан по индексу только на `created_at`, проверьте ещё две вещи:

- **Тип параметра.** Если `customer_id` имеет тип `bigint`, а драйвер передаёт `$1` как `numeric` или `text`, индекс может не использоваться. Это видно в плане: на колонке появится приведение типа.
- **Generic plan у prepared statements.** Если у вас сильный перекос (есть клиенты с миллионами заказов), после 5 выполнений Postgres может перейти на общий план, плохой для части клиентов. Диагностика: сравнить `EXPLAIN` через `PREPARE`/`EXECUTE` с обычным запросом. Как временное решение можно выставить `plan_cache_mode = force_custom_plan` для этой сессии или роли.

## Про ClickHouse и партиционирование

- **ClickHouse** для этого запроса подходит плохо. Это колоночная OLAP-СУБД, она сильна в агрегатах по миллиардам строк, а не в точечных выборках «50 строк одного клиента» с OLTP-нагрузкой рядом. К тому же вы получите вторую систему, синхронизацию данных и потерю транзакционности. Вам станет хуже, а не лучше.
- **Партиционирование по месяцам** этот запрос почти не ускорит. Отсечение партиций оставит 1–2 месяца, но внутри них всё равно нужен тот же индекс `(customer_id, created_at)`. Если индекса нет или он битый, партиции не спасут. Партиционирование стоит делать ради других задач: быстрое удаление старых данных через `DETACH`/`DROP PARTITION` вместо массового `DELETE`, более лёгкий VACUUM, архивирование. Если такие задачи появятся, к нему можно вернуться отдельно. Но это многоэтапная миграция 120 млн строк (новая партиционированная таблица, перенос батчами, переключение), и затевать её ради проблемы, которую решает один валидный индекс, не стоит.

## Порядок действий

1. Проверить `indisvalid`. Если там `false`, выполнить `DROP INDEX CONCURRENTLY` и `CREATE INDEX CONCURRENTLY`, затем `ANALYZE`. Сначала на staging, если есть такая возможность.
2. Перезапустить Postgres в окно обслуживания, чтобы применились 8GB `shared_buffers`, и проверить через `SHOW shared_buffers`.
3. Снять `EXPLAIN (ANALYZE, BUFFERS)` до и после, чтобы зафиксировать эффект в цифрах.
4. Если после этого запрос всё ещё медленный, пришлите план. Тогда разберём тип параметра и generic plan. К смене архитектуры имеет смысл возвращаться только после этого.

И ещё: если в проде нет пулера соединений (PgBouncer или аналога), его стоит добавить. На этот запрос он не повлияет, но при такой таблице и нагрузке это обязательный элемент.
