## What your measurements tell you

The useful detail is **tracemalloc flat at 110–130 MB while the container grows by gigabytes**. tracemalloc only sees allocations that go through Python's allocator. So the growth is in **native memory** that Python doesn't track, or in the page cache, which counts toward `working_set`. For an image-resizing service there are three likely causes, roughly in order of likelihood:

1. **Pillow pixel buffers that are never released.** Pillow allocates image data in C with its own allocator, outside `PyMem`. As I recall, tracemalloc doesn't see those buffers (not verified, confirm in the Pillow source). A leaked `Image` object costs only a few hundred bytes on the Python side, which tracemalloc sees, but it pins megabytes of pixels, which tracemalloc doesn't. That fits your picture exactly. Typical causes:
   - `Image.open()` without `with` or `.close()`
   - intermediate images (`convert()`, `resize()`, `thumbnail` copies) kept in a list, a cache, a closure or an exception traceback
   - an `lru_cache` or global dict holding images or BytesIO objects
2. **glibc malloc fragmentation across threads.** If your endpoints are `def` rather than `async def`, FastAPI runs them in a threadpool. glibc then creates a separate malloc arena per thread, and large short-lived buffers of varying sizes fragment those arenas. RSS grows even though everything gets freed. This usually levels off eventually instead of growing linearly forever, so I'd rank it second. It's cheap to rule out, though.
3. **Page cache or tmpfs from uploads.** Starlette spools uploads above ~1 MB to a temp file (recalled threshold, check your version). If `/tmp` is an `emptyDir` with `medium: Memory`, or files aren't closed and deleted, that memory lands in the container's cgroup as `shmem` or file cache, not in the process heap.

## How to tell them apart (about 30 minutes of work)

**Step 1: split the metric.** Plot `container_memory_rss` and `container_memory_cache` next to `working_set`, or read `memory.stat` inside the pod:

```bash
kubectl exec <pod> -- cat /sys/fs/cgroup/memory.stat | grep -E '^(anon|file|shmem) '
kubectl exec <pod> -- df -h /tmp
```

- `anon` grows → it's in the process: cause 1 or 2.
- `file` or `shmem` grows → cause 3.

**Step 2: count live Pillow images.** Add a temporary debug endpoint, protected or internal only, and call it every few minutes under traffic:

```python
import gc
from collections import Counter

from PIL import Image


@app.get("/_debug/pil")
def pil_objects() -> dict[str, int]:
    gc.collect()
    live_images = [obj for obj in gc.get_objects() if isinstance(obj, Image.Image)]
    return {
        "live_images": len(live_images),
        "live_pixels": sum(img.width * img.height for img in live_images),
        **{f"type:{name}": count for name, count in Counter(type(img).__name__ for img in live_images).most_common(5)},
    }
```

If `live_images` keeps rising with traffic, it's cause 1. `gc.get_referrers()` on one of the images will show you what's holding it.

**Step 3: test the allocator.** Redeploy one pod with only this change:

```yaml
env:
  - name: MALLOC_ARENA_MAX
    value: "2"
```

If memory levels off, it's cause 2. You can keep that setting, or switch to jemalloc via `LD_PRELOAD` (the path depends on your base image).

**Step 4 (if still unclear): profile native memory.** `memray run --native` tracks C-level allocations, including Pillow's, and gives you a flame graph of who allocated the memory that's still live (recalled flag, check `memray run --help`). Reproduce it locally with a load loop of ~1000 uploads and compare the start and end.

## The resize path, written so it can't leak

For comparison, this is how the resize path should look. It closes every image deterministically and uses `draft()` so JPEG decoding happens at reduced size, which cuts peak memory a lot for large photos:

```python
import io

from fastapi import HTTPException, UploadFile
from fastapi.responses import Response
from PIL import Image, UnidentifiedImageError

MAX_SIDE = 1024
JPEG_QUALITY = 85


@app.post("/resize")
def resize(file: UploadFile) -> Response:
    try:
        with Image.open(file.file) as src:
            src.draft("RGB", (MAX_SIDE, MAX_SIDE))  # JPEG-only; no-op for other formats
            src.thumbnail((MAX_SIDE, MAX_SIDE))     # in place, no extra copy kept around
            rgb = src if src.mode == "RGB" else src.convert("RGB")
            try:
                out = io.BytesIO()
                rgb.save(out, format="JPEG", quality=JPEG_QUALITY)
            finally:
                if rgb is not src:
                    rgb.close()
    except UnidentifiedImageError as exc:
        raise HTTPException(status_code=422, detail="Unsupported image format") from exc
    finally:
        file.file.close()
    return Response(content=out.getvalue(), media_type="image/jpeg")
```

Also check that `Image.MAX_IMAGE_PIXELS` is set to a sane value, so a single huge upload (or a decompression bomb) can't spike memory by itself.

## Stopgap while you investigate

If you need stability now, the honest version of "nightly restart" is recycling after N requests, not on a timer. uvicorn has `--limit-max-requests`. With a single worker, though, the process simply exits and Kubernetes restarts the container, so you'll see restarts, just not OOMKills. Gunicorn with `UvicornWorker`, `--max-requests` and `--max-requests-jitter` recycles workers gracefully instead. I haven't checked those flags against your versions, so confirm with `--help`. Either way, treat this as a stopgap, not the fix.
