**Set minReplicas to 12, but also cut the Hikari pool to about 20 per pod.** The pods aren't the real constraint here: the database is. If the change request only raises minReplicas, it will very likely make Black Friday worse.

### Pod math (CPU)

- Today you're at 4 pods × 60% CPU, which is about 2.4 pods' worth of CPU for 400 rps.
- At 3x (1,200 rps) you need about 7.2 pods' worth of CPU, assuming load scales linearly.
- If you want each pod at roughly 60% at peak, so there's room for spikes and the HPA has time to react: 7.2 / 0.6 = **12 pods**.
- Set maxReplicas to about 16 so a traffic spike above 3x can still scale out.

### Why 12 pods with the current pool breaks things

**1. Connections.** 12 pods × 50 connections = **600**, but RDS `max_connections` is **400**. Even at 8 pods you'd hit the limit. A rolling deploy with `maxSurge` adds more pods, and each new pod opens its own pool, so you'd go over even sooner. Once the limit is hit, new pods fail on connection errors and the checkout API starts returning errors.

You don't need 50 connections per pod anyway. By Little's law, 1,200 rps × about 0.15–0.18 s ≈ 180–220 requests in flight across the whole fleet, and only part of each request's time is spent holding a DB connection. With a pool of **20 per pod**:
- 12 pods × 20 = 240 connections
- 16 pods × 20 = 320 connections
- That leaves room under 400 for surge pods, migrations, admin sessions and the connections RDS reserves for itself.

If you ever need more than that, put RDS Proxy or PgBouncer in front of the database.

**2. Database CPU.** RDS is at 45% CPU at 400 rps. If that scales linearly, 1,200 rps needs about **135%**. It probably won't be exactly linear, since lock and buffer contention usually make things worse under load, not better. So the primary as it stands probably can't handle 3x, however many pods you add. Options, roughly in order of effort:
- **Move up an instance class** before the event. This is the fastest fix, and you can scale back down afterwards. It costs more per hour while it runs.
- **Move read-only queries to a read replica**, if checkout has any (price and inventory lookups, for example).
- **Find and fix the top queries** using Performance Insights or `pg_stat_statements`.

### What to put in the change request

1. Deployment/HPA: `minReplicas: 12`, `maxReplicas: 16`.
2. Hikari `maximumPoolSize: 20`. Consider setting `minimumIdle` equal to it so the pool doesn't churn connections.
3. RDS: resize the instance class before the event, with a rollback date to scale back down.
4. Make sure the node group or Karpenter can actually schedule 16 pods. Check the ASG max and your EC2 vCPU quota.

**Blast radius:** if the database saturates, every checkout slows down or fails, not just some of them. If the pods run short, you get higher latency, which the HPA can recover from.

**Rollback:** the pod count and pool size are config-only changes, so reverting them is easy. An RDS resize means a Multi-AZ failover of a minute or two in each direction, so schedule it outside peak hours.

### Before you commit to these numbers

Everything above assumes load scales linearly from a single data point. **Load-test at 1,200 rps against a production-sized database** before Black Friday, and watch pod CPU, Hikari pending threads, RDS CPU and `DatabaseConnections`. If you can't test in time, add more headroom on the database side rather than the pod side.
