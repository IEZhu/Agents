## Bottom line

I can write this runbook, but I don't think this plan fits the 6-hour window as written, so I wouldn't send it to on-call yet. The rehearsal timed only the **restore**. The real night has to fit **dump + restore + ANALYZE + cutover + smoke test**, and it also has to leave room to roll back. Add it up and there is no slack at all:

| Step | Duration | Source |
|---|---|---|
| Maintenance mode, drain Celery, quiesce DB | ~20 min | estimate |
| `pg_dump -Fd -j 8` of 1.2 TB | **unknown**, probably 1–2 h | not measured in the rehearsal |
| `pg_restore -j 8` | 3h50m | rehearsal |
| ANALYZE on Aurora (required, see below) | ~15–45 min | estimate |
| Secret switch, pod restarts, smoke test | ~20–30 min | estimate |
| **Total** | **~6h05m – 7h45m** | against a 6h00m window |

Three things make it worse than the table shows:

1. **The 480 GB table sets the minimum time.** `-j 8` runs one table per worker. That one table is dumped by a single worker, COPY'd by a single worker, and its indexes are built after it loads. Adding more `-j` does not shorten this part.
2. **pg_restore does not carry planner statistics** into PG 15. If you open traffic before ANALYZE finishes, Django queries run on default estimates and you can get very slow plans at 05:00 on the heaviest tables. ANALYZE is a required step, and the rehearsal's "everything came up fine" probably didn't include production load on un-analyzed tables.
3. **There's no rollback time budgeted.** Rolling back is cheap because the old primary is untouched: re-enable logins, point the secret back, restart pods. That still takes about 20–30 minutes, so you have to decide to abort by about **04:30**. On the numbers above, the restore is still running at 04:30.

Here's what I'd do, in order of preference:

- **Option A (recommended): logical replication PG 12 → Aurora 15.** The bulk copy runs online during the week, and Saturday becomes a cutover of about 30 minutes. Sketch below.
- **Option B: keep dump/restore, but earn the window first.** Before Saturday, run a full end-to-end rehearsal against a *quiesced, prod-sized* source on the same instance classes, timing dump + restore + analyze. Proceed only if that total is **≤ 4h15m**. That leaves time for maintenance mode, smoke tests and a rollback before 05:00. If it's over, either get a bigger window or switch to Option A.

The runbook below is for Option B, with hard go/no-go gates, so it stays safe even if the timings slip.

## Runbook: PG 12 → Aurora PG 15 cutover (dump/restore)

**Roles:** Incident lead (IL, makes the go/no-go calls), DB operator (DBO), App operator (APP, EKS/secrets), Smoke tester (QA).
**Comms:** one bridge channel. IL posts a timestamp at every gate.

### T-7 days to T-1 day: prerequisites (all must be done)

- [ ] **Full timed rehearsal** as described in Option B. Record dump time, restore time and ANALYZE time, and update the timings below with the real numbers.
- [ ] **Roles pre-created on Aurora.** pg_dump doesn't dump roles, and Aurora has no true superuser, so roles with `SUPERUSER` or replication attributes won't restore as-is. Create the app, read-only and migration roles and their grants by hand.
- [ ] **Extensions:** compare `SELECT extname, extversion FROM pg_extension;` on the source with what Aurora PG 15 supports. Create them on Aurora in advance.
- [ ] **Client binaries:** run the dump and restore with **PG 15** `pg_dump`/`pg_restore`. The newer pg_dump against the older server is the supported direction.
- [ ] **Restore host:** an EC2 instance in the same region and VPC as Aurora, with enough local disk for the directory-format dump (size it from the rehearsal dump size plus 30%). Check the network path from the PG 12 box to that host and measure its throughput. At about 1 Gbps, moving ~600–800 GB of dump takes well over an hour on its own.
- [ ] **Aurora sizing and connections:** instance class sized for the restore. Confirm `max_connections` covers 14 pods × pool size + 3 Celery deployments × concurrency + headroom.
- [ ] **Aurora parameter group for the load window:** autovacuum off during the restore, and a generous `maintenance_work_mem` for index builds. Revert both before opening traffic. Check how Aurora 15 applies these (dynamic or needs a reboot) in the parameter group docs, because I haven't verified that here.
- [ ] **TLS:** confirm whether the Aurora cluster enforces SSL (`rds.force_ssl`). If it does, make sure the new `DATABASE_URL` or Django `OPTIONS` sets `sslmode` correctly. I recall newer RDS/Aurora PG versions default this on, but I haven't verified it.
- [ ] **Django compatibility:** the app's Django and psycopg versions support PG 15, and the app test suite has passed against the rehearsal Aurora cluster.
- [ ] **Migration freeze:** no Django migrations merged from T-2 days.
- [ ] **Inventory of every DB client**, not just the 14 pods and 3 Celery deployments: Celery beat, CronJobs, BI/reporting users, ETL, admin scripts. Each one needs a stop step.
- [ ] **New secret staged:** the Aurora `DATABASE_URL` stored as a separate secret version, not yet active. The rollback secret (current value) is recorded.
- [ ] **Smoke test script** written and run against the rehearsal cluster: login, read path, write path, one Celery task end-to-end, and the 5 heaviest endpoints with latency checks.
- [ ] **Row-count and checksum queries** prepared for about 10 key tables. For the 480 GB table use `max(id)` and a count over a recent range, because an exact `count(*)` takes too long.

### Saturday timeline

Times are in UTC. Replace the times marked (est.) with rehearsal numbers.

**22:00 — Pre-flight (T-60)**
- IL: bridge open, roles confirmed, go/no-go on staffing.
- DBO: disk space on the restore host; Aurora cluster healthy and empty apart from roles and extensions; load-window parameters active.
- DBO: take a snapshot or base backup of PG 12 if your normal backups aren't recent. This gives a fallback that doesn't depend on the dump.
- APP: confirm the maintenance-mode toggle works; the staged secret is in place.

**23:00 — Maintenance mode**
- APP: enable maintenance mode, which serves a 503 page.
- APP: stop Celery beat first, then let workers finish in-flight tasks (cap at 10 min), then scale the 3 worker deployments to 0. Queued tasks stay in the broker and run after cutover. Make sure that's acceptable for any time-sensitive tasks.
- APP: suspend CronJobs and stop the other clients from the inventory.

**23:15 — Quiesce the source**
- DBO: `ALTER ROLE <app_role> NOLOGIN;` for every application role, then terminate the remaining sessions with `pg_terminate_backend` on those roles.
- DBO: check `pg_stat_activity`. Only DBO sessions may remain.
- DBO: leave these roles `NOLOGIN` **after** cutover too. That way a stray pod or cron job with the old secret cannot write to PG 12 and split the data.

**23:20 — Dump**
- DBO: run `pg_dump -Fd -j 8 -f /data/dump <db>` (PG 15 binary) against the primary.
- Watch progress by the size of the dump directory. Expect the 480 GB table to finish last.
- **Gate G1:** the dump must finish by **(23:20 + rehearsal dump time + 15%)**. If it runs past that, IL calls **ABORT**.

**~00:50 (est.) — Restore**
- DBO: `pg_restore -j 8 -d <aurora_db> /data/dump`, with `maintenance_work_mem` raised for the session (for example via `PGOPTIONS`).
- Log to a file and grep for `ERROR` as the restore runs. Some ownership and extension errors are expected. Anything on tables or indexes is a stop.
- **Gate G2 at 03:30:** the data section is done and index builds are in progress. If the 480 GB table's COPY is still running, **ABORT**.

**~04:40 (est.) — Post-restore**
- DBO: `vacuumdb --analyze-only -j 8 -d <aurora_db>`. Use `--analyze-in-stages` if you need usable stats sooner.
- DBO: revert the load-window parameters (autovacuum back on).
- DBO: compare row counts, `max(id)` and sequence values with the source. Spot-check that sequences are ahead of `max(id)` on the busiest tables.
- DBO: take a manual Aurora cluster snapshot (quick; it's your "restored and clean" point).

**Gate G3, the point of no return: by 04:30 at the latest if you follow this schedule.** Once any production write lands on Aurora, rolling back means losing that data. IL makes an explicit GO/ABORT call here.

**Cutover (about 25 min)**
- APP: activate the Aurora secret, then do a rolling restart of the 14 pods. Confirm that every pod has the new host, for example by logging the DB host on startup.
- APP: scale Celery workers up, then beat.
- QA: run the smoke tests with the site still in maintenance mode (allowlisted IPs or an internal route).
- **GO →** APP disables maintenance mode.

**After opening — 60 min hypercare**
- Watch: p99 latency against the pre-migration baseline, 5xx rate, Aurora CPU, `DatabaseConnections`, the slowest queries in `pg_stat_statements`, and Celery queue depth.
- Keep PG 12 running and `NOLOGIN` for at least 7 days. Decommission it later with a separate change.

### ABORT procedure (about 20–30 min, must start by the gate time)

1. DBO: stop the dump or restore. Leave Aurora as it is, or drop the database.
2. DBO: `ALTER ROLE <app_role> LOGIN;` on PG 12.
3. APP: make sure the secret still points at PG 12, restart pods, start Celery workers and beat, resume CronJobs.
4. QA: smoke test against PG 12, then APP disables maintenance mode.
5. IL: post a status update. The retrospective uses the gate timings to plan the next attempt.

## Option A sketch: logical replication, ~30 min downtime

This is the approach I'd push for. PG 12 supports native logical replication as a publisher, and Aurora PG 15 can subscribe.

**Weekdays, online:**
1. On PG 12, set `wal_level = logical` (plus `max_replication_slots` and `max_wal_senders`). This **needs a restart**, so do it in a short approved blip or reuse an existing patch window.
2. Every table needs a primary key or a `REPLICA IDENTITY`. Django tables usually have PKs, but check M2M and legacy tables.
3. Load the schema on Aurora with `pg_dump --schema-only`, then `CREATE PUBLICATION ... FOR ALL TABLES` on PG 12 and `CREATE SUBSCRIPTION` on Aurora.
4. The initial copy of the 480 GB table runs for hours, but with the site online. **Main risk:** the replication slot holds WAL on PG 12 until the copy catches up. Watch disk use on the source closely, because a full disk takes down production.
5. Freeze DDL and migrations from here until cutover, because DDL isn't replicated.

**Cutover night:**
1. Enable maintenance mode, stop Celery and crons, set app roles to `NOLOGIN` on PG 12.
2. Wait until the replication lag is 0.
3. **Sequences aren't replicated**: run `setval()` on every sequence on Aurora, from source values plus a margin.
4. ANALYZE (already done after the initial sync; refresh the hot tables), switch the secret, restart, smoke test, open.

Downtime is roughly 20–40 min, and the rollback is still simple. The costs are the one PG 12 restart, several days of DDL freeze, and WAL disk monitoring. AWS DMS is the managed alternative. For a same-engine PG→PG move, I'd expect native logical replication to be simpler and more faithful (types, constraints), but test that on your schema.
