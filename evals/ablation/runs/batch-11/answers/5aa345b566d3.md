**Short answer: no.** Opus plus a few examples will probably make the prose better and might cut the errors somewhat, but it won't make the notes reliable. All three failures come from the structure of the job. You are asking one call to do four things at once over about 90k tokens: find every relevant change, classify each one, pull out facts like rollout status, and write polished copy that fits on one page. When those are combined, the model silently drops items, classifies by feel, and lets writing style override the facts. Split the stages and check them with code instead of hoping the prompt holds.

## Why each failure happens

| Symptom | Likely cause | Why a bigger model / more prompt won't fix it |
|---|---|---|
| Real features missing | Recall across ~300 items in one long context, plus the "max 1 page" limit forcing silent cuts. Items in the middle of long contexts get less attention (Liu et al., 2023, "Lost in the Middle"). | The model still has to pick about 20 items out of 300 in a single pass, and nothing records what it dropped. |
| Dependency bumps / flag cleanup listed as "improvements" | Classification is implicit and mixed into writing. "Improvements" is a catch-all, and a model writing notes tends to fill it. | Examples show tone, not a decision rule. |
| Flagged feature described as GA | Rollout status is a fact buried in one PR body. Summarising favours clean marketing language like "now available". | "Double-check rollout status" is an instruction with no check behind it. It will work sometimes. |

## Recommended pipeline

```
[0] Deterministic pre-filter  →  [1] Per-PR extraction (LLM, structured)
      →  [2] Deterministic validation + grouping  →  [3] Writer (LLM, curated input only)
      →  [4] Verifier (code + LLM)  →  [5] PM review artifact
```

### Stage 0: Deterministic pre-filter (no LLM)
Remove the obvious noise before the model sees it:
- Author is a bot (dependabot, renovate, github-actions).
- Conventional-commit prefixes `chore:`, `ci:`, `build:`, `deps:`, `test:`, if your repos use them.
- Only files like `.github/**`, lockfiles or test directories changed.
- Labels such as `internal`, `no-release-note`.

Don't delete these PRs. Log them as `excluded_by_rule` so PMs can see them. This stage alone should fix most of the "dependency bump as improvement" cases.

### Stage 1: Per-PR extraction (one small call per PR, or per linked Jira epic)
Each call sees one PR, its linked Jira summary and a short instruction, and returns strict JSON:

```json
{
  "pr": "repo#1234",
  "customer_facing": true,
  "category": "feature | improvement | bugfix | internal",
  "internal_reason": null,
  "feature_key": "bulk-export",
  "customer_summary": "Admins can export up to 50k rows as CSV.",
  "rollout": {
    "status": "ga | flagged_partial | beta | internal_only | unknown",
    "evidence": "quoted text from PR/Jira, or null"
  },
  "confidence": "high | medium | low"
}
```

Key rules for this prompt:
- **Evidence is required.** `rollout.status` can't be `ga` unless there is quoted evidence. With no evidence it must be `unknown`, never assumed GA.
- **Give a definition of `internal`, with examples of borderline cases** (flag cleanup, refactor, dependency bump, telemetry). This is the right place for few-shot examples, not the writing prompt.
- **`feature_key`** groups the several PRs that make up one feature across your 6 repos.

This task is narrow and structured, so a small model (Haiku or Sonnet) should be enough. Check that on your own data (see Evaluation below).

### Stage 2: Deterministic validation and grouping (code)
- Merge PRs by `feature_key`. The combined rollout status is the most restrictive one in the group: any `flagged_partial` or `unknown` means the feature is not GA.
- **Best fix for rollout status:** if you use a feature-flag system (LaunchDarkly, Unleash, a homegrown one), look the flag up through its API and use that as the source of truth. PR text is a weaker signal. Even better, add required `Release note:` and `Rollout:` fields to the PR template, so the author states it at merge time. Kubernetes uses a similar release-note block in its PRs (recalled, not verified). This moves the problem upstream, which is cheaper than any prompt.
- Send `low` confidence and `unknown` rollout items to a review list rather than dropping them.

### Stage 3: Writer (one call, small input)
The input is only the validated feature groups, not 90k tokens of raw PRs, so probably a few thousand tokens. The prompt:
- Each bullet must end with hidden PR references (for example `<!-- repo#1234 -->`).
- Wording is set by rollout status: `flagged_partial` → "Rolling out gradually / available on request", `beta` → "Beta". This is a mapping, not a judgment call.
- **Give the ranking to the writer explicitly.** Either rank by a priority field (Jira priority, epic, PM-tagged) or ask the writer to return `included` and `omitted_with_reason`. Dropping items for length is fine; dropping them silently is the bug.

Your good-notes examples belong here. They help with tone and format.

### Stage 4: Verifier
Code checks (cheap and reliable):
- Every bullet cites at least one PR, and every cited PR exists and is `customer_facing`.
- **Coverage:** every customer-facing `feature` group is either in the notes or in `omitted_with_reason`.
- No bullet uses GA language ("now available", "all customers") when its group isn't `ga`. A keyword/regex check covers most of this, and an optional small LLM check can catch paraphrases.

On failure, rerun the writer once with the error list. If it still fails, flag it in the output instead of hiding it.

### Stage 5: PM review artifact
Output the notes plus three short lists: **omitted customer-facing items (with reason)**, **rollout unknown**, **excluded by rule/model**. PMs then review a diff instead of re-reading 300 PRs, and each correction they make becomes a test case.

## Cost and runtime
- Token volume should stay in the same range as today. The ~90k tokens of PR content get spread over about 300 small calls, and the writer's input is small. The per-call instruction is repeated about 300 times, so keep it tight and use **prompt caching** on the shared prefix.
- Since this runs overnight, the **Message Batches API** is a good fit. As I recall it is about 50% cheaper than synchronous calls, with results within 24h and usually much faster (recalled, not verified; check current pricing and SLA).
- Putting a small model on the 300 extraction calls and Sonnet (or Opus, if the prose is noticeably better) on the one writer call will likely cost the same as or less than one Opus call over 90k tokens. I don't have your exact numbers. Estimate it as `Σ(input_tokens × input_price) + Σ(output_tokens × output_price)` per stage, then read the real usage from one run.

## Evaluation (so you know it's reliable, not just that it reads well)
Build a golden set from the last 3 to 5 releases using the PMs' corrections: which features should have appeared, which items were internal, and the true rollout status. Track:
- **Feature recall**: customer-facing features that appear or are explicitly omitted. Target 100%, since the coverage check enforces it.
- **Internal-leak rate**: internal items that show up in the notes.
- **Rollout accuracy**: the target is zero GA claims for non-GA features.
- Extraction accuracy per PR, which tells you whether the small model is good enough or needs upgrading.

Run the old single-call setup and the new pipeline against the same golden set. That tells you whether Opus is worth it at each stage, instead of guessing.

**If you only do two things this week:** add the deterministic pre-filter, and switch to per-PR structured extraction with evidence-backed rollout status plus a code check against GA wording. Those target all three failure types directly. The writer and verifier improvements can follow.
