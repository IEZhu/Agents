fsck не нужен: файловая система почти наверняка цела. Скорее всего, место держит сам nginx. Файл удалён из каталога, но nginx продолжает держать его открытым и писать в него, поэтому ядро не освобождает блоки. `du` такие файлы не видит (имени больше нет), а `df` учитывает. Отсюда и разница: ~75 ГБ занято по `df` минус 31 ГБ по `du` ≈ те самые 41 ГБ access.log.

Часть вины на мне: в прошлом ответе я посоветовал удалить лог через `rm`, а это ошибка. Лог, открытый процессом, надо обнулять (`truncate`), а не удалять.

### Почему `lsof +L1` ничего не показал

Скорее всего, вы запускали его без `sudo`. Без root `lsof` видит только ваши собственные процессы, а nginx работает от root (master) и www-data (workers). Проверьте так:

```bash
sudo lsof +L1 | grep -i deleted
# или без lsof, напрямую через /proc:
sudo find /proc/*/fd -lname '*(deleted)' -printf '%p -> %l\n' 2>/dev/null
```

Ожидаемо увидите `nginx ... /var/log/nginx/access.log (deleted)` и размер около 41G.

### Как освободить место

Пусть nginx переоткроет лог-файлы. Сайт при этом не останавливается:

```bash
sudo nginx -s reopen          # сигнал USR1: закрыть и заново открыть логи
# альтернатива:
sudo systemctl reload nginx
```

Если `reload` почему-то не отпустит файл, помогает `sudo systemctl restart nginx`, но это короткий простой.

Если в выводе `lsof` окажутся и другие удалённые файлы (например, процессы внутри контейнеров), перезапустите соответствующий контейнер: `docker restart <name>`.

### Проверка

```bash
df -h /
sudo lsof +L1 | grep -i deleted   # должно быть пусто или без крупных файлов
ls -lh /var/log/nginx/             # access.log должен появиться заново
```

### Если после этого разница всё равно большая

Тогда проверьте остальные причины, fsck по-прежнему не первым делом:

```bash
df -T /                                   # тип ФС (на 22.04 обычно ext4)
sudo tune2fs -l /dev/<root-dev> | grep -i 'reserved block count'   # 5% резерва под root на ext4
# файлы, спрятанные под точками монтирования:
sudo mkdir -p /mnt/rootfs && sudo mount --bind / /mnt/rootfs && sudo du -xsh /mnt/rootfs/*; sudo umount /mnt/rootfs
```

Резерв ext4 объясняет лишь ~4 ГБ, а не 40. Прятать место под точкой монтирования может, например, каталог, в который что-то писалось до монтирования поверх него. Запускать `fsck` на смонтированном корне вообще нельзя: это может повредить ФС. Его делают только из recovery или live-режима, и повода для этого здесь я не вижу.

### Чтобы не повторилось

Лог на 41 ГБ означает, что ротация не работает или трафик аномальный (бот, флуд):

```bash
sudo logrotate -d /etc/logrotate.d/nginx      # dry-run: покажет, что бы сделал
systemctl status logrotate.timer              # запускается ли вообще
sudo awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head   # топ IP, когда лог наполнится снова
```

- **На будущее:** большой открытый лог чистите через `sudo truncate -s 0 /var/log/nginx/access.log`, а не через `rm`.
- **Логи контейнеров** (`/var/lib/docker/containers/*/*-json.log`) по умолчанию тоже не ограничены. Задайте лимит в `/etc/docker/daemon.json`:
  ```json
  { "log-driver": "json-file", "log-opts": { "max-size": "50m", "max-file": "3" } }
  ```
  После этого нужен `sudo systemctl restart docker`. Лимит применяется только к заново созданным контейнерам, то есть их надо пересоздать (`docker compose up -d --force-recreate`).
- **Про `docker system prune -a`:** он удалил все остановленные контейнеры и все образы, которые не используются запущенными контейнерами. Если какой-то из двух контейнеров был остановлен, его образ придётся заново подтянуть или собрать. Volumes он по умолчанию не трогает.
