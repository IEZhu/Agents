## Коротко

Все три бага вызывает одно и то же: состояние записи хранится в «флажках» пользовательской сессии, а не в самой записи, и слот не занимается атомарно. Правильная схема держится на трёх вещах:

1. **Запись (booking) — отдельная сущность в Redis со своим `id` и явным статусом.** Это конечный автомат. Статус меняется только атомарной операцией compare-and-set (CAS), то есть Lua-скриптом по схеме «если статус X, перевести в Y».
2. **Слот занимается атомарно в том же Lua-скрипте, который переводит запись в «ожидает оплаты».** Для двух клиентов на один слот `SET NX` выполнится только у одного.
3. **Каждая кнопка несёт `booking_id` и действие, а не опирается на FSM пользователя.** Любое нажатие, в том числе старое, повторное или двойное, проверяется по текущему статусу записи. Недопустимый переход отклоняется, пользователь получает понятный ответ.

Таймауты оплаты и возвраты обрабатывают фоновые воркеры, а не хендлеры. Поэтому клиент не может «зависнуть»: у любой записи в промежуточном статусе есть дедлайн, и после него запись гарантированно уходит в терминальный статус.

## 1. Модель данных в Redis

| Ключ | Тип | Содержимое |
|---|---|---|
| `booking:{id}` | HASH | `status`, `version`, `user_id`, `chat_id`, `service_id`, `master_id`, `start_ts` (UTC), `duration_min`, `slot_keys` (JSON), `payment_id`, `amount`, `hold_deadline`, `refund_status`, `refund_id`, `cancel_reason`, `created_at`, `updated_at` |
| `slot:{master_id}:{ts}` | STRING | `booking_id` владельца. **Без TTL**: слот освобождает только скрипт перехода |
| `user:{uid}:current_draft` | STRING | `id` актуального черновика |
| `user:{uid}:bookings` | SET | все `booking_id` пользователя (для «Мои записи») |
| `payment:{payment_id}` | STRING | `booking_id` (обратный индекс для вебхука) |
| `deadlines:hold` | ZSET | score — `hold_deadline`, member — `booking_id` |
| `queue:refunds` | LIST или STREAM | задания на возврат |
| `master:{id}:blocked:{ts}` | STRING | блокировка слота админом (мастер болеет) |

**Гранулярность слотов.** Храните занятость в единицах сетки, например по 15 минут. Услуга на 60 минут занимает 4 ключа `slot:*`. Иначе стрижка на 30 минут и комплекс на 90 минут пересекутся, и проверка по одному ключу этого не заметит. В скрипт передаётся список всех ключей, которые покрывает услуга.

Время везде храните в UTC (epoch). Часовой пояс барбершопа нужен только для отображения и для построения расписания.

Если Redis работает в режиме Cluster, все ключи одного Lua-скрипта должны лежать в одном hash slot. Для этого нужны hash tags, например `{m42}`. На одиночном Redis или Sentinel это не требуется.

## 2. Автомат состояний записи

```
States: DRAFT, AWAITING_PAYMENT, CONFIRMED,
        EXPIRED, PAYMENT_FAILED, CANCELLED_BY_CLIENT, CANCELLED_BY_ADMIN,
        COMPLETED, SUPERSEDED
Initial: DRAFT
Terminal: всё, кроме DRAFT / AWAITING_PAYMENT / CONFIRMED
```

| Из | В | Событие | Guard (проверяется атомарно) | Действия в том же скрипте | Действия после (асинхронно) |
|---|---|---|---|---|---|
| — | DRAFT | «Записаться» / `/start` | — | создать hash с TTL около 1 ч, `current_draft = id`, предыдущий черновик → SUPERSEDED | — |
| DRAFT | DRAFT | выбор услуги / мастера / даты / слота | `status == DRAFT` | записать поле | — |
| DRAFT | AWAITING_PAYMENT | «Подтвердить» | `status == DRAFT`, `current_draft == id`, все `slot:*` свободны и не заблокированы, слот в будущем | `SET` всех `slot:*`, `hold_deadline = now + 15 мин`, `ZADD deadlines:hold`, `PERSIST` (снять TTL), `DEL current_draft` | создать платёж в ЮKassa, отправить ссылку |
| AWAITING_PAYMENT | CONFIRMED | вебхук `payment.succeeded` | `status == AWAITING_PAYMENT`, `payment_id` совпадает | `ZREM deadlines:hold` | уведомить клиента и мастера |
| AWAITING_PAYMENT | EXPIRED | воркер дедлайнов | `status == AWAITING_PAYMENT`, `now >= hold_deadline + grace`, платёж в ЮKassa не `succeeded` | освободить `slot:*`, `ZREM` | сообщение «Время на оплату вышло» и кнопка «Выбрать другое время» |
| AWAITING_PAYMENT | PAYMENT_FAILED | вебхук `payment.canceled` / ошибка создания платежа | `status == AWAITING_PAYMENT` | освободить `slot:*`, `ZREM` | сообщение и кнопка «Попробовать снова» |
| AWAITING_PAYMENT | CANCELLED_BY_CLIENT | «Отменить» до оплаты | `status == AWAITING_PAYMENT` | освободить `slot:*`, `ZREM` | — (поздний платёж обработает правило из п. 4) |
| CONFIRMED | CANCELLED_BY_CLIENT | «Отменить» (второе нажатие, подтверждение) | `status == CONFIRMED`, `now < start_ts` | освободить `slot:*`; если `now <= start_ts − 3ч`, то `refund_status = pending` и `RPUSH queue:refunds`, иначе `refund_status = none` | уведомление с итогом по деньгам |
| AWAITING_PAYMENT, CONFIRMED | CANCELLED_BY_ADMIN | админ снимает запись | статус из этого множества | освободить `slot:*` (при необходимости сразу поставить блокировку мастера), `ZREM`, если оплата уже была — `refund_status = pending` и в очередь | уведомить клиента; для AWAITING_PAYMENT сверить платёж с API (п. 4) |
| CONFIRMED | COMPLETED | воркер, после `start_ts + duration` | `status == CONFIRMED` | слот можно не освобождать | — |

`refund_status` (`none`, `pending`, `succeeded`, `failed`) — **отдельное, ортогональное поле**, а не статус записи. Отмена фиксируется сразу, а возврат отрабатывает асинхронно, с ретраями. Так запись не застревает из-за того, что API ЮKassa ответил 500.

**Главный инвариант:** статус записи меняется только через одну функцию `transition(booking_id, allowed_from, to, ...)`. Внутри неё Lua-скрипт выполняет проверку и все изменения, включая слоты, дедлайны и очередь возвратов, одной атомарной операцией. Внешние вызовы (ЮKassa, Telegram) делаются **после** успешного перехода и никогда внутри.

## 3. Атомарный переход «Подтвердить»

Это ядро фикса багов 1 и 2:

```lua
-- KEYS[1] = booking:{id}
-- KEYS[2] = deadlines:hold
-- KEYS[3] = user:{uid}:current_draft
-- KEYS[4..n] = slot:{master}:{ts} (все единицы сетки, которые покрывает услуга)
-- ARGV[1] = booking_id, ARGV[2] = hold_deadline (epoch)
local status = redis.call('HGET', KEYS[1], 'status')
if status ~= 'DRAFT' then
  return {'ERR_STATE', status or 'GONE'}
end
if redis.call('GET', KEYS[3]) ~= ARGV[1] then
  return {'ERR_STALE'}
end
for i = 4, #KEYS do
  if redis.call('EXISTS', KEYS[i]) == 1 then
    return {'ERR_SLOT_TAKEN'}
  end
end
for i = 4, #KEYS do
  redis.call('SET', KEYS[i], ARGV[1])
end
redis.call('HSET', KEYS[1], 'status', 'AWAITING_PAYMENT', 'hold_deadline', ARGV[2])
redis.call('HINCRBY', KEYS[1], 'version', 1)
redis.call('PERSIST', KEYS[1])
redis.call('ZADD', KEYS[2], ARGV[2], ARGV[1])
redis.call('DEL', KEYS[3])
return {'OK'}
```

Блокировки мастера (`master:*:blocked:*`) проверяйте в этом же скрипте, добавив их в `KEYS`. Проверку «слот в будущем» и «слот в рабочих часах мастера» делайте в Python до вызова: расписание почти не меняется, а атомарность гарантирует сам `slot:*`.

Скрипт регистрируйте один раз через `redis.register_script(...)` в `redis.asyncio`. Это обёртка над `EVALSHA` (recalled, not verified — сверьтесь с документацией redis-py для своей версии).

После `OK`:

1. Создать платёж в ЮKassa с заголовком `Idempotence-Key: pay:{booking_id}` и `metadata: {"booking_id": ...}`. Повтор при сетевой ошибке не создаст второй платёж.
2. Сохранить `payment_id` в запись и в `payment:{payment_id}`.
3. Отправить сообщение с кнопками «Оплатить 500 ₽» (URL) и «Отменить».
4. Если платёж создать не удалось после N ретраев, перевести запись AWAITING_PAYMENT → PAYMENT_FAILED (слот освобождается) и написать клиенту.

Если бот упал между `OK` и созданием платежа, запись останется в AWAITING_PAYMENT без `payment_id`. Её подберёт воркер дедлайнов и переведёт в EXPIRED. Потерянных слотов не бывает.

## 4. Оплата и вебхук ЮKassa

### Про «ссылка живёт 15 минут»

Насколько я помню, у ЮKassa для обычного (одностадийного) платежа **нет параметра, который гасит ссылку ровно через 15 минут**. Неоплаченный платёж отменяется на их стороне по их собственному таймауту (recalled, not verified — проверьте в документации API). Поэтому 15 минут — **ваш** дедлайн. Проектируйте так, будто клиент может оплатить и на 16-й, и на 40-й минуте. Это закрывается одним общим правилом ниже.

### Обработчик вебхука

Эндпоинт `POST /yookassa/webhook` поднимается в том же aiohttp-приложении, что и webhook бота (или отдельным сервисом).

1. **Не доверять телу вебхука.** Взять из него `payment_id` и запросить платёж через API (`GET /v3/payments/{id}`). Насколько я знаю, вебхуки ЮKassa не подписываются, и рекомендуемая проверка — повторный запрос статуса плюс allowlist их IP (recalled — сверьтесь с докой).
2. Проверить сумму и валюту (`500.00 RUB`), найти `booking_id` по `metadata` или `payment:{id}`.
3. Применить **общее правило:**

| Статус платежа | Статус записи | Что делать |
|---|---|---|
| `succeeded` | AWAITING_PAYMENT, `payment_id` совпадает | CAS → CONFIRMED |
| `succeeded` | CONFIRMED с этим же `payment_id` | ничего (дубль вебхука) |
| `succeeded` | EXPIRED / PAYMENT_FAILED / CANCELLED_* / SUPERSEDED, или `payment_id` не совпадает | **автовозврат**: CAS `refund_status: none → pending` и `RPUSH queue:refunds`, сообщение «Слот уже недоступен, 500 ₽ вернутся» |
| `canceled` | AWAITING_PAYMENT | CAS → PAYMENT_FAILED, освободить слот |
| `canceled` | любой другой | ничего |

Только это правило закрывает все поздние оплаты: после истечения холда, после отмены клиентом, после снятия админом. Условие `refund_status: none → pending` через CAS гарантирует, что возврат ставится в очередь ровно один раз, сколько бы дублей вебхука ни пришло.

4. Отвечать 200 только после успешной обработки. При внутренней ошибке отвечать 5xx, чтобы ЮKassa повторила доставку. Насколько помню, повторы у неё есть, но на них одних не полагайтесь: см. сверку в п. 6.

### Гонка «оплата пришла на 14:59, вебхук — на 15:02»

Воркер дедлайнов не должен сразу переводить запись в EXPIRED:
- истекает только при `now >= hold_deadline + grace`, где grace около 2–5 минут;
- перед CAS запрашивает статус платежа в API: при `succeeded` выполняет переход в CONFIRMED сам, при `pending` или `canceled` — в EXPIRED.

Если вебхук и воркер сработают одновременно, CAS из AWAITING_PAYMENT пройдёт только у одного. Второй увидит новый статус и пойдёт по таблице выше: либо ничего не сделает, либо запустит автовозврат.

### Опционально: двухстадийный платёж

Если включить `capture: false`, деньги сначала только холдируются (`waiting_for_capture`). Бот делает `capture` только при успешном CAS в CONFIRMED, а в остальных случаях — `cancel`. Холд снимается, и настоящий возврат не нужен, что удобно для поздних оплат и отмены админом во время оплаты. Цена — ещё один шаг и ограниченный срок, за который нужно сделать capture (recalled, not verified — уточните в документации ЮKassa). Для MVP хватит одностадийного платежа с автовозвратом.

## 5. Отмены

### Клиент

1. «Отменить» в «Мои записи» или в сообщении записи. Бот считает `refundable = now <= start_ts − 3ч` и показывает: «Отменить запись на 14:00? Предоплата **будет возвращена** / **не возвращается**, до визита меньше 3 часов». Кнопки: `[Да, отменить] [Нет]`.
2. На «Да, отменить» условие **вычисляется заново** в Lua-скрипте, а `now` передаётся аргументом с сервера. Если граница пройдена между двумя нажатиями, клиент получает сообщение «Условия изменились, возврат уже не положен» и повторное подтверждение, а не молчаливую потерю денег.
3. Семантика границы: «не позже чем за 3 часа» означает `now <= start_ts − 10800`, включительно. Зафиксируйте это в коде константой и тестом.
4. Результат (`refund_eligible`, `cancelled_at`) сохраните в записи, чтобы потом разбирать споры.

### Админ

- Снятие одной записи или всех записей мастера за день (мастер заболел): это переход из `{AWAITING_PAYMENT, CONFIRMED}` → CANCELLED_BY_ADMIN.
- **Возврат всегда:**
  - CONFIRMED: `refund_status = pending` в том же скрипте;
  - AWAITING_PAYMENT: после перехода запросить платёж в API. При `succeeded` — возврат сразу. При `pending` ничего не делать: если клиент доплатит, сработает правило «succeeded при нетерминальном статусе → автовозврат».
- Слоты: при «мастер заболел» не просто освобождать `slot:*`, а ставить `master:{id}:blocked:{ts}`. Иначе освободившийся слот к больному мастеру сразу займёт кто-то другой.
- Права: список `admin_ids` в конфиге (переменная окружения) и фильтр на роутер админки. `callback_data` не должен быть единственной защитой, потому что её можно подделать.

### Очередь возвратов

Воркер читает `queue:refunds` (лучше Redis Stream с consumer group: сообщение не теряется, если воркер упал) и делает `POST /v3/refunds` с `Idempotence-Key: refund:{booking_id}`. Результат:
- успех → `refund_status = succeeded`, сохранить `refund_id`, уведомить клиента;
- временная ошибка → ретрай с экспоненциальной задержкой;
- после N неудач → `refund_status = failed` и алерт админу.

Ключ идемпотентности не даст вернуть деньги дважды, даже если задание обработается повторно.

## 6. Фоновые задачи

Это `asyncio`-таски, которые запускаются на старте бота или в отдельном процессе. Благодаря CAS несколько инстансов безопасны.

| Задача | Период | Что делает |
|---|---|---|
| Дедлайны холдов | 15–30 с | `ZRANGEBYSCORE deadlines:hold -inf now-grace`, для каждой записи сверка с API и CAS → EXPIRED или CONFIRMED |
| Возвраты | непрерывно | см. выше |
| Сверка (reconciliation) | 5–10 мин | все AWAITING_PAYMENT старше N минут и все `refund_status = pending` сверяются с API ЮKassa. Страховка от потерянных вебхуков |
| Завершение визитов | 10 мин | CONFIRMED → COMPLETED после окончания услуги |

На keyspace notifications об истечении TTL не полагайтесь: они не гарантируют доставку. Именно поэтому у `slot:*` нет TTL, а дедлайны лежат в ZSET.

## 7. Слой бота (aiogram 3.x)

- **Навигация без FSM-флажков.** Каждая кнопка несёт `booking_id` и действие через `CallbackData`-фабрику:
  ```python
  class BookingCb(CallbackData, prefix="bk"):
      booking_id: str   # короткий id, например 10–12 символов base62
      action: str       # "svc" | "mst" | "date" | "slot" | "confirm" | "cancel" | "cancel_yes"
      arg: str = ""
  ```
  Telegram ограничивает `callback_data` 64 байтами, поэтому id должны быть короткими, а UUID в полном виде не поместится. FSM aiogram (`RedisStorage`) можно оставить, только если нужен ввод текста (имя, телефон). Состояние записи в нём держать нельзя.
- **Каждый хендлер** загружает запись по `booking_id` и отвечает по её статусу. Если действие не подходит к статусу, хендлер не выполняет его, а отвечает `callback.answer("Эта запись уже оформлена", show_alert=True)` и перерисовывает актуальное сообщение.
- **Всегда вызывайте `callback.answer()`**, иначе у клиента крутится «часики».
- **После перехода** делайте `edit_reply_markup` / `edit_text` старого сообщения: убирайте или заменяйте кнопки. Это UX, а не защита. Защита — CAS: сообщение могло не отредактироваться, а клиент мог нажать до редактирования.
- **Бесплатные слоты** на экране выбора — только подсказка: они считаются из расписания минус занятые `slot:*`. Истина проверяется в момент «Подтвердить».
- **«Записаться» и `/start` всегда работают**: создают новый черновик и переводят предыдущий в SUPERSEDED. Если политика — «не больше одной неоплаченной записи на клиента», не блокируйте молча, а покажите: «У вас есть неоплаченная запись на 14:00: [Оплатить] [Отменить и начать заново]».
- **«Мои записи»** показывают все нетерминальные записи с действиями по статусу: оплатить или отменить для AWAITING_PAYMENT, отменить для CONFIRMED.

## 8. Как закрываются три бага

### Баг 1: «Подтвердить» в старом сообщении через час создаёт вторую запись

**Причина:** кнопка опиралась на флажки текущей сессии пользователя, а не на конкретную запись. Повторное нажатие проходило ту же логику заново.

**Фикс:**
- кнопка «Подтвердить» привязана к `booking_id` конкретного черновика;
- переход DRAFT → AWAITING_PAYMENT возможен только из DRAFT (атомарный CAS). Черновик, который уже подтверждён, оплачен или отменён, на повторное нажатие отвечает «уже оформлено». Второй записи не возникает;
- черновик, брошенный ради нового, помечается SUPERSEDED, и `current_draft` больше на него не указывает, поэтому его кнопка мертва (`ERR_STALE`). Черновик, простоявший час, к тому же истёк по TTL (`GONE`);
- двойной быстрый тап: оба нажатия приходят в Lua-скрипт, Redis выполняет их последовательно, и второе видит уже не DRAFT;
- платёж создаётся с `Idempotence-Key: pay:{booking_id}`, так что ретрай не порождает второй платёж.

### Баг 2: слот занял другой, пока клиент думал, и оба получили подтверждение

**Причина:** проверка «слот свободен» и запись «слот занят» шли разными командами (check-then-act). Между ними вклинивался второй клиент.

**Фикс:**
- проверка и захват всех единиц сетки слота выполняются **в одном Lua-скрипте** вместе со сменой статуса. Redis выполняет скрипт атомарно, поэтому из двух одновременных «Подтвердить» слот получает только один. Второй получает `ERR_SLOT_TAKEN` и сообщение «Это время только что заняли» с кнопкой выбора другого слота;
- захват по всем 15-минутным единицам исключает частичные пересечения услуг разной длины;
- «подтверждение» клиент получает только после CONFIRMED, то есть после оплаты, а до неё только «Время забронировано на 15 минут, оплатите». Даже если платёж пришёл по записи, которая уже потеряла слот, срабатывает автовозврат, а не второе подтверждение.

### Баг 3: оплата не пришла, клиент висит, помогает только `/start`

**Причина:** промежуточное состояние жило во флажках сессии без дедлайна и без выхода.

**Фикс:**
- у AWAITING_PAYMENT есть `hold_deadline` в ZSET. Воркер гарантированно переводит запись в EXPIRED (или в CONFIRMED, если платёж на самом деле прошёл), освобождает слот и пишет клиенту «Время на оплату вышло» с кнопкой «Выбрать другое время»;
- `payment.canceled` сразу переводит запись в PAYMENT_FAILED с кнопкой «Попробовать снова»;
- в любой момент ожидания доступна кнопка «Отменить»;
- навигация не зависит от флажков сессии: «Записаться» всегда начинает новый черновик, а незавершённое видно в «Мои записи»;
- потерянный вебхук подхватывает сверка с API, поэтому «оплатил, но бот не заметил» тоже не превращается в вечное ожидание.

## 9. Чек-лист крайних случаев для реализации

- [ ] Два одновременных «Подтвердить» по одной записи: одна запись, один платёж.
- [ ] Два клиента на пересекающиеся слоты (услуги 30 и 60 минут): подтверждается ровно один.
- [ ] Старое сообщение с «Подтвердить» после SUPERSEDED, EXPIRED или CONFIRMED: отказ с понятным текстом.
- [ ] Оплата на 14:59, вебхук на 15:03: CONFIRMED благодаря grace и сверке с API.
- [ ] Оплата после EXPIRED: автовозврат, слот не восстанавливается.
- [ ] Клиент отменил до оплаты, потом всё-таки оплатил: автовозврат.
- [ ] Админ снял запись в AWAITING_PAYMENT, клиент оплатил позже: автовозврат.
- [ ] Дублирующиеся вебхуки: один переход, один возврат.
- [ ] Отмена ровно в `start − 3ч` (граница включительно) и через 1 секунду после.
- [ ] Клиент увидел «возврат будет», а нажал «Да» уже после границы: повторное предупреждение.
- [ ] Бот упал между захватом слота и созданием платежа: воркер освобождает слот.
- [ ] ЮKassa недоступна при возврате: ретраи, затем алерт админу; отмена записи при этом не откатывается.
- [ ] Админ снял записи больного мастера: слоты заблокированы, а не освобождены.
- [ ] Клиент заблокировал бота: ошибка отправки (`TelegramForbiddenError`) логируется и не ломает переход.

**Тесты.** Логику переходов покрывайте unit-тестами против реального Redis в контейнере или `fakeredis` с поддержкой Lua (уточните, что ваша версия fakeredis умеет `EVAL`). Гонки проверяйте через `asyncio.gather` из двух одинаковых вызовов `transition(...)` с ожиданием ровно одного `OK`. Клиент ЮKassa замокайте на уровне вашего адаптера.

## Answer B
## Коротко

У всех трёх багов одна причина: состояние записи живёт во флажках `user data` и в том, в каком месте цепочки хендлеров находится пользователь. Серверной сущности «запись» с собственным статусом при этом нет. Лечится это тремя изменениями:

1. **Запись (booking) становится отдельной сущностью в Redis.** У неё есть `id`, явный статус и конечный набор допустимых переходов между статусами.
2. **Все переходы атомарные.** Каждый переход делается Lua-скриптом, который сверяет текущий статус (compare-and-set). Занятие слота тоже атомарно: захват ячеек расписания проходит через `SET NX` внутри того же скрипта.
3. **Каждая кнопка несёт `id` того, к чему относится.** Хендлер ничего не помнит сам: он загружает запись, проверяет, разрешено ли действие в её текущем статусе, и только потом что-то делает.

Таймауты оплаты, возвраты и ретраи уходят в фоновые воркеры. Хендлеры Telegram остаются тонкими и только рендерят состояние.

## 1. Слои

```

BookingService        — вся бизнес-логика: claim, confirm, cancel, expire, правило 3 часов.
BookingRepo (Redis)   — хранение + Lua-скрипты переходов. Единственное место, где меняется status.
PaymentGateway        — обёртка над API ЮKassa: create_payment, get_payment, create_refund.
webhook endpoint      — приём уведомлений ЮKassa → BookingService.
workers               — expiry (просроченные оплаты), refunds (возвраты с ретраями), reminders.
```

aiogram FSM остаётся только для визарда выбора (услуга → мастер → дата → слот). Там лежит **черновик**, а не запись. Черновик можно потерять или сбросить, ничего не сломается: слот он не держит и денег не касается.

## 2. Модель данных в Redis

Время храните в UTC (epoch seconds). В `Europe/Moscow` (или какая у вас зона) переводите только при показе, через `zoneinfo`.

| Ключ | Тип | Содержимое |
|---|---|---|
| `booking:{id}` | hash | `status`, `user_id`, `chat_id`, `message_id`, `service_id`, `master_id`, `slot_start`, `slot_end`, `prepay` (50000 копеек), `hold_until`, `payment_id`, `payment_status`, `refund_status`, `refund_id`, `cancel_reason`, `version`, `created_at` |
| `cell:{master_id}:{epoch_start}` | string | `booking_id`, владелец ячейки расписания |
| `user:{uid}:pending` | string | `booking_id` неоплаченной записи пользователя (не больше одной) |
| `user:{uid}:bookings` | set | все `booking_id` пользователя |
| `payment:{payment_id}` | string | `booking_id` (обратный индекс для вебхука) |
| `deadlines` | zset | `booking_id` → `hold_until` (для expiry-воркера) |
| `refunds:queue` | zset | `booking_id` → время следующей попытки |

**Ячейки расписания.** Сетку мастера режьте на ячейки фиксированной длины, например 15 минут. Услуга на 45 минут занимает 3 ячейки, и захватываются они все разом или ни одна. Если хранить только ключ «слот 14:00», две записи разной длительности смогут перекрыться: стрижка в 14:00 на час и борода в 14:30.

**`id` записи** равен `draft_id`, который генерируется при старте визарда (`secrets.token_urlsafe(9)` даёт 12 символов). От этого зависит закрытие бага №1, см. ниже.

## 3. Статусы и переходы

```
                 claim (атомарно)
DRAFT ─────────────────────────────► AWAITING_PAYMENT
(только FSM,                              │
 в Redis нет)       ┌─────────────────────┼──────────────────────┬──────────────────────┐
                    │ payment.succeeded   │ дедлайн прошёл /     │ клиент отменил       │ админ снял
                    │ + ячейки ещё наши   │ payment.canceled     │                      │
                    ▼                     ▼                      ▼                      ▼
                CONFIRMED              EXPIRED        CANCELLED_BY_CLIENT      CANCELLED_BY_ADMIN
                    │
                    ├── клиент отменил, ≥3 ч до визита → CANCELLED_BY_CLIENT (refund=yes)
                    ├── клиент отменил, <3 ч           → CANCELLED_BY_CLIENT (refund=no)
                    ├── админ снял                     → CANCELLED_BY_ADMIN  (refund=yes)
                    └── время визита прошло            → COMPLETED / NO_SHOW (по желанию)
```

Терминальные статусы: `EXPIRED`, `CANCELLED_*`, `COMPLETED`. Из них выхода нет.

**Статус оплаты хранится отдельно** (`payment_status`: `none → pending → succeeded | canceled`), и возврат тоже (`refund_status`: `none → required → pending → succeeded | failed`). Почему не одним полем: «админ снял запись, пока клиент платил» означает, что запись уже отменена, а деньги ещё идут. Два независимых поля описывают это без костылей.

**Правило возврата одно на всю систему.** Его проверяет и вебхук, и воркер:

> Деньги возвращаются, если `payment_status == succeeded` и запись **не** в `CONFIRMED`, за единственным исключением `CANCELLED_BY_CLIENT` с `refund=no`.

Из этого правила автоматически следует: оплата, пришедшая после отмены админом, после истечения брони или после отмены клиентом до оплаты, возвращается.

## 4. Атомарные операции (Lua)

Каждый переход — один Lua-скрипт. Внутри Redis он выполняется целиком, никто не вклинится. Внутри скрипта проверяются ожидаемые статусы, и если текущий статус не входит в список, скрипт возвращает `CONFLICT` и текущий статус. Сервис по этому ответу решает, что показать пользователю.

### 4.1 `claim`: создать запись и захватить слот

```lua
-- KEYS[1]=booking:{id}  KEYS[2]=user:{uid}:pending  KEYS[3]=deadlines  KEYS[4..]=cell:*
-- ARGV[1]=booking_id  ARGV[2]=hold_until  ARGV[3]=hold_ttl_ms  ARGV[4..]=пары field,value
if redis.call('EXISTS', KEYS[1]) == 1 then
  return {'EXISTS', redis.call('HGET', KEYS[1], 'status')}
end
local pending = redis.call('GET', KEYS[2])
if pending then return {'HAS_PENDING', pending} end
for i = 4, #KEYS do
  if redis.call('EXISTS', KEYS[i]) == 1 then return {'BUSY', KEYS[i]} end
end
for i = 4, #KEYS do
  redis.call('SET', KEYS[i], ARGV[1], 'PX', ARGV[3])
end
redis.call('SET', KEYS[2], ARGV[1], 'PX', ARGV[3])
redis.call('HSET', KEYS[1], 'status', 'AWAITING_PAYMENT', 'hold_until', ARGV[2],
           'payment_status', 'none', 'refund_status', 'none', 'version', 1, unpack(ARGV, 4))
redis.call('ZADD', KEYS[3], ARGV[2], ARGV[1])
return {'OK'}
```

Ячейки захватываются с TTL, равным брони (15 мин + грейс). Так слот освободится сам, даже если воркер упал. Зато при подтверждении оплаты надо проверить, что ячейки всё ещё принадлежат этой записи (см. 4.2).

### 4.2 `confirm`: оплата пришла

Атомарно, в одном скрипте:
- статус должен быть `AWAITING_PAYMENT`, иначе `CONFLICT`;
- каждая ячейка должна содержать этот `booking_id`, иначе `LOST_SLOT`: бронь протухла и слот уже занял другой;
- если всё сходится: ячейкам ставится `EXPIREAT` на `slot_end + сутки`, в записи `status=CONFIRMED` и `payment_status=succeeded`, из `deadlines` запись удаляется (`ZREM`), `user:{uid}:pending` удаляется **только если** в нём лежит этот `id`.

На `CONFLICT` (запись уже отменена или истекла) и на `LOST_SLOT` ставится `payment_status=succeeded` и `refund_status=required`, id уходит в `refunds:queue`.

### 4.3 `release`: expire / cancel

- Сверка статуса: для expire допустим только `AWAITING_PAYMENT`; для отмены клиентом `AWAITING_PAYMENT` или `CONFIRMED`; для отмены админом тоже `AWAITING_PAYMENT` или `CONFIRMED`.
- Ячейки удаляются по принципу **compare-and-delete**: `if GET(cell) == booking_id then DEL(cell)`. Чужую ячейку удалить нельзя. Это важно, потому что после истечения TTL ячейку мог уже захватить другой клиент.
- Проставляются новый статус, `cancel_reason`, `refund_status`. Если `payment_status == succeeded` и возврат положен, id попадает в `refunds:queue`.
- `ZREM deadlines`, чистится `user:{uid}:pending` (тоже через compare-and-delete).

Регистрируйте скрипты через `redis.asyncio` и `register_script` (есть в redis-py, но сигнатуру проверьте по своей версии). Если у вас Redis Cluster, ключи одного скрипта должны лежать в одном hash slot, и схему ключей тогда придётся переделывать. Для бота одного барбершопа хватит одного инстанса Redis, я исхожу из этого.

## 5. Сценарии по шагам

### 5.1 Визард выбора (FSM)

- `/start` или «Записаться» генерирует новый `draft_id` и кладёт его в FSM data. Старый черновик просто перезаписывается.
- Каждая кнопка визарда несёт `draft_id`. В aiogram 3 это фабрика `CallbackData`:

```python
class SlotCb(CallbackData, prefix="sl"):
    draft: str
    master: int
    start: int  # epoch

class BookingCb(CallbackData, prefix="bk"):
    action: str  # pay_check | cancel | cancel_yes | admin_cancel
    booking: str
```

- Хендлер визарда первым делом сверяет `callback_data.draft` с FSM data. Не совпало, значит кнопка из старого визарда: `callback.answer("Это меню устарело", show_alert=True)` и отрисовка текущего меню. `callback_data` в Telegram ограничен 64 байтами, так что id должны быть короткими.
- Список слотов строится по ячейкам, которые свободны **на момент показа**. Это подсказка, а не бронь. Гарантию даёт только `claim`.

### 5.2 «Подтвердить»

1. `BookingService.claim(draft_id, ...)`, где `booking_id = draft_id`.
2. Возможные результаты:
   - `OK`: идём дальше, к оплате;
   - `EXISTS`: кнопку нажали повторно или дважды; показываем текущее состояние этой записи, **ничего не создаём**;
   - `BUSY`: «Этот слот только что заняли» и свежий список слотов на ту же дату;
   - `HAS_PENDING`: «У вас есть неоплаченная запись на …» и кнопки [Оплатить] [Отменить её и записаться заново].
3. Создаём платёж в ЮKassa: сумма 500.00 RUB, `metadata={"booking_id": id}`, `confirmation.type=redirect` с `return_url` на бота, заголовок **`Idempotence-Key: pay:{booking_id}`**. Ретрай с тем же ключом не создаст второй платёж. Эти детали API я пишу по памяти, сверьте с документацией ЮKassa.
4. `payment_id` пишем в запись, заводим индекс `payment:{payment_id}`, ставим `payment_status=pending`.
5. Сообщение: «Оплатите до 14:35» и кнопки [Оплатить (URL)] [Проверить оплату] [Отменить]. `message_id` сохраняем в запись, чтобы при переходах статуса редактировать именно его.

Если процесс упал между шагами 1 и 4, получится запись без `payment_id`. Она штатно протухнет по дедлайну, дыры тут нет.

Если создать платёж не удалось окончательно (ретраи исчерпаны), делаем `release` в `EXPIRED` с `cancel_reason=payment_create_failed` и пишем честное сообщение с кнопкой «Попробовать снова».

### 5.3 Вебхук ЮKassa

1. **Телу уведомления не доверяйте.** Берите из него `payment_id` и перезапрашивайте платёж через `GET /payments/{id}`. Дополнительно можно пускать только IP ЮKassa: насколько помню, они публикуют список адресов, проверьте актуальный.
2. `booking_id` берите из `metadata` платежа или из индекса `payment:{id}`.
3. `succeeded`: вызывается `confirm` (4.2). На `OK` клиенту уходит «Запись подтверждена», сообщение редактируется. На `CONFLICT`/`LOST_SLOT` запускается возврат и клиенту приходит «Оплата пришла после отмены/истечения брони, деньги вернём».
4. `canceled` при `AWAITING_PAYMENT`: `release` в `EXPIRED` и кнопка «Записаться заново».
5. Отвечайте 200 быстро. Повторная доставка того же уведомления безопасна: второй `confirm` вернёт `CONFLICT` со статусом `CONFIRMED`, и это no-op.

### 5.4 Воркер просрочки

Цикл каждые 15–30 секунд: `ZRANGEBYSCORE deadlines -inf now`. Для каждой найденной записи:
1. Если есть `payment_id`, спрашиваем у ЮKassa статус платежа (на случай потерянного вебхука). Статус `succeeded` ведёт на путь `confirm`.
2. Иначе вызывается `release(expect=AWAITING_PAYMENT → EXPIRED)`. `CONFLICT` означает, что параллельно пришёл вебхук или была отмена, и тогда ничего не делаем.
3. Редактируем сообщение: «Время на оплату вышло, слот освобождён» и кнопка [Записаться заново].

Дедлайн: `hold_until = created + 15 мин + грейс 3–5 мин`. Клиенту показывайте 15 минут, грейс нужен на задержку вебхука. Не используйте keyspace notifications Redis как таймер: доставка там fire-and-forget, событие теряется при переподключении. Zset плюс поллинг надёжнее.

Есть нюанс. Я не уверен, что ЮKassa позволяет задать платёжной ссылке срок жизни 15 минут и отменить pending-платёж через API. Насколько помню, отмена через API доступна только для двухстадийных платежей в статусе `waiting_for_capture`. Поэтому система **обязана** переживать оплату, пришедшую после вашего дедлайна. Это и делает правило возврата из п. 3.

**Вариант надёжнее — двухстадийная оплата (`capture=false`).** Деньги сначала только холдируются. По уведомлению `waiting_for_capture` вызываете `confirm`: на `OK` делаете capture, на `CONFLICT`/`LOST_SLOT` делаете cancel платежа. В этом случае возврат вообще не нужен, холд просто снимается. Проверьте, поддерживают ли двухстадийку нужные вам способы оплаты. По памяти, СБП может не поддерживать, и тогда остаётся одностадийная схема с возвратами.

### 5.5 Отмена клиентом

1. [Отменить] в карточке записи. Сервис считает `refund = now <= slot_start - 3h` и показывает диалог: «Предоплата будет возвращена» или «Предоплата не возвращается, до визита меньше 3 часов». Кнопки [Да, отменить] [Назад].
2. [Да, отменить] пересчитывает правило **заново** на момент нажатия. Диалог мог висеть долго: открыли за 3:01, нажали за 2:58. Если исход изменился по сравнению с показанным, ничего не отменяем и показываем обновлённый диалог. Человек должен соглашаться на те условия, которые действительно применятся.
3. `release(expect={AWAITING_PAYMENT, CONFIRMED} → CANCELLED_BY_CLIENT, refund=...)`.
4. Отмена в `AWAITING_PAYMENT` означает «передумал платить». Слот освобождается. Если платёж всё-таки пройдёт, правило из п. 3 его вернёт.

Граница «не позже чем за 3 часа» включительная: ровно за 3:00:00 возврат есть. Зафиксируйте это в коде константой и покройте тестом, чтобы не спорить потом с клиентами.

### 5.6 Снятие админом

1. `release(expect={AWAITING_PAYMENT, CONFIRMED} → CANCELLED_BY_ADMIN, refund=yes)`.
2. `payment_status` определяет, что дальше:
   - `succeeded`: запись сразу идёт в `refunds:queue`;
   - `pending` (клиент прямо сейчас на странице оплаты): возвращать пока нечего, запись уже отменена; когда придёт `succeeded`, вебхук получит `CONFLICT` и запустит возврат;
   - при двухстадийной схеме с `waiting_for_capture`: cancel платежа.
3. Клиенту уходит «Запись отменена барбершопом, предоплата будет возвращена» и кнопка «Записаться к другому мастеру».
4. Бывает, что клиент уже сам отменил запись без возврата, а потом её снимает админ. Скрипт вернёт `CONFLICT` со статусом `CANCELLED_BY_CLIENT`. Покажите админу этот статус и отдельную кнопку «Вернуть предоплату вручную». Переписывать терминальный статус молча нельзя.
5. «Мастер заболел» обычно означает, что надо ещё и закрыть его расписание, иначе освободившиеся ячейки тут же займут. Это отдельная операция: блокирующие ячейки с `booking_id=BLOCK`.

### 5.7 Воркер возвратов

- Берёт из `refunds:queue` записи, у которых подошло время попытки.
- Сначала CAS `refund_status: required → pending`. Так два воркера не возьмут одну запись.
- `POST /refunds` с `Idempotence-Key: refund:{booking_id}` на всю сумму предоплаты. Повтор с тем же ключом не вернёт деньги дважды.
- Успех ставит `refund_status=succeeded`, `refund_id` и шлёт уведомление клиенту. Ошибка ставит обратно `required` с экспоненциальным backoff. После N неудач статус становится `failed` и уходит алерт админу.
- Возврат **никогда** не вызывается прямо из хендлера без очереди: сеть до ЮKassa упадёт, и деньги потеряются молча.

## 6. Как закрываются три бага

### Баг 1: старая кнопка «Подтвердить» через час создаёт вторую запись

**Причина.** Кнопка не несёт идентичности. Хендлер смотрит на текущие флажки в `user data` и каждый раз создаёт запись заново.

**Как закрывается:**
- `booking_id = draft_id`, и `draft_id` зашит в кнопку. `claim` первым делом проверяет `EXISTS booking:{id}`. Повторное нажатие, двойной клик или две параллельные обработки одного callback дают максимум одну запись: вторая получает `EXISTS` и просто видит текущий статус. aiogram может обрабатывать апдейты конкурентно, поэтому проверка обязана быть атомарной внутри Lua, а не через `if` в Python.
- Если старый визард не совпадает с текущим `draft_id` в FSM, кнопка отклоняется как устаревшая.
- `user:{uid}:pending` запрещает держать две неоплаченные брони одновременно.
- Косметика, а не защита: после действия убирайте клавиатуру у сообщения (`edit_reply_markup`). Полагаться только на это нельзя, клиент может нажать кнопку до того, как edit дошёл.

### Баг 2: двое подтвердили один слот

**Причина.** Проверка «слот свободен» и запись «слот занят» — две отдельные операции (check-then-act), между ними вклинивается второй клиент. К тому же проверка шла в момент выбора слота, а не в момент подтверждения.

**Как закрывается:**
- Слот занимается только в `claim`, а там проверка и захват ячеек идут в одном Lua-скрипте. Один из двух конкурентов получит `BUSY` и свежий список слотов.
- Ячейки захватываются все разом, поэтому услуги разной длительности тоже не перекрываются.
- Подтверждение после оплаты (`confirm`) дополнительно проверяет, что ячейки всё ещё принадлежат этой записи. Это закрывает поздний вариант гонки: бронь протухла, слот занял второй, и тут первый всё-таки оплатил. Первый получает возврат, а не дубль.

### Баг 3: оплата не пришла, клиент завис, спасает только /start

**Причина.** Состояние существует только как «позиция в цепочке хендлеров». Нет таймаута, нет выхода, и нет источника правды, по которому можно понять, где человек находится.

**Как закрываются:**
- Воркер просрочки гарантированно переводит неоплаченную запись в `EXPIRED`, освобождает слот и присылает кнопку «Записаться заново». Если воркер лежит, ячейки всё равно освобождаются по TTL.
- «Где сейчас клиент» определяется по его записям в Redis, а не по FSM. Любая точка входа (`/start`, «Мои записи», «Записаться») смотрит `user:{uid}:pending` и предлагает [Оплатить] [Отменить и начать заново].
- В ожидании оплаты у клиента всегда есть [Проверить оплату], которая опрашивает API ЮKassa на случай потерянного вебхука, и [Отменить].
- В роутере стоит fallback-хендлер на любой неизвестный или устаревший callback: `callback.answer(...)` и главное меню. Тупиков не остаётся.
- FSM-черновику дайте TTL: у `RedisStorage` в aiogram 3 есть `state_ttl`/`data_ttl`, но проверьте по своей версии. Брошенный визард очистится сам.

## 7. Обязательные тесты

Гоняйте их на настоящем Redis в docker, а не на моках: Lua в fakeredis работает через доп. зависимость и может вести себя иначе.

| # | Сценарий | Ожидание |
|---|---|---|
| 1 | Два параллельных `claim` с одним `draft_id` (`asyncio.gather`) | одна запись, второй получает `EXISTS` |
| 2 | Два параллельных `claim` разных пользователей на одну ячейку | один `OK`, один `BUSY` |
| 3 | Услуги 60 и 30 мин с перекрытием по времени | второй получает `BUSY` |
| 4 | Бронь истекла → слот занял B → пришёл `succeeded` для A | A получает `LOST_SLOT` и возврат, B не затронут |
| 5 | Админ снял запись при `pending` → затем `succeeded` | возврат ровно один |
| 6 | Отмена клиентом ровно за 3:00:00 и за 2:59:59 | возврат есть / возврата нет |
| 7 | Диалог отмены открыт за 3:01, подтверждён за 2:59 | повторный диалог, отмены нет |
| 8 | Дублирующий вебхук `succeeded` | no-op, одно уведомление |
| 9 | Вебхук и воркер просрочки одновременно | ровно один исход, без полу-состояний |
| 10 | Воркер возвратов упал после запроса в ЮKassa и перезапустился | повтор с тем же `Idempotence-Key`, деньги вернулись один раз |
| 11 | Клиент отменил без возврата → админ снимает | `CONFLICT`, статус не перезаписан |

Везде, где правило зависит от времени, передавайте `now` параметром, чтобы тесты были детерминированными.
