## Answer A
No. Your new data shows this is a leak, or something that behaves like one, not an undersized pod. My earlier advice to just raise the limit was the wrong call. Memory that climbs linearly with traffic and stays flat when idle is not a baseline that happened to be too high.

Here's the math on your proposal. At ~20 MB/min, 2Gi buys you roughly 90–100 minutes, not a day. A nightly restart wouldn't help, and you'd just get OOMKilled about every 1.5 hours instead of every 40 minutes.

## What your measurements tell you

The useful detail is **tracemalloc flat at 110–130 MB while the container grows by gigabytes**. tracemalloc only sees allocations that go through Python's allocator. So the growth is in **native memory** that Python doesn't track, or in the page cache, which counts toward `working_set`. For an image-resizing service there are three likely causes, roughly in order of likelihood:

1. **Pillow pixel buffers that are never released.** Pillow allocates image data in C with its own allocator, outside `PyMem`. As I recall, tracemalloc doesn't see those buffers (not verified, confirm in the Pillow source). A leaked `Image` object costs only a few hundred bytes on the Python side, which tracemalloc sees, but it pins megabytes of pixels, which tracemalloc doesn't. That fits your picture exactly. Typical causes:
   - `Image.open()` without `with` or `.close()`
   - intermediate images (`convert()`, `resize()`, `thumbnail` copies) kept in a list, a cache, a closure or an exception traceback
   - an `lru_cache` or global dict holding images or BytesIO objects
2. **glibc malloc fragmentation across threads.** If your endpoints are `def` rather than `async def`, FastAPI runs them in a threadpool. glibc then creates a separate malloc arena per thread, and large short-lived buffers of varying sizes fragment those arenas. RSS grows even though everything gets freed. This usually levels off eventually instead of growing linearly forever, so I'd rank it second. It's cheap to rule out, though.
3. **Page cache or tmpfs from uploads.** Starlette spools uploads above ~1 MB to a temp file (recalled threshold, check your version). If `/tmp` is an `emptyDir` with `medium: Memory`, or files aren't closed and deleted, that memory lands in the container's cgroup as `shmem` or file cache, not in the process heap.

## How to tell them apart (about 30 minutes of work)

**Step 1: split the metric.** Plot `container_memory_rss` and `container_memory_cache` next to `working_set`, or read `memory.stat` inside the pod:

```bash
kubectl exec <pod> -- cat /sys/fs/cgroup/memory.stat | grep -E '^(anon|file|shmem) '
kubectl exec <pod> -- df -h /tmp
```

- `anon` grows → it's in the process: cause 1 or 2.
- `file` or `shmem` grows → cause 3.

**Step 2: count live Pillow images.** Add a temporary debug endpoint, protected or internal only, and call it every few minutes under traffic:

```python
import gc
from collections import Counter

from PIL import Image


@app.get("/_debug/pil")
def pil_objects() -> dict[str, int]:
    gc.collect()
    live_images = [obj for obj in gc.get_objects() if isinstance(obj, Image.Image)]
    return {
        "live_images": len(live_images),
        "live_pixels": sum(img.width * img.height for img in live_images),
        **{f"type:{name}": count for name, count in Counter(type(img).__name__ for img in live_images).most_common(5)},
    }
```

If `live_images` keeps rising with traffic, it's cause 1. `gc.get_referrers()` on one of the images will show you what's holding it.

**Step 3: test the allocator.** Redeploy one pod with only this change:

```yaml
env:
  - name: MALLOC_ARENA_MAX
    value: "2"
```

If memory levels off, it's cause 2. You can keep that setting, or switch to jemalloc via `LD_PRELOAD` (the path depends on your base image).

**Step 4 (if still unclear): profile native memory.** `memray run --native` tracks C-level allocations, including Pillow's, and gives you a flame graph of who allocated the memory that's still live (recalled flag, check `memray run --help`). Reproduce it locally with a load loop of ~1000 uploads and compare the start and end.

## The resize path, written so it can't leak

For comparison, this is how the resize path should look. It closes every image deterministically and uses `draft()` so JPEG decoding happens at reduced size, which cuts peak memory a lot for large photos:

```python
import io

from fastapi import HTTPException, UploadFile
from fastapi.responses import Response
from PIL import Image, UnidentifiedImageError

MAX_SIDE = 1024
JPEG_QUALITY = 85


@app.post("/resize")
def resize(file: UploadFile) -> Response:
    try:
        with Image.open(file.file) as src:
            src.draft("RGB", (MAX_SIDE, MAX_SIDE))  # JPEG-only; no-op for other formats
            src.thumbnail((MAX_SIDE, MAX_SIDE))     # in place, no extra copy kept around
            rgb = src if src.mode == "RGB" else src.convert("RGB")
            try:
                out = io.BytesIO()
                rgb.save(out, format="JPEG", quality=JPEG_QUALITY)
            finally:
                if rgb is not src:
                    rgb.close()
    except UnidentifiedImageError as exc:
        raise HTTPException(status_code=422, detail="Unsupported image format") from exc
    finally:
        file.file.close()
    return Response(content=out.getvalue(), media_type="image/jpeg")
```

Also check that `Image.MAX_IMAGE_PIXELS` is set to a sane value, so a single huge upload (or a decompression bomb) can't spike memory by itself.

Either way, treat this as a stopgap, not the fix.

## Answer B
No. Going to 2Gi and adding a nightly restart won't fix this, and your numbers show why. I also need to correct what I said last turn: this isn't an undersized pod. The process is leaking memory.

## What your data says

- **The growth never levels off.** 512Mi lasted about 15 minutes and 1Gi lasted about 40. That's about 512 MB over about 25 extra minutes, which matches the ~20 MB/min you see in Grafana. An undersized pod climbs and then stays at some level. This one keeps climbing. At that rate 2Gi would last roughly 90 minutes, so a nightly restart would come about 20 hours too late.
- **The growth follows traffic.** Memory only rises while requests are being handled, so something grows with each request.
- **tracemalloc stays flat at 110–130 MB.** tracemalloc only sees memory allocated through Python's own allocator. Pillow keeps pixel data in C memory it allocates itself, so a 4000×3000 RGB image uses about 36 MB that tracemalloc never counts. The `Image` object that owns it looks like a few hundred bytes. So the growth is almost certainly outside the Python heap. That means native memory (Pillow/libjpeg/glibc) or memory the kernel charges to the container, such as tmpfs or shared memory.

## Likely causes, most likely first

1. **Native memory held by `Image` objects that are never released.** An image goes into a cache, a global, an `lru_cache`, a list kept for metrics or debugging, or an exception traceback that stays alive. tracemalloc would show this as a tiny, flat entry while tens of MB of pixel data stay pinned behind it.
2. **Temp files on memory-backed storage.** Starlette's `UploadFile` writes larger uploads to a temp file on disk. It also counts if you write intermediate files yourself. Check where `/tmp` lives: an `emptyDir` with `medium: Memory`, a tmpfs mount, or `/dev/shm` all count as container memory and can't be reclaimed. Files that are never closed or deleted then grow exactly like this.
3. **glibc malloc fragmentation or arena growth.** Sync (`def`) endpoints run in a threadpool, and each thread can get its own malloc arena. Large, differently sized Pillow buffers fragment them, so RSS keeps rising even after Python frees the memory. This is common with Pillow. It usually levels off eventually, though, so a perfectly linear climb points more toward 1 or 2. It's cheap to rule out anyway.

## How to tell which one it is (in order)

**1. Read cgroup memory.stat in a running pod, early and again 20 minutes later.**
```bash
kubectl exec <pod> -- cat /sys/fs/cgroup/memory.stat | grep -E '^(anon|file|shmem|active_file|inactive_file) '
# cgroup v1: /sys/fs/cgroup/memory/memory.stat (rss, cache, shmem)
```
- `shmem` growing → cause 2 (tmpfs/emptyDir). Check `df -h /tmp /dev/shm` and `ls -la /tmp`.
- `anon` growing → native heap, so cause 1 or 3. Go to step 2.

**2. Count live Pillow images inside the process.** Add a temporary debug endpoint or log line:
```python
import gc
from PIL import Image

def live_pil_images() -> int:
    return sum(1 for obj in gc.get_objects() if isinstance(obj, Image.Image))
```
If this number rises with traffic, you have cause 1. Use `gc.get_referrers()` on one of the images to find what is holding it.

**3. If image count is flat but `anon` still grows, test the allocator.** Change one thing at a time and watch the slope:
```yaml
env:
  - name: MALLOC_ARENA_MAX
    value: "2"
```
Also try jemalloc (`apt-get install libjemalloc2` plus `LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so.2`; the path varies by distro and architecture, so check it in your image). If the slope drops a lot, the problem was fragmentation. If it barely changes, it's a real leak.

**4. If it's still unclear, use a native-aware profiler.** `memray run --native` (or `memray attach`) under a local load test. Unlike tracemalloc, it tracks C allocations and shows which call sites still hold memory.

## Code hygiene worth doing anyway

Close images and uploads explicitly instead of waiting for GC:

```python
from io import BytesIO
from fastapi import UploadFile
from PIL import Image

async def resize(upload: UploadFile, size: tuple[int, int]) -> bytes:
    try:
        with Image.open(upload.file) as src:
            src.draft("RGB", size)  # JPEG only: decode at reduced scale, big memory win
            with src.convert("RGB") as rgb:
                rgb.thumbnail(size)
                out = BytesIO()
                rgb.save(out, format="JPEG", quality=85)
                return out.getvalue()
    finally:
        await upload.close()
```

`draft()` is worth adding even once the leak is fixed. It makes libjpeg decode a large JPEG at 1/2, 1/4 or 1/8 scale, which cuts peak memory per request a lot. Also set `Image.MAX_IMAGE_PIXELS` to a sensible limit so one huge upload can't blow the pod up.

## About 2Gi + restart

A higher limit is fine as short-term cover while you investigate. Use a liveness or memory-based restart rather than a nightly one, because at 20 MB/min a nightly restart is much too infrequent. Don't treat it as the fix. Once the slope is flat, you can probably go back to 512Mi–1Gi, sized from your peak concurrent image memory.
