Ubuntu 22.04, VPS на 80 ГБ, на нём nginx + docker (два контейнера с приложением). Сегодня утром df -h показывает / на 100%, приложение падает с "No space left on device". Что делать?

### Assistant
Скорее всего разрослись логи. Сделайте так:
1. `sudo journalctl --vacuum-size=200M`
2. Посмотрите самые большие файлы в /var/log: `sudo du -sh /var/log/* | sort -h`
3. Удалите старые/большие логи nginx (access.log, error.log) через rm.
4. Почистите docker: `docker system prune -a`.
После этого место должно освободиться.

## Answer A
fsck не нужен: файловая система почти наверняка цела. Скорее всего, место держит сам nginx. Файл удалён из каталога, но nginx продолжает держать его открытым и писать в него, поэтому ядро не освобождает блоки. `du` такие файлы не видит (имени больше нет), а `df` учитывает. Отсюда и разница: ~75 ГБ занято по `df` минус 31 ГБ по `du` ≈ те самые 41 ГБ access.log.

Часть вины на мне: в прошлом ответе я посоветовал удалить лог через `rm`, а это ошибка. Лог, открытый процессом, надо обнулять (`truncate`), а не удалять.

### Почему `lsof +L1` ничего не показал

Скорее всего, вы запускали его без `sudo`. Без root `lsof` видит только ваши собственные процессы, а nginx работает от root (master) и www-data (workers). Проверьте так:

```bash
sudo lsof +L1 | grep -i deleted
# или без lsof, напрямую через /proc:
sudo find /proc/*/fd -lname '*(deleted)' -printf '%p -> %l\n' 2>/dev/null
```

Ожидаемо увидите `nginx ... /var/log/nginx/access.log (deleted)` и размер около 41G.

### Как освободить место

Пусть nginx переоткроет лог-файлы. Сайт при этом не останавливается:

```bash
sudo nginx -s reopen          # сигнал USR1: закрыть и заново открыть логи
# альтернатива:
sudo systemctl reload nginx
```

Если `reload` почему-то не отпустит файл, помогает `sudo systemctl restart nginx`, но это короткий простой.

Если в выводе `lsof` окажутся и другие удалённые файлы (например, процессы внутри контейнеров), перезапустите соответствующий контейнер: `docker restart <name>`.

### Проверка

```bash
df -h /
sudo lsof +L1 | grep -i deleted   # должно быть пусто или без крупных файлов
ls -lh /var/log/nginx/             # access.log должен появиться заново
```

### Если после этого разница всё равно большая

Тогда проверьте остальные причины, fsck по-прежнему не первым делом:

```bash
df -T /                                   # тип ФС (на 22.04 обычно ext4)
sudo tune2fs -l /dev/<root-dev> | grep -i 'reserved block count'   # 5% резерва под root на ext4
# файлы, спрятанные под точками монтирования:
sudo mkdir -p /mnt/rootfs && sudo mount --bind / /mnt/rootfs && sudo du -xsh /mnt/rootfs/*; sudo umount /mnt/rootfs
```

Резерв ext4 объясняет лишь ~4 ГБ, а не 40. Прятать место под точкой монтирования может, например, каталог, в который что-то писалось до монтирования поверх него. Запускать `fsck` на смонтированном корне вообще нельзя: это может повредить ФС. Его делают только из recovery или live-режима, и повода для этого здесь я не вижу.

### Чтобы не повторилось

Лог на 41 ГБ означает, что ротация не работает или трафик аномальный (бот, флуд):

```bash
sudo logrotate -d /etc/logrotate.d/nginx      # dry-run: покажет, что бы сделал
systemctl status logrotate.timer              # запускается ли вообще
sudo awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head   # топ IP, когда лог наполнится снова
```

- **На будущее:** большой открытый лог чистите через `sudo truncate -s 0 /var/log/nginx/access.log`, а не через `rm`.
- **Логи контейнеров** (`/var/lib/docker/containers/*/*-json.log`) по умолчанию тоже не ограничены. Задайте лимит в `/etc/docker/daemon.json`:
  ```json
  { "log-driver": "json-file", "log-opts": { "max-size": "50m", "max-file": "3" } }
  ```
  После этого нужен `sudo systemctl restart docker`. Лимит применяется только к заново созданным контейнерам, то есть их надо пересоздать (`docker compose up -d --force-recreate`).
- **Про `docker system prune -a`:** он удалил все остановленные контейнеры и все образы, которые не используются запущенными контейнерами. Если какой-то из двух контейнеров был остановлен, его образ придётся заново подтянуть или собрать. Volumes он по умолчанию не трогает.


## Answer B
Файловая система, скорее всего, в порядке, fsck не нужен. Почти наверняка nginx до сих пор держит открытым удалённый `access.log`. Это моя ошибка в прошлом ответе: активный лог нельзя удалять через `rm`, его нужно было обнулить (truncate).

### Что произошло

- `rm` удаляет только имя файла из каталога. Сам inode и блоки на диске освобождаются лишь после того, как последний процесс закроет файл.
- nginx пишет в `access.log` через открытый дескриптор и продолжает писать в удалённый файл. `du` его не видит (имени нет), а `df` видит, потому что блоки заняты.
- Цифры сходятся: около 77 ГБ занято (97% от 80) минус 31 ГБ по `du` дают примерно 46 ГБ. Это ваши 41 ГБ плюс то, что nginx дописал с утра.

**Почему `lsof +L1` пустой.** Если вы запускали его без `sudo`, он показывает только процессы вашего пользователя. Лог-файлы nginx открывает master-процесс, а он работает от root. Воркеры работают от `www-data`, и чужие дескрипторы обычному пользователю тоже не видны.

### Проверка

```bash
sudo lsof +L1 | grep -i nginx
```
Ожидается строка вроде `nginx ... /var/log/nginx/access.log (deleted)` с большим SIZE.

Если `lsof` не установлен или вывод по-прежнему пустой:
```bash
sudo find /proc/*/fd -lname '*(deleted)' -printf '%p -> %l\n' 2>/dev/null | grep -v memfd
```
Здесь ищутся дескрипторы, которые указывают на удалённые файлы.

### Решение

Самый мягкий вариант: заставить nginx переоткрыть лог-файлы, без рестарта и без обрыва соединений.
```bash
sudo nginx -s reopen
```
Команда отправляет master-процессу сигнал USR1 (reopen log files), и тот создаёт новый `access.log`. После этого старый дескриптор закрывается и 41 ГБ освобождаются.

Если это не помогло:
```bash
sudo systemctl restart nginx
```
Это короткий простой в пару секунд, зато все дескрипторы гарантированно закроются.

Если перезапускать нельзя совсем, файл можно обнулить через `/proc`. PID и номер FD возьмите из вывода `lsof` (колонки PID и FD, у FD уберите букву `w`):
```bash
sudo truncate -s 0 /proc/<PID>/fd/<FD>
```

### Проверка результата

```bash
df -h /
sudo lsof +L1 | grep -i nginx      # должно быть пусто
ls -la /var/log/nginx/             # новый access.log должен появиться после reopen
```

### Почему не fsck

- Расхождение между `du` и `df` при удалённом, но открытом файле — штатное поведение ext4, а не повреждение.
- Запускать fsck на смонтированном `/` нельзя: так действительно можно повредить ФС. Для этого нужен rescue-режим VPS или загрузка с другого носителя.
- Признаков порчи вроде ошибок в `dmesg` или перемонтирования в read-only вы не описали. Проверить можно так: `sudo dmesg | grep -iE 'ext4|error'`.

### Чтобы не повторилось

1. **Больше никогда не делайте `rm` активного лога.** Вместо этого:
   ```bash
   sudo truncate -s 0 /var/log/nginx/access.log
   ```
2. **Выясните, почему лог вырос до 41 ГБ.** Обычно ломается logrotate:
   ```bash
   cat /etc/logrotate.d/nginx
   sudo logrotate -d /etc/logrotate.d/nginx   # dry-run, покажет ошибки
   systemctl status logrotate.timer
   ```
   Ещё одна частая причина — бот или сканер, который долбит сервер: `sudo tail -n 1000 /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head`. Если так, закройте его через fail2ban или `limit_req`.
3. **Docker-логи контейнеров.** `docker system prune` не трогает логи работающих контейнеров, а по умолчанию они растут без ограничений. Посмотреть их размер:
   ```bash
   sudo du -sh /var/lib/docker/containers/*/*-json.log
   ```
   Лимит задаётся в `/etc/docker/daemon.json`:
   ```json
   {
     "log-driver": "json-file",
     "log-opts": { "max-size": "50m", "max-file": "3" }
   }
   ```
   Затем `sudo systemctl restart docker`. Учтите, что это перезапустит контейнеры, а лимит применится только к контейнерам, созданным заново (`docker compose up -d --force-recreate`). Проверьте, что `daemon.json` — валидный JSON: с синтаксической ошибкой docker не стартует.

### Риски

- `docker system prune -a` из прошлого ответа удалил и все неиспользуемые образы, включая образы остановленных на тот момент контейнеров. Если какой-то контейнер был остановлен, при следующем запуске образ придётся скачать или собрать заново.
- `nginx -s reopen` безопасен. `restart` даёт краткий обрыв соединений.
