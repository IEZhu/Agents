## Latest user message
I'm automating our release notes. Every two weeks we ship a release with roughly 250-350 merged PRs across 6 repos. Right now a GitHub Action dumps all PR titles + descriptions + linked Jira ticket summaries (ends up around 90k tokens) into a single Claude Sonnet call with a prompt like "Write customer-facing release notes grouped into New features / Improvements / Bug fixes, skip internal refactors and CI changes, max 1 page". The output reads great but the PMs keep catching problems: a couple of real customer-facing features just don't appear, some internal changes (dependency bumps, a feature-flag cleanup) end up listed as "improvements", and last release it described a feature as GA when the PR said it's behind a flag for 10% of tenants. My first thought was to switch to Opus and add a few examples of good notes plus a 'double-check rollout status' line to the prompt. Would that be enough, or how should I restructure this so it's reliable? It runs in CI overnight so a few minutes of runtime is fine, but I'd like to keep the cost reasonable.

## Rubric (what a strong answer does)
1. The answer restructures the job into dependent stages where each output feeds the next, e.g. per-PR or small-batch classification into structured records (customer-facing vs internal, category, rollout/flag status), then filtering/grouping, then a final call that writes the notes only from the kept records.
2. The answer explains how the staged design fixes the reported failures: every PR gets an explicit decision so features are not silently dropped (e.g. a count or coverage check that every PR has a record), and rollout status is extracted as an explicit field so flagged features are not presented as GA.
3. The answer acknowledges that errors in the early classification step carry into the final notes and proposes a check point for it, such as logging intermediate records, a PM review of the classified list, or spot checks before the writing step.
4. The answer gives a clear verdict on the user's idea (bigger model + examples + an extra instruction) and takes the cost constraint seriously with a concrete measure, e.g. a cheaper model or batching for the per-PR classification step with the stronger model only for the final writing, or pre-filtering obvious internal PRs (dependency bumps, CI) by labels or rules before any model call.

## Answer A
**Short answer: no, probably not.** Switching to Opus and adding examples will likely improve the prose and cut the error rate somewhat. It won't remove the three failure modes, because they come from the architecture and not from how capable the model is. You're asking one call to do four jobs over about 300 items at once: filter, classify, extract facts, and write under a one-page limit. When the input is 90k tokens and the output has to fit on a page, the model is forced to compress silently. That produces exactly what your PMs are catching:

| Symptom | Root cause | Why Opus + examples won't reliably fix it |
|---|---|---|
| Real features missing | Recall over ~300 items in one pass, plus the length cap forcing silent drops | Nothing records whether every PR was considered |
| Dep bumps / flag cleanup listed as "improvements" | Classification done implicitly while writing | You can't see or test the per-PR decision |
| "GA" when it's actually 10% behind a flag | The rollout fact is buried in one PR description among 300 and gets paraphrased away | "Double-check rollout status" asks the model to check itself with no structured fact to check against |

The fix is to break the one call into steps you can check: **deterministic filtering → per-PR structured extraction → grouping → writing → automated verification → PM review.** Each LLM step does one job on a small input, and the facts that matter (rollout status especially) become fields your code can validate.

## The pipeline

### Stage 0: Deterministic pre-filter (no LLM)
Handle the easy cases in code first:
- Author is `dependabot` / `renovate` → drop
- Only touched `.github/`, `ci/`, lockfiles, `*.md` in docs-internal → drop
- Conventional-commit prefixes, if you use them: `chore:`, `ci:`, `build:`, `refactor:`, `test:` → drop (or send to a "probably internal" bucket for a cheap confirmation)
- Labels like `internal`, `no-release-note` → drop

Log every drop with its reason. That log is how you debug a missing feature later.

This probably removes a large share of the 250–350 PRs. I don't know your mix, so measure it on the last few releases.

### Stage 1: Per-PR extraction (small model, structured output)
One call per PR, or per small batch of about 10, returning JSON with a fixed schema:

```json
{
  "pr": "repo-a#1234",
  "customer_facing": true,
  "category": "feature | improvement | bugfix | internal",
  "internal_reason": null,
  "summary_customer": "Bulk export of audit logs to CSV",
  "feature_key": "audit-log-export",
  "rollout": {
    "status": "ga | flagged_partial | flagged_off | beta | unknown",
    "evidence": "quote from PR/Jira text supporting status",
    "flag_name": "audit_export_v2"
  },
  "confidence": "high | medium | low"
}
```

Why this works:
- **Classification becomes a single visible decision per PR.** You can audit it, test it, and override it.
- **Rollout status must be backed by an `evidence` quote.** That turns "don't hallucinate GA" from a request to the model into a check your code runs: if `status == ga` but the evidence mentions a flag or percentage, or there is no evidence, the PR gets flagged.
- **It runs on Haiku or Sonnet.** This is a narrow extraction task on about 300 tokens of input. Opus isn't needed here.
- **Everything goes through the Batch API**, since it runs overnight. It's discounted (about 50% as I recall; confirm current pricing). Put the instructions and examples in a fixed prefix so prompt caching covers them.

Your few-shot examples belong **here**, not in the writing prompt. Useful ones are a dependency bump (→ internal), a feature-flag cleanup (→ internal, reason `flag_cleanup`), a flagged 10% rollout (→ `flagged_partial`), and a bugfix that customers can see.

**Even better for rollout:** don't let an LLM infer it at all if you can avoid it. If your flag system (LaunchDarkly, Unleash, an in-house tool) exposes an API, look up `flag_name` there and use the actual rollout state. The LLM extracts the flag name and the flag system supplies the truth. Failing that, add a PR template field or label such as `rollout: ga/flagged/beta`, so the information is structured at the source.

### Stage 2: Grouping and dedup (code + one mid-size call)
A single customer-facing feature often spans several PRs across your 6 repos (backend + frontend + SDK). Group by `feature_key` and linked Jira epic in code, then use one Sonnet call to merge near-duplicate groups. The input is now only the extracted summaries, which is a few thousand tokens instead of 90k.

Rollout rule for a group: **use the most conservative status among its PRs.** If any PR says `flagged_partial`, the feature isn't GA.

### Stage 3: Writing (one call, Sonnet or Opus)
The input is the list of customer-facing items, already classified, with rollout status. The prompt constrains it:
- "Every item in the input MUST appear in the output. Do not add items. Do not change rollout status."
- Items with `flagged_partial` / `beta` go in their own section or get a fixed label, e.g. "Early access — rolling out gradually".
- If one page isn't enough, **ask for a ranked list and truncate in code**, keeping the dropped items in an appendix or a "full changelog" link. Never let the model decide on its own what to omit.

This is the one step where Opus might be worth paying for, since its output is what customers read. It's a single call on a small input, so the cost difference is small. Try both on past releases before deciding.

### Stage 4: Automated verification (code + one cheap call)
- **Coverage check (code):** every item with `customer_facing == true` must map to a line in the notes. The writer can include an item ID per bullet in a hidden or structured field, which is easier than fuzzy matching.
- **Claim check (LLM-as-judge, small model):** for each bullet, pass the bullet plus the source extraction and ask whether the bullet states anything not supported by the source, especially availability or rollout. Output pass/fail with the reason.
- **Leak check (code):** keywords like `bump`, `upgrade dependency`, `flag cleanup`, `remove flag`, `refactor` appearing in the notes → flag.

Anything that fails a check goes into a "needs review" list. It is not silently fixed.

### Stage 5: PM review as a PR
Open a PR containing the draft notes plus a review report:
- ⚠️ Items that failed verification
- Low-confidence classifications
- Everything classified `internal` by the LLM (not by the deterministic filter), as a collapsible list. This is where missing features get caught in seconds instead of by careful reading.
- The full drop log

That changes the PMs' job from finding what's missing in prose to scanning a short exceptions list.

## Cost

I can't give real numbers without your token counts, so here's how to estimate:
- **Extraction:** about 300 PRs × (cached instruction prefix + ~300 tokens of PR/Jira text + ~150 output tokens) on a small model through Batch. Total input is roughly the same 90k you already send, but on a cheaper model at a batch discount. This should cost less than your current single Sonnet call, not more. Verify with the token-counting endpoint on one real release.
- **Grouping + writing + verification:** a few thousand tokens each. Small, even on Opus.
- **Runtime:** batch jobs can take a while to finish. That's fine overnight. If you need a guaranteed deadline, use parallel non-batch calls for extraction instead.

My rough expectation is that total cost stays at or below what you pay now, while reliability improves a lot. Treat that as an estimate to confirm, not a benchmark.

## How to know it works

Build a golden set from your last 3–5 releases. Your PMs' corrections are already labeled data:
- **Recall on customer-facing items** (the missing-features problem): target ~100%. This is the metric that matters most.
- **Precision on internal leakage**: count of internal items that appear in the notes.
- **Rollout accuracy**: exact match on status per feature.

Run old and new pipelines on the same releases and compare. When the PMs correct a new mistake, add the case to the golden set and to the Stage 1 examples.

## If you only do three things first
1. **Deterministic pre-filter + per-PR JSON extraction with an `evidence`-backed rollout field.** This fixes most of the classification and GA problems.
2. **"Must include every input item; truncate in code, not in the model."** This fixes the missing features.
3. **Coverage check + "LLM classified as internal" list in the PM review.** This catches whatever still gets through.

Switching models is the last lever to pull, not the first.


## Answer B
**Short answer: no.** Opus plus a few examples will probably make the prose better and might cut the errors somewhat, but it won't make the notes reliable. All three failures come from the structure of the job. You are asking one call to do four things at once over about 90k tokens: find every relevant change, classify each one, pull out facts like rollout status, and write polished copy that fits on one page. When those are combined, the model silently drops items, classifies by feel, and lets writing style override the facts. Split the stages and check them with code instead of hoping the prompt holds.

## Why each failure happens

| Symptom | Likely cause | Why a bigger model / more prompt won't fix it |
|---|---|---|
| Real features missing | Recall across ~300 items in one long context, plus the "max 1 page" limit forcing silent cuts. Items in the middle of long contexts get less attention (Liu et al., 2023, "Lost in the Middle"). | The model still has to pick about 20 items out of 300 in a single pass, and nothing records what it dropped. |
| Dependency bumps / flag cleanup listed as "improvements" | Classification is implicit and mixed into writing. "Improvements" is a catch-all, and a model writing notes tends to fill it. | Examples show tone, not a decision rule. |
| Flagged feature described as GA | Rollout status is a fact buried in one PR body. Summarising favours clean marketing language like "now available". | "Double-check rollout status" is an instruction with no check behind it. It will work sometimes. |

## Recommended pipeline

```
[0] Deterministic pre-filter  →  [1] Per-PR extraction (LLM, structured)
      →  [2] Deterministic validation + grouping  →  [3] Writer (LLM, curated input only)
      →  [4] Verifier (code + LLM)  →  [5] PM review artifact
```

### Stage 0: Deterministic pre-filter (no LLM)
Remove the obvious noise before the model sees it:
- Author is a bot (dependabot, renovate, github-actions).
- Conventional-commit prefixes `chore:`, `ci:`, `build:`, `deps:`, `test:`, if your repos use them.
- Only files like `.github/**`, lockfiles or test directories changed.
- Labels such as `internal`, `no-release-note`.

Don't delete these PRs. Log them as `excluded_by_rule` so PMs can see them. This stage alone should fix most of the "dependency bump as improvement" cases.

### Stage 1: Per-PR extraction (one small call per PR, or per linked Jira epic)
Each call sees one PR, its linked Jira summary and a short instruction, and returns strict JSON:

```json
{
  "pr": "repo#1234",
  "customer_facing": true,
  "category": "feature | improvement | bugfix | internal",
  "internal_reason": null,
  "feature_key": "bulk-export",
  "customer_summary": "Admins can export up to 50k rows as CSV.",
  "rollout": {
    "status": "ga | flagged_partial | beta | internal_only | unknown",
    "evidence": "quoted text from PR/Jira, or null"
  },
  "confidence": "high | medium | low"
}
```

Key rules for this prompt:
- **Evidence is required.** `rollout.status` can't be `ga` unless there is quoted evidence. With no evidence it must be `unknown`, never assumed GA.
- **Give a definition of `internal`, with examples of borderline cases** (flag cleanup, refactor, dependency bump, telemetry). This is the right place for few-shot examples, not the writing prompt.
- **`feature_key`** groups the several PRs that make up one feature across your 6 repos.

This task is narrow and structured, so a small model (Haiku or Sonnet) should be enough. Check that on your own data (see Evaluation below).

### Stage 2: Deterministic validation and grouping (code)
- Merge PRs by `feature_key`. The combined rollout status is the most restrictive one in the group: any `flagged_partial` or `unknown` means the feature is not GA.
- **Best fix for rollout status:** if you use a feature-flag system (LaunchDarkly, Unleash, a homegrown one), look the flag up through its API and use that as the source of truth. PR text is a weaker signal. Even better, add required `Release note:` and `Rollout:` fields to the PR template, so the author states it at merge time. Kubernetes uses a similar release-note block in its PRs (recalled, not verified). This moves the problem upstream, which is cheaper than any prompt.
- Send `low` confidence and `unknown` rollout items to a review list rather than dropping them.

### Stage 3: Writer (one call, small input)
The input is only the validated feature groups, not 90k tokens of raw PRs, so probably a few thousand tokens. The prompt:
- Each bullet must end with hidden PR references (for example `<!-- repo#1234 -->`).
- Wording is set by rollout status: `flagged_partial` → "Rolling out gradually / available on request", `beta` → "Beta". This is a mapping, not a judgment call.
- **Give the ranking to the writer explicitly.** Either rank by a priority field (Jira priority, epic, PM-tagged) or ask the writer to return `included` and `omitted_with_reason`. Dropping items for length is fine; dropping them silently is the bug.

Your good-notes examples belong here. They help with tone and format.

### Stage 4: Verifier
Code checks (cheap and reliable):
- Every bullet cites at least one PR, and every cited PR exists and is `customer_facing`.
- **Coverage:** every customer-facing `feature` group is either in the notes or in `omitted_with_reason`.
- No bullet uses GA language ("now available", "all customers") when its group isn't `ga`. A keyword/regex check covers most of this, and an optional small LLM check can catch paraphrases.

On failure, rerun the writer once with the error list. If it still fails, flag it in the output instead of hiding it.

### Stage 5: PM review artifact
Output the notes plus three short lists: **omitted customer-facing items (with reason)**, **rollout unknown**, **excluded by rule/model**. PMs then review a diff instead of re-reading 300 PRs, and each correction they make becomes a test case.

## Cost and runtime
- Token volume should stay in the same range as today. The ~90k tokens of PR content get spread over about 300 small calls, and the writer's input is small. The per-call instruction is repeated about 300 times, so keep it tight and use **prompt caching** on the shared prefix.
- Since this runs overnight, the **Message Batches API** is a good fit. As I recall it is about 50% cheaper than synchronous calls, with results within 24h and usually much faster (recalled, not verified; check current pricing and SLA).
- Putting a small model on the 300 extraction calls and Sonnet (or Opus, if the prose is noticeably better) on the one writer call will likely cost the same as or less than one Opus call over 90k tokens. I don't have your exact numbers. Estimate it as `Σ(input_tokens × input_price) + Σ(output_tokens × output_price)` per stage, then read the real usage from one run.

## Evaluation (so you know it's reliable, not just that it reads well)
Build a golden set from the last 3 to 5 releases using the PMs' corrections: which features should have appeared, which items were internal, and the true rollout status. Track:
- **Feature recall**: customer-facing features that appear or are explicitly omitted. Target 100%, since the coverage check enforces it.
- **Internal-leak rate**: internal items that show up in the notes.
- **Rollout accuracy**: the target is zero GA claims for non-GA features.
- Extraction accuracy per PR, which tells you whether the small model is good enough or needs upgrading.

Run the old single-call setup and the new pipeline against the same golden set. That tells you whether Opus is worth it at each stage, instead of guessing.

**If you only do two things this week:** add the deterministic pre-filter, and switch to per-PR structured extraction with evidence-backed rollout status plus a code check against GA wording. Those target all three failure types directly. The writer and verifier improvements can follow.
