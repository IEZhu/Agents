## Latest user message
Quick capacity question. Our checkout API runs on 4 pods on EKS, handles ~400 rps at peak with p95 around 180 ms, pod CPU sits at ~60%. Each pod has a HikariCP pool of 50 connections to a single Postgres primary (RDS, max_connections = 400, CPU ~45% at peak). Marketing says Black Friday will be 3x normal peak. How many pods should I set minReplicas to? I need a number for the change request today.

## Rubric (what a strong answer does)
1. Gives a concrete pod-count answer (e.g. around 12, or somewhat more with headroom) derived from the 3x traffic figure, so the request for a number is met.
2. Notices that scaling to ~12 pods with 50-connection pools gives about 600 connections, which exceeds Postgres max_connections = 400, and proposes a fix (smaller per-pod pool, a pooler such as PgBouncer/RDS Proxy, or raising the limit).
3. Flags the linear-scaling assumption, and in particular the single Postgres primary (about 45% CPU now, far beyond capacity at 3x if load scales with traffic), as the weakest or most uncertain part of the estimate rather than presenting the pod count with unqualified confidence.
4. Recommends validating the estimate before Black Friday, e.g. a load test at 3x traffic against a production-like database.

## Answer A
**Set minReplicas to 12, but also cut the Hikari pool to about 20 per pod.** The pods aren't the real constraint here: the database is. If the change request only raises minReplicas, it will very likely make Black Friday worse.

### Pod math (CPU)

- Today you're at 4 pods × 60% CPU, which is about 2.4 pods' worth of CPU for 400 rps.
- At 3x (1,200 rps) you need about 7.2 pods' worth of CPU, assuming load scales linearly.
- If you want each pod at roughly 60% at peak, so there's room for spikes and the HPA has time to react: 7.2 / 0.6 = **12 pods**.
- Set maxReplicas to about 16 so a traffic spike above 3x can still scale out.

### Why 12 pods with the current pool breaks things

**1. Connections.** 12 pods × 50 connections = **600**, but RDS `max_connections` is **400**. Even at 8 pods you'd hit the limit. A rolling deploy with `maxSurge` adds more pods, and each new pod opens its own pool, so you'd go over even sooner. Once the limit is hit, new pods fail on connection errors and the checkout API starts returning errors.

You don't need 50 connections per pod anyway. By Little's law, 1,200 rps × about 0.15–0.18 s ≈ 180–220 requests in flight across the whole fleet, and only part of each request's time is spent holding a DB connection. With a pool of **20 per pod**:
- 12 pods × 20 = 240 connections
- 16 pods × 20 = 320 connections
- That leaves room under 400 for surge pods, migrations, admin sessions and the connections RDS reserves for itself.

If you ever need more than that, put RDS Proxy or PgBouncer in front of the database.

**2. Database CPU.** RDS is at 45% CPU at 400 rps. If that scales linearly, 1,200 rps needs about **135%**. It probably won't be exactly linear, since lock and buffer contention usually make things worse under load, not better. So the primary as it stands probably can't handle 3x, however many pods you add. Options, roughly in order of effort:
- **Move up an instance class** before the event. This is the fastest fix, and you can scale back down afterwards. It costs more per hour while it runs.
- **Move read-only queries to a read replica**, if checkout has any (price and inventory lookups, for example).
- **Find and fix the top queries** using Performance Insights or `pg_stat_statements`.

### What to put in the change request

1. Deployment/HPA: `minReplicas: 12`, `maxReplicas: 16`.
2. Hikari `maximumPoolSize: 20`. Consider setting `minimumIdle` equal to it so the pool doesn't churn connections.
3. RDS: resize the instance class before the event, with a rollback date to scale back down.
4. Make sure the node group or Karpenter can actually schedule 16 pods. Check the ASG max and your EC2 vCPU quota.

**Blast radius:** if the database saturates, every checkout slows down or fails, not just some of them. If the pods run short, you get higher latency, which the HPA can recover from.

**Rollback:** the pod count and pool size are config-only changes, so reverting them is easy. An RDS resize means a Multi-AZ failover of a minute or two in each direction, so schedule it outside peak hours.

### Before you commit to these numbers

Everything above assumes load scales linearly from a single data point. **Load-test at 1,200 rps against a production-sized database** before Black Friday, and watch pod CPU, Hikari pending threads, RDS CPU and `DatabaseConnections`. If you can't test in time, add more headroom on the database side rather than the pod side.


## Answer B
**For the change request, set `minReplicas: 12`.** But pods aren't what will limit you on Black Friday. Two other problems come first, and 12 pods with your current config will make one of them worse.

## Pod math

- Now: 4 pods × 60% CPU = 2.4 pods' worth of CPU for 400 rps.
- 3x traffic: 1,200 rps → about 7.2 pods' worth, if CPU scales linearly with rps. That's roughly true for a stateless API, but check it with a load test.
- To keep the same ~60% headroom: 7.2 / 0.6 = **12 pods**.
- Set `maxReplicas` to about 16 so HPA can absorb a spike above the forecast.
- Pre-scale a day or two ahead, and make sure the node group, Cluster Autoscaler or Karpenter can actually place 12–16 pods. Otherwise you'll have pending pods at 00:01.

This assumes "3x normal peak" means 3 × 400 rps. If marketing meant 3x average traffic, the number is lower. Confirm with them, but 12 is the safe choice.

## Blocker 1: connection pool overflow

- Today: 4 × 50 = 200 connections.
- At 12 pods: 12 × 50 = **600**, more than `max_connections = 400`. RDS also keeps a few connections for its own admin user, so the real limit is slightly lower.
- New pods will fail to get connections once the database hits the limit. That shows up as 5xx errors or pods failing readiness, right at peak.

**Fix: shrink the Hikari pool to about 20 per pod.**
- Little's law: 1,200 rps × 0.18 s ≈ 216 requests in flight across the whole fleet, or about 18 per pod at 12 pods. The time each request spends in the database is shorter than that, so 50 connections per pod is far more than you need.
- 16 pods × 20 = 320 connections, which stays under 400 even at `maxReplicas`.
- Freeze deploys during the event. A rolling update's `maxSurge` adds extra pods, and each one opens another pool.

## Blocker 2: the Postgres primary

- Database CPU is 45% at 400 rps. Scaled linearly, that's **about 135% at 1,200 rps**. The primary saturates, and adding pods only puts more queued load on it.
- It might not be perfectly linear, since caching and query mix matter, but I wouldn't bet Black Friday on it.
- Options, roughly in order of effort:
  1. **Move the RDS instance up a size class** (for example, double the vCPUs). Do it weeks ahead, not days. With Multi-AZ the resize still triggers a failover of about 1–2 minutes, so schedule a window. It costs more, so cover it in the change request, and you can size back down afterwards.
  2. **Send read-only queries to a read replica** (product and price lookups, for example). Checkout writes stay on the primary. This needs code changes plus a second Hikari pool.
  3. **Fix the top queries.** `pg_stat_statements` will show the heaviest ones, and one missing index can easily be worth 20% CPU.
  4. Cache read-heavy lookups in Redis or ElastiCache.

## What I'd put in the change request

| Item | Value |
|---|---|
| HPA `minReplicas` | 12 (from 4) |
| HPA `maxReplicas` | 16 |
| Hikari `maximumPoolSize` | 20 (from 50) |
| RDS instance | one size up, scheduled weeks ahead |
| Deploy freeze | Black Friday window |
| Pre-scale timing | 24–48 h before |

**Blast radius:** if the pool change goes wrong (too small), requests time out waiting for a connection. You'll see it in HikariCP's pending-threads metric and in p95 latency. If the RDS resize fails, the database is unavailable during the failover.

**Rollback:** reverting `minReplicas` and the pool size is a config revert plus a rolling restart. You can also resize RDS back down, which triggers another failover.

**Before the event, verify** with a load test at 1,200 rps or more against a staging copy at production size. Watch pod CPU, Hikari active and pending connections, RDS CPU, and `numbackends`. Without that test, the 12-pod number is an estimate, not a guarantee.
