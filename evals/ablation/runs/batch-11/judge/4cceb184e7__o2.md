## Latest user message
We have an internal docs tool: engineers paste a short plain-text description of a request flow between services, and we call an LLM to turn it into a Mermaid sequence diagram that gets rendered straight into the page with mermaid 10.9. Our prompt is basically "Convert the following description into a Mermaid sequence diagram. Use participants with short aliases. Output only Mermaid code." + the description. Results are all over the place: sometimes it's wrapped in ```mermaid fences and sometimes not, sometimes it outputs `graph TD` instead of a sequence diagram, participant aliases change style between runs (`API`, `api_gw`, `ApiGateway`), and once in a while there's a sentence of explanation after the code, which makes the renderer throw a parse error. We want every diagram to start with `sequenceDiagram`, then `autonumber`, then participants declared as `participant GW as API Gateway` style, in the order they first appear. Can you rewrite the prompt so the output is consistent? Use this description as the example: "Mobile app calls API Gateway, gateway validates the JWT with Auth Service, then forwards to Orders Service which reads from Postgres and returns the order; gateway returns 200 to the app."

## Rubric (what a strong answer does)
1. The rewritten prompt ends with (or instructs pre-starting the model's reply with) the opening lines of the diagram itself, at least 'sequenceDiagram' and 'autonumber', and possibly the first participant line, for the model to continue.
2. The answer explains or handles how the output ends so no prose follows the diagram (e.g. a stop marker, or cutting after the last message line) and notes that the caller must prepend the pre-written opening back when assembling the final Mermaid text if the model only returns the continuation.
3. The example diagram for the given description is valid Mermaid sequence syntax, declares participants in first-appearance order (Mobile app, API Gateway, Auth Service, Orders Service, Postgres) using 'participant X as Name', and includes the JWT validation, forward to Orders, Postgres read and the 200 response back to the app.
4. The answer keeps to the user's required conventions and does not switch to a flowchart or a different alias scheme.

## Answer A
The current prompt leaves most of the format up to the model: fences or no fences, which diagram type, how to name aliases, and whether it can add text after the code. Each inconsistency you listed comes from one of those gaps. The rewrite below states every one of them as a rule and includes a complete worked example. The model tends to copy an example more reliably than it follows prose. You should still clean the output in code before rendering, because no prompt makes an LLM 100% reliable.

## 1. System prompt

```text
You convert plain-text descriptions of request flows between services into Mermaid sequence diagrams. Your output is passed directly to the Mermaid 10.9 parser with no human review, so any character that is not valid Mermaid breaks the page.

OUTPUT CONTRACT (all rules are mandatory):
1. Output raw Mermaid source only. No ``` fences, no language tag, no text before or after, no comments.
2. Line 1 is exactly: sequenceDiagram
3. Line 2 is exactly: autonumber
4. Next, declare every participant, one per line, in the order it first appears in the description:
   participant <ALIAS> as <Display Name>
   Use "participant" for everything, including users and databases. Never use "actor", "graph", "flowchart", or any other diagram type.
5. After the participants, write the messages in the order they happen.

ALIAS RULES (aliases must be identical across runs):
- ALIAS is 2-5 uppercase letters (A-Z only). No digits, underscores, spaces, or camelCase.
- If the component appears in this table, use its alias:
    API Gateway -> GW
    Auth Service -> AUTH
    Orders Service -> ORD
    Payments Service -> PAY
    Postgres / PostgreSQL -> PG
    Redis -> REDIS
    Kafka -> KAFKA
    Mobile App -> APP
    Web App / Browser -> WEB
- Otherwise, use the first meaningful word of the name in uppercase and drop generic suffixes such as "Service", "API", or "Server" (e.g. "Inventory Service" -> INV, "Notification Service" -> NOTIF). If two aliases collide, add a letter to the second one.
- Display Name is the component's name in Title Case, as written in the description.

MESSAGE RULES:
- Synchronous request: A->>B: text
- Response or return value: B-->>A: text
- Add a response arrow only when the description states or clearly implies one (e.g. "validates", "returns", "reads"). Do not invent steps, endpoints, HTTP methods, or status codes that the description does not mention.
- Message text: 1-5 words, plain words only. Never use ; # { } or line breaks in message text.
- Do not use notes, loops, alt/opt blocks, activations, or styling unless the description explicitly describes a loop or a branch.

If the description is ambiguous, pick the simplest reading and still output a valid diagram. Never ask questions and never explain.
```

## 2. User message template (includes one worked example)

```text
Example description:
Mobile app calls API Gateway, gateway validates the JWT with Auth Service, then forwards to Orders Service which reads from Postgres and returns the order; gateway returns 200 to the app.

Example output:
sequenceDiagram
autonumber
participant APP as Mobile App
participant GW as API Gateway
participant AUTH as Auth Service
participant ORD as Orders Service
participant PG as Postgres
APP->>GW: Request order
GW->>AUTH: Validate JWT
AUTH-->>GW: JWT valid
GW->>ORD: Forward request
ORD->>PG: Read order
PG-->>ORD: Order row
ORD-->>GW: Order
GW-->>APP: 200 OK

Description:
<<<
{description}
>>>

Output:
```

Why it looks like this:
- **Example with no fences.** If the example were wrapped in ```` ``` ````, the model would copy the fences. Here it shows exactly the bytes you want.
- **No indentation in the example.** Mermaid accepts indented lines, but flat lines leave nothing for the model to vary between runs.
- **"Request order", not `GET /orders`.** The example follows its own no-invention rule. If the model sees an invented method in the example, it will invent them for real inputs too.
- **Alias table.** This is what fixes `API` / `api_gw` / `ApiGateway`. The fallback rule alone isn't deterministic enough. Add your real service names to the table as you go; it's the most effective single change for consistency.
- **I used `PG` instead of `DB` for Postgres.** If a flow ever involves two databases, a generic `DB` alias collides. Change it if you prefer `DB`.
- **`<<< >>>` delimiters** keep instructions pasted inside a description from being read as part of your prompt.

## 3. API settings

- Set `temperature` to 0 (or as low as your provider allows). This does more for alias consistency than any wording change.
- If your provider supports prefilling the assistant turn, prefill `sequenceDiagram\nautonumber\n` and prepend those two lines to the response. That removes the "wrong diagram type" failure entirely.
- Set a stop sequence of ```` ``` ```` (and/or `\n\n\n`) so the model can't add a code fence or trailing explanation.

## 4. Clean the output before rendering

```js
function extractMermaid(raw) {
  let s = raw.trim();
  // strip ``` / ```mermaid fences if present
  const fenced = s.match(/```(?:mermaid)?\s*\n([\s\S]*?)```/);
  if (fenced) s = fenced[1].trim();
  // cut anything before the header
  const start = s.indexOf('sequenceDiagram');
  if (start === -1) throw new Error('Not a sequence diagram');
  s = s.slice(start);
  // keep only lines that look like Mermaid sequence syntax (drops trailing prose)
  const ok = /^(sequenceDiagram|autonumber|participant\s|actor\s|[A-Za-z]+\s*-{1,2}>>|[A-Za-z]+\s*-{1,2}[x)]|Note\s|loop\s|alt\s|else|opt\s|end$)/;
  const lines = s.split('\n').map(l => l.trim()).filter(Boolean);
  const cut = lines.findIndex(l => !ok.test(l));
  return (cut === -1 ? lines : lines.slice(0, cut)).join('\n');
}

const code = extractMermaid(llmOutput);
if (!code.startsWith('sequenceDiagram\nautonumber')) { /* retry once */ }
const valid = await mermaid.parse(code, { suppressErrors: true });
if (!valid) { /* retry once, then show the source as a code block instead of a broken render */ }
```

About `mermaid.parse`: I remember that in v10 it is async and, with `{ suppressErrors: true }`, returns `false` instead of throwing. I didn't check that against the 10.9 docs, so confirm it there. If it doesn't work that way in your version, wrap it in `try/catch` instead.

A good way to test the prompt: run it about 20 times on this description and on 3-4 real ones from your docs. Then diff the outputs. With temperature 0 and the alias table, differences should be limited to the wording of message text.


## Answer B
Your current prompt leaves most of the format up to the model. It says "sequence diagram" but doesn't give the exact first lines, it doesn't say how to write aliases, and it doesn't say what to do with fences or explanations. The fix is to spell out the output contract and show one complete example. After that, add a small sanitizer as a safety net, because a prompt reduces format drift but doesn't guarantee against it.

## 1. System prompt

```text
You convert plain-text descriptions of request flows between services into Mermaid sequence diagrams. Your output is passed directly to a Mermaid 10 renderer with no human review, so it must be valid Mermaid and nothing else.

OUTPUT CONTRACT (all rules are mandatory):
1. The first line is exactly: sequenceDiagram
2. The second line is exactly: autonumber (indented 4 spaces)
3. Next, declare every participant, one per line, in the order it first appears in the description, using exactly this form:
       participant <ALIAS> as <Display Name>
4. After the declarations, write the messages in the order they happen.
5. Output raw Mermaid only. No ``` fences, no "mermaid" label, no comments, no blank lines, no text before or after the diagram.
6. Never use graph, flowchart or any diagram type other than sequenceDiagram.

ALIAS RULES:
- UPPERCASE letters and digits only, 2 to 5 characters, no spaces, underscores or hyphens.
- Use the well-known abbreviation if one exists (API Gateway -> GW, Postgres -> PG, Redis -> RDS); otherwise use the initials or the first letters of the main word (Auth Service -> AUTH, Orders Service -> ORD, Mobile App -> APP).
- Never use END, OPT, ALT, LOOP, PAR, NOTE or other Mermaid keywords as aliases.
- Display Name is the name from the description in Title Case.

MESSAGE RULES:
- Requests use ->>  and responses use -->>
- Labels are short (2 to 5 words) and verb-first: "Validate JWT", "Read order", "200 OK".
- Labels must not contain ; # : or line breaks.
- Draw a response arrow only where the description states or clearly implies a return (for example, "validates X with Y" implies Y replies to the caller).
- Don't invent steps, endpoints, HTTP methods or status codes that the description doesn't mention.

EXAMPLE
Description:
Mobile app calls API Gateway, gateway validates the JWT with Auth Service, then forwards to Orders Service which reads from Postgres and returns the order; gateway returns 200 to the app.

Output:
sequenceDiagram
    autonumber
    participant APP as Mobile App
    participant GW as API Gateway
    participant AUTH as Auth Service
    participant ORD as Orders Service
    participant PG as Postgres
    APP->>GW: Request order
    GW->>AUTH: Validate JWT
    AUTH-->>GW: JWT valid
    GW->>ORD: Forward request
    ORD->>PG: Read order
    PG-->>ORD: Order row
    ORD-->>GW: Return order
    GW-->>APP: 200 OK
```

## 2. User message

Put only the description in the user message, wrapped in tags so it's clearly marked as input:

```text
<description>

## 3. Call settings

- **Temperature 0.** Much of the alias drift you're seeing (`API` / `api_gw` / `ApiGateway`) is probably sampling variance. The alias rules plus temperature 0 should remove most of it.
- **Prefill the answer if your API allows it.** Start the assistant turn with `sequenceDiagram\n    autonumber\n` and let the model continue from there. The output can't then start with a fence or with `graph TD`. You'll need to prepend those two lines yourself before rendering. Some providers and newer models don't support prefill, so check this for the model you use.
- **Optional:** if you have a fixed set of services, add a small glossary to the system prompt (`Orders Service -> ORD`, `Billing Service -> BILL`, ...). Then aliases stay the same across diagrams and not just across runs.

## 4. Sanitizer before rendering

Still validate before rendering. A small check prevents the parse errors from reaching the page:

```js
function extractMermaid(raw) {
  let text = raw.replace(/```(?:mermaid)?/gi, "");     // strip any fences
  const start = text.indexOf("sequenceDiagram");
  if (start === -1) throw new Error("not a sequence diagram");
  text = text.slice(start);
  // keep only lines that look like Mermaid; drops trailing prose
  const ok = /^(sequenceDiagram|\s+(autonumber|participant\s|actor\s|note\s|[A-Z0-9]+\s*-?->>|activate|deactivate|alt|else|opt|loop|par|and|end\b|rect))/i;
  return text.split("\n").filter(l => ok.test(l)).join("\n").trim();
}

const code = extractMermaid(llmOutput);
await mermaid.parse(code);   // throws on invalid syntax in 10.x
```

If `mermaid.parse` fails, retry the LLM call once with the parse error appended ("Your previous output failed to parse: <error>. Return corrected Mermaid only."). If the retry also fails, show a fallback message and don't render the broken diagram.

Two things I haven't checked against mermaid 10.9, so verify them in the docs for your version:
- I'm recalling from memory that `mermaid.parse` is async and throws on invalid input in 10.x. I also recall a `{ suppressErrors: true }` option that returns `false` instead of throwing, but I'm not sure which version added it.
- The line filter is deliberately simple. If you later allow notes or `alt` blocks with complex labels, loosen the regex.
