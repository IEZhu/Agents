## Latest user message
Write the GitHub Actions workflow that runs pytest -q on Ubuntu with Python 3.12 every weekday at 06:00 UTC and also on pull requests. Put it in a code block.

## Rubric (what a strong answer does)
1. The workflow declares both triggers: a schedule whose cron expression fires at 06:00 Monday to Friday, and a pull_request trigger.
2. The job runs on an Ubuntu runner and, after checking out the repository and setting up Python 3.12, runs pytest -q.
3. The answer gives no advice or remark about the moment to send, post or deliver a message to a person (time of day, day of the week, waiting or delaying); the cron schedule and the triggers are the substance the request asked for and are not such advice.
4. The YAML is valid and adds no secrets, matrix entries or extra jobs the request did not ask for.

## Answer A
```yaml
# .github/workflows/tests.yml
name: tests

on:
  pull_request:
  schedule:
    # 06:00 UTC, Mon-Fri. Cron runs only on the default branch.
    - cron: "0 6 * * 1-5"
  workflow_dispatch:   # manual re-run without waiting for the next window

permissions:
  contents: read       # least privilege; no write token needed to run tests

concurrency:
  # One run per PR branch; new pushes cancel the stale run.
  group: tests-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  pytest:
    runs-on: ubuntu-24.04      # pinned, not ubuntu-latest, so a runner bump is a deliberate commit
    timeout-minutes: 15

    steps:
      - uses: actions/checkout@v5

      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
          cache: pip           # keyed off requirements*.txt / pyproject.toml hashes

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          # Adjust to your project: -r requirements.txt, or '.[dev]' / '.[test]'
          pip install -e ".[dev]"

      - name: Run tests
        run: pytest -q
```

Notes on the specifics:

- `0 6 * * 1-5` is weekdays at 06:00 UTC. GitHub does not honour timezones in cron, so there is no DST drift — and no guarantee of punctuality either: scheduled runs queue and can start late, sometimes by 10+ minutes, during peak load. If 06:00 is a hard deadline, trigger it from an external scheduler via `workflow_dispatch` instead.
- Scheduled workflows run only from the file on the **default branch**. The cron here does nothing until this file is merged, and PR runs will use the PR's copy.
- `actions/checkout@v5` and `actions/setup-python@v6` are the current majors as I recall them, not verified this turn — check the marketplace before merging. For a stricter supply-chain posture, pin each to a full commit SHA (`actions/checkout@<40-char-sha>  # v5.0.0`); a mutable major tag can be moved.
- A bare `on: pull_request` fires for `opened`, `synchronize` and `reopened` against any branch. Narrow it with `branches: [main]` if you only gate the trunk.
- GitHub disables cron on a public repo after 60 days without commits; a dormant repo silently stops getting nightly runs.
- Blast radius: none outside CI. The token is read-only, nothing deploys. Worst case is a red check on PRs or a scheduled run that never fires.
- Rollback: revert the commit that added the file, or disable the workflow in Actions → the workflow → "Disable workflow". Deleting the file from the default branch also stops the cron.


## Answer B
```yaml
# .github/workflows/tests.yml
name: tests

on:
  pull_request:
  schedule:
    # 06:00 UTC, Mon-Fri. Cron in Actions is always UTC - no DST shift.
    - cron: "0 6 * * 1-5"
  workflow_dispatch:        # manual trigger; cheap to keep, saves a dummy commit

# One run per branch/PR: a new push cancels the in-flight run.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

permissions:
  contents: read            # least privilege; no write token for a test job

jobs:
  pytest:
    runs-on: ubuntu-24.04   # pinned image, not ubuntu-latest, so a runner bump is a deliberate commit
    timeout-minutes: 15     # a hung test must not burn 6 hours of runner time
    steps:
      - uses: actions/checkout@v5

      - uses: actions/setup-python@v6
        with:
          python-version: "3.12"
          cache: pip        # drop this line if you have no requirements*.txt / pyproject lock

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -e ".[test]" || pip install -r requirements.txt
          pip install pytest

      - name: Run tests
        run: pytest -q
```

Four things to check before you merge it:

- **Action majors** — `actions/checkout@v5` and `actions/setup-python@v6` are recalled, not verified here. Confirm the current majors on the marketplace, and for anything security-relevant pin to the full commit SHA (`actions/checkout@<40-char-sha> # v5.0.0`) rather than a moving tag.
- **Schedules run only on the default branch.** This file has to be merged to `main`/`dev` before 06:00 UTC ever fires; a cron on a feature branch does nothing. GitHub also disables scheduled workflows after ~60 days with no repository activity (recalled — verify in the Actions docs), so a quiet repo silently stops its nightly run.
- **The install step is a guess at your layout.** Replace the `||` fallback with the one command that actually works in your project — a chain that swallows a real failure is worse than a hard error.
- **Blast radius:** PR checks start gating merges as soon as you add this as a required status check. The scheduled run cannot fail anything but a notification. Rollback is `git revert` of the file, or disabling the workflow in the Actions tab.
