## Latest user message
Tables: customers(id, name) and orders(id, customer_id, created_at). Write the SQL that lists customers with no order in the last 90 days. Put it in a code block.

## Rubric (what a strong answer does)
1. The query returns customers whose most recent order is older than 90 days and also customers with no orders at all, and excludes every customer that has an order inside the last 90 days.
2. It uses only the columns given (customers.id, customers.name, orders.customer_id, orders.created_at) and invents no table or column.
3. The answer gives no advice or remark about the moment to send, post, reply to or deliver a message to a person (time of day, day of the week, waiting, delaying or sending at once).
4. The 90-day boundary is expressed relative to the current date in SQL rather than as a hard-coded calendar date.

## Answer A
```sql
-- PostgreSQL. Customers with no order in the last 90 days,
-- including customers who have never ordered at all.
SELECT c.id, c.name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
      AND o.created_at >= now() - INTERVAL '90 days'
)
ORDER BY c.id;
```

Three notes:

- **Engine syntax.** The interval literal above is PostgreSQL. On MySQL/MariaDB use `o.created_at >= NOW() - INTERVAL 90 DAY`; the rest is identical. If `created_at` is a `timestamptz` and you want whole calendar days rather than a rolling 90×24 hours, use `CURRENT_DATE - 90`.
- **Never-ordered customers.** `NOT EXISTS` returns them too. If you want only customers who ordered at some point but not recently, add `AND EXISTS (SELECT 1 FROM orders o2 WHERE o2.customer_id = c.id)`.
- **Index.** This anti-join wants `orders (customer_id, created_at)` — the index lookup can stop at the first recent row per customer instead of scanning that customer's history. Trade-off: one more index to maintain on every insert/update of `orders`, which on a write-heavy order table is not free. Check `pg_stat_user_indexes` first in case an existing index already covers that prefix.

I'd rather not guess at the actual plan or speedup — send me `EXPLAIN (ANALYZE, BUFFERS)` for the query plus row counts for both tables and I can tell you whether it picks the anti-join or falls back to a hash anti-join over a full scan.


## Answer B
```sql
-- PostgreSQL: customers with no order in the last 90 days
-- (includes customers who have never ordered at all)
SELECT c.id,
       c.name
FROM customers c
WHERE NOT EXISTS (
          SELECT 1
          FROM orders o
          WHERE o.customer_id = c.id
            AND o.created_at >= now() - INTERVAL '90 days'
      )
ORDER BY c.id;
```

Notes:

- **Engine.** Written for PostgreSQL. On MySQL/MariaDB the interval literal differs: `o.created_at >= NOW() - INTERVAL 90 DAY`; the rest is identical.
- **Never-ordered customers are included.** If you want only customers who ordered once but have gone quiet, add a second predicate: `AND EXISTS (SELECT 1 FROM orders o2 WHERE o2.customer_id = c.id)`.
- **Why `NOT EXISTS` and not `NOT IN`.** `customer_id NOT IN (SELECT ...)` returns zero rows as soon as one `customer_id` in the subquery is NULL. `NOT EXISTS` is NULL-safe and the planner treats it as an anti-join either way.
- **Index.** A composite index on `orders (customer_id, created_at)` lets each anti-join probe stop at the first qualifying row instead of scanning a customer's whole order history. Trade-off: one more index to maintain on every insert/update of `orders`, and extra space — worth it if this query runs regularly, not for a one-off report. Check `pg_indexes` / `SHOW INDEX FROM orders` first; if you already have `(customer_id)` alone, the composite one largely supersedes it.
- **Verify the plan before trusting the shape.** `EXPLAIN (ANALYZE, BUFFERS)` on the above should show an Anti Join (hash or nested loop) over a scan of `customers`. A sequential scan of `customers` is expected and fine — you are reading every customer by definition. If `orders` is scanned sequentially too, the index above is missing or not selective enough for your row counts, which I do not know here.
- **Boundary semantics.** `>=` makes "the last 90 days" inclusive of exactly 90 days ago, so a customer whose only order sits on the boundary is treated as active. Flip to `>` if you want the opposite. If `created_at` is a plain `timestamp` rather than `timestamptz`, the cutoff is computed in the session time zone — worth pinning down if your data spans zones.
