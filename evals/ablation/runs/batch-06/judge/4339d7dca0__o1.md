## 1. Формат: включите Structured Outputs, а не пишите КАПСОМ

КАПС и строгие фразы снижают процент ошибок, но не убирают его. Это видно и по вашему опыту: чуть лучше стало, а совсем не ушло. У OpenAI есть `response_format` с `json_schema` и `strict: true`. В этом режиме декодирование ограничено схемой: модель физически не может обернуть ответ в ```json или вернуть urgency вне enum. Насколько я помню, `gpt-4o-mini` его поддерживает (это не проверено здесь, сверьтесь с документацией OpenAI по Structured Outputs).

```python
response_format = {
    "type": "json_schema",
    "json_schema": {
        "name": "ticket_classification",
        "strict": True,
        "schema": {
            "type": "object",
            "properties": {
                "category": {"type": "string",
                             "enum": ["billing", "bug", "feature_request", "account", "other"]},
                "urgency":  {"type": "string", "enum": ["low", "medium", "high"]},
                "reason":   {"type": "string",
                             "description": "Одно предложение НА РУССКОМ, даже если тикет на другом языке"}
            },
            "required": ["category", "urgency", "reason"],
            "additionalProperties": False
        }
    }
}
```

Что это даёт:
- ```json-обёртки исчезают;
- `"High"` или `"срочно"` в urgency невозможны, потому что допускаются только значения из enum;
- фразы «не добавляй текст», «не используй markdown» и «строго JSON» из промпта можно удалить, они больше не нужны.

Ещё стоит поставить `temperature=0`: для классификатора так стабильнее.

## 2. Язык reason: здесь нужен промпт и пример

Схема задаёт только тип поля (строка), язык она не ограничивает. Что помогает:
- **Объяснить причину, а не усиливать запрет.** Например: «reason пишется на русском независимо от языка обращения: его читает русскоязычная команда». Модели лучше выполняют правило, когда понимают, зачем оно.
- **Добавить few-shot с английским тикетом и русским reason.** Именно этот случай ломается, и один такой пример обычно действует сильнее любого количества инструкций.
- **Добавить страховку в коде.** Если в reason нет кириллицы (простой regex), сделайте повторный запрос или перевод. Это дешёвая страховка на случай оставшихся сбоев.

## 1. Формат и enum: Structured Outputs вместо уговоров

Обёртка в ```json и значения вроде "High"/"срочно" лечатся через `response_format` с JSON Schema в strict-режиме. В этом режиме модель не может выдать ничего, кроме JSON по схеме, а `enum` жёстко ограничивает набор значений.

```python
response = client.chat.completions.create(
    model="gpt-4o-mini",
    temperature=0,
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": ticket_text},
    ],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "ticket_classification",
            "strict": True,
            "schema": {
                "type": "object",
                "properties": {
                    "category": {
                        "type": "string",
                        "enum": ["billing", "bug", "feature_request", "account", "other"]
                    },
                    "urgency": {
                        "type": "string",
                        "enum": ["low", "medium", "high"]
                    },
                    "reason": {
                        "type": "string",
                        "description": "Одно предложение на русском языке, даже если обращение на другом языке."
                    }
                },
                "required": ["category", "urgency", "reason"],
                "additionalProperties": False
            }
        }
    },
)
```

Проверьте по документации OpenAI: структура `response_format` / `json_schema` / `strict` и поддержка strict-режима у gpt-4o-mini (насколько помню, начиная со снапшота `gpt-4o-mini-2024-07-18`) приведены по памяти, я их здесь не проверял. По тем же данным strict-режим требует, чтобы `additionalProperties: false` стоял и все поля были в `required`.

Обычный `{"type": "json_object"}` не подойдёт: он гарантирует только валидный JSON, но не значения enum.

## 2. Язык reason: схема этого не гарантирует

Никакой enum не заставит модель писать по-русски. Поэтому здесь три шага:

- **Пример вместо капса.** Добавьте в промпт один few-shot пример с тикетом на английском и `reason` на русском. Пример работает надёжнее любой формулировки «СТРОГО НА РУССКОМ».
- **Инструкция и в промпте, и в `description` поля.** Выше это уже сделано.
- **Проверка в коде.** Если в `reason` мало кириллицы (например, меньше 50% букв), отправляйте повторный запрос или отдельный дешёвый вызов «переведи на русский». На частоте 5–7% это дёшево, и такая проверка ловит то, что промпт пропустит.

После перехода на strict-схему ошибки формата и enum должны исчезнуть совсем. Останутся язык `reason` и качество самой классификации, а их вы теперь сможете измерять.
