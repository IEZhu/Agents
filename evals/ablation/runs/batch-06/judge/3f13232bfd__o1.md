## Latest user message
I have an internal text-to-SQL tool on Postgres 15 for our ops team. The prompt has the schema (orders, order_items, customers, warehouses, shipments) and then 6 hardcoded example pairs I wrote when we launched, like "how many orders yesterday" -> SELECT count(*) FROM orders WHERE created_at::date = current_date - 1, "list customers in Texas", "total revenue in March". Accuracy on simple lookups is fine, but when people ask things like "which warehouses had more than 10 late shipments last week, compared to the week before" or "customers who ordered in Q1 but not Q2", it produces wrong joins or forgets the anti-join entirely. I have about 900 question/SQL pairs from the last few months that the analysts have already verified. My plan is to just add 30 more of the hardest ones to the static example block. Is that the right move?

## Answer A
**Short answer: no.** Adding 30 more static examples is probably the weakest way to use 900 verified pairs. Retrieve the relevant examples for each question instead, and build an eval set first so you can measure whether the change helped.

## Why a bigger static block is the wrong lever

- **Coverage doesn't scale.** "Q1 but not Q2" needs an anti-join example. "Week vs week before" needs a period-comparison example. Thirty hand-picked hard cases will cover some patterns and miss others, and the next odd question will fail the same way.
- **Every request pays for all of it.** Roughly 36 examples at 100–200 tokens each adds several thousand tokens to every call, including "how many orders yesterday". That's a rough estimate; count it on your own examples.
- **Few-shot bias cuts both ways.** Examples shape output more than instructions do. A block full of complex CTEs can push simple questions toward over-engineered SQL, so you could lose accuracy where you have it now.
- **You'd be guessing.** Without a held-out test set you can't tell whether 30 examples beat 6, or whether they broke the simple lookups.

## What I'd do instead

### 1. Carve out an eval set first
- Hold out about 150–200 of the 900 pairs, stratified by type: simple lookup, aggregation, multi-join, anti-join, period comparison, window functions.
- Score on **execution accuracy**: run the generated SQL and the gold SQL, then compare result sets. Don't compare SQL strings, because many different queries are correct.
- Report accuracy per category, not just one overall number. Your problem is concentrated in a few categories, and a single average will hide it.

### 2. Dynamic few-shot retrieval (the main fix)
- Embed the questions of the remaining ~700 pairs. At query time, retrieve the top 4–8 most similar pairs and put those in the prompt.
- Keep 2–3 static examples of the basics as a floor.
- Refinement: before embedding, mask literals ("Texas" → `<state>`, "March" → `<month>`). Then retrieval matches on the *shape* of the question ("X in period A but not period B") instead of its surface words. Published text-to-SQL work (DAIL-SQL, from memory, not verified here) found that selecting examples by question/SQL-structure similarity beats random or fixed examples. Your eval set will tell you whether it holds on your data.
- Guard against leakage: when you evaluate, make sure a test question can't retrieve its own pair.

### 3. Put the missing semantics in the schema, not in examples
Many "wrong join" errors come from the model not knowing your business definitions. Annotate the schema directly:
- Explicit join paths: `order_items.order_id → orders.id`, `shipments.order_id → orders.id`, `shipments.warehouse_id → warehouses.id`. Use your real keys; these names are illustrative.
- Definitions, for example "a shipment is **late** when `delivered_at > promised_at`, or when it's undelivered and `now() > promised_at`". If the model has to guess what "late" means, no amount of examples will fix it reliably.
- Time conventions: which timezone "yesterday" means, and whether weeks start on Monday (`date_trunc('week', …)` in Postgres uses ISO weeks, which start Monday).

### 4. A short list of pattern rules for known traps
Keep this to 5–8 rules, not 50:
```
- "in A but not B" → NOT EXISTS subquery. Never NOT IN (NULLs break it) and never a plain INNER JOIN.
- Counting orders while joining order_items → count(DISTINCT o.id) or aggregate items in a subquery first (fan-out).
- "compared to previous period" → aggregate each period in a CTE (or FILTER (WHERE …)), then join/compare the CTEs.
- Date filters: use half-open ranges (created_at >= X AND created_at < Y), not created_at::date = …
```
That last rule applies to your own launch example. `created_at::date = current_date - 1` works, but it can't use a plain index on `created_at`, and it follows the session timezone. Change that example too, or the model will keep copying the pattern.

### 5. Optional: plan, then write SQL, then self-check
For questions that retrieval flags as complex (for example, when the nearest examples contain CTEs or anti-joins), ask the model to list the tables, join keys, filters and grain before it writes the SQL. Then run `EXPLAIN` on the output, and on an error send the message back once for a repair. That catches syntax and column-name errors cheaply. It won't catch wrong semantics; only the eval set does that.

## Order of operations
1. Build the eval set and measure the current prompt, per category.
2. Add schema annotations and pattern rules, and re-measure. This is cheap and may fix a surprising amount.
3. Add dynamic retrieval and re-measure.
4. Only then consider plan-then-SQL for what's still failing.

Change one thing at a time so you know which change moved which category.

## Caveats
- Retrieval quality depends on how varied the 900 pairs are. If they're 70% simple lookups, the hard categories may have too few neighbours. Check the category counts; you may need to write 10–20 extra hard examples. That's the one place your "add hard ones" instinct is right, but they should go into the **retrieval pool**, not the static prompt.
- Security note, since this is ops-facing: run the generated SQL as a read-only role with `statement_timeout` set. Don't rely on the prompt to prevent writes or runaway queries.


## Answer B
Not quite. Adding 30 hard examples to a static block will probably help a little, but it doesn't use most of what you have. You're sitting on 900 verified pairs. The usual fix for this kind of failure is **dynamic few-shot retrieval**: for each incoming question, pull the 5–8 most similar verified pairs into the prompt. The static block stays small.

## Why the static-30 plan is weak

- **Coverage.** Ops questions come in many shapes: anti-joins, period-over-period, HAVING thresholds, multi-hop joins through `order_items`/`shipments`. 30 fixed examples cover a few of them. The other ~870 verified pairs sit unused.
- **Few-shot bias.** Examples shape output more than instructions do. With 36 static examples, most are irrelevant to any given question. They add noise and can pull the model toward the wrong pattern. For example, a "Q1 vs Q2" question may copy the shape of a "revenue in March" example.
- **Cost and latency.** You pay for every example on every request, including the simple ones that already work.
- **No measurement.** Right now you can't tell whether adding 30 examples improves the hard cases or quietly breaks the easy ones.

## What to do instead

**1. Split the 900 pairs before anything else**
- Hold out about 150–200 as a **golden eval set**. Stratify it so the hard categories are well represented (anti-join, period comparison, multi-table aggregation).
- The remaining ~700 become the **retrieval pool**.
- Never retrieve from the eval set. Otherwise your accuracy numbers mean nothing.

**2. Dynamic few-shot retrieval**
- Embed the question side of each pool pair. At query time, retrieve the top-k by similarity. Start with k≈5–8 and tune it on the eval set.
- Add a diversity step, such as MMR, or cap near-duplicate SQL skeletons. That way you don't get 6 variants of the same query.
- Optional upgrade: also tag each pair by **SQL pattern** (`anti_join`, `period_compare`, `having_threshold`, `multi_hop_join`). A cheap classifier or keyword rules can then guarantee at least one example of the detected pattern. This targets your exact failures: "but not" → anti-join, "compared to" → period comparison.

**3. Keep a tiny static core: 3–4 canonical pattern examples, not 36**
This is where a few of your hard examples belong: one clean example per pattern that the model keeps getting wrong. For example:

```sql
-- "customers who ordered in Q1 but not Q2"
SELECT c.*
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id
    AND o.created_at >= '2026-01-01' AND o.created_at < '2026-04-01')
AND NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id
    AND o.created_at >= '2026-04-01' AND o.created_at < '2026-07-01');
```

```sql
-- "warehouses with >10 late shipments last week, vs the week before"
SELECT s.warehouse_id,
       count(*) FILTER (WHERE s.shipped_at >= date_trunc('week', current_date) - interval '7 days'
                          AND s.shipped_at <  date_trunc('week', current_date))                    AS late_last_week,
       count(*) FILTER (WHERE s.shipped_at >= date_trunc('week', current_date) - interval '14 days'
                          AND s.shipped_at <  date_trunc('week', current_date) - interval '7 days') AS late_prev_week
FROM shipments s
WHERE s.delivered_at > s.promised_at   -- your definition of "late"
GROUP BY s.warehouse_id
HAVING count(*) FILTER (WHERE s.shipped_at >= date_trunc('week', current_date) - interval '7 days'
                          AND s.shipped_at <  date_trunc('week', current_date)) > 10;
```
(The column names `customer_id`, `warehouse_id`, `shipped_at`, `delivered_at`, `promised_at` are guesses. Swap in your real ones.)

**4. Enrich the schema section. This is likely half your join problem.**
Raw DDL doesn't tell the model how to use the tables. Add short notes:
- **Join paths:** `order_items.order_id → orders.id`, `shipments.order_id → orders.id`, `shipments.warehouse_id → warehouses.id`, and so on. Also note which joins fan out rows. For example, joining `order_items` before summing order totals double-counts.
- **Business definitions:** what "late" means, what "revenue" means (item totals or order totals, and whether refunds count), and whether a week starts on Monday (`date_trunc('week', …)` in Postgres uses ISO weeks, which start Monday).
- **Time conventions:** timezone, and whether columns are `timestamp` or `timestamptz`.
- **Pattern rules:** "For 'X but not Y' questions, use `NOT EXISTS`. For 'compared to' questions, use `count(*) FILTER (...)` or CTEs per period."

**5. Make the model plan before writing SQL (for complex questions)**
Ask for a short plan first: tables needed, join keys, filters, whether an anti-join or period comparison is needed. Then the SQL. Discard the plan when parsing the output. This usually reduces forgotten anti-joins. It costs some latency, so route only non-trivial questions through it if needed.

**6. Validate by execution, then retry**
- Run `EXPLAIN` or execute under a **read-only role with `statement_timeout`**. On an error, feed the error message back for one retry.
- Evaluate on **execution accuracy**: compare result sets against the verified SQL's results, not SQL strings. Two correct queries rarely match as text.

## Rollout

1. Baseline: run your current prompt on the eval set and record accuracy per category.
2. Add retrieval only, then re-measure.
3. Add schema notes, then re-measure.
4. Add the pattern-core examples and the plan step, re-measuring after each change.

Changing one thing at a time tells you what actually moved the hard categories.

## One more thing: your launch example has a subtle bug

`WHERE created_at::date = current_date - 1` can't use a plain index on `created_at`. If the column is `timestamptz`, it also depends on the session `TimeZone`. Prefer a range:

```sql
WHERE created_at >= current_date - 1 AND created_at < current_date
```

The model copies whatever your examples show, so fix this in the pool too. Grep the 900 pairs for `::date =`.
