## Answer A
Причина одна: пример у вас один, и модель не отличает в нём **стиль** от **содержания**. Для неё «выдерживает семь-восемь заварок», «90°» и «сливочное масло» — такая же часть «стиля», как короткие фразы. Структура «Название из Региона.» копируется по той же причине. Инструкция «сохрани все факты» не мешает *добавлять* новые: запрета на это в промпте нет.

Чинить лучше в три слоя. Порядок ниже — по отдаче.

## 1. Описать стиль словами и отделить пример от фактов

Модель должна понять, что именно ей нравится в эталоне. Разберите его на правила и прямо скажите, что факты из примера использовать нельзя.

## 2. Дать 3–4 разных примера вместо одного

С одним примером модель копирует всё подряд. С несколькими непохожими она видит, что в них общее (тон), а что меняется (факты, порядок, начало). Попросите маркетолога написать ещё 2–3 эталона:
- **другой тип чая** (шу пуэр или жасминовый), с другими числами и другим первым предложением;
- **обязательно одну пару «бедный исходник → короткий текст»**: в исходнике нет ни региона, ни режима заваривания, и в результате их тоже нет. Это главный пример. Он показывает, что пропуск лучше выдумки.

Начала у примеров должны быть разные: с названия, с запаха, с вида листа, с того, как пить.

## 3. Разбить на два шага: извлечь факты → написать текст

Это самое надёжное лекарство от галлюцинаций на 1400 карточках.

**Шаг A — извлечение фактов** (стиля нет, только JSON):

```
Извлеки из описания товара факты. Используй ТОЛЬКО то, что прямо написано в тексте.
Если факта нет — ставь null. Ничего не додумывай и не выводи из названия сорта.

<описание>
{old_text}
</описание>

Верни JSON:
{
  "название": str,
  "регион": str | null,
  "вид_листа": str | null,
  "аромат_вкус": [str],        // только дескрипторы из текста
  "температура": str | null,
  "время_пролива": str | null,
  "количество_заварок": str | null,
  "прочее": [str]              // остальные факты дословно
}
```

**Шаг B — текст только из JSON:**

```
## Роль
Ты пишешь карточки для интернет-магазина чая.

## Задача
Напиши описание чая по фактам из JSON ниже.

## Главное правило
Используй ТОЛЬКО факты из JSON. Поле null или пустой список — не упоминай эту тему совсем.
Не пиши температуру, число заварок, регион или ароматы, которых нет в JSON,
даже если они типичны для такого чая. Короткий честный текст лучше длинного с выдумкой.

## Стиль
- Короткие предложения, разговорная интонация, как будто рассказываешь другу.
- Конкретика вместо оценок: «пахнет сиренью», а не «обладает выраженным ароматом».
- Советы по завариванию — на «вы», в повелительном наклонении: «заваривайте», «сливайте».
- Никакого канцелярита («данный», «обладает», «является»), никаких восклицательных знаков.
- Можно одну живую фразу в конце, если для неё есть факт («дальше уже вода»).
- Первое предложение каждый раз строй по-разному. Начинай с самого интересного факта
  из JSON: вид листа, аромат, история, способ заваривания. Не начинай по шаблону
  «Название из Региона.», если регион не самое интересное.
- Длина — 3–6 предложений, в зависимости от количества фактов.

## Примеры
Примеры показывают ТОЛЬКО тон и ритм. Факты из них (регион, температура, число заварок,
ароматы) к текущему чаю не относятся — не переноси их.

<пример>
<факты>{...JSON для Те Гуань Инь...}</факты>
<текст>Те Гуань Инь из Аньси. Сухой лист скручен в тугие шарики...</текст>
</пример>

<пример>
<факты>{...JSON для шу пуэра...}</факты>
<текст>...текст, который начинается НЕ с названия...</текст>
</пример>

<пример>

        "количество_заварок": null, "прочее": []}</факты>
<текст>...2 предложения, без температуры и без региона...</текст>
</пример>

## Факты для текущего чая
<факты>
{facts_json}
</факты>
```

Примеры в шаге B лучше давать парами «факты → текст», а не голым текстом. Так модель видит, как именно факты превращаются в фразы, а заодно видит, что null ничем не заменяется.

## 4. Автоматическая проверка перед публикацией

На 1400 карточках часть ошибок проскочит при любом промпте. Проверка стоит недорого:
- **Код, без LLM:** найдите регуляркой в результате числа, градусы и слова «заварок» или «пролив». Каждое число должно встречаться в JSON фактов. Если нет — карточку в ручную проверку. Так ловятся ваши «90°» и «семь-восемь».
- **LLM-проверка ароматов:** отдельный вызов, который видит только JSON и готовый текст: «Перечисли утверждения из текста, которых нет в фактах». Непустой ответ — на доработку. Вызов должен быть отдельным, без контекста генерации, иначе модель склонна оправдывать собственный текст.

## Ограничения

## Answer B
## Почему так вышло

У модели один пример и расплывчатая инструкция «в стиле примера», поэтому она не отличает стиль от содержания. Из единственного образца она копирует всё подряд:

- **факты**: 90°, «семь-восемь заварок», «сливочное масло». Для модели это такая же часть «стиля», как короткие фразы;
- **структуру**: «Название из Региона.» → лист → аромат → заваривание → число проливов. Один пример воспринимается как шаблон, а не как один из возможных вариантов.

Фраза «Сохрани все факты» не мешает добавлять новые. Она требует ничего не потерять и ничего не говорит о том, что выдумывать нельзя.

Лечится тремя вещами: отделить факты от стиля, описать стиль словами и дать несколько разных примеров, а в конце проверить результат.

### 3. Дать 3–4 разных примера вместо одного

По одному примеру модель делает шаблон, а по нескольким разным видит, что в них общего: тон. Примеры должны различаться по трём признакам:

- **Тип чая**: улун, зелёный, пуэр, ароматизированный. Тогда 90° и «семь-восемь заварок» перестают казаться общим правилом.
- **Начало**: один пример начинается с названия и региона, другой с аромата, третий с вида листа.
- **Полнота**: обязательно нужен пример по бедному исходнику, где нет ни региона, ни режима заваривания, и текст получается коротким. Именно этот пример учит модель не заполнять пробелы.

Например (сама маркетолог напишет лучше, это просто образец):

> Жасминовый зелёный. Пахнет так, будто рядом цветёт куст, — жасмин тут главный, чай скорее фон. Хорош вечером и к несладкой выпечке.

Здесь нет региона и режима заваривания, и текст всё равно полноценный. Такой пример как раз закрывает ваш случай с жасминовым.

Лучше просить маркетолога написать примеры по **реальным** исходникам из вашего каталога и держать пары «исходник → эталон». Так модель видит, как именно из сухого текста получается живой, и не добавляет лишнего.

### 4. Автопроверка после генерации

1400 карточек вручную не вычитать, поэтому нужны дешёвые фильтры:

- **Регулярки**: найти в новом тексте числа, `°`, «заварок/проливов», названия регионов. Если значения нет в JSON фактов, карточка уходит на ручную проверку.
- **LLM-проверка** (отдельный вызов, видит только факты и новый текст, черновик генерации ему не нужен): «Перечисли утверждения в тексте, которых нет в фактах. Если таких нет, верни пустой список». Отдельный контекст ловит выдумки лучше, чем просьба к той же модели «перепроверь себя».
- **Разнообразие начал**: посчитать первые 3–4 слова по всем текстам. Если больше ~20% начинаются одинаково, в примерах всё ещё слишком похожие начала.

## Если хочется попроще

Можно начать и с одного вызова: те же правила стиля, 3–4 разных примера, жёсткое «только факты из исходника, отсутствующее не упоминай», исходник в `<source>`. Скорее всего, выдумок станет сильно меньше. Но пока модель одновременно видит пример с конкретными цифрами и исходник без них, утечки, вероятно, иногда будут. Поэтому я бы сразу делал два шага и регулярку: это дешевле, чем потом вычищать 90° у сенчи в каталоге.

Ещё одна деталь: инструкция, стиль и примеры одинаковы для всех 1400 вызовов, поэтому их стоит поставить в начало промпта и включить prompt caching. На таком объёме это заметно снижает стоимость.
