## Latest user message
I maintain an LLM prompt that extracts fields from supplier invoices (PDF text -> JSON with vendor_name, invoice_number, invoice_date, total, currency, line_items). Every time finance reports a bad extraction I add a rule to the system prompt. We're at 43 rules now, stuff like "Rule 17: if the date is written like 03/04/2025 and the vendor is in the UK, treat it as DD/MM", "Rule 31: never put the VAT amount in total", "Rule 38: ALWAYS include currency even if missing", "Rule 40: do not guess values that aren't in the document". Lately it feels like fixing one thing breaks another: last week after adding rule 40 the model started returning null currency again. Today finance flagged an invoice where total came out as the subtotal before shipping. Can you write me rule 44 for that? I'll test it on that invoice and push.

## Rubric (what a strong answer does)
1. Points out that rule 38 (always include currency) and rule 40 (don't guess missing values) contradict each other and connects this to the null-currency regression, proposing a single resolved behavior (e.g. null plus a flag, or an explicit allowed inference)
2. Identifies the growing pile of 40+ patch rules as a cause of the whack-a-mole regressions and recommends consolidating/restructuring them (e.g. grouping by field, clear definitions, worked examples of tricky invoices) rather than only appending more
3. Recommends building a regression set of past problem invoices with expected JSON and running every prompt change against the whole set before pushing, instead of testing only on today's invoice
4. Still addresses the immediate total-vs-subtotal bug with a concrete definition of total as the invoice's final amount due (after shipping and tax), distinct from the subtotal, that fits the user's existing schema

## Answer A
Here's rule 44. I'd push back on "test on that invoice and push", though. That workflow is why fixes keep breaking other things, and you've already seen it happen once.

## Rule 44

```
Rule 44: `total` is the final amount payable on the invoice: the figure labelled
"Total", "Grand Total", "Amount Due", "Invoice Total" or "Balance Due" (or the
equivalent in the document's language). It includes shipping, freight,
handling, surcharges and tax, minus any discounts. NEVER use a "Subtotal",
"Net", "Net Total" or "Total before shipping" line as `total`. If several totals
appear, take the one that comes after all the adjustment lines (usually the
last or bottom-most total in the summary block).
```

Before you ship it, check it against the rules you already have:

- **It may conflict with Rule 31.** "Never put the VAT amount in total" can mean two things: don't put the VAT line *itself* into `total`, or `total` should be net of VAT. Rule 44 assumes `total` is gross, including VAT. If finance actually wants net, the wording has to change, and your current prompt may already be inconsistent on this point. Ask finance which one they mean and write the answer into the definition.
- **Deposits and partial payments.** "Invoice Total" and "Balance Due" can differ when something has already been paid. Rule 44 doesn't choose between them because only finance can make that call.

## The real problem: 43 patches with no regression test

What you're seeing (rule 40 brought back null currency, a new rule breaks an old case) is the usual result of adding rules without a regression suite. Some specific issues:

1. **Rules 38 and 40 contradict each other.** "ALWAYS include currency even if missing" and "do not guess values that aren't in the document" can't both hold when the invoice shows no currency. The model has to pick one, and after you added rule 40 it picked 40. No wording fix fixes this. You have to decide the policy, for example: "currency = ISO code from a symbol or code in the document; if none is present, return null". Then fill the gap in code using the vendor's country from your vendor master data.
2. **Patches instead of definitions.** Rules 31 and 44 are both really "what is `total`?", answered one failure at a time. Grouping the rules by field ("`total` means X. Edge cases: …") shrinks the prompt, shows you the conflicts, and gives the model one definition per field instead of scattered exceptions.
3. **Deterministic logic in the prompt.** Rule 17 (UK dates are DD/MM) is a lookup that code does reliably and an LLM does only most of the time. Have the model extract `invoice_date_raw` exactly as printed and parse it in code using the vendor's country.
4. **No arithmetic check.** Also extract `subtotal`, `shipping`, `tax` and `discount`, then assert `subtotal + shipping + tax - discount ≈ total` in code. The subtotal bug from today would have failed this check automatically, and it catches that whole class of errors going forward without another rule.

## What to do before pushing rule 44

1. **Build a golden set now.** Every invoice finance has flagged is a test case you already have: at least the ~43 behind your rules, plus 10–20 ordinary ones. Store each as PDF text and the expected JSON.
2. **Score each field separately** (exact match for `invoice_number` and `currency`, tolerance for amounts, normalized dates), not just pass/fail for the whole invoice.
3. **Run the full set on the current prompt** to get a baseline, then on prompt + rule 44. Push only if today's invoice passes and nothing else drops.
4. From now on, every finance report becomes a new test case before it becomes a prompt change.

Once the golden set exists, I'd refactor the 43 rules into field definitions, one change at a time with a re-run after each. The prompt will likely end up shorter and more stable, but the test set is what will show you whether it actually is.


## Answer B
Here's rule 44. Before you push it, though: testing it on one invoice is how you got the rule 40 regression, and this rule interacts with rule 31 in the same way.

## Rule 44 (drop-in)

```
Rule 44: `total` is the final amount payable on the invoice: the figure labeled
"Total", "Invoice Total", "Grand Total", "Total Due" or "Amount Due" that comes
AFTER shipping, freight, handling, surcharges, discounts and tax have been applied.
Never use a figure labeled "Subtotal", "Net", "Net Total" or "Total before tax/shipping".
If the invoice shows several totals, use the last one in the totals block that
includes all charges. If no such line exists, set total to null. Do not compute it.
```

The last sentence is there so rule 44 stays consistent with rule 40 (no guessing). Without it you're asking the model to add up numbers in some cases and forbidding inference in others, which is the same kind of clash as 38 vs 40.

## Check these before pushing

**1. Rule 31 conflicts with 44.** "Never put the VAT amount in total" can be read as "total excludes VAT", and that is the subtotal bug you're fixing now. Reword it:

```
Rule 31: `total` must never be the VAT/tax amount on its own. `total` INCLUDES VAT.
```

(Only do this if finance wants gross totals. Confirm that with them. If they want net, rule 44 is wrong as written.)

**2. "Amount Due" vs "Invoice Total".** When there are deposits, credits or partial payments, these differ. Ask finance which one they want. Right now the model is deciding that for you.

**3. Rules 38 and 40 contradict each other,** which is why currency went null again. One says always fill it, the other says never guess, and the model can't satisfy both. Pick one:

- The prompt returns what the document says: `currency: null` if it's absent, plus `"currency_source": "document" | "absent"`. Your code then fills the gap from vendor master data (vendor country or default currency). This is deterministic, auditable and doesn't depend on the prompt.
- Or allow inference explicitly: "If no currency symbol or code appears, infer from vendor address country and set `currency_inferred: true`." Then rule 40 needs an exception clause.

I'd go with the first. The LLM extracts, and business defaults live in code.

## Structural fix

With 43 patch rules, each fix is a new variable that nothing tests against the old cases. Two changes would stop the whack-a-mole:

**A. Regression set.** Every invoice finance has ever flagged (you have at least 43) goes into a golden set with the expected JSON. Run all of them on every prompt change. Push only if nothing that used to pass fails, and change one rule at a time. This is the single highest-value change.

**B. Extract components and validate in code.** Add fields to the schema:

```json
{
  "subtotal": 1200.00,
  "shipping": 45.00,
  "discount": 0.00,
  "tax": 249.00,
  "total": 1494.00
}
```

Then check in code: `abs(subtotal + shipping - discount + tax - total) <= 0.02`. On failure, flag the invoice for human review or re-prompt. That catches today's bug (total == subtotal while shipping > 0) and a whole class of similar bugs, without another prompt rule. Also check `sum(line_items.amount) ≈ subtotal`.

**C. Later: consolidate the 43 rules.** Most of them are probably patches on a few underlying definitions: what `total` means, how dates are parsed, when null is allowed. Rewriting them as one short definition per field, with 2-3 hard example invoices as few-shot, will likely hold up better than 43 numbered exceptions. But do it only once the regression set from (A) exists, or you won't know what you broke.

Summary: use rule 44 and fix rule 31 along with it. Run them against all past flagged invoices, not just today's. Resolve the 38/40 conflict by moving currency defaults into code.
