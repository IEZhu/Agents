## 1. Формат и enum: Structured Outputs вместо уговоров

Обёртка в ```json и значения вроде "High"/"срочно" лечатся через `response_format` с JSON Schema в strict-режиме. В этом режиме модель не может выдать ничего, кроме JSON по схеме, а `enum` жёстко ограничивает набор значений.

```python
response = client.chat.completions.create(
    model="gpt-4o-mini",
    temperature=0,
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": ticket_text},
    ],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "name": "ticket_classification",
            "strict": True,
            "schema": {
                "type": "object",
                "properties": {
                    "category": {
                        "type": "string",
                        "enum": ["billing", "bug", "feature_request", "account", "other"]
                    },
                    "urgency": {
                        "type": "string",
                        "enum": ["low", "medium", "high"]
                    },
                    "reason": {
                        "type": "string",
                        "description": "Одно предложение на русском языке, даже если обращение на другом языке."
                    }
                },
                "required": ["category", "urgency", "reason"],
                "additionalProperties": False
            }
        }
    },
)
```

Проверьте по документации OpenAI: структура `response_format` / `json_schema` / `strict` и поддержка strict-режима у gpt-4o-mini (насколько помню, начиная со снапшота `gpt-4o-mini-2024-07-18`) приведены по памяти, я их здесь не проверял. По тем же данным strict-режим требует, чтобы `additionalProperties: false` стоял и все поля были в `required`.

Обычный `{"type": "json_object"}` не подойдёт: он гарантирует только валидный JSON, но не значения enum.

## 2. Язык reason: схема этого не гарантирует

Никакой enum не заставит модель писать по-русски. Поэтому здесь три шага:

- **Пример вместо капса.** Добавьте в промпт один few-shot пример с тикетом на английском и `reason` на русском. Пример работает надёжнее любой формулировки «СТРОГО НА РУССКОМ».
- **Инструкция и в промпте, и в `description` поля.** Выше это уже сделано.
- **Проверка в коде.** Если в `reason` мало кириллицы (например, меньше 50% букв), отправляйте повторный запрос или отдельный дешёвый вызов «переведи на русский». На частоте 5–7% это дёшево, и такая проверка ловит то, что промпт пропустит.

## 3. Упрощённый промпт

Всё про формат теперь обеспечивает схема, и из промпта это можно убрать:

```
Ты классифицируешь обращения в поддержку.

Категории:
- billing — оплата, счета, возвраты, тарифы
- bug — что-то работает не так, ошибки
- feature_request — просьба добавить/изменить функциональность
- account — вход, доступ, профиль, удаление аккаунта
- other — всё остальное

Срочность:
- high — клиент не может работать или теряет деньги прямо сейчас
- medium — проблема мешает, но есть обходной путь
- low — вопрос, пожелание, некритичное неудобство

Если подходит несколько категорий, выбери ту, от которой зависит решение проблемы клиента.
Поле reason — одно предложение на русском, даже если обращение написано на другом языке.

Пример:
Обращение: "I was charged twice for my subscription this month, please refund."
Ответ: {"category": "billing", "urgency": "medium", "reason": "Клиент сообщает о двойном списании за подписку и просит возврат."}
```

Роль «опытный специалист» можно убрать: на классификацию она почти не влияет. Критерии срочности добавлены потому, что без них `low/medium/high` каждый раз определяется по-разному. Скорее всего, сейчас это основной источник шума в разметке, хотя вы на него пока не смотрите.

## 4. Главное: как вы проверяете

Прогон 5 тикетов глазами не может показать ошибку, которая случается в 5–7% ответов. При частоте 6% вероятность, что все 5 ответов окажутся чистыми, равна 0.94⁵ ≈ 73%. То есть три ваших правки промпта вы оценивали почти вслепую, и «стало чуть лучше» вполне может быть случайностью.

Что сделать:

1. Соберите 100–200 реальных тикетов, в том числе на английском, смешанные и короткие. Разметьте правильные `category`/`urgency` хотя бы у части из них.
2. Напишите скрипт с автоматическими проверками:
   - JSON парсится;
   - значения входят в enum;
   - в `reason` есть кириллица и одно предложение;
   - `category`/`urgency` совпадают с разметкой.
3. Меняйте по одной вещи и сравнивайте метрики на всём наборе.

После перехода на strict-схему ошибки формата и enum должны исчезнуть совсем. Останутся язык `reason` и качество самой классификации, а их вы теперь сможете измерять.

## Порядок действий

1. Включить `json_schema` + `strict` и `temperature=0`. Это закроет ```json и "High"/"срочно".
2. Добавить few-shot пример с английским тикетом и проверку кириллицы с повтором запроса.
3. Собрать тестовый набор и дальше работать уже над точностью категорий и срочности, а не над форматом.
