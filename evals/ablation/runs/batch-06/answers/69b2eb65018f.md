Not quite. Adding 30 hard examples to a static block will probably help a little, but it doesn't use most of what you have. You're sitting on 900 verified pairs. The usual fix for this kind of failure is **dynamic few-shot retrieval**: for each incoming question, pull the 5–8 most similar verified pairs into the prompt. The static block stays small.

## Why the static-30 plan is weak

- **Coverage.** Ops questions come in many shapes: anti-joins, period-over-period, HAVING thresholds, multi-hop joins through `order_items`/`shipments`. 30 fixed examples cover a few of them. The other ~870 verified pairs sit unused.
- **Few-shot bias.** Examples shape output more than instructions do. With 36 static examples, most are irrelevant to any given question. They add noise and can pull the model toward the wrong pattern. For example, a "Q1 vs Q2" question may copy the shape of a "revenue in March" example.
- **Cost and latency.** You pay for every example on every request, including the simple ones that already work.
- **No measurement.** Right now you can't tell whether adding 30 examples improves the hard cases or quietly breaks the easy ones.

## What to do instead

**1. Split the 900 pairs before anything else**
- Hold out about 150–200 as a **golden eval set**. Stratify it so the hard categories are well represented (anti-join, period comparison, multi-table aggregation).
- The remaining ~700 become the **retrieval pool**.
- Never retrieve from the eval set. Otherwise your accuracy numbers mean nothing.

**2. Dynamic few-shot retrieval**
- Embed the question side of each pool pair. At query time, retrieve the top-k by similarity. Start with k≈5–8 and tune it on the eval set.
- Add a diversity step, such as MMR, or cap near-duplicate SQL skeletons. That way you don't get 6 variants of the same query.
- Optional upgrade: also tag each pair by **SQL pattern** (`anti_join`, `period_compare`, `having_threshold`, `multi_hop_join`). A cheap classifier or keyword rules can then guarantee at least one example of the detected pattern. This targets your exact failures: "but not" → anti-join, "compared to" → period comparison.

**3. Keep a tiny static core: 3–4 canonical pattern examples, not 36**
This is where a few of your hard examples belong: one clean example per pattern that the model keeps getting wrong. For example:

```sql
-- "customers who ordered in Q1 but not Q2"
SELECT c.*
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id
    AND o.created_at >= '2026-01-01' AND o.created_at < '2026-04-01')
AND NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.id
    AND o.created_at >= '2026-04-01' AND o.created_at < '2026-07-01');
```

```sql
-- "warehouses with >10 late shipments last week, vs the week before"
SELECT s.warehouse_id,
       count(*) FILTER (WHERE s.shipped_at >= date_trunc('week', current_date) - interval '7 days'
                          AND s.shipped_at <  date_trunc('week', current_date))                    AS late_last_week,
       count(*) FILTER (WHERE s.shipped_at >= date_trunc('week', current_date) - interval '14 days'
                          AND s.shipped_at <  date_trunc('week', current_date) - interval '7 days') AS late_prev_week
FROM shipments s
WHERE s.delivered_at > s.promised_at   -- your definition of "late"
GROUP BY s.warehouse_id
HAVING count(*) FILTER (WHERE s.shipped_at >= date_trunc('week', current_date) - interval '7 days'
                          AND s.shipped_at <  date_trunc('week', current_date)) > 10;
```
(The column names `customer_id`, `warehouse_id`, `shipped_at`, `delivered_at`, `promised_at` are guesses. Swap in your real ones.)

**4. Enrich the schema section. This is likely half your join problem.**
Raw DDL doesn't tell the model how to use the tables. Add short notes:
- **Join paths:** `order_items.order_id → orders.id`, `shipments.order_id → orders.id`, `shipments.warehouse_id → warehouses.id`, and so on. Also note which joins fan out rows. For example, joining `order_items` before summing order totals double-counts.
- **Business definitions:** what "late" means, what "revenue" means (item totals or order totals, and whether refunds count), and whether a week starts on Monday (`date_trunc('week', …)` in Postgres uses ISO weeks, which start Monday).
- **Time conventions:** timezone, and whether columns are `timestamp` or `timestamptz`.
- **Pattern rules:** "For 'X but not Y' questions, use `NOT EXISTS`. For 'compared to' questions, use `count(*) FILTER (...)` or CTEs per period."

**5. Make the model plan before writing SQL (for complex questions)**
Ask for a short plan first: tables needed, join keys, filters, whether an anti-join or period comparison is needed. Then the SQL. Discard the plan when parsing the output. This usually reduces forgotten anti-joins. It costs some latency, so route only non-trivial questions through it if needed.

**6. Validate by execution, then retry**
- Run `EXPLAIN` or execute under a **read-only role with `statement_timeout`**. On an error, feed the error message back for one retry.
- Evaluate on **execution accuracy**: compare result sets against the verified SQL's results, not SQL strings. Two correct queries rarely match as text.

## Rollout

1. Baseline: run your current prompt on the eval set and record accuracy per category.
2. Add retrieval only, then re-measure.
3. Add schema notes, then re-measure.
4. Add the pattern-core examples and the plan step, re-measuring after each change.

Changing one thing at a time tells you what actually moved the hard categories.

## One more thing: your launch example has a subtle bug

`WHERE created_at::date = current_date - 1` can't use a plain index on `created_at`. If the column is `timestamptz`, it also depends on the session `TimeZone`. Prefer a range:

```sql
WHERE created_at >= current_date - 1 AND created_at < current_date
```

The model copies whatever your examples show, so fix this in the pool too. Grep the 900 pairs for `::date =`.
