Пока не делайте `docker system prune -a`: Docker здесь, скорее всего, не главная причина. Ключевая цифра у вас в выводе ncdu: раздел на 50G заполнен на 100%, а ncdu насчитал всего 12.3 GiB. Около 35–38G занято тем, что ncdu не видит. Prune вернёт максимум несколько гигабайт из тех 6.1G, а через час раздел снова заполнится. Кроме того, `-a` удалит все образы, которые не используются запущенными контейнерами. Остановленные сервисы потом придётся заново тянуть или пересобирать.

То, что место заканчивается примерно за час, говорит о каком-то процессе, который активно пишет. Мои прошлые советы (journal, apt, старые логи) освобождали место разово и до этой причины не добрались.

### Откуда берётся «невидимое» место (от наиболее вероятного)

**1. Удалённые файлы, которые держит открытыми процесс.** Самый частый случай. Лог удалили (например, через `rm` или при чистке /var/log), а процесс продолжает в него писать. Имени у файла уже нет, поэтому du и ncdu его не видят, а df видит.

```bash
sudo lsof -nP +L1 / 2>/dev/null | sort -k7 -n | tail -20
```
Показывает открытые файлы с нулём ссылок (удалённые) на корневой ФС. Смотрите на колонку SIZE и на COMMAND/PID. Если `lsof` не установлен, то же самое без него:
```bash
sudo find /proc/[0-9]*/fd -lname '*(deleted)' -printf '%p -> %l\n' 2>/dev/null
```

**2. ncdu запускали не от root.** Без sudo он не может зайти в закрытые каталоги (например, `/var/lib/docker/overlay2`, `/root`, часть `/var/lib`) и тихо их пропускает. Проверьте:
```bash
sudo ncdu -x /
```
Если теперь насчитает около 50G, «невидимое» место окажется просто нечитаемым, и ncdu покажет, где оно.

**3. Файлы, спрятанные под точкой монтирования.** Если что-то (скрипт, backup, контейнер) писало в `/mnt/...` или `/data` в момент, когда диск не был смонтирован, эти файлы лежат на корневом разделе под смонтированной ФС. `ncdu -x` их не покажет. Проверка через bind-mount корня, который не затрагивает данные:
```bash
sudo mkdir -p /mnt/rootfs && sudo mount --bind / /mnt/rootfs
sudo du -xh --max-depth=2 /mnt/rootfs 2>/dev/null | sort -h | tail -20
sudo umount /mnt/rootfs
```

### Найти, что растёт прямо сейчас

```bash
sudo find / -xdev -type f -mmin -60 -size +100M -printf '%s\t%p\n' 2>/dev/null | sort -n | tail
```
Большие файлы, изменённые за последний час. Удалённые открытые файлы сюда не попадут, для них нужен шаг 1.

Проверить и логи контейнеров Docker. Это частый источник, если у json-file драйвера нет лимита:
```bash
sudo sh -c 'du -h /var/lib/docker/containers/*/*-json.log' | sort -h | tail
```

### Как освободить, если виновник найден через lsof

- Лучший вариант: перезапустить процесс, который держит файл (`sudo systemctl restart <service>` или `docker restart <container>`). После этого место освободится.
- Если перезапуск сейчас невозможен, файл можно обнулить через дескриптор (PID и номер fd берутся из вывода lsof/find):
  ```bash
  sudo truncate -s 0 /proc/<PID>/fd/<FD>
  ```
  Внимание: содержимое этого файла будет потеряно безвозвратно. Если лог нужен, сначала скопируйте его: `sudo cp /proc/<PID>/fd/<FD> /some/other/disk/`.

Потом устраните причину: настройте logrotate с `copytruncate` или с корректным `postrotate` для этого сервиса. Если это логи Docker, задайте лимит в `/etc/docker/daemon.json`:
```json
{ "log-driver": "json-file", "log-opts": { "max-size": "100m", "max-file": "3" } }
```
Лимит применится только к контейнерам, созданным заново, после `sudo systemctl restart docker`. Ключи указаны по памяти, сверьтесь с документацией Docker по json-file logging driver.

### Проверка

```bash
df -h /
sudo lsof -nP +L1 / 2>/dev/null | wc -l
```
Через 15–30 минут повторите `df -h /`. Если занятое место стоит на месте, источник найден. Если снова растёт, пришлите вывод `sudo lsof -nP +L1 /` и `sudo ncdu -x /`, разберём дальше.

Docker-образы можно почистить и потом, аккуратнее: `docker image prune` (без `-a`) удаляет только dangling-образы. Но место на диске заканчивается не из-за них.
