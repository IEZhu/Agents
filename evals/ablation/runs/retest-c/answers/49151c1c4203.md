Не спешите с `docker system prune -a`: он не решит проблему. Главная подсказка — в ваших цифрах: `df` показывает занятыми ~50G, а `ncdu -x /` находит только 12.3 GiB. Около 38G занято тем, чего `ncdu` не видит, и оно растёт каждый час. Docker с его 6.1G к этому, скорее всего, не относится. Кстати, мои прошлые советы (журналы, apt, ядра) тоже лечили симптом, а не причину.

## Почему du/ncdu и df расходятся

Чаще всего по одной из трёх причин, по убыванию вероятности:

1. **Удалённые, но ещё открытые файлы.** Процесс пишет в лог, файл удалили (вручную или неправильной ротацией), но процесс держит дескриптор. Место не освобождается, в дереве каталогов файла нет, и он продолжает расти. Под «через час опять 100%» это подходит лучше всего.
2. **`ncdu` запущен не от root.** Каталоги без прав на чтение не считаются. Внизу `ncdu` в таком случае пишет, что были ошибки чтения.
3. **Данные спрятаны под точкой монтирования.** Если в каталог что-то записали до того, как в него смонтировали другой раздел, эти файлы занимают место на `/`, но их не видно.

## Что проверить

**1. Удалённые открытые файлы** (самое вероятное):

```bash
sudo lsof -nP +L1 | sort -k7 -n -r | head -20
```
`+L1` показывает открытые файлы с числом ссылок меньше 1, то есть удалённые. Седьмая колонка — размер в байтах. Ищите строки с `(deleted)` и большим SIZE.

Если `lsof` не установлен, то же самое без него:
```bash
sudo find /proc/*/fd -lname '*(deleted)' -printf '%p -> %l\n' 2>/dev/null
```

**2. Пересчитать от root:**
```bash
sudo du -xh --max-depth=1 / 2>/dev/null | sort -h | tail -15
```

**3. Файлы под точками монтирования.** Bind-mount корня показывает «голую» ФС без смонтированного поверх:
```bash
sudo mkdir -p /mnt/rootcheck
sudo mount --bind / /mnt/rootcheck
sudo du -xh --max-depth=2 /mnt/rootcheck 2>/dev/null | sort -h | tail -20
sudo umount /mnt/rootcheck
```
Если здесь итог заметно больше 12G, смотрите, какой каталог раздут (обычно это `/mnt/...`, `/media/...`, `/data` или `/backup`).

## Если нашёлся удалённый файл

Сразу место освобождается либо перезапуском процесса, который его держит:
```bash
sudo systemctl restart <сервис>
```
либо, если перезапускать нельзя, обнулением файла через дескриптор (PID и номер FD берутся из вывода `lsof`/`find`):
```bash
sudo truncate -s 0 /proc/<PID>/fd/<FD>
```
Обнуление уничтожит содержимое этого лога. Если он нужен для разбора, сначала скопируйте хвост: `sudo tail -c 100M /proc/<PID>/fd/<FD> > /tmp/big.log` (при условии, что `/tmp` лежит не на том же забитом разделе).

Но это лечит только симптом. Процесс, который пишет примерно 30+ ГБ за несколько часов, почти наверняка сыплет ошибками в цикле. Посмотрите, что он пишет (`sudo tail -f /proc/<PID>/fd/<FD>`), и устраните причину: ошибку, debug-уровень логирования, сломанную ротацию. Если ротация сделана через `logrotate` без `copytruncate` и без сигнала процессу, это и есть классический источник «удалённых, но открытых» логов.

## Проверка

```bash
df -h /
sudo lsof -nP +L1 | grep -c deleted
watch -n 60 'df -h /'
```
`df` должен показать реальное освобождение, а за `watch` в течение 10–20 минут будет видно, растёт ли занятое снова.

## Про docker prune

Как уборка он допустим, но освободит максимум ~6G и проблему не решит. К тому же `-a` удаляет **все** образы, которые не используются запущенными контейнерами, включая образы остановленных, но нужных вам контейнеров. Потом их придётся заново тянуть или собирать. Сначала посмотрите, что там лежит:
```bash
docker system df -v
```
Если всё-таки чистить, безопаснее начать с `docker image prune` (только dangling-образы) и `docker builder prune`.

Если `lsof +L1` и bind-mount ничего крупного не покажут, пришлите вывод всех трёх проверок и `df -i /` — будем копать дальше.
