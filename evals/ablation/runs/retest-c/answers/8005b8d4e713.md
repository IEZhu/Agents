**Коротко:** скорее всего под убивает не OOM, а ваша же livenessProbe. Приложение стартует 80–90 с (в кластере, вероятно, ещё дольше), а у probe «бюджет» примерно 50–60 с: `initialDelaySeconds 30` плюс 3 неудачные проверки с интервалом 10 с. Старый образ укладывался в эти рамки (40 с), новый уже нет. Kubelet перезапускает контейнер посреди старта, и так по кругу: это и есть CrashLoopBackOff. Ниже полный список того, что проверить, чтобы подтвердить или опровергнуть эту версию.

---

## 1. Подтвердить, что убивает именно liveness, а не OOM

- **Reason в lastState.** `Error` + 137 означает «убит сигналом SIGKILL» (128 + 9). При OOM kubelet обычно пишет `Reason: OOMKilled`. Проверьте точно:
  ```bash
  kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState.terminated}{"\n"}'
  ```
- **Хронология событий.** Сопоставьте время `Started` и `Killing`:
  ```bash
  kubectl get events --field-selector involvedObject.name=<pod> --sort-by=.lastTimestamp
  ```
  Если между стартом контейнера и `Container app failed liveness probe` проходит ~50–60 с, то это совпадает с расчётом.
- **Логи предыдущего запуска:**
  ```bash
  kubectl logs <pod> --previous
  ```
  Ищите строку `Started <App> in X seconds`. Если её нет и лог обрывается посреди инициализации (Hibernate, Flyway, создание бинов), значит, приложение просто не успевало стартовать.
- **Почему 137, а не 143.** При провале liveness kubelet сначала шлёт SIGTERM, а SIGKILL только после `terminationGracePeriodSeconds`. Код 137 означает, что JVM не завершилась по SIGTERM за это время, например потому что shutdown hooks зависли, пока контекст ещё не поднялся. Посмотрите `terminationGracePeriodSeconds` в спеке. Для диагноза это вторично, но объясняет, откуда 137.
- **Исключить OOM на уровне ноды:** `kubectl describe node <node>` (раздел событий), `dmesg | grep -i oom` на ноде. Если есть Prometheus, посмотрите `container_memory_working_set_bytes` относительно лимита 1Gi.

## 2. Проверить настройки probe

- **`timeoutSeconds`.** Если его нет в манифесте, действует дефолт 1 с. `context deadline exceeded` означает, что ответ не пришёл за этот таймаут. Под нагрузкой старта (JIT, загрузка классов, CPU throttling) даже живой `/actuator/health` может отвечать дольше секунды.
- **Что проверяет эндпоинт.** `/actuator/health` по умолчанию агрегирует health indicators: DB, Redis, диск, внешние сервисы. Если медленна зависимость, liveness падает и под перезапускается, хотя сам процесс в порядке. Для liveness лучше подходят `/actuator/health/liveness` и `/actuator/health/readiness`: они включены в Spring Boot 2.3+, а в Kubernetes активируются автоматически (включение вручную: `management.endpoint.health.probes.enabled=true`; ключ по памяти, сверьте с документацией вашей версии Boot).
- **Порт и путь в новом образе.** Проверьте, не поменялись ли `server.port`, `management.server.port`, `server.servlet.context-path` или `management.endpoints.web.base-path`. Если бы на 8080 ничего не слушало, скорее всего была бы `connection refused`, а не timeout. Поэтому ваш симптом больше похож на медленный ответ, но проверить стоит.
- **Есть ли `startupProbe`.** Если нет, то liveness начинает работать через 30 с, независимо от того, стартовало ли приложение.

## 3. Проверить ресурсы в кластере (почему в поде может быть ещё медленнее, чем локально)

- **CPU requests/limits.** Это самый частый виновник медленного старта JVM в k8s. Локально у JVM все ядра, в поде может быть, например, `limits.cpu: 500m`, и CFS throttling растягивает старт в разы. Смотрите:
  ```bash
  kubectl get pod <pod> -o jsonpath='{.spec.containers[0].resources}'
  ```
  В Prometheus: `container_cpu_cfs_throttled_periods_total` / `container_cpu_cfs_periods_total`.
- **Сколько CPU видит JVM.** При лимите меньше 1 ядра JVM может решить, что у неё 1 процессор, и выбрать SerialGC, а пулы потоков получатся маленькими. Проверить: `kubectl exec <pod> -- java -XX:+PrintFlagsFinal -version | grep -E 'ActiveProcessorCount|UseSerialGC|UseG1GC'` (если успеете, пока под жив; иначе запустите образ отдельно с тем же лимитом).
- **Память JVM относительно 1Gi.** Java 17 учитывает лимиты контейнера, но heap по умолчанию составляет около 25% лимита (`MaxRAMPercentage`). Если в новом образе заданы `-Xmx`/`MaxRAMPercentage` в `JAVA_TOOL_OPTIONS`/`JAVA_OPTS`, проверьте, что heap + metaspace + thread stacks + direct memory укладываются в 1Gi. Маленький heap даёт частые GC и медленный старт, слишком большой приводит к OOMKilled.
- **Как сравнивать с локальным запуском.** Для честного сравнения запустите локально с теми же лимитами: `docker run --cpus=<limit> --memory=1g ...`. Если время вырастет до 120+ с, причина найдена.

## 4. Выяснить, почему старт вырос с 40 до 80–90 с (diff образов)

- **Базовый образ и JDK.** Поменялись ли дистрибутив или версия JDK, JRE на JDK, alpine/musl на glibc? Не пропал ли CDS/AppCDS-архив?
- **Версии Spring Boot и зависимостей.** Новые auto-configuration, лишний classpath scanning, новые стартеры.
- **Миграции БД.** Flyway/Liquibase при старте: новые или тяжёлые миграции, ожидание lock на таблице `flyway_schema_history` / `DATABASECHANGELOGLOCK` (например, от предыдущего убитого пода, который не снял lock в Liquibase).
- **Внешние зависимости при старте.** Подключение к БД, Kafka, Config Server, Vault, прогрев кэшей. В кластере могут быть другие таймауты или DNS, чем локально, и новый код может ходить туда, куда раньше не ходил.
- **JVM-флаги и переменные окружения.** Сравните `ENTRYPOINT`/`CMD`, `JAVA_TOOL_OPTIONS`, профиль (`SPRING_PROFILES_ACTIVE`), уровень логирования (DEBUG сильно замедляет старт).
- **Формат артефакта.** Fat jar против layered/exploded: запуск из exploded-директории обычно быстрее.
- **Где именно тратится время.** Логи старта с таймстемпами; `spring.main.lazy-initialization=true` как эксперимент; `ApplicationStartup` (`BufferingApplicationStartup` + `/actuator/startup`) покажет самые медленные бины.

Команды для сравнения образов:
```bash
docker history <old-image>; docker history <new-image>
docker inspect <new-image> --format '{{json .Config.Env}} {{json .Config.Entrypoint}}'
```

## 5. Проверить изменения в манифесте и окружении

- `kubectl rollout history deploy/<name>` и `kubectl diff`: поменялось ли что-то кроме тега образа (ресурсы, env, ConfigMap/Secret)?
- ConfigMap/Secret, на которые ссылается под: не изменились ли URL зависимостей и таймауты.
- NetworkPolicy/egress: доступны ли из пода зависимости, к которым новый код обращается при старте. Если коннект висит до таймаута, старт растягивается.

## Что сделать, если гипотеза подтвердится

Добавьте `startupProbe`: пока она не пройдёт, liveness и readiness не запускаются. Liveness и readiness разведите по отдельным эндпоинтам:

```yaml
startupProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  periodSeconds: 10
  failureThreshold: 18      # до ~180 с на старт, с запасом над 80–90 с + throttling
  timeoutSeconds: 3
livenessProbe:
  httpGet:
    path: /actuator/health/liveness   # только состояние процесса, без внешних зависимостей
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
  timeoutSeconds: 3
readinessProbe:
  httpGet:
    path: /actuator/health/readiness  # здесь уместны проверки БД и т.п.
    port: 8080
  periodSeconds: 5
  failureThreshold: 3
  timeoutSeconds: 3
```

Просто поднимать `initialDelaySeconds` до 120+ хуже: это замедлит обнаружение реально зависшего пода при каждом рестарте.

Параллельно разберитесь, откуда взялся двукратный рост времени старта (раздел 4). Startup probe лечит симптом, а 90 с на старт замедляют rollout и восстановление после сбоев.

**Сейчас:** если прод лежит, откатитесь на старый образ (`kubectl rollout undo deploy/<name>`) и спокойно диагностируйте новый. **Blast radius:** при rolling update с корректной readiness старые поды должны продолжать обслуживать трафик. Но если `maxUnavailable` > 0 или реплик мало, ёмкость уже снижена. Проверьте `kubectl get deploy <name>` (READY/AVAILABLE).
