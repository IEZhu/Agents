## Things to plan for going from 13 to 18

This skips 5 major versions, so it isn't a routine bump:

- **Upgrade method:** `pg_upgrade --link` (fast, needs downtime, supports a direct 13 → 18 upgrade) or logical replication to a new 18 cluster (almost no downtime, more setup). Which one fits depends on how big your database is and how much downtime you can accept.
- **Read the release notes for 14, 15, 16, 17 and 18.** Changes that commonly break things:
  - In 15, the `CREATE` privilege on the `public` schema was removed from `PUBLIC`.
  - In 14, `password_encryption` defaults to `scram-sha-256`, so old md5-only clients may break.
  - In 18, `initdb` enables data checksums by default. That matters for `pg_upgrade`, which needs the old and new clusters to match on checksums (recalled, not verified — check the 18 release notes).
- **Extensions:** every extension (PostGIS, pg_trgm, TimescaleDB, etc.) needs a build for 18.
- **After the upgrade:** run `ANALYZE` on the whole database (for example `vacuumdb --all --analyze-in-stages`), because `pg_upgrade` doesn't carry over planner statistics. Until that finishes, query plans can be bad.
- **Before you start:** take a full backup (`pg_dump` or a base backup/snapshot), and rehearse the upgrade on a staging copy of production first.
