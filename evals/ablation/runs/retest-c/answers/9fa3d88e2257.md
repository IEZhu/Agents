**Short answer:** use the 15 minutes to separate three causes, and have every command scripted before 02:05. The three causes are:

1. **Replay blocked:** the startup process is waiting on a recovery conflict with a reporting query.
2. **Replay too slow:** a nightly write burst on the primary produces WAL faster than the single-threaded replay can apply it.
3. **Metric artefact:** the lag number is `now() - pg_last_xact_replay_timestamp()` while the primary is committing almost nothing.

The window covers the onset (02:10) and about 10 minutes of the climb. That's enough to tell the three apart if you're sampling from the first second.

A ~300 s ceiling followed by recovery is suspicious. `max_standby_streaming_delay = 5min` would produce exactly that: replay waits up to 300 s for a conflicting query, then cancels it and catches up. This is a hypothesis, not a diagnosis. Check it first.

## Before 02:05 (no host access needed)

- **Put every query below into two scripts, one per host, and test them on any PG15 instance.** Typing during the window wastes it.
- **Decide where the output goes.** A "read-only" session may mean you can't write files on the hosts. If so, run `psql` from your jump host with `tee` to a local file, or log the whole terminal with `script -a session.log`.
- **Ask the app, ETL and backup owners what starts around 02:00–02:10.** Common culprits: ETL loads, `REINDEX`, `VACUUM FULL`, `CLUSTER`, partition create/drop, `TRUNCATE`, `pg_basebackup` or file-level backups on the replica, and the reporting jobs themselves.
- **Check which metric your monitoring actually graphs.** Is it bytes behind (LSN diff) or time since the last replayed commit?

## 02:05–02:20: samplers every 5 s on both hosts

**Primary: is WAL reaching the replica, and where is it stuck?**
```sql
SELECT now(), pg_current_wal_lsn(), application_name, state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_gap_bytes,
       write_lag, flush_lag, replay_lag
FROM pg_stat_replication;
```

**Primary: what starts at 02:10?**
```sql
SELECT pid, usename, application_name, backend_type, state, xact_start,
       wait_event_type, wait_event, left(query, 150)
FROM pg_stat_activity
WHERE state <> 'idle' AND pid <> pg_backend_pid()
ORDER BY xact_start NULLS LAST;

-- AccessExclusiveLocks get replayed on the standby and conflict with every reader of that table
SELECT l.pid, l.relation::regclass, l.mode, left(a.query, 100)
FROM pg_locks l JOIN pg_stat_activity a USING (pid)
WHERE l.locktype = 'relation' AND l.mode = 'AccessExclusiveLock';

SELECT * FROM pg_stat_progress_vacuum;
SELECT * FROM pg_stat_progress_create_index;
SELECT * FROM pg_stat_progress_cluster;
```

**Replica: is replay moving, and what is the startup process waiting on?**
```sql
SELECT now(),
       pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn(),
       pg_wal_lsn_diff(pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn()) AS unapplied_bytes,
       now() - pg_last_xact_replay_timestamp() AS since_last_replayed_commit,
       pg_is_wal_replay_paused();

SELECT pid, wait_event_type, wait_event
FROM pg_stat_activity WHERE backend_type = 'startup';

SELECT locktype, relation::regclass, mode, pid, granted
FROM pg_locks WHERE NOT granted;

-- the reporting queries that could be blocking replay
SELECT pid, usename, application_name, state, backend_xmin,
       now() - xact_start AS xact_age, wait_event_type, wait_event, left(query, 150)
FROM pg_stat_activity
WHERE backend_type = 'client backend' AND state <> 'idle'
ORDER BY xact_start;
```

**A simple loop form, e.g.:**
```bash
while sleep 5; do psql -XAt -F$'\t' -h replica -c "<query>"; done | tee replica_replay.tsv
```

**OS level on the replica (02:08 onward):**
- `watch -n5 'ps -o pid,pcpu,stat,wchan:20,args -C postgres | grep -E "startup|walreceiver"'`. The startup process title shows `recovering <WAL segment>`. If the segment name stops changing, replay is stalled. If it changes but slowly, replay is throughput-bound.
- `iostat -x 5` and `top -p <startup pid>`. Startup near 100% CPU means CPU-bound replay. High `%util` or await means IO-bound. Also check whether reporting queries or a backup are hammering the same disk.

## Previous nights' logs (while the samplers run)

On both hosts, grep the last few days' logs around 02:00–02:45 for:
- `conflict with recovery`
- `recovery still waiting` (this is only logged if `log_recovery_conflict_waits` is on; it defaults to off)
- `checkpoint starting` / `checkpoint complete`
- `automatic vacuum` / `automatic analyze`
- any long `duration:` lines

Checkpoint and autovacuum logging are on by default in PG15 as I recall (`log_checkpoints=on`, `log_autovacuum_min_duration=10min`). Confirm with the settings query above.

## How to read the result

| What you see | Likely cause | Direction of fix |
|---|---|---|
| `replay_lsn` frozen while receive LSN advances; startup waiting on `Lock` or a `RecoveryConflict*` wait event; a long reporting query is running; `confl_*` counters rise around 02:15; `max_standby_streaming_delay` ≈ 300 s | **Recovery conflict.** The trigger is usually an AccessExclusiveLock on the primary (DDL, TRUNCATE, partition maintenance, VACUUM truncating the table tail), or vacuum cleanup under a long snapshot. | Move either the primary job or the report. For snapshot conflicts, `hot_standby_feedback=on`, at the cost of bloat on the primary. For lock conflicts from vacuum truncation, the `vacuum_truncate=false` table option. Or a dedicated reporting replica. |
| Replay advancing but slower than primary WAL generation; `wal_bytes`/`wal_fpi` jump at 02:10; startup CPU- or IO-bound | **WAL burst exceeds single-threaded apply.** Full-page images after a checkpoint, a bulk load or a rewrite. | Throttle or split the job, enable `wal_compression`, space checkpoints further apart, keep `recovery_prefetch` on, reduce IO contention on the replica at that hour. |
| `write_lag`/`flush_lag` grow too, not just `replay_lag` | **Network, WAL receiver or replica disk-write bottleneck.** | Check `pg_stat_wal_receiver`, NIC throughput, disk-write latency on the replica. |
| `unapplied_bytes` ≈ 0 but "lag" still climbs | **Artefact.** Primary is idle, or one long transaction means no commits to replay. | Nothing to fix in the database; alert on LSN byte lag instead. |

Two caveats:
- The wait-event names are from memory, not checked against the PG15 docs. Whatever the exact name, the pattern that matters is `Lock` or `RecoveryConflict…` versus IO waits versus none.
- Everything above is a read. Any fix (settings, `hot_standby_feedback`, rescheduling) needs a separate change window: test on staging first, and have a current backup before any config or schema change on the primary.
