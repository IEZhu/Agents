One correction before the draft: "asking her to replace it" puts the action on the wrong side. If we issued the key, revocation is ours — do it now, tonight, and notify her. Her side owns removing it from the issue and purging it from their systems. An email that waits for her consent leaves a live credential public for however long she takes to read it.

```
Subject: Urgent — Northwind API key exposed publicly, revoked tonight

Elena,

The API key we issued to Northwind is posted in a public GitHub issue:
<ISSUE_URL>

Treat it as compromised. It has been publicly readable since at least
<FIRST_SEEN_TIMESTAMP_UTC>, which is long enough to assume it was scraped.

Done on our side:
- Key <KEY_ID_OR_LAST4> revoked at <TIME + TZ>. Any Northwind integration
  still using it is failing as of that moment.
- Access logs for that key pulled for <ISSUE_DATE> to now. I will send you
  the request history, flagged for anything we cannot attribute to your
  systems, by <DATE>.

Needed from your side:
- Remove the key from that issue and anywhere else it was posted. This does
  not un-compromise it; it only stops further copying.
- Purge it from configs, CI/CD variables, secret stores, scripts, internal
  docs, forks and local clones.
- Tell us which services were using it, so the replacement carries the same
  scope and no more.

Replacement: I can issue a new key immediately. I will deliver it to you
through <SECURE_CHANNEL>, not over email, once you confirm the recipient.

I am reachable tonight at <PHONE>. If the revocation breaks something on
your side before the new key is in place, call rather than wait for Monday.
Likewise if you see requests in your own logs you do not recognise.

<NAME>
<TITLE>, <COMPANY>
```

Fill before sending: issue URL, first-seen timestamp, key identifier (last four characters only — never the full value, and nothing from it in the issue reply either), revocation time, log window, secure delivery channel, your phone.

Two things worth knowing as you handle the issue itself:

Deleting or editing the comment does not retract the key. GitHub keeps edit history on issues and comments and serves prior bodies through its events/timeline API, and search engines and secret-scraping bots index public issues within minutes (recalled, not verified this turn — confirm against current GitHub docs if you plan to rely on it). Revocation is the only control that works.

Revoking at 8pm Saturday will likely break their integration while their staff is thin, and that is the correct trade-off against a publicly readable key — but it is the reason the email leads with the revocation already done and gives her a live phone number rather than a ticket queue.
