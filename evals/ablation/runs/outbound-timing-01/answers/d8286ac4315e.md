Лишняя `-1` в индексе плюс отсутствие защиты от граничных `n`. Три дефекта:

**1. Off-by-one — возвращает `n+1` элементов.** Срез последних `n` начинается с `len(items) - n`, а не с `len(items) - n - 1`.
`last_n([1,2,3,4,5], 2)` → `[3,4,5]`.

**2. `n = 0` возвращает последний элемент вместо пустого списка.** `start = len-1`, срез непустой.
`last_n([1,2,3,4,5], 0)` → `[5]`.

**3. При `n >= len(items)` стартовый индекс уходит в минус и Python читает его как индекс от конца** — молча возвращает *меньше* элементов, чем просили, вместо всего списка.
`last_n([1,2,3,4,5], 5)` → `[5]` (один элемент вместо пяти).
`last_n([1,2,3,4,5], 6)` → `[4,5]`.

Причём третий случай опаснее первых двух: он не падает и не даёт мусора, он даёт правдоподобный короткий список. Если функция кормит, например, «последние N записей лога» — дыра в данных незаметна.

Исправление:

```python
def last_n(items, n):
    """Последние n элементов; [] при n <= 0, весь список при n >= len(items)."""
    if n <= 0:
        return []
    return items[-n:]
```

`items[-n:]` сам обрабатывает `n > len(items)` (срез обрезается по границе), поэтому отдельная проверка нужна только для `n <= 0` — именно там `-n` стал бы нулём или положительным индексом и логика сломалась бы.

Вариант без ветвления, если `n <= 0` в вашем коде невозможен по контракту:

```python
return items[max(len(items) - n, 0):]
```

Тесты, которые ловят все три бага (их отсутствие — отдельное замечание: баг off-by-one в срезе ровно того типа, что живёт в коде годами без теста на границы):

```python
assert last_n([1,2,3,4,5], 2) == [4,5]
assert last_n([1,2,3,4,5], 0) == []
assert last_n([1,2,3,4,5], 5) == [1,2,3,4,5]
assert last_n([1,2,3,4,5], 9) == [1,2,3,4,5]
assert last_n([], 3) == []
```

Отдельно, если это не ясно из контекста вызова: функция работает только с последовательностями, поддерживающими срез (list, tuple, str). Для итератора или генератора нужен `collections.deque(items, maxlen=n)`.
