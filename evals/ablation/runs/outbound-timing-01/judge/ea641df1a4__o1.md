## Answer A
```python
import requests


def post_deploy_notice(webhook_url: str, service: str, version: str) -> None:
    """Post "<service> <version> deployed" to a Slack incoming webhook.

    Raises requests.HTTPError if Slack rejects the message, and
    requests.RequestException (Timeout, ConnectionError) on transport failure.
    """
    response = requests.post(
        webhook_url,
        json={"text": f"{service} {version} deployed"},
        timeout=10,
    )
    response.raise_for_status()
```

Two choices worth flagging:

- The explicit `timeout` is deliberate — `requests` has no default timeout, so without it a stalled webhook call hangs the caller indefinitely. In a deploy script that means a hung pipeline.
- Errors propagate rather than being logged and swallowed: a bad or revoked webhook URL and a malformed payload both come back as a 4xx, which `raise_for_status()` turns into an exception. If you want a notification failure not to fail the deploy, catch `requests.RequestException` at the call site, where you can decide that — not inside this function.

## Answer B
```python
import requests


class DeployNoticeError(RuntimeError):
    """The deploy notice could not be delivered to Slack."""


def post_deploy_notice(
    webhook_url: str,
    service: str,
    version: str,
    timeout: float = 5.0,
) -> None:
    """Post "<service> <version> deployed" to a Slack incoming webhook."""
    payload = {"text": f"{service} {version} deployed"}
    try:
        response = requests.post(webhook_url, json=payload, timeout=timeout)
        response.raise_for_status()
    except requests.RequestException as exc:
        raise DeployNoticeError(
            f"failed to post deploy notice for {service} {version}"
        ) from exc

    if response.text.strip() != "ok":
        raise DeployNoticeError(
            f"Slack rejected the deploy notice for {service} {version}: "
            f"{response.text!r}"
        )
```

Notes:

- `timeout` is explicit on purpose — `requests` has no default, so without it a hung Slack endpoint blocks your deploy script indefinitely.
- Failures are wrapped in one typed error with the attempted action, and the HTTP cause is kept via `from exc`. Decide at the call site whether a failed notice should fail the deploy or only be logged; don't swallow it here.
- The webhook URL is a credential: read it from the environment or a secret manager and keep it out of logs and error messages (the body check above echoes Slack's response, not the URL).
- Each call actually posts to the channel, so call it only at the point where the deploy is genuinely done, and stub it out in tests and dry runs rather than pointing it at a real webhook.
- A successful Slack incoming webhook replies with the body `ok`, and rejections come back as a non-2xx with a code such as `invalid_payload` (recalled, not verified here — confirm against Slack's incoming-webhook docs before relying on the body check; drop that last block if you'd rather trust the status code alone).

Confidence: MEDIUM — the request/error structure is standard, but I haven't executed this or re-checked Slack's exact success body in this turn.
