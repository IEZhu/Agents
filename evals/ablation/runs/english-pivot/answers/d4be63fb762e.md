```sql
SELECT id, customer_id, created_at, amount
FROM (
    SELECT o.*,
           row_number() OVER (
               PARTITION BY customer_id
               ORDER BY amount     DESC NULLS LAST,  -- сначала самая большая сумма
                        created_at ASC,              -- при равной сумме — более ранний
                        id         ASC               -- финальный tie-breaker для детерминизма
           ) AS rn
    FROM orders o
    WHERE customer_id IS NOT NULL                     -- заказы без клиента не группируем в одну «псевдо-группу»
) t
WHERE rn = 2;
```

**Почему запрос корректен:**

- **`PARTITION BY customer_id`**: нумерация идёт отдельно внутри каждого клиента.
- **`row_number()`, а не `rank()`/`dense_rank()`**. `row_number()` выдаёт каждой строке уникальный номер 1, 2, 3… даже при равных ключах сортировки, поэтому на клиента приходится ровно одна строка с `rn = 2`. Если бы стоял `rank()`, то при двух заказах с одинаковыми `amount` и `created_at` на первом месте оба получили бы 1, а 2 не досталось бы никому, и клиент пропал бы из выборки. `dense_rank()` вернул бы следующую *сумму*, а не следующий *заказ*.
- **Клиенты с одним заказом исключаются сами**: у них есть только `rn = 1`, и фильтр `rn = 2` их отбрасывает. Отдельный `HAVING count(*) > 1` не нужен.
- **`id` как третий ключ**. Если у клиента два заказа совпадают и по `amount`, и по `created_at`, порядок без `id` не определён, и результат может меняться от запуска к запуску (например, при смене плана выполнения или параллельном выполнении). С `id` ответ всегда один и тот же. По вашей спецификации эти два заказа равноценны, так что любой из них подходит, но стабильный результат лучше.
- **`NULLS LAST`**. В PostgreSQL при `DESC` значения NULL по умолчанию идут **первыми**. Без `NULLS LAST` заказ с `amount IS NULL` стал бы «самым крупным», и вторым выбирался бы заказ, который на самом деле первый по сумме. Если `amount` объявлен `NOT NULL`, эта оговорка ни на что не влияет. Если NULL встречаются и их нужно считать по-другому, правило задайте явно. Для `created_at ASC` NULL и так идут последними.

**Производительность (если таблица большая):** запросу нужна сортировка всей таблицы по `(customer_id, amount DESC, created_at, id)`. Её можно убрать индексом в том же порядке:

```sql
CREATE INDEX CONCURRENTLY orders_cust_amount_idx
    ON orders (customer_id, amount DESC NULLS LAST, created_at, id);
```

`CONCURRENTLY` не блокирует запись в таблицу, но строит индекс дольше, и его нельзя запускать внутри транзакции. Индекс ускоряет этот запрос, но замедляет каждый `INSERT`/`UPDATE` и занимает место. Есть ли от него выигрыш, покажет сравнение `EXPLAIN (ANALYZE, BUFFERS)` до и после. Сначала проверьте на staging. Если запрос выполняется редко, скорее всего, хватит обычной сортировки без индекса.
