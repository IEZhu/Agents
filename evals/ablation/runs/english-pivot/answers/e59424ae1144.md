```sql
SELECT id, customer_id, created_at, amount
FROM (
    SELECT o.*,
           row_number() OVER (
               PARTITION BY customer_id
               ORDER BY amount DESC NULLS LAST,   -- по сумме по убыванию
                        created_at ASC,           -- при равной сумме: раньше созданный идёт первым
                        id ASC                    -- последний тай-брейк, чтобы порядок был детерминированным
           ) AS rn
    FROM orders o
) t
WHERE rn = 2
ORDER BY customer_id;
```

**Почему это корректно**

- **`row_number()`, а не `rank()`/`dense_rank()`.** `row_number()` нумерует строки внутри клиента подряд 1, 2, 3… без пропусков и без повторов, поэтому `rn = 2` всегда ровно одна строка, «вторая в заданном порядке». С `rank()` при равенстве первых двух (сумма и дата совпадают) получится 1, 1, 3, и второго заказа не будет. С `dense_rank()` под `= 2` может попасть несколько строк.
- **Клиенты с одним заказом отсекаются сами.** У них есть только `rn = 1`, строки с `rn = 2` нет, поэтому отдельный `HAVING count(*) > 1` не нужен.
- **`PARTITION BY customer_id`**: нумерация начинается заново для каждого клиента.
- **`id` как третий ключ.** Если у двух заказов совпадают и `amount`, и `created_at`, без него порядок между ними не определён, и результат может меняться от запуска к запуску. По условию задачи такие заказы равноправны, а `id` просто фиксирует выбор.

**Нюансы с NULL (проверьте, что поведение то, которое нужно)**

- В PostgreSQL `DESC` по умолчанию ставит NULL **первыми**, и заказ без суммы оказался бы «самым крупным». Поэтому я добавил `NULLS LAST`. Если `amount` объявлен `NOT NULL`, это ни на что не влияет.
- Для `created_at ASC` NULL по умолчанию и так идут последними.
- Строки с `customer_id IS NULL` попадут в одну общую группу. Если они не нужны, добавьте во внутренний запрос `WHERE customer_id IS NOT NULL`.

**Производительность (необязательно)**

Запрос делает один проход по таблице с сортировкой. На большой таблице сортировку может убрать индекс, совпадающий с окном:

```sql
-- CONCURRENTLY не блокирует запись в таблицу; цена: дополнительная нагрузка на INSERT/UPDATE
CREATE INDEX CONCURRENTLY orders_cust_amount_idx
    ON orders (customer_id, amount DESC NULLS LAST, created_at, id);
```

Стоит ли его создавать, видно только по `EXPLAIN (ANALYZE, BUFFERS)` на ваших данных: если в плане есть `Sort` с `external merge`, индекс скорее всего поможет. Если клиентов мало, а заказов у каждого много, с тем же индексом может оказаться быстрее вариант через `LATERAL (... ORDER BY ... OFFSET 1 LIMIT 1)` по списку клиентов. Это тоже нужно проверять по плану.
