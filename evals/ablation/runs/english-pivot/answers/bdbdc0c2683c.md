Да, почти наверняка их можно вернуть. `git reset --hard` не удаляет коммиты, а только переносит указатель ветки. Сами коммиты остаются в репозитории как недостижимые (unreachable), а их хэши записаны в reflog. Вернуть не получится только **незакоммиченные** изменения, которые были в рабочей директории в момент reset. О них сказано в конце.

## Шаги

**0. Пока ничего не чистите.** Не запускайте `git gc --prune=now` и `git reflog expire`. По умолчанию недостижимые записи reflog хранятся около 30 дней (recalled, not verified: это настройка `gc.reflogExpireUnreachable`), так что время есть, но лучше не тянуть.

**1. Найдите состояние ветки до reset:**

```bash
git reflog show feature/payments
```

или общий reflog HEAD:

```bash
git reflog
```

Ищите строку вида:

```
abc1234 HEAD@{0}: reset: moving to HEAD~3
def5678 HEAD@{1}: commit: <сообщение вашего последнего коммита>
```

Вам нужна запись **сразу под** `reset: moving to HEAD~3`, в примере это `def5678` / `HEAD@{1}`. Лучше скопировать хэш, а не `HEAD@{1}`: номера сдвигаются после каждой следующей операции.

**2. Проверьте, что это те самые коммиты:**

```bash
git log --oneline -5 def5678
```

В выводе должны быть три пропавших коммита сверху.

**3. Поставьте страховочную ветку.** Это ничего не меняет в текущем состоянии:

```bash
git branch backup/payments-restore def5678
```

С этого момента коммиты снова достижимы, и `gc` их не удалит.

**4. Верните ветку на место.** Сначала посмотрите `git status`.

- Если рабочая директория чистая:
  ```bash
  git switch feature/payments
  git reset --hard def5678
  ```
- Если после reset вы уже что-то меняли и не закоммитили, не делайте `reset --hard`, иначе потеряете и эти правки. Выполните:
  ```bash
  git stash
  git reset --hard def5678
  git stash pop
  ```
- Если после reset вы успели сделать **новые коммиты**, не используйте reset: он их выбросит. Перенесите старые коммиты поверх новых:
  ```bash
  git cherry-pick <хэш_1> <хэш_2> <хэш_3>   # от старого к новому
  ```
  Другой вариант: `git rebase` новых коммитов на `backup/payments-restore`.

**5. Проверьте результат:**

```bash
git log --oneline -5
git diff backup/payments-restore   # пустой вывод = ветка восстановлена полностью
```

**6. Удалите страховку**, когда убедитесь, что всё на месте:

```bash
git branch -d backup/payments-restore
```

## Быстрый вариант

Если сразу после reset вы ничего не делали, обычно хватает одной команды:

```bash
git reset --hard ORIG_HEAD
```

`reset` записывает в `ORIG_HEAD` предыдущую позицию. Но `ORIG_HEAD` перезаписывают и другие команды: `merge`, `rebase`, следующий `reset`. Поэтому сначала проверьте его через `git log --oneline -3 ORIG_HEAD`.

## Если в reflog ничего нет

Такое бывает, если reflog отключён или почищен. Тогда поищите «висячие» коммиты:

```bash
git fsck --lost-found --no-reflogs | grep commit
git show <хэш>
```

Найденный нужный коммит восстанавливается так же, как в шаге 3.

## Чего вернуть нельзя

Изменения, которые не были закоммичены в момент `reset --hard`, через reflog не восстановить. Если они были добавлены в индекс (`git add`), их содержимое иногда находится среди «dangling blob» в выводе `git fsck --lost-found`. Имена файлов при этом теряются, и восстанавливать придётся вручную. Правки, которые не попали ни в коммит, ни в индекс, Git не сохранял вообще.

**Уверенность: HIGH** по самой процедуре (reflog + reset или cherry-pick): это стандартный и проверенный путь. Сроки хранения reflog я указал по памяти, их стоит перепроверить в `git help config`.
