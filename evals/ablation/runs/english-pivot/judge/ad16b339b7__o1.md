## Latest user message
PostgreSQL 16, таблица orders(id bigint, customer_id bigint, created_at timestamptz, amount numeric). Нужно для каждого клиента вывести его второй заказ по сумме: заказы клиента упорядочиваем по amount по убыванию, при равной сумме — по created_at по возрастанию, и берём второй в этом порядке. Клиентов с одним заказом не выводить. Напиши запрос и коротко поясни, почему он корректен.

## Rubric (what a strong answer does)
1. Numbers each customer's orders with ROW_NUMBER() (or an equivalent that always yields exactly one second row) partitioned by customer_id and ordered by amount DESC, created_at ASC, and keeps row number 2 (NULLS LAST or a final id tiebreaker is fine).
2. Customers with a single order drop out because they have no second row, or the query excludes them explicitly.
3. The explanation correctly describes how equal amounts are ordered by created_at.
4. The reply is in Russian, with code, commands and identifiers left as written, and contains no English restatement of the request.

## Answer A
```sql
SELECT id, customer_id, created_at, amount
FROM (
    SELECT o.*,
           row_number() OVER (
               PARTITION BY customer_id
               ORDER BY amount DESC NULLS LAST,   -- по сумме по убыванию
                        created_at ASC,           -- при равной сумме: раньше созданный идёт первым
                        id ASC                    -- последний тай-брейк, чтобы порядок был детерминированным
           ) AS rn
    FROM orders o
) t
WHERE rn = 2
ORDER BY customer_id;
```

**Почему это корректно**

- **`row_number()`, а не `rank()`/`dense_rank()`.** `row_number()` нумерует строки внутри клиента подряд 1, 2, 3… без пропусков и без повторов, поэтому `rn = 2` всегда ровно одна строка, «вторая в заданном порядке». С `rank()` при равенстве первых двух (сумма и дата совпадают) получится 1, 1, 3, и второго заказа не будет. С `dense_rank()` под `= 2` может попасть несколько строк.
- **Клиенты с одним заказом отсекаются сами.** У них есть только `rn = 1`, строки с `rn = 2` нет, поэтому отдельный `HAVING count(*) > 1` не нужен.
- **`PARTITION BY customer_id`**: нумерация начинается заново для каждого клиента.
- **`id` как третий ключ.** Если у двух заказов совпадают и `amount`, и `created_at`, без него порядок между ними не определён, и результат может меняться от запуска к запуску. По условию задачи такие заказы равноправны, а `id` просто фиксирует выбор.

**Нюансы с NULL (проверьте, что поведение то, которое нужно)**

- В PostgreSQL `DESC` по умолчанию ставит NULL **первыми**, и заказ без суммы оказался бы «самым крупным». Поэтому я добавил `NULLS LAST`. Если `amount` объявлен `NOT NULL`, это ни на что не влияет.
- Для `created_at ASC` NULL по умолчанию и так идут последними.
- Строки с `customer_id IS NULL` попадут в одну общую группу. Если они не нужны, добавьте во внутренний запрос `WHERE customer_id IS NOT NULL`.

**Производительность (необязательно)**

Запрос делает один проход по таблице с сортировкой. На большой таблице сортировку может убрать индекс, совпадающий с окном:

```sql
-- CONCURRENTLY не блокирует запись в таблицу; цена: дополнительная нагрузка на INSERT/UPDATE
CREATE INDEX CONCURRENTLY orders_cust_amount_idx
    ON orders (customer_id, amount DESC NULLS LAST, created_at, id);
```

Стоит ли его создавать, видно только по `EXPLAIN (ANALYZE, BUFFERS)` на ваших данных: если в плане есть `Sort` с `external merge`, индекс скорее всего поможет. Если клиентов мало, а заказов у каждого много, с тем же индексом может оказаться быстрее вариант через `LATERAL (... ORDER BY ... OFFSET 1 LIMIT 1)` по списку клиентов. Это тоже нужно проверять по плану.


## Answer B
```sql
SELECT id, customer_id, created_at, amount
FROM (
    SELECT o.*,
           row_number() OVER (
               PARTITION BY customer_id
               ORDER BY amount     DESC NULLS LAST,  -- сначала самая большая сумма
                        created_at ASC,              -- при равной сумме — более ранний
                        id         ASC               -- финальный tie-breaker для детерминизма
           ) AS rn
    FROM orders o
    WHERE customer_id IS NOT NULL                     -- заказы без клиента не группируем в одну «псевдо-группу»
) t
WHERE rn = 2;
```

**Почему запрос корректен:**

- **`PARTITION BY customer_id`**: нумерация идёт отдельно внутри каждого клиента.
- **`row_number()`, а не `rank()`/`dense_rank()`**. `row_number()` выдаёт каждой строке уникальный номер 1, 2, 3… даже при равных ключах сортировки, поэтому на клиента приходится ровно одна строка с `rn = 2`. Если бы стоял `rank()`, то при двух заказах с одинаковыми `amount` и `created_at` на первом месте оба получили бы 1, а 2 не досталось бы никому, и клиент пропал бы из выборки. `dense_rank()` вернул бы следующую *сумму*, а не следующий *заказ*.
- **Клиенты с одним заказом исключаются сами**: у них есть только `rn = 1`, и фильтр `rn = 2` их отбрасывает. Отдельный `HAVING count(*) > 1` не нужен.
- **`id` как третий ключ**. Если у клиента два заказа совпадают и по `amount`, и по `created_at`, порядок без `id` не определён, и результат может меняться от запуска к запуску (например, при смене плана выполнения или параллельном выполнении). С `id` ответ всегда один и тот же. По вашей спецификации эти два заказа равноценны, так что любой из них подходит, но стабильный результат лучше.
- **`NULLS LAST`**. В PostgreSQL при `DESC` значения NULL по умолчанию идут **первыми**. Без `NULLS LAST` заказ с `amount IS NULL` стал бы «самым крупным», и вторым выбирался бы заказ, который на самом деле первый по сумме. Если `amount` объявлен `NOT NULL`, эта оговорка ни на что не влияет. Если NULL встречаются и их нужно считать по-другому, правило задайте явно. Для `created_at ASC` NULL и так идут последними.

**Производительность (если таблица большая):** запросу нужна сортировка всей таблицы по `(customer_id, amount DESC, created_at, id)`. Её можно убрать индексом в том же порядке:

```sql
CREATE INDEX CONCURRENTLY orders_cust_amount_idx
    ON orders (customer_id, amount DESC NULLS LAST, created_at, id);
```

`CONCURRENTLY` не блокирует запись в таблицу, но строит индекс дольше, и его нельзя запускать внутри транзакции. Индекс ускоряет этот запрос, но замедляет каждый `INSERT`/`UPDATE` и занимает место. Есть ли от него выигрыш, покажет сравнение `EXPLAIN (ANALYZE, BUFFERS)` до и после. Сначала проверьте на staging. Если запрос выполняется редко, скорее всего, хватит обычной сортировки без индекса.
