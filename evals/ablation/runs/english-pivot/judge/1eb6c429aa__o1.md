## Latest user message
Пытаюсь подключиться: psql -h db.local -p 5432 -U app, получаю «psql: ошибка: подключиться к серверу "db.local" (192.168.1.20), порту 5432 не удалось: В соединении отказано. Сервер действительно работает по данному адресу и принимает TCP-соединения?». С самого сервера через localhost всё работает. Что проверить?

## Answer A
Скорее всего, PostgreSQL слушает только `localhost`. «В соединении отказано» (connection refused) означает, что TCP-пакет дошёл до 192.168.1.20, но на этом адресе и порту никто не принимает соединения либо файрвол отвечает REJECT. До `pg_hba.conf` дело ещё не дошло: при проблеме в нём ошибка была бы другой, `no pg_hba.conf entry for host ...`.

Проверяйте по порядку.

### 1. На каком адресе слушает сервер (самая вероятная причина)

На сервере:

```bash
# Какие адреса и порты слушает postgres
sudo ss -ltnp | grep 5432
```

- Если видите только `127.0.0.1:5432` (и/или `[::1]:5432`), то причина найдена. По умолчанию `listen_addresses = 'localhost'`, поэтому через localhost всё и работает.
- Если `0.0.0.0:5432` или `192.168.1.20:5432`, то сервер слушает правильно, переходите к пунктам 3–4.
- Если на 5432 ничего нет, проверьте порт: `SHOW port;`.

Текущие настройки и откуда они взялись:

```sql
-- Выполнить через локальный psql на сервере
SHOW listen_addresses;
SHOW port;
-- Показывает, из какого файла и строки взято значение (postgresql.conf или postgresql.auto.conf)
SELECT name, setting, sourcefile, sourceline
FROM pg_settings WHERE name IN ('listen_addresses', 'port');
```

Исправление:

```sql
-- Слушать localhost и LAN-интерфейс. Лучше указать конкретный IP, а не '*'
ALTER SYSTEM SET listen_addresses = 'localhost,192.168.1.20';
```

```bash
# listen_addresses применяется только после рестарта, reload не поможет
sudo systemctl restart postgresql
```

Учтите, что рестарт обрывает все текущие соединения, так что на проде планируйте окно. `ALTER SYSTEM` пишет в `postgresql.auto.conf` и перекрывает `postgresql.conf`. Откатить можно командой `ALTER SYSTEM RESET listen_addresses;` и ещё одним рестартом.

### 2. pg_hba.conf (понадобится сразу после пункта 1)

Когда сервер начнёт слушать сеть, следующей ошибкой почти наверняка будет `no pg_hba.conf entry`. Добавьте строку, ограниченную вашей подсетью и нужной базой:

```
# TYPE  DATABASE  USER  ADDRESS          METHOD
host    appdb     app   192.168.1.0/24   scram-sha-256
```

```sql
SHOW hba_file;            -- где лежит файл
SELECT pg_reload_conf();  -- для pg_hba достаточно reload
-- В PG 15+ можно проверить ошибки разбора файла (recalled, not verified: в 15 добавлена колонка rule_number):
SELECT * FROM pg_hba_file_rules WHERE error IS NOT NULL;
```

Не открывайте `0.0.0.0/0` с `trust`. Если пароль пользователя `app` хранится в md5, а метод стоит `scram-sha-256`, вход не пройдёт, поэтому проверьте `password_encryption` и при необходимости переустановите пароль.

### 3. Файрвол на сервере

Если `ss` показывает правильный адрес, а отказ остаётся, вероятно, мешает правило REJECT. При DROP был бы таймаут, а не отказ.

```bash
sudo ufw status verbose                 # Ubuntu/Debian
sudo firewall-cmd --list-all            # RHEL/Fedora
sudo nft list ruleset | grep -i 5432    # или iptables -L -n | grep 5432
```

Открывать порт стоит только для вашей подсети, например `sudo ufw allow from 192.168.1.0/24 to any port 5432 proto tcp`.

### 4. Тот ли это хост и тот ли путь

```bash
# На клиенте: куда резолвится имя и открыт ли порт
getent hosts db.local
nc -zv 192.168.1.20 5432

# На сервере: свой ли это IP. И подключение по LAN-IP, а не по localhost
ip -br addr
psql -h 192.168.1.20 -U app -d appdb
```

Последняя команда хорошо разделяет причины. Если она отказывает прямо на сервере, проблема в `listen_addresses` или в локальном файрволе, а не в сети. Если на сервере работает, а с клиента нет, ищите сетевой файрвол между машинами или ошибку в DNS (`.local` иногда обрабатывается через mDNS и может резолвиться неожиданно).

### 5. Если Postgres в Docker

Проверьте `docker ps`. Публикация вида `127.0.0.1:5432->5432/tcp` или её полное отсутствие (`5432/tcp` без стрелки) даёт ровно такой симптом. Нужно `-p 192.168.1.20:5432:5432` или `-p 5432:5432`.

### Что ещё стоит сделать

Если к базе будет ходить приложение по сети, поставьте перед ней pgBouncer (или другой пулер). Тогда наружу смотрит пулер, а сам Postgres можно оставить на localhost.

Если после пункта 1 ошибка изменится, пришлите вывод `ss -ltnp | grep 5432` и новый текст ошибки, по ним уже будет видно точную причину.


## Answer B
**Коротко:** «В соединении отказано» (connection refused) означает, что TCP-пакет дошёл до хоста 192.168.1.20, но на порту 5432 этого адреса никто не слушает, либо фаервол отвечает REJECT. До проверки пароля и `pg_hba.conf` дело не доходит: при отказе по `pg_hba.conf` текст ошибки был бы другим (`no pg_hba.conf entry for host ...`). Почти наверняка PostgreSQL слушает только `localhost`, потому что `listen_addresses = 'localhost'` стоит по умолчанию.

## 1. На каком адресе и порту слушает сервер

На сервере БД:

```bash
ss -ltnp | grep postgres
```

- `127.0.0.1:5432` (и/или `[::1]:5432`): слушает только loopback. Это ваш случай с вероятностью ~90%.
- `0.0.0.0:5432` или `192.168.1.20:5432`: слушает сеть, переходите к пункту 3.
- Порт не 5432: значит, кластер настроен на другой порт. Учтите, что `psql` без `-h` ходит через unix-socket, поэтому «локально работает» ещё не доказывает, что сервер слушает TCP на 5432.

Проверить настройку изнутри:

```sql
SHOW listen_addresses;
SHOW port;
SHOW config_file;
```

## 2. Исправить `listen_addresses`

В `postgresql.conf` (путь показывает `SHOW config_file`):

```conf
# Слушать loopback и конкретный сетевой интерфейс. Безопаснее, чем '*'
listen_addresses = 'localhost,192.168.1.20'
```

Или через SQL:

```sql
ALTER SYSTEM SET listen_addresses = 'localhost,192.168.1.20';
```

**Важно:** этот параметр применяется только после **перезапуска** сервера, `reload` его не подхватит:

```bash
sudo systemctl restart postgresql   # имя юнита зависит от дистрибутива/версии, например postgresql@16-main
```

При перезапуске все текущие соединения рвутся. Если сервер продовый, делайте это в окно обслуживания.

## 3. Фаервол на сервере

Если `ss` показывает, что сервер слушает внешний адрес, а отказ остаётся, вероятно, порт закрыт правилом REJECT (при DROP вы бы получили таймаут, а не отказ):

```bash
sudo ufw status                        # Ubuntu/Debian
sudo firewall-cmd --list-all           # RHEL/Fedora
sudo nft list ruleset | grep 5432      # или iptables -S | grep 5432
```

Открывайте порт только для нужной подсети, например `sudo ufw allow from 192.168.1.0/24 to any port 5432 proto tcp`.

## 4. Туда ли вы вообще подключаетесь

- Убедитесь, что `db.local` разрешается в адрес именно этого сервера. Имена `.local` часто обслуживает mDNS, и они могут указывать не туда. На сервере выполните `ip -4 addr`, на клиенте `getent hosts db.local`.
- Если PostgreSQL работает в Docker, проверьте публикацию порта: `-p 127.0.0.1:5432:5432` открывает его только локально, нужно `-p 5432:5432` или `-p 192.168.1.20:5432:5432`.
- С клиента: `nc -vz 192.168.1.20 5432`. Ответ `refused` означает, что проблема на стороне сервера или фаервола, а `succeeded` означает, что TCP проходит.

## 5. Следующий шаг: `pg_hba.conf`

Когда TCP заработает, следующей ошибкой, скорее всего, будет `no pg_hba.conf entry for host "<ip клиента>"`. Добавьте строку:

```conf
# TYPE  DATABASE  USER  ADDRESS          METHOD
host    all       app   192.168.1.0/24   scram-sha-256
```

Для изменений в `pg_hba.conf` перезапуск не нужен, хватит `SELECT pg_reload_conf();`.

**Компромисс:** открывая PostgreSQL в сеть, вы увеличиваете поверхность атаки. Ограничьте доступ тремя слоями: `listen_addresses` (только нужный интерфейс), фаервол (только нужная подсеть) и `pg_hba.conf` (конкретный пользователь и подсеть, `scram-sha-256`, а не `trust`).

**Проверка:** с клиента выполните `psql -h db.local -p 5432 -U app -c 'SELECT inet_server_addr(), inet_client_addr();'`. В ответе должны быть `192.168.1.20` и IP клиента.
