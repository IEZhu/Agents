## Root cause: why the proposed line doesn't hold

- **The order is wrong for that claim.** Pool saturation (16:55) comes before the deploy completed (16:58:40). A rolling deploy that was already underway could still explain it, but "completed" is the only timestamp you have. You need the deploy **start** time before you can link the two.
- **Recovery came 15 min after the rollback** (17:11 to 17:26). That fits "rollback fixed it", and it also fits a DB-side problem clearing on its own. With these data points you can't tell them apart.
- **17:11 is when Ravi's Slack message was sent**, which isn't necessarily when the rollback happened. Take the rollback time from GitHub Actions or your deploy tool.

A line you can defend today:

> **Root cause: under investigation.** postgres-primary connection pool saturation began at 16:55 UTC, before the payments-api v4.12.0 deploy completed at 16:58:40. Service recovered at 17:26 UTC following a rollback to v4.11.3 at about 17:11 UTC.

If you confirm that v4.12.0 was already rolling out before 16:55 and that it changed DB access (pool size, queries, migrations, connection handling), then your original line becomes justified.

## Other things to fix before this goes to your director

1. **The date isn't a Monday.** 2026-09-22 is a Tuesday. Either the outage was on Monday, 2026-09-21, and the GitHub timestamp you copied is from a different run, or "Monday" is wrong. Check the date on the Actions run.
2. **Status page lag.** "Investigating" went up at 17:31 UTC. That's 27 min after the first page and 5 min after errors had already recovered. Reviewers will notice, so it probably belongs in the action items.
3. **Datadog monitor timestamps are trigger times.** Each monitor evaluates over a window, so the pool problem may have started a few minutes before 16:55. Check the raw pool metric graph for the actual onset.
4. **Other consumers of postgres-primary.** If services other than payments-api were affected, that points away from the deploy.

Checks to run: deploy start and end times for both v4.12.0 and the rollback, the v4.12.0 diff for DB-related changes, the raw connection pool metric from about 16:40 UTC, and the list of clients connected to postgres-primary at 16:55.

## Issues to fix before you send it

1. **The date doesn't match "Monday."** 2026-09-22 is a Tuesday; Monday was 2026-09-21. Check the GitHub Actions date, or change "Monday" in the doc.
2. **The pool saturation came before the deploy finished.** The only way to blame v4.12.0 is if the rollout was already live before 16:55. That's possible, but you need the deploy **start** time and the time the first new pods or instances took traffic.
3. **We only know when the rollback was announced.** The 17:11 time comes from a Slack message, not deploy logs. Get the actual rollback start and finish times from GitHub Actions.
4. **Recovery took 15 minutes after the rollback** (17:11 → 17:26). That gap needs an explanation, for example pool drain, slow rollout, or recovery that had nothing to do with the rollback.
5. **The status page went up after users were already fine.** "Investigating" was posted at 17:31, which is 27 minutes after the first page and 5 minutes after the error rate recovered. Your director will likely spot this, so address it in the doc.
6. **The data is missing:**
   - What changed in v4.12.0, especially DB queries, pool settings or migrations
   - When the pool alert cleared
   - Whether other services share `postgres-primary`
   - The pool usage trend before 16:55
