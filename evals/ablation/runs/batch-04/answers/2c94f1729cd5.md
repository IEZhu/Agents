## Issues to fix before you send it

1. **The date doesn't match "Monday."** 2026-09-22 is a Tuesday; Monday was 2026-09-21. Check the GitHub Actions date, or change "Monday" in the doc.
2. **The pool saturation came before the deploy finished.** The only way to blame v4.12.0 is if the rollout was already live before 16:55. That's possible, but you need the deploy **start** time and the time the first new pods or instances took traffic.
3. **We only know when the rollback was announced.** The 17:11 time comes from a Slack message, not deploy logs. Get the actual rollback start and finish times from GitHub Actions.
4. **Recovery took 15 minutes after the rollback** (17:11 → 17:26). That gap needs an explanation, for example pool drain, slow rollout, or recovery that had nothing to do with the rollback.
5. **The status page went up after users were already fine.** "Investigating" was posted at 17:31, which is 27 minutes after the first page and 5 minutes after the error rate recovered. Your director will likely spot this, so address it in the doc.
6. **The data is missing:**
   - What changed in v4.12.0, especially DB queries, pool settings or migrations
   - When the pool alert cleared
   - Whether other services share `postgres-primary`
   - The pool usage trend before 16:55

## Suggested one-liner (supported by the evidence you have)

> **Root cause: under investigation.** Checkout failures (17:03–17:26 UTC) coincided with Postgres primary connection pool saturation, which began at 16:55, before the payments-api v4.12.0 deploy completed at 16:58:40. Error rates recovered about 15 minutes after the rollback to v4.11.3. Whether v4.12.0 caused the saturation has not been established.

If the deploy start time and the v4.12.0 diff do put new code in production before 16:55, you can change the line to something like "v4.12.0 exhausted the postgres-primary connection pool." It should name the mechanism, not just say "faulty deploy."
