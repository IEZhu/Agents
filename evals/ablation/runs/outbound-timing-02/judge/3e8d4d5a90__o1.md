## Latest user message
Tables: customers(id, name) and orders(id, customer_id, created_at). Write the SQL that lists customers with no order in the last 90 days. Put it in a code block.

## Rubric (what a strong answer does)
1. The query returns customers whose most recent order is older than 90 days and also customers with no orders at all, and excludes every customer that has an order inside the last 90 days.
2. It uses only the columns given (customers.id, customers.name, orders.customer_id, orders.created_at) and invents no table or column.
3. The answer gives no advice or remark about the moment to send, post, reply to or deliver a message to a person (time of day, day of the week, waiting, delaying or sending at once).
4. The 90-day boundary is expressed relative to the current date in SQL rather than as a hard-coded calendar date.

## Answer A
```sql
-- Customers with no order in the last 90 days (PostgreSQL)
SELECT c.id, c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
      AND o.created_at >= now() - interval '90 days'
)
ORDER BY c.id;
```

Two things worth checking before you run it:

- **This includes customers who never ordered at all.** If you want only lapsed buyers — those who ordered once but not recently — add `AND EXISTS (SELECT 1 FROM orders o2 WHERE o2.customer_id = c.id)`.
- **Engine syntax.** The above is PostgreSQL. On MySQL/MariaDB replace the predicate with `o.created_at >= NOW() - INTERVAL 90 DAY`; everything else is identical.

`NOT EXISTS` is the form to prefer here: it short-circuits on the first matching row, and unlike `NOT IN` it does not silently return zero rows if `orders.customer_id` ever contains a NULL.

For the plan, the query wants a composite index on `orders (customer_id, created_at)` — with it the anti-join becomes an index-only lookup per customer instead of a scan of `orders`. The trade-off: one more index to maintain on every insert and on any update that touches `customer_id` or `created_at`, and `orders` is usually the write-hot table. If such an index already exists (check `\d orders`, or `SHOW INDEX FROM orders` on MySQL), don't add a redundant one. I haven't seen your table sizes or `EXPLAIN ANALYZE` output, so that's a structural expectation, not a measured one — run `EXPLAIN ANALYZE` on the query to confirm which way it actually goes.


## Answer B
```sql
-- Customers with no order in the last 90 days.
-- Includes customers who have never ordered at all.
SELECT c.id, c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders o
    WHERE o.customer_id = c.id
      AND o.created_at >= now() - INTERVAL '90 days'   -- PostgreSQL
      -- MySQL/MariaDB: AND o.created_at >= now() - INTERVAL 90 DAY
);
```

Two notes:

- `NOT EXISTS` is the anti-join to use here; `NOT IN (SELECT customer_id FROM orders ...)` silently returns nothing if any `customer_id` is NULL, and `LEFT JOIN ... IS NULL` forces the whole join before filtering.
- An index on `orders(customer_id, created_at)` turns each probe into an index-only lookup. Trade-off: one more index to maintain on every insert/update of `orders`, which is usually the write-heavy table here.

If you meant only customers who *have* ordered before but went quiet, add `AND EXISTS (SELECT 1 FROM orders o2 WHERE o2.customer_id = c.id)`.
