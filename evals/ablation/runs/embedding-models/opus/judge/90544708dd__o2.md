## Latest user message
PostgreSQL 16, таблица orders(id bigint, customer_id bigint, created_at timestamptz, amount numeric). Нужно для каждого клиента вывести его второй заказ по сумме: заказы клиента упорядочиваем по amount по убыванию, при равной сумме — по created_at по возрастанию, и берём второй в этом порядке. Клиентов с одним заказом не выводить. Напиши запрос и коротко поясни, почему он корректен.

## Rubric (what a strong answer does)
1. Numbers each customer's orders with ROW_NUMBER() (or an equivalent that always yields exactly one second row) partitioned by customer_id and ordered by amount DESC, created_at ASC, and keeps row number 2 (NULLS LAST or a final id tiebreaker is fine).
2. Customers with a single order drop out because they have no second row, or the query excludes them explicitly.
3. The explanation correctly describes how equal amounts are ordered by created_at.
4. The reply is in Russian, with code, commands and identifiers left as written, and contains no English restatement of the request.

## Answer A
```sql
SELECT id, customer_id, created_at, amount
FROM (
    SELECT o.*,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY amount DESC NULLS LAST,  -- по сумме по убыванию; NULL-суммы в конец
                        created_at ASC,          -- при равной сумме — более ранний первым
                        id ASC                   -- финальный tie-breaker для детерминизма
           ) AS rn
    FROM orders o
) t
WHERE rn = 2;
```

## Почему это корректно

- **`ROW_NUMBER()`, а не `RANK()`/`DENSE_RANK()`.** `ROW_NUMBER` даёт строкам внутри клиента сквозную нумерацию 1, 2, 3… без пропусков и повторов, поэтому `rn = 2` всегда ровно одна строка, то есть второй заказ в заданном порядке. С `RANK` при двух заказах с одинаковыми (amount, created_at) обе строки получили бы 1, а строки с номером 2 не было бы совсем. С `DENSE_RANK` под `= 2` могли бы попасть сразу несколько строк.
- **`PARTITION BY customer_id`.** Нумерация начинается заново для каждого клиента.
- **Клиенты с одним заказом выпадают сами.** У них есть только `rn = 1`, и фильтр `rn = 2` их отсекает. Отдельный `HAVING count(*) > 1` не нужен.
- **`id` в конце `ORDER BY`.** Если у клиента совпадают и `amount`, и `created_at`, порядок без него не определён, и результат мог бы меняться от запуска к запуску. Условие задачи на такой случай ничего не говорит, `id` просто фиксирует выбор.
- **`NULLS LAST`.** В PostgreSQL при `DESC` значения NULL по умолчанию идут **первыми**. Без `NULLS LAST` заказ с `amount IS NULL` считался бы «самым дорогим». Если колонка объявлена `NOT NULL`, эта часть ни на что не влияет. Если же NULL должен считаться «первым», уберите `NULLS LAST`.

## Производительность (по желанию)

На большой таблице окно потребует сортировки по всему `orders`. Её можно убрать индексом, порядок которого совпадает с окном:

```sql
-- CONCURRENTLY — чтобы не блокировать запись в orders на время построения
CREATE INDEX CONCURRENTLY orders_cust_amount_idx
    ON orders (customer_id, amount DESC NULLS LAST, created_at, id);
```

Плюс: возможен план без узла Sort (проверьте через `EXPLAIN (ANALYZE, BUFFERS)`, работает ли так на ваших данных). Минус: индекс замедляет каждую вставку и обновление и занимает место. Нужен он, только если запрос частый, а Sort в плане действительно дорогой.


## Answer B
```sql
SELECT id, customer_id, created_at, amount
FROM (
    SELECT o.*,
           row_number() OVER (
               PARTITION BY customer_id
               ORDER BY amount DESC NULLS LAST,   -- сначала самые крупные; NULL-суммы в конец
                        created_at ASC,           -- при равной сумме более ранний заказ идёт первым
                        id ASC                    -- финальный tie-breaker для полной детерминированности
           ) AS rn
    FROM orders o
) t
WHERE rn = 2;
```

**Почему это корректно**

- **`row_number()`, а не `rank()`/`dense_rank()`.** `row_number()` выдаёт каждой строке внутри клиента уникальный номер 1, 2, 3… строго по заданному порядку, поэтому `rn = 2` всегда ровно одна строка, то есть второй заказ в этом порядке. `rank()` при равенстве по первому месту дал бы `1, 1, 3`, и строки с `rank = 2` не оказалось бы вовсе. `dense_rank()` вернул бы «вторую по величине сумму», а не второй заказ, и мог бы дать несколько строк.
- **Клиенты с одним заказом отсекаются сами собой.** У них есть только строка с `rn = 1`, а `rn = 2` нет, поэтому `HAVING count(*) > 1` или отдельный подзапрос не нужны.
- **`PARTITION BY customer_id`** — нумерация начинается заново для каждого клиента.
- **`id` как последний ключ.** Если у клиента два заказа с одинаковыми `amount` и `created_at`, порядок по условию задачи не определён, и без tie-breaker'а между запусками может возвращаться то одна строка, то другая. С `id` результат стабилен. Если такие дубли по смыслу невозможны, этот ключ ничего не меняет.
- **`NULLS LAST`.** В PostgreSQL при `DESC` NULL по умолчанию идут **первыми**, и заказ с `amount IS NULL` занял бы первое место. Скорее всего, это не то, что нужно, поэтому NULL-суммы явно отправлены в конец. Если `amount` объявлен `NOT NULL`, эта оговорка ни на что не влияет. Для `created_at ASC` NULL по умолчанию и так идут последними.

**Производительность (если таблица большая)**

Запросу подойдёт индекс, совпадающий с окном:

```sql
CREATE INDEX CONCURRENTLY orders_cust_amount_created_idx
    ON orders (customer_id, amount DESC NULLS LAST, created_at, id);
```

С ним PostgreSQL может отдавать строки уже отсортированными и обойтись без Sort-узла. Но это стоит подтвердить по `EXPLAIN (ANALYZE, BUFFERS)` на реальных данных. Здесь всё равно читается вся таблица, и на маленьком объёме индекс может не окупиться, а каждый дополнительный индекс замедляет запись. `CONCURRENTLY` не блокирует запись в таблицу, но строится дольше и не работает внутри транзакции.
