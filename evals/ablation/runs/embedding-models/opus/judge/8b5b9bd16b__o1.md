## Latest user message
Под с сервисом на Java 21 в Kubernetes каждые пару часов перезапускается, в kubectl describe pod вижу Last State: Terminated, Reason: OOMKilled, Exit Code: 137. В контейнере limits.memory: 512Mi, приложение запускается с -Xmx512m. Почему так и что поменять?

## Rubric (what a strong answer does)
1. Explains that -Xmx caps only the heap while the JVM also uses non-heap memory (metaspace, thread stacks, code cache, direct buffers), so a 512m heap lets the process exceed the 512Mi limit and the container is OOM-killed (exit code 137).
2. Recommends a concrete fix: a heap well below the limit (for example replacing -Xmx with -XX:MaxRAMPercentage, or a smaller -Xmx) and/or a higher limits.memory, and suggests measuring actual memory use.
3. Does not mistake the symptom for a Java OutOfMemoryError: it is a container OOM kill.
4. The reply is in Russian, with code, commands and identifiers left as written, and contains no English restatement of the request.

## Answer A
**Коротко:** вы отдали под heap всю память контейнера. `-Xmx512m` ограничивает только heap, а JVM использует ещё и память вне heap. Когда heap за пару часов заполняется до 512 MiB, суммарное потребление процесса превышает `limits.memory: 512Mi`, и ядро (cgroup OOM killer) убивает процесс сигналом SIGKILL: 137 = 128 + 9. Это не Java-шный `OutOfMemoryError`, поэтому в логах приложения ничего не видно и heap dump не создаётся.

### Почему так

Память Java-процесса (RSS) складывается примерно так:

```
RSS ≈ Heap (до -Xmx)
    + Metaspace (классы; у Spring/Hibernate обычно 80–200 MB)
    + Code Cache (JIT, по умолчанию до ~240 MB reserved)
    + Thread stacks (≈1 MB на поток × число потоков)
    + GC structures (G1: remembered sets, card table и т.п.)
    + Direct/NIO buffers (Netty, драйверы БД, HTTP-клиенты)
    + malloc/glibc arenas, JNI, прочее native
```

Типичный overhead сверх heap — от 150 до 300+ MB, в зависимости от фреймворка и числа потоков (это оценка, у вас может быть иначе). Сразу после старта heap почти пустой, и всё работает. Почему это случается раз в пару часов: G1 не спешит запускать full GC и отдавать память ОС, поэтому heap постепенно растёт до потолка `-Xmx`. Как только heap + non-heap превышает 512Mi, контейнер убивают.

### Что поменять

**1. Перестать жёстко задавать `-Xmx`, размер heap считать от лимита контейнера.** Java 21 читает cgroup v1/v2 и видит лимит:

```yaml
containers:
  - name: app
    image: registry.example.com/app:1.4.2   # pinned tag/digest, не latest
    env:
      - name: JAVA_TOOL_OPTIONS
        # 75% от лимита под heap, остальное под non-heap.
        # Для 768Mi это ~576 MB heap и ~190 MB запаса.
        value: >-
          -XX:MaxRAMPercentage=75.0
          -XX:InitialRAMPercentage=50.0
          -XX:+ExitOnOutOfMemoryError
          -XX:NativeMemoryTracking=summary
    resources:
      requests:
        memory: 768Mi      # request = limit -> предсказуемое планирование, меньше шанс eviction
        cpu: 500m
      limits:
        memory: 768Mi
```

Убедитесь, что `-Xmx512m` нигде не остался (Dockerfile `ENTRYPOINT`, `JAVA_OPTS`, скрипт запуска): при явном `-Xmx` флаг `MaxRAMPercentage` игнорируется.

**2. Выбрать: поднять лимит или уменьшить heap.**
- Если приложению действительно нужно ~500 MB heap, поднимите лимит до 768Mi–1Gi.
- Если лимит поднять нельзя, оставьте 512Mi и heap ~300–350 MB (`MaxRAMPercentage=65`), затем проверьте по GC-логам, что heap хватает.

Влияние на стоимость: +256Mi на реплику × число реплик. На плотно заполненных нодах поды могут перестать помещаться, и тогда понадобятся дополнительные ноды.

**3. Опционально ограничить отдельные области**, если NMT покажет, кто растёт:
`-XX:MaxMetaspaceSize=192m`, `-XX:ReservedCodeCacheSize=128m`, `-XX:MaxDirectMemorySize=128m`, `-Xss512k` (последний только если потоков очень много и глубокой рекурсии нет).

### Как проверить, куда уходит память

```bash
# Подтвердить причину рестартов
kubectl get pod <pod> -o jsonpath='{.status.containerStatuses[0].lastState}'

# Реальное потребление контейнера во времени
kubectl top pod <pod> --containers

# Разбивка памяти JVM (нужен -XX:NativeMemoryTracking=summary, overhead ~5–10%)
kubectl exec <pod> -- jcmd 1 VM.native_memory summary

# Какой heap реально выбрала JVM
kubectl exec <pod> -- java -XX:+PrintFlagsFinal -version | grep -E 'MaxHeapSize|MaxRAMPercentage'

# Число потоков
kubectl exec <pod> -- sh -c 'ls /proc/1/task | wc -l'
```

Если в NMT со временем без остановки растёт одна область (например, `Other`/`Internal` — это часто direct buffers, или `Thread` — утечка потоков), это уже утечка памяти, и одно увеличение лимита только отодвинет следующий OOMKilled. Тогда смотрите на последние изменения кода и зависимостей, которые совпали по времени с началом рестартов.

Если в образе только JRE без `jcmd` (distroless и т.п.), используйте `kubectl debug` с ephemeral-контейнером на базе JDK-образа той же версии.

### Деплой, blast radius, откат

- Применить: `kubectl apply -f` / Helm / ArgoCD. Rolling update пересоздаст поды по очереди. Проверьте, что настроен `PodDisruptionBudget`, а `maxUnavailable` не уронит сервис.
- Blast radius: только этот Deployment. Риск: если на нодах не хватит памяти под новый request, новые поды зависнут в `Pending`. Rolling update при этом остановится, а старые поды продолжат работать.
- Откат: `kubectl rollout undo deployment/<name>` или откат коммита в GitOps-репозитории.

Флаги JVM и формат вывода `jcmd` я привёл по памяти и не проверял на вашей версии. Сверьтесь с `java -XX:+PrintFlagsFinal` на вашем образе.


## Answer B
**Коротко:** `-Xmx512m` ограничивает только heap, а не весь процесс JVM. Кроме heap, JVM тратит память на metaspace, code cache, стеки потоков, структуры GC, direct/NIO-буферы и malloc-арены glibc. При лимите 512Mi вы отдали под heap весь лимит контейнера, и на остальное места не осталось. Когда heap постепенно растёт до 512 MiB (поэтому падение случается раз в пару часов, а не сразу), суммарный RSS превышает лимит cgroup. Тогда ядро убивает процесс через SIGKILL: 128 + 9 = 137, `OOMKilled`. Это не Java `OutOfMemoryError`, поэтому heap dump и стектрейса в логах нет.

Кстати, `512Mi` и `512m` в Java означают одно и то же (512 MiB), то есть heap буквально равен лимиту.

## Из чего складывается память JVM

Примерно, для типичного Spring Boot или подобного сервиса:

| Область | Порядок величины |
|---|---|
| Heap | `-Xmx` |
| Metaspace | 50–150 MiB (зависит от числа классов) |
| Code cache (JIT) | 20–50 MiB, до ~240 MiB по умолчанию |
| Стеки потоков | ~1 MiB × число потоков (200 потоков Tomcat ≈ до 200 MiB резерва, реально обычно меньше) |
| GC (G1: remembered sets и т.п.) | обычно ещё 5–10% от heap |
| Direct buffers (Netty, NIO) | по умолчанию до размера `-Xmx` |
| glibc malloc arenas | может набежать десятки MiB |

Эти цифры оценочные: реальные значения у вас могут сильно отличаться. Точно их покажет Native Memory Tracking (см. ниже). Как правило, non-heap занимает 150–300 MiB.

## Что поменять

**1. Не задавайте heap равным лимиту. Лучше уберите `-Xmx` и задавайте процент от лимита.** Java 21 видит лимиты cgroup v1/v2, поэтому:

```yaml
resources:
  requests:
    memory: "768Mi"
    cpu: "500m"
  limits:
    memory: "768Mi"   # для памяти request = limit: предсказуемое планирование, меньше шансов на eviction
env:
  - name: JAVA_TOOL_OPTIONS
    value: >-
      -XX:MaxRAMPercentage=70.0
      -XX:InitialRAMPercentage=50.0
      -XX:MaxMetaspaceSize=192m
      -XX:ReservedCodeCacheSize=96m
      -XX:MaxDirectMemorySize=64m
      -Xss512k
      -XX:+ExitOnOutOfMemoryError
      -XX:+HeapDumpOnOutOfMemoryError
      -XX:HeapDumpPath=/tmp
  - name: MALLOC_ARENA_MAX
    value: "2"        # ограничивает разрастание malloc-арен glibc; на Alpine/musl не нужен
```

- При 768Mi и 70% heap получится около 537 MiB, а на non-heap останется примерно 230 MiB. Если хотите оставить лимит 512Mi, heap выйдет около 360 MiB. Хватит ли этого, зависит от нагрузки, проверяйте по метрикам GC.
- Ограничения на metaspace, code cache и direct memory делают потребление предсказуемым. Если ограничение окажется слишком жёстким, вы получите внятный `OutOfMemoryError: Metaspace/Direct buffer memory` в логах вместо молчаливого 137. Значения выше — стартовые, подстройте их по NMT. `-Xss512k` уберите, если в приложении глубокая рекурсия.
- `-XX:+ExitOnOutOfMemoryError` нужен, чтобы при настоящем OOM в heap под перезапускался чисто, а не продолжал работать в полумёртвом состоянии.

**2. Измерьте, куда реально уходит память.** Временно добавьте `-XX:NativeMemoryTracking=summary` (даёт небольшой оверхед) и выполните:

```bash
kubectl exec <pod> -- jcmd 1 VM.native_memory summary
kubectl exec <pod> -- jcmd 1 GC.heap_info
kubectl top pod <pod> --containers
```

Если jcmd запущен не от того пользователя, под которым работает JVM, или PID не 1, сначала найдите процесс через `jcmd -l`.

Также смотрите на графике `container_memory_working_set_bytes`. Именно с этой метрикой kubelet и OOM killer сравнивают лимит.

**3. Если после правок память всё равно растёт до лимита**, значит, это не настройка, а утечка. Если в NMT растёт heap, снимите heap dump (`jcmd 1 GC.heap_dump /tmp/heap.hprof`) и откройте его в Eclipse MAT. Если растёт `Other`, `Internal` или `Thread`, ищите утечку native-памяти: direct buffers, JNI, бесконечное создание потоков.

## Выкатка, риск и откат

- Изменение затрагивает только этот Deployment. При rolling update новые поды поднимаются постепенно. Если на нодах не хватит памяти под новый request 768Mi, поды зависнут в `Pending`. Проверьте свободную память: `kubectl describe nodes | grep -A5 Allocated`.
- Как проверить результат: `kubectl get pod -w` показывает, перестал ли расти счётчик `RESTARTS`. Через несколько часов посмотрите `kubectl describe pod`: в `Last State` не должно появляться `OOMKilled`.
- Откат: `kubectl rollout undo deployment/<name>`. Если манифесты в Git (Helm или ArgoCD), откатите коммит.
