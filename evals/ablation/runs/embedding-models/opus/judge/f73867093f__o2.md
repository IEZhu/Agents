## Answer A
«В соединении отказано» (connection refused) означает, что TCP-пакет дошёл до 192.168.1.20:5432 и получил RST. Обычно этому две причины: на этом IP никто не слушает порт 5432, или firewall отвечает REJECT. До аутентификации дело не доходит. Если бы мешал `pg_hba.conf`, ошибка была бы другой: `no pg_hba.conf entry for host ...`. Поэтому начинать стоит с того, на каком адресе слушает PostgreSQL.

### 1. На каком адресе слушает сервер (самая частая причина)

На сервере:

```bash
# Какие адреса и порты слушает postgres
sudo ss -tlnp | grep 5432
```

- `127.0.0.1:5432` (и/или `[::1]:5432`): сервер слушает только loopback. Это значение `listen_addresses` по умолчанию, и именно поэтому через localhost всё работает.
- `0.0.0.0:5432` или `192.168.1.20:5432`: со слушателем всё в порядке, переходите к пункту 3.

Посмотрите текущее значение и файл, из которого оно взялось:

```sql
-- psql на сервере
SHOW listen_addresses;
SHOW port;
SELECT name, setting, sourcefile, sourceline
FROM pg_settings WHERE name IN ('listen_addresses', 'port');
```

Последний запрос нужен, потому что значение могли переопределить в `postgresql.auto.conf` (через `ALTER SYSTEM`) или в `conf.d/`, и тогда правка `postgresql.conf` ничего не даст.

### 2. Как исправить

```sql
-- Слушать loopback и LAN-интерфейс. Это безопаснее, чем '*'
ALTER SYSTEM SET listen_addresses = 'localhost,192.168.1.20';
```

Можно вместо этого прописать то же самое в `postgresql.conf`.

**Важно:** `listen_addresses` применяется только при **перезапуске**, `reload` не поможет:

```bash
sudo systemctl restart postgresql   # имя юнита зависит от дистрибутива, например postgresql@16-main
```

Перезапуск разорвёт все текущие соединения. На проде делайте его в окно обслуживания. Перед правкой сохраните копию конфигов (`cp postgresql.conf postgresql.conf.bak`), чтобы быстро откатиться.

Компромисс: `'*'` открывает порт на всех интерфейсах, включая те, что вы не планировали. Лучше указать конкретный IP и закрыть доступ firewall'ом.

### 3. Firewall на сервере

Если `ss` показывает правильный адрес, а ошибка остаётся, проверьте firewall:

```bash
sudo ufw status verbose                 # Ubuntu/Debian
sudo firewall-cmd --list-all            # RHEL/Fedora
sudo nft list ruleset | grep -n 5432    # или iptables -L -n | grep 5432
```

Если порт закрыт, откройте его только для нужной подсети:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 5432 proto tcp
```

### 4. Тот ли это хост

Проверьте, что `db.local` действительно указывает на эту машину, а не на старый адрес из `/etc/hosts` или mDNS:

```bash
# На сервере: есть ли такой IP на интерфейсах
ip -br addr | grep 192.168.1.20
# На клиенте: доступен ли порт, без участия psql
nc -vz 192.168.1.20 5432
```

Ещё один частый случай: PostgreSQL работает в Docker, а порт опубликован как `127.0.0.1:5432:5432`. Тогда снаружи будет тот же отказ, и `docker ps` покажет привязку.

### 5. Следующий шаг: pg_hba.conf

Когда порт откроется, может появиться ошибка `no pg_hba.conf entry`. В этом случае добавьте строку:

```
# TYPE  DATABASE  USER  ADDRESS          METHOD
host    all       app   192.168.1.0/24   scram-sha-256
```

Для `pg_hba.conf` перезапуск не нужен, хватит `SELECT pg_reload_conf();`.

### Проверка

```bash
# С клиента
psql "host=db.local port=5432 user=app dbname=postgres" -c "SELECT inet_server_addr(), inet_client_addr();"
```

Если в ответе `inet_server_addr()` = 192.168.1.20, соединение идёт по сети, а не через loopback.

Если после этих шагов отказ останется, пришлите вывод `ss -tlnp | grep 5432` и `SHOW listen_addresses;`, по ним будет понятно, в чём дело.


## Answer B
**Коротко:** «В соединении отказано» (connection refused) означает, что TCP-соединение отклонено ещё до PostgreSQL-аутентификации. Значит, `pg_hba.conf` тут пока ни при чём. Почти наверняка PostgreSQL слушает только `localhost`. Самый частый случай: в `listen_addresses` осталось значение по умолчанию `'localhost'`. Второй по частоте вариант: файрвол отвечает REJECT.

Если бы мешал `pg_hba.conf`, ошибка была бы другой: `no pg_hba.conf entry for host ...` или ошибка аутентификации. А если бы пакеты молча отбрасывались (DROP), вы бы увидели таймаут, а не отказ.

## 1. На каком адресе слушает PostgreSQL (на сервере)

```bash
sudo ss -tlnp | grep 5432
```

- `127.0.0.1:5432` (и/или `[::1]:5432`): слушает только loopback. Причина найдена, переходите к шагу 2.
- `0.0.0.0:5432` или `192.168.1.20:5432`: с этим всё в порядке, переходите к шагу 3.

Узнать текущее значение и файл конфигурации можно так:

```bash
sudo -u postgres psql -c "SHOW listen_addresses;" -c "SHOW config_file;" -c "SHOW port;"
```

## 2. Исправить listen_addresses

В `postgresql.conf`, или через `ALTER SYSTEM`, который пишет в `postgresql.auto.conf`. Значения из этого файла перекрывают `postgresql.conf`, поэтому загляните и в него:

```sql
-- Слушать loopback и конкретный LAN-интерфейс (безопаснее, чем '*')
ALTER SYSTEM SET listen_addresses = 'localhost,192.168.1.20';
```

Учтите: после изменения `listen_addresses` нужен **перезапуск**, `reload` его не применит:

```bash
sudo systemctl restart postgresql   # имя юнита зависит от дистрибутива/версии, например postgresql@16-main
```

Перезапуск обрывает все текущие соединения, поэтому на проде делайте его в окно обслуживания. Предварительно сохраните копию конфигов (`cp postgresql.conf postgresql.conf.bak`).

Компромисс: `'*'` проще, но тогда PostgreSQL слушает на всех интерфейсах, включая внешние, если они есть. Явный адрес безопаснее. Минус в том, что если IP сервера сменится, PostgreSQL не сможет привязаться к адресу.

## 3. Файрвол на сервере

```bash
sudo ufw status verbose                  # Ubuntu/Debian с ufw
sudo firewall-cmd --list-all             # RHEL/Fedora с firewalld
sudo nft list ruleset | grep -n 5432     # или iptables -L -n | grep 5432
```

Открывать порт стоит только для своей подсети, например:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 5432 proto tcp
# или
sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" port port="5432" protocol="tcp" accept' && sudo firewall-cmd --reload
```

## 4. Проверить, туда ли вы вообще подключаетесь

- `db.local` разрешился в `192.168.1.20`. Убедитесь, что это действительно IP сервера: выполните на нём `ip -br addr`. Имена `.local` часто резолвятся через mDNS или `/etc/hosts` и иногда указывают на устаревший адрес.
- Если PostgreSQL работает в **Docker**, проверьте, что порт опубликован: `docker ps` должен показывать `0.0.0.0:5432->5432/tcp`, а не только `127.0.0.1:5432->...`.
- Проверьте сетевую доступность с клиента:

```bash
nc -vz 192.168.1.20 5432     # refused / timeout / succeeded
```

## 5. Следующий шаг: pg_hba.conf

Когда TCP-соединение заработает, скорее всего появится уже другая ошибка: `no pg_hba.conf entry for host "192.168.1.x"`. Добавьте строку для своей подсети:

```
# TYPE  DATABASE  USER  ADDRESS          METHOD
host    all       app   192.168.1.0/24   scram-sha-256
```

Для применения хватит перезагрузки конфигурации, перезапуск не нужен: `SELECT pg_reload_conf();`. Метод `scram-sha-256` сработает, только если пароль пользователя `app` хранится в формате SCRAM. Для старых паролей в md5 укажите `md5` или задайте пароль заново.
