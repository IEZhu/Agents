## Latest user message
Случайно сделал git reset --hard HEAD~3 на своей локальной ветке feature/payments. Три последних коммита я не пушил. Их можно вернуть? Напиши по шагам.

## Rubric (what a strong answer does)
1. Says the commits are recoverable through git reflog and shows how to find the commit before the reset.
2. Restores them with exact commands: git reset --hard to that hash (or HEAD@{1} / ORIG_HEAD), or a new branch at that commit.
3. Warns that uncommitted changes discarded by reset --hard cannot be recovered through reflog.
4. The reply is in Russian, with code, commands and identifiers left as written, and contains no English restatement of the request.

## Answer A
Да, их почти наверняка можно вернуть. `git reset --hard` не удаляет коммиты, он только переносит указатель ветки. Сами коммиты остаются в репозитории, и на них по-прежнему ссылается reflog. По умолчанию недостижимые записи reflog хранятся 30 дней (`gc.reflogExpireUnreachable`; значение по памяти, не проверено). Восстанавливать лучше сразу и не запускать `git gc`.

### Шаг 1. Ничего лишнего не делайте

Пока не восстановили ветку, не запускайте `git gc` или `git prune` и не делайте новых reset. Новые коммиты сами по себе не помешают, но лучше не усложнять картину.

### Шаг 2. Найдите состояние до reset в reflog

```bash
git checkout feature/payments   # если вы не на ней
git reflog -n 10
```

Вы увидите примерно такое:

```
a1b2c3d HEAD@{0}: reset: moving to HEAD~3
9f8e7d6 HEAD@{1}: commit: <сообщение вашего последнего коммита>
...
```

Нужна строка сразу под `reset: moving to HEAD~3`. Обычно это `HEAD@{1}`, и её хеш указывает на последний из трёх потерянных коммитов. Можно смотреть и reflog самой ветки, там меньше шума от переключений между ветками:

```bash
git reflog show feature/payments
```

### Шаг 3. Убедитесь, что это нужный коммит

```bash
git log --oneline -5 9f8e7d6
```

В выводе должны быть все три ваших коммита сверху.

### Шаг 4. Верните ветку на этот коммит

```bash
git reset --hard 9f8e7d6        # или: git reset --hard HEAD@{1}
```

Если reset был последней операцией, которая двигала HEAD, подойдёт и короткий вариант:

```bash
git reset --hard ORIG_HEAD
```

`reset` записывает в `ORIG_HEAD` позицию HEAD до своего выполнения. Но `merge`, `rebase` и другой `reset` его перезаписывают, поэтому вариант с хешем из reflog надёжнее.

Есть и более осторожный путь: сначала сохранить коммиты в отдельную ветку, а потом уже трогать текущую:

```bash
git branch payments-rescue 9f8e7d6
```

### Шаг 5. Проверьте результат

```bash
git log --oneline -5
git status
```

Когда убедитесь, что всё на месте, запушьте ветку, чтобы такая ситуация больше не грозила потерей работы:

```bash
git push -u origin feature/payments
```

### Важная оговорка

Reflog возвращает только **закоммиченное**. Если на момент reset у вас были незакоммиченные изменения, `--hard` их стёр:

- изменения, которые были добавлены в индекс (`git add`), но не закоммичены, иногда можно найти среди висячих blob-объектов: `git fsck --lost-found` (файлы появятся в `.git/lost-found/other/`, без имён);
- изменения, которые не добавлялись в индекс, Git не сохранял, и вернуть их можно только из истории IDE (например, Local History в JetBrains) или из бэкапов.

**Уверенность: HIGH** для восстановления коммитов через reflog и `ORIG_HEAD`, это стандартный и проверенный механизм Git. Срок хранения 30 дней указан по памяти.


## Answer B
Да, почти наверняка можно. `git reset --hard` двигает только указатель ветки, а сами коммиты остаются в репозитории. Найти их помогает reflog: это локальный журнал перемещений `HEAD` и веток. Пока вы не запускали `git gc --prune=now` и не чистили reflog вручную, коммиты на месте. По умолчанию недостижимые записи reflog живут около 30 дней (`gc.reflogExpireUnreachable`; значение по памяти, если важно, проверьте в `git help config`).

## Шаги

**0. Ничего не делайте в ветке до восстановления.** Не запускайте `git gc` и не делайте новых reset. Новые коммиты, в принципе, не помешают, но так проще.

**1. Посмотрите reflog ветки:**

```bash
git reflog show feature/payments
```

или общий журнал `HEAD`:

```bash
git reflog
```

Вы увидите примерно такое:

```
a1b2c3d feature/payments@{0}: reset: moving to HEAD~3
9f8e7d6 feature/payments@{1}: commit: Add refund handling
...
```

Вам нужна запись **сразу под** строкой `reset: moving to HEAD~3`, то есть состояние до reset. Обычно это `feature/payments@{1}` (или `HEAD@{1}`, если после reset вы ничего не делали).

**2. Убедитесь, что это нужные коммиты:**

```bash
git log --oneline -5 feature/payments@{1}
```

В выводе должны быть три пропавших коммита сверху. Если сомневаетесь, посмотрите содержимое через `git show <hash>`.

**3. (Рекомендую) Сделайте страховочную ветку:**

```bash
git branch backup/payments-before-restore feature/payments@{1}
```

Теперь коммиты доступны по имени ветки, и reflog больше не нужен.

**4. Верните ветку на прежнее место.** Убедитесь, что вы на `feature/payments` (`git status`) и что у вас нет незакоммиченных изменений, которые жалко потерять: `reset --hard` их снова сотрёт. Затем:

```bash
git reset --hard feature/payments@{1}
```

или по хэшу из шага 1:

```bash
git reset --hard 9f8e7d6
```

Если есть незакоммиченная работа, сначала сделайте `git stash`, а после восстановления `git stash pop`.

**5. Проверьте результат:**

```bash
git log --oneline -5
git status
```

Если всё на месте, страховочную ветку можно удалить: `git branch -d backup/payments-before-restore`.

## Если в reflog ничего нет

Такое бывает редко, например если reflog отключён или очищен. Тогда ищите «висящие» коммиты:

```bash
git fsck --lost-found
```

Команда выведет `dangling commit <hash>`. Проверьте каждый через `git show <hash>` и восстановите нужный так же: `git branch recovered <hash>`.

## Важное ограничение

Восстанавливаются только **закоммиченные** изменения. Если на момент reset в рабочей директории были незакоммиченные правки, `reset --hard` их перезаписал, и Git их не хранит. Исключение: файлы, которые были добавлены через `git add`. Их содержимое может найтись среди `dangling blob` в выводе `git fsck --lost-found`, но уже без имён файлов.

Пушить ничего не нужно: ветка не публиковалась, поэтому force-push не понадобится.
