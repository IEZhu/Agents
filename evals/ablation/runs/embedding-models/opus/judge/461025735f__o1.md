## Latest user message
What's the actual difference between readiness and liveness probes in Kubernetes? We had a liveness probe hitting /health that checks the database, and during a DB outage all our pods restarted in a loop. Why, and how should we set it up?

## Rubric (what a strong answer does)
1. A failing readiness probe removes the pod from Service endpoints without a restart; a failing liveness probe makes the kubelet restart the container.
2. Explains that the database check in the liveness probe turned a dependency outage into restarts of every pod, and keeps liveness to the process itself.
3. Mentions a sensible setting such as a startup probe, initialDelaySeconds or failureThreshold.

## Answer A
**Short answer:** the two probes trigger different actions. A failed **liveness** probe makes the kubelet **kill and restart the container**. A failed **readiness** probe only **removes the pod from Service endpoints** so it stops getting traffic. Nothing restarts. Your liveness probe checked the database, so a database outage looked to Kubernetes like "every container is broken, restart them all." Restarting your app can't fix a database that is down, so the restarts just kept going.

## What each probe is for

| | Liveness | Readiness | Startup |
|---|---|---|---|
| Question it answers | "Is this process stuck beyond repair?" | "Should this pod get traffic right now?" | "Has the app finished starting?" |
| On failure | Container is killed and restarted (per `restartPolicy`) | Pod is removed from Service/EndpointSlice endpoints | Container is restarted. Liveness and readiness don't run until it passes. |
| Should check | Only state inside the process (deadlock, hung event loop, wedged worker pool) | Whether this instance can serve: init done, caches warm, not shutting down | Same as liveness, with a long enough window for slow boots |
| Should **not** check | Any external dependency (DB, cache, other services) | Shared dependencies, usually (see below) | — |

Use liveness only for problems that **a restart actually fixes**. If restarting the container wouldn't help, that check doesn't belong in liveness.

## Why your pods restart-looped

1. The DB goes down, so `/health` fails on **every pod at once**, since they all share the same dependency.
2. After `failureThreshold` consecutive failures (default 3 at a 10s period, from memory, so check the docs for your version), the kubelet kills each container.
3. The containers come back, `/health` still fails, and they get killed again. After repeated restarts you hit CrashLoopBackOff, where the kubelet waits longer and longer (up to roughly 5 minutes) between restarts.
4. When the DB recovers, several things make it worse:
   - Many pods are stuck in backoff, so recovery lags behind the DB by minutes.
   - The pods that are up all reconnect at once and run their startup work together. That thundering herd can knock a fragile DB over again.
   - Every restart throws away in-flight requests, warm caches and connection pools.

So a dependency outage that should have caused degraded responses became a full outage that lasted longer than the DB problem itself. This is a well-known cascading-failure pattern.

## A point that's easy to miss: readiness on a shared DB isn't free either

The common advice is to move the DB check into readiness. That's better than liveness because nothing restarts, but think it through. If the DB is down, **every** pod goes unready, the Service has zero endpoints, and clients get connection refused or a generic 502/503 from the ingress. That replaces your own error handling with an opaque one.

What I'd recommend in most cases:

- **Readiness should not fail on a dependency that all replicas share.** Removing a pod from rotation only helps if another pod could serve the request instead. During a DB outage, none can.
- Handle the outage in the app instead. Return fast, explicit errors (503 with `Retry-After`), serve from cache, use a circuit breaker and connection timeouts. Then report DB status through metrics and alerts, not probes.
- A dependency check in readiness makes sense when it's **specific to this pod**. Examples: this instance's connection pool is exhausted, or it hasn't loaded its config or warmed its cache yet.

Some teams still put a DB check in readiness so the load balancer fails fast. That's a reasonable choice if you accept zero endpoints during an outage. Just make it a deliberate choice.

## Recommended setup

Split the endpoints:

- `/livez`: returns 200 if the process can answer at all. It does no I/O. At most it checks an internal heartbeat, e.g. "the worker loop ticked in the last N seconds." It never touches the DB.
- `/readyz`: returns 200 when startup is complete and the pod isn't draining. It returns 503 once SIGTERM arrives, so the pod drains cleanly during rollouts.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      terminationGracePeriodSeconds: 30
      containers:
        - name: api
          image: registry.example.com/api:1.14.2   # pinned tag (ideally a digest), never :latest
          ports:
            - name: http
              containerPort: 8080

          # Covers slow boots (migrations check, cache warm-up) so liveness
          # can stay strict without killing pods that are still starting.
          # Allows up to 30 x 5s = 150s to start.
          startupProbe:
            httpGet: { path: /livez, port: http }
            periodSeconds: 5
            failureThreshold: 30

          # Process-local only. Restart only if the process is truly wedged:
          # 3 failures x 10s = ~30s unresponsive before a restart.
          livenessProbe:
            httpGet: { path: /livez, port: http }
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3

          # Traffic gating: startup done, not draining, pod-local health.
          # Fails fast so traffic moves away quickly.
          readinessProbe:
            httpGet: { path: /readyz, port: http }
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
            successThreshold: 1

          lifecycle:
            preStop:
              # Gives endpoint removal time to reach kube-proxy/ingress
              # before the app gets SIGTERM. Requires a `sleep` binary in
              # the image; on K8s >= 1.30 you can use the native
              # `preStop.sleep` action instead (recalled, verify for your version).
              exec:
                command: ["sleep", "5"]
```

Other things to get right:

- **Timeouts:** the liveness handler must not block on anything slow. A health endpoint that waits on a DB connection pool can time out under load, and then liveness kills pods that are healthy but busy. This is another common source of restart loops.
- **Make the app survive a missing DB:** connect lazily or retry with backoff and jitter. Don't exit on startup if the DB is unreachable. Otherwise you get the same restart loop from crashes instead of probes.
- **Pod Disruption Budget and replica count** don't help here, because probe-driven restarts aren't evictions. The probe design is the actual fix.

## Rolling it out

- **Blast radius:** this changes the pod template, so it triggers a rolling update of the Deployment. If `/livez` or `/readyz` is wrong (for example, the path returns 404), new pods never become ready. The rollout then stalls, and old pods keep serving as long as `maxUnavailable` isn't 100%. Ship the new endpoints in the app **before** or **together with** the probe change.
- **Verify:**
  ```bash
  kubectl rollout status deploy/api
  kubectl describe pod -l app=api | grep -iE 'liveness|readiness|startup|Unhealthy'
  kubectl get endpointslices -l kubernetes.io/service-name=api -o wide
  kubectl get pods -l app=api -w   # RESTARTS should stay flat
  ```
  Best test: in staging, block the DB with a NetworkPolicy or scale it down. Pods should keep `RESTARTS` at 0 and return your app's 503s instead of crash-looping.
- **Rollback:** `kubectl rollout undo deploy/api` (or revert the manifest commit if you use GitOps/Helm, e.g. `helm rollback api <rev>`). Rolling back brings back the old DB-checking liveness probe, so that's only a short-term fallback.


## Answer B
**Short version:** a failing liveness probe tells the kubelet to *kill and restart the container*. A failing readiness probe tells Kubernetes to *stop sending traffic to the pod*, and nothing gets restarted. Your liveness probe checked the database, which every pod shares. When the DB went down, every pod failed liveness at once, and the kubelet "fixed" that by restarting all of them, over and over. A restart can't fix a database outage, so you got a restart loop.

## What each probe actually does

| Probe | Question it answers | What happens on failure |
|---|---|---|
| **Liveness** | "Is this process broken in a way only a restart will fix?" (deadlocked, wedged event loop, corrupted in-memory state) | kubelet kills the container and restarts it under the pod's `restartPolicy`. Repeated failures end in `CrashLoopBackOff`. |
| **Readiness** | "Can this pod serve requests *right now*?" | The pod is taken out of the Service's endpoints, so no new traffic reaches it. The container keeps running. Once the probe passes again, the pod is added back. Runs for the whole life of the pod, not just at startup. |
| **Startup** | "Has the app finished booting?" | Liveness and readiness are held off until it passes. If it never passes within its budget, the container is restarted. Use it for slow-starting apps so you don't need a huge `initialDelaySeconds` on liveness. |

## Why your setup blew up

1. **The DB went down, so `/health` failed on every pod at the same moment.** The dependency was shared, so the failure was correlated across the whole Deployment.
2. **The kubelet restarted every container.** That did nothing for the DB, so the probes failed again after the restart, and the containers went into `CrashLoopBackOff` with growing backoff delays.
3. **The outage got longer and worse:**
   - Pods that could have served cached or DB-free endpoints, or returned clean 503s, were busy restarting.
   - After the DB recovered, many pods were still sitting in backoff and came back slowly.
   - Every restart opens a fresh connection pool and runs warm-up queries. That's a thundering herd hitting a DB that has only just recovered, and it can knock it over again.
4. **Probe timeouts add a second way to fail.** A DB check that *hangs* instead of erroring goes past the probe's `timeoutSeconds`. As I recall, the default is 1 second (not verified, so check the docs for your version). That means even a *slow* DB, not just a dead one, can trigger restarts.

Rule of thumb: **never put an external dependency in a liveness probe.** Liveness should only check things inside the process that a restart would actually fix.

## How to set it up

**Liveness → `/livez`**: cheap and local. Return 200 if the process can answer an HTTP request at all, meaning the server loop is responsive and threads aren't deadlocked. No DB, no cache, no downstream calls. If you have a known internal failure mode, such as a worker thread that can wedge, check that here.

**Readiness → `/readyz`**: "can I take traffic?" Return 503 while starting up, warming caches, or draining on shutdown. Whether to include the DB here is a real trade-off:
- **Include it** if the pod truly can't do anything useful without the DB, *and* you have more than one DB or shard, so only some pods would fail. Then traffic shifts to the healthy pods.
- **Leave it out** (usually my recommendation for one shared DB). If the shared DB is down, every pod goes unready, the Service has zero endpoints, and clients get a generic ingress/LB error. They lose your app's controlled response, any DB-free endpoints, and your error logging. It's usually better to handle DB failure inside the app: short query timeouts, a circuit breaker, a fast 503 with a meaningful body, and alerting on DB health through monitoring rather than through probes.

**Startup → reuse `/livez` or `/readyz`** with a generous budget so slow boots don't count against liveness.

```yaml
# Container spec excerpt. Probe field names are standard core/v1;
# timing values are starting points — tune to your app's real startup/latency.
containers:
  - name: api
    image: registry.example.com/api:1.4.2   # pinned tag (or digest)
    ports:
      - containerPort: 8080
    startupProbe:
      httpGet:
        path: /livez
        port: 8080
      periodSeconds: 5
      failureThreshold: 30        # up to ~150s to boot before liveness takes over
    livenessProbe:
      httpGet:
        path: /livez              # process-local only: NO database check
        port: 8080
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3         # ~30s of consecutive failures before restart
    readinessProbe:
      httpGet:
        path: /readyz             # startup/warm-up/draining state; DB only if justified (see above)
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2
      successThreshold: 1
```

A few related points:
- **Graceful shutdown:** when you receive SIGTERM, start failing `/readyz` and keep serving in-flight requests until `terminationGracePeriodSeconds` runs out. Many teams add a short `preStop` sleep so endpoint removal has time to propagate before the process stops accepting connections.
- **Keep probe handlers cheap.** They run every few seconds on every pod. A probe that runs a real query is effectively a constant load test against your DB.
- **Monitor the DB separately.** Use your monitoring stack, for example Prometheus with a DB exporter plus an alert. Probes control routing and restarts. They aren't how you find out the database is down.

## Rolling this out safely

- **Blast radius:** probe changes cause a rolling restart of the Deployment. If the new `/livez` or `/readyz` endpoints are wrong (bad path, wrong port), new pods either never become ready, which stalls the rollout while old pods keep serving if `maxUnavailable` allows it, or they crash-loop.
- **Order:** deploy the app version that adds `/livez` and `/readyz` first, then switch the probes to them. Watch with `kubectl rollout status deploy/<name>` and `kubectl get pods -w`. `kubectl describe pod <pod>` shows probe failures under Events.
- **Test it:** in staging, block DB access (a NetworkPolicy, or scaling the DB to zero) and confirm pods *don't* restart. `RESTARTS` in `kubectl get pods` should stay flat, and the app should return its own 503s.
- **Rollback:** `kubectl rollout undo deploy/<name>`, or revert the manifest in Git if you deploy through GitOps.
