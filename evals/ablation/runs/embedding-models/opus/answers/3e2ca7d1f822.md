### Analysis

The spec asks for one pure function: check the format (only ASCII digits, length 10 or 12), then check the control digits with the FNS weighted-checksum algorithm. One trap matters here. Python's `str.isdigit()` also accepts non-ASCII digits such as full-width `７` or Arabic-Indic `٣`, and `int()` parses them without complaint. A naive version would accept them, even though the spec says any non-digit character must give `False`. I use `re.fullmatch` with an explicit `[0-9]` class, which also rejects a trailing `\n`. A regex using `$` would let that newline through.

### Implementation

`inn_validator.py`

```python
"""Validation of Russian taxpayer identification numbers (INN)."""

import re

LEGAL_ENTITY_LENGTH = 10
INDIVIDUAL_LENGTH = 12

# Control-digit weights defined by the FNS algorithm.
_WEIGHTS_10 = (2, 4, 10, 3, 5, 9, 4, 6, 8)
_WEIGHTS_12_FIRST = (7, 2, 4, 10, 3, 5, 9, 4, 6, 8)
_WEIGHTS_12_SECOND = (3, 7, 2, 4, 10, 3, 5, 9, 4, 6, 8)

# Explicit ASCII class: str.isdigit()/\d would also accept Unicode digits.
_ASCII_DIGITS = re.compile(r"[0-9]+")


def _control_digit(digits: list[int], weights: tuple[int, ...]) -> int:
    weighted_sum = sum(d * w for d, w in zip(digits, weights))
    return weighted_sum % 11 % 10


def validate_inn(inn: str) -> bool:
    """Return True if `inn` is a valid 10-digit (legal entity) or 12-digit (individual) INN."""
    if not isinstance(inn, str) or not _ASCII_DIGITS.fullmatch(inn):
        return False

    digits = [int(ch) for ch in inn]

    if len(digits) == LEGAL_ENTITY_LENGTH:
        return digits[9] == _control_digit(digits, _WEIGHTS_10)

    if len(digits) == INDIVIDUAL_LENGTH:
        return (
            digits[10] == _control_digit(digits, _WEIGHTS_12_FIRST)
            and digits[11] == _control_digit(digits, _WEIGHTS_12_SECOND)
        )

    return False
```

`test_inn_validator.py` (pytest)

```python
import pytest

from inn_validator import validate_inn


@pytest.mark.parametrize("inn", [
    "7707083893",    # valid legal-entity INN
    "500100732259",  # valid individual INN
])
def test_valid_inn(inn):
    assert validate_inn(inn) is True


@pytest.mark.parametrize("inn", [
    "7707083894",    # 10 digits, wrong control digit
    "500100732249",  # 12 digits, wrong 11th digit
    "500100732258",  # 12 digits, wrong 12th digit
])
def test_wrong_control_digits(inn):
    assert validate_inn(inn) is False


@pytest.mark.parametrize("inn", [
    "",
    "123456789",       # 9
    "77070838931",     # 11
    "5001007322590",   # 13
])
def test_wrong_length(inn):
    assert validate_inn(inn) is False


@pytest.mark.parametrize("inn", [
    " 7707083893",
    "7707083893 ",
    "7707083893\n",
    "7707 083893",
    "          ",
    "77070838a3",
    "-707083893",
    "７７０７０８３８９３",  # full-width digits: isdigit() is True, must still be rejected
])
def test_non_digit_input(inn):
    assert validate_inn(inn) is False


def test_non_string_input():
    assert validate_inn(7707083893) is False  # type: ignore[arg-type]
```

### Verification

- I could not run the tests in this context. Please run `pytest test_inn_validator.py` before merging.
- I checked the checksums of the test fixtures by hand:
  - `7707083893`: the weighted sum is 267, and 267 mod 11 = 3, which matches the 10th digit.
  - `500100732259`: the first sum is 148 → 148 mod 11 = 5, which matches the 11th digit. The second sum is 141 → 141 mod 11 = 9, which matches the 12th digit.
- The weights and the `% 11 % 10` rule are the published FNS algorithm as I remember it. I did not check them against an official source here. The hand-checked real INNs above passing is strong supporting evidence, though.
- Complexity: O(n) time and O(n) extra space, with n ≤ 12.

**Points for the spec authors to confirm:**
1. **All-zero numbers.** `0000000000` and `000000000000` pass the checksum, because the sum is 0 and so is the control digit. The spec doesn't exclude them. If you want them rejected, that needs an extra rule, for example a check on the region code in the first two digits.
2. **Non-string input.** I return `False` rather than raising `TypeError`, so the function always returns a `bool` as the spec says. If your codebase prefers to fail fast on type errors, change that one line.
3. **No normalisation.** Following the spec, input such as `" 7707083893 "` is rejected, not stripped. If callers pass user-entered values, they should strip them before calling.
