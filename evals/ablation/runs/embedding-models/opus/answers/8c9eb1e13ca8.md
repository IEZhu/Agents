```sql
SELECT id, customer_id, created_at, amount
FROM (
    SELECT o.*,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY amount DESC NULLS LAST,  -- по сумме по убыванию; NULL-суммы в конец
                        created_at ASC,          -- при равной сумме — более ранний первым
                        id ASC                   -- финальный tie-breaker для детерминизма
           ) AS rn
    FROM orders o
) t
WHERE rn = 2;
```

## Почему это корректно

- **`ROW_NUMBER()`, а не `RANK()`/`DENSE_RANK()`.** `ROW_NUMBER` даёт строкам внутри клиента сквозную нумерацию 1, 2, 3… без пропусков и повторов, поэтому `rn = 2` всегда ровно одна строка, то есть второй заказ в заданном порядке. С `RANK` при двух заказах с одинаковыми (amount, created_at) обе строки получили бы 1, а строки с номером 2 не было бы совсем. С `DENSE_RANK` под `= 2` могли бы попасть сразу несколько строк.
- **`PARTITION BY customer_id`.** Нумерация начинается заново для каждого клиента.
- **Клиенты с одним заказом выпадают сами.** У них есть только `rn = 1`, и фильтр `rn = 2` их отсекает. Отдельный `HAVING count(*) > 1` не нужен.
- **`id` в конце `ORDER BY`.** Если у клиента совпадают и `amount`, и `created_at`, порядок без него не определён, и результат мог бы меняться от запуска к запуску. Условие задачи на такой случай ничего не говорит, `id` просто фиксирует выбор.
- **`NULLS LAST`.** В PostgreSQL при `DESC` значения NULL по умолчанию идут **первыми**. Без `NULLS LAST` заказ с `amount IS NULL` считался бы «самым дорогим». Если колонка объявлена `NOT NULL`, эта часть ни на что не влияет. Если же NULL должен считаться «первым», уберите `NULLS LAST`.

## Производительность (по желанию)

На большой таблице окно потребует сортировки по всему `orders`. Её можно убрать индексом, порядок которого совпадает с окном:

```sql
-- CONCURRENTLY — чтобы не блокировать запись в orders на время построения
CREATE INDEX CONCURRENTLY orders_cust_amount_idx
    ON orders (customer_id, amount DESC NULLS LAST, created_at, id);
```

Плюс: возможен план без узла Sort (проверьте через `EXPLAIN (ANALYZE, BUFFERS)`, работает ли так на ваших данных). Минус: индекс замедляет каждую вставку и обновление и занимает место. Нужен он, только если запрос частый, а Sort в плане действительно дорогой.
