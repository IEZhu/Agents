### Analysis

Ошибка «Connection refused» (В соединении отказано) при работающем `localhost` однозначно указывает на то, что сетевой пакет доходит до сервера, но сервер отклоняет его на уровне TCP. 

Поскольку локально всё работает, проблема заключается в одном из трёх уровней:
1. **Слушатель (Listening):** PostgreSQL по умолчанию слушает только интерфейс `localhost` (127.0.0.1) и игнорирует запросы на внешние IP-адреса.
2. **Межсетевой экран (Firewall):** Порт 5432 закрыт на уровне ОС сервера.
3. **Авторизация (pg_hba.conf):** Даже если TCP-соединение будет установлено, PostgreSQL сбросит его, если в конфиге доступа не прописан разрешенный IP клиента (хотя обычно это вызывает ошибку `no pg_hba.conf entry`, а не `Connection refused`).

---

### Solution

#### Шаг 1: Настройка прослушивания интерфейсов
Проверьте файл `postgresql.conf` (путь зависит от версии и ОС, обычно `/etc/postgresql/XX/main/postgresql.conf` или в директории данных).

Найдите параметр `listen_addresses`. Скорее всего, там сейчас:
```conf
listen_addresses = 'localhost'
```
**Измените на:**
```conf
# Слушать все доступные сетевые интерфейсы
listen_addresses = '*' 
```
*Примечание: Если сервер имеет несколько IP и вы хотите ограничить доступ, укажите конкретный IP через запятую.*

#### Шаг 2: Настройка прав доступа (pg_hba.conf)
Теперь нужно разрешить пользователю `app` подключаться с вашего IP. Откройте `pg_hba.conf`.

Добавьте строку в конец файла:
```conf
# TYPE  DATABASE        USER            ADDRESS                 METHOD
host    all             app             192.168.1.0/24          scram-sha-256
```
*Замените `192.168.1.0/24` на конкретный IP вашего клиента или подсеть. Метод `scram-sha-256` актуален для новых версий, для старых используйте `md5`.*

#### Шаг 3: Открытие порта в Firewall
Если на сервере включен firewall, разрешите входящий трафик на порт 5432.

**Для Ubuntu (ufw):**
```bash
sudo ufw allow 5432/tcp
```
**Для CentOS/RHEL (firewalld):**
```bash
sudo firewall-cmd --permanent --add-port=5432/tcp
sudo firewall-cmd --reload
```

#### Шаг 4: Перезапуск сервиса
Изменения в `listen_addresses` требуют полного перезапуска.

```bash
sudo systemctl restart postgresql
```

---

### Performance Impact
Данные изменения не влияют на производительность запросов. Однако открытие порта `*` увеличивает поверхность атаки. **Рекомендуется** ограничить доступ на уровне Firewall или `pg_hba.conf` только доверенными IP.

---

### Migration Plan
1. **Backup**: Сделайте копию конфигов перед правкой: `cp postgresql.conf postgresql.conf.bak`.
2. **Apply**: Внесите правки в `postgresql.conf` $\rightarrow$ `pg_hba.conf` $\rightarrow$ Firewall.
3. **Restart**: Перезапустите службу.
4. **Rollback**: В случае проблем верните `.bak` файлы и перезапустите сервис.

### Verification

**1. На сервере:** Проверьте, что Postgres теперь слушает все интерфейсы (0.0.0.0), а не только 127.0.0.1.
```bash
ss -nlt | grep 5432
# Ожидаемый результат: LISTEN 0.0.0.0:5432 или [::]:5432
```

**2. С клиента:** Проверьте доступность порта с помощью `nc` (netcat) или `telnet` перед запуском `psql`.
```bash
nc -zv db.local 5432
# Ожидаемый результат: Connection to db.local 5432 port [tcp/postgresql] succeeded!
```

**3. Финальный тест:**
```bash
psql -h db.local -p 5432 -U app
```
