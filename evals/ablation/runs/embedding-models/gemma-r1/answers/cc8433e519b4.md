### Анализ
Ошибка «Connection refused» (В соединении отказано) при условии, что локально всё работает, однозначно указывает на то, что запрос доходит до сервера, но сервер (или ОС) отклоняет его на уровне сетевого стека. 

В PostgreSQL это классическая проблема, которая обычно сводится к одной из двух причин:
1. **PostgreSQL слушает только localhost**: по умолчанию сервер настроен принимать соединения только с интерфейса `127.0.0.1`.
2. **Блокировка брандмауэром (Firewall)**: порт 5432 закрыт для внешних входящих соединений.

---

### Решение

#### Шаг 1: Настройка прослушивания интерфейсов (`postgresql.conf`)
Проверьте, на каких адресах сервер ожидает соединений.

1. Найдите файл `postgresql.conf` (обычно в `/etc/postgresql/X.X/main/` или в директории данных `PGDATA`).
2. Найдите параметр `listen_addresses`. Скорее всего, там написано `listen_addresses = 'localhost'`.
3. Измените его на:
   ```ini
   # Слушать все доступные сетевые интерфейсы
   listen_addresses = '*' 
   ```
   *Или укажите конкретный IP сервера: `listen_addresses = '192.168.1.20'`.*

**Важно:** После изменения этого параметра требуется **перезапуск** сервиса:
```bash
sudo systemctl restart postgresql
```

#### Шаг 2: Настройка прав доступа (`pg_hba.conf`)
Даже если сервер начнет «слушать» сеть, он отклонит попытку входа, если в файле `pg_hba.conf` нет разрешающей записи для вашего IP или сети.

1. Откройте `pg_hba.conf` (лежит в той же папке, что и `postgresql.conf`).
2. Добавьте строку в конец файла, чтобы разрешить пользователю `app` подключаться из вашей сети:
   ```conf
   # TYPE  DATABASE        USER            ADDRESS                 METHOD
   host    all             app             192.168.1.0/24          scram-sha-256
   ```
   *Замените `192.168.1.0/24` на ваш конкретный IP, если хотите ограничить доступ.*

**Важно:** Для применения изменений `pg_hba.conf` достаточно **перезагрузки** (reload), перезапуск всего сервиса не обязателен:
```bash
sudo systemctl reload postgresql
```

#### Шаг 3: Проверка брандмауэра (Firewall)
Если первые два шага не помогли, проверьте, открыт ли порт 5432 в ОС сервера.

**Для Ubuntu (ufw):**
```bash
sudo ufw allow 5432/tcp
```

**Для CentOS/RHEL (firewalld):**
```bash
sudo firewall-cmd --permanent --add-port=5432/tcp
sudo firewall-cmd --reload
```

### Верификация

Чтобы понять, на каком этапе происходит сбой, используйте следующие инструменты:

**1. На сервере: Проверка, слушает ли Postgres порт на внешнем IP**
Выполните команду:
```bash
ss -tlnp | grep 5432
```
*   **Плохо:** `127.0.0.1:5432` (слушает только локально).
*   **Хорошо:** `0.0.0.0:5432` или `*:5432` (слушает всех).

**2. С клиента: Проверка доступности порта (без psql)**
Попробуйте «простучать» порт с помощью `nc` (netcat) или `telnet`:
```bash
nc -zv db.local 5432
# или
telnet db.local 5432
```
*   Если пишет `Connection refused` $\rightarrow$ проблема в `listen_addresses` или Firewall.
*   Если соединение установлено $\rightarrow$ проблема в `pg_hba.conf` (вы получите ошибку авторизации в `psql`, а не отказ в соединении).

### Резюме по безопасности
*   **Никогда** не ставьте `trust` в `pg_hba.conf` для внешних сетей. Используйте `scram-sha-256` или `md5`.
*   Если сервер доступен из интернета, ограничьте `listen_addresses` конкретным внутренним IP и закройте порт 5432 внешним Firewall, оставив доступ только для доверенных IP.
