### Architecture

The issue you experienced is a classic Kubernetes anti-pattern: **coupling the Liveness probe to an external dependency.**

Here is the fundamental difference:

*   **Liveness Probe (`livenessProbe`):** Answers *"Is the process deadlocked or crashed?"* If this fails, Kubernetes **kills the container and restarts it**. It is intended to recover from internal states (like a deadlock) that a restart can fix.
*   **Readiness Probe (`readinessProbe`):** Answers *"Is the application ready to handle requests?"* If this fails, Kubernetes **removes the Pod from the Service endpoints**. The Pod stays alive, but no traffic is routed to it. It is intended to handle temporary unavailability (like a DB outage or loading a large cache).

**Why your pods restarted in a loop:**
When your database went down, the Liveness probe failed. Kubernetes assumed the *application process* was broken and restarted it. Since the DB was still down, the new pod also failed its Liveness probe and was restarted. This created a "restart storm" that added unnecessary load to your cluster and provided zero benefit, as restarting the app cannot fix a remote database.

---

### Implementation

You should split your health checks. The Liveness probe should be "shallow" (checking only the process), and the Readiness probe should be "deep" (checking dependencies).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: app-container
        image: my-app:1.2.3 # Pin your versions
        ports:
        - containerPort: 8080
        
        # LIVENESS: Shallow check. 
        # Only fails if the web server itself is unresponsive.
        livenessProbe:
          httpGet:
            path: /healthz # A dedicated endpoint that returns 200 OK immediately
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
          timeoutSeconds: 2
          failureThreshold: 3

        # READINESS: Deep check. 
        # Fails if the DB is down, removing the pod from the LoadBalancer.
        readinessProbe:
          httpGet:
            path: /readyz # An endpoint that pings the DB/Cache
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
          timeoutSeconds: 5
          failureThreshold: 3
```

#### Recommended Endpoint Logic:
1.  **`/healthz` (Liveness):** Simply return `HTTP 200`. If this fails, the process is likely frozen or the event loop is blocked.
2.  **`/readyz` (Readiness):** Perform a `SELECT 1` on the database. If the DB is down, return `HTTP 503`.

---

### Deployment

Apply the updated manifest to your cluster:

```bash
kubectl apply -f deployment.yaml
```

**Blast Radius:** This change triggers a rolling update. Pods will be replaced one by one. If the DB is currently down, the new pods will start but will not receive traffic until the DB recovers.

---

### Verification

To verify the behavior during a simulated outage:

1.  **Check current status:**
    `kubectl get pods`
2.  **Simulate DB Outage:** (e.g., change DB password or block port via NetworkPolicy).
3.  **Observe Readiness:**
    `kubectl get pods` $\rightarrow$ You should see `READY 0/1`. The pods remain `Running`, but are not `Ready`.
4.  **Observe Liveness:**
    `kubectl describe pod <pod-name>` $\rightarrow$ Check the "Events" section. You should **not** see "Liveness probe failed: ..." or "Container restarted".
5.  **Restore DB:**
    The pods should automatically transition back to `READY 1/1` within 10 seconds.

---

### Rollback

If the new probe configuration causes unexpected behavior (e.g., pods never becoming ready due to a misconfigured `/readyz` path):

```bash
kubectl rollout undo deployment/my-app
```
