## Latest user message
Под с сервисом на Java 21 в Kubernetes каждые пару часов перезапускается, в kubectl describe pod вижу Last State: Terminated, Reason: OOMKilled, Exit Code: 137. В контейнере limits.memory: 512Mi, приложение запускается с -Xmx512m. Почему так и что поменять?

## Rubric (what a strong answer does)
1. Explains that -Xmx caps only the heap while the JVM also uses non-heap memory (metaspace, thread stacks, code cache, direct buffers), so a 512m heap lets the process exceed the 512Mi limit and the container is OOM-killed (exit code 137).
2. Recommends a concrete fix: a heap well below the limit (for example replacing -Xmx with -XX:MaxRAMPercentage, or a smaller -Xmx) and/or a higher limits.memory, and suggests measuring actual memory use.
3. Does not mistake the symptom for a Java OutOfMemoryError: it is a container OOM kill.
4. The reply is in Russian, with code, commands and identifiers left as written, and contains no English restatement of the request.

## Answer A
### Architecture

Проблема заключается в фундаментальном непонимании того, как JVM потребляет память внутри контейнера. 

**Ошибка:** Вы установили лимит контейнера (`limits.memory`) равным максимальному размеру кучи (`-Xmx`). 

**Почему это приводит к OOMKilled:**
Память Java-процесса состоит не только из Heap (кучи). Общий объем потребления памяти (RSS — Resident Set Size) выглядит так:
`Total Memory = Heap + Non-Heap (Metaspace, Code Cache, Stack) + Native Memory + Overhead ОС`

Когда вы ставите `-Xmx512m` и `limits.memory: 512Mi`, вы оставляете **0 байт** на всё остальное. Как только JVM потребуется выделить память под Metaspace (загрузка классов) или создать новый поток (Stack), общее потребление превысит 512Mi, и Linux Kernel (OOM Killer) мгновенно убьет процесс с кодом 137.

---

### Implementation

Есть два пути решения: «быстрый» (ручной расчет) и «правильный» (динамический).

#### Вариант 1: Правильный (Container-aware)
В Java 21 лучше не использовать жестко заданный `-Xmx`, а использовать процент от доступной памяти контейнера. Это позволяет менять лимиты в Kubernetes без правки аргументов запуска.

**Изменения в Deployment YAML:**
1. Удалите `-Xmx512m`.
2. Добавьте флаг `-XX:MaxRAMPercentage=75.0`. Это скажет JVM: «используй до 75% от лимита контейнера под Heap, остальное оставь под Non-Heap».

```yaml
spec:
  containers:
  - name: java-service
    image: my-app:1.0.0
    resources:
      limits:
        memory: "768Mi" # Увеличиваем лимит, чтобы при 75% Heap было ~576Mi
      requests:
        memory: "512Mi"
    env:
    - name: JAVA_OPTS
      value: "-XX:MaxRAMPercentage=75.0 -XX:+UseG1GC"
```

#### Вариант 2: Быстрый (Ручной расчет)
Если вы хотите оставить `-Xmx512m`, вам нужно увеличить лимит контейнера, чтобы создать «запас» (headroom) для Non-Heap памяти (обычно 256–512Mi в зависимости от приложения).

```yaml
resources:
  limits:
    memory: "768Mi" # 512Mi (Heap) + 256Mi (Non-Heap/OS)
  requests:
    memory: "512Mi"
```

Примените изменения через `kubectl` или ваш CI/CD пайплайн:

```bash
kubectl apply -f deployment.yaml
```

**Blast Radius:** Перезапуск всех подов сервиса (Rolling Update). Влияние минимально, если настроены `readinessProbe` и `livenessProbe`.

   Следите за реальным потреблением памяти в реальном времени:
   ```bash

   ```

2. **Анализ логов JVM (если есть доступ):**

Если приложение стало потреблять слишком много памяти и начало тормозить из-за GC (Garbage Collector), верните предыдущие значения:

```bash

```

| Параметр | Было | Стало (Рекомендуемо) | Причина |

## Answer B
### Architecture

Проблема заключается в фундаментальном непонимании того, как JVM потребляет память внутри контейнера. 

**Ошибка:** Вы установили лимит памяти контейнера (`limits.memory`) равным максимальному размеру Heap (`-Xmx`).

**Почему это приводит к OOMKilled:**
Память Java-процесса состоит не только из Heap (кучи). Общий объем потребления памяти (RSS — Resident Set Size) выглядит так:
`Total Memory = Heap + Non-Heap (Metaspace, Code Cache, Stack) + Direct Buffers + JVM Overhead + Native Memory`

Когда ваша JVM доходит до использования `-Xmx512m`, она считает, что всё еще в рамках лимита. Однако Non-Heap области (например, Metaspace для хранения классов или стеки потоков) добавляют еще 100–200 МБ сверху. В итоге процесс пытается занять, например, 650 МБ, что превышает `limits.memory: 512Mi`. Linux Kernel видит превышение лимита cgroup и мгновенно убивает процесс (`SIGKILL`), что в Kubernetes отображается как `OOMKilled` (Exit Code 137).

---

### Implementation

Есть два пути решения: «быстрый» (жесткие лимиты) и «правильный» (динамические проценты).

#### Вариант 1: Правильный (Container-aware)
Начиная с Java 10+, JVM умеет считывать лимиты контейнера. Вместо жесткого `-Xmx` используйте параметр `MaxRAMPercentage`. Это позволит вам менять лимиты в Kubernetes без правки аргументов запуска Java.

**Рекомендуемые настройки:**
- `MaxRAMPercentage=75.0` (оставляет 25% памяти под Non-Heap и ОС).

**Обновленный Deployment YAML:**
```yaml
spec:
  containers:
  - name: java-app
    image: my-app:1.0.0 # Pin version
    resources:
      requests:
        memory: "512Mi"
        cpu: "500m"
      limits:
        memory: "512Mi" # Оставляем лимит, но меняем логику JVM
    env:
    - name: JAVA_TOOL_OPTIONS
      value: "-XX:MaxRAMPercentage=75.0 -XX:+UseContainerSupport"
```
*В этом случае Heap будет автоматически рассчитан как $512 \text{Mi} \times 0.75 \approx 384 \text{Mi}$.*

#### Вариант 2: Быстрый (Hardcoded)
Если вы хотите оставить `-Xmx`, он должен быть существенно меньше, чем `limits.memory`.

**Правило большого пальца:** Heap $\approx 70\text{--}80\%$ от лимита контейнера.
- Если `limits.memory: 512Mi`, то `-Xmx` должен быть $\approx 384\text{m}$.

```yaml
# В аргументах запуска:
-Xmx384m
```

### Deployment

1. **Примените изменения** в манифесте Deployment:
   ```bash
   kubectl apply -f deployment.yaml
   ```
2. **Перезапустите поды** (если не произошло автоматического обновления):
   ```bash
   kubectl rollout restart deployment <deployment-name>
   ```

### Verification

Чтобы убедиться, что проблема решена, мониторьте потребление памяти в реальном времени:

1. **Проверка текущего потребления:**
   ```bash
   kubectl top pod <pod-name>
   ```
   *Значение должно стабилизироваться ниже 512Mi.*

2. **Анализ логов событий:**
   ```bash
   kubectl get events --sort-by='.lastTimestamp'
   ```
   *Убедитесь, что события `OOMKilled` перестали появляться в течение нескольких часов.*

3. **Проверка параметров JVM внутри пода:**
   ```bash
   kubectl exec <pod-name> -- java -XX:+PrintFlagsFinal -version | grep MaxHeapSize
   ```

---

### Rollback

Если приложение начало падать с `java.lang.OutOfMemoryError: Java heap space` (это значит, что 75% памяти не хватает самому приложению), увеличьте лимиты самого контейнера:

1. Увеличьте `limits.memory` до `768Mi` или `1Gi`.
2. Если используете `MaxRAMPercentage`, Heap вырастет автоматически.
3. Примените изменения: `kubectl apply -f deployment.yaml`.

**Blast Radius:** Изменение лимитов памяти может привести к перераспределению подов по узлам (Rescheduling), если на текущих нодах недостаточно свободных ресурсов.

**Cost Warning:** Увеличение `limits.memory` может привести к необходимости масштабирования Node Pool (добавление новых узлов), что увеличит стоимость инфраструктуры.
