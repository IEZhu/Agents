## Latest user message
What's the actual difference between readiness and liveness probes in Kubernetes? We had a liveness probe hitting /health that checks the database, and during a DB outage all our pods restarted in a loop. Why, and how should we set it up?

## Rubric (what a strong answer does)
1. A failing readiness probe removes the pod from Service endpoints without a restart; a failing liveness probe makes the kubelet restart the container.
2. Explains that the database check in the liveness probe turned a dependency outage into restarts of every pod, and keeps liveness to the process itself.
3. Mentions a sensible setting such as a startup probe, initialDelaySeconds or failureThreshold.

## Answer A
### Architecture

The issue you experienced is a classic Kubernetes anti-pattern: **coupling the Liveness probe to an external dependency.**

In Kubernetes, these probes serve two fundamentally different purposes:

1.  **Liveness Probe (`livenessProbe`):** Determines if the container is in a "broken" state (e.g., a deadlock or a frozen process) and needs to be **restarted**.
2.  **Readiness Probe (`readinessProbe`):** Determines if the container is ready to **accept network traffic**. If it fails, the Pod is removed from the Service endpoints, but it is **not restarted**.

**Why your pods restarted in a loop:**
When your database went down, your `/health` endpoint returned an error. Because this was tied to the **Liveness** probe, Kubernetes assumed the application process itself had crashed or hung. It killed the pod and started a new one. The new pod also couldn't reach the DB, failed its liveness check, and was killed. This created a "restart storm" that provided zero benefit because restarting the application cannot fix a broken database.

---

### Implementation

The correct pattern is to split your health checks:
- **Liveness:** Check only the internal health of the process (e.g., "Is the HTTP server responding?").
- **Readiness:** Check the dependencies required to serve a request (e.g., "Can I connect to the DB?").

#### Corrected Kubernetes Manifest

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    spec:
      containers:
      - name: app-container
        image: my-app:1.2.3 # Pin your versions
        ports:
        - containerPort: 8080
        
        # LIVENESS: Only checks if the app is frozen.
        # Does NOT check the database.
        livenessProbe:
          httpGet:
            path: /healthz # A lightweight endpoint that just returns 200 OK
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
          timeoutSeconds: 2
          failureThreshold: 3

        # READINESS: Checks if the app can actually do work.
        # Checks the database connection.
        readinessProbe:
          httpGet:
            path: /ready # An endpoint that pings the DB
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
          timeoutSeconds: 5
          failureThreshold: 3
```

#### Application Logic (Pseudo-code)

```go
// Liveness endpoint: Fast, no dependencies.
// If this fails, the pod is deadlocked/frozen.
func LivenessHandler(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK) 
}

// Readiness endpoint: Checks external dependencies.
// If this fails, the pod is healthy but cannot serve traffic.
func ReadinessHandler(w http.ResponseWriter, r *http.Request) {
    if err := db.Ping(); err != nil {
        w.WriteHeader(http.StatusServiceUnavailable)
        return
    }
    w.WriteHeader(http.StatusOK)
}
```

---

### Deployment

1.  **Update Application Code**: Implement two distinct endpoints (`/healthz` and `/ready`).
2.  **Update Manifest**: Apply the YAML changes above using `kubectl apply -f deployment.yaml`.
3.  **Rolling Update**: Kubernetes will perform a rolling update, ensuring new pods are "Ready" (DB connected) before terminating old pods.

---

### Verification

To verify the fix, simulate a DB outage:

1.  **Check current state**: `kubectl get pods` (All should be `Running` and `1/1 Ready`).
2.  **Simulate DB failure**: Block the DB port or stop the DB service.
3.  **Observe Pods**: 
    - Run `kubectl get pods -w`.
    - You should see the `READY` column change from `1/1` to `0/1`.
    - **Crucially**, the `RESTARTS` column should **not** increment.
4.  **Check Service**: Try to hit the application via the Service IP/DNS; you should receive a 503 or a timeout (as the Pod is removed from the load balancer), but the Pods remain alive.

---

### Rollback

If the new probe configuration causes pods to be marked as "Not Ready" incorrectly:

1.  **Revert Manifest**: `kubectl rollout undo deployment/my-app`.
2.  **Blast Radius**: This change affects the traffic routing of the entire deployment. If the readiness probe is too aggressive (too short a timeout), you may experience "flapping," where pods are repeatedly added and removed from the load balancer, causing intermittent 503 errors for users.


## Answer B
### Architecture

The issue you experienced is a classic Kubernetes anti-pattern: **coupling the Liveness probe to an external dependency.**

Here is the fundamental difference:

*   **Liveness Probe (`livenessProbe`):** Answers *"Is the process deadlocked or crashed?"* If this fails, Kubernetes **kills the container and restarts it**. It is intended to recover from internal states (like a deadlock) that a restart can fix.
*   **Readiness Probe (`readinessProbe`):** Answers *"Is the application ready to handle requests?"* If this fails, Kubernetes **removes the Pod from the Service endpoints**. The Pod stays alive, but no traffic is routed to it. It is intended to handle temporary unavailability (like a DB outage or loading a large cache).

**Why your pods restarted in a loop:**
When your database went down, the Liveness probe failed. Kubernetes assumed the *application process* was broken and restarted it. Since the DB was still down, the new pod also failed its Liveness probe and was restarted. This created a "restart storm" that added unnecessary load to your cluster and provided zero benefit, as restarting the app cannot fix a remote database.

---

### Implementation

You should split your health checks. The Liveness probe should be "shallow" (checking only the process), and the Readiness probe should be "deep" (checking dependencies).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: app-container
        image: my-app:1.2.3 # Pin your versions
        ports:
        - containerPort: 8080
        
        # LIVENESS: Shallow check. 
        # Only fails if the web server itself is unresponsive.
        livenessProbe:
          httpGet:
            path: /healthz # A dedicated endpoint that returns 200 OK immediately
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
          timeoutSeconds: 2
          failureThreshold: 3

        # READINESS: Deep check. 
        # Fails if the DB is down, removing the pod from the LoadBalancer.
        readinessProbe:
          httpGet:
            path: /readyz # An endpoint that pings the DB/Cache
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
          timeoutSeconds: 5
          failureThreshold: 3
```

#### Recommended Endpoint Logic:
1.  **`/healthz` (Liveness):** Simply return `HTTP 200`. If this fails, the process is likely frozen or the event loop is blocked.
2.  **`/readyz` (Readiness):** Perform a `SELECT 1` on the database. If the DB is down, return `HTTP 503`.

---

### Deployment

Apply the updated manifest to your cluster:

```bash
kubectl apply -f deployment.yaml
```

**Blast Radius:** This change triggers a rolling update. Pods will be replaced one by one. If the DB is currently down, the new pods will start but will not receive traffic until the DB recovers.

---

### Verification

To verify the behavior during a simulated outage:

1.  **Check current status:**
    `kubectl get pods`
2.  **Simulate DB Outage:** (e.g., change DB password or block port via NetworkPolicy).
3.  **Observe Readiness:**
    `kubectl get pods` $\rightarrow$ You should see `READY 0/1`. The pods remain `Running`, but are not `Ready`.
4.  **Observe Liveness:**
    `kubectl describe pod <pod-name>` $\rightarrow$ Check the "Events" section. You should **not** see "Liveness probe failed: ..." or "Container restarted".
5.  **Restore DB:**
    The pods should automatically transition back to `READY 1/1` within 10 seconds.

---

### Rollback

If the new probe configuration causes unexpected behavior (e.g., pods never becoming ready due to a misconfigured `/readyz` path):

```bash
kubectl rollout undo deployment/my-app
```
