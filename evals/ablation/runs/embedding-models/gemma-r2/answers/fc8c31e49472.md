### Architecture

The fundamental difference is **what happens when the probe fails**:

*   **Liveness Probe**: "Am I dead?" $\rightarrow$ **Action: Restart.** 
    If this fails, Kubernetes kills the container and restarts it according to the `restartPolicy`.
*   **Readiness Probe**: "Am I ready for traffic?" $\rightarrow$ **Action: Isolate.** 
    If this fails, Kubernetes removes the Pod's IP from the endpoints of all Services. The Pod stays running, but no traffic is routed to it.

#### Why your pods restarted in a loop (The "Death Spiral")
You created a **circular dependency** between your infrastructure (DB) and your process lifecycle (K8s). 

When the DB went down:
1. The Liveness probe failed because the DB was unreachable.
2. Kubernetes assumed the *application process* was frozen or corrupted.
3. Kubernetes killed the Pod and started a new one.
4. The new Pod started, checked the DB, failed the Liveness probe, and was killed.

**Restarting the application cannot fix a broken database.** By linking Liveness to an external dependency, you turned a temporary outage into a cascading failure, putting unnecessary load on your control plane and preventing the app from recovering instantly once the DB came back online.

### Implementation

The rule of thumb is: **Liveness probes should only check for internal state (deadlocks, memory corruption). Readiness probes should check for external dependencies.**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-service
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: api-container
        image: my-api:1.2.0 # Pin versions
        ports:
        - containerPort: 8080
        
        # 1. STARTUP PROBE: Use this for apps that take a while to boot.
        # It disables Liveness and Readiness until it succeeds once.
        startupProbe:
          httpGet:
            path: /health/startup
            port: 8080
          failureThreshold: 30 # Give it 5 minutes (30 * 10s)
          periodSeconds: 10

        # 2. LIVENESS PROBE: Only checks if the process is responsive.
        # DO NOT check the DB here.
        livenessProbe:
          httpGet:
            path: /health/live
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 15
          failureThreshold: 3

        # 3. READINESS PROBE: Checks if the app can actually do work.
        # THIS is where the DB check belongs.
        readinessProbe:
          httpGet:
            path: /health/ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
          failureThreshold: 3
```

#### Expected Endpoint Logic:
- `/health/live`: Returns `200 OK` as long as the HTTP server is running.
- `/health/ready`: Performs a `SELECT 1` or equivalent on the DB. Returns `200 OK` if the DB is reachable; `503 Service Unavailable` otherwise.

---

### Deployment

1. Update your application code to expose the three distinct endpoints.
2. Update your Deployment YAML with the probes shown above.
3. Apply the changes:
   ```bash
   kubectl apply -f deployment.yaml
   ```

---

### Verification

To verify this setup, simulate a DB failure:

1. **Check current status**: `kubectl get pods` (All should be `Ready 1/1`).
2. **Simulate DB failure**: (e.g., change DB password in Secret or block port via NetworkPolicy).
3. **Observe Readiness**: 
   - Run `kubectl get pods -w`. 
   - You will see `Ready 1/1` change to `Ready 0/1`.
   - The Pods **will NOT restart**.
4. **Observe Traffic**: 
   - Try to curl the Service. You should get a 503 or connection error (since no endpoints exist), but the Pods remain alive.
5. **Restore DB**:
   - Fix the connection. 
   - Observe the pods automatically transition back to `Ready 1/1` and begin accepting traffic immediately.

---

### Rollback

If the new probe configuration causes pods to be marked "Unready" incorrectly:

```bash
# Roll back to the previous deployment revision
kubectl rollout undo deployment/api-service

# Verify the rollback
kubectl rollout status deployment/api-service
```

**Blast Radius**: Changing probes affects traffic routing. An incorrect `readinessProbe` can remove all pods from a service, causing a complete outage for that service even if the pods are healthy. Always test in a staging environment first.
