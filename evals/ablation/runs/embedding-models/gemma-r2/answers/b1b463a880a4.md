### Architecture

The issue you experienced is a classic Kubernetes anti-pattern: **coupling external dependency health to process liveness.**

In Kubernetes, these two probes serve fundamentally different purposes:

1.  **Liveness Probe (`livenessProbe`):** Answers *"Is the process crashed or deadlocked?"* 
    *   **Action on failure:** Kubernetes kills the container and restarts it.
    *   **Wrong usage:** Checking a database. If the DB is down, restarting the application 1,000 times will not fix the database; it only adds load to your cluster and prevents the app from recovering automatically once the DB returns.

2.  **Readiness Probe (`readinessProbe`):** Answers *"Is the application ready to handle requests?"*
    *   **Action on failure:** Kubernetes removes the Pod's IP from the Service endpoints. The Pod stays running, but no traffic is routed to it.
    *   **Correct usage:** Checking database connectivity, loading large caches, or waiting for a configuration sync.

**The Root Cause:** Because your DB check was in the **liveness** probe, a DB outage signaled to Kubernetes that the *application process* was dead. K8s tried to "fix" it by restarting the pods, leading to the restart loop (CrashLoopBackOff).

---

### Implementation

You should split your health check into two distinct endpoints: `/healthz` (Liveness) and `/readyz` (Readiness).

#### 1. Application Logic (Conceptual)
*   **`/healthz`**: Returns `200 OK` as long as the web server is running. It should perform no external I/O.
*   **`/readyz`**: Checks if the DB connection is active. Returns `200 OK` if connected, `503 Service Unavailable` if not.

#### 2. Kubernetes Configuration
Pin your image versions and define the probes explicitly in your deployment.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app-container
        image: my-registry/my-app:v1.2.3 # Pin version
        ports:
        - containerPort: 8080
        
        # Liveness: Only checks if the process is responsive.
        # If this fails, the pod REBOOTS.
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
          timeoutSeconds: 2
          failureThreshold: 3

        # Readiness: Checks if dependencies (DB) are available.
        # If this fails, the pod is REMOVED FROM LOAD BALANCER.
        readinessProbe:
          httpGet:
            path: /readyz
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
          timeoutSeconds: 2
          failureThreshold: 3
```

### Deployment

1.  **Update Application Code**: Implement the separate endpoints.
2.  **Apply Manifest**:
    ```bash
    kubectl apply -f deployment.yaml
    ```
3.  **Rollout Status**:
    ```bash
    kubectl rollout status deployment/my-app
    ```

### Verification

To confirm this is fixed, simulate a database failure:

1.  **Simulate DB Outage**: Block the network path to the DB or stop the DB service.
2.  **Check Pod Status**: 
    ```bash
    kubectl get pods
    ```
    *   **Expected Result**: Pods remain `Running`, but the `READY` column changes from `1/1` to `0/1`.
3.  **Check Service Traffic**: 
    Try to curl your service. You should get a `503` or a timeout from the Load Balancer/Ingress, but the pods **must not restart**.
4.  **Restore DB**:
    *   **Expected Result**: Pods automatically transition back to `1/1` and resume receiving traffic without any restarts.

---

### Rollback

If the new probes cause pods to be marked as "Not Ready" too aggressively (causing a total outage), revert to the previous manifest version:

```bash
kubectl rollout undo deployment/my-app
```

**Blast Radius:** Changing probes affects the availability of the service. If `readinessProbe` is too strict, you may accidentally remove all pods from the service, resulting in a `503` for all users. Always test `initialDelaySeconds` to ensure the app has time to boot before K8s starts probing.
