Ошибка «Connection refused» (В соединении отказано) на уровне TCP означает, что запрос дошел до сервера, но ОС сервера отклонила его. Поскольку через `localhost` всё работает, проблема почти наверняка в том, что PostgreSQL либо не «слушает» внешние интерфейсы, либо доступ к порту заблокирован фаерволом.

### Анализ
Когда вы подключаетесь через `localhost`, PostgreSQL использует либо Unix-сокет, либо loopback-интерфейс (`127.0.0.1`). По умолчанию PostgreSQL настроен в целях безопасности игнорировать любые запросы, пришедшие из внешней сети.

### Что проверить (пошагово)

#### 1. Настройка `listen_addresses` (Конфигурация PostgreSQL)
Это самая частая причина. Проверьте файл `postgresql.conf`.

**Что сделать:**
Найдите параметр `listen_addresses`. Скорее всего, там установлено `localhost`.
```bash
# Поиск пути к конфигу, если вы его не знаете
psql -U postgres -c "SHOW config_file;"
```
Откройте файл и измените строку:
```conf
# Было:
# listen_addresses = 'localhost' 

# Стало (слушать все интерфейсы):
listen_addresses = '*' 
```
*Примечание: Если сервер имеет несколько IP, можно указать конкретный через запятую: `listen_addresses = 'localhost, 192.168.1.20'`.*

**Важно:** После изменения этого параметра требуется **перезагрузка** сервиса:
```bash
sudo systemctl restart postgresql
# или
sudo service postgresql restart
```

#### 2. Проверка порта на сервере (Netstat/SS)
Убедитесь, что PostgreSQL действительно начал слушать внешний адрес после перезагрузки.
Выполните на сервере:
```bash
ss -nlt | grep 5432
```
**Результат:**
*   Если видите `127.0.0.1:5432` $\rightarrow$ всё еще слушает только локально (см. пункт 1).
*   Если видите `0.0.0.0:5432` или `*:5432` $\rightarrow$ слушает всех, переходите к пункту 3.

#### 3. Фаервол (OS Firewall)
Если PostgreSQL слушает `*`, но вы всё еще получаете «Connection refused», значит пакеты отбрасываются фаерволом.

**Для Ubuntu/Debian (UFW):**
```bash
sudo ufw allow 5432/tcp
```
**Для CentOS/RHEL/Fedora (firewalld):**
```bash
sudo firewall-cmd --permanent --add-port=5432/tcp
sudo firewall-cmd --reload
```
**Для iptables:**
```bash
sudo iptables -A INPUT -p tcp --dport 5432 -j ACCEPT
```

### Следующий шаг: Ошибка `pg_hba.conf`
Как только вы решите проблему с TCP-соединением, вы, скорее всего, столкнетесь со следующей ошибкой:
`psql: fatal: no pg_hba.conf entry for host "192.168.1.x", user "app", database "..."`

Это уже уровень авторизации PostgreSQL. Чтобы её исправить:
1. Откройте файл `pg_hba.conf`.
2. Добавьте строку, разрешающую доступ пользователю `app` с вашего IP или подсети:
```conf
# TYPE  DATABASE        USER            ADDRESS                 METHOD
host    all             app             192.168.1.0/24          scram-sha-256
```
3. Перезагрузите конфигурацию (перезапуск сервера не нужен, достаточно `reload`):
```bash
sudo systemctl reload postgresql
```

### Итоговый чек-лист для проверки с клиента
Чтобы быстро понять, где затык, используйте `nc` (netcat) или `telnet` с вашего рабочего компьютера:
```bash
nc -zv db.local 5432
```
*   **Connection refused** $\rightarrow$ либо `listen_addresses`, либо фаервол.
*   **Timeout** $\rightarrow$ фаервол (пакеты дропаются молча).
*   **Succeeded/Connected** $\rightarrow$ сеть работает, ищите проблему в `pg_hba.conf` или правах пользователя.
