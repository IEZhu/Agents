### Почему это происходит

Вы столкнулись с классической проблемой разрыва между пониманием памяти внутри JVM и тем, как её видит Kubernetes (cgroups).

**Главная ошибка: `-Xmx512m` при `limits.memory: 512Mi`.**

Память Java-процесса состоит не только из Heap (кучи). Общий объем памяти (RSS), который потребляет контейнер, складывается из:
1. **Heap Memory** (ограничена `-Xmx`).
2. **Metaspace** (хранение метаданных классов).
3. **Code Cache** (компилированный JIT-код).
4. **Thread Stacks** (память на каждый поток, обычно по 1МБ).
5. **Direct Buffers** (используются для NIO, сетевого ввода-вывода).
6. **JVM Overhead** (внутренние структуры самой виртуальной машины).
7. **Native Memory** (память, выделяемая через `malloc` библиотеками или JNI).

Когда вы устанавливаете `-Xmx512m`, вы говорите JVM: «Можешь использовать до 512МБ **только под кучу**». Но как только JVM потребуется еще 10-50МБ под Metaspace или стеки потоков, суммарное потребление процесса превысит 512Mi. Kubernetes видит превышение лимита cgroup и мгновенно убивает процесс через `SIGKILL` (Exit Code 137).

---

### Что поменять

#### 1. Правильный подход: Использование процентов (Container Awareness)
В Java 21 не рекомендуется жестко прописывать `-Xmx` в мегабайтах, так как это делает манифесты негибкими. Вместо этого используйте флаг `MaxRAMPercentage`. JVM сама вычислит размер кучи, исходя из лимита контейнера.

**Рекомендуемое значение:** `70.0%` — `80.0%`. Это оставляет 20-30% памяти для не-heap областей.

#### 2. Обновление конфигурации

**В манифесте Kubernetes (Deployment):**
Увеличьте лимит, если приложению действительно нужно 512МБ кучи, или оставьте как есть, но ограничьте кучу.

```yaml
resources:
  requests:
    memory: "640Mi" # Рекомендуется ставить request чуть выше лимита кучи
    cpu: "500m"
  limits:
    memory: "640Mi" # Увеличиваем лимит, чтобы дать место для Non-Heap
    cpu: "1000m"
```

**В аргументах запуска JVM:**
Уберите `-Xmx512m` и добавьте следующие флаги:

```bash
-XX:MaxRAMPercentage=75.0 \
-XX:InitialRAMPercentage=75.0 \
-XX:+UseG1GC \
-XX:+ExitOnOutOfMemoryError
```

*   `MaxRAMPercentage=75.0`: JVM выделит под Heap $\approx 480\text{MB}$ (от $640\text{MB}$), оставив $\approx 160\text{MB}$ на всё остальное.
*   `ExitOnOutOfMemoryError`: Важный флаг для K8s. Если внутри JVM случится `java.lang.OutOfMemoryError`, процесс завершится с ошибкой, и K8s перезапустит его, вместо того чтобы оставить «зомби-под» в зависшем состоянии.

### Итоговая схема реализации

#### Implementation

**До (плохо):**
*   `limits.memory: 512Mi`
*   `JAVA_OPTS: "-Xmx512m"` $\rightarrow$ **Результат: OOMKilled**

**После (хорошо):**
*   `limits.memory: 640Mi`
*   `JAVA_OPTS: "-XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError"` $\rightarrow$ **Результат: Стабильная работа**

### Verification
Чтобы убедиться, что настройки применились, выполните команду внутри пода:
```bash
kubectl exec <pod_name> -- java -XX:+PrintFlagsFinal -version | grep MaxHeapSize
```
Вы увидите значение в байтах. Оно должно быть меньше, чем `limits.memory` в вашем YAML.

### Rollback
Если приложение начнет падать с внутренней ошибкой `java.lang.OutOfMemoryError: Java heap space` (а не `OOMKilled` от K8s), значит, приложению не хватает именно Heap. В этом случае:
1. Увеличьте `limits.memory` до `800Mi` или `1Gi`.
2. Сохраните `MaxRAMPercentage=75.0`.
3. Перезапустите деплоймент.
