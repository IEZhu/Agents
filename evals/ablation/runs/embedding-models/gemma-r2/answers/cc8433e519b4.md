Ошибка «Connection refused» (В соединении отказано) на уровне TCP означает, что запрос дошел до сервера, но операционная система сервера отклонила его, так как на указанном порту (5432) нет процесса, который «слушает» входящие соединения с этого конкретного сетевого интерфейса.

Так как локально (`localhost`) всё работает, проблема в том, что PostgreSQL настроен слушать только локальный интерфейс (loopback), либо трафик блокируется брандмауэром.

### Анализ
1. **Listen Addresses**: По умолчанию PostgreSQL часто настроен на `listen_addresses = 'localhost'`, что заставляет его игнорировать любые запросы, приходящие не с самого сервера.
2. **Firewall**: Брандмауэр (ufw, firewalld, iptables) может сбрасывать пакеты на порт 5432.
3. **Слой авторизации (pg_hba.conf)**: Это вторая линия защиты. Даже если вы исправите ошибку «Connection refused», вы можете получить ошибку «no pg_hba.conf entry», если сервер не знает, что пользователю `app` с вашего IP разрешено подключаться.

---

### Решение

#### Шаг 1: Проверка фактического прослушивания портов
Зайдите на сервер и выполните команду, чтобы увидеть, на каком IP «висит» Postgres:
```bash
sudo ss -tlnp | grep 5432
# или если ss нет:
sudo netstat -tlnp | grep 5432
```
* **Если видите `127.0.0.1:5432`** $\rightarrow$ сервер слушает только себя. Нужно менять конфиг.
* **Если видите `0.0.0.0:5432` или `*:5432`** $\rightarrow$ сервер слушает все интерфейсы. Проблема в брандмауэре.

#### Шаг 2: Настройка `postgresql.conf`
Если сервер слушает только localhost:
1. Найдите файл `postgresql.conf` (обычно в `/etc/postgresql/X.X/main/` или в директории данных `/var/lib/pgsql/data/`).
2. Найдите параметр `listen_addresses`.
3. Измените его на:
   ```ini
   listen_addresses = '*' 
   ```
   *(Знак `*` означает слушать все доступные сетевые интерфейсы. Для повышенной безопасности можно указать конкретный внутренний IP сервера).*

**Важно:** После этого изменения требуется **перезагрузка** сервиса:
```bash
sudo systemctl restart postgresql
```

#### Шаг 3: Настройка брандмауэра (Firewall)
Если Postgres слушает `0.0.0.0`, но доступа нет, откройте порт:

* **Для Ubuntu/Debian (UFW):**
  ```bash
  sudo ufw allow 5432/tcp
  ```
* **Для CentOS/RHEL/Fedora (Firewalld):**
  ```bash
  sudo firewall-cmd --permanent --add-port=5432/tcp
  sudo firewall-cmd --reload
  ```

#### Шаг 4: Разрешение доступа в `pg_hba.conf`
Теперь, когда TCP-соединение будет установлено, Postgres проверит, можно ли вам зайти.
1. Откройте файл `pg_hba.conf` (лежит рядом с `postgresql.conf`).
2. Добавьте строку в конец файла, разрешающую доступ пользователю `app` из вашей сети:
   ```text
   # TYPE  DATABASE        USER            ADDRESS                 METHOD
   host    all             app             192.168.1.0/24          scram-sha-256
   ```
   *(Замените `192.168.1.0/24` на вашу подсеть или конкретный IP клиента. Метод `scram-sha-256` — стандарт для новых версий, для старых может быть `md5`).*

3. Перезагрузите конфигурацию (перезагружать весь сервер не обязательно):
   ```bash
   sudo systemctl reload postgresql
   ```

### Итоговый чек-лист проверки

| Что проверить | Команда/Место | Ожидаемый результат |
| :--- | :--- | :--- |
| **Слушает ли сеть?** | `ss -tlnp \| grep 5432` | `0.0.0.0:5432` |
| **Разрешен ли порт?** | `ufw status` / `firewall-cmd` | `5432 ALLOW` |
| **Разрешен ли IP?** | `pg_hba.conf` | Строка с вашим IP и пользователем `app` |

### Верификация
С клиента попробуйте сначала проверить доступность порта через `telnet` или `nc`, чтобы исключить влияние самого `psql`:
```bash
nc -zv db.local 5432
# или
telnet db.local 5432
```
Если соединение установлено (`Connected`), значит сетевой уровень настроен верно, и можно запускать `psql`.
