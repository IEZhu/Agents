## Latest user message
Под с сервисом на Java 21 в Kubernetes каждые пару часов перезапускается, в kubectl describe pod вижу Last State: Terminated, Reason: OOMKilled, Exit Code: 137. В контейнере limits.memory: 512Mi, приложение запускается с -Xmx512m. Почему так и что поменять?

## Rubric (what a strong answer does)
1. Explains that -Xmx caps only the heap while the JVM also uses non-heap memory (metaspace, thread stacks, code cache, direct buffers), so a 512m heap lets the process exceed the 512Mi limit and the container is OOM-killed (exit code 137).
2. Recommends a concrete fix: a heap well below the limit (for example replacing -Xmx with -XX:MaxRAMPercentage, or a smaller -Xmx) and/or a higher limits.memory, and suggests measuring actual memory use.
3. Does not mistake the symptom for a Java OutOfMemoryError: it is a container OOM kill.
4. The reply is in Russian, with code, commands and identifiers left as written, and contains no English restatement of the request.

## Answer A
### Почему это происходит

Основная причина в том, что **память Java-процесса $\neq$ Heap (куча)**.

Когда вы устанавливаете `-Xmx512m` и `limits.memory: 512Mi`, вы говорите JVM, что она может использовать до 512 МБ только под объекты в куче. Однако контейнер потребляет гораздо больше, так как помимо Heap существуют:

1.  **Metaspace**: Хранение метаданных классов (может занимать десятки и сотни МБ).
2.  **Code Cache**: JIT-компилированный код.
3.  **Thread Stacks**: Каждый поток в Java потребляет память (по умолчанию $\approx 1$ МБ на поток). Если у вас 50 потоков — это уже 50 МБ.
4.  **Direct Buffers**: Память вне кучи (Off-heap), используемая для NIO, сетевых библиотек (Netty и т.д.).
5.  **JVM Overhead**: Сама виртуальная машина, GC-структуры и т.д.

**Итог:** Общее потребление памяти процессом (RSS) становится примерно `512MB (Heap) + 100-200MB (Non-Heap)`. Как только сумма превышает `limits.memory`, Kubernetes (точнее, Linux OOM Killer) принудительно убивает процесс с кодом **137**.

---

### Что поменять

Есть два пути: либо увеличить лимит контейнера, либо ограничить Heap так, чтобы осталось место для Non-Heap. 

Для Java 21 в контейнерах **крайне не рекомендуется** использовать жестко заданные значения `-Xmx`. Вместо этого используйте процентное соотношение.

#### Вариант 1: Использование MaxRAMPercentage (Рекомендуемый)

JVM в Java 21 отлично понимает лимиты контейнера. Вместо `-Xmx` используйте флаг `-XX:MaxRAMPercentage`.

**Настройки:**
*   **`limits.memory: 512Mi`** (оставляем или увеличиваем)
*   **JVM Args:** `-XX:MaxRAMPercentage=75.0`

В этом случае JVM возьмет 75% от 512 МБ ($\approx 384$ МБ) под кучу, а остальные 25% оставит под Metaspace, стеки и прочее.

#### Вариант 2: Ручная корректировка (Если нельзя менять флаги)

Если вы хотите оставить `-Xmx512m`, вам нужно поднять лимит в Kubernetes минимум до **768Mi** или **1Gi**.

---

### Реализация (Пример YAML)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: java-app
spec:
  template:
    spec:
      containers:
      - name: java-app
        image: my-app:1.0.0 # Pin versions!
        resources:
          requests:
            memory: "512Mi"
            cpu: "500m"
          limits:
            memory: "512Mi" # Оставляем лимит 512
            cpu: "1000m"
        env:
        - name: JAVA_OPTS
          value: >-
            -XX:MaxRAMPercentage=75.0 
            -XX:InitialRAMPercentage=75.0 
            -XX:+UseG1GC 
            -XX:+ExitOnOutOfMemoryError
```

*Примечание: `-XX:InitialRAMPercentage` устанавливается равным Max, чтобы избежать лишних аллокаций памяти при старте и избежать "раздувания" Heap.*

---

### Верификация

1.  **Мониторинг потребления:**
    Используйте `kubectl top pod`, чтобы увидеть реальное потребление RSS. Оно должно стабилизироваться ниже 512 МБ.
    ```bash
    kubectl top pod <pod-name>
    ```

2.  **Проверка логов JVM:**
    Добавьте флаг `-Xlog:gc*`, чтобы видеть, как работает Garbage Collector и сколько памяти реально используется.

3.  **Анализ через Prometheus/Grafana:**
    Следите за метрикой `container_memory_working_set_bytes`. Если она приближается к лимиту $\rightarrow$ увеличивайте `limits.memory`.

### Rollback

Если после изменения `-XX:MaxRAMPercentage=75.0` приложение начало падать с `java.lang.OutOfMemoryError: Java heap space` (внутренняя ошибка Java, а не OOMKilled от K8s), значит приложению физически не хватает 384 МБ кучи.

**Действие:**
1.  Увеличить `limits.memory` до `1Gi`.
2.  Оставить `-XX:MaxRAMPercentage=75.0` (куча автоматически станет $\approx 768$ МБ).

**Blast Radius:** Изменение ресурсов требует перезапуска подов (RollingUpdate). При неправильном расчете лимитов приложение может начать падать чаще или работать медленнее из-за частых циклов GC.


## Answer B
### Почему это происходит

Вы столкнулись с классической проблемой разрыва между пониманием памяти внутри JVM и тем, как её видит Kubernetes (cgroups).

**Главная ошибка: `-Xmx512m` при `limits.memory: 512Mi`.**

Память Java-процесса состоит не только из Heap (кучи). Общий объем памяти (RSS), который потребляет контейнер, складывается из:
1. **Heap Memory** (ограничена `-Xmx`).
2. **Metaspace** (хранение метаданных классов).
3. **Code Cache** (компилированный JIT-код).
4. **Thread Stacks** (память на каждый поток, обычно по 1МБ).
5. **Direct Buffers** (используются для NIO, сетевого ввода-вывода).
6. **JVM Overhead** (внутренние структуры самой виртуальной машины).
7. **Native Memory** (память, выделяемая через `malloc` библиотеками или JNI).

Когда вы устанавливаете `-Xmx512m`, вы говорите JVM: «Можешь использовать до 512МБ **только под кучу**». Но как только JVM потребуется еще 10-50МБ под Metaspace или стеки потоков, суммарное потребление процесса превысит 512Mi. Kubernetes видит превышение лимита cgroup и мгновенно убивает процесс через `SIGKILL` (Exit Code 137).

---

### Что поменять

#### 1. Правильный подход: Использование процентов (Container Awareness)
В Java 21 не рекомендуется жестко прописывать `-Xmx` в мегабайтах, так как это делает манифесты негибкими. Вместо этого используйте флаг `MaxRAMPercentage`. JVM сама вычислит размер кучи, исходя из лимита контейнера.

**Рекомендуемое значение:** `70.0%` — `80.0%`. Это оставляет 20-30% памяти для не-heap областей.

#### 2. Обновление конфигурации

**В манифесте Kubernetes (Deployment):**
Увеличьте лимит, если приложению действительно нужно 512МБ кучи, или оставьте как есть, но ограничьте кучу.

```yaml
resources:
  requests:
    memory: "640Mi" # Рекомендуется ставить request чуть выше лимита кучи
    cpu: "500m"
  limits:
    memory: "640Mi" # Увеличиваем лимит, чтобы дать место для Non-Heap
    cpu: "1000m"
```

**В аргументах запуска JVM:**
Уберите `-Xmx512m` и добавьте следующие флаги:

```bash
-XX:MaxRAMPercentage=75.0 \
-XX:InitialRAMPercentage=75.0 \
-XX:+UseG1GC \
-XX:+ExitOnOutOfMemoryError
```

*   `MaxRAMPercentage=75.0`: JVM выделит под Heap $\approx 480\text{MB}$ (от $640\text{MB}$), оставив $\approx 160\text{MB}$ на всё остальное.
*   `ExitOnOutOfMemoryError`: Важный флаг для K8s. Если внутри JVM случится `java.lang.OutOfMemoryError`, процесс завершится с ошибкой, и K8s перезапустит его, вместо того чтобы оставить «зомби-под» в зависшем состоянии.

---

### Итоговая схема реализации

#### Implementation

**До (плохо):**
*   `limits.memory: 512Mi`
*   `JAVA_OPTS: "-Xmx512m"` $\rightarrow$ **Результат: OOMKilled**

**После (хорошо):**
*   `limits.memory: 640Mi`
*   `JAVA_OPTS: "-XX:MaxRAMPercentage=75.0 -XX:+ExitOnOutOfMemoryError"` $\rightarrow$ **Результат: Стабильная работа**

### Verification
Чтобы убедиться, что настройки применились, выполните команду внутри пода:
```bash
kubectl exec <pod_name> -- java -XX:+PrintFlagsFinal -version | grep MaxHeapSize
```
Вы увидите значение в байтах. Оно должно быть меньше, чем `limits.memory` в вашем YAML.

### Rollback
Если приложение начнет падать с внутренней ошибкой `java.lang.OutOfMemoryError: Java heap space` (а не `OOMKilled` от K8s), значит, приложению не хватает именно Heap. В этом случае:
1. Увеличьте `limits.memory` до `800Mi` или `1Gi`.
2. Сохраните `MaxRAMPercentage=75.0`.
3. Перезапустите деплоймент.
