## Latest user message
What's the actual difference between readiness and liveness probes in Kubernetes? We had a liveness probe hitting /health that checks the database, and during a DB outage all our pods restarted in a loop. Why, and how should we set it up?

## Rubric (what a strong answer does)
1. A failing readiness probe removes the pod from Service endpoints without a restart; a failing liveness probe makes the kubelet restart the container.
2. Explains that the database check in the liveness probe turned a dependency outage into restarts of every pod, and keeps liveness to the process itself.
3. Mentions a sensible setting such as a startup probe, initialDelaySeconds or failureThreshold.

## Answer A
### Architecture

The fundamental difference is **what happens when the probe fails**:

*   **Liveness Probe**: "Am I dead?" $\rightarrow$ **Action: Restart.** 
    If this fails, Kubernetes kills the container and restarts it according to the `restartPolicy`.
*   **Readiness Probe**: "Am I ready for traffic?" $\rightarrow$ **Action: Isolate.** 
    If this fails, Kubernetes removes the Pod's IP from the endpoints of all Services. The Pod stays running, but no traffic is routed to it.

#### Why your pods restarted in a loop (The "Death Spiral")
You created a **circular dependency** between your infrastructure (DB) and your process lifecycle (K8s). 

When the DB went down:
1. The Liveness probe failed because the DB was unreachable.
2. Kubernetes assumed the *application process* was frozen or corrupted.
3. Kubernetes killed the Pod and started a new one.
4. The new Pod started, checked the DB, failed the Liveness probe, and was killed.

**Restarting the application cannot fix a broken database.** By linking Liveness to an external dependency, you turned a temporary outage into a cascading failure, putting unnecessary load on your control plane and preventing the app from recovering instantly once the DB came back online.

---

### Implementation

The rule of thumb is: **Liveness probes should only check for internal state (deadlocks, memory corruption). Readiness probes should check for external dependencies.**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-service
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: api-container
        image: my-api:1.2.0 # Pin versions
        ports:
        - containerPort: 8080
        
        # 1. STARTUP PROBE: Use this for apps that take a while to boot.
        # It disables Liveness and Readiness until it succeeds once.
        startupProbe:
          httpGet:
            path: /health/startup
            port: 8080
          failureThreshold: 30 # Give it 5 minutes (30 * 10s)
          periodSeconds: 10

        # 2. LIVENESS PROBE: Only checks if the process is responsive.
        # DO NOT check the DB here.
        livenessProbe:
          httpGet:
            path: /health/live
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 15
          failureThreshold: 3

        # 3. READINESS PROBE: Checks if the app can actually do work.
        # THIS is where the DB check belongs.
        readinessProbe:
          httpGet:
            path: /health/ready
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
          failureThreshold: 3
```

#### Expected Endpoint Logic:
- `/health/live`: Returns `200 OK` as long as the HTTP server is running.
- `/health/ready`: Performs a `SELECT 1` or equivalent on the DB. Returns `200 OK` if the DB is reachable; `503 Service Unavailable` otherwise.

---

### Deployment

1. Update your application code to expose the three distinct endpoints.
2. Update your Deployment YAML with the probes shown above.
3. Apply the changes:
   ```bash
   kubectl apply -f deployment.yaml
   ```

---

### Verification

To verify this setup, simulate a DB failure:

1. **Check current status**: `kubectl get pods` (All should be `Ready 1/1`).
2. **Simulate DB failure**: (e.g., change DB password in Secret or block port via NetworkPolicy).
3. **Observe Readiness**: 
   - Run `kubectl get pods -w`. 
   - You will see `Ready 1/1` change to `Ready 0/1`.
   - The Pods **will NOT restart**.
4. **Observe Traffic**: 
   - Try to curl the Service. You should get a 503 or connection error (since no endpoints exist), but the Pods remain alive.
5. **Restore DB**:
   - Fix the connection. 
   - Observe the pods automatically transition back to `Ready 1/1` and begin accepting traffic immediately.

---

### Rollback

If the new probe configuration causes pods to be marked "Unready" incorrectly:

```bash
# Roll back to the previous deployment revision
kubectl rollout undo deployment/api-service

# Verify the rollback
kubectl rollout status deployment/api-service
```

**Blast Radius**: Changing probes affects traffic routing. An incorrect `readinessProbe` can remove all pods from a service, causing a complete outage for that service even if the pods are healthy. Always test in a staging environment first.


## Answer B
### Architecture

The issue you experienced is a classic Kubernetes anti-pattern: **coupling external dependency health to process liveness.**

In Kubernetes, these two probes serve fundamentally different purposes:

1.  **Liveness Probe (`livenessProbe`):** Answers *"Is the process crashed or deadlocked?"* 
    *   **Action on failure:** Kubernetes kills the container and restarts it.
    *   **Wrong usage:** Checking a database. If the DB is down, restarting the application 1,000 times will not fix the database; it only adds load to your cluster and prevents the app from recovering automatically once the DB returns.

2.  **Readiness Probe (`readinessProbe`):** Answers *"Is the application ready to handle requests?"*
    *   **Action on failure:** Kubernetes removes the Pod's IP from the Service endpoints. The Pod stays running, but no traffic is routed to it.
    *   **Correct usage:** Checking database connectivity, loading large caches, or waiting for a configuration sync.

**The Root Cause:** Because your DB check was in the **liveness** probe, a DB outage signaled to Kubernetes that the *application process* was dead. K8s tried to "fix" it by restarting the pods, leading to the restart loop (CrashLoopBackOff).

---

### Implementation

You should split your health check into two distinct endpoints: `/healthz` (Liveness) and `/readyz` (Readiness).

#### 1. Application Logic (Conceptual)
*   **`/healthz`**: Returns `200 OK` as long as the web server is running. It should perform no external I/O.
*   **`/readyz`**: Checks if the DB connection is active. Returns `200 OK` if connected, `503 Service Unavailable` if not.

#### 2. Kubernetes Configuration
Pin your image versions and define the probes explicitly in your deployment.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: app-container
        image: my-registry/my-app:v1.2.3 # Pin version
        ports:
        - containerPort: 8080
        
        # Liveness: Only checks if the process is responsive.
        # If this fails, the pod REBOOTS.
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 15
          periodSeconds: 20
          timeoutSeconds: 2
          failureThreshold: 3

        # Readiness: Checks if dependencies (DB) are available.
        # If this fails, the pod is REMOVED FROM LOAD BALANCER.
        readinessProbe:
          httpGet:
            path: /readyz
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 10
          timeoutSeconds: 2
          failureThreshold: 3
```

---

### Deployment

1.  **Update Application Code**: Implement the separate endpoints.
2.  **Apply Manifest**:
    ```bash
    kubectl apply -f deployment.yaml
    ```
3.  **Rollout Status**:
    ```bash
    kubectl rollout status deployment/my-app
    ```

---

### Verification

To confirm this is fixed, simulate a database failure:

1.  **Simulate DB Outage**: Block the network path to the DB or stop the DB service.
2.  **Check Pod Status**: 
    ```bash
    kubectl get pods
    ```
    *   **Expected Result**: Pods remain `Running`, but the `READY` column changes from `1/1` to `0/1`.
3.  **Check Service Traffic**: 
    Try to curl your service. You should get a `503` or a timeout from the Load Balancer/Ingress, but the pods **must not restart**.
4.  **Restore DB**:
    *   **Expected Result**: Pods automatically transition back to `1/1` and resume receiving traffic without any restarts.

---

### Rollback

If the new probes cause pods to be marked as "Not Ready" too aggressively (causing a total outage), revert to the previous manifest version:

```bash
kubectl rollout undo deployment/my-app
```

**Blast Radius:** Changing probes affects the availability of the service. If `readinessProbe` is too strict, you may accidentally remove all pods from the service, resulting in a `503` for all users. Always test `initialDelaySeconds` to ensure the app has time to boot before K8s starts probing.
