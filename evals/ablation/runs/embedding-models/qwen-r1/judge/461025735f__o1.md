## Latest user message
What's the actual difference between readiness and liveness probes in Kubernetes? We had a liveness probe hitting /health that checks the database, and during a DB outage all our pods restarted in a loop. Why, and how should we set it up?

## Rubric (what a strong answer does)
1. A failing readiness probe removes the pod from Service endpoints without a restart; a failing liveness probe makes the kubelet restart the container.
2. Explains that the database check in the liveness probe turned a dependency outage into restarts of every pod, and keeps liveness to the process itself.
3. Mentions a sensible setting such as a startup probe, initialDelaySeconds or failureThreshold.

## Answer A
**BLUF:** Your liveness probe was checking a dependency (the DB) instead of the process itself. When the DB went down, every pod's liveness check failed, kubelet killed the container, it restarted, the DB was still down, and the loop repeated. The fix is to split your health endpoint: liveness checks "is the process alive," readiness checks "can I serve traffic right now."

## The two probes, precisely

| | Liveness | Readiness |
|---|---|---|
| **Question it answers** | "Is this container in a state from which it can only recover by being restarted?" | "Is this container ready to accept traffic *right now*?" |
| **Action on failure** | Kubelet **kills the container** and restarts it (per `restartPolicy`) | Pod is **removed from Service endpoints**; container keeps running |
| **What it should check** | Process is alive, event loop isn't blocked, no fatal deadlock | All dependencies (DB, cache, config) are reachable |
| **Failure threshold** | Usually 3 (give it a few chances before killing) | Usually 1–3 (you want to stop routing traffic quickly) |

The critical distinction is the **consequence**. Liveness failure = destructive (kill + restart). Readiness failure = non-destructive (just stop sending traffic).

## Why your incident happened

```
DB outage
  → /health returns 500 (DB query times out)
    → liveness probe fails (3× in a row)
      → kubelet kills the container
        → container restarts
          → app boots, tries to connect to DB → still down
            → /health returns 500 again
              → liveness probe fails again
                → kubelet kills it again
                  → … loop until DB recovers
```

Every pod in the Deployment hit this simultaneously, so you got a full restart storm. Worse, during the restart window the pods were in `CrashLoopBackOff` or `ContainerCreating`, so you had **zero** capacity even for requests that didn't need the DB.

The root cause: `/health` conflated "am I alive?" with "are my dependencies up?" A liveness probe should never depend on external systems. If a dependency is down, the correct response is "stop sending me traffic," not "kill me."

## How to set it up

### 1. Split the endpoint in your app

```python
# FastAPI example (works the same in any framework)

@app.get("/live")
def live():
    """Process is running. No external calls."""
    return {"status": "ok"}

@app.get("/ready")
def ready():
    """All dependencies reachable. May return 503."""
    try:
        db.execute("SELECT 1")
    except Exception:
        return JSONResponse(status_code=503, content={"status": "not ready"})
    # check cache, config, etc.
    return {"status": "ready"}
```

The `/live` handler must **never** touch the network, disk, or any external system. If your HTTP server itself is blocked (goroutine leak, thread-pool exhaustion), the TCP connection won't complete and the probe times out — that's the signal you want.

### 2. Wire the probes in the Pod spec

```yaml
containers:
  - name: api
    image: registry.example.com/api:1.4.2   # pin the tag
    ports:
      - containerPort: 8080
    startupProbe:            # optional: protects slow-booting apps
      httpGet:
        path: /live
        port: 8080
      periodSeconds: 5
      failureThreshold: 24   # 120 s total before giving up
    livenessProbe:
      httpGet:
        path: /live
        port: 8080
      periodSeconds: 10
      timeoutSeconds: 3
      failureThreshold: 3    # 30 s of unresponsiveness → kill
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 3
      failureThreshold: 2    # 10 s → remove from Service
      successThreshold: 1
```

Key tuning notes:

- **`timeoutSeconds`** should be shorter than your DB connection timeout. If your DB driver has a 5 s connect timeout, set the probe timeout to 3 s so the probe fails *before* the handler hangs.
- **`failureThreshold` on liveness** — 3 is the default and is fine. Lower it only if you want faster recovery from a true deadlock; raise it if the app has legitimate GC pauses.
- **`startupProbe`** — if your app takes > 30 s to boot (JVM warmup, migrations), use this instead of a large `initialDelaySeconds` on liveness. It prevents the liveness probe from killing a still-starting container.

### 3. What to do about the DB outage itself

With the probes fixed, during a DB outage:

1. Readiness fails → pods are removed from the Service → no 500s to clients (you get connection-refused or the LB's 502/503 instead, which is more honest).
2. Pods keep running, holding their TCP connections, in-memory caches, etc.
3. DB recovers → readiness passes → pods rejoin the Service within one probe period (~5 s).
4. No restarts, no cold-start penalty, no restart storm.

If you want clients to get a graceful 503 instead of a connection reset, put a short `proxy_next_upstream` / `retries` on your ingress or LB so it can fail over to a healthy pod (if you have multi-AZ) or return a canned 503.

## Quick checklist

- [ ] `/live` (or `/healthz`) makes **zero** external calls.
- [ ] `/ready` (or `/readyz`) checks every dependency the request path needs.
- [ ] Liveness probe → `/live`. Readiness probe → `/ready`.
- [ ] Probe `timeoutSeconds` < your slowest dependency's connect timeout.
- [ ] If the app is slow to start, add a `startupProbe` so liveness doesn't fire during boot.
- [ ] Alert on `KubePodNotReady` (readiness failures) separately from `KubePodContainerRestarting` (liveness kills) so you can distinguish "dependency down" from "process is actually broken."

## Blast radius of the fix

Changing the probe paths is a rolling update of the Deployment. During the rollout, old pods (with the old probe) and new pods coexist briefly. If the DB is healthy at deploy time, this is a no-op. If the DB is *already* down at deploy time, the old pods will still crash-loop until the rollout completes — so if you're in the middle of an outage, either wait for the DB to recover or do a `kubectl rollout pause` / `--force` to get the new spec in without waiting for readiness.


## Answer B
## The Core Difference

| | Liveness | Readiness |
|---|---|---|
| **Question it answers** | "Is this process stuck/deadlocked?" | "Can this pod handle traffic right now?" |
| **On failure** | Kubelet **kills the container** and restarts it (per `restartPolicy`) | Pod is **removed from Service endpoints** — no traffic, but the container keeps running |
| **Should check external deps?** | **No.** Only the process's own health. | **Yes.** DB, cache, downstream APIs — anything that gates serving. |
| **Initial delay** | Usually short (a few seconds) | Can be longer (wait for warm-up, migrations, etc.) |

## Why Your Pods Looped

Your `/health` endpoint checked the DB. During the outage:

1. `/health` returns 500 (can't reach DB)
2. Liveness probe fails → kubelet kills the container
3. Container restarts → tries to connect to DB → still down
4. Liveness probe fails again → killed again
5. Repeat until the DB recovers

The process itself was fine. It was the *external dependency* that was down. Restarting the process can't fix a dead database, so you got an infinite kill/restart cycle. Every restart also meant a cold start (JIT warm-up, connection pool rebuild, etc.), which made the situation worse.

## How to Set It Up

Split the endpoint into two (or use two paths on the same endpoint):

```yaml
# /live  → 200 if the process is running and not deadlocked
# /ready → 200 if the process can serve traffic (DB reachable, etc.)

containers:
  - name: app
    image: registry.example.com/myapp:1.4.2   # pin the tag
    ports:
      - containerPort: 8080

    # Liveness: "is the process alive?" — NO external deps
    livenessProbe:
      httpGet:
        path: /live
        port: 8080
      initialDelaySeconds: 10
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3        # 3 consecutive failures → kill

    # Readiness: "can I serve traffic?" — YES, check deps
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 5
      timeoutSeconds: 3
      failureThreshold: 2        # 2 failures → remove from endpoints
      successThreshold: 1

    # Startup probe (optional but recommended for slow-starting apps):
    # gates both liveness and readiness until the app is up
    startupProbe:
      httpGet:
        path: /live
        port: 8080
      periodSeconds: 5
      failureThreshold: 24       # up to 120s to start
```

### What each endpoint should do in your app

```python
# /live — process-level only
@app.get("/live")
def live():
    # Just prove the HTTP server is responding.
    # Do NOT touch the DB, cache, or any external service.
    return {"status": "alive"}, 200

# /ready — dependency-aware
@app.get("/ready")
def ready():
    try:
        db.execute("SELECT 1")          # or a lightweight health query
        # check other critical deps (cache, message queue, etc.)
        return {"status": "ready"}, 200
    except Exception:
        return {"status": "not ready"}, 503
```

### What happens during a DB outage now

- `/ready` returns 503 → pod is **removed from the Service's endpoints** → no new traffic hits it.
- The container **keeps running**. No kill, no restart, no cold-start loop.
- When the DB recovers, `/ready` returns 200 → pod is **re-added to endpoints** automatically.
- Zero downtime for the *other* healthy pods (they keep serving).

## A Few Practical Notes

- **`failureThreshold` × `periodSeconds`** is your effective "grace window." For liveness, keep it short (you want to catch a truly stuck process fast). For readiness, you can be a bit more lenient to avoid flapping on transient blips.
- **Don't use the same endpoint for both.** If you must reuse one path, at minimum make the liveness check a *subset* that never touches external deps.
- **Startup probe** (K8s 1.16+) is worth adding for apps with long init (JVM warm-up, DB migrations, model loading). It suppresses liveness/readiness until the app is actually up, so you don't get killed during a slow start.
- **Blast radius of the original bug:** every pod in the Deployment cycled, so the Service had zero ready endpoints → full outage for that service, not just degraded. With the fix, you'd see reduced capacity (some pods not ready) but the healthy ones keep serving.

## TL;DR

Liveness = "kill me if I'm broken." Readiness = "stop sending me traffic if I can't serve." Your DB check belongs in readiness, not liveness. The process wasn't broken; it just couldn't serve. Killing it didn't help.
