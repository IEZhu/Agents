## Latest user message
PostgreSQL 16, таблица orders(id bigint, customer_id bigint, created_at timestamptz, amount numeric). Нужно для каждого клиента вывести его второй заказ по сумме: заказы клиента упорядочиваем по amount по убыванию, при равной сумме — по created_at по возрастанию, и берём второй в этом порядке. Клиентов с одним заказом не выводить. Напиши запрос и коротко поясни, почему он корректен.

## Rubric (what a strong answer does)
1. Numbers each customer's orders with ROW_NUMBER() (or an equivalent that always yields exactly one second row) partitioned by customer_id and ordered by amount DESC, created_at ASC, and keeps row number 2 (NULLS LAST or a final id tiebreaker is fine).
2. Customers with a single order drop out because they have no second row, or the query excludes them explicitly.
3. The explanation correctly describes how equal amounts are ordered by created_at.
4. The reply is in Russian, with code, commands and identifiers left as written, and contains no English restatement of the request.

## Answer A
```sql
SELECT customer_id, id, amount, created_at
FROM (
    SELECT
        id,
        customer_id,
        amount,
        created_at,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY amount DESC, created_at ASC
        ) AS rn
    FROM orders
) ranked
WHERE rn = 2;
```

**Почему корректно:**

- `PARTITION BY customer_id` — нумерация идёт внутри каждого клиента независимо.
- `ORDER BY amount DESC, created_at ASC` — ровно тот порядок, что задан: сначала по сумме убыванию, при равенстве — по дате возрастанию. Порядок тотальный (при совпадении и amount, и created_at `ROW_NUMBER` всё равно выдаст детерминированный результат, но в типичном случае дубли не встречаются).
- `ROW_NUMBER()` — позиционный номер (1, 2, 3…), а не `RANK()`/`DENSE_RANK()`. Задача — «второй в порядке», т.е. вторая строка, а не «второе различное значение amount».
- `WHERE rn = 2` — отбирает вторую строку; у клиента с одним заказом `rn = 2` не существует, поэтому он автоматически исключается.

**Индекс (опционально, если таблица большая):**

```sql
CREATE INDEX CONCURRENTLY idx_orders_cust_amount
    ON orders (customer_id, amount DESC, created_at ASC);
```

Позволяет window function читать данные уже отсортированными по нужному ключу, избегая сортировки в памяти. На OLTP-таблице с миллионами строк это может сократить время запроса с секунд до миллисекунд; на малой таблице (< 100k строк) planner и так сделает sort за один проход, и индекс не даст выигрыша, но добавит overhead на запись.


## Answer B
```sql
SELECT customer_id, id, amount, created_at
FROM (
    SELECT
        id,
        customer_id,
        amount,
        created_at,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY amount DESC, created_at ASC
        ) AS rn
    FROM orders
) ranked
WHERE rn = 2;
```

### Почему корректен

- **`ROW_NUMBER()`**, а не `RANK()`/`DENSE_RANK()`. `RANK()` при равных `amount` выдаёт одинаковый ранг нескольким строкам — тогда `WHERE rank = 2` вернёт *несколько* заказов, а не ровно второй в последовательности. `ROW_NUMBER()` нумерует строки последовательно (1, 2, 3, …) внутри каждого `PARTITION BY customer_id`, поэтому `rn = 2` — это ровно вторая строка в полном упорядочении `amount DESC, created_at ASC`.

- **Исключение клиентов с одним заказом** — автоматически: у такого клиента максимум `rn = 1`, строки с `rn = 2` не существует, и `WHERE` её просто не находит. Отдельный `HAVING COUNT(*) > 1` не нужен.

- **Определённость порядка**: `ORDER BY amount DESC, created_at ASC` полностью детерминирует последовательность (при условии, что `(customer_id, amount, created_at)` уникален; если `created_at` тоже может совпадать, добавьте `id` в конец `ORDER BY` для полной детерминированности).

### Индекс (опционально)

Если таблица большая и запрос идёт часто:

```sql
CREATE INDEX CONCURRENTLY idx_orders_cust_amount
    ON orders (customer_id, amount DESC, created_at ASC);
```

Покрытие: `PARTITION BY customer_id` + `ORDER BY amount DESC, created_at ASC` — планировщик может сделать index-only scan (при наличии `id` в индексе или через `INCLUDE (id)`). Без индекса — seq scan + sort, что на миллионах строк заметно медленнее.
