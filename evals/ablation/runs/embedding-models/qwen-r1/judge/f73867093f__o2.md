## Answer A
### Diagnosis

«Connection refused» (а не timeout) на внешнем IP при рабочей работе через localhost — в 90 % случаев это **`listen_addresses`**: PostgreSQL слушает только `127.0.0.1` и не принимает TCP на внешнем интерфейсе. Остальные 10 % — firewall с правилом REJECT (не DROP).

### Пошаговая проверка (на сервере `db.local`)

**1. На каком адресе реально слушает PostgreSQL**

```bash
ss -tlnp | grep 5432
```

Ожидаемый «здоровый» вывод:

```
LISTEN  0  24  0.0.0.0:5432  0.0.0.0:*  users:(("postgres",pid=1234,fd=7))
```

Если видите `127.0.0.1:5432` — причина найдена: сервер привязан только к loopback.

**2. Конфиг `listen_addresses`**

```bash
# Найти активный конфиг
psql -U postgres -c "SHOW config_file;"
# или
sudo cat /etc/postgresql/*/main/postgresql.conf | grep -n listen_addresses
```

Если строка закомментирована или равна `'localhost'` / `'127.0.0.1'` — PostgreSQL по умолчанию слушает только loopback.

**3. Firewall**

```bash
# nftables (Debian 12+, RHEL 9+)
sudo nft list ruleset | grep 5432

# iptables (старее)
sudo iptables -L INPUT -n --line-numbers | grep 5432

# ufw (Ubuntu)
sudo ufw status | grep 5432
```

Правило `REJECT` даст именно «connection refused». `DROP` дал бы timeout — раз у вас refused, либо REJECT, либо порт просто не открыт (п. 1).

**4. SELinux (RHEL / CentOS / Fedora)**

```bash
sudo getenforce
sudo ausearch -m avc -ts recent | grep postgres
```

Если `Enforcing` и есть AVC-записи — SELinux блокирует bind на внешний адрес.

### Решение (если `listen_addresses` — причина)

```bash
# 1. Бэкап конфига (на всякий случай)
sudo cp /etc/postgresql/16/main/postgresql.conf{,.bak}

# 2. Разрешить слушать на всех интерфейсах
#    (или конкретный IP, если не нужен доступ со всех)
sudo sed -i "s/^#listen_addresses = 'localhost'/listen_addresses = '*'/" \
  /etc/postgresql/16/main/postgresql.conf

# 3. Перезапуск (не reload — listen_addresses требует restart)
sudo systemctl restart postgresql

# 4. Подтвердить
ss -tlnp | grep 5432
# → 0.0.0.0:5432
```

> **Важно:** `listen_addresses` — параметр, требующий **restart**, а не `pg_reload_conf()`.

### После открытия порта — `pg_hba.conf`

Без записи в `pg_hba.conf` вы получите уже другое сообщение: *«no pg_hba.conf entry for host "192.168.1.x", user "app", no encryption»*. Добавьте:

```
# /etc/postgresql/16/main/pg_hba.conf
# TYPE  DATABASE  USER  ADDRESS         METHOD
host    all       app   192.168.1.0/24  scram-sha-256
```

Затем `sudo systemctl reload postgresql` (для `pg_hba.conf` reload достаточно).

### Быстрая проверка с клиента

```bash
# До перезапуска — должно быть refused:
nc -zv db.local 5432

# После — должно быть "succeeded":
nc -zv db.local 5432
```

### Итого — порядок действий

| # | Что | Команда |
|---|-----|---------|
| 1 | Где слушает | `ss -tlnp \| grep 5432` |
| 2 | Конфиг | `grep listen_addresses postgresql.conf` |
| 3 | Firewall | `nft list ruleset \| grep 5432` |
| 4 | SELinux | `getenforce` + `ausearch` |
| 5 | Исправить + restart | см. выше |
| 6 | `pg_hba.conf` | добавить запись, reload |
| 7 | Тест | `psql -h db.local -p 5432 -U app` |

В 9 случаях из 10 останавливаетесь на шаге 2.


## Answer B
**Самая вероятная причина:** PostgreSQL слушает только `localhost` (127.0.0.1), а не внешний интерфейс. Параметр `listen_addresses` по умолчанию равен `'localhost'`, поэтому TCP-соединение на 192.168.1.20:5432 получает RST → «connection refused».

Проверяйте по порядку:

### 1. На чём слушает PostgreSQL

```bash
# На сервере (db.local / 192.168.1.20)
ss -tlnp | grep 5432
# или
netstat -tlnp | grep 5432
```

Если видите `127.0.0.1:5432` — подтверждено: слушает только loopback. Должно быть `0.0.0.0:5432` или `*:5432`.

Исправление в `postgresql.conf` (обычно `/etc/postgresql/<ver>/<cluster>/postgresql.conf` или `/var/lib/pgsql/data/postgresql.conf`):

```ini
listen_addresses = '*'          # или конкретный IP: '192.168.1.20'
```

Перезапуск:

```bash
sudo systemctl restart postgresql
```

> **Trade-off:** `'*'` открывает порт на всех интерфейсах. Если сервер в DMZ или за NAT — допустимо. В противном случае лучше указать конкретный IP.

### 2. Файрвол

Даже после исправления `listen_addresses` порт может быть закрыт:

```bash
# UFW (Ubuntu/Debian)
sudo ufw status | grep 5432

# nftables / iptables
sudo nft list ruleset | grep 5432
sudo iptables -L -n | grep 5432
```

Если правила отсутствуют или порт не в allow-списке:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 5432 proto tcp
# или для nftables/iptables — соответствующее правило
```

> «Connection refused» (а не timeout) говорит, что RST доходит — значит, либо сам PostgreSQL не слушает на этом интерфейсе (пункт 1), либо в файрволе правило `REJECT` (а не `DROP`).

### 3. pg_hba.conf (после того как TCP-соединение заработает)

Это **не** причина текущего «refused», но без записи здесь вы получите `FATAL: no pg_hba.conf entry for host "192.168.1.20"`. Добавьте:

```
# TYPE  DATABASE  USER  ADDRESS          METHOD
host    all       app   192.168.1.0/24   scram-sha-256
```

Перезапуск не нужен — достаточно:

```bash
sudo systemctl reload postgresql
```

### 4. Быстрая проверка с клиента

```bash
# TCP-уровень: порт вообще открыт?
nc -zv 192.168.1.20 5432
# или
timeout 3 bash -c 'echo > /dev/tcp/192.168.1.20/5432' && echo OK || echo CLOSED
```

Если `nc` говорит «Connection refused» — проблема на стороне сервера (пункты 1–2). Если «timed out» — файрвол с `DROP`.

### 5. SELinux / AppArmor (редко, но бывает)

```bash
# RHEL/CentOS
sudo getenforce
sudo ausearch -m avc -ts recent | grep postgres

# Ubuntu
sudo aa-status | grep postgres
```

Если SELinux в enforcing-режиме и есть deny-записи — либо `setenforce 0` для диагностики, либо добавить policy.

---

**Коротко:** в 90 % случаев это `listen_addresses = 'localhost'` в `postgresql.conf`. Один `ss -tlnp | grep 5432` на сервере подтвердит или опровергнет за секунду.
