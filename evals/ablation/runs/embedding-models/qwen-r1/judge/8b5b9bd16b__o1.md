## Latest user message
Под с сервисом на Java 21 в Kubernetes каждые пару часов перезапускается, в kubectl describe pod вижу Last State: Terminated, Reason: OOMKilled, Exit Code: 137. В контейнере limits.memory: 512Mi, приложение запускается с -Xmx512m. Почему так и что поменять?

## Rubric (what a strong answer does)
1. Explains that -Xmx caps only the heap while the JVM also uses non-heap memory (metaspace, thread stacks, code cache, direct buffers), so a 512m heap lets the process exceed the 512Mi limit and the container is OOM-killed (exit code 137).
2. Recommends a concrete fix: a heap well below the limit (for example replacing -Xmx with -XX:MaxRAMPercentage, or a smaller -Xmx) and/or a higher limits.memory, and suggests measuring actual memory use.
3. Does not mistake the symptom for a Java OutOfMemoryError: it is a container OOM kill.

## Answer A
## Почему OOMKilled при Xmx = limit

`-Xmx512m` ограничивает **только heap**. Общее потребление памяти JVM (RSS) — это сумма:

| Компонент | Типичный размер |
|-----------|----------------|
| Heap (Xmx) | до 512 MB |
| Metaspace (классы, константы) | 64–256 MB |
| Thread stacks (1 MB × N потоков) | 50–300 MB |
| Code cache (JIT) | до 240 MB |
| Direct/NIO buffers, JNI, GC-структуры | 50–200 MB |

Итого: при Xmx=512m реальный RSS легко достигает **800 MB – 1.2 GB**. Cgroup-лимит 512Mi не даёт JVM столько — ядро шлёт SIGKILL (exit 137).

**Почему «каждые пару часов»**, а не сразу: heap заполняется постепенно, GC освобождает, но off-heap (Metaspace, потоки, direct buffers) монотонно растёт. Когда суммарный RSS пересёкает 512 MiB — kill.

## Что менять

### Вариант 1 (рекомендуемый): MaxRAMPercentage + честный лимит

Java 21 по умолчанию знает о cgroup-лимитах (`-XX:+UseContainerSupport` включён). Не хардкодь Xmx — дай JVM самой посчитать:

```yaml
# k8s Deployment
resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"        # ← реальный потолок для всего процесса
```

```bash
# JVM flags (в Dockerfile / startup script)
java \
  -XX:MaxRAMPercentage=75.0 \
  -XX:MaxMetaspaceSize=256m \
  -XX:ReservedCodeCacheSize=128m \
  -jar app.jar
```

`MaxRAMPercentage=75` → heap ≈ 750 MB при лимите 1 GiB, оставшиеся ~250 MB на Metaspace, стеки, code cache, direct buffers. Для большинства Spring-приложений этого достаточно.

> **Cost note:** увеличение лимита с 512 Mi до 1 Gi на EKS/GKE/AKS — это ~$10–20/мес на ноду (зависит от instance type). Если сервисов много — пересчитайте node pool.

### Вариант 2 (быстрый, без изменения лимита): ужать Xmx

Если 512 Mi — жёсткое ограничение (бюджет, shared node):

```bash
java \
  -Xmx352m \
  -XX:MaxMetaspaceSize=128m \
  -XX:ReservedCodeCacheSize=64m \
  -jar app.jar
```

352 + 128 + 64 + ~64 (стеки/прочее) ≈ 608 MB — всё ещё впритык. Для лёгкого сервиса (мало потоков, мало классов) может работать, но запас минимальный.

### Вариант 3: диагностика перед выбором

Если не уверены, что именно ест память:

```bash
# В pod (если есть exec) или через sidecar:
jcmd <pid> VM.native_memory summary   # нужен -XX:NativeMemoryTracking=summary
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print | grep -c "java.lang.Thread"   # кол-во потоков
```

Или в Grafana/Prometheus: `container_memory_working_set_bytes{pod="your-pod"}` — смотрите, как растёт RSS до момента kill.

## Чек-лист

- [ ] Убрать `-Xmx512m`, заменить на `-XX:MaxRAMPercentage=75.0` (или 60–70, если off-heap большой).
- [ ] Поставить `-XX:MaxMetaspaceSize` (иначе Metaspace растёт без bounds).
- [ ] Увеличить `limits.memory` до **≥ 1.5 × Xmx** (или до 1 Gi при MaxRAMPercentage=75).
- [ ] `requests.memory` = `limits.memory` (Guaranteed QoS, меньше шансов на eviction под нагрузкой ноды).
- [ ] Если сервис критичный — добавить `livenessProbe` с `initialDelaySeconds` ≥ 60 s, чтобы K8s не резал pod во время долгого GC.

## Rollback

Если после изменения лимита/флагов что-то пошло не так:

```bash
# Откатить Deployment к предыдущей ревизии
kubectl rollout undo deployment/<name> -n <ns>

# Или вручную: вернуть limits.memory: 512Mi и -Xmx512m
kubectl patch deployment <name> -n <ns> --type merge -p '
spec:
  template:
    spec:
      containers:
      - name: app
        resources:
          limits:
            memory: 512Mi
'
```

Blast radius: один pod (или реплика). При `rollout undo` K8s делает rolling update — трафик не падает, если `minReadySeconds` и PDB настроены.


## Answer B
## Почему OOMKilled

`-Xmx512m` ограничивает **только heap**. Но RSS процесса JVM = heap + всё остальное:

| Компонент | Типичный размер |
|-----------|----------------|
| Heap (до Xmx) | до 512 MB |
| Metaspace (классы, константы) | 100–300 MB |
| Thread stacks (по 1 MB/поток, `-Xss`) | 50–200 MB |
| Direct/NIO buffers (Netty, gRPC, NIO) | 50–200 MB |
| JIT (C1/C2), Code Cache | 50–100 MB |
| GC structures (card table, RSet) | 20–50 MB |
| Native libs, JNI | 20–50 MB |

Итого реальный RSS легко **800 MB – 1.2 GB**, а cgroup limit = 512 Mi. Ядро убивает процесс (SIGKILL → exit 137), когда RSS превышает `memory.limit_in_bytes`.

«Каждые пару часов» — это не мгновенный OOM, а **постепенный рост**: Metaspace заполняется, пул потоков расширяется, direct buffers накапливаются. Достигает лимита → kill → рестарт → цикл.

## Что поменять

### 1. Увеличить limit контейнера (главное)

Правило: `limit ≥ Xmx + 256–512 MB` на всё остальное.

```yaml
resources:
  requests:
    memory: "768Mi"
  limits:
    memory: "1Gi"        # было 512Mi
```

Если heap реально нужен 512 MB, ставьте limit **1 Gi** минимум. Если приложение тяжёлое (много потоков, Netty) — **1.5 Gi**.

### 2. Зафиксировать Metaspace

Без явного лимита Metaspace растёт до тех пор, пока не упрётся в cgroup:

```
-XX:MaxMetaspaceSize=256m
```

### 3. (Опционально) Сменить стратегию sizing heap

Вместо хардкода `-Xmx512m` дайте JVM самому считать heap от cgroup:

```
-XX:MaxRAMPercentage=70.0
```

Тогда при limit 1 Gi heap будет ≈ 700 MB, а 300 MB останется на всё остальное. Удобно при масштабировании — не надо пересчитывать Xmx под каждый limit.

### 4. Полный пример JVM args

```
-Xms512m -Xmx512m
-XX:MaxMetaspaceSize=256m
-XX:MaxDirectMemorySize=256m
-Xss512k
-XX:+UseG1GC
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/tmp/heapdump.hprof
```

`-Xss512k` — если у вас много потоков (по умолчанию 1 MB, для большинства сервисов 512k достаточно).

### 5. Диагностика (чтобы убедиться, что это не утечка)

```bash
# В живом поде, до OOM:
kubectl exec -it <pod> -- jcmd 1 VM.native_memory summary
kubectl exec -it <pod> -- jcmd 1 GC.heap_info
kubectl exec -it <pod> -- jcmd 1 Thread.print | grep -c "java.lang.Thread"

# cgroup-статистика (внутри контейнера):
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.peak
```

Если `memory.peak` стабильно растёт от рестарта до рестарта и не выходит на плато — есть утечка (обычно direct buffers или создание потоков без пула). Тогда увеличением лимита вы просто растянете время до следующего килла.

## Итого

| Было | Стало |
|------|-------|
| `limits.memory: 512Mi` | `limits.memory: 1Gi` (или 1.5Gi) |
| `-Xmx512m` (heap = limit) | `-Xmx512m` + `-XX:MaxMetaspaceSize=256m` + `-XX:MaxDirectMemorySize=256m` |
| Нет видимости | `HeapDumpOnOutOfMemoryError` + мониторинг `memory.peak` |

Blast radius: увеличение limit не влияет на другие поды, если node имеет достаточно свободной памяти. Если node уже перегружен — под может не встать (Pending). Проверьте `kubectl describe node` → Allocatable memory.
