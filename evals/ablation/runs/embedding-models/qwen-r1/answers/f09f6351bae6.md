## Почему OOMKilled

`-Xmx512m` ограничивает **только heap**. Но RSS процесса JVM = heap + всё остальное:

| Компонент | Типичный размер |
|-----------|----------------|
| Heap (до Xmx) | до 512 MB |
| Metaspace (классы, константы) | 100–300 MB |
| Thread stacks (по 1 MB/поток, `-Xss`) | 50–200 MB |
| Direct/NIO buffers (Netty, gRPC, NIO) | 50–200 MB |
| JIT (C1/C2), Code Cache | 50–100 MB |
| GC structures (card table, RSet) | 20–50 MB |
| Native libs, JNI | 20–50 MB |

Итого реальный RSS легко **800 MB – 1.2 GB**, а cgroup limit = 512 Mi. Ядро убивает процесс (SIGKILL → exit 137), когда RSS превышает `memory.limit_in_bytes`.

«Каждые пару часов» — это не мгновенный OOM, а **постепенный рост**: Metaspace заполняется, пул потоков расширяется, direct buffers накапливаются. Достигает лимита → kill → рестарт → цикл.

## Что поменять

### 1. Увеличить limit контейнера (главное)

Правило: `limit ≥ Xmx + 256–512 MB` на всё остальное.

```yaml
resources:
  requests:
    memory: "768Mi"
  limits:
    memory: "1Gi"        # было 512Mi
```

Если heap реально нужен 512 MB, ставьте limit **1 Gi** минимум. Если приложение тяжёлое (много потоков, Netty) — **1.5 Gi**.

### 2. Зафиксировать Metaspace

Без явного лимита Metaspace растёт до тех пор, пока не упрётся в cgroup:

```
-XX:MaxMetaspaceSize=256m
```

### 3. (Опционально) Сменить стратегию sizing heap

Вместо хардкода `-Xmx512m` дайте JVM самому считать heap от cgroup:

```
-XX:MaxRAMPercentage=70.0
```

Тогда при limit 1 Gi heap будет ≈ 700 MB, а 300 MB останется на всё остальное. Удобно при масштабировании — не надо пересчитывать Xmx под каждый limit.

### 4. Полный пример JVM args

```
-Xms512m -Xmx512m
-XX:MaxMetaspaceSize=256m
-XX:MaxDirectMemorySize=256m
-Xss512k
-XX:+UseG1GC
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/tmp/heapdump.hprof
```

`-Xss512k` — если у вас много потоков (по умолчанию 1 MB, для большинства сервисов 512k достаточно).

### 5. Диагностика (чтобы убедиться, что это не утечка)

```bash
# В живом поде, до OOM:
kubectl exec -it <pod> -- jcmd 1 VM.native_memory summary
kubectl exec -it <pod> -- jcmd 1 GC.heap_info
kubectl exec -it <pod> -- jcmd 1 Thread.print | grep -c "java.lang.Thread"

# cgroup-статистика (внутри контейнера):
cat /sys/fs/cgroup/memory.current
cat /sys/fs/cgroup/memory.peak
```

Если `memory.peak` стабильно растёт от рестарта до рестарта и не выходит на плато — есть утечка (обычно direct buffers или создание потоков без пула). Тогда увеличением лимита вы просто растянете время до следующего килла.

## Итого

| Было | Стало |
|------|-------|
| `limits.memory: 512Mi` | `limits.memory: 1Gi` (или 1.5Gi) |
| `-Xmx512m` (heap = limit) | `-Xmx512m` + `-XX:MaxMetaspaceSize=256m` + `-XX:MaxDirectMemorySize=256m` |
| Нет видимости | `HeapDumpOnOutOfMemoryError` + мониторинг `memory.peak` |

Blast radius: увеличение limit не влияет на другие поды, если node имеет достаточно свободной памяти. Если node уже перегружен — под может не встать (Pending). Проверьте `kubectl describe node` → Allocatable memory.
