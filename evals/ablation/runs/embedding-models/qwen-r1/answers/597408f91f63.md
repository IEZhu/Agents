## Почему OOMKilled при Xmx = limit

`-Xmx512m` ограничивает **только heap**. Общее потребление памяти JVM (RSS) — это сумма:

| Компонент | Типичный размер |
|-----------|----------------|
| Heap (Xmx) | до 512 MB |
| Metaspace (классы, константы) | 64–256 MB |
| Thread stacks (1 MB × N потоков) | 50–300 MB |
| Code cache (JIT) | до 240 MB |
| Direct/NIO buffers, JNI, GC-структуры | 50–200 MB |

Итого: при Xmx=512m реальный RSS легко достигает **800 MB – 1.2 GB**. Cgroup-лимит 512Mi не даёт JVM столько — ядро шлёт SIGKILL (exit 137).

**Почему «каждые пару часов»**, а не сразу: heap заполняется постепенно, GC освобождает, но off-heap (Metaspace, потоки, direct buffers) монотонно растёт. Когда суммарный RSS пересёкает 512 MiB — kill.

## Что менять

### Вариант 1 (рекомендуемый): MaxRAMPercentage + честный лимит

Java 21 по умолчанию знает о cgroup-лимитах (`-XX:+UseContainerSupport` включён). Не хардкодь Xmx — дай JVM самой посчитать:

```yaml
# k8s Deployment
resources:
  requests:
    memory: "512Mi"
  limits:
    memory: "1Gi"        # ← реальный потолок для всего процесса
```

```bash
# JVM flags (в Dockerfile / startup script)
java \
  -XX:MaxRAMPercentage=75.0 \
  -XX:MaxMetaspaceSize=256m \
  -XX:ReservedCodeCacheSize=128m \
  -jar app.jar
```

`MaxRAMPercentage=75` → heap ≈ 750 MB при лимите 1 GiB, оставшиеся ~250 MB на Metaspace, стеки, code cache, direct buffers. Для большинства Spring-приложений этого достаточно.

> **Cost note:** увеличение лимита с 512 Mi до 1 Gi на EKS/GKE/AKS — это ~$10–20/мес на ноду (зависит от instance type). Если сервисов много — пересчитайте node pool.

### Вариант 2 (быстрый, без изменения лимита): ужать Xmx

Если 512 Mi — жёсткое ограничение (бюджет, shared node):

```bash
java \
  -Xmx352m \
  -XX:MaxMetaspaceSize=128m \
  -XX:ReservedCodeCacheSize=64m \
  -jar app.jar
```

352 + 128 + 64 + ~64 (стеки/прочее) ≈ 608 MB — всё ещё впритык. Для лёгкого сервиса (мало потоков, мало классов) может работать, но запас минимальный.

### Вариант 3: диагностика перед выбором

Если не уверены, что именно ест память:

```bash
# В pod (если есть exec) или через sidecar:
jcmd <pid> VM.native_memory summary   # нужен -XX:NativeMemoryTracking=summary
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print | grep -c "java.lang.Thread"   # кол-во потоков
```

Или в Grafana/Prometheus: `container_memory_working_set_bytes{pod="your-pod"}` — смотрите, как растёт RSS до момента kill.

## Чек-лист

- [ ] Убрать `-Xmx512m`, заменить на `-XX:MaxRAMPercentage=75.0` (или 60–70, если off-heap большой).
- [ ] Поставить `-XX:MaxMetaspaceSize` (иначе Metaspace растёт без bounds).
- [ ] Увеличить `limits.memory` до **≥ 1.5 × Xmx** (или до 1 Gi при MaxRAMPercentage=75).
- [ ] `requests.memory` = `limits.memory` (Guaranteed QoS, меньше шансов на eviction под нагрузкой ноды).
- [ ] Если сервис критичный — добавить `livenessProbe` с `initialDelaySeconds` ≥ 60 s, чтобы K8s не резал pod во время долгого GC.

## Rollback

Если после изменения лимита/флагов что-то пошло не так:

```bash
# Откатить Deployment к предыдущей ревизии
kubectl rollout undo deployment/<name> -n <ns>

# Или вручную: вернуть limits.memory: 512Mi и -Xmx512m
kubectl patch deployment <name> -n <ns> --type merge -p '
spec:
  template:
    spec:
      containers:
      - name: app
        resources:
          limits:
            memory: 512Mi
'
```

Blast radius: один pod (или реплика). При `rollout undo` K8s делает rolling update — трафик не падает, если `minReadySeconds` и PDB настроены.
