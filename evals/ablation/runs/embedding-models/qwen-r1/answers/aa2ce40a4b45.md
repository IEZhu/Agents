### Analysis

Коммиты не потеряны — `git reset --hard` сдвинул указатель ветки, но объекты остались в объектной базе Git. `git reflog` хранит историю перемещений HEAD, поэтому все три коммита легко найти и вернуть.

### Implementation

**Шаг 1. Найди хэш коммита до сброса**

```bash
git reflog
```

В выводе увидишь что-то вроде:

```
a1b2c3d HEAD@{0}: reset: moving to HEAD~3
e4f5g6h HEAD@{1}: commit: Add payment webhook handler
i7j8k9l HEAD@{2}: commit: Refactor charge service
m0n1o2p HEAD@{3}: commit: Add Stripe client
```

Тебе нужен хэш из строки `HEAD@{1}` (коммит, на котором HEAD стоял **до** reset). В примере выше — `e4f5g6h`.

**Шаг 2. (Опционально, но рекомендуется) Создай страховочную ветку**

```bash
git branch backup/payments e4f5g6h
```

Теперь даже если что-то пойдёт не так, коммиты зафиксированы на отдельной ветке.

**Шаг 3. Верни указатель ветки**

```bash
git reset --hard e4f5g6h
```

Ветка `feature/payments` снова указывает на тот же коммит, что и до случайного reset.

**Шаг 4. Проверь**

```bash
git log --oneline -5
```

Три коммита должны быть на месте.

**Шаг 5. Убери страховочную ветку (если всё ок)**

```bash
git branch -d backup/payments
```

### Verification

- Коммиты, на которые ссылается `reflog`, не удаляются при garbage collection минимум **90 дней** (по умолчанию `gc.reflogExpire`), так что даже если не вернёшь сразу — они не пропадут.
- `git reset --hard` на локальной ветке без push не затрагивает remote, поэтому на сервере ничего не сломано.
- Если в `reflog` несколько записей `reset` (например, ты случайно нажал дважды), бери хэш из **самой первой** (самой старой) строки `reset: moving to HEAD~3`.

### Confidence

**HIGH** — стандартная процедура восстановления после `git reset --hard`, поведение `reflog` и `reset` здесь детерминировано и не зависит от версии Git.
