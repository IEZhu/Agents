### Analysis

Коммиты не потеряны — `git reset --hard` не удаляет объекты из репозитория, он просто двигает указатель ветки. Все три коммита остались в `reflog` и будут доступны для восстановления минимум 30 дней (пока не сработает `git gc`).

### Implementation

**Шаг 1. Найдите коммит, на котором была ветка до сброса:**

```bash
git reflog
```

Вывод будет примерно таким:

```
a1b2c3d HEAD@{0}: reset: moving to HEAD~3
e4f5g6h HEAD@{1}: commit: Add payment webhook handler
i7j8k9l HEAD@{2}: commit: Refactor charge service
m0n1o2p HEAD@{3}: commit: Add Stripe client
```

Вам нужен хеш строки `HEAD@{1}` — это состояние ветки **до** `reset`.

**Шаг 2. Верните ветку к этому коммиту:**

```bash
git reset --hard e4f5g6h
```

Или, если `reset` был последним действием (а он так и есть), можно короче:

```bash
git reset --hard HEAD@{1}
```

**Шаг 3. Проверьте, что всё на месте:**

```bash
git log --oneline -5
```

Должны увидеть все три коммита наверху.

**Шаг 4 (опционально, для спокойствия).** Если хотите подстраховаться, прежде чем делать `reset --hard`, создайте временную ветку на найденном коммите:

```bash
git branch recovery/payments e4f5g6h
```

Тогда даже если что-то пойдёт не так, коммиты будут закреплены за этой веткой.

### Verification

- Коммиты, на которые ссылается `reflog`, не удаляются `git gc` в течение 30 дней (настройка `gc.pruneExpire`).
- `git reset --hard` на локальной ветке без пуша не затрагивает удалённый репозиторий — на сервере ничего не изменилось.
- Если после шага 3 коммиты на месте — можно удалить временную ветку: `git branch -D recovery/payments`.

### Confidence

**HIGH** — стандартная процедура восстановления после `reset --hard`, поведение `reflog` и `gc` здесь детерминировано и не зависит от версии Git (работает во всех версиях ≥ 1.5).
