## Latest user message
PostgreSQL 16, таблица orders(id bigint, customer_id bigint, created_at timestamptz, amount numeric). Нужно для каждого клиента вывести его второй заказ по сумме: заказы клиента упорядочиваем по amount по убыванию, при равной сумме — по created_at по возрастанию, и берём второй в этом порядке. Клиентов с одним заказом не выводить. Напиши запрос и коротко поясни, почему он корректен.

## Rubric (what a strong answer does)
1. Numbers each customer's orders with ROW_NUMBER() (or an equivalent that always yields exactly one second row) partitioned by customer_id and ordered by amount DESC, created_at ASC, and keeps row number 2 (NULLS LAST or a final id tiebreaker is fine).
2. Customers with a single order drop out because they have no second row, or the query excludes them explicitly.
3. The explanation correctly describes how equal amounts are ordered by created_at.
4. The reply is in Russian, with code, commands and identifiers left as written, and contains no English restatement of the request.

## Answer A
```sql
SELECT customer_id, id, amount, created_at
FROM (
    SELECT
        id, customer_id, created_at, amount,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY amount DESC, created_at ASC
        ) AS rn
    FROM orders
) ranked
WHERE rn = 2;
```

### Почему корректно

- **`PARTITION BY customer_id`** — окно (сортировка, нумерация) считается отдельно для каждого клиента.
- **`ORDER BY amount DESC, created_at ASC`** — в точности ваш порядок: сначала по сумме убывание, при равенстве — по дате возрастание.
- **`ROW_NUMBER()`** — присваивает строго последовательные номера 1, 2, 3… внутри каждого окна. Даже при полном совпадении `amount` и `created_at` каждая строка получает уникальный номер (порядок между дублями неопределён, но номер один).
- **`WHERE rn = 2`** — отбирает ровно вторую строку. Клиент с единственным заказом имеет лишь `rn = 1`, поэтому отсекается без дополнительного `HAVING COUNT(*) > 1`.

### Мелочь про индексы

Для больших таблиц (миллионы строк) полезно иметь индекс, который покрывает сортировку окна:

```sql
CREATE INDEX CONCURRENTLY idx_orders_cust_amount
    ON orders (customer_id, amount DESC, created_at ASC);
```

Это не гарантирует, что планёр пойдёт по индексу вместо сортировки (зависит от статистики и размера выборки), но при умеренном количестве строк на клиента даёт шанс избежать full sort. В любом случае — `CREATE INDEX CONCURRENTLY`, чтобы не блокировать запись.

Проверка:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, id, amount, created_at
FROM (
    SELECT id, customer_id, created_at, amount,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY amount DESC, created_at ASC
           ) AS rn
    FROM orders
) ranked
WHERE rn = 2;
```

Смотрите, сортировка идёт через `Sort` или через `Index Scan` — это покажет, работает ли новый индекс на ваш workload.


## Answer B
```sql
SELECT customer_id, id, amount, created_at
FROM (
    SELECT
        customer_id,
        id,
        amount,
        created_at,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY amount DESC, created_at ASC
        ) AS rn
    FROM orders
) ranked
WHERE rn = 2;
```

### Почему корректен

- **`PARTITION BY customer_id`** — нумерация идёт независимо внутри каждого клиента.
- **`ORDER BY amount DESC, created_at ASC`** — ровно тот порядок, что задан: сначала по сумме убывающей, при равенстве — по дате возрастающей. Это тотальный порядок (на практике `timestamptz` с микросекундной точностью не даёт коллизий; если хотите гарантию — добавьте `id` в конец `ORDER BY`).
- **`ROW_NUMBER()`**, а не `RANK()` / `DENSE_RANK()` — мы хотим *второй элемент в упорядоченном списке*, а не «все строки со второй суммой». При равных `amount` разный `created_at` даёт разные позиции, и нам нужна именно вторая.
- **`WHERE rn = 2`** — автоматически исключает клиентов с одним заказом (у них максимум `rn = 1`, строки со `rn = 2` не существует). Отдельный `HAVING` или подзапрос на `COUNT` не нужны.

### Нюанс детерминизма

Если в пределах одного клиента возможны два заказа с одинаковым `amount` **и** одинаковым `created_at`, порядок между ними недетерминирован. Если это критично, допишите `id ASC` в `ORDER BY`:

```sql
ORDER BY amount DESC, created_at ASC, id ASC
```

### Performance-замечание

Для таблицы без миллионов строк запрос отработает за один sequential scan + sort. При большом объёме (`orders` > десятки млн строк) убедитесь, что есть индекс:

```sql
CREATE INDEX CONCURRENTLY idx_orders_customer_amount
    ON orders (customer_id, amount DESC, created_at ASC);
```

Это позволит планировщику использовать index scan вместо sort, но при этом увеличит время на запись. Оправдано, если запрос частый и таблица большая.
