## Latest user message
What's the actual difference between readiness and liveness probes in Kubernetes? We had a liveness probe hitting /health that checks the database, and during a DB outage all our pods restarted in a loop. Why, and how should we set it up?

## Rubric (what a strong answer does)
1. A failing readiness probe removes the pod from Service endpoints without a restart; a failing liveness probe makes the kubelet restart the container.
2. Explains that the database check in the liveness probe turned a dependency outage into restarts of every pod, and keeps liveness to the process itself.
3. Mentions a sensible setting such as a startup probe, initialDelaySeconds or failureThreshold.

## Answer A
The core distinction is what question each probe asks of the kubelet:

- **Liveness**: "Is this container wedged, and should I kill it and start a fresh one?" A failure triggers a **restart**.
- **Readiness**: "Can this container accept traffic right now?" A failure removes the pod from the **Service endpoints** (and from Ingress backends, etc.). The container keeps running.

That's the entire semantic split. One is self-healing (restart), the other is traffic gating (drain).

## Why your incident happened

Your liveness probe hit `/health`, which returned non-200 when the DB was unreachable. The kubelet interpreted that as "container is broken," killed it, and restarted it. The DB was still down, so the new container's first `/health` check also failed, and the cycle repeated — a restart loop with no recovery path, because **restarting the app container doesn't fix the database**.

You also lost all serving capacity during the outage. Even if some requests could have been served (cached data, non-DB endpoints, graceful degradation), every pod was in `CrashLoopBackOff` or mid-restart, so the Service had zero endpoints the whole time. When the DB came back, you got a thundering-herd connection spike as all pods came up simultaneously.

The mistake is putting a **dependency check** in a **process-alive** probe. The liveness probe should answer "is the process itself healthy (not deadlocked, not OOM-killed, event loop still turning?)" — not "are all upstream services reachable."

## How to set it up

Split the health endpoint into two (or more):

```
GET /healthz/live   → 200 if the process can respond to HTTP. No external calls.
GET /healthz/ready  → 200 if DB + cache + any other required deps are reachable.
```

If your app only exposes a single `/health`, the minimal fix is to use a different probe type for liveness — a TCP socket check on the listen port, or a dedicated lightweight endpoint. But the proper fix is splitting the endpoint in code.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-service
spec:
  containers:
    - name: app
      image: registry.example.com/my-service:1.4.2   # pin the tag
      ports:
        - containerPort: 8080
      startupProbe:                    # optional: gives slow-init apps grace
        httpGet:
          path: /healthz/ready
          port: 8080
        periodSeconds: 5
        failureThreshold: 24           # 120 s to boot before liveness kicks in
      livenessProbe:
        httpGet:
          path: /healthz/live
          port: 8080
        periodSeconds: 10
        failureThreshold: 3            # 30 s of being truly wedged → restart
        timeoutSeconds: 3
      readinessProbe:
        httpGet:
          path: /healthz/ready
          port: 8080
        periodSeconds: 5
        failureThreshold: 2            # ~10 s → remove from endpoints
        timeoutSeconds: 3
```

### Tuning rationale

| Parameter | Liveness | Readiness | Why |
|-----------|----------|-----------|-----|
| `periodSeconds` | 10 | 5 | Liveness: you don't want to kill pods on transient 5 s blips. Readiness: you want traffic drained quickly. |
| `failureThreshold` | 3 | 2 | Liveness: 3 consecutive failures = 30 s before restart. Readiness: 2 = 10 s to stop routing. |
| `timeoutSeconds` | 3 | 3 | Short so a hung TCP doesn't block the probe thread. |
| `startupProbe` | — | — | Prevents liveness from firing during slow init (JVM warmup, schema migration, large cache load). |

### What `/healthz/live` should check (and not check)

**Should:**
- Process is running and the HTTP server can accept a connection.
- (If relevant) goroutine/event-loop is not deadlocked.
- (If relevant) a simple internal invariant, e.g. "the request handler registered itself."

**Should not:**
- Query the database.
- Call external microservices.
- Check disk space or memory (those are resource-pressure signals, not "am I alive" signals).
- Do any I/O with a timeout > 1 s.

### What `/healthz/ready` should check

- DB: a lightweight query (`SELECT 1` or a prepared-pool ping), not a full table scan.
- Cache (Redis/Memcached): `PING`.
- Any downstream service that is a **hard** prerequisite for serving requests.
- Return 503 (not 500) when a dependency is down — semantically correct and lets you distinguish "app bug" from "dependency unavailable" in logs.

### If you can't change the app code immediately

As a stopgap, switch liveness to a TCP check so it only verifies the port is listening:

```yaml
livenessProbe:
  tcpSocket:
    port: 8080
  periodSeconds: 10
  failureThreshold: 3
```

This won't catch a deadlocked process that still holds the socket open, but it stops the DB-outage restart loop. It's a band-aid, not a fix.

## Deployment / rollout notes

- If you're running this behind a HPA and the DB outage causes all pods to become NotReady at once, the HPA will scale out new pods that also can't become Ready — a feedback loop. Make sure your HPA has a `minReplicas` floor and consider `stabilizationWindowSeconds` to prevent flapping.
- If you're on ArgoCD or Flux, a rolling update of the Deployment with the new probe spec is safe: `maxUnavailable: 1` (or `0` with `maxSurge: 1`) ensures old pods keep serving until new pods pass readiness.
- Blast radius of changing probes on a live Deployment: during the rollout, if the new liveness is stricter than the old one, you could transiently lose pods. Do it during a low-traffic window or with `maxUnavailable: 0`.

## The core semantic difference

They answer two different questions to two different "clients":

| Probe | Question | Who acts | On failure |
|-------|----------|----------|------------|
| **Liveness** | "Is this container in a state from which it can recover *without* intervention?" | Kubelet | **Kills the container** and restarts it per `restartPolicy` |
| **Readiness** | "Can this pod accept traffic *right now*?" | kube-proxy / Service / Ingress | **Removes the pod from the Service's endpoint list** — no new traffic, but the container keeps running |

The liveness probe is the kubelet's "pull the plug" signal. The readiness probe is the load balancer's "don't route here" signal.

## Why your DB check in liveness caused a restart loop

Here's the exact sequence during the outage:

1. DB goes unreachable.
2. Your `/health` endpoint (which pings the DB) starts returning 503 or timing out.
3. After `failureThreshold` consecutive liveness failures, the kubelet kills the container.
4. K8s schedules a new container. App starts, tries to connect to the DB — still down.
5. The new container's `/health` immediately starts failing again.
6. After another `failureThreshold × periodSeconds`, the kubelet kills it again.
7. **Loop.** Every pod in the deployment cycles through this, and you never get a stable running instance.

The root design error: **a downed dependency is not the same as a dead process.** Your app was perfectly alive — its event loop was running, its HTTP server was listening, its goroutines/threads were healthy. It simply couldn't fulfil requests because an *external* system was unavailable. Restarting the container doesn't fix an external dependency, so the kubelet is just churning containers for no benefit.

There's a secondary damage: each restart tears down the connection pool, re-runs initialization, and (if you have many replicas) creates a thundering-herd of reconnections the moment the DB recovers.

## The correct split

**Liveness (`/livez`)** — prove the *process* is alive. No external I/O.

```yaml
livenessProbe:
  httpGet:
    path: /livez
    port: 8080
  initialDelaySeconds: 15   # give the process time to bind the socket
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3       # 30 s of unresponsiveness before the kubelet acts
```

Your `/livez` handler should do essentially nothing beyond return `200 OK`. The only legitimate additions are checks for internal deadlocks (e.g., "is my worker thread pool fully saturated with zero in-flight progress?", "is my channel buffer backed up to 100%?"). Anything that involves a network call to another service is out of scope.

**Readiness (`/readyz`)** — prove the pod *can serve traffic*. This is where dependencies belong.

```yaml
readinessProbe:
  httpGet:
    path: /readyz
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 5
  timeoutSeconds: 3
  failureThreshold: 2       # remove from LB quickly when a dep goes down
```

Your `/readyz` handler checks:

- DB connection pool has at least one healthy connection (or a lightweight `SELECT 1` with a tight timeout).
- Any required cache / message-broker / upstream API is reachable.
- Application-level readiness: migrations applied, warm-up complete, etc.

If any check fails, return `503`. The pod stays **running**, its endpoints are removed, and the moment the dependency recovers the next probe passes and traffic flows again — no restart, no cold start.

### Example handler split (Go-flavoured, any language works)

```go
// /livez — "am I alive?"
func livez(w http.ResponseWriter, _ *http.Request) {
    // Deliberately NO database call.
    // Optional: check that the main goroutine isn't wedged,
    // e.g. a heartbeat channel written to every tick by a background loop.
    w.WriteHeader(http.StatusOK)
}

// /readyz — "can I serve a request right now?"
func readyz(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
    defer cancel()

    // DB check
    if err := dbPool.PingContext(ctx); err != nil {
        http.Error(w, "db unavailable", http.StatusServiceUnavailable)
        return
    }

    // Add other dependency checks here (cache, external APIs…)

    w.WriteHeader(http.StatusOK)
}
```

## What happens in each scenario now

| Scenario | Liveness | Readiness | Result |
|----------|----------|-----------|--------|
| DB outage | Passes (process is fine) | Fails → pod removed from Service | Pod sits idle, no traffic, **no restart**. When DB returns, next probe passes, traffic resumes in seconds. |
| App deadlocked (goroutine leak, full GC stall) | Fails → kubelet kills container | (irrelevant) | Container restarted — this is the *correct* use of liveness. |
| Pod mid-startup | Not yet evaluated (`initialDelaySeconds`) | Not yet evaluated | No premature failures. |
| OOM / kernel kill | N/A (container is gone) | N/A | K8s restarts per `restartPolicy`. |

## A few practical notes

- **Startup probe** (K8s ≥ 1.18): if your app takes a long time to initialise (large model load, many migrations), add a `startupProbe` so the liveness/readiness timers don't fire during the slow boot.

  ```yaml
  startupProbe:
    httpGet:
      path: /readyz
      port: 8080
    periodSeconds: 3
    failureThreshold: 60   # up to 180 s to become ready
  ```

  Once startup succeeds, liveness and readiness take over as normal.

- **Don't share the same endpoint** for both probes. The whole point is that they have different failure semantics. A single `/health` that does everything forces you into the restart-loop trap you just hit.

- **Tune `failureThreshold` / `periodSeconds` per probe.** You generally want readiness to react *faster* (remove bad traffic quickly) and liveness to react *slower* (avoid killing a container on a transient GC pause or network blip).

- **If all pods share the same DB**, they'll all go NotReady at once and you'll have zero serving capacity. That's unavoidable — the dependency is genuinely down. The difference is that your pods recover in seconds rather than minutes of crash-loop backoff, and you don't burn CPU/memory on pointless restarts while the DB team fixes the problem.

- **Blast radius of the fix:** changing probe paths and adding the split endpoints is a config + code change. It requires a rolling deployment of the pod template. During the rollout, old pods (with the bad liveness) coexist with new pods. If the DB is healthy at rollout time, there's no disruption. If the DB is down at rollout time, you'll see the old pods crash-loop while the new ones simply go NotReady — plan the rollout for a window where the DB is up.

- **Rollback:** revert the Deployment manifest to the previous revision (`kubectl rollout undo deployment/<name>`). The old image with the old `/health` liveness is still in the container registry, so this is a one-step revert.

## TL;DR

Liveness = "should the kubelet kill this container?" → only check the process's own liveness.
Readiness = "should the load balancer route traffic here?" → check all dependencies the pod needs to serve a request.

Putting a DB check in liveness means "DB down → kill my own process → restart → DB still down → kill again." Putting it in readiness means "DB down → stop sending me traffic, but keep my container warm → DB back → resume in seconds."
