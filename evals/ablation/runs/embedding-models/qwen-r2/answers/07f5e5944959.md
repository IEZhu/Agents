```sql
SELECT customer_id, id, amount, created_at
FROM (
    SELECT
        id, customer_id, created_at, amount,
        ROW_NUMBER() OVER (
            PARTITION BY customer_id
            ORDER BY amount DESC, created_at ASC
        ) AS rn
    FROM orders
) ranked
WHERE rn = 2;
```

### Почему корректно

- **`PARTITION BY customer_id`** — окно (сортировка, нумерация) считается отдельно для каждого клиента.
- **`ORDER BY amount DESC, created_at ASC`** — в точности ваш порядок: сначала по сумме убывание, при равенстве — по дате возрастание.
- **`ROW_NUMBER()`** — присваивает строго последовательные номера 1, 2, 3… внутри каждого окна. Даже при полном совпадении `amount` и `created_at` каждая строка получает уникальный номер (порядок между дублями неопределён, но номер один).
- **`WHERE rn = 2`** — отбирает ровно вторую строку. Клиент с единственным заказом имеет лишь `rn = 1`, поэтому отсекается без дополнительного `HAVING COUNT(*) > 1`.

### Мелочь про индексы

Для больших таблиц (миллионы строк) полезно иметь индекс, который покрывает сортировку окна:

```sql
CREATE INDEX CONCURRENTLY idx_orders_cust_amount
    ON orders (customer_id, amount DESC, created_at ASC);
```

Это не гарантирует, что планёр пойдёт по индексу вместо сортировки (зависит от статистики и размера выборки), но при умеренном количестве строк на клиента даёт шанс избежать full sort. В любом случае — `CREATE INDEX CONCURRENTLY`, чтобы не блокировать запись.

Проверка:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT customer_id, id, amount, created_at
FROM (
    SELECT id, customer_id, created_at, amount,
           ROW_NUMBER() OVER (
               PARTITION BY customer_id
               ORDER BY amount DESC, created_at ASC
           ) AS rn
    FROM orders
) ranked
WHERE rn = 2;
```

Смотрите, сортировка идёт через `Sort` или через `Index Scan` — это покажет, работает ли новый индекс на ваш workload.
