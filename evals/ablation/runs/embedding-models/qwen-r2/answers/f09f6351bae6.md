## Почему так

`-Xmx512m` задаёт **максимум heap**. Но процесс JVM ест память не только из heap:

| Сегмент | Сколько съедает (ориентир) |
|---|---|
| Java heap (`-Xmx`) | до 512 MiB |
| Metaspace (классы, константы) | 50–150+ MiB |
| Thread stacks (по 1 MiB/поток, дефолт) | 100–300 MiB при 100–300 потоках |
| Code cache (JIT) | 24–240 MiB |
| Direct byte buffers / NIO | десятки MiB |
| Нативные аллокации, GC-буферы | десятки MiB |

Итого процесс уверенно живёт в **700–1000+ MiB**, а cgroup-лимит контейнера — ровно **512 MiB**. Как только суммарное потребление перескает cgroup limit, ядро шлёт `SIGKILL` (128 + 9 = **137**).

Почему «каждые пару часов», а не сразу: Metaspace, Direct Buffers и thread pool постепенно разрастаются по мере нагрузки. Heap при GC укладывается в лимит, но всё остальное копит до тех пор, пока cgroup OOM killer не сработает.

## Что поменять

**Главное правило: heap < контейнерного лимита с запасом на non-heap.**

```yaml
# k8s Deployment (фрагмент)
resources:
  requests:
    memory: "512Mi"   # = limits, чтобы Pod schedulable и не thrash-илась
  limits:
    memory: "512Mi"
```

Два равноценных варианта JVM-флагов:

### Вариант A — явный Xmx (предсказуемо, для продакшена)

```dockerfile
# Dockerfile / entrypoint
ENV JAVA_OPTS="\
  -XX:MaxRAMPercentage=75.0 \
  -XX:InitialRAMPercentage=50.0 \
  -XX:MaxMetaspaceSize=128m \
  -XX:MaxDirectMemorySize=64m \
  -XX:+UseG1GC \
  -XX:G1MaxNewSizePercent=50 \
  -XX:MaxGCPauseMillis=100 \
  -XX:+ExitOnOutOfMemoryError \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/tmp/heapdump.hprof"
```

`MaxRAMPercentage=75` → при лимите 512 MiB heap ≈ **384 MiB**, остаётся ~128 MiB на всё остальное. Это безопасный запас для типовой Spring Boot / Micronaut / Quarkus-приложения.

### Вариант B — если хочется фиксированный Xmx

```
-Xms256m -Xmx384m
-XX:MaxMetaspaceSize=128m
-XX:MaxDirectMemorySize=64m
```

384 + 128 + 64 = 576 → уже чуть больше 512, так что при 512 MiB лимите берите `-Xmx352m` или поднимите лимит до **768 Mi / 1 Gi**.

### Если лимит 512 MiB объективно мало для приложения

Поднимите контейнерный лимит до **1 Gi** и используйте:

```
-XX:MaxRAMPercentage=75.0   # heap ≈ 768 MiB
-XX:MaxMetaspaceSize=128m
```

Это чаще всего правильный ответ: 512 MiB для Java-сервиса с JIT, pool'ами и метаданными — мало.

## Дополнительные шаги

1. **Смонтируйте volume для heap dump** (или sidecar, который забирает файл), чтобы при следующем OOM можно было открыть `heapdump.hprof` в JFR/MAT и понять, растёт ли heap или non-heap.

2. **Prometheus / Micrometer** — добавьте сборник `jvm.memory.used` по areas `heap`, `nonheap`, `threads`, `direct`. Наблюдайте тренд: если heap стабильно после GC, а nonheap/direct растёт — это не «нужно больше heap», а лик в native-коде или утечка Direct Buffers.

3. **`-XX:+ExitOnOutOfMemoryError`** — вместо зависания при OOM в heap; Pod перезапустится сразу, а не будет «мёртвым грузом» жрать cgroup.

4. **Проверьте thread count**: `jstack` или Actuator `/metrics/jvm.threads`. Если 500+ потоков × 1 MiB stack = 500 MiB только на stack'и. Лимит: `-XX:ThreadStackSize=512` (KB) или сократите pool.

## Быстрый чек-лист (что проверить прямо сейчас)

```bash
# 1. Убедиться, что JVM видит cgroup (JDK 10+ — by default, но проверьте)
kubectl exec -it <pod> -- java -XX:+PrintFlagsFinal -version 2>&1 | grep -i container
# должно быть: -XX:MaxRAMPercentage=... (не 0), -XX:+UseContainerSupport=true

# 2. Посмотреть текущее потребление изнутри (если Pod ещё жив)
kubectl exec -it <pod> -- cat /sys/fs/cgroup/memory/memory.usage_in_bytes   # cgroup v1
# или
kubectl exec -it <pod> -- cat /sys/fs/cgroup/memory.current                 # cgroup v2

# 3. JMX / Actuator
kubectl exec -it <pod> -- curl -s localhost:8080/actuator/metrics/jvm.memory.used
```

## Rollback / blast radius

- Изменение флагов в `JAVA_OPTS` и пересборка/перестарт Pod — **низкий риск**, затронут только этот Deployment.
- Подъём `limits.memory` с 512→1Gi — нужен свободный node capacity; на кластере с плотным bin-packing может занять 20–60 сек на reschedule.
- Если приложение уже в проде и «каждые 2 часа» — каждый рестарт = окно недоступности. Если SLA не допускает: поставьте `minReadySeconds` + `PodDisruptionBudget` и делайте `kubectl rollout restart` в low-traffic окно.

**TL;DR:** `-Xmx512m` = 100 % лимита контейнера. Уберите `-Xmx`, поставьте `-XX:MaxRAMPercentage=75.0` + `-XX:MaxMetaspaceSize=128m`. Если 512 MiB объективно мало — поднимите лимит до 1 Gi.
