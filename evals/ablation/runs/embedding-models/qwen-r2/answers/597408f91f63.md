**BLUF:** `-Xmx512m` = 512 MiB heap. Контейнерный лимит тоже 512 Mi. Свободного места на metaspace, thread stacks, native memory и GC-структуры **ноль** — как только они подтянутся поверх heap, ядро убивает процесс (SIGKILL → 137).

## Почему именно так

`-Xmx` задаёт только **heap**. Реальный RSS JVM =

| Компонент |_TYP. размер для 512m heap_ |
|-----------|---------------------------|
| Heap (Xmx) | до 512 MiB |
| Metaspace (классы, JIT code) | 100–200 MiB |
| Thread stacks (1 MiB × N потоков) | 50–200 MiB |
| Direct / NIO memory (Netty, gRPC) | 32–128 MiB |
| GC-инфраструктура, code cache, OS | 20–50 MiB |
| **Итого** | **~700–1100 MiB** |

У вас лимит 512 Mi, а только heap уже занимает весь бюджет. Первые часы JVM работает в режиме, когда heap ещё не заполнен и metaspace небольшой — всё укладывается. Через пару часов heap растёт (нормальная нагрузка или утечка) + metaspace доходит до стабильного значения → RSS пробивает 512 Mi → cgroup OOM killer → `Exit Code: 137`.

«Каждые пару часов» — это время, за которое heap + non-heap добираются до лимита. Если паттерн строго монотонный (каждый раз одинаково по времени) — подозревайте утечку в heap.

## Что менять

### 1. Уменьшить Xmx (обязательно)

Правило: heap ≈ 60–75 % от container limit.

```yaml
# 512 Mi limit → Xmx 384m (75%) или 320m (62%)
command: [java, "-Xmx384m", "-Xms384m", "-XX:MaxMetaspaceSize=128m", "-XX:MaxDirectMemorySize=64m", "-jar", "app.jar"]
```

Фиксация `Xms = Xmx` убирает джиттер от dynamic resize и делает прогноз потребления предсказуемым.

### 2. Зафиксировать non-heap компоненты

```
-XX:MaxMetaspaceSize=128m      # без него metaspace растёт безbound
-XX:MaxDirectMemorySize=64m    # Netty / NIO Buffer (по умолчанию = Xmx!)
-XX:ReservedCodeCacheSize=128m # JIT code
-XX:MaxHeapFreeRatio=70        # G1 не будет держать heap на максимуме
```

### 3. (Опционально) Поднять лимит, если приложение реально нужно больше

Если после снижения Xmx приложение деградирует (частый GC, OOMError в heap) — проблема не в конфигурации, а в объёме данных. Тогда:

```yaml
resources:
  requests:
    memory: "768Mi"   # = Xmx + overhead, для scheduling
  limits:
    memory: "1Gi"     # ~75% на heap (768m) + 256m на non-heap
```

### 4. Диагностика утечки (если паттерн «каждые N часов» не меняется после фикса)

```bash
# GC-лог (Java 21: unified logging)
-verbose:gc -Xlog:gc*:file=/tmp/gc.log:time,uptime,level,tags:filecount=5,filesize=10M

# Heap dump при OOM (чтобы снять до kill)
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/tmp/heapdump.hprof
```

Сматривать:
```bash
# В JFR / jmap (в sidecar или через kubectl exec, если успели)
kubectl exec -it <pod> -- jmap -histo:live <pid> | head -40

# Grafana + JMX exporter: heap used vs time — линейный рост = утечка
```

## Чек-лист после фикса

```bash
# 1. Поднялось ли pod без OOM > 6h
kubectl get pod <pod> -w

# 2. Реальное потребление (не Xmx, а RSS)
kubectl top pod <pod>

# 3. В logs контейнера нет "Java heap space"
kubectl logs <pod> | grep -i "out of memory"

# 4. В describe: Last State отсутствует или RestartCount не растёт
kubectl describe pod <pod> | grep -A3 "Last State"
```

## Rollback

Если после изменения лимитов/флагов приложение начинает `OutOfMemoryError: Java heap space` (heap реально меньше, чем нужно):

```bash
# Откат в Git → redeploy. Или hotfix:
kubectl set resources deploy/<app> -c <container> --requests=memory=768Mi --limits=memory=1Gi
kubectl set env deploy/<app> -c <container> JAVA_OPTS="-Xmx768m -Xms768m"
```

Blast radius: один deployment, rolling update без downtime (если replicas ≥ 2 и `maxUnavailable: 0`).

## Коротко

| Было | Стало |
|------|-------|
| `limits.memory: 512Mi` | `limits.memory: 512Mi` (или 1Gi, если нужно) |
| `-Xmx512m` | `-Xmx384m -Xms384m` |
| Нет Metaspace cap | `-XX:MaxMetaspaceSize=128m` |
| Нет DirectMemory cap | `-XX:MaxDirectMemorySize=64m` |

Heap не должен быть равен контейнерному лимиту — это как жить в комнате, где кровать занимает всю площадь. Оставляйте 25–40 % на всё остальное.
