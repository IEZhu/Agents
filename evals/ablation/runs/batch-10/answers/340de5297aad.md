**Короткий ответ:** я бы не брал ни тот, ни другой вариант. Лучше динамический few-shot: под каждое обращение достаём из ваших 6 000 размеченных примеров 10–20 самых похожих и добавляем их в промпт. Параллельно переписываем описания путающихся категорий. Статические 126 примеров оставьте как запасной вариант, но только с prompt caching.

## Почему не подходят оба варианта

**8 «трудных» примеров.** Не сработает по простой арифметике: 8 примеров не покроют 15 редких категорий. Примеры влияют на ответ сильнее инструкций. Если сдвинуть восьмёрку в сторону редких классов, модель начнёт чаще их предсказывать, и просядут частые категории, то есть 88% трафика. Точность на редких подрастёт, а общая может упасть.

**126 примеров (по 3 на категорию).**
- Стоимость: 20k × 30 000 = ~600M входных токенов в день. С prompt caching (статический префикс одинаков для всех запросов) кэшированные токены стоят в разы дешевле. По памяти, у Anthropic скидка на чтение из кэша около 90%, но это не проверено, сверьтесь с актуальным прайсом вашего провайдера. При ~20 запросах в минуту кэш почти всегда будет «тёплым». Так что довод «дорого» решается кэшем.
- Качество: главная проблема не в цене. Три случайных примера на «ИИС» не гарантируют, что модель научится отличать ИИС от вклада. Путаница возникает на пограничных формулировках, а в фиксированной тройке их может и не оказаться. К тому же 20k токенов шума почти во всех примерах не относятся к текущему обращению.

## Что делать

### 1. Сначала описания категорий (самое дешёвое)
Точность 50% на паре классов часто означает, что граница между ними плохо описана, и дело не в примерах. Для каждой путающейся пары добавьте явный критерий различения:

```
### Спор по chargeback
Клиент оплатил КАРТОЙ покупку у продавца/сервиса и оспаривает её:
товар не получен, услуга не оказана, двойное списание, подписка не отменена.
НЕ путать с «Ошибочный перевод»: там клиент САМ перевёл деньги
не тому человеку/по неверным реквизитам (СБП, по номеру карты/счёта), продавца нет.

### Вопрос по налоговому вычету по ИИС
Упоминается ИИС, брокерский счёт, вычет тип А/Б, 3-НДФЛ, справка для ФНС.
НЕ путать с «Вклады»: вклад — депозит с фиксированной ставкой, без брокера и вычета.
```

Пары для такой правки возьмите из confusion matrix, а не по интуиции. Отдельно стоит выборочно перепроверить разметку этих классов: если асессоры сами путают chargeback и ошибочный перевод, промпт это не исправит.

### 2. Dynamic few-shot
1. Прогоните все 6 000 примеров через эмбеддинг-модель (для русского подойдёт любая приличная мультиязычная) и сохраните векторы.
2. Для входящего обращения найдите top-k ближайших, k ≈ 30.
3. Отберите из них 10–15 так:
   - не больше 2–3 примеров на категорию, чтобы одна частая категория не забила весь контекст;
   - специально включите примеры **соседних** категорий. Если в выдаче есть chargeback, добавьте 1–2 примера «ошибочного перевода». Такой контрастный пример учит модель границе.
4. Отсортируйте их так, чтобы самые похожие стояли ближе к самому обращению.

Структура промпта (порядок важен для кэша):
```
[system: роль, инструкции, 42 категории с описаниями]   ← статично, кэшируется
[примеры: 10–15 динамических]                            ← меняется
[обращение клиента]
```
Выходит примерно 2–4k токенов динамики поверх кэшированного префикса. Это на порядок меньше варианта со 126 примерами.

Две оговорки:
- если правильной категории нет среди найденных соседей, примеры не помогут. Замерьте **retrieval recall@k**: в какой доле обращений нужная категория встречается среди top-k. Если на редких классах она ниже ~80–90%, сначала чините поиск (другая модель, больший k, гибридный поиск с BM25 по ключевым словам вроде «ИИС», «3-НДФЛ», «chargeback»);
- защита от prompt injection: текст обращения обрамляйте тегами (`<ticket>...</ticket>`) и укажите, что это данные, а не инструкции. Для банка это обязательно.

### 3. Как выбрать между вариантами: мерить
- Отложите стратифицированный тест: например, по 15–20 обращений на каждую редкую категорию плюс пропорциональную выборку частых. Эти примеры **исключите из пула для поиска**, иначе модель найдёт сам тестовый пример и метрики окажутся завышены.
- Метрики: **macro-F1** и recall по каждой категории. Общая accuracy спрячет редкие классы за частыми. Плюс confusion matrix и цена/латентность на запрос.
- Сравните по одному изменению за раз:
  1. текущий baseline;
  2. baseline + новые описания;
  3. (2) + 126 статичных примеров с кэшем;
  4. (2) + dynamic few-shot.
- Полезный бесплатный бенчмарк: простой kNN-классификатор (голосование ближайших соседей по эмбеддингам) без LLM. Если он уже даёт на редких классах около 75%, это хороший ориентир.

### 4. Если всё равно не дотягивает
- **Двухэтапная классификация:** сначала группа (карты / переводы / инвестиции / споры / кредиты), потом категория внутри группы со своими описаниями и примерами. На каждом шаге задача проще.
- **Дешёвый классификатор + LLM как fallback:** 6 000 примеров хватает для логрегрессии на эмбеддингах или дообучения небольшой модели. Уверенные случаи она закроет сама, а в LLM уйдут только неуверенные. При 30k обращений в день это, вероятно, самый выгодный вариант по цене.

**Мой прогноз** (оценка, не замер): основной прирост на редких классах дадут новые описания пар и dynamic few-shot с контрастными примерами. Вариант со 126 статичными примерами, скорее всего, окажется где-то посередине по качеству. Проверьте это на тесте, прежде чем выбирать.
