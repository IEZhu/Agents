## Latest user message
We run an intent router for a travel app chatbot on gpt-4o-mini. 27 intents (change_booking, cancel_booking, refund_status, baggage_allowance, seat_selection, visa_question, etc.). The prompt lists the intents with one-line descriptions plus 10 hand-picked English example utterances with their labels, same for every call. Traffic is ~40% English, 35% German, 25% Spanish. Overall accuracy on our 1,500-utterance labeled eval set is 84%, but German and Spanish users asking about refunds get routed to cancel_booking a lot, and seat_selection vs. change_booking gets mixed up in all languages. We also have ~9,000 labeled production utterances in all three languages sitting in a spreadsheet. I've already tried rewriting the intent descriptions twice and it barely moved. My plan is to translate the 10 examples into German and Spanish and hand-pick maybe 20 more that cover the confused pairs, so ~50 fixed examples total. Is that the right move, and which examples should I pick?

## Rubric (what a strong answer does)
1. Recommends retrieving a small number of the most similar labeled utterances per incoming message from the ~9,000-utterance set (e.g. via multilingual embeddings) rather than using the same 10 examples for every call
2. Addresses the language mismatch explicitly, e.g. retrieved examples should match or be close to the user's language (German/Spanish), not only English
3. Tackles the specific confusions (refund_status vs cancel_booking, seat_selection vs change_booking), e.g. ensuring contrasting examples of both intents can appear, or placing the most similar example closest to the query
4. Advises validating the change against the existing 1,500-utterance eval set, ideally broken down per language and per intent

## Answer A
**Short answer: partly.** Adding German and Spanish examples and targeting the confused pairs is the right idea. A fixed set of 50 hand-picked examples is not the best way to do it. You have 9,000 labeled production utterances in all three languages, so pick the examples **per call by retrieval** instead of fixing them by hand. Also add explicit tie-break rules for the two confused pairs, since better descriptions alone didn't fix them.

## Why a fixed set of 50 is a weak fit

- **Translated examples aren't how people actually write.** Real German and Spanish users say "Ich habe storniert, wo bleibt mein Geld?" or "cancelé el vuelo y no me han devuelto nada". Those sentences contain cancel words but the intent is `refund_status`. You already have real messages like these in your spreadsheet. Translations of English examples mostly won't contain these patterns.
- **50 examples across 27 intents is fewer than 2 per intent.** Either coverage is thin, or you overweight the confused pairs and the model starts to over-predict those labels (few-shot examples bias predictions toward the labels they show).
- **You pay for 50 examples on every call**, including the roughly 80% of calls that are nowhere near a confused pair.
- **Hand-picking can't be improved systematically.** When the next pair starts getting confused, you're back to picking by hand.

## Recommended approach: dynamic few-shot (kNN retrieval)

1. **Build the pool.** Take the 9k production utterances. **Remove anything that is in, or nearly identical to, the 1,500-utterance eval set.** Otherwise you'll leak eval data and your accuracy numbers will be meaningless. Clean obvious label noise first, especially in refund/cancel and seat/change rows.
2. **Embed the pool** with a multilingual embedding model. OpenAI's `text-embedding-3-small` should handle DE/ES adequately. That's from memory, so check it on a sample.
3. **At each call**, retrieve the top ~8–15 nearest labeled examples and put them in the prompt before the user message. Two refinements:
   - Prefer examples in the **same language** as the query, for example 70% same language and 30% any language.
   - Cap examples per label (e.g. 4 max), so a single dominant label can't flood the examples.
4. **Keep the static part small**: the list of intents with descriptions, the tie-break rules below, and output restricted to an enum via structured output / JSON schema so it can't return an invalid label.

This approach naturally puts contrastive neighbors in the prompt: a German refund question pulls in German refund and cancel examples with their correct labels. That is exactly the signal the model is missing now.

## Add explicit tie-break rules for the two confused pairs

Your descriptions say what each intent *is*. They don't say how to decide between two intents when a message fits both. Add rules like these:

```
## Disambiguation rules (apply in order)
- Money back / refund / "wo bleibt mein Geld" / "reembolso" / status of a refund
  → refund_status, EVEN IF the message says the booking was already cancelled.
- cancel_booking ONLY when the user wants to cancel now and does not ask about money already owed.
  If they want to cancel AND ask about the refund amount → cancel_booking.
- Seat-only changes (seat number, window/aisle, sit together, "Sitzplatz", "asiento")
  → seat_selection, even if the verb is "change/ändern/cambiar".
- change_booking ONLY for date, time, route, passenger name, or fare changes.
```

The second rule ("cancel now + refund amount → `cancel_booking`") is a **product decision**. Check it against how your eval set is labeled. If the labels are inconsistent on these edge cases, part of your 84% accuracy ceiling is label noise, and no prompt change will fix that.

## Which examples to use if you stay static

If you can't add retrieval right now (infrastructure, latency), pick examples like this rather than translating:

- **Take them from production, not from translations.** Real DE/ES utterances in roughly your traffic mix: about 40/35/25.
- **For each confused pair, use minimal pairs**: two utterances that look alike but have different labels.
  - DE: "Ich möchte meinen Flug stornieren" → `cancel_booking` / "Ich habe storniert, wann bekomme ich mein Geld?" → `refund_status`
  - ES: "Quiero cancelar mi reserva" → `cancel_booking` / "Cancelé hace dos semanas y no veo el reembolso" → `refund_status`
  - EN: "Can I change my seat to a window?" → `seat_selection` / "Can I change my flight to Friday?" → `change_booking`
  - DE/ES versions of the seat pair: "Sitzplatz ändern" vs "Flug umbuchen", "cambiar asiento" vs "cambiar la fecha del vuelo".
- **Use errors to choose.** Run the current prompt over the 9k and take misclassified utterances from the confused pairs. Those are the hard cases the model needs to see.
- **Keep at least one example for every intent**, so the rarer intents don't lose out.
- **Shuffle or interleave labels.** Don't group all examples for one intent together, because the order can bias predictions.

## How to measure it (one change at a time)

1. **Baseline:** confusion matrix on the eval set, split by **language** and by **pair**. Record refund→cancel errors for DE and ES and seat↔change errors for each language, not just the overall 84%.
2. **Change 1:** tie-break rules only.
3. **Change 2:** add dynamic few-shot.
4. **Change 3 (optional):** static 50 set vs dynamic, compared on the same eval set.
5. Track per-language accuracy, error rate on each confused pair, tokens per call and p95 latency.

Predicting the gain is guesswork. My expectation is that the rules plus retrieval will probably move the confused pairs much more than hand-picked examples would. The eval should decide.

## Other options worth considering

- **Fine-tuning.** With about 9k labeled examples you're in a range where fine-tuning gpt-4o-mini is realistic. As far as I recall it can be fine-tuned via the OpenAI API; check current availability and pricing. That usually beats few-shot for a fixed classification task and shortens the prompt. Keep the eval set separate.
- **Embedding classifier.** A logistic regression over multilingual embeddings, trained on the 9k. It's cheap, fast, and often strong for intent routing. You could use it as a first pass and send only low-confidence cases to the LLM.

**Bottom line:** don't translate. Add tie-break rules for the two pairs, retrieve real same-language examples from the 9k for each call, keep the eval set out of the retrieval pool, and measure per language and per pair.


## Answer B
**Short answer:** You're right that examples are the lever, not descriptions. A fixed set of ~50 examples is the wrong way to use them, though. You have 9,000 labeled utterances, so retrieve examples for each query instead of hand-picking a static set. Before any of that, check whether the refund/cancel confusion is really a labeling-policy problem, because no choice of examples will fix that.

## 1. Diagnose before you pick anything (about half a day)

Build a confusion matrix of **intent × language** from the 1,500-item eval set, and pull 50–100 misrouted refund→cancel and seat→change cases. For each one, ask:

- **Is the gold label defensible?** "Ich möchte mein Geld zurück für den Flug nach Madrid" can reasonably mean either intent. If your labelers disagree on these, the ceiling comes from the labels and not the prompt. Check the 9k spreadsheet for the same inconsistency.
- **Is it a language gap or a boundary gap?** If English refund questions route fine and German/Spanish ones don't, the English-only examples are the problem. If all three languages fail on the same kind of phrasing, the boundary is undefined.

My guess from what you describe: refund/cancel is mostly a language gap, since the English examples are anchoring the model. Seat/change is a boundary gap, because the verb "change" pulls requests like "change my seat" toward change_booking. That's a guess, and the audit will tell you.

## 2. Add explicit decision rules for the two confused pairs

Rewriting descriptions barely moved accuracy because descriptions say what an intent *is*. The model needs to know how to decide at the *boundary*. Add a short tie-breaker section:

```
## Disambiguation rules
- refund_status vs cancel_booking:
  - refund_status = the user asks about money: whether, when, or how much they get back,
    including for a booking that is already cancelled.
  - cancel_booking = the user wants to end or cancel a booking now.
  - Mentioning money alone does NOT mean cancel_booking.
  - If the user says both "cancel it" and "will I get a refund", choose cancel_booking.
- seat_selection vs change_booking:
  - Any request that only affects the seat (pick, change, upgrade, move seat) = seat_selection,
    even if the word "change"/"ändern"/"cambiar" appears.
  - change_booking = date, time, route, passenger name, or flight changes.
```

These rules follow the draft labeling policy. Adjust them to whatever your label guidelines say, and fix the guidelines first if they're ambiguous.

This is one change, so test it on its own.

## 3. Replace static examples with retrieved ones

**Setup:**
1. Remove from the 9k pool any utterance that's in the eval set or near-duplicates one (for example, cosine similarity > 0.95). If you skip this, your accuracy gain is leakage.
2. Embed the pool with a multilingual embedding model.
3. For each incoming query, retrieve the top ~20 neighbors. Keep 8–12 of them, with at most about 3 per label, so one intent doesn't flood the context. Prefer neighbors in the query's language.
4. Put the static part (intent list + disambiguation rules) first and the retrieved examples last, with the closest neighbor nearest the query.

**Why this beats 50 fixed examples:**
- A German refund question gets German refund *and* German cancel neighbors, which are exactly the contrastive examples it needs. Hand-picked examples can only cover the confusions you already know about.
- It uses fewer tokens per call than 50 fixed examples (roughly 10 × ~20 tokens against 50 × ~20), so it's cheaper and faster on 4o-mini.
- Caching trade-off: OpenAI automatically caches a static prompt prefix above a certain length (recalled as about 1,024 tokens; not verified here, so check current docs). Putting the dynamic examples after the static block keeps that part cacheable.

**Risk:** retrieval quality now caps accuracy. If a query's nearest neighbors are mislabeled, the model copies the mistake. Clean labels (step 1) matter even more.

## 4. If you stay with static examples, how to pick them

A fixed set is still a reasonable baseline or fallback. Choose examples like this:

- **Minimal pairs across the boundary, in each language.** For example:
  - "Wann bekomme ich mein Geld für die stornierte Buchung?" → refund_status
  - "Ich will die Buchung stornieren" → cancel_booking
  - "¿Puedo cambiar mi asiento al pasillo?" → seat_selection
  - "¿Puedo cambiar mi vuelo al martes?" → change_booking
- **Actual production failures**, rather than clean textbook phrasings. Take them from the 9k set by running the current prompt over it and sampling its errors.
- **Balanced labels.** If 15 of 50 examples are refund/cancel, the model will over-predict those two intents, because examples bias output more than instructions do.
- **Native utterances over translations.** Translated examples sound like translations. Real German and Spanish users phrase things differently ("Erstattung", "Rückzahlung", "devolución", "reembolso").
- **All 27 intents represented,** with at least one example each, so the other 25 don't regress.

## 5. Consider leaving few-shot prompting altogether

With 9k labeled examples, two alternatives are worth a cheap comparison:

- **kNN-only baseline:** embed the query and take a majority vote over its top-k neighbors, with no LLM call. It costs almost nothing to test. If it lands near 84%, you learn a lot about where the remaining errors come from.
- **Fine-tuning gpt-4o-mini** on the cleaned 9k (as I recall it's fine-tunable; confirm current availability and pricing). For a fixed 27-class task with this much data, it often beats prompting and lets you drop most of the prompt. That last point is likely, not guaranteed, so measure it.
