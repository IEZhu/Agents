## Answer A
Сразу выполнять шаги 4–6 одним блоком нельзя: бэкфилл пропустил батч, и после него `SET NOT NULL` упадёт прямо в окне релиза. Ниже объясняю, что случилось, и даю исправленный порядок.

## Что пропущено

Батчи идут по 10 000 id: батч N покрывает `(N-1)*10000+1 … N*10000`.

- Батч 2299 = `22980001–22990000`. Это последний батч, записанный в лог, значит он точно закоммичен.
- Батч 2300 = **`22990001–23000000`**. Именно на нём скрипт упал.
- Перезапуск с `--start-id 23000001` начал сразу с батча 2301.

Выходит, диапазон `22990001–23000000` (до 10 000 строк) остался незаполненным. Скорее всего, там `amount_cents IS NULL`. Есть и другой вариант: `SSL SYSCALL error: EOF` мог прилететь во время COMMIT, и тогда сервер успел закоммитить батч. Узнать это заранее нельзя. Но это и не нужно: UPDATE с условием `amount_cents IS NULL` можно безопасно запускать повторно.

Второе замечание: ваш шаг 5 (переключение чтения в приложении) — это деплой, а не SQL. `DROP COLUMN amount` можно выполнять только после того, как код, который читает и пишет `amount`, полностью выкачен. Иначе приложение начнёт падать. Поэтому шаг 6 в тот же блок не включаю.

## Блок для админа: закрыть дыру и проверить данные (шаг 4, часть 1)

```sql
-- 0. Бэкап перед изменением схемы (выполнить в shell заранее):
--    pg_dump -Fc -t orders -f orders_before_notnull.dump <db>

-- 1. Дозаполнить пропущенный батч 2300 (идемпотентно)
UPDATE orders
SET    amount_cents = round(amount * 100)
WHERE  id BETWEEN 22990001 AND 23000000
  AND  amount_cents IS NULL;

-- 2. Проверка по всей таблице: NULL-ы и расхождения с amount
--    (ловит и другие возможные дыры, и ошибки dual write).
--    Seq scan по 40M строк, блокировок не берёт.
SELECT
  count(*) FILTER (WHERE amount_cents IS NULL)                              AS null_cents,
  count(*) FILTER (WHERE amount IS NULL)                                    AS null_amount,
  count(*) FILTER (WHERE amount_cents IS DISTINCT FROM round(amount * 100)) AS mismatches
FROM orders;
-- Ожидаем 0 / 0 / 0. Если нет — СТОП, дальше не идём.
```

Если `null_amount > 0`, значит в исходной колонке были NULL. Тогда сначала решите, что для таких строк значит NOT NULL (0 или другое значение), и только потом идите дальше.

## Блок: NOT NULL без долгой ACCESS EXCLUSIVE блокировки (шаг 4, часть 2)

Прямой `ALTER COLUMN ... SET NOT NULL` сканирует все 40M строк и всё это время держит ACCESS EXCLUSIVE lock, то есть таблица блокируется и на чтение, и на запись. Обход такой: сначала CHECK-констрейнт, который валидируется под более слабой блокировкой. Начиная с PG 12, `SET NOT NULL` использует валидный CHECK вместо полного скана (помню это по документации ALTER TABLE, в release notes для 14 перепроверять не стал).

```sql
SET lock_timeout = '5s';   -- не встаём в очередь за долгой транзакцией, при таймауте просто повторить

-- мгновенно, без скана
ALTER TABLE orders
  ADD CONSTRAINT orders_amount_cents_nn CHECK (amount_cents IS NOT NULL) NOT VALID;

-- скан, но под SHARE UPDATE EXCLUSIVE: чтение и запись продолжают работать
ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_cents_nn;

-- быстро: доказательство берётся из валидного CHECK
ALTER TABLE orders ALTER COLUMN amount_cents SET NOT NULL;

-- CHECK больше не нужен
ALTER TABLE orders DROP CONSTRAINT orders_amount_cents_nn;

-- после 40M UPDATE в таблице много dead tuples, обновим и статистику
VACUUM (ANALYZE) orders;
```

**DOWN:** `ALTER TABLE orders ALTER COLUMN amount_cents DROP NOT NULL;`

## Шаг 5: деплой приложения, не SQL

Выкатываете чтение из `amount_cents` и убираете запись в `amount`. Если `amount` объявлена как NOT NULL, то перед отключением записи в неё снимите это ограничение: `ALTER TABLE orders ALTER COLUMN amount DROP NOT NULL;`. Иначе новые INSERT начнут падать.

## Шаг 6: отдельно, через несколько дней после шага 5

`DROP COLUMN` необратим. Откатиться можно будет только из бэкапа. Советую подождать, пока новый код поработает в проде.

```sql
-- что зависит от колонки: индексы, вьюхи, триггеры
SELECT indexrelid::regclass FROM pg_index
WHERE  indrelid = 'orders'::regclass
  AND  (SELECT attnum FROM pg_attribute
        WHERE attrelid = 'orders'::regclass AND attname = 'amount') = ANY (indkey);
-- вьюхи/функции: \d+ orders и поиск по pg_depend / pg_views

-- страховочная копия данных
CREATE TABLE orders_amount_backup AS SELECT id, amount FROM orders;

SET lock_timeout = '5s';
ALTER TABLE orders DROP COLUMN amount;   -- только метаданные, быстро; место на диске освобождается при перезаписи строк
```

**DOWN:** `ADD COLUMN amount numeric(12,2)` + `UPDATE ... FROM orders_amount_backup`.

Всё это стоит сначала прогнать на staging. На мелкой таблице каждый шаг проходит за секунды. Если в проде `VALIDATE` или `SET NOT NULL` поведут себя иначе, проверьте в `pg_stat_activity`, не висят ли долгие транзакции.


## Answer B
Сначала о проблеме: запускать 4–6 одним блоком сейчас нельзя. В бэкфилле, скорее всего, пропущен диапазон.

## Что не так с перезапуском

Батч N покрывает id `(N-1)*10000+1 … N*10000`. По логу батч 2299 — это `22980001–22990000`. Значит, батч 2300 — это **`22990001–23000000`**, а перезапустили с `23000001`. Эти 10 000 id никто не обработал, если батч 2300 не успел закоммититься до обрыва.

Есть и обратный вариант: лог пишется после коммита, поэтому батч 2300 мог закоммититься, а строчка в лог не попала. Какой случай ваш, не видно ни из лога, ни из ошибки. Это покажет запрос ниже. `UPDATE` с `AND amount_cents IS NULL` идемпотентен, так что догнать диапазон безопасно в любом случае.

Кроме пропуска, `SET NOT NULL` может упасть ещё по двум причинам:
- **`amount` сам бывает NULL.** Тогда `round(NULL*100)` = NULL, и `SET NOT NULL` упадёт. Нужно заранее решить, что делать с такими строками.
- **Баги dual write.** Строки, которые изменили после бэкфилла, могут расходиться между колонками.

## Шаг 4 — проверки, догон, NOT NULL

Перед выполнением сделайте бэкап или снапшот (`pg_dump -t orders` или снапшот диска). Сначала прогоните на staging.

```sql
-- === 4.0 Диагностика (только чтение) ===

-- Пропущенный диапазон: >0 значит, батч 2300 не был закоммичен
SELECT count(*) AS gap_nulls
FROM orders
WHERE id BETWEEN 22990001 AND 23000000
  AND amount_cents IS NULL;

-- Все NULL по таблице + сколько из них с NULL в amount (seq scan по 40M, займёт время)
SELECT count(*)                                AS null_cents,
       count(*) FILTER (WHERE amount IS NULL)  AS null_amount
FROM orders
WHERE amount_cents IS NULL;

-- === 4.1 Догон пропущенного диапазона (10k строк, один короткий UPDATE) ===
UPDATE orders
SET amount_cents = round(amount * 100)
WHERE id BETWEEN 22990001 AND 23000000
  AND amount_cents IS NULL;

-- Повторите запрос null_cents из 4.0. Должно быть 0.
-- Если null_amount > 0, остановитесь: решите, что делать с этими строками
-- (оставить колонку nullable или заполнить значением) и только потом идите дальше.

-- === 4.2 Сверка значений (проверка dual write) ===
SELECT count(*) AS mismatches
FROM orders
WHERE amount_cents IS DISTINCT FROM round(amount * 100);
-- Ожидается 0. Если не 0, сначала ищите баг в dual write и не переходите к шагу 5.

-- === 4.3 NOT NULL без долгой эксклюзивной блокировки ===
-- Прямой SET NOT NULL держит ACCESS EXCLUSIVE на всё время скана 40M строк,
-- то есть блокирует и чтение, и запись. Поэтому идём через CHECK-констрейнт.
SET lock_timeout = '5s';   -- не встать в очередь за долгой транзакцией и не повесить всё за собой

-- Мгновенно: проверяются только новые записи
ALTER TABLE orders
  ADD CONSTRAINT orders_amount_cents_not_null
  CHECK (amount_cents IS NOT NULL) NOT VALID;

-- Долго (полный скан), но под SHARE UPDATE EXCLUSIVE: DML не блокируется
SET statement_timeout = 0;
ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_cents_not_null;

-- В PG 12+ при валидном CHECK (col IS NOT NULL) повторный скан пропускается,
-- и блокировка короткая (по памяти, не проверял — сверьтесь с доками ALTER TABLE для 14)
ALTER TABLE orders ALTER COLUMN amount_cents SET NOT NULL;

-- Констрейнт больше не нужен
ALTER TABLE orders DROP CONSTRAINT orders_amount_cents_not_null;

RESET lock_timeout;
RESET statement_timeout;

-- DOWN для шага 4:
-- ALTER TABLE orders ALTER COLUMN amount_cents DROP NOT NULL;
```

Если какой-то `ALTER` упал по `lock_timeout`, это нормально: найдите долгие транзакции в `pg_stat_activity` и повторите.

## Шаг 5 — это не SQL

Переключение чтения на `amount_cents` и отключение dual write делаются деплоем приложения. Перед деплоем проверьте, что `amount` не используется на стороне БД:

```sql
-- Вьюхи, которые ссылаются на orders.amount
SELECT view_schema, view_name
FROM information_schema.view_column_usage
WHERE table_name = 'orders' AND column_name = 'amount';

-- Индексы с amount
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders' AND indexdef ILIKE '%amount%';

-- Триггеры на orders (их тела с amount проверьте вручную)
SELECT tgname FROM pg_trigger
WHERE tgrelid = 'orders'::regclass AND NOT tgisinternal;
```

Тем же поиском проверьте функции, отчёты, ETL и реплики/выгрузки для аналитики.

## Шаг 6 — отдельно и не в этом окне

`DROP COLUMN` нельзя откатить (DOWN только из бэкапа), поэтому в общий блок я его не включаю. Рекомендую выполнить его в следующий релиз, после того как новая версия приложения проработает какое-то время без обращений к `amount`. Выполнять только после явного подтверждения и свежего бэкапа:

```sql
SET lock_timeout = '5s';
ALTER TABLE orders DROP COLUMN amount;   -- только метаданные, быстро, но нужен короткий ACCESS EXCLUSIVE
RESET lock_timeout;
```

Что при этом учесть:
- Место на диске не освободится сразу, оно уйдёт по мере перезаписи строк (или через `pg_repack`, если нужно).
- Если где-то ещё работает старый код с `SELECT *` и prepared statements, он может получить `cached plan must not change result type`. Это ещё одна причина делать DROP после полного раската нового кода.
