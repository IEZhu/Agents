## Latest user message
We run a small public payments API (Node 20, Express, Postgres) used by ~40 merchant integrations we don't control. Two things on my plate this sprint:

1. Some merchants' HTTP clients time out after 10s and retry POST /v1/charges. When our upstream processor is slow, the first request actually succeeds, so the customer gets charged twice. Last week that happened 17 times. My plan is to dedupe server-side: if the same merchant sends a charge with the same amount and card in the last 60 seconds, return the existing charge.

2. Our charge response has `amount` as a float in dollars (e.g. 19.99) and we've had rounding bugs. I want to change `amount` to an integer in cents (1999) in the same deploy so it's fixed for everyone at once.

Can you sanity-check both plans and tell me what you'd actually ship?

## Rubric (what a strong answer does)
1. Rejects the amount+card+60s heuristic as the primary fix (it can block legitimate repeat purchases and miss retries outside the window) and recommends a client-supplied idempotency key header stored per merchant, returning the original result for a repeated key
2. Addresses what happens when the same idempotency key is reused with a different request body or while the first request is still in progress (e.g. reject with an error such as 409/422) rather than silently treating it as a replay
3. Advises against changing the type/meaning of the existing `amount` field in place under /v1, and instead proposes an additive change (e.g. a new integer field in minor units alongside the old one, with deprecation) or a new API version
4. Gives a concrete, shippable recommendation for both items that fits the stated constraints (Express/Postgres, merchants not under their control)

## Answer A
**Short version:** both plans aim at the right problems, but I wouldn't ship either one as written. The dedupe heuristic will block legitimate charges and still let some duplicates through. Changing the units of `amount` in place is a silent breaking change for 40 clients you don't control, and it could cause errors worth 100x the intended amount. What I'd ship instead is below.

---

## 1. Duplicate charges: use idempotency keys, not "same amount + card within 60s"

### Problems with the heuristic

- **It blocks real charges.** Two $4.50 coffees on the same card a minute apart, a split shipment, a customer buying two tickets in separate checkouts: all of these are legitimate, and they'd get the first charge back with no second charge made. The merchant thinks they were paid twice and were only paid once. That's a harder bug to find than a double charge, because nobody complains about it at checkout.
- **It misses slow retries.** A 60s window assumes retries arrive quickly. Clients with backoff, job queues or a manual "retry failed payments" button will retry after 60s.
- **It has a race condition.** In your failure case the first request is still in flight (waiting on the slow processor) when the retry arrives. A "look for an existing charge" query finds nothing because the first charge hasn't been written yet. So the heuristic probably wouldn't have stopped many of your 17 incidents. You can check this from logs: compare the retry arrival time with the time the first charge row was committed.
- **"Same card" needs care.** Compare on a processor token or card fingerprint, never on PAN data, or you pull more of the system into PCI scope.

### What I'd ship

**a) Support an `Idempotency-Key` header on POST /v1/charges.** This is the standard pattern (Stripe popularized it, and there's an IETF draft for the header). The client generates a unique key per logical charge and sends the same key on every retry. The server guarantees that one key maps to at most one charge.

Schema sketch:

```sql
CREATE TABLE idempotency_keys (
  merchant_id   bigint      NOT NULL,
  key           text        NOT NULL,
  request_hash  text        NOT NULL,         -- hash of method + path + canonical body
  status        text        NOT NULL,         -- 'in_progress' | 'completed'
  response_code int,
  response_body jsonb,
  created_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (merchant_id, key)
);
```

Request flow:

1. `INSERT ... (status = 'in_progress') ON CONFLICT (merchant_id, key) DO NOTHING RETURNING *`. The primary key closes the race: only one request can claim the key.
2. If the insert claimed the key, call the processor, store the response and set `status = 'completed'`.
3. If the key already existed:
   - `request_hash` differs → `422`, because the key was reused for a different request.
   - `in_progress` → `409` with `Retry-After`, because the original request is still running.
   - `completed` → replay the stored status code and body exactly.
4. Scope keys per merchant and expire them after about 24h.

**b) Send an idempotency key to your upstream processor too**, if it supports one (most do; check its docs). Derive it from your charge ID. Your own retries to the processor then can't double-charge either, and that's the layer where the money actually moves.

**c) Deal with the merchants that don't send keys.** This is the hard part with 40 integrations you don't control:

- Use your logs to find out who produced the 17 duplicates. I'd guess it's a small number of merchants with 10s timeouts. Contact them directly and ask them to send `Idempotency-Key`. That's probably the highest-leverage step.
- If you still want a heuristic for key-less requests, make it **opt-in per merchant**, or have it flag instead of dedupe: create the charge but mark `possible_duplicate` and alert or auto-review it. Don't silently return a different charge than the one the client asked for.
- Look at your p99 latency against the 10s client timeout. If the processor is the slow part, a processor-side timeout under 10s that returns a clear `pending` state (plus a way to fetch the final status) cuts down the ambiguous-outcome window. Clients have to handle `pending` for this to work, so it's a longer-term change.

## 2. `amount` float → integer cents: right goal, wrong migration

Storing and computing money as integer minor units is correct. Changing what an existing field *means*, in place, for clients you don't control, is not.

- **It fails silently, not loudly.** A merchant that parses `amount` as dollars will now read `1999` as $1,999.00. Nothing throws. It shows up in their receipts, reconciliation, refund logic and accounting. Refunds are the worst case: if a client echoes the response amount back into a refund call, you've got a 100x refund.
- **"Fixed for everyone at once" really means "broken for everyone at once"** unless all 40 integrations deploy a matching change at the same moment. They won't.
- **Don't ship it in the same deploy as the idempotency work.** If something goes wrong with charges that day you'll have two confounded causes, and the amount change can't be rolled back once clients have adapted to it.

### What I'd ship

**Step 1: fix the rounding internally now. No API change needed.** The rounding bugs almost certainly come from floats inside your own code path. Postgres returns `numeric` columns as strings in node-postgres by default (recalled, not verified here; check your `pg` type parsers), and somewhere they get `parseFloat`-ed and multiplied.
- Store amounts as `bigint` cents (or confirm `numeric(12,2)` and never convert it to a JS float).
- Do all arithmetic in integer cents.
- Convert to a dollar float only in the response serializer, and only for the legacy field: `(cents / 100)` is exact enough for display, and the one float conversion happens at the edge.
- For request parsing, convert incoming dollar floats with `Math.round(amount * 100)` and reject inputs with more than 2 decimal places.

This probably fixes most of the bugs you've actually seen, without touching the contract.

**Step 2: add the integer field alongside the old one.**

```json
{ "amount": 19.99, "amount_cents": 1999, "currency": "usd" }
```

(Name it `amount_cents`, or `amount_minor` if you'll ever support zero-decimal or 3-decimal currencies like JPY or KWD. If multi-currency is realistic, `amount_minor` is the name that stays accurate.)

Accept `amount_cents` on requests too. If a request sends both fields, reject it when they disagree.

**Step 3: deprecate `amount`.** Document it, add a `Deprecation`/`Sunset` header, email the merchants, and watch your logs for who still sends or relies on it. Remove it only in a versioned change (`/v2`, or a dated API-version header if you want Stripe-style versioning), and only once usage has actually dropped.

## Answer B
**Short version:** both plans aim at real problems, but as written I wouldn't ship either one. Plan 1 would block legitimate charges and still miss some duplicates. Plan 2 is a silent breaking change to a public money field, so it could cause mischarges 100 times too large or too small in integrations you can't fix. Here's what I'd ship instead.

---

## 1. Double charges: use idempotency keys, not a heuristic dedupe

### Problems with "same merchant + amount + card within 60s"

- **False positives on real purchases.** Two $4.50 coffees on the same card, a split shipment, or a customer who really does buy twice would be silently merged into one charge. The merchant thinks it collected twice and only collected once. You'd be swapping a visible bug (double charge, refundable) for a quieter one (missing revenue, hard to reconcile).
- **It misses the exact race you described.** The retry arrives about 10s in, while the first request is still waiting on the slow processor. If the charge row is only written after the processor responds, the retry's lookup finds nothing, and both requests charge the card. A time-window check has no way to see an in-flight request.
- **The window is arbitrary.** A client with backoff that retries at 65s gets through.
- **"Same card" means comparing card data.** That has to be a token or fingerprint, never the PAN, or you've widened your PCI scope.

### What I'd ship

**a) `Idempotency-Key` header on `POST /v1/charges`** (the Stripe-style pattern that merchant developers already know):

```sql
CREATE TABLE idempotency_keys (
  merchant_id    bigint      NOT NULL,
  key            text        NOT NULL,
  request_hash   text        NOT NULL,   -- hash of the canonicalized request body
  status         text        NOT NULL CHECK (status IN ('in_progress', 'completed')),
  charge_id      bigint,
  response_code  int,
  response_body  jsonb,
  created_at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (merchant_id, key)
);
```

Request flow:

1. `INSERT ... ON CONFLICT (merchant_id, key) DO NOTHING RETURNING *`. The primary key does the concurrency control, so two simultaneous requests can't both win.
2. **Inserted:** process the charge, then store the response and set `status = 'completed'`.
3. **Conflict:** load the existing row, then:
   - `request_hash` differs → `422` (key reused with different parameters)
   - `in_progress` → `409` with `Retry-After` (the original is still running)
   - `completed` → replay the stored status code and body exactly
4. Expire keys after 24h or more with a cleanup job. That's long enough to cover any reasonable retry policy.

**b) Write the charge as `pending` *before* calling the processor.** Every request then leaves a durable record before the slow part starts. This also handles a crash mid-call: a reconciler can take any charge stuck in `pending` and ask the processor what actually happened, instead of leaving it in limbo.

**c) Pass an idempotency key to the processor too, if it supports one.** Most major processors do, but check your processor's docs. For example, use your internal charge ID as the key. That protects you from your *own* retries to the processor.

**d) Keep your response time under the clients' 10s timeout where you can.** If the processor hasn't answered in about 8s, return `202` with the charge in `pending` status and let the merchant poll or get a webhook. Whether that's viable depends on your API contract. It's a bigger change, so treat it as a follow-up.

### The catch: merchants you don't control won't send the header tomorrow

The key only protects merchants who send it. So:

- Ship it as opt-in, document it, and contact the merchants behind the 17 incidents first. Your logs should show which ones retry.
- For requests **without** a key, don't auto-merge. Run your heuristic as **detection only**: flag and alert on likely duplicates so you can refund quickly. If a specific merchant asks for it, you could enable auto-dedupe for just that merchant as a narrow, explicit setting.
- Later, consider making the key required in `/v2` or for new integrations.

## 2. `amount` float to integer cents: not in place, and not in the same deploy

Changing the unit of an existing field in a public payments API is the most dangerous kind of breaking change, because nothing fails loudly. A merchant client reading `1999` as dollars shows or reconciles $1,999.00. One that sends `19.99` to an endpoint that now expects cents charges $0.20, or you round it somehow. Your ~40 integrations won't all update on your deploy day, and you can't make them.

"Fixed for everyone at once" really means broken for everyone at once, except the merchants who happened to deploy in sync with you.

### What I'd ship

- **Fix the rounding bugs internally now, without changing the contract.** The bugs almost certainly come from doing arithmetic on JS floats somewhere between Postgres and the response. Store integer cents in the DB (`bigint`), do all math in integer cents, and turn cents into dollars only at the serialization edge (`cents / 100` for output, parsed input converted with `Math.round(value * 100)` plus validation that rejects more than 2 decimal places). One thing to check: I believe node-postgres returns `NUMERIC` and `BIGINT` columns as strings by default, so if anything does `parseFloat` on a `NUMERIC` money column, that's a likely source. Please confirm against your `pg` version and code.
- **Add a new field alongside the old one:** `amount_cents: 1999` (or `amount_minor` plus `currency` if multi-currency is on your horizon). This is additive, so nobody breaks.
- **Deprecate `amount`:** announce it, add a `Deprecation` / `Sunset` header, track which merchants still read it (as far as you can tell), and remove it only in `/v2` or after a sunset date you've communicated.
- **Apply the same approach to request bodies.** Accept `amount_cents` as input and keep accepting `amount` during the deprecation window. Reject requests that send both and disagree.

---

## Why these should be separate deploys

Both changes touch `POST /v1/charges`, one of them affects money semantics, and the idempotency work changes how the endpoint handles concurrency. If something goes wrong in a combined release, you won't be able to tell which change caused it, and a rollback reverts the double-charge fix too. I'd ship the idempotency work first, since it addresses active customer harm. Ship the internal cents fix plus the additive `amount_cents` field as its own release.

**Sprint plan I'd commit to:**
1. Pending-before-processor write, the `Idempotency-Key` table and middleware, the processor-side idempotency key, and duplicate *detection* alerts for keyless requests. Tests should cover concurrent requests with the same key (for example, two parallel supertest calls asserting exactly one processor call), hash mismatch, and replay.
2. Integer cents internally, the additive `amount_cents` field, and a deprecation notice for `amount`.

The SQL and flow above are a design sketch I haven't run against your schema, so adapt the names and types to your codebase. The overall approach (idempotency keys plus additive API changes) is the standard, well-established one for this class of problem.
