## Latest user message
Node 20, Express 4.19. We have an invoice download route and Chrome keeps saving PDFs as "download" with no extension, and sometimes shows them as text/plain in the preview:

```js
const express = require('express');
const path = require('path');
const fs = require('fs');
const app = express();

app.get('/invoices/download', (req, res) => {
  const file = req.query.file; // e.g. "2024/INV-00123.pdf"
  const full = path.join(__dirname, 'storage', 'invoices', file);
  fs.readFile(full, (err, data) => {
    if (err) return res.status(404).send('Not found: ' + full);
    res.send(data);
  });
});
```

The links are generated on the customer dashboard, like `/invoices/download?file=2024/INV-00123.pdf`. How do I get the right content type and filename so it downloads as INV-00123.pdf?

## Rubric (what a strong answer does)
1. Fixes the actual question: sets Content-Type application/pdf and Content-Disposition attachment with filename INV-00123.pdf (e.g. via res.download(full, 'INV-00123.pdf') or res.type/res.attachment).
2. Flags that the user-controlled `file` parameter enables path traversal (e.g. `../` sequences) and proposes a concrete guard: resolve the path and verify it stays inside the invoices directory, restrict to an expected filename pattern, or look invoices up by ID instead of path.
3. Notes that the route should check the requested invoice belongs to the authenticated customer (authorization), since anyone can change the query parameter.
4. Points out that the 404 message echoes the full server file path and should return a generic message instead.

## Answer A
Use `res.download()`. It sets `Content-Type` from the file extension (`application/pdf`) and adds `Content-Disposition: attachment; filename="INV-00123.pdf"`, so you don't have to write either header yourself. Before you ship it, though, the route has two security holes that matter more than the filename problem. The fix below covers both.

### Why Chrome shows "download" and text/plain

- `res.send(buffer)` sends raw bytes. It sends no `Content-Disposition` header. As far as I recall, it also defaults the type to `application/octet-stream` (recalled, not verified; check `res.send` in `express/lib/response.js`).
- With no filename header, Chrome names the file after the last URL segment, which is `download`, and it has no content type to pick an extension from.
- The `text/plain` preview probably comes from Chrome's MIME sniffing or from a proxy or CDN rewriting the type. Sending an explicit, correct `Content-Type` removes that uncertainty either way.

### The bigger problems

1. **Path traversal.** `file` goes straight into `path.join`. A request like `?file=../../../../etc/passwd` or `?file=../../.env` resolves outside `storage/invoices`, and `fs.readFile` will serve whatever it lands on.
2. **No authorization check (IDOR).** Any logged-in user, or anyone at all if the route isn't behind auth, can download any invoice by guessing `INV-00124.pdf`. Sequential invoice numbers make guessing easy.
3. **Information leak.** `'Not found: ' + full` sends your absolute server path to the client.

### Fixed route (keeps your current URL shape)

```js
const express = require('express');
const path = require('path');

const app = express();

const INVOICE_ROOT = path.join(__dirname, 'storage', 'invoices');
// Whitelist the exact shape you generate: "2024/INV-00123.pdf"
const INVOICE_PATH_PATTERN = /^\d{4}\/INV-\d{5}\.pdf$/;

app.get('/invoices/download', requireAuth, async (req, res, next) => {
  const file = req.query.file;

  if (typeof file !== 'string' || !INVOICE_PATH_PATTERN.test(file)) {
    return res.status(400).json({ error: { code: 'INVALID_FILE', message: 'Invalid invoice reference' } });
  }

  try {
    // Replace with your real ownership check (DB lookup by invoice number + customer id)
    const allowed = await invoiceBelongsToCustomer(file, req.user.customerId);
    if (!allowed) {
      // 404 rather than 403 so the response does not reveal which invoices exist
      return res.status(404).json({ error: { code: 'NOT_FOUND', message: 'Invoice not found' } });
    }
  } catch (err) {
    return next(err);
  }

  const downloadName = path.basename(file); // "INV-00123.pdf"

  res.download(file, downloadName, { root: INVOICE_ROOT }, (err) => {
    if (!err) return;
    if (res.headersSent) {
      // Stream failed mid-transfer; nothing useful can be sent to the client now
      console.error('Invoice download aborted', { file, err: err.message });
      return;
    }
    if (err.code === 'ENOENT' || err.status === 404 || err.statusCode === 404) {
      return res.status(404).json({ error: { code: 'NOT_FOUND', message: 'Invoice not found' } });
    }
    next(err);
  });
});
```

Notes:

- **Three layers of defense.** The regex stops traversal before any filesystem call. Passing `root` makes Express's `send` resolve the path relative to that directory and refuse `..` segments. The ownership check stops IDOR. The regex alone would handle traversal, but the other two layers cost nothing.
- **Signature.** Express 4.x supports `res.download(path, filename, options, fn)`, and `options.root` has been there since roughly 4.16 (recalled, not verified; check the 4.x API docs). It streams the file, so you also stop buffering entire PDFs into memory with `readFile`.
- **Non-ASCII filenames.** `res.download` builds the header with the `content-disposition` package, which adds the `filename*=UTF-8''...` form when needed. Don't build that header by hand.
- `requireAuth` and `invoiceBelongsToCustomer` are placeholders for your own middleware and data access.

### If you'd rather preview in the browser than download

Keep the correct filename and send it `inline`:

```js
res.type('pdf');
res.set('Content-Disposition', `inline; filename="${downloadName}"`); // safe: downloadName matched the regex
res.sendFile(file, { root: INVOICE_ROOT }, callback);
```

Chrome then opens the PDF viewer, and "Save" defaults to `INV-00123.pdf`.

### Better long-term design

Stop putting storage paths in URLs. Use `/invoices/:invoiceId/download`, look the invoice up in the DB scoped to the current customer, and read the file path from that DB record. The client never controls a filesystem path, and the URL ending (`.../INV-00123/download`) no longer matters because the header supplies the filename.

## Answer B
Use `res.download()`. It sets `Content-Type` from the file extension and adds `Content-Disposition: attachment; filename="INV-00123.pdf"`. Before shipping it, though, you need to fix a more serious problem in this route: as written it lets anyone read any file the Node process can read.

### Why Chrome does this

- **No `Content-Disposition` header.** Without one, Chrome builds the filename from the last URL path segment. Here that segment is `/invoices/download`, so the file is saved as `download`. The query string is ignored.
- **No explicit `Content-Type`.** `res.send(buffer)` doesn't know the buffer is a PDF. It falls back to a generic type (`application/octet-stream`, as I recall; check Express's `res.send` source to confirm). That leaves the browser guessing, and it explains the odd previews. You also aren't sending `X-Content-Type-Options: nosniff`, so the browser is free to sniff the content.

### The bigger problem: path traversal and information leak

```
/invoices/download?file=../../../../etc/passwd
/invoices/download?file=../../.env
```

`path.join` resolves `..` segments, so both of these URLs escape `storage/invoices`. On top of that, the 404 response (`'Not found: ' + full`) sends your absolute server path back to the client.

There's also an authorization gap. Even with traversal fixed, any user who can guess `2024/INV-00124.pdf` can download another customer's invoice. If invoices belong to customers, check ownership before serving the file.

### Fixed route

```js
const express = require('express');
const path = require('path');

const app = express();

const INVOICE_ROOT = path.join(__dirname, 'storage', 'invoices');
// Whitelist the exact shape you generate: "YYYY/INV-NNNNN.pdf"
const INVOICE_PATH_PATTERN = /^(\d{4})\/(INV-\d{5})\.pdf$/;

app.get('/invoices/download', async (req, res, next) => {
  const requested = String(req.query.file ?? '');
  const match = INVOICE_PATH_PATTERN.exec(requested);
  if (!match) {
    return res.status(400).json({ error: { code: 'INVALID_FILE', message: 'Invalid invoice reference' } });
  }

  // Authorization: make sure this invoice belongs to the logged-in customer.
  // const allowed = await invoiceBelongsTo(req.user.id, match[2]);
  // if (!allowed) return res.status(404).end();

  const downloadName = path.basename(requested); // "INV-00123.pdf"

  res.set('X-Content-Type-Options', 'nosniff');
  res.download(requested, downloadName, { root: INVOICE_ROOT, dotfiles: 'deny' }, (err) => {
    if (!err) return;
    if (res.headersSent) return next(err); // stream failed mid-transfer; let Express close it
    if (err.code === 'ENOENT' || err.status === 404) {
      return res.status(404).json({ error: { code: 'NOT_FOUND', message: 'Invoice not found' } });
    }
    next(err);
  });
});
```

What changed:

- **`res.download(path, filename, options, callback)`** (the 4-argument form with `options` exists in Express 4.16+, recalled, so check the 4.x API docs). It sets:
  - `Content-Disposition: attachment; filename="INV-00123.pdf"`, which fixes the filename.
  - `Content-Type: application/pdf` from the `.pdf` extension, which fixes the preview.
- **`root` option**: the relative path is resolved inside `INVOICE_ROOT`. As I recall, the underlying `send` module rejects paths containing `..` with a 403 when `root` is set. Don't rely on that alone. The regex whitelist is the primary guard, because it only accepts the exact format your dashboard generates.
- **Streaming instead of `fs.readFile`**: the whole PDF is no longer buffered in memory, and you get `ETag`, `Last-Modified` and range support for free.
- **Error response**: the filesystem path is no longer included.

If you'd rather have the PDF **open in the browser tab** (with the right name if the user then saves it), use `res.sendFile` with an inline disposition:

```js
res.type('pdf');
res.set('Content-Disposition', `inline; filename="${downloadName}"`);
res.sendFile(requested, { root: INVOICE_ROOT, dotfiles: 'deny' }, callback);
```

`downloadName` is safe to put in the header here only because the regex has already limited it to `[A-Z0-9-.]`. If you ever allow arbitrary names, use `res.attachment(name)` or the `content-disposition` package. They handle quoting and RFC 5987 encoding for non-ASCII names.
