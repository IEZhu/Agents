The load step is already fast since we switched to COPY last quarter, so it's the Python transform. def lookup_customer(email):

## Answer A
**The cost is almost certainly not the string cleaning. It's `lookup_customer`, which makes one `SELECT` round-trip to Postgres for each of the 1.2M rows.** 50 min ÷ 1.2M rows ≈ 2.5 ms per row. That matches a network round-trip plus a query, not a `.strip().lower()` call. Vectorizing the other three lines won't help much, and PyPy can't speed up time spent waiting on the database. Fix the lookup first. That alone will probably get you well under 15 minutes, and you may not need PyPy.

Check this before rewriting anything:

```python
import cProfile, pstats
cProfile.run("main()", "etl.prof")   # wrap your loop in main()
pstats.Stats("etl.prof").sort_stats("cumulative").print_stats(15)
```

If `lookup_customer` / `cursor.execute` accounts for most of the cumulative time, that confirms it. Also check that `customers.email` has an index (`\d customers`). Without one, each lookup is a full sequential scan.

## Option 1 (recommended): do the join in Postgres

Send the raw rows to a staging table with COPY, then resolve `customer_id` with one set-based join. Python only does the light cleaning.

```python
import io
import pandas as pd
import psycopg2

conn = psycopg2.connect(DSN)
cur = conn.cursor()

# dtype=str + keep_default_na=False reproduces csv.DictReader: every field is a string, "" stays ""
df = pd.read_csv("export.csv", dtype=str, keep_default_na=False)

df["email"]   = df["email"].str.strip().str.lower()
df["amount"]  = pd.to_numeric(df["amount"].replace("", "0")).round(2)   # same as float(x or 0); bad values still raise
df["country"] = df["country"].map(COUNTRY_MAP).fillna(df["country"])    # same as COUNTRY_MAP.get(x, x)

buf = io.StringIO()
df[["email", "amount", "country", "ts"]].to_csv(buf, index=False, header=False)
buf.seek(0)

# Staging table with the same column types as sales, dropped at commit
cur.execute("CREATE TEMP TABLE sales_stage (LIKE sales) ON COMMIT DROP")
cur.copy_expert("COPY sales_stage (email, amount, country, ts) FROM STDIN WITH CSV", buf)
cur.execute("""
    INSERT INTO sales (customer_id, email, amount, country, ts)
    SELECT c.id, s.email, s.amount, s.country, s.ts
    FROM sales_stage s
    LEFT JOIN customers c ON c.email = s.email
""")
conn.commit()
```

`LIKE sales` copies the column types, so `ts` and `amount` are parsed exactly as your current COPY into `sales` parses them. Adjust if `sales` has NOT NULL or other constraints that the staging rows (with `customer_id` still NULL) would violate. `LIKE` without `INCLUDING CONSTRAINTS` copies NOT NULL but not CHECK constraints. If `customer_id` is NOT NULL, create the staging table with explicit columns instead.

## Option 2: preload a dict (smallest change)

If you'd rather keep the join in Python, run one query instead of 1.2M:

```python
cur.execute("SELECT email, id FROM customers")
email_to_id = dict(cur.fetchall())

df["customer_id"] = df["email"].map(email_to_id).astype("Int64")
cols = ["customer_id", "email", "amount", "country", "ts"]
buf = io.StringIO()
df[cols].to_csv(buf, index=False, header=False)
buf.seek(0)

conn.commit()
```

Memory scales with the size of `customers`. Tens of millions of rows start to hurt, and Option 1 has no such limit.

## Things to watch in the vectorized version

- **`customer_id` dtype.** Once there's a single miss, a plain `.map()` produces float64, so `to_csv` writes `1234.0` and COPY into an integer column fails. Keep the `.astype("Int64")`: the nullable integer writes misses as empty fields, which COPY CSV reads as NULL, the same as your current `None`.
- **Keep everything as strings.** Without `dtype=str, keep_default_na=False`, pandas turns `""`/`"NA"`/`"null"` into NaN and may parse ZIP-like or ID-like columns as numbers. That silently changes the output.
- **Duplicate emails in `customers`.** Today `fetchone()` picks one row arbitrarily. A SQL `LEFT JOIN` would **duplicate the sales row**, and `dict()` keeps the last one. Check `SELECT email, count(*) FROM customers GROUP BY 1 HAVING count(*) > 1`. If that returns rows, dedupe them (e.g. `DISTINCT ON (email)`) or add a unique constraint.
- **Case and collation.** You lowercase the export side only. If `customers.email` stores mixed case, both the old and new code miss those rows. Behaviour is unchanged, but it may be a latent bug worth fixing (`lower(c.email)` with an expression index, or `citext`).
- **Rounding.** Python `round()` and pandas `.round()` both use round-half-to-even on binary floats, so results should match. If `amount` is `numeric` in Postgres, consider letting Postgres do the rounding (`round(s.amount, 2)` in the INSERT) to avoid float artifacts.
- **Validate before cutover.** Run old and new code on the same export and diff the outputs: row count, NULL `customer_id` count, and a checksum over the sorted CSV.

## PyPy: probably skip it

The plan has a built-in conflict: **PyPy is fast for pure-Python loops, but slow for C-extension-heavy code like pandas/numpy.** From memory (I haven't verified this against current releases, so check before committing):

- **psycopg2** is a CPython C extension. Under PyPy it either won't build or runs through the cpyext compatibility layer with significant overhead. The usual PyPy options are `psycopg2cffi` (a drop-in, but check how actively it's maintained) or **psycopg 3** in its pure-Python mode.
- **pandas/numpy** also run through cpyext on PyPy. They work, but often slower than on CPython, and wheel availability varies.
- So pick one approach: either **vectorize on CPython** (recommended), or keep a plain-Python row loop (with the dict lookup) on PyPy. Doing both combines the downsides.

After removing the per-row queries, I'd expect the transform to take seconds to a small number of minutes on CPython. That's an estimate, so profile it. The remaining time will likely be CSV parsing and the COPY/INSERT, and PyPy doesn't help with either.

**Priority:** 1) confirm with the profiler, 2) replace the per-row lookup (Option 1), 3) vectorize the cleaning on CPython, 4) consider PyPy only if you're still over budget, which is unlikely.


## Answer B
**Short version:** vectorizing and PyPy probably won't fix this, because the time is most likely going into `lookup_customer`. That function makes one synchronous database round trip per row, which is 1.2M `SELECT`s. Remove that and the job will probably drop from ~50 min to about a minute on plain CPython, without pandas or PyPy. Measure it before you rewrite anything.

## Why I think the lookup is the bottleneck

- 50 min ÷ 1.2M rows ≈ **2.5 ms per row**. That is about the cost of one query round trip to Postgres (network + parse/plan + execute). `strip().lower()`, `float()`, `round()` and a dict `.get()` together take on the order of a microsecond per row in CPython (a rough estimate, not measured). That's around 1000× less.
- **"Crept up"** is a clue. If `customers.email` has no index, or the index doesn't match the expression, each lookup is a sequential scan. The job would then slow down as the `customers` table grows, which matches what you're seeing. Check with:
  ```sql
  EXPLAIN (ANALYZE, BUFFERS) SELECT id FROM customers WHERE email = 'someone@example.com';
  ```
  `Seq Scan` here confirms it. Even with an index scan you still pay the per-row round trip, so the fix below applies either way.
- Vectorization speeds up Python-level CPU work. PyPy's JIT does the same. Neither one reduces time spent waiting on the network.

## Fix option A: prefetch customers once (smallest change)

This keeps your structure and semantics and replaces 1.2M queries with one.

```python
import csv, io, psycopg2

conn = psycopg2.connect(DSN)

# One pass over customers, streamed with a server-side cursor so memory stays flat while fetching
customers = {}
with conn.cursor(name="cust_prefetch") as c:
    c.itersize = 50_000
    c.execute("SELECT email, id FROM customers")
    for email, cid in c:
        customers.setdefault(email, cid)   # see duplicate-email note below

country_map = COUNTRY_MAP  # local alias
buf = io.StringIO()
w = csv.writer(buf)
with open("export.csv", newline="") as f:
    for r in csv.DictReader(f):
        email = r["email"].strip().lower()
        amount = round(float(r["amount"] or 0), 2)
        country = country_map.get(r["country"], r["country"])
        w.writerow([customers.get(email), email, amount, country, r["ts"]])

buf.seek(0)
with conn.cursor() as cur:
    cur.copy_expert(
        "COPY sales (customer_id, email, amount, country, ts) FROM STDIN WITH CSV", buf
    )
conn.commit()
```

The output matches your current code byte for byte, including `None` → empty field → `NULL` under `COPY ... CSV`, so it's easy to diff old vs new output on a sample. The cost is memory. As a rough guess, a Python dict of email→id takes ~150–200 bytes per entry, so a few hundred MB for a million customers. Check your customer count.

## Fix option B: push the transform into Postgres (fastest, most scalable)

COPY the raw file into a staging table, then do the cleanup and join in one set-based statement:

```sql
CREATE TEMP TABLE sales_raw (email text, amount text, country text, ts text);
-- COPY sales_raw FROM STDIN WITH CSV HEADER   (via copy_expert, streaming the file directly)

INSERT INTO sales (customer_id, email, amount, country, ts)
SELECT c.id,
       s.email_norm,
       round(coalesce(nullif(s.amount, ''), '0')::numeric, 2),
       coalesce(m.to_code, s.country),
       s.ts::timestamptz          -- or whatever sales.ts is
FROM (SELECT *, lower(btrim(email)) AS email_norm FROM sales_raw) s
LEFT JOIN customers   c ON c.email = s.email_norm
LEFT JOIN country_map m ON m.from_code = s.country;   -- COUNTRY_MAP loaded as a small table
```

You can stream the file straight into `copy_expert`, so Python never parses rows at all. Option B does change semantics in three places:
- `btrim(x)` trims only spaces by default. Python's `strip()` also removes tabs, newlines and other Unicode whitespace.
- `round(numeric, 2)` rounds half away from zero. Python `round(float, 2)` works on the binary float value (e.g. `round(2.675, 2) == 2.67`). A few cents can differ.
- If `customers.email` is **not unique**, the join **duplicates sales rows**. Your current code silently takes an arbitrary match. Check for this first.

## If you still want the pandas version

It's fine on CPython, but it isn't what saves the time here. The main gotchas:

```python
import pandas as pd

df = pd.read_csv("export.csv", dtype=str, keep_default_na=False,
                 usecols=["email", "amount", "country", "ts"])
df["email"] = df["email"].str.strip().str.lower()
df["amount"] = pd.to_numeric(df["amount"].replace("", "0")).round(2)
df["country"] = df["country"].map(COUNTRY_MAP).fillna(df["country"])
df["customer_id"] = df["email"].map(customers).astype("Int64")   # nullable int!

buf = io.StringIO()
df.to_csv(buf, index=False, header=False,
          columns=["customer_id", "email", "amount", "country", "ts"])
```

- **`dtype=str, keep_default_na=False`** is required. Without it, pandas turns `""`, `"NA"`, `"null"` (and possibly a real country code like `"NA"` for Namibia) into NaN and guesses types for `ts`.
- **`Int64`, not `int64`/float.** An unmatched lookup creates NaN, which silently makes the column float. `COPY` then receives `"123.0"` into an integer column and fails, or worse. The nullable `Int64` writes missing values as an empty field, which becomes `NULL`.
- **Rounding:** `Series.round` uses numpy's scale-and-round-half-even, which can differ from Python's `round()` on a few edge values. Diff a sample.
- `map(...).fillna(original)` will also "restore" any key whose `COUNTRY_MAP` value is deliberately `None`, which differs from your current behavior.

## PyPy + psycopg2: I'd drop PyPy from the plan

From memory, not verified here (check the current PyPy and psycopg docs):
- **psycopg2 is a CPython C extension.** On PyPy it either runs through the `cpyext` compatibility layer, which is slow for chatty call patterns like yours, or needs a replacement such as `psycopg2cffi` or psycopg 3's pure-Python/ctypes build. Each of those is a separate dependency with its own behavior differences to test.
- **pandas/numpy on PyPy** also go through `cpyext`. They generally *lose* performance compared to CPython, so "vectorize + PyPy" pulls in opposite directions: PyPy speeds up pure-Python loops, and vectorization moves work out of Python loops.
- Once the lookup is gone, the remaining CPU work is probably well under a minute on CPython. PyPy would add operational risk (different interpreter in prod, wheel availability, a second driver) to optimize something that no longer matters.
