## Answer A
### Коротко

N+1 у вас не убран: он остался в `get_total`. `obj.orderitem_set.aggregate(...)` не берёт данные из prefetch-кэша, а на каждый заказ отправляет в БД отдельный `SELECT SUM(...)`. При `page_size=200` это 200 лишних запросов на страницу. Скорее всего, именно они дают основную часть из 1.9 с, а не ModelSerializer. Поэтому менять порядок надо так: сначала убрать `aggregate`, потом замерить, и только если сериализация всё ещё заметна, переходить на orjson и ручные dict'ы. Код для обоих пунктов ниже, но начинать стоит с первого шага.

### 1. Главный фикс: считать total из prefetch

`prefetch_related("orderitem_set__product")` уже загрузил позиции в память, так что считаем по ним:

```python
class OrderSerializer(serializers.ModelSerializer):
    customer_email = serializers.CharField(source="customer.email")
    items = OrderItemSerializer(many=True, source="orderitem_set")
    total = serializers.SerializerMethodField()

    class Meta:
        model = Order
        fields = ["id", "created", "status", "customer_email", "items", "total"]

    def get_total(self, obj):
        # .all() читает prefetch-кэш; .aggregate() всегда идёт в БД
        return sum((item.qty * item.price for item in obj.orderitem_set.all()), Decimal("0"))
```

Можно и через `.annotate(total=Sum(F("orderitem__qty") * F("orderitem__price")))` в queryset. Это тоже корректно, пока в запросе нет других multi-valued JOIN'ов, но позиции всё равно подгружаются, так что сумма в Python проще и не добавляет запросов.

Обратите внимание на контракт ответа. Сейчас `total` приходит как `Decimal`, а стандартный `JSONEncoder` DRF отдаёт его строкой (если не менять `COERCE_DECIMAL_TO_STRING`, `SerializerMethodField` не форматирует значение сам). После замены на orjson это нужно учесть, подробности ниже.

Закрепите это тестом, чтобы регрессия не вернулась:


### 3. orjson-рендерер

Если профиль показывает, что заметная доля уходит на `json.dumps`:

```python
# api/renderers.py
from decimal import Decimal

import orjson
from django.utils.functional import Promise
from rest_framework.renderers import BaseRenderer


def _default(obj):
    # orjson не умеет Decimal и lazy-строки (переводы в сообщениях об ошибках DRF)
    if isinstance(obj, Decimal):
        return str(obj)  # тот же контракт, что у стандартного DRF-энкодера
    if isinstance(obj, Promise):
        return str(obj)
    raise TypeError(f"Type is not JSON serializable: {type(obj).__name__}")


class ORJSONRenderer(BaseRenderer):
    media_type = "application/json"
    format = "json"
    charset = None  # orjson отдаёт UTF-8 bytes

    def render(self, data, accepted_media_type=None, renderer_context=None):
        if data is None:
            return b""
        return orjson.dumps(data, default=_default, option=orjson.OPT_NON_STR_KEYS)
```

```python
# settings.py

    "DEFAULT_RENDERER_CLASSES": [
        "api.renderers.ORJSONRenderer",
        "rest_framework.renderers.BrowsableAPIRenderer",  # оставьте только для dev, если нужно
    ],
}
```

Нюансы. Я их не перепроверял в этом ответе, сверьтесь с README orjson для вашей версии:
- `orjson.dumps` возвращает `bytes`, `default` вызывается для неподдерживаемых типов, `OPT_NON_STR_KEYS` разрешает нестроковые ключи. Подклассы `dict`/`list` (DRF-шные `ReturnDict`/`ReturnList`) orjson, насколько я помню, сериализует нативно.
- `datetime` orjson сериализует сам в RFC 3339, но в формате `+00:00`, а DRF-шный `DateTimeField` пишет `Z`. Через ModelSerializer дата приходит уже строкой, так что разницы нет. В ручных dict'ах это важно (см. ниже).
- Есть готовый пакет `drf-orjson-renderer` (название вспоминаю по памяти, проверьте на PyPI). Своих 20 строк обычно достаточно, лишняя зависимость ради этого не нужна.

### 4. Ручная сборка dict'ов

Имеет смысл только если профиль после шагов 1–3 показывает, что `to_representation` всё ещё занимает значимую часть. Цена: теряете декларативность, схему для OpenAPI (drf-spectacular) и единый контракт форматирования. Эти функции придётся поддерживать вручную.

```python
# api/fast_serializers.py
from decimal import Decimal

from rest_framework.fields import DateTimeField

_dt_field = DateTimeField()  # тот же формат дат, что у ModelSerializer (с 'Z', с учётом TIME_ZONE)


def serialize_order_item(item) -> dict:
    return {
        "id": item.id,
        "product_name": item.product.name,
        "qty": item.qty,
        "price": str(item.price),  # DecimalField DRF отдаёт строкой
    }


def serialize_order(order) -> dict:
    items = order.orderitem_set.all()  # prefetch-кэш, без запросов
    total = sum((i.qty * i.price for i in items), Decimal("0"))
    return {
        "id": order.id,
        "created": _dt_field.to_representation(order.created),
        "status": order.status,
        "customer_email": order.customer.email,
        "items": [serialize_order_item(i) for i in items],
        "total": str(total),
    }
```

```python
# api/views.py
from django.db.models import Prefetch
from rest_framework import viewsets
from rest_framework.response import Response

from .fast_serializers import serialize_order


class OrderViewSet(viewsets.ReadOnlyModelViewSet):
    serializer_class = OrderSerializer  # остаётся для retrieve и OpenAPI-схемы

    def get_queryset(self):
        return (
            Order.objects.select_related("customer")
            .only("id", "created", "status", "customer__email")
            .prefetch_related(
                Prefetch(
                    "orderitem_set",
                    queryset=OrderItem.objects.select_related("product")
                    .only("id", "order_id", "qty", "price", "product__name"),
                )
            )
            .order_by("-created")
        )

    def list(self, request, *args, **kwargs):
        queryset = self.filter_queryset(self.get_queryset())
        page = self.paginate_queryset(queryset)
        if page is None:
            return Response([serialize_order(o) for o in queryset])
        return self.get_paginated_response([serialize_order(o) for o in page])
```

Замечания:
- `order_id` в `only()` для `OrderItem` обязателен: по нему Django раскладывает prefetch по заказам. Названия полей (`order`, `product`) я взял из вашего кода по догадке, сверьте с моделями.
- `.only()` даёт выигрыш, только если в таблицах есть широкие колонки (текст, JSON). Если их нет, можно не усложнять.
- Проверьте, что `DecimalField` у `price` в модели имеет нужный `decimal_places`. `str(Decimal)` из PostgreSQL `numeric(p, s)` обычно сохраняет scale колонки, но у DRF это `quantize` по `decimal_places`. На краевых значениях сравните выводы.
- Контракт-тест, который удержит совместимость ответа:

```python
def test_fast_serializer_matches_model_serializer(self):
    orders = OrderViewSet().get_queryset()[:20]
    self.assertEqual(
        [serialize_order(o) for o in orders],
        # приведение total к строке — если в старом ответе он строкой через JSONEncoder
        json.loads(json.dumps(OrderSerializer(orders, many=True).data, cls=DjangoJSONEncoder)),
    )
```

## Answer B
### Коротко

N+1 в этом коде не убран: он остался в `get_total`. `obj.orderitem_set.aggregate(...)` всегда идёт отдельным запросом в БД. Prefetch-кэш он не использует, потому что `aggregate()` строит новый QuerySet. При `page_size=200` это **200 лишних SQL-запросов на каждую страницу**. Скорее всего, основная часть из 1.9 с уходит именно на них, а не на ModelSerializer. Для 200 заказов по 5–6 позиций (примерно 1200–1400 объектов) сериализация через DRF по моему опыту занимает десятки миллисекунд, а не секунды. Это оценка, не замер, поэтому ниже есть способ проверить.

Поэтому порядок такой: сначала убираем запросы в `get_total` и меряем. Код для orjson и ручных dict'ов я тоже дам, но переходить на них стоит, только если профилирование после первого шага покажет, что сериализация действительно заметна.

### Шаг 1 (главный): убрать запросы из `get_total`

Позиции уже загружены prefetch'ем, поэтому сумму проще посчитать в Python по тому же кэшу:

```python
from django.db.models import Prefetch


class OrderItemSerializer(serializers.ModelSerializer):
    product_name = serializers.CharField(source="product.name")

    class Meta:
        model = OrderItem
        fields = ["id", "product_name", "qty", "price"]


class OrderSerializer(serializers.ModelSerializer):
    customer_email = serializers.CharField(source="customer.email")
    items = OrderItemSerializer(many=True, source="orderitem_set")
    total = serializers.SerializerMethodField()

    class Meta:
        model = Order
        fields = ["id", "created", "status", "customer_email", "items", "total"]

    def get_total(self, obj):
        # .all() reads the prefetch cache — no extra query, unlike .aggregate()
        return sum((item.qty * item.price for item in obj.orderitem_set.all()), 0)


class OrderViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = (
        Order.objects.select_related("customer")
        .prefetch_related(
            Prefetch(
                "orderitem_set",
                queryset=OrderItem.objects.select_related("product"),
            )
        )
        .order_by("-created")
    )
    serializer_class = OrderSerializer
```

Здесь два изменения:
- в `get_total` вместо `aggregate()` используется `.all()` по prefetch-кэшу, так что 200 запросов превращаются в 0;
- `Prefetch(..., select_related("product"))` вместо `"orderitem_set__product"`: позиции и товары приходят одним JOIN-запросом, а не двумя.

В итоге на страницу должно уходить 3 запроса: `COUNT` от пагинатора, заказы с клиентами и позиции с товарами.

Если по `total` нужно сортировать или фильтровать, лучше сделать аннотацию в SQL:

```python
from decimal import Decimal
from django.db.models import DecimalField, F, Sum, Value
from django.db.models.functions import Coalesce

MONEY = DecimalField(max_digits=12, decimal_places=2)  # подставьте свои размеры

queryset = queryset.annotate(
    total=Coalesce(
        Sum(F("orderitem__qty") * F("orderitem__price"), output_field=MONEY),
        Value(Decimal("0")),
        output_field=MONEY,
    )
)
# в сериализаторе: total = serializers.DecimalField(max_digits=12, decimal_places=2, read_only=True)
```

`output_field` обязателен, потому что `int * Decimal` иначе даёт ошибку mixed types. `orderitem` здесь — имя обратной связи по умолчанию, если у FK не задан `related_name`.

Одна деталь по формату. `price` сейчас отдаётся строкой (по умолчанию в DRF `COERCE_DECIMAL_TO_STRING=True`), а `get_total` вернёт `Decimal`, который обработает уже JSON-энкодер. Если клиентам нужен одинаковый формат, возвращайте `str(...)` или используйте вариант с `DecimalField`.

### Шаг 2: orjson-рендерер

orjson (насколько я помню API, сверьтесь с README orjson) не сериализует `Decimal` без `default`. Стандартный DRF-энкодер это умеет, поэтому нужен хук:

```python
# api/renderers.py
from decimal import Decimal

import orjson
from rest_framework.renderers import BaseRenderer


def _orjson_default(obj):
    if isinstance(obj, Decimal):
        return str(obj)
    raise TypeError(f"Type {type(obj).__name__} is not JSON serializable")


class ORJSONRenderer(BaseRenderer):
    media_type = "application/json"
    format = "json"
    charset = None  # JSON is always UTF-8; same as DRF's JSONRenderer

    def render(self, data, accepted_media_type=None, renderer_context=None):
        if data is None:
            return b""
        return orjson.dumps(data, default=_orjson_default)
```

```python
# settings.py
REST_FRAMEWORK = {
    "DEFAULT_RENDERER_CLASSES": [
        "api.renderers.ORJSONRenderer",
        "rest_framework.renderers.BrowsableAPIRenderer",  # при необходимости
    ],
}
```

`ReturnDict` и `ReturnList` из DRF являются подклассами `dict` и `list`. orjson, насколько я помню, сериализует такие подклассы по умолчанию. Это проверяется тем же контрактным тестом, что ниже. Есть готовый пакет `drf-orjson-renderer`, но для 15 строк кода отдельная зависимость, на мой взгляд, не нужна.

Реалистичный выигрыш здесь невелик: `json.dumps` для ответа примерно на 1400 объектов, скорее всего, занимает единицы миллисекунд.

### Шаг 3: сериализация без ModelSerializer (только для горячего list)

Вот реализация, которая не ломает пагинацию и оставляет `retrieve` на обычном сериализаторе:

```python
def _item_to_dict(item: OrderItem) -> dict:
    return {
        "id": item.id,
        "product_name": item.product.name,
        "qty": item.qty,
        "price": str(item.price),
    }


def _order_to_dict(order: Order) -> dict:
    items = list(order.orderitem_set.all())  # prefetch cache
    return {
        "id": order.id,
        "created": _format_datetime(order.created),
        "status": order.status,
        "customer_email": order.customer.email,
        "items": [_item_to_dict(i) for i in items],
        "total": str(sum((i.qty * i.price for i in items), 0)),
    }


def _format_datetime(value):
    # mirror DRF DateTimeField default output: ISO 8601, UTC as "Z"
    iso = value.isoformat()
    return iso[:-6] + "Z" if iso.endswith("+00:00") else iso


class OrderViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = ...  # как в шаге 1
    serializer_class = OrderSerializer  # остаётся для retrieve и схемы OpenAPI

    def list(self, request, *args, **kwargs):
        queryset = self.filter_queryset(self.get_queryset())
        page = self.paginate_queryset(queryset)
        orders = page if page is not None else queryset
        data = [_order_to_dict(o) for o in orders]
        if page is not None:
            return self.get_paginated_response(data)
        return Response(data)
```

Форматы нужно сверить с вашими настройками. `_format_datetime` и `str(Decimal)` повторяют поведение DRF по умолчанию, как я его помню, но `DATETIME_FORMAT`, `COERCE_DECIMAL_TO_STRING` и `decimal_places` у вас могут отличаться. Поэтому обязательно добавьте контрактный тест, который сравнивает старый и новый вывод:

```python
def test_manual_dict_matches_serializer(self):
    orders = list(OrderViewSet.queryset)
    expected = OrderSerializer(orders, many=True).data
    actual = [_order_to_dict(o) for o in orders]
    self.assertEqual(orjson.loads(orjson.dumps(expected, default=_orjson_default)),
                     orjson.loads(orjson.dumps(actual, default=_orjson_default)))
```

Минусы у этого подхода такие: схема ответа дублируется в двух местах, OpenAPI-генерация продолжит смотреть на `OrderSerializer`, и при каждом новом поле нужно править обе версии. Контрактный тест как раз защищает от их расхождения.
