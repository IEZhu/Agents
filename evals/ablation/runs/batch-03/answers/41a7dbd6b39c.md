## Коротко

Дубли и пропуски даёт **offset-пагинация** (`page`/`page_size`) на данных, которые меняются. Лечится переходом на **cursor-пагинацию (keyset)**. Кроме этого, перед релизом надо исправить ещё два блокера: токен в query string и отсутствие версионирования API. Мобильные клиенты обновляются медленно, поэтому всё, что уйдёт в этом релизе, придётся поддерживать годами.

---

## 1. Почему дубли и пропуски

`page=3&page_size=20` в итоге превращается в `ORDER BY ... OFFSET 40 LIMIT 20`. Offset считается от **текущего** состояния таблицы, а не от того, что пользователь видел.

**Дубли.** Пользователь загрузил страницу 1 (заказы 1–20). Сверху добавились 3 новых заказа. Теперь `OFFSET 20` начинается со старого заказа №18, и заказы 18–20 он получит второй раз.

**Пропуски.** Заказ со страницы 1 удалили, или сменился статус и заказ выпал из фильтра (например, лента показывает только активные). Всё сдвигается на одну позицию вверх, и один заказ со стыка страниц пользователь не увидит никогда.

**Третья причина: нестабильная сортировка.** Её часто упускают, проверьте обязательно. Если `order_by` отсутствует или идёт по неуникальному полю (`created_at` с одинаковыми значениями, `status`), PostgreSQL не гарантирует порядок строк с равными ключами между запросами. Тогда дубли и пропуски будут даже без новых заказов.

## 2. Как чинить

### Бэкенд: CursorPagination

В DRF есть встроенная `CursorPagination`. Она запоминает позицию последнего элемента, а не номер страницы. Запрос следующей страницы выглядит как «дай 20 заказов старше этого», поэтому вставки сверху и удаления на неё не влияют.

```python
# pagination.py
from rest_framework.pagination import CursorPagination

class OrderFeedPagination(CursorPagination):
    page_size = 20
    page_size_query_param = "page_size"
    max_page_size = 50          # иначе клиент может запросить page_size=100000
    ordering = "-id"            # уникальное, монотонное, не меняется
```

```python
class OrderViewSet(viewsets.ReadOnlyModelViewSet):
    serializer_class = OrderSerializer
    pagination_class = OrderFeedPagination

    def get_queryset(self):
        return Order.objects.filter(user=self.request.user)
```

Ответ содержит `next`/`previous` с непрозрачным `cursor=...`. Клиент ничего не вычисляет, а просто идёт по ссылке `next`.

Важный нюанс. Поле сортировки должно быть **уникальным (или почти уникальным) и неизменяемым**. Насколько я помню, DRF строит позицию курсора по первому полю `ordering`, а совпадения значений обрабатывает через offset внутри курсора. Поэтому `ordering = "-created_at"` с частыми совпадениями частично возвращает исходную проблему. Если `id` автоинкрементный и совпадает с порядком создания, берите `-id`. Если сортировать нужно по полю, которое меняется (`updated_at`, приоритет), курсор это тоже не спасёт: такой заказ «перепрыгнет» через курсор. Тогда нужен отдельный подход, например snapshot-время в первом запросе.

### Новые заказы вверху ленты

Курсор вниз их не покажет, и это правильно. Для новых заказов нужен отдельный механизм: pull-to-refresh или плашка «N новых заказов», которая запрашивает `previous` от первого элемента (или `?since_id=<max id на экране>`).

### Клиент: страховка

На iOS/Android стоит дедуплицировать ленту по `id` (DiffableDataSource / DiffUtil с `id` как ключом). От пропусков это не спасёт, но дубль в UI не появится ни при каком баге бэка.

## 3. Что ещё кривое в эндпоинтах

### [BLOCKER] `access_token` в query string
**Где:** `GET /api/getOrders?...&access_token=eyJ...`
**Проблема:** URL оседает в access-логах nginx/балансировщика, в логах Django, в APM/Sentry breadcrumbs, в логах прокси и иногда в аналитике. Каждый такой лог превращается в хранилище рабочих токенов пользователей.
**Фикс:** `Authorization: Bearer <token>`, а параметр в query перестать принимать. На время перехода можно принимать оба варианта, но только для старых версий приложения. И почистить/ротировать логи, где токены уже лежат.

### [BLOCKER] Нет версионирования API
**Проблема:** старые версии приложения будут жить у пользователей месяцами. Если в этом релизе поменять контракт `/api/getOrders`, старые клиенты сломаются. Если не менять, кривой контракт останется навсегда.
**Фикс:** новые эндпоинты выпускать под `/api/v1/...` (DRF: `URLPathVersioning`), старые оставить как legacy до отключения. Плюс механизм «минимальная поддерживаемая версия», чтобы со временем можно было заставить обновиться.

### [BLOCKER, если не проверено] Проверка владельца заказа (IDOR)
**Где:** `cancel` и `updateAddress` принимают `order_id` из тела.
**Проблема:** из запроса не видно, проверяется ли, что заказ принадлежит `request.user`. Если там `Order.objects.get(id=order_id)`, любой пользователь может отменить или перенаправить чужой заказ, перебирая id.
**Фикс:** всегда искать заказ внутри `Order.objects.filter(user=request.user)`. Для чужого заказа отдавать 404, а не 403, чтобы не раскрывать, что такой id существует. Код я не видел, поэтому просто проверьте это место.

### [MAJOR] HTTP 200 на любые ошибки
**Проблема:**
- HTTP-клиенты, ретраи, circuit breakers и мониторинг (APM, алерты по 5xx) ошибок не видят: для них всё успешно. Упавший бэк выглядит как «ok: false» с кодом 200.
- Прокси и CDN могут закэшировать ответ с ошибкой как успешный.
- `msg: "Заказ не найден"` — человекочитаемая локализованная строка. Если мобильщики ветвят логику по ней, первая же правка текста или перевод сломает клиент.

Мобильщикам на самом деле не проще: они всё равно парсят тело и проверяют `ok`. Проверить статус-код — одна строка в любом сетевом слое (URLSession/Alamofire/Retrofit/OkHttp).

**Фикс:** нормальные статусы (400/401/403/404/409/422/5xx) плюс единый формат тела со **стабильным машинным кодом**:
```json
{"error": {"code": "order_not_found", "message": "Заказ не найден"}}
```
В DRF это делается одним кастомным `EXCEPTION_HANDLER` в `REST_FRAMEWORK` settings, а не правкой каждой view.

### [MAJOR] Неидемпотентные мутации на мобильной сети
**Проблема:** на мобилке запрос часто уходит, а ответ теряется, и клиент повторяет его. Если повторный `cancel` возвращает ошибку «уже отменён», пользователь видит ошибку при успешной операции.
**Фикс:** `cancel` уже отменённого заказа отвечает 200 с текущим состоянием заказа. Для недопустимых переходов (заказ уже доставлен) отвечать 409 с `code: "order_not_cancellable"`. Переход статуса делать атомарно: `select_for_update()` или условный `UPDATE ... WHERE status IN (...)`, иначе параллельные `cancel` и `updateAddress` создадут гонку. Для `updateAddress` нужна та же проверка: можно ли менять адрес в текущем статусе.

### [MAJOR] Нет верхней границы `page_size`
`page_size=100000` одним запросом нагружает БД и сериализатор. Нужен `max_page_size` (есть в примере выше).

### [MINOR] Именование и консистентность
- Глаголы в URL (`getOrders`, `cancel`, `updateAddress`) и смешение стилей: `order_id` vs `orderId`, `new_address` в snake_case рядом с `orderId` в camelCase. Мобильщики будут ловить баги маппинга на ровном месте.
- Предложение для v1:
  ```
  GET   /api/v1/orders/?cursor=...        — лента
  GET   /api/v1/orders/{id}/              — один заказ
  POST  /api/v1/orders/{id}/cancel/       — действие (@action в ViewSet)
  PATCH /api/v1/orders/{id}/  {"address": "..."}
  ```
  id берётся из URL, в теле только данные. Выберите один стиль полей и держите его везде. Для DRF естественен snake_case. Если клиентам нужен camelCase, его делают на уровне renderer/parser, а не вручную в сериализаторах.
- `new_address` принимается строкой: проверьте, что длина ограничена и есть хотя бы базовая валидация в сериализаторе.

### [POSITIVE]
Бесконечная прокрутка с серверной пагинацией, а не загрузка всего списка, — правильная основа. Переход на курсор ложится на неё без переделки UI.
