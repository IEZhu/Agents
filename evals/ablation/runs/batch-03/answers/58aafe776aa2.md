**Short version:** both plans aim at the right problems, but I wouldn't ship either one as written. The dedupe heuristic will block legitimate charges and still let some duplicates through. Changing the units of `amount` in place is a silent breaking change for 40 clients you don't control, and it could cause errors worth 100x the intended amount. What I'd ship instead is below.

## 1. Duplicate charges: use idempotency keys, not "same amount + card within 60s"

### Problems with the heuristic

- **It blocks real charges.** Two $4.50 coffees on the same card a minute apart, a split shipment, a customer buying two tickets in separate checkouts: all of these are legitimate, and they'd get the first charge back with no second charge made. The merchant thinks they were paid twice and were only paid once. That's a harder bug to find than a double charge, because nobody complains about it at checkout.
- **It misses slow retries.** A 60s window assumes retries arrive quickly. Clients with backoff, job queues or a manual "retry failed payments" button will retry after 60s.
- **It has a race condition.** In your failure case the first request is still in flight (waiting on the slow processor) when the retry arrives. A "look for an existing charge" query finds nothing because the first charge hasn't been written yet. So the heuristic probably wouldn't have stopped many of your 17 incidents. You can check this from logs: compare the retry arrival time with the time the first charge row was committed.
- **"Same card" needs care.** Compare on a processor token or card fingerprint, never on PAN data, or you pull more of the system into PCI scope.

### What I'd ship

**a) Support an `Idempotency-Key` header on POST /v1/charges.** This is the standard pattern (Stripe popularized it, and there's an IETF draft for the header). The client generates a unique key per logical charge and sends the same key on every retry. The server guarantees that one key maps to at most one charge.

Schema sketch:

```sql
CREATE TABLE idempotency_keys (
  merchant_id   bigint      NOT NULL,
  key           text        NOT NULL,
  request_hash  text        NOT NULL,         -- hash of method + path + canonical body
  status        text        NOT NULL,         -- 'in_progress' | 'completed'
  response_code int,
  response_body jsonb,
  created_at    timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (merchant_id, key)
);
```

Request flow:

1. `INSERT ... (status = 'in_progress') ON CONFLICT (merchant_id, key) DO NOTHING RETURNING *`. The primary key closes the race: only one request can claim the key.
2. If the insert claimed the key, call the processor, store the response and set `status = 'completed'`.
3. If the key already existed:
   - `request_hash` differs → `422`, because the key was reused for a different request.
   - `in_progress` → `409` with `Retry-After`, because the original request is still running.
   - `completed` → replay the stored status code and body exactly.
4. Scope keys per merchant and expire them after about 24h.

**b) Send an idempotency key to your upstream processor too**, if it supports one (most do; check its docs). Derive it from your charge ID. Your own retries to the processor then can't double-charge either, and that's the layer where the money actually moves.

**c) Deal with the merchants that don't send keys.** This is the hard part with 40 integrations you don't control:

- Use your logs to find out who produced the 17 duplicates. I'd guess it's a small number of merchants with 10s timeouts. Contact them directly and ask them to send `Idempotency-Key`. That's probably the highest-leverage step.
- If you still want a heuristic for key-less requests, make it **opt-in per merchant**, or have it flag instead of dedupe: create the charge but mark `possible_duplicate` and alert or auto-review it. Don't silently return a different charge than the one the client asked for.
- Look at your p99 latency against the 10s client timeout. If the processor is the slow part, a processor-side timeout under 10s that returns a clear `pending` state (plus a way to fetch the final status) cuts down the ambiguous-outcome window. Clients have to handle `pending` for this to work, so it's a longer-term change.

## 2. `amount` float → integer cents: right goal, wrong migration

Storing and computing money as integer minor units is correct. Changing what an existing field *means*, in place, for clients you don't control, is not.

- **It fails silently, not loudly.** A merchant that parses `amount` as dollars will now read `1999` as $1,999.00. Nothing throws. It shows up in their receipts, reconciliation, refund logic and accounting. Refunds are the worst case: if a client echoes the response amount back into a refund call, you've got a 100x refund.
- **"Fixed for everyone at once" really means "broken for everyone at once"** unless all 40 integrations deploy a matching change at the same moment. They won't.
- **Don't ship it in the same deploy as the idempotency work.** If something goes wrong with charges that day you'll have two confounded causes, and the amount change can't be rolled back once clients have adapted to it.

### What I'd ship

**Step 1: fix the rounding internally now. No API change needed.** The rounding bugs almost certainly come from floats inside your own code path. Postgres returns `numeric` columns as strings in node-postgres by default (recalled, not verified here; check your `pg` type parsers), and somewhere they get `parseFloat`-ed and multiplied.
- Store amounts as `bigint` cents (or confirm `numeric(12,2)` and never convert it to a JS float).
- Do all arithmetic in integer cents.
- Convert to a dollar float only in the response serializer, and only for the legacy field: `(cents / 100)` is exact enough for display, and the one float conversion happens at the edge.
- For request parsing, convert incoming dollar floats with `Math.round(amount * 100)` and reject inputs with more than 2 decimal places.

This probably fixes most of the bugs you've actually seen, without touching the contract.

**Step 2: add the integer field alongside the old one.**

```json
{ "amount": 19.99, "amount_cents": 1999, "currency": "usd" }
```

(Name it `amount_cents`, or `amount_minor` if you'll ever support zero-decimal or 3-decimal currencies like JPY or KWD. If multi-currency is realistic, `amount_minor` is the name that stays accurate.)

Accept `amount_cents` on requests too. If a request sends both fields, reject it when they disagree.

**Step 3: deprecate `amount`.** Document it, add a `Deprecation`/`Sunset` header, email the merchants, and watch your logs for who still sends or relies on it. Remove it only in a versioned change (`/v2`, or a dated API-version header if you want Stripe-style versioning), and only once usage has actually dropped.
