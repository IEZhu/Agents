**Short version:** vectorizing and PyPy probably won't fix this, because the time is most likely going into `lookup_customer`. That function makes one synchronous database round trip per row, which is 1.2M `SELECT`s. Remove that and the job will probably drop from ~50 min to about a minute on plain CPython, without pandas or PyPy. Measure it before you rewrite anything.

## Why I think the lookup is the bottleneck

- 50 min ÷ 1.2M rows ≈ **2.5 ms per row**. That is about the cost of one query round trip to Postgres (network + parse/plan + execute). `strip().lower()`, `float()`, `round()` and a dict `.get()` together take on the order of a microsecond per row in CPython (a rough estimate, not measured). That's around 1000× less.
- **"Crept up"** is a clue. If `customers.email` has no index, or the index doesn't match the expression, each lookup is a sequential scan. The job would then slow down as the `customers` table grows, which matches what you're seeing. Check with:
  ```sql
  EXPLAIN (ANALYZE, BUFFERS) SELECT id FROM customers WHERE email = 'someone@example.com';
  ```
  `Seq Scan` here confirms it. Even with an index scan you still pay the per-row round trip, so the fix below applies either way.
- Vectorization speeds up Python-level CPU work. PyPy's JIT does the same. Neither one reduces time spent waiting on the network.

## Fix option A: prefetch customers once (smallest change)

This keeps your structure and semantics and replaces 1.2M queries with one.

```python
import csv, io, psycopg2

conn = psycopg2.connect(DSN)

# One pass over customers, streamed with a server-side cursor so memory stays flat while fetching
customers = {}
with conn.cursor(name="cust_prefetch") as c:
    c.itersize = 50_000
    c.execute("SELECT email, id FROM customers")
    for email, cid in c:
        customers.setdefault(email, cid)   # see duplicate-email note below

country_map = COUNTRY_MAP  # local alias
buf = io.StringIO()
w = csv.writer(buf)
with open("export.csv", newline="") as f:
    for r in csv.DictReader(f):
        email = r["email"].strip().lower()
        amount = round(float(r["amount"] or 0), 2)
        country = country_map.get(r["country"], r["country"])
        w.writerow([customers.get(email), email, amount, country, r["ts"]])

buf.seek(0)
with conn.cursor() as cur:
    cur.copy_expert(
        "COPY sales (customer_id, email, amount, country, ts) FROM STDIN WITH CSV", buf
    )
conn.commit()
```

The output matches your current code byte for byte, including `None` → empty field → `NULL` under `COPY ... CSV`, so it's easy to diff old vs new output on a sample. The cost is memory. As a rough guess, a Python dict of email→id takes ~150–200 bytes per entry, so a few hundred MB for a million customers. Check your customer count.

## Fix option B: push the transform into Postgres (fastest, most scalable)

COPY the raw file into a staging table, then do the cleanup and join in one set-based statement:

```sql
CREATE TEMP TABLE sales_raw (email text, amount text, country text, ts text);
-- COPY sales_raw FROM STDIN WITH CSV HEADER   (via copy_expert, streaming the file directly)

INSERT INTO sales (customer_id, email, amount, country, ts)
SELECT c.id,
       s.email_norm,
       round(coalesce(nullif(s.amount, ''), '0')::numeric, 2),
       coalesce(m.to_code, s.country),
       s.ts::timestamptz          -- or whatever sales.ts is
FROM (SELECT *, lower(btrim(email)) AS email_norm FROM sales_raw) s
LEFT JOIN customers   c ON c.email = s.email_norm
LEFT JOIN country_map m ON m.from_code = s.country;   -- COUNTRY_MAP loaded as a small table
```

You can stream the file straight into `copy_expert`, so Python never parses rows at all. Option B does change semantics in three places:
- `btrim(x)` trims only spaces by default. Python's `strip()` also removes tabs, newlines and other Unicode whitespace.
- `round(numeric, 2)` rounds half away from zero. Python `round(float, 2)` works on the binary float value (e.g. `round(2.675, 2) == 2.67`). A few cents can differ.
- If `customers.email` is **not unique**, the join **duplicates sales rows**. Your current code silently takes an arbitrary match. Check for this first.

## If you still want the pandas version

It's fine on CPython, but it isn't what saves the time here. The main gotchas:

```python
import pandas as pd

df = pd.read_csv("export.csv", dtype=str, keep_default_na=False,
                 usecols=["email", "amount", "country", "ts"])
df["email"] = df["email"].str.strip().str.lower()
df["amount"] = pd.to_numeric(df["amount"].replace("", "0")).round(2)
df["country"] = df["country"].map(COUNTRY_MAP).fillna(df["country"])
df["customer_id"] = df["email"].map(customers).astype("Int64")   # nullable int!

buf = io.StringIO()
df.to_csv(buf, index=False, header=False,
          columns=["customer_id", "email", "amount", "country", "ts"])
```

- **`dtype=str, keep_default_na=False`** is required. Without it, pandas turns `""`, `"NA"`, `"null"` (and possibly a real country code like `"NA"` for Namibia) into NaN and guesses types for `ts`.
- **`Int64`, not `int64`/float.** An unmatched lookup creates NaN, which silently makes the column float. `COPY` then receives `"123.0"` into an integer column and fails, or worse. The nullable `Int64` writes missing values as an empty field, which becomes `NULL`.
- **Rounding:** `Series.round` uses numpy's scale-and-round-half-even, which can differ from Python's `round()` on a few edge values. Diff a sample.
- `map(...).fillna(original)` will also "restore" any key whose `COUNTRY_MAP` value is deliberately `None`, which differs from your current behavior.

## PyPy + psycopg2: I'd drop PyPy from the plan

From memory, not verified here (check the current PyPy and psycopg docs):
- **psycopg2 is a CPython C extension.** On PyPy it either runs through the `cpyext` compatibility layer, which is slow for chatty call patterns like yours, or needs a replacement such as `psycopg2cffi` or psycopg 3's pure-Python/ctypes build. Each of those is a separate dependency with its own behavior differences to test.
- **pandas/numpy on PyPy** also go through `cpyext`. They generally *lose* performance compared to CPython, so "vectorize + PyPy" pulls in opposite directions: PyPy speeds up pure-Python loops, and vectorization moves work out of Python loops.
- Once the lookup is gone, the remaining CPU work is probably well under a minute on CPython. PyPy would add operational risk (different interpreter in prod, wheel availability, a second driver) to optimize something that no longer matters.
