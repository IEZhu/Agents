Use `res.download()`. It sets `Content-Type` from the file extension and adds `Content-Disposition: attachment; filename="INV-00123.pdf"`. Before shipping it, though, you need to fix a more serious problem in this route: as written it lets anyone read any file the Node process can read.

### Why Chrome does this

- **No `Content-Disposition` header.** Without one, Chrome builds the filename from the last URL path segment. Here that segment is `/invoices/download`, so the file is saved as `download`. The query string is ignored.
- **No explicit `Content-Type`.** `res.send(buffer)` doesn't know the buffer is a PDF. It falls back to a generic type (`application/octet-stream`, as I recall; check Express's `res.send` source to confirm). That leaves the browser guessing, and it explains the odd previews. You also aren't sending `X-Content-Type-Options: nosniff`, so the browser is free to sniff the content.

### The bigger problem: path traversal and information leak

```
/invoices/download?file=../../../../etc/passwd
/invoices/download?file=../../.env
```

`path.join` resolves `..` segments, so both of these URLs escape `storage/invoices`. On top of that, the 404 response (`'Not found: ' + full`) sends your absolute server path back to the client.

There's also an authorization gap. Even with traversal fixed, any user who can guess `2024/INV-00124.pdf` can download another customer's invoice. If invoices belong to customers, check ownership before serving the file.

### Fixed route

```js
const express = require('express');
const path = require('path');

const app = express();

const INVOICE_ROOT = path.join(__dirname, 'storage', 'invoices');
// Whitelist the exact shape you generate: "YYYY/INV-NNNNN.pdf"
const INVOICE_PATH_PATTERN = /^(\d{4})\/(INV-\d{5})\.pdf$/;

app.get('/invoices/download', async (req, res, next) => {
  const requested = String(req.query.file ?? '');
  const match = INVOICE_PATH_PATTERN.exec(requested);
  if (!match) {
    return res.status(400).json({ error: { code: 'INVALID_FILE', message: 'Invalid invoice reference' } });
  }

  // Authorization: make sure this invoice belongs to the logged-in customer.
  // const allowed = await invoiceBelongsTo(req.user.id, match[2]);
  // if (!allowed) return res.status(404).end();

  const downloadName = path.basename(requested); // "INV-00123.pdf"

  res.set('X-Content-Type-Options', 'nosniff');
  res.download(requested, downloadName, { root: INVOICE_ROOT, dotfiles: 'deny' }, (err) => {
    if (!err) return;
    if (res.headersSent) return next(err); // stream failed mid-transfer; let Express close it
    if (err.code === 'ENOENT' || err.status === 404) {
      return res.status(404).json({ error: { code: 'NOT_FOUND', message: 'Invoice not found' } });
    }
    next(err);
  });
});
```

What changed:

- **`res.download(path, filename, options, callback)`** (the 4-argument form with `options` exists in Express 4.16+, recalled, so check the 4.x API docs). It sets:
  - `Content-Disposition: attachment; filename="INV-00123.pdf"`, which fixes the filename.
  - `Content-Type: application/pdf` from the `.pdf` extension, which fixes the preview.
- **`root` option**: the relative path is resolved inside `INVOICE_ROOT`. As I recall, the underlying `send` module rejects paths containing `..` with a 403 when `root` is set. Don't rely on that alone. The regex whitelist is the primary guard, because it only accepts the exact format your dashboard generates.
- **Streaming instead of `fs.readFile`**: the whole PDF is no longer buffered in memory, and you get `ETag`, `Last-Modified` and range support for free.
- **Error response**: the filesystem path is no longer included.

If you'd rather have the PDF **open in the browser tab** (with the right name if the user then saves it), use `res.sendFile` with an inline disposition:

```js
res.type('pdf');
res.set('Content-Disposition', `inline; filename="${downloadName}"`);
res.sendFile(requested, { root: INVOICE_ROOT, dotfiles: 'deny' }, callback);
```

`downloadName` is safe to put in the header here only because the regex has already limited it to `[A-Z0-9-.]`. If you ever allow arbitrary names, use `res.attachment(name)` or the `content-disposition` package. They handle quoting and RFC 5987 encoding for non-ASCII names.

### How to verify

```bash
# Expect: 200, Content-Type: application/pdf, Content-Disposition: attachment; filename="INV-00123.pdf"
curl -sI 'http://localhost:3000/invoices/download?file=2024/INV-00123.pdf'

# Expect: 400 (rejected by the whitelist), no filesystem path in the body
curl -si 'http://localhost:3000/invoices/download?file=../../package.json'
curl -si 'http://localhost:3000/invoices/download?file=2024%2F..%2F..%2F..%2Fpackage.json'

# Expect: 404 JSON, no absolute path
curl -si 'http://localhost:3000/invoices/download?file=2024/INV-99999.pdf'
```

Worth adding as regression tests (supertest): one for the headers, one for traversal returning 400, and one checking that a 404 body doesn't contain `__dirname`.

If your real filenames don't all match `YYYY/INV-NNNNN.pdf` (for example, 6-digit numbers or subfolders), loosen the regex to match your actual naming scheme. Don't drop it.
