Three of the five will cause problems tonight: #2 gives wrong numbers, #3 fails, and #4 locks the table.

**1. VARCHAR(255) → TEXT: No performance difference.**
Both use the same storage (`varlena`). The change is binary-coercible, so it doesn't rewrite the table. The only real change is that the 255-char limit is gone. If the app relies on that limit, add `CHECK (length(email) <= 255)`.

**2. `NOT IN` with a nullable subquery column: No, this is a bug.**
If even one `blacklist.customer_id` is NULL, `x NOT IN (..., NULL)` evaluates to NULL for every row, so the query returns **0**. Orders with a NULL `customer_id` are also silently excluded. Use `NOT EXISTS`:

```sql
SELECT count(*)
FROM orders o
WHERE NOT EXISTS (
  SELECT 1 FROM blacklist b WHERE b.customer_id = o.customer_id
);
```

`NOT EXISTS` is also easier to plan well: Postgres can turn it into an anti-join, but it can't do that for `NOT IN`.

**3. `CREATE INDEX CONCURRENTLY` inside a transaction: No, it will fail.**
Postgres rejects it with `ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. Mark this migration as non-transactional. From memory (check your tool's docs for the exact spelling):
- Flyway: `executeInTransaction=false`
- Alembic: `op.get_context().autocommit_block()`
- Rails: `disable_ddl_transaction!`

Make it the only statement in that migration. If it fails partway, it leaves an `INVALID` index behind. Find it with `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;`, then `DROP INDEX CONCURRENTLY` it and try again.

**4. `ADD COLUMN ... NOT NULL DEFAULT gen_random_uuid()` on 200M rows: No, this is the dangerous one.**
The PG 11 fast default only applies to **non-volatile** defaults. `gen_random_uuid()` is volatile, so Postgres rewrites the whole table while holding an `ACCESS EXCLUSIVE` lock. Nothing can read or write `events` until the rewrite finishes, which is likely many minutes to hours at 200M rows (an estimate, not measured). It also temporarily needs about double the table's disk space. Split it into steps:

```sql
-- 1. Instant: nullable column, no default
ALTER TABLE events ADD COLUMN public_id uuid;
-- 2. Instant: new rows get a value from now on
ALTER TABLE events ALTER COLUMN public_id SET DEFAULT gen_random_uuid();
-- 3. Backfill existing rows in batches (e.g. 10k–50k rows per batch, committing each one)
UPDATE events SET public_id = gen_random_uuid()
WHERE id IN (SELECT id FROM events WHERE public_id IS NULL LIMIT 10000);
-- 4. Enforce NOT NULL without a long lock
ALTER TABLE events ADD CONSTRAINT events_public_id_nn CHECK (public_id IS NOT NULL) NOT VALID;
ALTER TABLE events VALIDATE CONSTRAINT events_public_id_nn;  -- weaker lock (SHARE UPDATE EXCLUSIVE)
ALTER TABLE events ALTER COLUMN public_id SET NOT NULL;      -- PG12+ uses the validated CHECK and skips the full scan
ALTER TABLE events DROP CONSTRAINT events_public_id_nn;
```

The backfill takes time, won't fit in tonight's window, and creates a lot of WAL. Keep an eye on replica lag and autovacuum while it runs. If you need `public_id` to be unique, build that index with `CREATE UNIQUE INDEX CONCURRENTLY`. Back up or snapshot before starting, and test on staging first.

**5. `ADD COLUMN note text` (nullable, no default): Yes, it's instant.**
It only changes metadata and doesn't rewrite the table. It still needs a brief `ACCESS EXCLUSIVE` lock, though. If a long-running query is holding a lock on `orders`, the ALTER waits in line, and every query that arrives after it waits too. Put `SET lock_timeout = '5s';` in front of it, and do the same for #1 and every other DDL statement. If it times out, retry it rather than let it stall the site.
