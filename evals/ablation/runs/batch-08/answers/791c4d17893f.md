**Short answer:** No. Node 20 stopped getting security fixes when it reached end-of-life on **2026-04-30**, so you've been on an unsupported runtime for about five months. Standardize on **Node 24 LTS**, which is supported until **2028-04-30**.

I'm giving these dates from memory of the official Node.js release schedule. I didn't check them against the live source for this answer. Before they go into the planning doc, confirm them at https://nodejs.org/en/about/previous-releases or in the schedule in https://github.com/nodejs/Release. It takes a minute.

### Release status as of late Sept 2026

| Line | Status now | End of life |
|---|---|---|
| Node 20 | **EOL**, no security patches | 2026-04-30 |
| Node 22 | Maintenance LTS (security and critical fixes only) | 2027-04-30 |
| Node 24 | Active LTS, moving to Maintenance around Oct 2026 | **2028-04-30** |
| Node 26 | Current, scheduled to become LTS around Oct 2026 | ~2029-04-30 |

### Why Node 24 and not the others

- **Node 22**: it would work, but it reaches EOL in April 2027. You'd be doing this migration again in about six months.
- **Node 24**: it has had about a year of LTS hardening, so the ecosystem (Express, NestJS 10/11, native addons) has caught up. It's supported for roughly 19 more months, which covers your one-year planning window with margin.
- **Node 26**: it doesn't become LTS until late October, and early LTS releases tend to break native modules and tooling. Plan to evaluate it in H1 2027. Don't make it the target for Q4 2026.
- Node.js has discussed changing its release cadence for future majors. As far as I know that doesn't affect the 24 and 26 dates above, but I haven't confirmed it.

### Suggested wording for the doc

> **Target:** Node 24 LTS (`node:24-alpine`, pinned by digest) for all 14 API services, **completed by 2026-12-31**. Node 20 has been EOL since 2026-04-30. Node 24 is supported until 2028-04-30. Re-evaluate Node 26 LTS in Q2 2027.

### Migration notes

- **Blast radius**: changing the base image affects every service. Roll it out one service at a time behind your normal canary or rolling deploy, starting with the lowest-risk service. To roll back, redeploy the previous `node:20-alpine` image tag or digest.
- **Pin the image by digest**, not just `node:24-alpine`. That makes builds reproducible and rollback exact. Use Renovate or Dependabot to handle digest bumps.
- **Main risks**:
  - Native addons (`bcrypt`, `sharp`, and anything using `node-gyp`) need rebuilding for musl on the new ABI.
  - Node 24 ships npm 11 (I believe), which may change lockfile or `engines` behavior.
  - OpenSSL and TLS defaults changed between 20 and 24.
  - Some APIs deprecated in 20 or 22 have been removed.
- **Alpine caveat**: Node's official build tier for musl is "experimental". If a service hits odd native-module problems, `node:24-bookworm-slim` is the safer fallback.
- **CI**: set `engines.node: ">=24 <25"` in each `package.json`. Run the test suite on Node 24 before you change any Dockerfile.
