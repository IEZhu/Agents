## Latest user message
Doing a pre-deploy sanity check before tonight's release on Postgres 15. Just need quick yes/no answers with a one-line reason each, unless something is actually a problem:

1. We changed `users.email` from VARCHAR(255) to TEXT in the new schema. Any performance difference in Postgres?
2. Report query: `SELECT count(*) FROM orders WHERE customer_id NOT IN (SELECT customer_id FROM blacklist);` blacklist.customer_id is nullable. This returns orders from non-blacklisted customers, right?
3. Our migration tool wraps each migration in a transaction. One migration does `CREATE INDEX CONCURRENTLY idx_orders_created ON orders(created_at);`. Fine?
4. `ALTER TABLE events ADD COLUMN public_id uuid NOT NULL DEFAULT gen_random_uuid();` on a 200M-row table. Since PG 11 adding a column with a default is instant metadata-only, so no downtime, correct?
5. Another migration: `ALTER TABLE orders ADD COLUMN note text;` (nullable, no default) on a 50M-row table. That's instant too, right?

## Rubric (what a strong answer does)
1. Says item 4 is not instant: gen_random_uuid() is volatile, so Postgres must rewrite the whole table (holding an ACCESS EXCLUSIVE lock), and suggests a safer approach such as adding the column nullable without a default, backfilling in batches, then adding the NOT NULL constraint
2. Says item 2 is wrong if blacklist.customer_id contains any NULL (NOT IN then yields no rows / count 0) and recommends NOT EXISTS or filtering NULLs in the subquery
3. Answers item 1 (no meaningful performance difference between VARCHAR(n) and TEXT), item 5 (yes, adding a nullable column without a default is metadata-only) and item 3 (CREATE INDEX CONCURRENTLY cannot run inside a transaction block, so the migration will fail unless run outside a transaction) correctly
4. Keeps the straightforward items (1, 3, 5) short as requested and reserves the step-by-step explanation for the traps (2 and 4)

## Answer A
Three of the five will cause problems tonight: #2 gives wrong numbers, #3 fails, and #4 locks the table.

**1. VARCHAR(255) → TEXT: No performance difference.**
Both use the same storage (`varlena`). The change is binary-coercible, so it doesn't rewrite the table. The only real change is that the 255-char limit is gone. If the app relies on that limit, add `CHECK (length(email) <= 255)`.

**2. `NOT IN` with a nullable subquery column: No, this is a bug.**
If even one `blacklist.customer_id` is NULL, `x NOT IN (..., NULL)` evaluates to NULL for every row, so the query returns **0**. Orders with a NULL `customer_id` are also silently excluded. Use `NOT EXISTS`:

```sql
SELECT count(*)
FROM orders o
WHERE NOT EXISTS (
  SELECT 1 FROM blacklist b WHERE b.customer_id = o.customer_id
);
```

`NOT EXISTS` is also easier to plan well: Postgres can turn it into an anti-join, but it can't do that for `NOT IN`.

**3. `CREATE INDEX CONCURRENTLY` inside a transaction: No, it will fail.**
Postgres rejects it with `ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. Mark this migration as non-transactional. From memory (check your tool's docs for the exact spelling):
- Flyway: `executeInTransaction=false`
- Alembic: `op.get_context().autocommit_block()`
- Rails: `disable_ddl_transaction!`

Make it the only statement in that migration. If it fails partway, it leaves an `INVALID` index behind. Find it with `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;`, then `DROP INDEX CONCURRENTLY` it and try again.

**4. `ADD COLUMN ... NOT NULL DEFAULT gen_random_uuid()` on 200M rows: No, this is the dangerous one.**
The PG 11 fast default only applies to **non-volatile** defaults. `gen_random_uuid()` is volatile, so Postgres rewrites the whole table while holding an `ACCESS EXCLUSIVE` lock. Nothing can read or write `events` until the rewrite finishes, which is likely many minutes to hours at 200M rows (an estimate, not measured). It also temporarily needs about double the table's disk space. Split it into steps:

```sql
-- 1. Instant: nullable column, no default
ALTER TABLE events ADD COLUMN public_id uuid;
-- 2. Instant: new rows get a value from now on
ALTER TABLE events ALTER COLUMN public_id SET DEFAULT gen_random_uuid();
-- 3. Backfill existing rows in batches (e.g. 10k–50k rows per batch, committing each one)
UPDATE events SET public_id = gen_random_uuid()
WHERE id IN (SELECT id FROM events WHERE public_id IS NULL LIMIT 10000);
-- 4. Enforce NOT NULL without a long lock
ALTER TABLE events ADD CONSTRAINT events_public_id_nn CHECK (public_id IS NOT NULL) NOT VALID;
ALTER TABLE events VALIDATE CONSTRAINT events_public_id_nn;  -- weaker lock (SHARE UPDATE EXCLUSIVE)
ALTER TABLE events ALTER COLUMN public_id SET NOT NULL;      -- PG12+ uses the validated CHECK and skips the full scan
ALTER TABLE events DROP CONSTRAINT events_public_id_nn;
```

The backfill takes time, won't fit in tonight's window, and creates a lot of WAL. Keep an eye on replica lag and autovacuum while it runs. If you need `public_id` to be unique, build that index with `CREATE UNIQUE INDEX CONCURRENTLY`. Back up or snapshot before starting, and test on staging first.

**5. `ADD COLUMN note text` (nullable, no default): Yes, it's instant.**
It only changes metadata and doesn't rewrite the table. It still needs a brief `ACCESS EXCLUSIVE` lock, though. If a long-running query is holding a lock on `orders`, the ALTER waits in line, and every query that arrives after it waits too. Put `SET lock_timeout = '5s';` in front of it, and do the same for #1 and every other DDL statement. If it times out, retry it rather than let it stall the site.


## Answer B
Two blockers (#3, #4) and one wrong result (#2). Details below.

**1. VARCHAR(255) → TEXT: No performance difference.**
Both use the same varlena storage, so VARCHAR(n) only adds a length check. The `ALTER` is binary-coercible, so there is no table rewrite. You do lose the 255 limit, so add a `CHECK (length(email) <= 255)` if anything relied on it.

**2. `NOT IN` with a nullable subquery column: No, this is a bug.**
If even one `blacklist.customer_id` is NULL, `x NOT IN (..., NULL)` evaluates to NULL for every row, so the count is **0**. It may look correct today only because no NULLs exist yet. Use `NOT EXISTS`, which is NULL-safe and usually plans as an anti-join:

```sql
-- NULL-safe: counts orders whose customer is not blacklisted
SELECT count(*)
FROM orders o
WHERE NOT EXISTS (
  SELECT 1 FROM blacklist b WHERE b.customer_id = o.customer_id
);
```

**3. `CREATE INDEX CONCURRENTLY` inside a transaction: No, it will fail.**
Postgres rejects it with `ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`. Mark that single migration as non-transactional. The option depends on your tool, for example Flyway's `executeInTransaction=false` script config, Alembic's `autocommit_block()`, or golang-migrate's own-file approach (I'm recalling these from memory, so check your tool's docs). Also:
- If it fails partway, it leaves an `INVALID` index behind. Check with `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid;`, then `DROP INDEX CONCURRENTLY` and retry.
- Consider `CREATE INDEX CONCURRENTLY IF NOT EXISTS` so a rerun is idempotent. But an invalid leftover index will make `IF NOT EXISTS` silently skip, so do the check above.

**4. `ADD COLUMN ... DEFAULT gen_random_uuid()` on 200M rows: No, this is not instant. It is a release blocker.**
The PG 11+ fast default only works for **non-volatile** defaults, and `gen_random_uuid()` is volatile because each row needs a different value. Postgres will **rewrite the whole table under an ACCESS EXCLUSIVE lock**, so reads and writes on `events` are blocked for the whole rewrite. On 200M rows that probably means many minutes, plus about 2x the table's disk space during the rewrite. A safer sequence:

```sql
-- 1. Instant: nullable column, no default (metadata-only)
ALTER TABLE events ADD COLUMN public_id uuid;

-- 2. Instant: default applies to NEW rows only, no rewrite
ALTER TABLE events ALTER COLUMN public_id SET DEFAULT gen_random_uuid();

-- 3. Backfill existing rows in batches (run repeatedly, outside one big txn)
UPDATE events SET public_id = gen_random_uuid()
WHERE id IN (SELECT id FROM events WHERE public_id IS NULL LIMIT 10000);

-- 4. Enforce NOT NULL without a long lock
ALTER TABLE events ADD CONSTRAINT events_public_id_nn
  CHECK (public_id IS NOT NULL) NOT VALID;          -- instant
ALTER TABLE events VALIDATE CONSTRAINT events_public_id_nn;  -- scans, but allows reads/writes
ALTER TABLE events ALTER COLUMN public_id SET NOT NULL;      -- PG12+: uses the valid CHECK and skips the scan
ALTER TABLE events DROP CONSTRAINT events_public_id_nn;

-- DOWN: ALTER TABLE events DROP COLUMN public_id;
```

Trade-off: this takes more steps and the backfill creates dead tuples and WAL, so let autovacuum keep up and watch replica lag. If you need a unique index on `public_id`, build it with `CONCURRENTLY` (as a non-transactional migration, see #3). Given the timing, the simplest option is probably to pull this migration from tonight's release.

**5. `ADD COLUMN note text` (nullable, no default): Yes, it's metadata-only.**
One caveat: it still needs a brief ACCESS EXCLUSIVE lock. If a long-running query holds a lock on `orders`, the `ALTER` waits in the queue and blocks every query behind it. Set a timeout in the migration so it fails fast instead of stalling traffic:

```sql
SET lock_timeout = '5s';
ALTER TABLE orders ADD COLUMN note text;
```

The same `lock_timeout` guard applies to #1 and to steps 1, 2 and 4 of #4. Take a backup or snapshot before the release, as usual.
