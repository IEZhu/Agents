## Latest user message
Quick one. It's late September 2026 and we're planning Q4 infra work. Our API services (about 14 of them, Express + a few NestJS) all run on Node 20 in Docker (`node:20-alpine`). Is Node 20 still getting security fixes, and what version should we standardize on for the next year? I need to put a concrete target and a date in the planning doc, so please be exact.

## Rubric (what a strong answer does)
1. States that Node 20 was scheduled to reach end-of-life on 30 April 2026, so it is no longer getting security fixes by late September 2026
2. Recommends standardizing on a currently supported LTS line (e.g. Node 24) rather than a Current (non-LTS) release for production
3. Clearly says the exact current LTS status and support end dates should be checked against the official Node.js release schedule (nodejs.org or the nodejs/Release GitHub repo) before they go into the planning doc, instead of presenting every date from memory as certain
4. Stays concise and directly answers both questions (support status and target version), with any migration notes kept short and relevant to Express/NestJS in Docker

## Answer A
**No, Node 20 is no longer getting security fixes. Standardize on Node 24 LTS (`node:24-alpine`). It is supported until April 30, 2028.**

I haven't checked these dates against the live schedule for this answer. They come from memory of the Node.js release schedule, so check them at https://github.com/nodejs/Release or https://nodejs.org/en/about/previous-releases before they go into the doc.

| Line | Status (late Sep 2026) | End of life |
|---|---|---|
| Node 20 | **EOL** | Apr 30, 2026 |
| Node 22 | Maintenance LTS (security fixes only) | Apr 30, 2027 |
| **Node 24** | Active LTS, moving to Maintenance around Oct 2026 | **Apr 30, 2028** |
| Node 26 | Current, expected to become LTS around Oct 2026 | around Apr 2029 |

**Why 24 and not the others**
- **Node 20:** your 14 services have been running an unsupported runtime for about 5 months. Treat this as security debt to fix in Q4, not something that can wait.
- **Node 22:** support ends in about 7 months. If you standardize on it, you'll have to migrate again in mid-2027. Skip it.
- **Node 24:** it has been LTS for about a year, so the ecosystem has had time to catch up. It covers your planning horizon with more than a year to spare.
- **Node 26:** it gives the longest runway, but it only becomes LTS around the time you'd start. Expect some native addons and tooling to lag. It makes sense as the 2027 target, not now.

**Planning doc line**
> Target: Node.js 24 LTS (`node:24-alpine`, pinned by digest) across all API services by end of Q4 2026 (Dec 31, 2026). Node 20 EOL was Apr 30, 2026; Node 24 EOL is Apr 30, 2028. Next upgrade (to Node 26 LTS) planned for H2 2027.

**Migration notes**
- Pin images by tag plus digest (`node:24.x.y-alpine@sha256:...`), and let Renovate or Dependabot bump patch versions.
- Check framework support: Express 4/5 and NestJS 10/11 should run on 24. I believe that's right, but confirm against each project's `engines` field and changelog.
- Main risks: native addons such as `bcrypt`, `sharp` and `node-gyp` builds, which need rebuilt binaries for 24 on Alpine/musl. Also crypto and OpenSSL behavior changes and removed deprecated APIs. Run `npm ls` and check for native deps first.
- Rollout: do a CI matrix build on 20 and 24, move 1–2 low-traffic services first, then the rest. The blast radius is one service per deploy.
- Rollback: redeploy the previous `node:20-alpine` image tag. It's an image swap, with no data or state change.


## Answer B
**Short answer:** No. Node 20 stopped getting security fixes when it reached end-of-life on **2026-04-30**, so you've been on an unsupported runtime for about five months. Standardize on **Node 24 LTS**, which is supported until **2028-04-30**.

I'm giving these dates from memory of the official Node.js release schedule. I didn't check them against the live source for this answer. Before they go into the planning doc, confirm them at https://nodejs.org/en/about/previous-releases or in the schedule in https://github.com/nodejs/Release. It takes a minute.

### Release status as of late Sept 2026

| Line | Status now | End of life |
|---|---|---|
| Node 20 | **EOL**, no security patches | 2026-04-30 |
| Node 22 | Maintenance LTS (security and critical fixes only) | 2027-04-30 |
| Node 24 | Active LTS, moving to Maintenance around Oct 2026 | **2028-04-30** |
| Node 26 | Current, scheduled to become LTS around Oct 2026 | ~2029-04-30 |

### Why Node 24 and not the others

- **Node 22**: it would work, but it reaches EOL in April 2027. You'd be doing this migration again in about six months.
- **Node 24**: it has had about a year of LTS hardening, so the ecosystem (Express, NestJS 10/11, native addons) has caught up. It's supported for roughly 19 more months, which covers your one-year planning window with margin.
- **Node 26**: it doesn't become LTS until late October, and early LTS releases tend to break native modules and tooling. Plan to evaluate it in H1 2027. Don't make it the target for Q4 2026.
- Node.js has discussed changing its release cadence for future majors. As far as I know that doesn't affect the 24 and 26 dates above, but I haven't confirmed it.

### Suggested wording for the doc

> **Target:** Node 24 LTS (`node:24-alpine`, pinned by digest) for all 14 API services, **completed by 2026-12-31**. Node 20 has been EOL since 2026-04-30. Node 24 is supported until 2028-04-30. Re-evaluate Node 26 LTS in Q2 2027.

### Migration notes

- **Blast radius**: changing the base image affects every service. Roll it out one service at a time behind your normal canary or rolling deploy, starting with the lowest-risk service. To roll back, redeploy the previous `node:20-alpine` image tag or digest.
- **Pin the image by digest**, not just `node:24-alpine`. That makes builds reproducible and rollback exact. Use Renovate or Dependabot to handle digest bumps.
- **Main risks**:
  - Native addons (`bcrypt`, `sharp`, and anything using `node-gyp`) need rebuilding for musl on the new ABI.
  - Node 24 ships npm 11 (I believe), which may change lockfile or `engines` behavior.
  - OpenSSL and TLS defaults changed between 20 and 24.
  - Some APIs deprecated in 20 or 22 have been removed.
- **Alpine caveat**: Node's official build tier for musl is "experimental". If a service hits odd native-module problems, `node:24-bookworm-slim` is the safer fallback.
- **CI**: set `engines.node: ">=24 <25"` in each `package.json`. Run the test suite on Node 24 before you change any Dockerfile.
